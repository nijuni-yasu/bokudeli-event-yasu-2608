# スキル提案

今回のブランチや PR の変更を分析し、プロジェクトに追加すべきスキルを提案する。PR マージ前や、一定量の作業が溜まったタイミングで利用する想定。

## 適用場面

- **ブランチの変更分析**: development からの差分を分析し、スキル候補を検討する。skills.sh で既存スキルを検索し、利用 or 新規作成を提案する
- **PR マージ前**: code-review-doc-update と併せて実行し、新規スキルの要否を検討する

※ 変更が空の場合（差分なし）は、その旨を報告する。

## 手順

1. ブランチの変更差分を取得する

```
git diff development...HEAD --stat
git diff development...HEAD
git log development...HEAD --oneline
```

デフォルトブランチは development。リモートが基準の場合は `origin/development` に置き換える。

2. 既存スキル一覧を確認する

- AGENTS.md の Skills 一覧を参照
- .cursor/skills/ 配下の各 SKILL.md の description を読み、既存スキルの役割と重複しないか把握する

3. スキル候補を検討する

参照セクションを参照し、プロジェクト固有のルールやドメイン知識を把握した上で、以下の観点で追加すべきスキルがないか検討する。

**繰り返しパターン**
- 同じ種類の修正・リファクタリングが複数ファイルで行われていないか
- コミット履歴に同種の修正が複数含まれていないか
- 類似の手順を何度も踏んでいるワークフローはないか

**新規ドメイン・複雑な責務**
- 請求書発行、PDF 生成、外部 API 連携など、手順が多く判断が難しい領域はないか
- プロジェクト固有のルールや制約が多く、AI が誤りやすい領域はないか
- プロジェクト技術スタック（Firebase、Vue、TypeScript 等）に関連する新規領域はないか

**定型ワークフロー**
- 複数ステップの手順が決まっている作業はないか
- テンプレートやフォーマットに沿った出力が必要な作業はないか

**既存スキルとの関係**
- 既存スキルの description と照合し、重複・カバー範囲を確認する
- 既存スキルでカバーできるか、新規スキルが必要か
- 既存スキルの拡張・分割で対応できるか

4. 既存スキルを検索する（提案候補がある場合）

各提案候補について、skills.sh で類似スキルが公開されていないか検索する。

```
npx skills find [検索クエリ]
```

検索クエリは提案候補のドメイン・タスクに応じて設定する（例: 請求書 → `invoice`、PDF 生成 → `pdf`、PR レビュー → `pr review`）。プロジェクト固有のスキル（shokujii-code-review 等）は検索をスキップして新規作成を提案する。

5. 提案を出力する

提案がある場合、以下の形式で出力する。提案がない場合はその旨と理由を報告する。

## 出力形式

### 提案 1: [スキル名 または 既存スキル名]

**種別**: 既存スキルを利用 / 新規スキルを作成

スキル名は kebab-case で記述する（例: `invoice-generation`）。既存スキルの場合は検索で見つかったスキル名を記載する。

**目的**: 何を支援するスキルか（1〜2文）

**トリガー**: どのような依頼時に使うか（「〇〇して」と依頼された時に使用する、の形式）

**根拠**: この PR/ブランチのどの変更からこの提案に至ったか（ファイル・パターン・ワークフローを具体的に）

**優先度**: 高 / 中 / 低（任意）

**次のステップ**:
- **既存スキルの場合**: `npx skills add <owner/repo@skill>` でインストールし、プロジェクトに合わせて調整する。必要に応じて AGENTS.md に登録する
- **新規作成の場合**: create-skill スキル（または Cursor のスキル作成機能）を使って .cursor/skills/ に SKILL.md を作成し、AGENTS.md（および CLAUDE.md）の Skills 一覧に登録する

---

（複数提案がある場合は同形式で繰り返す。優先度の高い順に並べる）

### 提案がない場合の出力例

```
今回の変更からは新規スキル提案はありません。

理由: 既存スキルでカバー可能なため。
```

※ 理由の例: 変更が軽微で定型化の余地が小さい / 単発の修正であり繰り返しパターンに該当しない 等。いずれも具体的に記述すること。

## 参照

- [shokujii-code-review.md](../../../documents/コードレビュー/shokujii-code-review.md) を参照し、プロジェクト固有のルールやよくあるパターンを把握する
- documents/ 内の仕様書でドメイン知識を補う
- skills.sh の検索: `npx skills find [query]` で既存スキルを検索する。https://skills.sh/ でブラウズ可能

## 制約

- 既存スキルと重複する提案は避ける（既存の description と照合すること）
- 根拠は具体的な変更内容に紐づける
- 提案は検討案であり、必ずしも実装する必要はない
- 日本語で記述する

## 運用上の推奨

- PR マージ前に code-review-doc-update と併せて実行すると、レビュー規約とスキルの両方を更新できる
