# レビューコメント検討

PR でレビュー依頼した Copilot、Codex、kokufu によるレビューを全て読み込み、各コメントについて修正すべきか・修正不要かをフラットに検討し、**識別子 `RC-n` 付きの検討結果をユーザーに伝える**。さらに**同じ内容をリポジトリ内ドキュメントに追記**し、読み込み・検討・伝達・記録まで本スキルで完結させる。

## 他スキルとの役割分担

| スキル | 役割 | `pr-<番号>.md` |
|--------|------|----------------|
| **本スキル**（review-comments-evaluate） | **外部**レビュー（Copilot / Codex / kokufu）コメントの妥当性評価 | 追記（手順 4） |
| [/shokujii-code-review](../shokujii-code-review/SKILL.md) | **能動的**な差分レビュー（規約チェックリスト） | 指摘があれば追記（手順 5） |

- 同一 PR では **RC 番号を通し**で共有する（evaluate の続き番号ルールに従う）。
- 推奨フロー（目安）: shokujii-code-review → 外部 AI レビュー依頼 → 本スキルで evaluate → 修正 → review-comments-reply。
- 既存 `pr-*.md` に `🚨 修正推奨` / `❌ 未対応` 等の**旧ラベル**が残っていてもよい。**新規セッション**からは [判断結果（4区分）](#判断結果4区分プロジェクト共通) のみ使う。

## 手順

1. PR のレビューコメントを全て取得する

   **取得対象**
   - トップレベルコメント（PR 本文へのコメント）
   - インラインコメント（コード上のレビューコメント）
   - Copilot・Codex・kokufu・その他のレビュワーを区別せず全て対象とする
     - Copilot: AI レビュワー
     - Codex: AI レビュワー
     - kokufu: エンジニアのレビュワー

   **除外対象**
   - Outdated（修正済み・対応済み）のインラインコメントは読み込まない。該当コードが push 等で変更されたため、GitHub 上で「Outdated」と表示されるコメントは検討対象から除外する。API レスポンスで `position` が `null` のコメントは Outdated とみなす。
   - Outdated のコメントは評価を行わない。依頼者に対してログへの出力やコメントを行わない。Outdated の件数のみを出力する。

   **レビュー非該当（スキップ）**

   コードレビューに言及していないコメントは、Outdated と同様 **評価・RC 採番・`pr-<番号>.md` への RC 記録ブロック記載を行わない**。件数のみ報告する（チャットでは 1 行サマリ可）。

   **現時点の除外リスト（狭く始める）** — 次のいずれかに該当すればスキップする:

   1. **Codex 問題なしのみ** — 具体指摘がなく、問題なし・称賛のみのサマリ（例: `Didn't find any major issues`）。接続案内の `<details>` ボイラープレートが付いていても同様。
   2. **レビュー依頼の定型文** — `@copilot @codex review` で始まる依頼コメント（`git-create-pull-request` 手順 11 の固定文など）。
   3. **接続案内ボイラープレートのみ** — Codex / Copilot コネクタのセットアップ案内や `About Codex in GitHub` の `<details>` のみで、コード変更・設計・仕様への言及がないもの。

   **様子見（現時点ではスキップしない）**:

   - Copilot の `Pull request overview` 等、変更サマリのみのトップレベルコメント（具体指摘がなくても RC 対象とする）
   - 対応完了の返信のみのコメント
   - 上記以外で判定に迷うコメント → ユーザーに確認するか、保守的に RC 対象に含める

   **RC 番号**はスキップしたコメントを除いた残りにのみ付与する。並び順の計算もスキップ分を除いてから行う。

   **取得方法**

   - **PR URL が渡された場合**: 渡された URL を `gh pr view` の引数に渡し、その PR のコメントを取得する
   - **URL が渡されていない場合**: 現在のブランチに対応する PR を対象にする

   **PR URL が渡された場合**

   ```
   # PR 番号を取得（URL で指定した PR）
   gh pr view <URL> --json number -q '.number'

   # インラインコメントを取得（GitHub API）。Outdated を除外する場合は jq で position が null でないものを抽出
   gh api "repos/{owner}/{repo}/pulls/$(gh pr view <URL> --json number -q '.number')/comments" | jq 'map(select(.position != null))'

   # トップレベルコメントを取得
   gh pr view <URL> --comments
   ```

   **URL が渡されていない場合（現在のブランチの PR）**

   ```
   # PR 番号を取得（現在のブランチの PR）
   gh pr view --json number -q '.number'

   # インラインコメントを取得（GitHub API）。Outdated を除外する場合は jq で position が null でないものを抽出
   gh api "repos/{owner}/{repo}/pulls/$(gh pr view --json number -q '.number')/comments" | jq 'map(select(.position != null))'

   # トップレベルコメントを取得
   gh pr view --comments
   ```

   ※ `position` が `null` のコメントは、該当行が修正済みで GitHub 上で「Outdated」と表示される。これらは検討対象から除外する。
   ※ 現在のブランチに PR が紐づいていない場合は、PR 番号または URL の入力を促す
   ※ ユーザーが貼り付けたテキストを読み込む方法も可（この場合、手順 4 の記録用に **PR 番号をユーザーに確認**する。確認できないときだけ `manual-<YYYYMMDD-HHmm>.md` で記録してよい）

   **インラインコメントのメタデータ（RC 記録ブロック用）**

   `gh api "repos/{owner}/{repo}/pulls/{number}/comments"` の各要素から、RC 記録に使う:

   | フィールド | 用途 |
   |------------|------|
   | `id` | GitHub id（識別子行に併記） |
   | `user.login` | **レビュワー** |
   | `path` | **指摘箇所**のファイルパス |
   | `line` または `original_line` | **指摘箇所**の行（`line` 優先、無ければ `original_line`） |
   | `body` | **レビュワーのコメント（原文）** — 一字一句そのまま |
   | `diff_hunk` | **該当コード（レビュー時点の diff）** — 改変禁止 |

   ※ `diff_hunk` が空・未取得のインラインは、記録前に API 再取得または [該当コードの取得（共通）](#該当コードの取得共通) で補完する。補完できない場合のみ **該当コード** に `(diff_hunk 未取得)` と1行明記し、**指摘箇所**は必ず書く。

   **`diff_hunk` の補完（REST に無いコメント）**

   新規インラインが REST `GET .../pulls/{number}/comments` に出てこない場合がある（レビュー直後など）。**GraphQL** の `reviewThreads` → `comments.nodes.diffHunk` で取得する。

   ```
   gh api graphql -f query='
   query($owner: String!, $name: String!, $number: Int!) {
     repository(owner: $owner, name: $name) {
       pullRequest(number: $number) {
         reviewThreads(first: 100) {
           nodes {
             comments(first: 10) {
               nodes { databaseId path line body diffHunk }
             }
           }
         }
       }
     }
   }' -f owner=nijuniinc -f name=bokudeli-event-new -F number=<PR番号>
   ```

   ※ `databaseId` を GitHub id として識別子行に併記する。

   **検討対象の並びと識別子（RC-n）**

   - 検討結果に載せる各コメントには、後続の作業依頼で参照できるよう **`RC-1`, `RC-2`, …** 形式の識別子を付与する（**R**eview **C**omment の略）。
   - **並び順**（同一 PR 内で一貫させる）:
     1. トップレベルコメント（PR の issue コメント）を **`created_at` 昇順**
     2. 続けてインラインコメント（`position != null` のみ）を **`path` 文字列昇順**、同一 `path` 内は **`position` 昇順**（`position` が無い場合は `line` 等で安定順）
   - API で取得する場合は、**レビュー非該当を除いたうえで**上記のキーでソートし、`RC-1` から通し番号を振る。貼り付けテキストのみのときも、スキップ対象を除いた順を `RC-1` から付与してよい。
   - **同一 PR の追加評価セッション（既存 `pr-<番号>.md` がある場合）では、番号をリセットせず前セッションの最終 RC 番号の次から連番で付与する**（例: 前回が `RC-15` で終わっていれば、新セッションの新規コメントは `RC-16`, `RC-17`, … と続ける）。これにより RC 識別子は PR ごとにグローバルに一意となり、既存ドキュメントの参照（後続タスクの「`RC-3` に対応して」等）と矛盾しない。
   - インラインコメントで GitHub API の `id` が取得できている場合は、識別子行に **`RC-1（GitHub id: 123456789）`** のように併記する（トップレベルは取得方法によって `id` を付けられる場合のみ併記でよい）。

2. **RC 対象**の各コメントについて以下を検討する（レビュー非該当は手順 1 の除外リストに従いスキップ）
   - 指摘内容の妥当性（プロジェクトの規約・shokujii-code-review に照らして）
   - 修正すべきか、修正不要か
   - 修正不要の場合、その理由（誤解・プロジェクト固有の判断・過剰指摘等）

3. 検討結果をユーザーに伝える
   - **RC 対象**の各コメントについて、**RC 記録ブロック（必須8項目）** に従って結果を出力する
   - **レビュー非該当**は RC 記録ブロックを書かない。先頭で `Outdated 除外件数` と **`レビュー非該当スキップ件数`** を報告し、必要ならスキップ理由を 1 行ずつ列挙する（GitHub id・種別のみでよい）
   - **チャット**: 8項目すべて載せる。`diff_hunk` が長い場合のみ末尾 40〜80 行に省略してよい（省略時は「末尾抜粋」と明記し、ドキュメントには全文または末尾優先ルールで記載）

4. 評価内容をドキュメントに追記する（**PR 番号ごとに 1 ファイル**）

   **保存先**

   - ディレクトリ: `documents/レビューコメント/`（存在しなければ作成する）

   **ファイル名**

   - PR 番号が分かる場合: **`documents/レビューコメント/pr-<PR番号>.md`**（例: `pr-42.md`）
   - PR 番号がどうしても分からない場合のみ: **`documents/レビューコメント/manual-<YYYYMMDD-HHmm>.md`**
   - 新規に本文を組み立てるときは **[pr-xxxx_template.md](../../../documents/レビューコメント/pr-xxxx_template.md)** の見出し・ブロック順に合わせてよい（テンプレのプレースホルダを実値に置き換え、`pr-<番号>.md` として保存する）。

   **記載方針**（`pr-<番号>.md` 冒頭または評価セッションに書いてよい）

   - **レビュワーのコメント（原文）**
     - **GitHub コメント**: `body` を**一字一句そのまま**（要約禁止）。Markdown のまま掲載してよい（``` フェンスは任意。Badge 等を壊さないため）
     - **エージェント指摘**（[/shokujii-code-review](../shokujii-code-review/SKILL.md)）: チャットで出した 🚨 / 🟡 / 👌 付き指摘文をそのまま。識別子行は `（GitHub id: なし・エージェントレビュー）` 等と明記
   - **該当コード**: [該当コードの取得（共通）](#該当コードの取得共通) に従う

   **同一 PR の扱い**

   - 対象パスに**既にファイルがある場合は上書きしない**。ファイル**末尾**に水平線（`---`）を入れてから、**新しい「評価セッション」ブロックを追記**する。これにより **1 PR あたり 1 ファイル**で複数回の評価履歴を残す。
   - 既存ファイルの**冒頭付近にある通し `### RC 別対応チェックリスト`** には、新セッションで採番した RC 行を**その通しリストの末尾にも追記**する（前セッションの行は書き換えない）。冒頭の通しリストは「PR 全体の RC 一覧」として **前セッション分＋新セッション分の全 RC** が並ぶ状態を維持する。`[x]` / `[ ]` のチェック状態は**本文末尾のセッション内チェックリストと一致**させる。
   - 既存ファイルに通しチェックリストが無い（または初回の評価セッション）場合は、本セッションのチェックリストがそのまま通しリストを兼ねるため、冒頭側への追記は不要。

   **追記するブロックの構成（この順・この粒度を守る）**

   1. `## 評価セッション`（見出し）
   2. メタデータ（箇条書き）: **評価日時**（例: 2026-04-23 15:04 JST）、**ブランチ名**（`git rev-parse --abbrev-ref HEAD` 等で取得できる場合）、**PR**（URL または `#番号`）、**Outdated 除外件数**、**レビュー非該当スキップ件数**
   3. **`### RC 別対応チェックリスト`** — **この評価セッションで RC を付けたコメント** を **昇順で 1 行ずつ** 並べる（初回セッションは `RC-1` から、追加セッションは前セッションの続き番号から）。レビュー非該当はチェックリストに載せない。先頭の `[ ]` / `[x]` は **実装・運用対応が完了したか**（手元のコード・PR の状態に合わせて更新する）。
      - **👌 修正不要** / **✅ 対応済み**: 追加のコード対応が不要、または完了済みのため **`[x]`** で開始してよい。
      - **🚨 必須修正** / **🟡 修正提案**: コード修正や確認が残る場合は **`[ ]`**。対応完了後は **判断結果** を **✅ 対応済み** に更新し **`[x]`** にする（**❌ 未対応は使わない**）。
      - 各行の形式: `- [ ] **RC-n**（GitHub id: …）— 🚨 必須修正（短いメモ）` のように **識別子・id（分かる場合）・判断結果（4区分）** を含める。必要なら **括弧で対象ファイルや作業メモ**を短く付ける。
      - チャットへの伝達でも、このチェックリストをそのまま載せてよい（ドキュメントと一致させる）。
   4. 各 `RC-n` ごとに **RC 記録ブロック（必須8項目）** を、この順・この見出し名で繰り返す（末尾に `---`）。
   5. **追加セッションのとき**は、上記 1〜4 の追記が完了した後に、**ファイル冒頭の通し `### RC 別対応チェックリスト`** にも本セッションで扱った RC 行を追記する（**同一 PR の扱い**の項を参照）。冒頭の通しリストと本文末尾セッション内チェックリストで、新規追加分の `[x]` / `[ ]` 状態が一致していることを確認する。

   チャット向け出力とドキュメント追記の内容は**対応する RC ごとに一致**させる（判断結果・理由・指摘箇所・該当コード・原文が食い違わないようにする）。

## 該当コードの取得（共通）

[/shokujii-code-review](../shokujii-code-review/SKILL.md) と同一。`diff` フェンス内に貼り、**改変禁止**。

| 出典 | 取得方法 |
|------|----------|
| GitHub インライン | API の **`diff_hunk`**（REST または上記 GraphQL） |
| エージェント指摘 | `git diff origin/development...HEAD -- <path>` の該当 hunk。ベースは PR のマージ先（通常 `origin/development`） |
| 補完不可 | `(diff_hunk 未取得)` と1行明記（**指摘箇所**は必須） |

**長い diff**: 先頭1行に `…（diff 先頭省略・N 行）` を入れ、**末尾を優先して最大約 80 行**まで掲載可。

**トップレベルコメント**（インライン行なし）: `（インライン指摘なし）` と1行明記。

## 判断結果（4区分・プロジェクト共通）

[/shokujii-code-review](../shokujii-code-review/SKILL.md) と同一。**❌ 未対応は使わない**。未着手はチェックリストの **`[ ]`** と 🚨 / 🟡 で表す。

| 判断結果 | 意味 | チェックリスト |
|----------|------|----------------|
| 🚨 **必須修正** | マージ前に対応が必要（セキュリティ・バグ・データ不整合等） | 未対応 `[ ]`、完了後 **✅ 対応済み** に更新して `[x]` |
| 🟡 **修正提案** | 改善推奨（マージ必須ではない） | 同上 |
| 👌 **修正不要** | 指摘はあるが対応不要（誤解・仕様どおり・過剰指摘等） | 初めから `[x]` でよい |
| ✅ **対応済み** | コード・PR で既に解消済み | `[x]` |

**Codex / Copilot 等の評価の目安**: P1 / must / セキュリティ → 🚨 必須修正。P2 / 設計改善 → 🟡 修正提案。問題なし・誤指摘 → 👌 修正不要。手元で既に直っている → ✅ 対応済み。

## RC 記録ブロック（必須8項目）

※ Outdated のコメントは評価対象外。件数のみを出力する（例: Outdated: 5件）。
※ レビュー非該当（手順 1 の除外リスト該当）は RC を付けず、`pr-<番号>.md` に RC 記録ブロックを書かない。件数のみ（例: レビュー非該当スキップ: 2件）。
※ **判断結果**は上記 **4区分のみ**（❌ は使わない）。
※ **RC 対象**の各コメントには手順 1 の並びに従い **`RC-1`, `RC-2`, …** を付与する。後続タスクで「`RC-3` に対応して」等と依頼できるようにする。

**ドキュメント**（`documents/レビューコメント/pr-<番号>.md`）では、RC 対象ごとに **必ず** 以下の **8項目** を **この順** で記載する。**チャット**も原則同じ（`diff_hunk` のみチャットで末尾抜粋可。ドキュメントは下記ルール）。

**識別子**: `RC-1`（インラインで GitHub のコメント `id` が分かる場合は `RC-1（GitHub id: 123456789）` のように併記）

**レビュワー**: Copilot / Codex / kokufu 等を明記

**指摘箇所**: `` `path/to/file.ts:123` `` 形式（API の `path` と `line` / `original_line`）。**トップレベルコメント**（インライン行なし）の場合は `PR トップレベル` 等と明記

**該当コード（レビュー時点の diff）**:

- **インラインコメント**: GitHub API の **`diff_hunk` を改変せず**、````diff` フェンス内に貼る
- **長い `diff_hunk`**: ドキュメントでは先頭1行に `…（diff 先頭省略）` を入れ、**末尾を優先して最大約 80 行**まで掲載可
- **トップレベルコメント**: `（インライン指摘なし）` と1行明記
- **`diff_hunk` 未取得**: `(diff_hunk 未取得)` と1行明記（**指摘箇所**は省略しない）

**レビュワーのコメント（原文）**:

- **GitHub**: `body` を一字一句そのまま（要約は **コメント要約** のみ）。``` フェンスは任意
- **エージェント**: shokujii-code-review の指摘文をそのまま（🚨 / 🟡 / 👌 付き）

**コメント要約**: 指摘内容を1〜2文で簡潔に要約

**判断結果**: 🚨 必須修正 / 🟡 修正提案 / 👌 修正不要 / ✅ 対応済み

## 参照

- [shokujii-code-review.md](../shokujii-code-review/shokujii-code-review.md) を参照してプロジェクト規約に照らす（**判断結果の4区分**も shokujii-code-review と共通）
- 記録フォーマットの例: [documents/レビューコメント/pr-xxxx_template.md](../../../documents/レビューコメント/pr-xxxx_template.md)

## 制約

- レビュワー（Copilot/Codex/kokufu 等）に依らず、指摘内容の妥当性のみで判断する
- プロジェクトのコーディング規約に基づいて客観的に評価する
- `pr-<番号>.md` への追記で **指摘箇所** または **レビュワーのコメント（原文）** を省略した RC ブロックは未完成とみなし、追記前に補完する
- インラインコメントでは **該当コード（diff_hunk）** も省略しない（未取得時は `(diff_hunk 未取得)` と明記）
