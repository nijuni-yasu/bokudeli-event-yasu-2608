# 未コミット変更の分類（正本）

git-commit-workflow / git-fixup / git-squash / git-split-commit が参照する分類ルール。判断ロジックは本ファイルを正本とし、各スキルに重複記述しない。

## 適用範囲

- fixup / squash / autosquash は **現在チェックアウトしている作業ブランチ** に対してのみ行う。
- 吸収先コミットは **そのブランチの先端からたどれる範囲** に置く。`origin/development` **より手前の、ブランチ専用のコミット**にのみ吸収する。
- すでに **`origin/development` に取り込まれた履歴のコミット** を吸収先にすると、`git rebase … <吸収先>~1` が共通祖先まで遡り、**全履歴の書き換え・リモートとの大幅乖離**につながる。ユーザーが明示しない限り、そのような吸収先は **選ばない**。

**確認の目安**:

```
base=$(git merge-base HEAD origin/development)
```

各吸収先が **`base` の子孫** であることを確認する。吸収先が `base` より **development 側の過去**にしかない場合は吸収先を選び直すか **D** とする。

## 事前コマンド

```
git status
git log --oneline --name-only
git merge-base HEAD origin/development
```

## 分類一覧

| 分類                        | 条件の目安                                                                  | 次のアクション                                              |
| --------------------------- | --------------------------------------------------------------------------- | ----------------------------------------------------------- |
| **B. 新規コミット（複数）** | 責務が複数、または [doc]/[ai]/[common] を単独コミットにすべき               | **git-split-commit**                                        |
| **C. 新規コミット（1つ）**  | 過去コミットに属さない新機能・方針変更で、先端に 1 コミット足す             | **git-commit-message** → `git commit`                       |
| **D. 判断不能**             | 吸収先が複数候補で同程度、または development 側の古いコミットしか候補がない | ユーザーに確認。統合は進めない                              |
| **A0. amend**               | 吸収先が **HEAD**                                                           | `git commit --amend`（メッセージ要否で git-commit-message） |
| **A1. fixup**               | 非 HEAD、**A1-fast 合格**（レビュー追随等。メッセージはそのまま）           | **git-fixup** 手順5以降                                     |
| **A2. squash**              | 非 HEAD、**A1-full 判定で乖離**、またはユーザーが squash 明示               | **git-squash** 手順4以降                                    |

A 系は、まず各変更ファイルの吸収先コミットを特定してから A0/A1/A2 を判定する。

## 吸収先の特定

変更ファイルごとに、その変更を論理的に含むべきコミットを吸収先とする。`git log --oneline --name-only` の出力から、各ファイルが含まれるコミットを確認する。

**禁止**: `origin/development` にすでにマージ済みの過去コミットだけを吸収先にする。吸収先は **いまのブランチに載っているコミット** に絞る。

吸収先が **HEAD** の場合は fixup/squash ではなく **A0 amend** を使う。非 HEAD では `commit --amend` は使えない。

## B / C すべき典型

- **git-split-commit の単独コミット規則**に当たる変更を、過去コミットへ fixup/squash しない
  - 例: 初出の [doc]/[ai] ファイル、common スキーマの新規追加、特定ファイルの削除・廃止方針
- **そのファイルを最後に触ったコミットと無関係**な変更（別 Issue・別機能の混在。A1-full で別 Issue と判定された変更）
- **吸収先がブランチ上にない**（`git log --oneline --name-only` で当該パスが出てこない）
- **吸収先が `merge-base HEAD origin/development` より development 側だけ**
- ユーザーが **新規コミット・分割コミット**を明示した場合

## A 系に吸収してよい典型

- レビュー指摘の追随、文言・UI の微修正
- 同一 PR 内で導入したファイルの仕様書追記（ユーザーが過去の doc コミットに統合と明示した場合を含む）

## A1 判定（fixup 向きか）

A1 fixup に進む前に、**吸収先コミットごと**に判定する。デフォルトは **A1-fast**。昇格条件に該当したら **A1-full** を実行し、full でも NG なら **A2 squash** または **B/C** へ。

### A1-fast（デフォルト・必須）

**入力**（深読みしない）

- 吸収先タイトル1行: `git log -1 --format=%s <吸収先>`
- 吸収先が触ったファイル一覧: `git show --name-only --format= <吸収先>`
- 足す未コミット diff のファイル一覧と行数: `git diff --stat`

**手順**

1. [B/C すべき典型](#b--c-すべき典型) に該当しないこと
2. 吸収先が `merge-base HEAD origin/development` の子孫であること
3. **機械チェック**（下表）をすべてパスすること
4. **fast 合格条件**（下表）をすべて満たすこと
5. [coherence-lite](../../git-commit-message/references/issue-resolution.md#coherence-lite-フローa1-fast-用) を実行する（`gh` 不要）

**機械チェック**

| 観点                 | NG 例                          | NG 時の行き先   |
| -------------------- | ------------------------------ | --------------- |
| タグとパス           | `[user]` なのに `functions/` のみ | A2 または C     |
| 吸収先とのファイル関係 | ブランチ上で吸収先が一度も触っていないパス | B/C または D    |
| `#` の有無           | 吸収先タイトルに `#` が無い    | A2 squash       |
| 単独コミット規則     | 初出 [doc]/[ai]、common 新規スキーマ等 | B               |

**fast 合格条件**（すべて YES）

| #  | 条件                                                                                                                                                                      |
| -- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| F1 | 変更ファイルが、吸収先コミット（または同一 PR 内のそのコミット以降）で触ったパスと **同一トップレベル**（`user/` `partner/` `functions/` `base/` `common/` `.agents/` 等）に収まる |
| F2 | **新規ファイルなし**（`.agents/` 初出 doc/ai を除く — 該当すれば B）                                                                                                    |
| F3 | 未コミット diff が **小さい**（目安: 変更ファイル ≤ 8、追加削除合計 ≤ 300 行。超えたら A1-full へ）                                                                     |
| F4 | タイトル動詞と変更種別が **明白に矛盾しない**（「追加」なのに当該ファイルが削除のみ、等）                                                                                 |

**A1-fast OK** → **A1 fixup**（意味チェック不要）

**出力（OK 時は1行）**: `<hash>: A1-fast OK（同一スコープ・レビュー追随）`

### A1-full へ昇格（いずれかで必須）

- F3 超過（大きな diff）
- 新規ファイルあり（B 以外）
- タグとパス不一致、動詞と変更種別の矛盾
- 吸収先タイトルと変更の性質がずれそう（UI 微修正 → ロジック大変更など）
- 複数吸収先で Issue `#` が異なる
- coherence-lite でブランチ名と `#` が明らかに不一致
- ユーザーが「メッセージも直して」と示唆

### A1-full（昇格時のみ）

[issue-resolution.md coherence-full モード](../../git-commit-message/references/issue-resolution.md#coherence-full-フローa1-full-昇格時) と、次の **意味チェック** を実行する。

> 統合後のコミット全体を読んだ人が、**今のメッセージだけ** で内容を正しく理解できるか？

| 結果                         | 次                                       |
| ---------------------------- | ---------------------------------------- |
| OK                           | **A1 fixup**（メッセージそのまま）       |
| NG（メッセージ更新で足りる） | **A2 squash**                            |
| NG（別 Issue・別機能）       | **B/C**                                  |

**squash に昇格すべき典型**（A1-full NG）

- タイトルの機能説明と実装の性質が変わった
- メッセージに無い責務・ファイル種別が増えた
- 「削除」「廃止」なのにメッセージが「追加」のまま
- coherence-full NG で同一 `#` に無理に載せられない

**fixup でよい典型**（A1-fast 想定）

- typo・文言・スタイル・レビュー追随の微修正
- 同一機能のバグ修正でタイトルが修正内容と一致
- 本文の説明範囲内の追記・微調整

### ユーザー明示との関係

- ユーザーが「fixup のみ」と明示しても、A1-full 昇格条件・full NG 時は **A2 squash を優先**し、例外理由を1行示す（B の [ai]/[common] 単独規則と同様）。
- ユーザーが「squash して」と明示した場合、分類前から **A2 squash** として扱う。

## 委譲の進め方

1. ワークツリーを分類表で一覧化する
2. **B が 1 件でもある** → **git-split-commit** で分割案を出す。ユーザー承認後に B（と必要なら C）をコミットし、残った A だけで fixup/squash/amend を再開する
3. **B がなく C のみ** → **git-commit-message** でメッセージ生成し C をコミットしてから、A だけ fixup/squash/amend
4. **A のみ** → A0 / A1 / A2 に従って実行
5. **D がある** → ユーザー確認まで **停止**

**禁止**: B/C を無理に `commit --fixup` / `commit --squash` する。

## 実行順序

混在時は次の順序で実行する。

```
1. B（分割コミット）
2. C（新規1件）
3. A0 / A1 / A2（amend / fixup / squash）
```

## 出力フォーマット

```
### 分類
- A0 amend: …
- A1 fixup: …
- A2 squash: …（理由: …）
- B 分割: … → git-split-commit
- C 新規1件: … → git-commit-message
- D: … → 確認待ち

### A1 判定
- <hash>: A1-fast OK
- <hash>: A1-full OK — …
- <hash>: A2 squash へ（理由: …）
- <hash>: B/C へ（理由: …）

### イシュー（A1-full / squash / 新規コミット時のみ）
- 吸収先 #NNNN: coherence-full OK|NG
- 採用: #NNNN（full 時）

### 実行計画
1. …
2. …
```

**ユーザー確認**: **D のみ停止**。A2 squash は計画に理由を書いて **自動実行**する。
