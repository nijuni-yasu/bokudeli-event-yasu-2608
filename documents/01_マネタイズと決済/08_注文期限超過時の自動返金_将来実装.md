# 注文期限超過時の対応

## 1. 概要

### 1.1 背景・課題

現状、`createStripeCheckoutSession` には注文期限のチェックがなく、以下の問題が発生しうる。

1. 注文期限を過ぎた後でも Stripe 決済セッションを作成できてしまう
2. 注文期限直前（5〜15分前など）に決済を開始し、決済完了が注文期限を超過するケース
   - 注文期限到来時に自動送信される注文締切メール（`orderDeadlineMail`）には、まだ `in_cart` 状態のこの注文が含まれない
   - その後 Webhook で `ordered` に遷移しても、お店・主催者には伝わらない

### 1.2 今回の対応: 注文締切メール送信の5分延長

飲食店・主催者・メンバーへの注文締切メールの送信タイミングを **5分遅らせる**。伸ばすことで多少時刻を過ぎた注文にも対応する。

- **対象**: 店舗向け・主催者向け・メンバー向けの注文締切メール（`sendOrderDeadlineMailToShop`, `sendOrderDeadlineMailToOrganizers`, `sendOrderDeadlineMailToMembers`）
- **リマインダー**: 注文期限1日後のリマインダーメールは現状のまま（変更しない）

### 1.3 将来実装: 注文期限超過時の自動返金

「主催者からのキャンセル返金処理機能」ができた後に実装する。

- セッション作成時の注文期限チェック（期限切れの場合は拒否）
- Webhook 受信時の注文期限チェック（超過していた場合は自動返金）
- **ステータス**: `deadline_canceled`（期限超過）、`organizer_canceled`（主催者によるキャンセル）を新設。返金の有無に依存しない命名とする
- 期限超過時のユーザー向けモーダル表示
- 期限超過時のユーザー向け通知メール送信

### 1.4 対象ユーザー

- イベント参加者（決済を行うユーザー）
- お店・主催者・メンバー（注文締切メールの受信者）

## 2. 今回の対応: 注文締切メール送信の5分延長

### 2.1 変更内容

`pollingTask.ts` において、以下の3つのメール送信のタイミングを **注文期限の5分後** に変更する。

| メール | 現状 | 変更後 |
|:---|:---|:---|
| 店舗向け注文締切 | 注文期限の1分窓で送信 | 注文期限 + 5分の1分窓で送信 |
| 主催者向け注文締切 | 注文期限の1分窓で送信 | 注文期限 + 5分の1分窓で送信 |
| メンバー向け注文締切 | 注文期限の1分窓で送信 | 注文期限 + 5分の1分窓で送信 |
| 店舗向けリマインダー（1日後） | 注文期限 + 1日の1分窓で送信 | **変更なし** |

### 2.2 変更対象ファイル

**`functions/default/src/pollingTask.ts`**

`getAcceptingOrderEventsByTime(start, end)` は `event_deadline_datetime` が `[start, end]` に入るイベントを取得する。5分遅延させるには、時間範囲を5分前にずらして呼び出す。

```typescript
const FIVE_MINUTES_MS = 5 * 60 * 1000

// 店舗・主催者・メンバー向け: 注文期限の5分後に送信
sendOrderDeadlineMailToShop(start - FIVE_MINUTES_MS, end - FIVE_MINUTES_MS, false),
sendOrderDeadlineMailToOrganizers(start - FIVE_MINUTES_MS, end - FIVE_MINUTES_MS),
sendOrderDeadlineMailToMembers(start - FIVE_MINUTES_MS, end - FIVE_MINUTES_MS),

// リマインダー: 現状のまま（変更なし）
sendOrderDeadlineMailToShop(start + ONE_DAY_MILLIS, end + ONE_DAY_MILLIS, true),
```

### 2.3 実装タスク

- [ ] `pollingTask.ts`: `FIVE_MINUTES_MS` 定数を追加
- [ ] `pollingTask.ts`: 店舗・主催者・メンバー向けメールの呼び出しに `- FIVE_MINUTES_MS` を適用
- [ ] `pollingTask.ts`: リマインダー（`is_reminder: true`）の呼び出しは変更しない

## 3. 将来実装: 注文期限超過時の自動返金

### 3.1 実装タイミング

**主催者からのキャンセル返金処理機能** ができた後に実装する。

### 3.2 ステータス設計

`EventOrder` のステータスに `deadline_canceled` と `organizer_canceled` を追加する。主催者請求書払いやクーポンなど返金を伴わない場合もあるため、`refunded` ではなく `canceled` とする。

```typescript
// common/src/schemas/EventOrder.ts
export const EVENT_ORDER_STATUS_VALUES = ['in_cart', 'ordered', 'canceled', 'deadline_canceled', 'organizer_canceled'] as const
```

| ステータス | 意味 |
|:---|:---|
| `in_cart` | カートに入っている（未決済） |
| `ordered` | 注文完了（決済済み） |
| `canceled` | ユーザー自身の意思によるキャンセル |
| `deadline_canceled` | 注文期限超過によるシステム自動キャンセル |
| `organizer_canceled` | 主催者によるキャンセル |

#### 期限超過時の保存フィールド（`deadline_canceled`）

| フィールド | 値 | 備考 |
|:---|:---|:---|
| `status` | `'deadline_canceled'` | 新ステータス |
| `canceled_at` | `Timestamp.now().toMillis()` | キャンセル日時として記録 |
| `payment_intent` | `session.payment_intent` | Webhook の session から取得 |
| `refund_id` | `refund.id` | Stripe 返金 ID（カード決済の場合。主催者請求書・クーポン等は null の可能性） |

### 3.3 処理フロー

#### 3.3.1 正常フロー（注文期限内に決済完了）

```
ユーザーが「決済する」ボタンを押す
  → [stripe.ts] 注文期限チェック ✓
  → [stripe.ts] Stripe Checkout Session 作成
  → Stripe 決済画面に遷移
  → ユーザーが決済完了
  → [stripeWebhook.ts] checkout.session.completed 受信
  → [stripeWebhook.ts] 注文期限チェック ✓
  → order.status を 'ordered' に更新
  → [onOrderChanged] 注文完了メールを送信
  → ユーザーが success_url にリダイレクト
  → フロントで注文ステータスを監視 → 'ordered' を検知
  → 成功モーダルを表示
```

#### 3.3.2 拒否フロー（注文期限を過ぎた後にセッション作成を試行）

```
ユーザーが「決済する」ボタンを押す
  → [stripe.ts] 注文期限チェック ✗（期限超過）
  → HttpsError('failed-precondition', '注文期限を過ぎています') をスロー
  → フロントでエラーメッセージを表示
```

#### 3.3.3 自動返金フロー（決済中に注文期限を超過）

```
ユーザーが「決済する」ボタンを押す（注文期限の数分前）
  → [stripe.ts] 注文期限チェック ✓（この時点ではまだ期限内）
  → Stripe 決済画面に遷移
  → ★ 注文期限到来（決済操作中）
  → ★ pollingTask: 注文締切メール送信（5分延長により、この注文が含まれる可能性あり）
  → ユーザーが決済完了
  → [stripeWebhook.ts] checkout.session.completed 受信
  → [stripeWebhook.ts] 注文期限チェック ✗（期限超過）
  → Stripe 自動返金（stripe.refunds.create）
  → order に payment_intent, refund_id, status='deadline_canceled', canceled_at を保存
  → 注文期限超過メールをユーザーに送信
  → ユーザーが success_url にリダイレクト
  → フロントで注文ステータスを監視 → 'deadline_canceled' を検知
  → 注文期限超過モーダルを表示
```

### 3.4 変更対象ファイルと実装内容

#### 3.4.1 `functions/default/src/stripe.ts`（セッション作成時チェック）

- イベント取得後に `event_deadline_datetime` と現在時刻を比較
- 注文期限を過ぎていた場合は `HttpsError('failed-precondition')` をスロー
- `success_url` に `orderId` をクエリパラメータとして追加（フロントで注文ステータスを特定するために必要）

#### 3.4.2 `functions/default/src/stripeWebhook.ts`（自動返金）

#### 依存の追加

- `getEvent` を `./stores/event.js` から import
- `secrets` に `'SENDGRID_API_KEY'` を追加

#### 注文期限チェックの挿入位置

既存の各種チェックの後、`order.status = 'ordered'` の前に挿入する。

```
1. 冪等性チェック（既に ordered なら正常終了）     ← 既存
2. ステータス遷移チェック（in_cart 以外なら何もしない） ← 既存
3. payment_intent バリデーション               ← 既存
4. ★ 注文期限チェック（ここに挿入）              ← 新規
5. order.status = 'ordered' ...                ← 既存
```

#### 期限超過時の処理

1. `session.payment_intent`（Webhook イベントの session から直接取得）を使って `stripe.refunds.create` で全額返金
   - `order.payment_intent` はこの時点では未保存のため使用不可
   - 冪等性キー: `deadline_refund_${communityId}_${eventId}_${orderId}`
2. `order` に以下を保存:
   - `order.status = 'deadline_canceled'`
   - `order.canceled_at = Timestamp.now().toMillis()`
   - `order.payment_intent = session.payment_intent`（Stripe の payment_intent ID）
   - `order.refund_id = refund.id`（Stripe の返金 ID）
3. 注文期限超過メールをユーザーに送信
4. `res.status(200).json({ received: true })` で正常レスポンスを返す

`order.status` を `'ordered'` にしないため、`onOrderChanged` トリガーによる注文完了メールは**送信されない**。

#### 返金 API 失敗時のエラーハンドリング

- `stripe.refunds.create` が失敗した場合は `res.status(500)` を返す
- Stripe は 500 レスポンスを受け取ると自動的に Webhook をリトライする（最大数日間）
- `order` のステータスは更新せず `in_cart` のまま残す（リトライ時に再処理される）
- エラーログを出力し、必要に応じてアラートを検討

#### 3.4.3 `base/src/components/UserSuccessJoinEventDialog.vue`（モーダル）

- Stripe からのリダイレクト後、`orderId` を使って注文ドキュメントの `status` を Firestore リアルタイムリスナー（`onSnapshot`）で監視
- Webhook の処理完了前にリダイレクトされるケースがあるため、ステータスが `in_cart` の間はローディング状態を表示
- `status` の値に応じてモーダルを切り替え:
  - `'ordered'` → 既存の成功モーダルを表示
  - `'deadline_canceled'` → 注文期限超過モーダルを表示（「注文期限を過ぎたため、自動返金されました」等）
- タイムアウト処理: 一定時間（例: 30秒）経過してもステータスが `in_cart` のままの場合、「処理に時間がかかっています。注文履歴をご確認ください」等のフォールバックメッセージを表示

#### 3.4.4 `user/src/pages/u/[userId].vue`（モーダル表示ロジック）

- `success_url` に追加された `orderId` クエリパラメータを `UserSuccessJoinEventDialog` に渡す
- 既存の `isUserSuccessJoinEventDialogVisible` のロジックを調整

#### 3.4.5 注文期限超過メール（新規）

- `stripeWebhook.ts` 内で送信
- SendGrid テンプレートの新規作成が必要
- 送信先: 決済したユーザーのメールアドレス
- 内容: イベント名、返金が行われた旨、返金が反映されるまでの目安（5〜10 営業日）

### 3.5 注意事項

#### 3.5.1 注文完了メールの抑制

`onOrderChanged`（`orderCompletionMail.ts`）は `status` が `'ordered'` に変わった場合にのみ注文完了メールを送信する。期限超過時は `status` を `'deadline_canceled'` に更新するため、注文完了メールは送信されない。追加のコード変更は不要。

#### 3.5.2 Webhook とリダイレクトの非同期性

Stripe の `success_url` へのリダイレクトと Webhook の到達は非同期で、順序が保証されない。フロント側では注文ステータスを Firestore リアルタイムリスナーで監視し、Webhook の処理完了を待ってからモーダルを表示する。

#### 3.5.3 Stripe `expires_at` について

Stripe Checkout Session の `expires_at` は最短30分〜最長24時間の制約があり、短時間（10分等）には設定できない。本機能では `expires_at` は使用せず、Webhook での期限チェック + 自動返金で対応する。

#### 3.5.4 返金の反映タイミング

Stripe の返金はカード会社の処理により、ユーザーへの反映に 5〜10 営業日かかる場合がある。期限超過メールとモーダルにその旨を記載する。

#### 3.5.5 `payment_intent` の取得元

Webhook での返金処理では `order.payment_intent` ではなく `session.payment_intent`（Stripe Webhook イベントの session オブジェクトから取得）を使用する。期限超過の分岐は `order.payment_intent` への値保存より前に実行されるため、`order` からは取得できない。

#### 3.5.6 ステータスによる区別

`deadline_canceled` と `organizer_canceled` を分離しているため、フロント・管理画面で各キャンセル理由を明確に区別できる。`canceled`（ユーザー自身）、`deadline_canceled`（期限超過）、`organizer_canceled`（主催者）で表示を切り替える。
