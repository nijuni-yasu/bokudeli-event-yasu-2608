# チャット機能 画像添付

本書は `01_チャット機能_01.md`（以下「本体仕様」）の **Phase 3「画像添付」** を詳細化したものである。食事会で撮影した写真の共有を主目的とし、**画像のみ**を対象とする。PDF・Office 文書等のファイル添付、動画添付は **初期スコープ外**（動画は将来検討）。章番号・用語・データモデルは本体仕様に準拠する。

## 1. 概要

### 1.1 目的

イベント・コミュニティ・1:1 のチャットで、テキストに加えて **食事会で撮影した写真** を送受信できるようにする。当日の集合写真・料理の写真・会場の雰囲気などをアプリ内で共有し、「食事でつながる」を継続させる。

### 1.2 スコープ

- **対象は画像のみ**（インラインサムネ＋拡大表示）。PDF・Office・CSV 等のファイル添付は **user チャットでは需要が薄い**ため初期は対象外。
- **動画は初期非対応**（iPhone の HEVC/.mov 問題・トランスコード工数・帯域コスト。将来需要が明確になった段階で別途検討。§1.6）。
- **音声・その他バイナリ・実行可能形式は対象外**。
- 既存の **`chat_rooms/{roomId}/messages` サブコレクションに乗せる**（添付専用コレクションは作らない）。テキストメッセージと同一の送信・既読・送信取り消し・プレビューのフローを流用する。
- どのルーム種別（`direct` / `event` / `community`）でも共通。

### 1.3 フェーズ分割

| フェーズ | 内容 |
| --- | --- |
| **Phase 3.1** | 画像 1 枚 + 任意の本文。送信・一覧プレビュー・拡大表示・送信取り消し連携 |
| **Phase 3.2** | 1 メッセージあたり複数画像（最大 `N` 枚）、オーファン GC |

### 1.4 前提

- 本体仕様 Phase 1（イベントグループチャット）・Phase 2（送信取り消し `recallChatMessage`）が実装済みであること。
- メッセージはクライアントから Firestore へ直接 `addDoc` する現行方式（`base/src/stores/chat.ts` の `sendMessage`）を踏襲する。

### 1.5 対応形式（ホワイトリスト）

**MIME ベースのホワイトリスト**で判定する（Storage Rules は `contentType`、Firestore/クライアントは MIME 定数）。拡張子はあくまで UI の `accept` ヒントであり、認可判定には使わない。

| 形式 | MIME | 採否 | 備考 |
| --- | --- | --- | --- |
| PNG | `image/png` | ◎ | 基本 |
| JPEG | `image/jpeg` | ◎ | 基本 |
| GIF | `image/gif` | ◎ | アニメも `<img>` で再生 |
| WebP | `image/webp` | ◎ | 基本 |
| AVIF | `image/avif` | ○（任意） | 主要ブラウザ対応・低リスク。画像セットに含めてよい |
| HEIC/HEIF | `image/heic` `image/heif` | ✗ | **ブラウザが描画不可**。初期は非対応（§1.5.1） |
| SVG | `image/svg+xml` | ✗（必須除外） | **XSS の温床**。インライン描画禁止 |

**初期採用セット（確定）**

- `image/png` / `image/jpeg` / `image/gif` / `image/webp`（+任意で `image/avif`）
- 必須除外: `image/svg+xml` / HEIC / 動画・ファイル系 MIME すべて

#### 1.5.1 HEIC（iPhone）の扱い

iPhone は標準で HEIC で保存するが、**ブラウザは HEIC を描画できない**。一方、**iOS Safari の `<input type="file" accept="image/*">` 経由では多くの場合 JPEG に自動変換**される。

- クライアント検証は **「ホワイトリスト（§1.5 の MIME 定数）に一致するもの以外はすべて拒否」** とする（HEIC を名指しで弾くのではなく、**不明・空 MIME を含めてホワイトリスト外を一律拒否**）。ブラウザによっては HEIC の `File.type` が **空文字**になり、`'image/heic'` 一致での判定をすり抜けるため。NG 時はトースト `chat.error.attachment_type` を表示する。
- `uploadAlbumImage`（`base/src/utils/storage.ts`）は空 `type` を `application/octet-stream` にフォールバックするが、**チャットでは fallback させず拒否**する（ホワイトリスト判定を `contentType` 確定前に行う）。
- **実機検証必須**: iOS Safari / Android Chrome で `<input accept="image/*">` からの送信が JPEG 等に変換されることを Phase 3.1 リリース前に確認する。

### 1.6 将来検討（初期スコープ外）

**ファイル（PDF・Office・CSV 等）**

- user チャットでの需要は薄い（主催者/店舗向け資料配布は partner/manage 側の論点）。要望が出た場合に限定的に追加する。

**動画**

- 食事会の短尺動画（乾杯・雰囲気）への需要は想定されるが、**iPhone 標準の HEVC/.mov はブラウザ再生不可**のため、reliable な提供には **サーバー側トランスコード**（Cloud Functions / 外部サービス）が必要で工数・コストが大きい。
- 将来追加する場合は別仕様で、トランスコード方式・コスト上限・サイズ/長さ制限を先に決定する。best-effort の mp4/webm のみ許可は「再生できない動画が残る」UX リスクがあるため、初期は採用しない。

## 2. データモデル

### 2.1 方針: `message_type` は増やさない

`message_type`（`'user' | 'system'`）は増やさず、**`user` メッセージに optional な `attachments` 配列を追加する**。送信取り消し・未読加算・プレビューの分岐を増やさないため。

### 2.2 `ChatAttachment` スキーマ（新規・`common/src/schemas/ChatMessage.ts`）

初期スコープは **画像のみ**のため、`type` フィールドは持たない（将来動画等を追加する場合に `'image' | 'video'` 等を導入する）。

| フィールド | 型 | 必須 | 説明 |
| --- | --- | --- | --- |
| `storage_path` | string | ✓ | Storage 上のパス（§3.1）。`chat_rooms/{roomId}/` 配下のみ許可 |
| `content_type` | string | ✓ | MIME（ホワイトリスト。§1.5） |
| `file_name` | string | ✓ | 元ファイル名（画像 `alt` 用）。表示時はエスケープし、保存時にサニタイズ（§11） |
| `byte_size` | number | ✓ | バイト数（上限チェック・UI 表示） |
| `width` | number | ✓ | 画像幅（レイアウトシフト防止） |
| `height` | number | ✓ | 画像高さ（同上） |

- DbSchema / AppSchema とも snake_case。日時フィールドは持たない（メッセージの `created_at` に従う）。
- `content_type` は **Zod の enum でホワイトリスト**にする（§1.5 の初期採用セット）。
- **`ChatMessage` クラス本体への配線も必須**: `common/src/schemas/ChatMessage.ts` の `ChatMessage` クラスに `attachments?: ChatAttachment[]` のプロパティ宣言を追加し、`constructor`（`Object.assign`/個別代入）と `convertToDb`（undefined フィルタ通過）で扱えるようにする。スキーマ（Db/App）だけ更新してクラス未対応にならないよう注意する。
- **MIME ホワイトリストは `common` の定数に集約**し、Zod バリデーション・クライアントの `<input accept>`・Storage Rules の正規表現（手動ミラー）で使い回す。例:

```ts
// common/src/schemas/ChatMessage.ts（または近接ファイル）
export const CHAT_ATTACHMENT_IMAGE_MIME_TYPES = [
  'image/png',
  'image/jpeg',
  'image/gif',
  'image/webp',
  // 'image/avif', // 任意で追加
] as const
```

### 2.3 `ChatMessage`（`user`）への追加

| フィールド | 型 | 説明 |
| --- | --- | --- |
| `attachments` | `ChatAttachment[]`（optional） | 画像配列。最大 `N` 件（Phase 3.1 は 1、3.2 で `N`） |

### 2.4 `body` 必須条件の緩和

現状の `requireBodyUnlessDeleted`（`common/src/schemas/ChatMessage.ts`）は「`user` かつ未削除なら `body` 必須」である。これを次のように緩和する。

> `body` が必須なのは: `message_type === 'user'` かつ `deleted_at` 未設定 **かつ `attachments` が空または未設定** のとき

これにより「画像のみ・本文なし」と「本文 + 画像」の両方を許可する。`attachments` がある場合は `body` 省略可。

### 2.5 送信取り消し（recall）との整合

`deleted_at` 設定時は本体仕様 §4.2.11 に従い `body` を Firestore から削除するが、画像メッセージでは加えて以下を行う（§5.2）。

- `attachments` フィールドを Firestore から削除する。
- Storage 上の実ファイル（`chat_rooms/{roomId}/{messageId}/` 配下）を **物理削除**する（通信の秘密・秘匿要件）。

## 3. Storage 設計

### 3.1 パス規約

`common/src/utils/storagePaths.ts` に生成関数を追加する。

```
chat_rooms/{roomId}/{messageId}/{attachmentId}
```

```ts
export function getChatAttachmentStoragePath(roomId: string, messageId: string, attachmentId: string): string {
  return `chat_rooms/${roomId}/${messageId}/${attachmentId}`
}
```

- `roomId` を含めることで Storage Rules で `chat_rooms/{roomId}` のメンバー判定が可能。
- `messageId` 配下にまとめ、recall / アカウント削除時に **prefix 一括削除**を容易にする。
- `attachmentId` は `crypto.randomUUID()`。

### 3.2 アップロード順序とオーファン対策

メッセージはクライアント直書き込みのため、以下の順で `base/src/stores/chat.ts` の送信処理を拡張する。

1. `messageId` を **先に採番**する（`doc(getMessagesCollectionRef(roomId))` で空ドキュメント参照を作り `id` を確定）。
2. 各画像を `getChatAttachmentStoragePath(roomId, messageId, attachmentId)` へ `uploadBytes` でアップロード（`base/src/utils/storage.ts` の `uploadAlbumImage` と同様に `contentType` を明示）。
3. 全アップロード成功後、`setDoc(messageRef, { message_type: 'user', sender_user_id, body?, attachments, created_at: serverTimestamp() })` で message を作成する。
4. **ロールバック**: 3 が失敗したら 2 でアップロード済みのファイルを `deleteObject` で削除する。2 が途中失敗した場合も成功分を削除する。
5. **オーファン GC（Phase 3.2）**: 「message doc が存在しない `chat_rooms/{roomId}/{messageId}/` 配下のファイル」を回収する Scheduled Function を別途用意する。

> **代替案（Callable finalize）**: MIME 偽装防止・HEIC 変換・サムネイル生成などサーバー確定が必要になった場合は、`sendChatAttachmentMessage` のような Callable で message 作成を finalize する方式に切り替える。ただし現状はテキストもクライアント直書き込みのため、まずは「クライアントアップロード + Storage Rules 検証」で一貫性を取る。

### 3.3 画像取得（メンバー限定 read の担保）

チャット添付は **ルームメンバー限定 read**（§6.2）にする。取得方式は以下に注意する。

- `base/src/utils/storage.ts` の `convertStoragePathToURL`（`read: if true` 前提・通信なしで URL 生成）は **使用できない**。
- **`getDownloadURL` も使わない**。`getDownloadURL` が返すのは **長命のトークン付き公開 URL** で、**Security Rules を迂回**する（トークンを知る者は認証なしでアクセス可能）。メンバー限定 read（通信の秘密）を担保できないため不採用。

**採用方式（案A）: SDK の `getBytes` / `getBlob` + Object URL**

- `firebase/storage` の **`getBytes(ref)` または `getBlob(ref)`** で取得する。これらは **認証付きリクエスト**で行われ、**Storage Security Rules（§6.2 のメンバー限定 read）が強制される**。
- 取得した Blob から **`URL.createObjectURL(blob)`** で Object URL を生成し、`<img :src="objectUrl">` に表示する。
- **解放**: コンポーネント unmount / メッセージ破棄時に **`URL.revokeObjectURL`** で解放しメモリリークを防ぐ。
- 取得失敗（権限なし・削除済み）時はプレースホルダー / エラー表示にフォールバックする。
- `chat_rooms/{roomId}/` 配下専用の取得ヘルパー（`storage_path` → Blob → Object URL）を `base/src/utils/storage.ts` に追加してよい。

> **将来の代替**: 一覧での大量取得や帯域最適化が課題になった場合は、Function で **短命の署名付き URL（有効期限付き）** を発行する方式に切り替える（§3.2 の Callable finalize と合わせて検討）。`getDownloadURL` の長命トークン URL は採用しない。

## 6. セキュリティルール

### 6.1 Firestore Rules（`firestore.rules` の messages create 拡張）

現状の messages create は本文テキスト固定の `hasOnly(['message_type', 'sender_user_id', 'body', 'created_at'])` で縛られている。これを以下のように拡張する。

- `keys().hasOnly([..., 'attachments'])` に `attachments` を追加。
- **本文 or 画像添付の片方は必須**:
  - `body` ありの場合は従来の `body is string && size() > 0 && size() <= 8000`。
  - `attachments` ありの場合は `attachments is list && size() >= 1 && size() <= N`。
- `message_type == 'user'`、`sender_user_id == request.auth.uid`、`created_at == request.time`、`isChatRoomWritable(roomId)` は維持。
- Rules では配列要素の**深い**検証（`content_type` / `byte_size` / 寸法）は Web SDK の `setDoc` と相性が悪く `permission-denied` になるため、Firestore 側は「list である・枚数上限・各 `storage_path` の prefix 一致」までに留める。MIME・サイズ・寸法は **Storage Rules + クライアント（Zod）** で担保する。
- **実装メモ（RC-74/83）**: 多層防御として Rules に MIME / 数値検証を入れる案は試したが、ネストした `attachments` 配列では Web SDK 書き込みと Rules 評価が一致せず送信不能になった。**Firestore は prefix のみ**とし、RC-74/83 の深い検証は Storage + クライアント側で満たす。
- **`storage_path` の prefix 検証は Rules でも行う**。各要素の `storage_path` が `chat_rooms/{roomId}/{messageId}/` 始まりであることを文字列前方一致で検証する（最大 12 枚は添字参照 `attachments[i]` で検証。`list.map` は Web SDK `setDoc` と相性が悪く `permission-denied` になるため使わない）。例:

```javascript
function isValidChatAttachmentAt(prefix, index) {
  let attachment = request.resource.data.attachments[index];
  return attachment.storage_path is string
      && attachment.storage_path.matches('^' + prefix + '[^/]+$');
}
function isValidChatAttachmentPath(roomId, messageId) {
  let prefix = 'chat_rooms/' + roomId + '/' + messageId + '/';
  let n = request.resource.data.attachments.size();
  return n >= 1 && isValidChatAttachmentAt(prefix, 0)
      && (n < 2 || isValidChatAttachmentAt(prefix, 1))
      && (n < 3 || isValidChatAttachmentAt(prefix, 2))
      // ... attachments[3] 〜 attachments[11] まで同様（実装は firestore.rules を正本とする）
      ;
}
```
- `allow update, delete: if false` は維持（recall は Admin SDK）。

#### トラブルシュート: sandbox で画像送信が `permission-denied` になる

**症状**（2026-06-25 sandbox2604 で確認）:

- テキストのみ送信は成功（`addDoc`・`attachments` なし）。
- 画像 1 枚以上を含む送信は Firestore `setDoc` が `permission-denied`。Storage へのアップロード自体は成功し、ロールバック時の Storage DELETE が 403 になる（`storage.rules` で `delete: if false` のため。副次現象）。

**原因**: Web SDK の `setDoc` で `attachments` 配列を書き込む際、Firestore Rules の **`list.map`** および **ネストした数値型検証**（`is int` / `is number` / `> 0` 等）が評価と一致せず、`isValidChatAttachmentPath` で拒否される。

**試したが効果がなかった修正**:

1. `is int` → `is number` への変更
2. 数値型チェックを比較演算子のみに簡略化
3. `storage_path` を prefix 一致のみに簡略化（`list.map` は残したまま）

**解決策**: `list.map` をやめ、**`attachments[0]` 〜 `attachments[11]` の添字参照**で prefix 一致のみ検証（`firestore.rules` の `isValidChatAttachmentAt` / `isValidChatAttachmentPath`）。1 枚・3 枚送信で sandbox 確認済み。

**運用上の注意**: 送信失敗後に Storage に残る orphan ファイル（`chat_rooms/{roomId}/{messageId}/{uuid}`）は Console から手動削除が必要。

### 6.2 Storage Rules（`storage.rules` に chat ブロック新設）

現状 `users` / `communities` は `allow read: if true` だが、**チャット添付はルームメンバー限定 read** とする。`firestore.get` でメンバー・書き込み可否を判定する。

```text
function isChatRoomMemberStorage(roomId) {
  return request.auth != null &&
    request.auth.uid in firestore.get(/databases/(default)/documents/chat_rooms/$(roomId)).data.member_user_ids
}
function isChatRoomWritableStorage(roomId) {
  return isChatRoomMemberStorage(roomId) &&
    firestore.get(/databases/(default)/documents/chat_rooms/$(roomId)).data.is_active == true
}

// 許可 MIME（§1.5 の初期採用セット。common の定数と手動ミラー）
function isAllowedChatImageType() {
  return request.resource.contentType.matches('image/(png|jpeg|gif|webp)');
}

match /chat_rooms/{roomId}/{messageId}/{attachmentId} {
  allow read: if isChatRoomMemberStorage(roomId);
  allow create: if isChatRoomWritableStorage(roomId)
    && request.resource.size <= 10 * 1024 * 1024            // 10MB（§10-2）
    && isAllowedChatImageType();
  allow update, delete: if false;                          // 削除は Admin SDK（recall / GC）
}
```

- `update, delete: if false` のため、recall / GC のファイル削除は **Functions（Admin SDK）** が担う。
- read を `member` 限定にするため、画像取得は **`getBytes` / `getBlob` + Object URL**（§3.3）を使う。`getDownloadURL`（長命トークン URL）は Rules を迂回するため使わない。
- **MIME 偽装の限界**: `contentType` はクライアント申告値。Rules でのホワイトリストは「明らかな非対応形式の拒否」まで。厳格化が必要なら §3.2 の Callable finalize 方式（工数増）。

## 10. 決定事項

1. **対応形式**: **画像のみ**（png / jpeg / gif / webp、+任意で avif）。PDF・Office・CSV は **対象外**。動画は **初期非対応・将来検討**（§1.6）。
2. **上限値**: 1 メッセージあたり **Phase 3.1 は 1 枚**、**Phase 3.2 は最大 12 枚**（`CHAT_ATTACHMENT_MAX_COUNT`）。1 枚あたり **10MB**（要実装時確認）。表示グリッドは **モバイル 2 列 / PC（600px 以上）3 列**。
3. **read 制御**: チャット添付の Storage read を **メンバー限定**（確定）。`convertStoragePathToURL`・`getDownloadURL` は使わず、**`getBytes`/`getBlob` + Object URL**（Rules を強制する取得）で表示する（§3.3）。
4. **作成経路**: **クライアント直アップロード + 直 create**（現行テキスト送信と一貫）。Callable finalize は将来検討。
5. **サムネイル生成**: **原寸 + CSS 制御**（Functions / Extension でのサムネ生成は行わない）。
6. **アカウント削除時の画像**: **保持**（メッセージ本文と一貫）。
7. **画像 EXIF**: **当面は除去せず注意喚起のみ**（§11）。

## 11. 追加論点の決定方針（推奨採用）

以下は推奨（低工数）案を **採用方針として確定**する。

| 項目 | 決定 | 実装メモ |
| --- | --- | --- |
| 画像 EXIF / 位置情報 | **当面は除去しない（注意喚起のみ）** | 写真の GPS 等が共有されうる旨をヘルプ/送信時注記で周知。自動除去は別フェーズ |
| 画像の向き（EXIF orientation） | **CSS 既定に委ねる** | `<img>` は既定で `image-orientation: from-image` のため追加対応なし |
| `file_name` のサニタイズ | **表示エスケープ + 長さ制限** | 表示は `{{ file_name }}` / `v-text`（`v-html` 禁止）。最大長（例 255 文字）でトリム |
| HEIC（iPhone） | **明示拒否 + iOS 実機検証** | `<input accept="image/*">` 経由の JPEG 自動変換を Phase 3.1 前に実機確認（§1.5.1） |
| MIME 偽装 | **Rules ホワイトリスト + サイズ上限で許容** | マジックナンバー検証はしない |
| 大容量 GIF / 解像度 | **サイズ上限で抑制（自動リサイズなし）** | §10-2 の 10MB 上限で制御 |
| 画像の遅延読み込み | **`loading="lazy"` + `width/height` 指定** | `ChatAttachment.width/height` を使う（§2.2） |
| 既存アップロード基盤の再利用 | **`uploadAlbumImage` と同パターンに統一** | `base/src/utils/storage.ts` を踏襲。取得は `getBytes`/`getBlob` + Object URL ヘルパー（§3.3） |
| 通報・モデレーション | **message 単位で通報 → 運営が message + Storage 削除** | 本体仕様 §6.3 のモデレーションに含める |
| リテンション | **初期はなし（コスト監視で判断）** | 自動削除は導入しない |
| 送信失敗・再送 | **エラートースト + 入力保持（自動再送なし）** | アップロード途中失敗は §3.2 のロールバック。再送はユーザー操作 |
