# チャット機能

## 1. 概要

### 1.1 機能の目的

食事イベント・コミュニティ参加をきっかけに、参加者同士・たべとも同士がアプリ内で気軽にコミュニケーションできるようにする。「食事でつながる」を継続的な関係性に発展させる。

### 1.2 主要な機能

- **個人チャット（1:1）**: たべとも（同一イベント参加経験者）同士でメッセージを送受信する
- **グループチャット（イベント）**: `event.members` 全員が参加するルーム。注文完了後に「チャットで挨拶しよう」導線を表示する
- **グループチャット（コミュニティ）**: コミュニティメンバー全員が読み書き可能なルーム
- **システムメッセージ**: 「{user_name}さんがチャットに参加しました」をルーム内に表示する（プッシュ通知は行わない）
- **リアルタイム表示**: Firestore `onSnapshot` によるメッセージ同期
- **アプリ内未読管理**: ルーム一覧・未読バッジ（プッシュ通知は別仕様 `02_プッシュ通知.md`、別フェーズ）
- **送信取り消し**: 自分のメッセージを論理削除し、ルーム内に「{user_name}がメッセージを削除しました」を表示（Phase 2）

### 1.3 対象ユーザー

- ログイン済み一般ユーザー（`user` アプリ）
- イベント参加者（`event.members` に含まれるユーザー）
- コミュニティメンバー
- たべとも（`users/{userId}/friends/{friendUserId}` が存在する相手）

## 2. ねらい

### 2.1 ビジネス目標

- イベント参加後の再参加率・コミュニティ継続率の向上
- 注文完了直後の離脱を減らし、参加者同士の交流を促進する

### 2.2 ユーザー価値

- 「誰と会ったか」を思い出しやすく、次の食事会への自然な誘いができる
- イベント当日の連絡・待ち合わせをアプリ内で完結できる

### 2.3 成功指標（KPI）

- 注文完了 → イベントチャット入室率
- イベントチャット送信ユーザー率（参加者に対する割合）
- 1:1 チャット開始数 / MAU
- チャットルームあたりの平均メッセージ数

## 3. 前提条件

### 3.1 技術的前提条件

- Firebase Authentication によるユーザー認証
- Firestore リアルタイムリスナー
- `common` の Zod スキーマ、`base` / `functions/default` の store パターンに従う
- DB 操作は store 経由、`xxxRef` は `withConverter` 付き

### 3.2 ビジネス的前提条件

- **たべとも（友人）機能が実装済みであること**（別ブランチで実装中。本仕様は実装済み前提で検討する）
- たべともの Firestore フィールド名は **snake_case** に統一する（`02_友人招待機能.md` の camelCase 案は本仕様では採用しない）
- **たべとも仕様との整合（責任分界）**: たべとも機能のマージ PR 担当者が、本仕様（`01_チャット機能.md`）を正本として `02_友人招待機能.md` および実装コードのフィールド名を snake_case に揃える。チャット実装 PR とは別 PR でもよいが、**1:1 チャット（Phase 2）着手前**に完了すること
- イベント参加者は `event.members`（`status === 'ordered'` な注文から再集約されたユーザー）で定義する

## 4. 画面仕様

### 4.1 画面遷移

```
ヘッダー #navbar-icons（カートボタン横）──► /chat（チャット一覧）
  └─ ルーム詳細 /chat/:roomId

注文完了ダイアログ ──「チャットで挨拶しよう」──► イベントグループチャット（/chat/event_{...}）
イベントページ ──「イベントチャット」──► イベントグループチャット（Phase 2）
コミュニティページ ──「コミュニティチャット」──► コミュニティグループチャット（Phase 2）
たべとも一覧 / ユーザープロフィール ──「メッセージ」──► 1:1 チャット（Phase 2）
```

**Phase 1 の主導線**: ヘッダーのチャットアイコン（常時）と、注文完了ダイアログ（イベントルーム直リンク）。

**ルート（user アプリ）**

| パス | 説明 |
| --- | --- |
| `/chat` | ルーム一覧。**memberships 初回反映後**、1件以上なら先頭ルームへ **replace** 遷移（§4.1 初期表示）。0件なら §4.2.6 空状態 |
| `/chat/:roomId` | ルーム一覧 + 当該ルームのメッセージ（同一 `ChatApp` コンポーネント） |

**ルーティング方針**

- Materio 原文は単一ページ内で `activeChat` を切り替える。Shokujii では **`base/src/components/chat/ChatApp.vue` を共有**し、user 側の 2 ルートは `roomId` prop / route param の差のみとする
- **`/chat` 初期表示**
  - `chat_memberships` の初回 `onSnapshot` 反映後に判定する（`membershipsLoaded`。読み込み中は空状態を出さない）
  - ルームが **1件以上**: 先頭ルーム（§4.2.1 の並びの1件目）を **`openRoom` で即時表示**し、**`/chat/:roomId` へ replace 遷移**する（replace 完了を待たず右ペインを空白にしない）
  - ルームが **0件**: メイン領域に空状態（§4.2.6）を表示。URL は `/chat` のまま
  - 自動選択は **検索フィルタ前**の `rooms[0]`（store 順）を使う
- **`/chat/:roomId` 直リンク**: Firebase Auth 確定後（`currentUserId` 取得後）に `openRoom` する。Auth より先に `roomId` watch が走っても、ログイン完了時に再評価してルームを開く
- **ログイン必須**: 未ログイン時はログイン導線へリダイレクト
- **メンテナンスモード**: `maintenance_mode === true` のとき他画面と同様にメンテナンスページへリダイレクト（§3.3）
- **レイアウト**: user 側の `/chat` / `/chat/:roomId` で `definePage({ meta: { layoutWrapperClasses: 'layout-content-height-fixed chat-layout-stretch' } })` を指定する（`base/materio/@layouts/stores/config.ts` の `route.meta.layoutWrapperClasses` 経由）。`chat-layout-stretch` は `user/src/styles/styles.scss` で横方向 shrink-wrap を防ぐ override（**Materio 本体は変更しない**）。ページ直下は `VCard`（`elevation="2"`）で `ChatApp` を包み、**12px（sm 以上 16px）の padding** を残して見切れを防ぐ。`block-size: 100%; overflow: hidden` の flex 縦積みとし、**ページ全体の縦スクロールは禁止**する（§4.2.9）
- **サイトフッター**: `/chat` / `/chat/:roomId` では `user/src/layouts/default.vue` が `FooterType.Hidden` を設定し、SNS・リンク等のサイトフッターを非表示にする（manage のイベント編集画面と同パターン）。チャット UI がナビ直下〜ビューポート下端まで使えるようにする

**ヘッダーナビ（チャットアイコン）**

チャット一覧への **常時導線** は、左ナビのテキストリンク（`user/src/navigation/index.ts`）ではなく、**右上 `#navbar-icons` スロット**（カートボタンと同列）に置く。

| 項目 | 内容 |
| --- | --- |
| 実装ファイル | `user/src/layouts/default.vue` の `#navbar-icons` |
| 配置 | **カートアイコンの隣**（カートと `UserProfile` の間。カート左・チャット右を推奨） |
| 表示条件 | ログイン済み（`currentUser != null`）。未ログイン時は非表示 |
| アイコン | `mdiMessageOutline` 等（カートの `mdiCartOutline` と同系統の `variant="text"` + `icon` ボタン） |
| 遷移先 | `/chat` |
| 未読バッジ | `users/{uid}/chat_memberships` の `unread_count` 合計。カートの `v-badge` と同パターン（Phase 1 から表示） |
| i18n | `aria-label` 用キー例: `navigation.chat` |

**左ナビ（`navigation/index.ts`）には Phase 1 では追加しない**（ホーム / コミュニティ等のテキストリンク列と、カート横アイコンは UI 上別エリアのため）。

参考（現行カート実装）: `user/src/layouts/default.vue` の `#navbar-icons` 内 `v-badge` + `to="/cart"`。

### 4.2 UI 要素

#### 4.2.1 チャット一覧

- **データソース（リアルタイム）**: `users/{uid}/chat_memberships` の `onSnapshot`（§5.1.4）。ソート・未読・プレビュー・終了状態は membership から取得
- **表示メタデータ（名称・アイコン）**: membership には **denormalize しない**。`room_id` / `room_type` から ID を解決し、**表示時に join** する（§4.2.7 / §5.1.6）
- ルーム名: イベント名 / コミュニティ名 / 相手の表示名（join 先から取得。読込前はプレースホルダー可）
- ルームアイコン: イベントカバー / 相手アバター等（§4.2.10）
- ルーム種別（1:1 / イベント / コミュニティ）
- 最終メッセージプレビュー（`last_message_preview`）・日時（`last_message_at`）
- 未読バッジ（`unread_count`。表示は 99 超で「99+」に打ち切り）
- 並び順: `last_message_at` 降順
- **自動選択**: `/chat` 遷移時は上記並びの **先頭1件** を初期表示ルームとする（§4.1）
- **読み取り専用ルーム**: `chat_memberships.is_active === false` のとき一覧に「終了」ラベルを表示（`chat_rooms.is_active` を denormalize。§5.1.4）
- **ルーム検索**（左サイドバー）: join 済みの **`displayTitle`** でフィルタ（§5.1.6 / §5.9）。`displayTitleReady === false` の行は検索対象外

#### 4.2.2 メッセージ画面

- メッセージ一覧（自分 / 相手 / システムでスタイル分岐）
- **グループチャット（event / community）**: Materio `ChatLog` の 1:1 前提を改修する。送信者ごとに **アバター・表示名** を表示し、自分の投稿は右、他人は左に配置する
- **送信取り消し**: 自分のユーザーメッセージに 3 点リーダーメニューから「送信を取り消す」（§4.2.11）
- **取り消し済みメッセージ**: 本文吹き出しの代わりに `{user_name}がメッセージを削除しました` を中央寄せ・控えめスタイルで表示（§4.2.11）
- **システムメッセージ**: 中央寄せ・控えめなスタイル（背景色なし等）。`message_type === 'system'` で分岐。`system_event` + `system_params` から i18n 描画（§4.2.5 / §5.1.3）
- **1:1 チャット**: 相手との左右 2 者分岐（Materio ベースを流用）
- テキスト入力欄 + 送信ボタン
- 相手プロフィールへのリンク（1:1）
- **グループルーム補助 UI**: メッセージヘッダーまたはルーム上部に「このイベントの詳細を見る」リンク（イベント / コミュニティ詳細へ）。**参加者一覧は Phase 2**
- 日時表示は **`common/src/utils/datetime.ts`** の関数を使う（Materio `formatters.ts` の `Intl` / `en-US` は使わない）

**メッセージ表示 UX**

| 項目 | 仕様 |
| --- | --- |
| 末尾自動スクロール | ルーム入室時・自分の送信時は末尾へ。過去メッセージ閲覧中（上方向スクロール済み）は追従しない |
| 日付セパレータ | 「今日」「昨日」、それ以前は `YYYY/MM/DD`（`datetime.ts` 利用） |
| 時刻表示 | 24 時間表記（例: `14:30`） |
| 連投時の集約 | 同一送信者が 5 分以内に連続投稿した場合、2 件目以降はアバター・表示名を省略 |
| URL リンク化 | 既存の **`v-linkify` ディレクティブ**（`@shokujii/base/directives/linkify`）を使用。**`v-html` 禁止** |
| 一覧プレビュー（システム） | `last_message_preview` に **固定日本語**短縮文を denormalize（例: 「◯◯さんが参加しました」。§5.6）。ルーム内表示は `system_event` + i18n |

#### 4.2.7 アバター・表示名・ルーム表示メタデータ

**方針**: ユーザー名・アバター・イベント名・イベントカバーは **membership / message へ denormalize しない**。表示時に store 経由で join する（§5.1.6）。名称変更時の Trigger 同期（旧 `onChatRoomTitleSync`）は **採用しない**。

| 項目 | 仕様 |
| --- | --- |
| 表示名フィールド | `users.user_name` / `events.event_name` / コミュニティ名 |
| アバター URL | `users.user_image_url` |
| イベントカバー | `getEventCoverStoragePath(community_id, event_id)` → URL 変換（`base/src/stores/event.ts` の `coverImageUrl` と同パターン） |
| 削除ユーザー | `users.is_deleted === true` のとき「削除されたユーザー」+ デフォルトアバター |
| フォールバック | `base/src/assets/images/avatars/default_profile.jpeg` |
| コンポーネント（ユーザー） | `base/src/components/UserAvatar.vue` |
| Materio `avatarText` | **ユーザーアバターでは使用しない**。イベントカバー未設定時の **一時フォールバック** のみ可 |
| メッセージ送信者 | `sender_user_id` → `useUserStore(senderId)` → `UserAvatar`（§4.2.10.1 でプロフィールリンク。`resolveProfilePath` prop） |
| ルーム一覧・ヘッダー（event） | `room_id` パース → **軽量 event snapshot**（§5.1.6）+ カバー URL（Storage パス、read 不要） |
| ルーム一覧・ヘッダー（direct） | `room_id` から相手 UID を算出 → `useUserStore(opponentUid)`（Phase 2） |
| ルーム一覧・ヘッダー（community） | `room_id` パース → `useCommunityStore`（Phase 2） |
| 読込前 | スケルトンまたは `avatarText` プレースホルダー。join 完了後に差し替え |
| base のルーティング | **`/u/...` や `/c/...` を base にハードコードしない**。`emit` または prop で user 側に委譲（§5.9） |

#### 4.2.10 ルーム一覧・メッセージのアイコンとリンク

##### 4.2.10.1 ユーザーアイコン → マイページ遷移

| 画面 | 対象 | 遷移先 |
| --- | --- | --- |
| チャット一覧（左サイドバー） | **1:1（direct）** ルームの相手アバター | `/u/{userId}`（`user/src/router/utils.ts` の `getUserPath`） |
| メッセージ画面（`ChatLog`） | **自分以外**の送信者アバター | 同上 |

- 1:1 一覧: `avatarText(room.title)` ではなく **`UserAvatar`**（相手の `user_image_url`）を表示する（Phase 2）
- **`ChatLog`**: prop **`resolveProfilePath: (userId: string) => string`** を受け取り、自分以外の送信者アバターを `router-link` でラップ（Phase 1）。user 側が `getUserPath(userId)` を渡す
- アバターは **`router-link` でラップ**。ルーム行クリック（ルーム選択）との **`@click.stop`** でイベント分離
- **自分**の送信者アバターはリンクにしない
- **`users.is_deleted === true`**: リンク非活性または遷移先で §4.2.7 の表示
- `aria-label`: `chat.open_user_profile`（例: 「{name}のプロフィールを見る」）
- **Phase 1**: イベントグループの `ChatLog` 送信者アバターリンクのみ必須。direct 一覧は Phase 2

##### 4.2.10.2 イベントルームのアイコン（カバー画像）

- `room_type === 'event'` の **一覧・ルームヘッダー** で、イベント名イニシャル（`avatarText`）の代わりに **イベントカバー画像** を小さく表示する
- サイズ: **40px**（`VAvatar` 内 `VImg`、`cover`）
- 画像ソース: §4.2.7（Storage パスから URL 生成。**イベント doc の read は不要**）
- **フォールバック**: カバー未設定・読込失敗時は `avatarText(displayTitle)` または汎用プレースホルダー
- **クリック**: `ChatApp` / `ChatContact` は **`emit('openEvent', { communityId, eventId })`** を発火。user 側が `event.community_account` 取得後 `getEventPath(communityAccount, eventId)` へ遷移（§5.9）。join 完了前はクリック無効
- `@click.stop` でルーム選択と分離
- **コミュニティルーム**の画像化は Phase 2 コミュニティチャット着手時に別途検討

#### 4.2.11 メッセージ送信取り消し

**対象**: 自分が送信した **ユーザーメッセージ**（`message_type === 'user'` かつ `deleted_at` 未設定）のみ。

**UI**

- 自分のメッセージ付近に **3 点リーダー**（`mdi-dots-vertical` 等）。PC はホバー表示、モバイルはタップ表示等（アクセシビリティ確保）
- メニュー: 「送信を取り消す」（`chat.recall_message`）
- 確認ダイアログ後に Callable `recallChatMessage` を呼び出す（§5.6）
- **読み取り専用ルーム**（`is_active === false`）: メニュー非表示
- **取り消し期限**: Phase 2 追加仕様では **期限なし**

**取り消し後の表示**

- 元の本文吹き出しは非表示
- 同一位置に **`{name}がメッセージを削除しました`**（`chat.system_message_deleted`）。`name` は message の **`deleted_display_name`**（Callable が取り消し時に `users.user_name` をスナップショット保存。§5.1.3）
- スタイル: システムメッセージと同様（中央寄せ・控えめ）

**未読数**

- 送信取り消し時、**`unread_count` の自動減算は行わない**。ユーザーがルームを開いて `markAsRead` したタイミングで解消する

**一覧プレビュー**

- 取り消された message が最新だった場合、Functions が `last_message_*` を再計算（§5.6 `recalculateRoomLastMessage`）
- 有効な直前メッセージがない場合、プレビューは **`メッセージが削除されました`**（`chat.last_message_preview_deleted`）

**データ保持・秘匿**

- ドキュメント自体は **物理 delete しない**（`deleted_at` 等のメタデータとトゾーストーン表示のため残す）
- 取り消し時、Callable `recallChatMessage` は **`body` フィールドを Firestore から削除**する（同室メンバーが SDK で直接 read しても本文を取得できないようにする）
- `deleted_display_name` / `sender_user_id` / `created_at` 等は残す（誰がいつ取り消したかの表示用）
- Firebase Console / Admin SDK / バックアップ等、運用側からはメタデータが参照可能（監査・通報対応の範囲）

**i18n（`base/src/locales/messages/ja.ts`）**

| キー | 文言（例） |
| --- | --- |
| `chat.open_user_profile` | `{name}のプロフィールを見る` |
| `chat.recall_message` | 送信を取り消す |
| `chat.recall_confirm_title` | 送信を取り消す |
| `chat.recall_confirm_message` | このメッセージを取り消しますか？取り消し後は元に戻せません。 |
| `chat.system_message_deleted` | `{name}がメッセージを削除しました` |
| `chat.last_message_preview_deleted` | メッセージが削除されました |

#### 4.2.8 アクセシビリティ

- メッセージ一覧: `role="log"`、`aria-live="polite"`
- 送信ボタン・チャットアイコン: `aria-label`（i18n キー）
- フォーカスリングを省略しない（システムメッセージの控えめスタイルでも WCAG コントラストを満たす）

#### 4.2.9 レイアウト構造（メッセージ画面）

メッセージ画面は **3 領域の縦積み** とし、ビューポート内に収める（`ChatApp.vue`）。

| 領域 | 挙動 |
| --- | --- |
| ルームヘッダー | 上部固定（`flex-shrink: 0`） |
| メッセージ一覧 | **唯一の縦スクロール領域**（`flex-grow: 1; min-height: 0; overflow-y: auto`） |
| 送信フォーム | **画面下部固定**（`flex-shrink: 0`）。メッセージ量が増えても常に表示 |

**実装要件**

- user ページは §4.1 の `layout-content-height-fixed` を有効化する
- `ChatApp` ルートは `block-size: 100%` + `overflow: hidden` の flex 縦積み
- スクロールイベント（過去読み込み・末尾スクロール）はメッセージ一覧コンテナ **1 つ**にバインドする
- 子コンポーネント（`ChatLog`）に独自の `overflow` / `@scroll` を持たせない

#### 4.2.3 入力フィールド

- **メッセージ本文**
  - 必須
  - 最大 **2000 文字**（Zod バリデーション。Rules 側は UTF-8 バイト数で 8000 バイト上限。§5.4）
  - Phase 1 はテキストのみ（画像添付は将来対応）

**入力 UX**

| 項目 | 仕様 |
| --- | --- |
| コンポーネント | `VTextarea`（`VTextField` 単行は使わない） |
| auto-grow | 初期 1 行。入力に応じて最大 **3 行**まで自動拡張 |
| 3 行超過 | テキストエリア内でスクロール（送信欄自体は下部固定のまま） |
| Enter / Shift+Enter | PC: Enter で送信、Shift+Enter で改行。モバイル: 送信ボタンのみ（Enter は改行） |
| 送信中 | 送信ボタンをローディング状態にし、連打防止 |
| 送信ボタン配置 | 入力欄（`VTextarea`）の**右外側**（`append-inner` 内に置かない）。`mdi-send` アイコン + 「送信」ラベル |
| 下書き | ルーム単位で **メモリ内のみ**保持（永続化なし）。ルーム切替時も保持、ログアウトで破棄 |
| 読み取り専用ルーム | 入力欄非活性（`chat_memberships.is_active === false`。§4.2.6） |

#### 4.2.4 ボタン・アクション

- **チャットアイコン**（ヘッダー `#navbar-icons`。§4.1）
  - 表示条件: ログイン済み
  - アクション: `/chat` へ遷移
  - 未読合計バッジ: `chat_memberships` の `unread_count` 合計（0 のときバッジ非表示）
- **「チャットで挨拶しよう」**（注文完了ダイアログ `UserSuccessJoinEventDialog.vue`）
  - 表示条件: PayPay 等の遅延決済処理中でない（`isProcessing === false`）**かつ** 当該ユーザーの注文が `ordered` であること（`event.members` に含まれること）
  - アクション: `/chat/event_{community_id}_{event_id}` へ遷移
  - **ルーム未準備時**: `users/{uid}/chat_memberships/{roomId}` の **`onSnapshot` で作成を待つ**（最大 **10 秒**。タイムアウト時はトースト `chat.error.preparing`「準備中です。しばらくしてから再度お試しください」）。Callable ポーリングは使わない
- **「メッセージ」**（たべとも一覧・プロフィール）
  - 表示条件: ログイン済みかつたべとも関係がある
  - アクション: 1:1 チャットルームを開く（未作成なら作成）
- **送信**
  - 空文字不可、2000 文字以内
- **送信を取り消す**（自分のメッセージ・Phase 2）
  - 3 点リーダー → 確認ダイアログ → Callable `recallChatMessage`（§4.2.11）

#### 4.2.5 表示要素（システムメッセージ）

- イベント / コミュニティグループチャットにユーザーが参加したとき、ルーム内に `{user_name}さんがチャットに参加しました` を表示する
- **再参加時**（キャンセル後に再注文など）も参加のたびに 1 件追加する（`syncEventChatMember` は member 差分で新規追加 UID のみ生成。§5.6）
- **プッシュ通知は送らない**（アプリ内表示のみ）
- 作成は **Functions のみ**（`message_type: 'system'`）。クライアントからは作成不可

**保存形式（i18n 対応）**

`body` に日本語直書きせず、テンプレート化して保存する:

| フィールド | 値（例） |
| --- | --- |
| `message_type` | `'system'` |
| `system_event` | `'member_joined'` |
| `system_params` | `{ "user_name": "山田太郎" }` |
| `body` | 空文字または未設定（後方互換用。表示は `system_event` + `system_params` から i18n 描画） |

クライアントは `system_event === 'member_joined'` のとき `$t('chat.system.member_joined', { user_name })` で描画する。

**`last_message_preview`（一覧用）**

| メッセージ種別 | Functions が denormalize する内容 |
| --- | --- |
| user | 本文を truncate（言語非依存）。`deleted_at` 設定済みは §4.2.11 の短縮文 |
| system | **固定日本語**短縮文（例: `{user_name}さんが参加しました`）。Functions に locale コンテキストはないため Phase 1 は日本語固定。ルーム内の i18n 描画とは別 |

#### 4.2.6 空状態・エラー状態

| 状態 | 表示 | i18n キー（例） |
| --- | --- | --- |
| ルーム 0 件（メイン） | 「チャットはまだありません」+ 補足「イベントに参加するとチャットが利用できます。」 | `chat.empty.no_rooms` / `chat.empty.no_rooms_hint` |
| ルーム 0 件（サイドバー） | 「チャットはまだありません」（補足なし） | `chat.empty.no_rooms` |
| ルーム未選択プレースホルダ | **廃止**（`/chat` では原則表示しない。先頭ルーム自動表示 or 0件空状態） | — |
| メッセージ 0 件 | 入力欄のみ表示（空の吹き出しは出さない） | — |
| ネットワークエラー | トースト「通信エラーが発生しました。接続を確認してください。」+ 再試行ボタン | `chat.error.network` |
| 送信失敗 | トースト「送信に失敗しました。」+ 入力内容は保持 | `chat.error.send_failed` |
| 読み取り専用ルーム | 入力欄を非活性化し「このチャットは終了しています」と表示 | `chat.readonly.hint` |
| 無効 / 未参加 roomId | トースト「チャットが見つかりません」→ `/chat` へ redirect | `chat.error.room_not_found` |
| membership 不在（離脱済み） | 同上 | `chat.error.room_not_found` |

## 5. 技術仕様・データ構造設計

### 5.1 データモデル方針

**案 A: トップレベル `chat_rooms` を採用する。**

1:1 / イベント / コミュニティを統一管理し、ユーザーのルーム一覧取得を `users/{userId}/chat_memberships` で行う。

#### 5.1.1 コレクション構造（新規追加）

```
/chat_rooms/{roomId}
  /messages/{messageId}

/users/{userId}/chat_memberships/{roomId}

/users/{userId}/friends/{friendUserId}   （たべとも機能・別仕様）
```

既存構成との関係（参考: `documents/00_仕様概要/01_仕様概要.md`）:

```
/communities/{communityId}
  /events/{eventId}
    /members/{userId}
    /orders/{orderId}
  /members/{userId}

/users/{userId}
```

#### 5.1.2 `chat_rooms` ドキュメント

| フィールド | 型 | 必須 | 説明 |
| --- | --- | --- | --- |
| `id` | string | ✓ | ドキュメント ID |
| `room_type` | `'direct' \| 'event' \| 'community'` | ✓ | ルーム種別 |
| `community_id` | string | event / community 時 | コミュニティ ID |
| `event_id` | string | event 時 | イベント ID |
| `member_user_ids` | string[] | ✓ | 参加ユーザー UID 一覧（Functions で同期）。Phase 1 は配列で管理（§5.1.2 注記） |
| `direct_user_ids` | string[2] | direct 時 | 辞書順ソート済み 2 UID（重複防止） |
| `title` | string | event / community 時 | **サーバー側参考用**（Functions 作成時にイベント名等をセット可）。**クライアント一覧表示は join を正とする**（§5.1.6）。`chat_memberships` には同期しない |
| `is_active` | boolean | ✓ | `true`: 読み書き可。`false`: 読み取り専用（§5.2.2 / §5.2.3） |
| `last_message_at` | Timestamp | optional | 最終メッセージ日時（メッセージ未送信時は未設定） |
| `last_message_preview` | string | optional | 一覧プレビュー（最大 100 文字） |
| `created_at` | Timestamp | ✓ | 作成日時 |
| `updated_at` | Timestamp | ✓ | 更新日時 |

**roomId 生成ルール**

| 種別 | roomId |
| --- | --- |
| direct | `{uidA}_{uidB}`（2 UID を辞書順ソートして `_` で結合。Firebase Auth UID は `_` を含まない） |
| event | `event_{community_id}_{event_id}` |
| community | `community_{community_id}` |

**注記**

- `community_id` / `event_id` は Firestore 自動 ID（`communities/{id}` / `events/{id}`）。**URL 用の `community_account` ではない**
- 区切り文字 `_` を維持する。`community_id` / `event_id` に `_` が含まれない前提（Firestore 自動 ID は英数字のみ）
- `member_user_ids` 配列: Phase 1 は配列で管理。想定上限は `event_max_people`（default 25、スキーマ上ハードキャップなし）。**数百人規模**になった場合は `chat_rooms/{roomId}/members/{uid}` サブコレクション化を Phase 2 以降で検討

**`room_id` パース / 生成ユーティリティ（`common`）**

- 配置: `common/src/schemas/ChatRoom.ts`（または `common/src/utils/chatRoomId.ts`）に **`buildEventChatRoomId` / `parseEventChatRoomId` / `parseDirectChatRoomId` / `parseCommunityChatRoomId`** を定義
- **`parseEventChatRoomId(roomId)`**: `{ communityId, eventId } | null`。プレフィックス `event_` を除去し、残りを **最初の `_` で分割** — 前半を `community_id`、後半を `event_id` として返す（`event_{community_id}_{event_id}` の逆変換）
- **`parseDirectChatRoomId(roomId, currentUserId)`**: 相手 UID を返す（Phase 2）
- **`parseCommunityChatRoomId(roomId)`**: `{ communityId } | null`（Phase 2）
- **単体テスト必須**: build ↔ parse の往復、不正 roomId で `null`、direct の相手 UID 算出（§7.4）

#### 5.1.3 `messages` サブコレクション

| フィールド | 型 | 必須 | 説明 |
| --- | --- | --- | --- |
| `id` | string | ✓ | ドキュメント ID |
| `message_type` | `'user' \| 'system'` | ✓ | ユーザー投稿 / システム |
| `sender_user_id` | string | user 時 | 送信者 UID（system 時は未設定。Zod で optional） |
| `body` | string | user 時（未削除） | 本文（最大 2000 文字）。**論理削除後は Firestore から削除**（§4.2.11）。system 時は空または未設定 |
| `deleted_at` | Timestamp | optional | 送信取り消し日時。設定時は論理削除済み（§4.2.11） |
| `deleted_by_user_id` | string | optional | 取り消し実行 UID（通常 `sender_user_id` と一致） |
| `deleted_display_name` | string | optional | 取り消し時点の `users.user_name` スナップショット。トゾーストーン表示用（§4.2.11） |
| `system_event` | string | system 時 | テンプレート種別（例: `'member_joined'`） |
| `system_params` | map | system 時 | テンプレートパラメータ（例: `{ user_name: string }`） |
| `processed` | boolean | optional | `onChatMessageCreated` の冪等処理フラグ（Functions のみ更新） |
| `created_at` | Timestamp | ✓ | 送信日時（`serverTimestamp()`） |

#### 5.1.4 `chat_memberships`（ユーザー別インデックス）

**Per-user / リアルタイム** に必要なフィールドのみ membership に保持する。イベント名・カバー画像・相手表示名等の **表示メタデータは denormalize しない**（§5.1.6）。更新は Functions（`syncEventChatMember` / `onChatMessageCreated` / `recallChatMessage` 等）が行う。

| フィールド | 型 | 必須 | 説明 |
| --- | --- | --- | --- |
| `room_id` | string | ✓ | ルーム ID |
| `room_type` | `'direct' \| 'event' \| 'community'` | ✓ | ルーム種別 |
| `is_active` | boolean | ✓ | `chat_rooms.is_active` と同期。`false` のとき一覧に「終了」表示・入力非活性（default `true`） |
| `unread_count` | number | ✓ | 未読数（default 0。0 以上。表示は 99 超で「99+」） |
| `last_read_at` | Timestamp | optional | 最終既読日時 |
| `last_message_at` | Timestamp | optional | 一覧ソート用 |
| `last_message_preview` | string | optional | 一覧プレビュー（最大 100 文字） |
| `created_at` | Timestamp | ✓ | 作成日時 |
| `updated_at` | Timestamp | ✓ | 更新日時 |

**`title` フィールドは持たない**（イベント名・相手名等は join で表示。§5.1.6）。開発中の既存 doc に `title` が残っていても **スキーマから削除**し、データは **削除してよい**（§5.1.6「開発データ」）。

**離脱時の扱い**: ユーザーがルームから外れたとき、当該ユーザーの **`chat_memberships/{roomId}` ドキュメントを削除**する。メッセージ履歴は `chat_rooms/{roomId}/messages` に残すが、Security Rules により当該ユーザーは読み書き不可となる。

#### 5.1.5 Zod スキーマ定義

- 配置: `common/src/schemas/ChatRoom.ts`, `common/src/schemas/ChatMessage.ts`, `common/src/schemas/ChatMembership.ts`
- DbSchema: 日時は `TimestampSchema`
- AppSchema: 日時は `EpochMillisSchema`
- フィールド名は snake_case
- `ChatRoom`: `is_active`（default `true`）を含む
- `ChatMembership`: `is_active`（default `true`）を含む。**`title` フィールドはスキーマに含めない**（DbSchema / AppSchema / クラス / `toFirestore` すべてから削除）
- `ChatMessage`: **`message_type` による discriminated union**（`z.discriminatedUnion('message_type', [...])`）
  - `user`: `sender_user_id` 必須。`body` は **未削除時のみ必須**（`deleted_at` 設定済みの場合は optional で Firestore に保存しない）。`deleted_at` / `deleted_by_user_id` / `deleted_display_name` は optional
  - `system`: `system_event`, `system_params` 必須。`body` は空または未設定
- `processed`: DbSchema のみ（Functions 内部用）。**AppSchema には含めない**（クライアントに露出しない）

#### 5.1.6 一覧表示メタデータの join（denormalize 方針）

| データ | membership 冗長化 | 取得方法 |
| --- | --- | --- |
| `unread_count` / `last_read_at` | **する** | membership（ユーザーごとに異なる） |
| `last_message_at` / `last_message_preview` | **する** | membership + Trigger 更新（一覧ソート・リアルタイムプレビュー） |
| `is_active` | **する** | membership（`chat_rooms` 追加 read なしで終了判定） |
| イベント名 | **しない** | `parseEventChatRoomId` → **軽量 event snapshot**（下記） |
| イベントカバー | **しない** | `getEventCoverStoragePath(community_id, event_id)` → URL（**イベント doc の read 不要**） |
| コミュニティ名・アイコン | **しない** | `parseCommunityChatRoomId` → `useCommunityStore`（Phase 2） |
| 1:1 相手名・アバター | **しない** | `parseDirectChatRoomId` → `useUserStore`（Phase 2） |
| メッセージ送信者名・アバター | **しない** | `sender_user_id` → `useUserStore`（§4.2.7） |

**イベント join（軽量 snapshot）**

- **collectionGroup クエリは使わない**。`communities/{communityId}/events/{eventId}` への **DocumentReference 直 read** または **単一 doc の `onSnapshot`**
- 取得フィールドは **`event_name` のみ**（将来 `event_cover_image_path` 等を足す場合は最小限に留める）
- 既存 `useEventStore` が重い場合は、チャット一覧専用の **軽量 composable / store** を base に追加してよい
- 同一 `(communityId, eventId)` は **キャッシュ共有**（ルーム数に比例する重複 read を避ける）

**UI 表示モデル（`ChatRoomListItem`）**

| フィールド | 説明 |
| --- | --- |
| `displayTitle` | join 済みの表示名（イベント名 / 相手名等）。未 join 時は空文字 |
| `displayTitleReady` | join 完了フラグ。`false` の間はスケルトン / プレースホルダー |
| `coverImageUrl` | イベントカバー URL（event のみ。未設定時は `undefined`） |

- **一覧検索**（左サイドバー）: `displayTitleReady === true` の行のみ、`displayTitle` で部分一致フィルタ

**`onChatRoomTitleSync` は採用しない**。イベント名・コミュニティ名・カバー変更は join 先の snapshot / store が更新されれば UI が追従する。

**開発データ（`title` 削除）**

- チャット機能は **開発中** のため、`chat_memberships` に **`title` フィールドを持たない** スキーマを正とする
- 既存 Firestore doc に `title` が含まれていても **後方互換は行わない**（optional 化もしない）。**`users/*/chat_memberships/*` を削除**して再生成する
- Functions（`syncEventChatMember` 等）は membership 作成時に **`title` を書き込まない**
- 表示は **`ChatRoomListItem.displayTitle`**（join 結果）のみ。`membership.title` を read するコードは **実装しない**

### 5.2 ルーム種別ごとの仕様

#### 5.2.1 個人チャット（direct）

- **参加条件**: `users/{uid}/friends/{friendUserId}` が存在する（たべとも関係）
- **読み書き**: 双方のみ
- **開始**: Callable Function `openDirectChat` で友人関係をサーバー側検証し、room + memberships を作成（既存なら取得）。**Transaction で atomic に実行**（§5.6）
- **title**: `chat_rooms.title` は未設定。一覧・ヘッダーの相手名・アバターは `room_id` から相手 UID を算出し **`useUserStore` で join**（§5.1.6）

#### 5.2.2 グループチャット（event）

- **参加条件**: `event.members` に含まれるユーザー（`recalcEventMembers` により `status === 'ordered'` な注文から再集約）
- **読み書き**: `event.members` 全員
- **参加タイミング**: 注文確定後、`event.members` に追加されたとき（`applyOrderConfirmedSideEffects` 連携）
- **離脱タイミング**: 注文キャンセル等で `event.members` から外れたとき（`applyOrderCanceledSideEffects` 連携）
- **離脱時**: `member_user_ids` から除外し、当該ユーザーの `chat_memberships` を **削除**
- **システムメッセージ**: 参加のたびに `{user_name}さんがチャットに参加しました`（プッシュなし。再参加時も同様。member 差分のみ生成）
- **注文完了導線**: `UserSuccessJoinEventDialog.vue` に「チャットで挨拶しよう」ボタン
- **読み取り専用化**: イベントが `event_canceled` または `is_deleted === true` になったとき、ルームの `is_active` を `false` に更新する（§5.6）。全メンバーの `chat_memberships.is_active` も同期。履歴は閲覧可・新規投稿不可。一覧に「終了」表示
- **archive の主トリガー**: lazy 作成前提では **`is_deleted === true`（論理削除）が主**。`cancelEvent` は Phase 1 で参加者ゼロのイベントのみキャンセル可のため、チャットルーム未作成のケースが多い
- **既存データ**: リリース時に **条件を満たすイベントのみ** 初回マイグレーション（§6.1）。それ以外は lazy 作成。過去全件は **UX・プライバシー上の理由で対象外**（§6.1）

#### 5.2.3 グループチャット（community）

- **参加条件**: `communities/{communityId}/members/{userId}` が存在する
- **読み書き**: コミュニティメンバー全員（管理者・一般メンバー問わず）
- **参加タイミング**: コミュニティ参加時
- **離脱タイミング**: コミュニティ退会時
- **離脱時**: `member_user_ids` から除外し、当該ユーザーの `chat_memberships` を **削除**
- **システムメッセージ**: 参加のたびに `{user_name}さんがチャットに参加しました`（プッシュなし）
- **読み取り専用化**: コミュニティ解散（将来実装）時に `is_active` を `false` に更新（`chat_rooms` + 全 `chat_memberships`）

### 5.3 Firestore フロントエンド処理

- **ルーム一覧**: `users/{uid}/chat_memberships` を `last_message_at` 降順で `onSnapshot`（§5.1.4 の Per-user フィールド）。**名称・アイコンは join**（§5.1.6 / §4.2.10）。Phase 1 はページングなし
- **ルーム一覧検索**: `ChatLeftSidebarContent` 等で **`displayTitle`** による部分一致（§5.1.6）。`displayTitleReady === false` は対象外
- **ルーム表示メタデータ**: `ChatContact` / ルームヘッダーで `room_type` に応じて event snapshot / user / community store を参照。join 完了前はプレースホルダー表示可
- **メッセージ取得（ページネーション + リアルタイム）**:
  1. **初回**: `orderBy('created_at', 'desc').limit(50)` で取得 → UI 表示用に **昇順に reverse**
  2. **リアルタイム**: 同一クエリ（`limit(50)`）の `onSnapshot` で最新 50 件を維持。新着は末尾にマージ
  3. **過去読み込み**: 上方向スクロールで `startAfter(最古ドキュメント).limit(50)` を **getDocs**（追加 snapshot は張らない）
  4. **マージ規則**: `messageId` で重複排除。昇順ソートを維持。store の `mergeMessages(existing, incoming)` で統一（§5.9）
- **無効 roomId**: membership が存在しない / Rules で read 不可 → §4.2.6 のエラー処理
- **送信**: store 経由で `messages` へ追加。`created_at` は **`FieldValue.serverTimestamp()`** を使用。Security Rules で制限
- **既読モデル**:
  - ルーム入室時: `markAsRead(roomId)` で `unread_count: 0`、`last_read_at` / `updated_at` を `serverTimestamp()` で更新
  - 表示中ルームに新着到着時: **即座に `markAsRead`**（Trigger の未読加算を相殺）
  - バックグラウンドタブ / 別ルーム表示中: 既読化しない
- **表示中ルームの未読バッジ抑制**: **`markAsRead` による即既読化を正**とする。ヘッダー未読合計は membership の `unread_count` 合計をそのまま表示（即既読化で自然に 0 になる）
- **読み取り専用判定**: `chat_memberships.is_active === false` で入力非活性（`chat_rooms` の追加 read 不要）
- **送信者表示名・アバター**: `sender_user_id` から `useUserStore` 等で解決（§4.2.7 / §4.2.10.1）
- **送信取り消し**: Callable `recallChatMessage` 経由のみ（クライアントから message の update / delete 不可。§5.4）
- **リスナー管理**: 同時 `onSnapshot` は **一覧 1 + アクティブルーム メッセージ 1** のみ（§5.9）。イベント join 用 store は既存キャッシュを利用し、ルーム数に比例する追加 snapshot は最小化する

### 5.4 Firestore セキュリティルール

`firestore.rules` に以下を追加する（Phase 1 必須）。`chat_memberships` / `friends` は **既存の `match /users/{user_id}` ブロック内** にネストする（トップレベルに重複定義しない）。

```javascript
// トップレベルに追加
function isChatRoomMember(roomId) {
  return request.auth != null
    && request.auth.uid in get(/databases/$(database)/documents/chat_rooms/$(roomId)).data.member_user_ids;
}

function isChatRoomWritable(roomId) {
  return isChatRoomMember(roomId)
    && get(/databases/$(database)/documents/chat_rooms/$(roomId)).data.is_active == true;
}

function chatMembershipUpdateAllowed() {
  return request.resource.data.diff(resource.data).affectedKeys()
      .hasOnly(['last_read_at', 'unread_count', 'updated_at'])
    && request.resource.data.unread_count == 0
    && request.resource.data.updated_at == request.time;
}

match /chat_rooms/{roomId} {
  allow read: if isChatRoomMember(roomId);
  allow create, update, delete: if false;

  match /messages/{messageId} {
    allow read: if isChatRoomMember(roomId);
    allow create: if isChatRoomWritable(roomId)
                  && request.resource.data.message_type == 'user'
                  && request.resource.data.sender_user_id == request.auth.uid
                  && request.resource.data.body is string
                  && request.resource.data.body.size() > 0
                  && request.resource.data.body.size() <= 8000
                  && request.resource.data.created_at == request.time;
    allow update, delete: if false;
  }
}

// 既存 match /users/{user_id} { ... } の内部に追加
match /users/{user_id} {
  // ... 既存 allow read / create / update ...

  match /chat_memberships/{roomId} {
    allow read: if request.auth != null && request.auth.uid == user_id;
    allow create, delete: if false;
    allow update: if request.auth != null
                  && request.auth.uid == user_id
                  && chatMembershipUpdateAllowed();
  }
  match /friends/{friendUserId} {
    allow read: if request.auth != null && request.auth.uid == user_id;
    allow write: if false;
  }
}
```

**補足**

- `message_type: 'system'` の messages は **Functions のみ** 作成可能（Admin SDK は Rules を bypass）
- `body.size()` は **UTF-8 バイト数**。上限 8000 バイトは Zod の 2000 **文字**上限と整合（日本語 3 バイト/文字想定）
- `created_at == request.time` でクライアントのタイムスタンプ偽装を防止。送信側は `serverTimestamp()` を使用
- `chat_memberships.update` は **既読化のみ**（`unread_count == 0`、`updated_at == request.time`）。`last_read_at` は `serverTimestamp()` 使用を推奨
- `chat_memberships` / `friends` の **create / delete は Functions（Admin SDK）のみ**。ユーザー自身のルーム退出 UX は Phase 3 で検討
- `isChatRoomMember` / `isChatRoomWritable` はメッセージ read / create ごとに `chat_rooms` を `get` する（Rules 評価コストに注意）。Phase 1 は許容し、超大規模イベント時に subcollection 化等を検討
- `messages` の **update / delete はクライアント不可**（`allow update, delete: if false`）。**送信取り消し**は Callable `recallChatMessage`（Admin SDK）のみ（§4.2.11）
- `users/{userId}` 直下の既存 `allow create, update` ルールと subcollection ルールが共存する

### 5.5 Firestore インデックス設計

- **ルーム一覧**: `users/{uid}/chat_memberships` サブコレクションに対する `orderBy('last_message_at', 'desc')`。collectionGroup インデックスは **不要**（サブコレクションクエリのみ）
- **メッセージ**: `chat_rooms/{roomId}/messages` サブコレクションに対する `orderBy('created_at', 'desc')` + `limit`。collectionGroup インデックスは **不要**

単一フィールドの並び替えは多くの場合自動インデックスで足りる。デプロイ時にエラーが出た場合のみ `firestore.indexes.json` に追加する。

### 5.6 Functions 設計

Functions は必要最小限とし、複数ドキュメントの一貫更新・権限検証はサーバー側で行う。

| Function | 種別 | 用途 |
| --- | --- | --- |
| `openDirectChat` | Callable | たべとも関係の検証、direct room / memberships 作成（Transaction） |
| `syncEventChatMember` | 内部（side effect から呼出） | `event.members` 変更に伴う event ルーム同期・システムメッセージ |
| `syncCommunityChatMember` | Trigger または side effect | コミュニティ members 変更に伴う community ルーム同期 |
| `onChatMessageCreated` | Trigger（`chat_rooms/{roomId}/messages/{messageId}` 作成） | `chat_rooms.last_message_*` 更新、各メンバーの `chat_memberships` 更新、未読加算 |
| `recallChatMessage` | Callable | 送信取り消し（論理削除）。`deleted_at` 設定、`last_message_*` 再計算。**Phase 2** |
| `archiveChatRoom` | 内部 | `is_active: false` を `chat_rooms` + 全 `chat_memberships` に設定 |
| `onEventArchived` | Trigger（`communities/{cid}/events/{eid}` の `onDocumentWritten`） | `is_deleted` / `event_status.value` 変更を検知し `archiveChatRoom` を呼び出す |

全 Function で **`createModuleLogger('chat')`**（またはモジュール名に応じた logger）を使用し、`roomId` / `userId` / `messageId` をログに含める。

**`onChatMessageCreated` の詳細**

- **送信者の `unread_count` は加算しない**が、**送信者を含む全メンバー**の `last_message_at` / `last_message_preview` は更新する（送信者の一覧プレビュー・ソートを正しく保つ）
- `message_type === 'system'` のときも `last_message_*` は更新するが、未読加算は行わない
- `last_message_preview` は `message_type` に応じて生成:
  - **user**: `Array.from(body).slice(0, 100).join('')` で truncate
  - **system**: 固定日本語（例: `{user_name}さんが参加しました`。`system_params.user_name` を使用）
- `unread_count` 加算は `FieldValue.increment(1)`。加算後 **最大 99 で clamp**（表示は 99+）
- **冪等性**: Trigger は at-least-once 配信。Transaction 内で `messages/{messageId}.processed === true` を確認し、未処理のみ更新後に `processed: true` をセット。重複実行時は no-op
- グループルームでメンバー数が多い場合、membership 更新は **500 件 batch 単位**で分割する
- Trigger 失敗時は Cloud Logging に記録し、再試行（Functions の retry）に任せる

**`syncEventChatMember` の詳細**

- `recalcEventMembers` の `updated: false` でも、**引数 `userId` が `event.members` に含まれる場合は参加同期を実行**する（membership 欠損の修復・冪等性）
- 同様に、含まれない場合は離脱同期を実行する
- ルーム初回作成時に `chat_rooms.title`（イベント名・参考用）、`is_active: true`、各 membership の `is_active: true` をセットする。**`chat_memberships` には `title` フィールド自体を持たない**（§5.1.4 / §5.1.6）
- **システムメッセージ**: 直前の `member_user_ids` との差分で **新規追加された UID のみ**生成（冪等同期での重複防止）。再参加（キャンセル後の再注文）は差分に含まれるため 1 件追加される

**`openDirectChat` の詳細**

- `runTransaction` で room / memberships の存在確認 → 作成を atomic に実行
- 並走呼び出し時の重複 room 作成を防止
- membership には `room_id` / `room_type` / Per-user フィールドのみ作成。**相手名は join**（§5.1.6）

**`recallChatMessage` の詳細（Phase 2）**

- 入力: `{ room_id, message_id }`（`RecallChatMessageRequestSchema`）
- 検証: 認証 UID === `sender_user_id`、ルーム書き込み可（`is_active === true`）、`deleted_at` 未設定、`message_type === 'user'`
- 処理: 当該 message に `deleted_at` / `deleted_by_user_id` / **`deleted_display_name`**（取り消し時点の `users.user_name`）をセットし、**`body` フィールドを Firestore から削除**（ドキュメント自体は物理 delete しない。§4.2.11）
- **`unread_count` は減算しない**（§4.2.11）。ユーザーがルームを開いて `markAsRead` するまで未読のまま
- 取り消し対象がルーム最新メッセージの場合、`recalculateRoomLastMessage(roomId)` で `chat_rooms` と全 membership の `last_message_*` を再計算
- membership 更新は **500 件 batch 分割**

**`recalculateRoomLastMessage`（内部ヘルパー）**

- `chat_rooms/{roomId}/messages` を `orderBy('created_at', 'desc').limit(50)` で取得
- **先頭から走査**し、次を **スキップ**して最初の有効メッセージを採用:
  - `message_type === 'user'` かつ `deleted_at` が設定済み
- 有効メッセージが見つかった場合: 通常の preview 生成ルール（§5.6 `onChatMessageCreated` と同じ）
- 見つからない場合: `last_message_preview` = **`メッセージが削除されました`**（`chat.last_message_preview_deleted` の固定文。Functions 側は固定日本語で denormalize）

**`archiveChatRoom` の詳細**

- `chat_rooms.is_active` を `false` に更新し、**全メンバーの `chat_memberships.is_active` も `false` に同期**（一覧「終了」表示・入力非活性のため）
- membership は削除しない（履歴閲覧のため）。`member_user_ids` は維持
- 対象: イベント `event_canceled` または `is_deleted === true`、コミュニティ解散（将来）

**`onEventArchived` の詳細（Phase 1 必須）**

- **Trigger**: `communities/{communityId}/events/{eventId}` の `onDocumentWritten`
- **検知条件**:
  - `is_deleted` が `false` → `true` に変化（論理削除。`base/src/stores/event.ts` の `deleteEvent`）
  - `event_status.value` が `event_canceled` に変化（`functions/default/src/eventCancellation.ts` の `cancelEvent`）
- **処理**: 対応 roomId `event_{community_id}_{event_id}` が存在すれば `archiveChatRoom` を呼び出す。存在しなければ no-op（lazy 作成で未作成のケース）

**連携ポイント**

- `applyOrderConfirmedSideEffects`: `recalcEventMembers` 成功後に `syncEventChatMember`（参加）
- `applyOrderCanceledSideEffects`: `recalcEventMembers` 成功後に `syncEventChatMember`（離脱）
- **論理削除 / キャンセル**: `onEventArchived` Trigger → `archiveChatRoom`（Phase 1 必須）
- **直接呼び出し不要**: クライアント `deleteEvent` は Firestore update のみ。archive は Trigger が担う

プッシュ通知送信は `02_プッシュ通知.md` の別フェーズで `onChatMessageCreated` から呼び出す。

### 5.7 処理フロー

#### 5.7.1 イベントグループチャット参加

1. ユーザーが注文確定（既存フロー。PayPay 完了後に `ordered` になる）
2. `recalcEventMembers` により `event.members` に UID が追加される
3. `applyOrderConfirmedSideEffects` 内で `syncEventChatMember` を呼び出す（`recalcEventMembers` 成功後。**`updated` の真偽にかかわらず**、membership の冪等同期）
4. `syncEventChatMember` が room 作成・`member_user_ids` 更新・`chat_memberships` 作成・システムメッセージ追加
5. 注文完了ダイアログの「チャットで挨拶しよう」は **3 完了後** に遷移可能（未完了時は §4.2.4 のローディング）

#### 5.7.2 イベントグループチャット離脱

1. ユーザーが注文キャンセル（既存フロー）
2. `recalcEventMembers` により `event.members` から UID が削除される
3. `syncEventChatMember` が `member_user_ids` から除外し、当該ユーザーの **`chat_memberships` ドキュメントを削除**
4. 以降、当該ユーザーはルームの読み書き不可（過去メッセージも閲覧不可）

#### 5.7.3 1:1 チャット開始

1. たべとも一覧またはプロフィールから「メッセージ」をタップ
2. Callable `openDirectChat` で `users/{uid}/friends/{friendUserId}` を検証
3. room + memberships を作成（既存なら roomId を返却）
4. `/chat/{roomId}` へ遷移

#### 5.7.4 メッセージ送信

1. フロントでバリデーション（空文字・2000 文字超を拒否）
2. `chat_rooms/{roomId}/messages` に `message_type: 'user'`、`created_at: serverTimestamp()` で追加
3. Trigger `onChatMessageCreated` が `chat_rooms` と**全** `chat_memberships` の `last_message_*` を更新し、**送信者以外**の `unread_count` を加算
4. 表示中ルームの場合、store が即座に既読化（§5.3）
5. プッシュ通知は別フェーズ（`02_プッシュ通知.md`）

#### 5.7.5 メッセージ送信取り消し

1. ユーザーが 3 点リーダー →「送信を取り消す」→ 確認（§4.2.11）
2. Callable `recallChatMessage` を呼び出す
3. サーバーが message を論理削除（`deleted_display_name` 含む。**`body` は Firestore から削除**）し、必要なら `recalculateRoomLastMessage` で `last_message_*` を再計算。**`unread_count` は変更しない**
4. クライアントは messages の `onSnapshot` で `deleted_at` を検知し、トゾーストーン表示に切り替える

### 5.8 データ整合性

- `chat_rooms.member_user_ids` の更新は Transaction で行う
- `event.members` / コミュニティ members が正とし、チャットメンバーはそれに追随する（二重管理しない）
- メッセージ送信後の未読加算・`last_message_*` の membership 反映は Trigger で行い、クライアントが他ユーザーの membership を直接更新しない
- `chat_rooms` と `chat_memberships` の **`last_message_preview` / `last_message_at` / `is_active`** は Trigger または sync 関数で **両方更新**する（Per-user / リアルタイムフィールド）
- **イベント名・カバー・相手名**は membership に同期しない（§5.1.6）。`onChatRoomTitleSync` は **実装しない**

### 5.9 store 設計

| 層 | パス | 責務 |
| --- | --- | --- |
| Zod スキーマ | `common/src/schemas/ChatRoom.ts`, `ChatMessage.ts`, `ChatMembership.ts` | DbSchema / AppSchema、バリデーション |
| base store | `base/src/stores/chat.ts` | Pinia。memberships / messages の `onSnapshot`、送信・既読。`activeRoomId` 管理。リスナー unsubscribe |
| functions store | `functions/default/src/stores/chat.ts` | Admin SDK。room / membership / system message の read/write。Transaction 対応 |
| Functions 本体 | `functions/default/src/syncEventChatMember.ts`, `onChatMessageCreated.ts`, `onEventArchived.ts`, `archiveChatRoom.ts`, `openDirectChat.ts`, `recallChatMessage.ts`（Phase 2） 等 | side effect 連携、Trigger、Callable |

**base store の責務（詳細）**

- `subscribeMemberships()` / `unsubscribeMemberships()`: ルーム一覧の `onSnapshot`
- `subscribeMessages(roomId)` / `unsubscribeMessages()`: アクティブルームのメッセージ `onSnapshot`（`limit(50)` desc）
- `loadOlderMessages(roomId)`: 上方向スクロール時に `startAfter` + `getDocs` で過去 50 件追加
- `mergeMessages(existing, incoming)`: `messageId` で重複排除し昇順マージ
- `waitForMembership(roomId, timeoutMs)`: 注文完了導線用。membership の `onSnapshot` で作成を待つ（§4.2.4）
- `activeRoomId`: 現在表示中のルーム ID
- `markAsRead(roomId)`: `unread_count: 0`, `last_read_at` / `updated_at` を `serverTimestamp()` で更新
- `sendMessage(roomId, body)`: メッセージ送信
- `recallMessage(roomId, messageId)`: Callable `recallChatMessage` 呼び出し（Phase 2）
- `resolveRoomDisplay(room)`: `room_type` に応じた `displayTitle` / `coverImageUrl` / `displayTitleReady` の join（§5.1.6）。`ChatContact` / ルームヘッダーから利用
- 同時 `onSnapshot` は **最大 2 本**（一覧 + アクティブルーム）+ **イベント join 用の軽量 snapshot**（ルームごと。キャッシュ共有）

**base コンポーネントのルール**

- `ChatApp.vue` / `ChatContact.vue` 等の `base` コンポーネント内に **ルーティングパスをハードコードしない**
- **イベント詳細遷移**: `emit('openEvent', { communityId, eventId })`。user 側ラッパー（例: `user/src/pages/chat/[[roomId]].vue`）が `event.community_account` 取得後 `getEventPath(communityAccount, eventId)` で遷移
- **プロフィール遷移**: `ChatLog` に `resolveProfilePath` prop。user 側が `getUserPath(userId)` を渡す
- チャットの状態・購読は **store** に集約し、composable は UI 補助のみ

**既存データへの対応（初回マイグレーション + lazy 作成）**

チャット機能リリース時は **限定マイグレーション** と **lazy 作成** を併用する。過去イベント全件の遡及は行わない（理由: §6.1「過去イベント全件を対象外とする理由」）。

#### 過去イベント全件をマイグレーションしない理由（UX・プライバシー）

**方針**: 終了済みイベントや `accepting_order` 以外への **一括チャット付与は Phase 1 では行わない**。運営上「たまに過去参加者へ連絡したい」需要は理解するが、**デフォルト機能として全過去イベントに room を作ることは採用しない**。

**ユーザー期待とのズレ**

- 参加者が注文・参加時に想定しているのは **当該イベントの食事に関する一時的な連絡**（日時・場所・当日調整等）であり、**終了後も参加者全員と連絡し続けられること**までは明示的に説明していない
- リリース後に **過去イベント分のルームが一括作成** されると、当時の文脈を超えた接触経路が突然できる。参加者によっては **想定外・不快** と感じられる

**モラル・プロダクト上のリスク**

| リスク | 内容 |
| --- | --- |
| 意図しない接触 | 顔合わせ程度の参加者同士が、イベント終了後も相互にメッセージ可能になる |
| 退出手段の不足 | Phase 1 ではユーザー自身によるルーム退出は未対応（§6.3）。付与した membership は一覧に残り続ける |
| 一覧 UX | 終了済みイベントのルームが大量に並ぶ（「終了」表示があっても心理的負担） |
| 将来の通知 | FCM プッシュ（別フェーズ）導入後、古いルームからの通知は特にストレスが大きい |
| メンバー集合の鮮度 | 当時の `event.members` と現在の関係性（退会・アカウント削除等）が一致しない |

**セキュリティ上の位置づけ**

- Firestore Rules 上、**ルームメンバー以外の read/write は禁止** されるため、第三者への「全公開」ではない
- それでも **「イベント参加 = 無期限のグループチャット許可」** と解釈されると、**意図しないコミュニケーション権限の付与** になりうる。技術的アクセス制御と **利用者の同意・期待** は別問題として扱う

**過去イベントへの連絡が必要な場合（Phase 1）**

- **全件マイグレーションに拡大しない**
- 代替: **たべとも → 1:1 チャット**（Phase 2）、**新規イベント（再会）の作成**、運営判断による **個別スクリプト**（対象イベント限定・dry-run 必須）
- 将来、過去イベント向け機能を足す場合は **オプトイン**（明示同意）・**期限付き**・**主催者発の限定用途** 等を別途設計する（本仕様 Phase 1 では対象外）

#### 初回マイグレーション（Phase 1 リリース時・1 回）

**目的**: リリース前から注文済みの参加者がいる **開催前イベント** で、lazy 同期だけだと「新規注文者だけルームに入る」問題を防ぐ（全 `event.members` を同一ルームに揃える）。

**対象条件**（以下を **すべて** 満たすイベント）

| 条件 | フィールド / 判定 |
| --- | --- |
| 参加受付中 | `event_status.value === 'accepting_order'` |
| 論理削除されていない | `is_deleted === false` |
| 参加者がいる | `event.members.length > 0`（`recalcEventMembers` 相当の ordered 集約結果） |
| 開催前 | `event_end_datetime > マイグレーション実行時刻` |

**対象外（マイグレーションしない）**

- **終了済み**（`event_end_datetime` 経過。DB 上 `accepting_order` のままでも除外）
- **`event_canceled`**、`is_deleted === true`
- **`accepting_order` 以外**（`in_draft` / `applying_reservation` 等）
- **参加者ゼロ**

**処理内容**（イベント 1 件あたり）

1. `roomId = event_{community_id}_{event_id}` の `chat_rooms` を作成（既存なら取得）
2. `member_user_ids` を **当該イベントの `event.members` 全員** で設定（不足分を merge。既存メンバーは維持）
3. 各 UID の `users/{uid}/chat_memberships/{roomId}` を作成（既存なら Per-user フィールドのみ必要に応じて更新）
4. **`chat_rooms.title`**（イベント名・参考用）と `is_active: true` をセット
5. **システムメッセージは生成しない**（一括バックフィル時の「◯◯さんが参加しました」連発を避ける）
6. **冪等**: 再実行しても duplicate しない（room / membership の存在確認）

**実装**

- 配置: `functions/default/src/scripts/migrateEventChatRooms.ts`（または同等）
- Admin SDK + 既存 store（`chatRoom` / `chatMembership`）を利用
- 本番実行前に sandbox で dry-run（対象件数・membership 数のログ出力）
- チャット機能 **デプロイ直後・ユーザー利用前** に 1 回実行する

#### lazy 作成（マイグレーション対象外 + リリース後の通常運用）

- **対象**: 初回マイグレーション条件外のイベント、およびリリース後の **新規注文確定 / キャンセル**
- **処理**: `syncEventChatMember` が **トリガーとなった `userId` 1 人分** のみ room / membership を同期（§5.6 / §5.7.1）
- **結果**: マイグレーション対象外の過去イベントは、原則チャットルームが存在しない（ユーザーからは見えない）。今後注文変更があれば当該ユーザー分のみ追加される

**例（10 名参加済み + リリース後 5 名追加）**

| イベント状態 | 挙動 |
| --- | --- |
| マイグレーション対象（`accepting_order`・開催前・10 名） | リリース時に **10 名全員** を room に追加 |
| リリース後 5 名が新規注文 | `syncEventChatMember` で **5 名追加** → 合計 **15 名** |
| マイグレーション対象外（終了済み等） | lazy のみ。新規注文者だけルームに入る可能性あり |

## 7. 注意事項

### 7.1 既存システムへの影響

- **注文確定 / キャンセル side effect** にチャット同期処理を追加する
- **既存データ**: リリース時 **初回マイグレーション**（`accepting_order`・開催前・参加者あり → 全 `event.members`）+ それ以外は **lazy 作成**（§6.1）
- **開発中の `chat_memberships`**: 旧 doc に `title` があっても互換しない。**削除して lazy / マイグレーションで再作成**（§5.1.6）
- **イベントキャンセル / 論理削除**: `archiveChatRoom` で `is_active: false`（読み取り専用。履歴閲覧可）
- **アカウント削除**（`13_アカウント削除.md` 連携）:
  - **`functions/default/src/deleteUserAccount.ts` 内**に処理を追加（専用 Function は分けない）
  - **探索方法**: 当該 UID の `users/{uid}/chat_memberships` を列挙し、各 `room_id` の `chat_rooms` を更新（collectionGroup 不要）
  - 各 room の `member_user_ids` から UID を除外（Transaction または batch。room 数が多い場合は batch 分割）
  - 当該ユーザーの全 `chat_memberships` を削除
  - **direct ルーム**: 相手側の membership / 履歴 / `member_user_ids`（相手 UID）は残す。相手からは「削除されたユーザー」として表示（§4.2.7）
  - 過去メッセージ本文は保持
- **メンテナンスモード**: チャット含め user アプリは全面ブロック（§3.3）
- **Firestore 読み取りコスト**: グループチャットのメッセージ `onSnapshot` は参加者数に比例する。メッセージはページネーション必須（§5.3）。ルーム一覧の名称・カバーは event 等への **join read**（ルーム数に比例。§5.1.6）だが、1 ユーザーあたりのルーム数は当面少ない想定

### 7.2 セキュリティ考慮事項

- ルームメンバー以外の読み取り・書き込みを禁止する
- 1:1 チャットは Callable でたべとも関係をサーバー側検証する
- **XSS 対策**: メッセージ本文は `{{ body }}` / `v-text` で表示（**`v-html` 禁止**）。URL リンク化は既存 **`v-linkify` ディレクティブ**（`@shokujii/base/directives/linkify`）を使用（§4.2.2）
- 読み取り専用ルーム（`is_active === false`）への message create を Rules で拒否
- **過去イベントへの一括チャット付与**: 行わない（§6.1）。メンバー限定 Rules だけでは **参加者の同意・期待** までは担保できない
- **送信レート制限**: Phase 1 では実装しない。**Phase 2 で検討**（スパム報告が増えた場合に優先）

### 7.3 運用考慮事項

- **初回マイグレーション**: 本番はメンテナンス窗口または低トラフィック時に実行。対象件数・書き込み数を事前 dry-run で確認（§6.1）
- モデレーション（主催者 / 運営によるメッセージ削除権限）は Phase 3 以降で検討（ユーザー自身の送信取り消しは Phase 2。§4.2.11）
- 大量メッセージ時の Storage / コスト監視
