# プッシュ通知

## 1. 概要

### 1.1 機能の目的

Shokujii の **チャット新着メッセージ** を、ユーザーがアプリを開いていないときにも端末の通知センターで気づけるようにする。アプリ内未読バッジ（`01_チャット機能_01.md` Phase 1）を補完し、イベント当日の連絡や 1:1 会話の返信率を高める。

### 1.2 技術概要（FCM）

**FCM（Firebase Cloud Messaging）** は Google が提供するプッシュ通知配信基盤。Shokujii は既存の Firebase プロジェクト（Auth / Firestore / Functions）上で動作するため、**同一プロジェクトに FCM を追加**する。

```
[user アプリ] ── トークン登録 ──► [Firestore]
                                        ▲
[Cloud Functions] ◄── onChatMessageCreated ── [chat messages]
       │
       └── FCM Admin SDK ──► [FCM] ──► [ユーザー端末（Web）]
```

| 用語 | 説明 |
| --- | --- |
| **FCM トークン** | 端末・ブラウザごとに発行される通知先 ID（Registration Token） |
| **Web Push** | ブラウザ向けプッシュ。Service Worker が受信口 |
| **VAPID 鍵** | Web Push 用の公開鍵/秘密鍵ペア。Firebase Console で生成 |
| **Data payload** | アプリ側で処理する付加データ（`room_id` 等）。通知タップ時の遷移に使用 |
| **Notification payload** | OS / ブラウザがそのまま表示するタイトル・本文 |

### 1.3 スコープ（Phase 1）

| 対象 | Phase 1 | 備考 |
| --- | --- | --- |
| **チャット新着（ユーザーメッセージ）** | ✓ | 本仕様の主対象 |
| **user アプリ（Web）** | ✓ | Vue + Vite。PWA / ブラウザ通知 |
| **partner アプリ** | ✗ | 対象外 |
| **ネイティブアプリ（iOS / Android）** | ✗ | 将来検討 |
| **注文リマインド・イベント通知等** | ✗（Phase 1） | Phase 2 以降は §14。メール（SendGrid）と連動して検討 |
| **システムメッセージ** | ✗ | 「◯◯さんが参加しました」等はプッシュしない（チャット仕様と同じ） |
| **送信取り消し** | ✗ | 取り消し時にプッシュは送らない。既存未読はアプリ内で解消 |

### 1.4 対象ユーザー

- ログイン済み一般ユーザー（`user` アプリ）
- **通知許可を OS / ブラウザで許可したユーザー**（未許可の場合はアプリ内未読のみ）

### 1.5 PWA との関係（概要）

`user` アプリは `vite-plugin-pwa` により **PWA 対応済み**（manifest・アイコン・Workbox Service Worker）。PWA 対応 **だけでは通知は届かない** が、FCM 実装の **前提条件の多くを満たしている**（§3.4）。

| 項目 | PWA | FCM プッシュ |
| --- | --- | --- |
| 主目的 | ホーム画面追加・オフライン・standalone 表示 | バックグラウンド新着通知 |
| 共通基盤 | Service Worker、HTTPS、manifest / アイコン | 同上（SW が受信口） |
| 自動連携 | — | **別途 FCM 用 SW 処理・トークン登録・Functions 送信が必要** |

**プラットフォーム別の要点**（詳細は §4.8）:

- **iOS**: ホーム画面に追加して **PWA として起動** しないと Web Push **不可**（Safari 通常タブでは不可）
- **Android**: PWA インストール **不要**。Chrome 等のブラウザで URL を開き **通知許可** すれば可
- **PC**: PWA 不要。ブラウザの通知許可のみ

### 1.6 ドキュメントステータス

**たたき台（Draft）**。実装着手前に 【要検討】 項目を確定する。

## 2. ねらい

### 2.1 ビジネス目標

- チャット返信率・イベント当日の連絡到達率の向上
- アプリ内未読に気づかず離脱するユーザーの再訪促進

### 2.2 ユーザー価値

- ロック画面・通知センターから新着に気づき、ワンタップで該当ルームを開ける
- アプリを常時開いていなくても、待ち合わせ変更等の連絡を逃しにくくなる

### 2.3 成功指標（KPI）

- 通知許可率（許可ユーザー / ログインユーザー）。**プラットフォーム別**（PC / Android / iOS PWA）にも分解して計測
- 通知タップ率（通知クリック / 通知送信成功数）
- 通知受信 → 24 時間以内のチャット返信率
- 通知 OFF 率（設定画面からの無効化。Phase 2 以降）

### 2.4 リスクと UX 上の注意

| リスク | 内容 | 対策案 |
| --- | --- | --- |
| 通知疲れ | グループチャットで連投時に通知が大量に届く | Phase 1 は 1 メッセージ = 1 通知。将来 **ルーム単位の通知集約** を検討 |
| 古いルーム | 終了済みイベントのルームからも通知が届く | `is_active === false` のルームは **プッシュ対象外**（§4.3） |
| 通信の秘密 | 通知本文にメッセージ内容が含まれる | プレビューは `buildMessagePreview` と同程度の短縮文に限定（§4.4） |
| Safari 制限 | iOS は **PWA ホーム画面追加 + standalone 起動** が必須（§4.8） | iOS 向けに「ホーム画面に追加」案内 UI を出す。非対応環境はアプリ内未読のみ |
| iOS 到達率 | ホーム画面追加までのハードルが高い | Android / PC を主戦場とし、iOS はベストエフォート。KPI を分けて計測 |

## 3. 前提条件

### 3.1 技術的前提条件

- Firebase プロジェクトに **Cloud Messaging API** が有効であること
- `user` アプリは **HTTPS** で配信されること（Web Push 必須）
- `base/src/firebase.ts` に `messagingSenderId` が設定済み（Messaging SDK 初期化は本フェーズで追加）
- DB 操作は store 経由、`xxxRef` は `withConverter` 付き（AGENTS.md 準拠）
- チャット基盤（`01_チャット機能_01.md`）の **Phase 1 以上** がデプロイ済みであること
- `user` アプリの **PWA 基盤**（`vite-plugin-pwa`）が build 時に有効であること（§3.4）

### 3.2 既存 PWA 基盤（user アプリ）

Shokujii は Phase 1 チャット以前から PWA を導入済み。FCM 実装時はこれを **再利用・拡張** する。

| 項目 | 現状（`user/vite.config.ts`） | FCM 実装時の追加 |
| --- | --- | --- |
| PWA プラグイン | `vite-plugin-pwa`（build 時のみ） | 変更最小限 |
| Service Worker | Workbox `generateSW`（キャッシュ・オフライン） | **FCM の push handler を同居**（§7.1）。SW は原則 1 つ |
| manifest | `name` / `short_name` / `icons`（96〜512px） | iOS Web Push 向けに **`display: 'standalone'`**（または `fullscreen`）を **追加**（現状未設定。WebKit 要件） |
| 通知アイコン | `pwa-192x192.png` 等 | notification payload の icon に流用 |
| Messaging SDK | 未初期化 | `getMessaging` + VAPID 鍵 |

**Workbox × FCM の統合方針（Phase 1）**

Service Worker は **1 端末 1 本**のため、次のいずれかで実装する（実装 PR で具体案を選定）:

1. **`injectManifest` に切り替え**: 自前 SW に Workbox precache + FCM `onBackgroundMessage` を同居
2. **Workbox SW から `importScripts`**: FCM 専用処理を別ファイルから読み込み

PWA があるから FCM が自動で動くわけではないが、**manifest / アイコン / SW 登録の土台**は揃っている。

### 3.3 ビジネス的前提条件

- **電気通信事業届出**: 本番提供前に `03_電気通信事業届出準備.md` に従い、プッシュ通知を含むチャット役務の届出要否・記載内容を確認する
- 通知本文に個人情報（メッセージ内容・表示名）を含める場合、プライバシーポリシー・利用規約への追記を検討する

## 4. 機能仕様

### 4.1 通知許可フロー（クライアント）

#### 4.1.1 基本方針（オプトイン）

**許可したユーザーのみ** プッシュを受け取る。未許可ユーザーは **アプリ内未読バッジのみ**（`01_チャット機能_01.md` Phase 1 と同じ）。

- サーバーは Firestore に登録された **FCM トークンがある UID** にのみ送信する
- ログイン直後の **自動プロンプトは行わない**（許可率低下・UX 悪化を避ける）
- OS / ブラウザで **拒否** された場合、当該端末ではトークンを取得できない

#### 4.1.2 2 段階許可（アプリ内 → OS）

Web Push では **必ず OS / ブラウザの許可** が必要。PC ブラウザでよく見る「通知を許可しますか？」は **②** に相当する。Shokujii では **① を挟む**（いきなり OS ダイアログを出さない）。

| 段階 | 内容 | 誰が表示 |
| --- | --- | --- |
| **① アプリ内** | タイトル・説明文 + **「許可する」「あとで」の 2 ボタン**（§4.1.3） | Shokujii UI（§7.3 i18n） |
| **② OS / ブラウザ** | 「shokujii.jp が通知を送信します」等 | iOS / Android / macOS / Windows の **ネイティブ UI** |

**なぜスマホで②を見たことが少ないか**

- 日常使いの LINE・Gmail 等は **ネイティブアプリ** のインストール時許可であり、Web の `Notification.requestPermission()` とは別
- Web サイトがモバイルで通知を求める例自体が少ない（iOS は PWA 追加までハードルが高い）
- スマホの②は PC の画面上部バナーと **見た目が異なる**（画面中央の OS ダイアログ等）

#### 4.1.3 許可プロンプト UI（①）

初回チャット送信成功後など、§4.1.4 の表示条件を満たすとき **1 回** 表示する **モーダル / ダイアログ**。

**レイアウト**

| 要素 | 仕様 |
| --- | --- |
| タイトル | `push.enable_title`（例: 新着メッセージを通知で受け取る） |
| 説明文 | `push.enable_body` |
| **Primary ボタン** | **「許可する」**（`push.enable_button`）。`variant` は filled / 強調 |
| **Secondary ボタン** | **「あとで」**（`push.enable_later`）。`variant` は text 等・弱め |
| × 閉じる | Phase 1 では **付けない**（「あとで」と役割が重複するため） |
| 3 択以上 | Phase 1 では **採用しない** |

**ボタン別の挙動**

| 操作 | 処理 | `Notification.requestPermission()`（②） |
| --- | --- | --- |
| **許可する** | §4.1.4 の許可フローへ | **呼ぶ**（ユーザー操作の直後のみ） |
| **あとで** | ダイアログを閉じる | **呼ばない** |

**「あとで」の位置づけ**

- ブラウザの **拒否（`denied`）ではない**。`Notification.permission` は **`default` のまま**（② 未到達のため）
- 後日、再度 ① を表示すれば **「許可する」→ ②** を試せる（② でブロックしていない限り）
- Phase 1: **同一ブラウザセッション内では ① を再表示しない**（localStorage 等は使わなくてよい）
- Phase 2: 設定画面から「通知をオンにする」導線（§4.7）。② が `denied` の場合は **ブラウザ設定への案内**（プログラムから ② は再表示不可）

**表示前チェック**

| `Notification.permission` | ① の表示 |
| --- | --- |
| `default` | 表示可（未プロンプト） |
| `granted` | **表示しない**（トークン登録のみ必要なら別処理） |
| `denied` | **表示しない**（「許可する」を出しても ② は出ないため）。Phase 2 で設定案内 |

#### 4.1.4 推奨タイミング

| タイミング | 内容 |
| --- | --- |
| 初回チャット送信成功後 | ① を表示（§4.1.3）。`permission !== 'granted'` かつ当セッション未表示 |
| iOS で PWA 未追加の場合 | ① の前または代わりに **「ホーム画面に追加」案内**（§4.8.2） |
| 設定画面（将来） | 通知 ON / OFF トグル（Phase 2） |

#### 4.1.5 許可フロー（「許可する」選択時）

**ユーザー操作必須** とは、② の `Notification.requestPermission()` を **ページ読み込み直後などユーザー操作なしに呼ばない** こと。① の **「許可する」タップ** がその操作となる。

1. ユーザーが **「許可する」** をタップ
2. （iOS のみ）PWA ホーム画面追加済みか判定。未追加なら §4.8.2 の案内を表示し **② へ進まない**
3. `Notification.requestPermission()` を呼び出す（②）
4. ② が **許可** された場合、`getToken(messaging, { vapidKey })` で FCM トークンを取得
5. Firestore にトークンを保存（§5.1）
6. ② が **拒否** された場合: トークンは取得しない。`Notification.permission === 'denied'` となり **同一 origin から ② は再表示不可**（ブラウザ仕様）。Phase 1 では追加の ① も出さない。Phase 2 でブラウザ設定への案内（§4.7）

#### 4.1.6 「あとで」選択時

1. ダイアログを閉じる
2. `Notification.requestPermission()` は **呼ばない**
3. 当セッションでは ① を **再表示しない**
4. アプリ内未読バッジ等、既存 UX は継続

#### 4.1.7 Service Worker

- Workbox SW と **統合** して FCM のバックグラウンド handler を実装（§3.2）
- バックグラウンド受信・通知タップ時の `clients.openWindow` を実装

### 4.2 通知の表示内容

| 項目 | 仕様 |
| --- | --- |
| **タイトル** | ルーム種別に応じた表示名（§4.2.1） |
| **本文** | `buildMessagePreview(message)` と同じルール（最大 100 文字相当） |
| **アイコン** | Shokujii アプリアイコン（`user` の favicon / manifest icon） |
| **data payload** | `room_id`, `message_id`, `room_type`（タップ時遷移用） |

#### 4.2.1 タイトル生成ルール

| `room_type` | タイトル | 取得元 |
| --- | --- | --- |
| `direct` | 送信者の `users.user_name` | `sender_user_id` → users |
| `event` | イベント名 | `chat_rooms.title`（参考用 denormalize 済み）または events join |
| `community` | コミュニティ名 | community join（Phase 2 チャットと同期） |

- 送信者名 + グループルーム名の **2 行表示**（例: タイトル「田中太郎」、本文「待ち合わせ 18:00 で」）は Phase 1 では **採用しない**。タイトル = ルーム名、本文 = プレビューとする
- 【要検討】グループチャットで「誰が送ったか」をタイトルに含める案（例: 「田中太郎（春の食事会）」）。UX テスト後に決定

#### 4.2.2 本文プレビュー（`buildMessagePreview` 準拠）

| メッセージ種別 | 本文例 |
| --- | --- |
| テキスト | 本文先頭 100 文字（truncate） |
| 画像のみ | `画像を送信しました` |
| テキスト + 画像 | テキスト優先。テキスト空なら `画像を送信しました` |

### 4.3 送信条件（サーバー）

`onChatMessageCreated` 完了後（または同一 Trigger 内の membership 更新後）に、**未読加算対象と同一条件**でプッシュを送る。

| 条件 | プッシュ |
| --- | --- |
| `message_type === 'user'` | 送る |
| `message_type === 'system'` | **送らない** |
| 送信者本人 | **送らない** |
| `claimed === false`（Trigger 再実行・冪等 no-op） | **送らない** |
| `shouldApplyLastMessage === false`（古いメッセージの遅延到着） | **送らない** |
| `last_read_at >= lastMessageAt`（既読済み） | **送らない** |
| `chat_memberships.is_active === false`（終了 / アーカイブ済みルーム） | **送らない** |
| 受信者に有効な FCM トークンが 0 件 | 送らない（ログのみ） |
| 受信者が **当該ルームをフォアグラウンド表示中** | **送らない**（§4.5） |

**送信取り消し（`recallChatMessage`）**: プッシュは送らない。取り消し前に届いた通知は OS 側で自動削除しない（Phase 1）。

### 4.4 プライバシー・通信の秘密

- 通知本文には **メッセージ全文を載せない**（100 文字 truncate）
- ロック画面に表示される前提で、機密性の高い内容はユーザー自身の判断に委ねる（一般的なチャットアプリと同水準）
- `03_電気通信事業届出準備.md` §3.2 のとおり、通知本文を含める場合は **通信の秘密・個人情報** の観点で届出書類・プライバシーポリシーを更新する
- data payload に **メッセージ本文を含めない**（`room_id` / `message_id` のみ）

### 4.5 フォアグラウンド時の挙動

| アプリ状態 | 挙動 |
| --- | --- |
| **フォアグラウンド**（該当 `roomId` を表示中） | OS 通知は **表示しない**。`onMessage` で受信しても UI 更新は Firestore `onSnapshot` に任せる |
| **フォアグラウンド**（別ルーム表示中） | OS 通知を **表示する**（または 【要検討】 アプリ内トーストのみ） |
| **バックグラウンド / タブ非表示** | Service Worker が OS 通知を表示 |
| **ブラウザ終了** | Web Push が届く環境では Service Worker が受信 |

**フォアグラウンド判定（サーバー側）**

- Phase 1 では **サーバーはフォアグラウンドを知らない** ため、クライアントが `users/{uid}/presence/active_room_id` 等に Heartbeat を書く方式は **Phase 2 で検討**
- Phase 1 は **フォアグラウンドでも OS 通知が出る可能性** を許容するか、**クライアント `onMessage` で通知を抑制** する（表示中ルームのみ）

### 4.6 通知タップ時の遷移

1. ユーザーが通知をタップ
2. Service Worker の `notificationclick` で `room_id` を取得
3. `/chat/{roomId}` を開く（未ログイン時はログイン後にリダイレクト）
4. `markAsRead(roomId)` を実行（既存チャット store）

### 4.7 通知 OFF（Phase 2）

Phase 1 では **OS / ブラウザの通知設定** のみ。アプリ内トグルは Phase 2。

| 方式 | 内容 |
| --- | --- |
| ② で `denied` | プログラムから ② は再表示不可。Phase 2 で `push.denied_hint_*` により **ブラウザのサイト設定** への案内 |
| OS 設定 OFF | トークンは残すが FCM 配信は端末側で表示されない |
| アプリ内 OFF（Phase 2） | `users/{uid}.push_notifications_enabled === false` でサーバー送信をスキップ |

### 4.8 プラットフォーム別の制約と UX

#### 4.8.1 対応一覧（Phase 1）

| 環境 | PWA（ホーム画面追加） | Web Push | 通知許可 | Phase 1 の位置づけ |
| --- | --- | --- | --- | --- |
| **PC Chrome / Edge / Firefox** | 不要 | ✓ | ② OS / ブラウザダイアログ | **主対象** |
| **Android Chrome 等** | 不要 | ✓ | 同上 | **主対象** |
| **iPhone / iPad（Safari 通常タブ）** | — | **✗** | — | 非対応。アプリ内未読のみ |
| **iPhone / iPad（ホーム画面 PWA）** | **必須** | ✓（**iOS / iPadOS 16.4+**） | ② + 事前に PWA 追加 | **ベストエフォート**。案内 UI 必須 |
| **macOS Safari 13+** | 不要 | ✓ | ② | 対応 |
| **非対応ブラウザ** | — | ✗ | — | 通知 UI 非表示 |

**確定事項（旧 P-6）**

- **iOS**: Web Push は **ホーム画面に追加した PWA をアイコンから standalone 起動** した場合のみ。Safari の通常タブでは **不可**
- **Android**: **PWA インストール不要**。ブラウザでサイトを開き、許可すれば通知可能
- **PC**: **PWA 不要**。ブラウザ通知許可のみ

#### 4.8.2 iOS 向け「ホーム画面に追加」案内

iOS で通知許可（§4.1.5 ②）に進む **前** に、次を満たしている必要がある。

1. **iOS / iPadOS 16.4 以上**
2. manifest に `display: 'standalone'` または `fullscreen`（§3.2。**実装時に manifest へ追加**）
3. Safari / Chrome / Edge 等の **共有 → 「ホーム画面に追加」**
4. **ホーム画面のアイコンから起動**（ブラウザタブから開いた状態では Web Push 不可）

**UI 方針（Phase 1）**

- iOS かつ standalone 起動でない場合、**「許可する」** の代わりに **追加手順ダイアログ** を表示（「あとで」で閉じられる）
- 共有ボタン付近のイラスト / ステップ説明（1. 共有 → 2. ホーム画面に追加 → 3. アイコンから開く → 4. もう一度 **「許可する」**）
- standalone 起動を検知したら通常の §4.1.5 フローへ

**検知方法（案）**

- `window.matchMedia('(display-mode: standalone)').matches` または `navigator.standalone`（iOS Safari レガシー）
- User-Agent で iOS 判定 + standalone 未満なら案内 UI

#### 4.8.3 プラットフォーム別フロー図

```
【Android / PC】
  初回チャット送信

【iPhone】

```

### 5.1 FCM トークン（Firestore）

**パス**: `users/{userId}/fcm_tokens/{tokenId}`

`tokenId` は **FCM トークン文字列の SHA-256 ハッシュ先頭 32 文字** 等、固定長 ID とする（トークン自体を doc ID にすると長すぎる場合がある）。

| フィールド | 型 | 必須 | 説明 |
| --- | --- | --- | --- |
| `token` | string | ✓ | FCM Registration Token |
| `platform` | `'web'` | ✓ | Phase 1 は web のみ |
| `user_agent` | string | optional | デバッグ・サポート用 |
| `created_at` | Timestamp | ✓ | 初回登録日時 |
| `updated_at` | Timestamp | ✓ | 最終更新（トークン再取得時） |
| `last_used_at` | Timestamp | optional | 最終送信成功時（クリーンアップ用） |

**Rules（案）**

- `read`: 本人のみ
- `create` / `update` / `delete`: 本人のみ
- `token` フィールドは create 後 **変更不可**（改ざん防止。更新は delete + create）

**トークン lifecycle**

| イベント | 処理 |
| --- | --- |
| ログイン + 許可 | upsert |
| トークン refresh（FCM 側） | `onTokenRefresh` で upsert |
| ログアウト | 当該端末のトークン doc を **delete** |
| 送信失敗（`messaging/registration-token-not-registered` 等） | 該当 token doc を **delete** |
| アカウント削除 | 全 `fcm_tokens` を delete（§5.5） |

**1 ユーザーあたりのトークン数**

- 複数ブラウザ・端末を許容（上限 **10 件**。超過時は `updated_at` が最も古いものから delete）【要検討】

| ファイル | 内容 |
| --- | --- |
| `common/src/schemas/FcmToken.ts` | `FcmToken` クラス + DbSchema / AppSchema |
| `common/src/schemas/User.ts` | Phase 2: `push_notifications_enabled` 追加 |

### 5.3 インデックス

- トークン列挙は `users/{uid}/fcm_tokens` のサブコレクション `getDocs` のみ。**collectionGroup インデックス不要**
- 送信時は **受信者 UID からトークンを取得**（メッセージ Trigger 側で `memberUserId` が既知）

## 6. サーバー仕様（Functions）

### 6.1 Function 一覧

| Function / モジュール | 種別 | 用途 |
| --- | --- | --- |
| `sendChatPushNotifications` | 内部 | 1 メッセージに対するプッシュ送信。`onChatMessageCreated` から呼び出し |
| `onChatMessageCreated` | Trigger（既存） | membership 更新 **後** に `sendChatPushNotifications` を呼ぶ（§6.2） |
| `registerFcmToken` | Callable（案） | トークン登録のサーバー検証が必要な場合のみ。【要検討】Phase 1 は **クライアント直接 write + Rules** でも可 |
| `deleteUserAccount`（既存） | Callable | 全 `fcm_tokens` 削除を追加（§5.5） |

### 6.2 `onChatMessageCreated` との連携

既存 Trigger（`functions/default/src/onChatMessageCreated.ts`）の **membership batch commit 成功後** にプッシュ送信を行う。

```
onChatMessageCreated
  ├─ claimMessageProcessed（既存）
  ├─ chat_rooms / chat_memberships 更新（既存）
  └─ sendChatPushNotifications（新規）
        ├─ 送信対象 memberUserId を列挙（shouldIncrementMembershipUnread と同条件）
        ├─ 各 UID の fcm_tokens を取得
        ├─ タイトル・本文を組み立て
        └─ admin.messaging().sendEachForMulticast() または sendEach()
```

**冪等性**

- プッシュ送信も `claimed === true` のときのみ実行（未読加算と同じ）
- FCM 送信自体は at-least-once になりうるが、**同一 messageId の重複通知** は許容範囲とする（稀）。厳密に防ぐ場合は `messages/{messageId}.push_sent_at` を Transaction で記録【要検討】

**エラーハンドリング**

- 個別トークンの失敗は **他トークンの送信を継続**
- 無効トークンは delete してログに記録
- Trigger 全体は **FCM 失敗でも throw しない**（membership 更新は成功済みのため）。Cloud Logging + Error Reporting で監視

### 6.3 FCM 送信ペイロード（案）

```typescript
// 概念例（実装時は shokujii-functions-implementation スキルに従う）
{
  notification: {
    title: '春の食事会',
    body: '待ち合わせ18時でお願いします',
  },
  data: {
    type: 'chat_message',
    room_id: 'event_community1_event1',
    message_id: 'abc123',
    room_type: 'event',
  },
  webpush: {
    fcmOptions: {
      link: 'https://user.shokujii.jp/chat/event_community1_event1',
    },
  },
  tokens: ['...', '...'],
}
```

- `notification` + `data` の **ハイブリッド** を Phase 1 で採用（バックグラウンドは Service Worker、タップ遷移は `data.room_id`）
- 環境ごとの `link` ベース URL は Functions の環境変数で注入

### 6.4 パフォーマンス

| 項目 | 方針 |
| --- | --- |
| グループルーム（大人数） | membership 更新と同様 **500 件 chunk**。FCM `sendEach` は最大 500 トークン/リクエスト |

### 6.5 アカウント削除連携

`functions/default/src/deleteUserAccount.ts` に以下を追加:

1. `users/{uid}/fcm_tokens` を列挙して全 delete
2. FCM 側のトークン無効化は **Firestore delete のみ**（Admin SDK に revoke API はない。無効トークンは次回送信失敗で整理）

## 12. チャット以外のプッシュ候補（SendGrid メール連動）

Phase 1 は **チャット新着のみ**（§9.1）。本節は Phase 2 以降の拡張候補。**正本は SendGrid メール仕様** と `functions/default` の既存送信処理。プッシュは「今すぐ気づいてほしい・タップで画面へ」の通知に限定する。

### 12.1 方針

| 観点 | メール（SendGrid） | プッシュ（FCM） |
| --- | --- | --- |
| 到達条件 | `user_email` | FCM トークン + OS 許可（§4.1） |
| 本文 | 長文・テンプレ変数多数 | タイトル + 短い本文（100 文字程度） |

#### 12.4.2 プッシュ非推奨（メールのまま）

| 種別 | 理由 |
| --- | --- |
| ログイン / メール変更 OTP（`user.ts`） | セキュリティ。別端末へのプッシュ不適切 |

| イベント終了アンケート | メール + リンクで十分 |
| コミュニティ作成・管理者招待 | 初回セットアップ系 |

### 12.5 共通設計

#### 12.5.1 送信条件チェックリスト（メールと共用）

1. イベント / コミュニティの **`enterprise_id`**（PF only はスキップ）
2. **`is_public`** / 定員 / **`event_status`**（`accepting_order` 等）
3. **送信済みフラグ**（新着・人気イベントはイベント doc）
4. **受信者フィルタ**（全メンバー / 未注文のみ / ordered のみ）
5. **FCM トークン**有無 + `push_notifications_enabled`（Phase 2）
6. **メールとの二重通知**（§12.5.3）

#### 12.5.2 data payload 共通フィールド（チャット以外）

| フィールド | 説明 |
| --- | --- |
| `type` | `new_event` / `order_deadline_reminder` / `in_cart_reminder` / `order_deadline_closed` / `order_completed` / `event_start_reminder` / `letter` / `chat_message`（§6.3） |
| `community_id` | コミュニティ ID |
| `event_id` | イベント ID（該当時） |
| `letter_id` | レター ID（該当時） |

- **メッセージ本文・長い `event_desc` は載せない**（§4.4 と同様）
- タップ後は Firestore Rules でアクセス検証

#### 12.5.3 メールとプッシュの関係【要検討 P-8】

| 方式 | 内容 |
| --- | --- |
| A: 両方送る | 実装単純。スマホでメール + プッシュの **二重通知** になりうる |
| B: プッシュ優先 | トークンあり → プッシュのみ。なし → メールのみ |
| C: ユーザー設定 | Phase 2 で「メール / プッシュ / 両方 / オフ」を種別ごとに選択 |

Phase 2a 着手前に **A か B** を最低限決定する。

#### 12.5.4 通知種別ごとの設定（Phase 2 以降）

`users/{uid}` またはサブコレクションに、種別 ON/OFF を持つ案:

| 設定キー | デフォルト |
| --- | --- |
| `push_chat_enabled` | true（許可ユーザー） |
| `push_new_event_enabled` | true |
| `push_order_reminder_enabled` | true |
| `push_marketing_enabled` | false |
