# テスト方針

## 現状の品質担保手法

静的解析・スキーマ検証に加え、**Vitest によるユニットテストを PR verify で自動実行**している。
E2E テストや VRT は未導入。リリース前の画面・業務フロー確認は手動テスト項目書で行う。

| 手法 | 詳細 | CI 実行 |
|:--|:--|:--|
| TypeScript 型チェック | `vue-tsc --noEmit` / `tsc -b` | PR verify（`pr-verify.yml`） |
| ESLint | `--max-warnings=0` で警告もエラー扱い | PR verify / デプロイ workflow |
| Prettier | `format:check` でフォーマット統一 | PR verify / デプロイ workflow |
| Zod スキーマバリデーション | `withConverter` 経由で Firestore 読み書き時にランタイム検証 | - |
| ユニットテスト (Vitest) | `common` / `base` / `user` / `partner` / `functions/default` | PR verify |
| 手動テスト項目書 | リリース単位の実機確認（例: `v2.10_テスト項目書.md`） | - |
| AI コードレビュー | `/shokujii-code-review` による PR 単位のレビュー | - |

### Vitest の現状（2026-06 時点）

| パッケージ | テストファイル数（目安） | 主な対象 |
|:--|:--|:--|
| `common` | 17 | 日付・期限、料金、Zod スキーマ、バリデーション |
| `functions/default` | 13 | userProfile、friends、side effects、store |
| `base` | 2 | composable（CSV export、イベントコピー） |
| `user` | 1 | router utils |
| `partner` | 1 | navigation utils |
| `manager` | 1（レガシー） | 例示のみ。新規追加しない |

ローカル実行:

```
npm -w common run test
npm -w base run test
npm -w user run test
npm -w partner run test
npm -w functions/default run test
```

PR verify と同じ一括チェックは `/lint-and-format` スキル（`.agents/skills/lint-and-format/SKILL.md`）を参照。

## テスト手法の全体像と優先度

コストが低い（導入しやすい）ものから順に並べる。

```
コストが低い（導入しやすい）
  ↑
  │  ✅ 型チェック (TypeScript)        ← 導入済み（PR verify）
  │  ✅ Lint / Format                  ← 導入済み（PR verify）
  │  ✅ スキーマバリデーション (Zod)     ← 導入済み
  │  ✅ ユニットテスト (Vitest)         ← 基盤導入済み・拡充フェーズ
  │  ── ここまでが今のライン ──
  │  🔄 Playwright MCP（手動テストの代替） ← 設定追加済み・Phase A 試行中
  │  ⬜ Firestore ルールのエミュレータテスト
  │  ⬜ インテグレーションテスト
  │  ⬜ E2E テスト (Playwright)
  │  ⬜ VRT（Visual Regression Test）
  ↓
コストが高い（維持が大変）
```

## 自動テストと手動テストの棲み分け

| 種別 | 目的 | いつ使う |
|:--|:--|:--|
| Vitest | ロジックの退行防止。同じ入力なら同じ結果を保証 | 実装・修正時、PR マージ前（CI 自動） |
| 手動テスト項目書 | 画面・権限・デプロイ・実機連携の確認 | リリース前（sandbox / development / production） |
| Playwright MCP | 開発中の探索的確認。「動くか見て」を AI に任せる | 機能開発中（テスト資産にはならない） |
| E2E テスト | 主要 UI フローの退行防止 | 導入後は PR / 定期実行（未導入） |

手動テスト項目書は `documents/テスト方針・テスト項目書/` にリリース単位で置く。自動テストでカバーできるロジック（日付計算、料金、副作用）は Vitest に寄せ、手動項目書は画面・権限・外部サービス連携に集中する。

E2E / Playwright の導入検討（フロー候補・MCP 手順）は [`E2E_Playwright_導入検討.md`](./E2E_Playwright_導入検討.md) を参照。

## 困りごと別の手法選定ガイド

| 困りごと | 向いている手法 | 具体例 |
|:--|:--|:--|
| ロジックのバグが怖い | ユニットテスト (Vitest) | 料金計算、日付処理、参加条件の判定 |
| リリース後に画面が壊れる | E2E テスト (Playwright) | ログイン → イベント参加の主要フロー |
| 手動確認が面倒 | Playwright MCP | 開発中の画面確認を Claude に任せる |
| デザイン崩れに気づけない | VRT (reg-suit 等) | スクリーンショット比較で差分検出 |
| Firestore ルールが不安 | エミュレータテスト | ルールの許可/拒否を自動検証 |

## いつ Vitest を書くか

新規・修正時に次を満たすコードにはテスト追加を検討する。

1. **ビジネスロジック** — 条件分岐が多い、バグの影響が大きい（料金、期限、参加可否、Stripe webhook）
2. **純粋関数** — 外部 I/O が少なく、入力と出力が明確（`common/src/utils` 等）
3. **バグ修正** — 再発防止のため、修正内容を再現するテストを追加

優先度は `common` → `functions/default` → その他。Vue コンポーネントの DOM テストや E2E は後回しでよい。

## 導入ステップ

段階的に導入する。いきなり全部入れず、効果が高くコストが低いものから進める。

### Step 1: common のユニットテスト（Vitest）— ✅ 基盤導入済み

- Zod スキーマのバリデーション、ユーティリティ関数のテスト
- 依存が少なく書きやすい。壊れにくい
- **次**: 未カバーの utils / schemas をリリース変更に合わせて追加

### Step 2: functions/default のユニットテスト（Vitest）— ✅ 基盤導入済み

- userProfile、friends、side effects、store 等にテストあり
- **次**: Stripe webhook、メール送信ロジック、注文確定副作用など重要ドメインを優先して拡充

### Step 2b: base / user / partner — ✅ 基盤のみ

- vitest.config と CI 連携は済。テスト数は少ない
- **次**: router / navigation 以外は無理に増やさず、共通ロジックは `common` 側に寄せてテストする

### Step 3: Playwright MCP の導入 — 🔄 Phase A 済・Phase B 準備済（development）

- MCP 設定: [`.cursor/mcp.json`](../../.cursor/mcp.json) / [`.mcp.json`](../../.mcp.json)
- Phase A 試行手順: [`playwright-mcp/手順/PhaseA_試行手順.md`](./playwright-mcp/手順/PhaseA_試行手順.md)
- **Phase B 試行手順**: [`playwright-mcp/手順/PhaseB_試行手順.md`](./playwright-mcp/手順/PhaseB_試行手順.md)（`{USER_BASE_URL}` + ログイン uid。実値は `環境設定.local.md` 参照）
- 環境テンプレート: [`playwright-mcp/環境/環境設定.template.md`](./playwright-mcp/環境/環境設定.template.md)
- 概要: [`E2E_Playwright_導入検討.md`](./E2E_Playwright_導入検討.md) §6

### Step 4: Firestore ルールのエミュレータテスト — ⬜ 未着手

- Security Rules の許可/拒否を自動検証
- PR verify に組み込む前に、ローカルで `@firebase/rules-unit-testing` 等の PoC から始める

### Step 5: E2E テスト（Playwright テストコード）— ⬜ 必要になったら

- 主要フロー（ログイン → イベント参加 → 決済）だけに絞って書く
- 維持コストが高いので「壊れたら困るフロー」に限定する
- CI に組み込むには Firebase エミュレータ環境の整備も必要になる
- フロー候補・優先度: [`E2E_Playwright_導入検討.md`](./E2E_Playwright_導入検討.md) §4

## TDD（テスト駆動開発）について

TDD（先にテストを書く → Red → Green → Refactor）は手法であってゴールではない。
このプロジェクトでは以下の順番で進める。

1. まず既存コードにテストを後付けして「テストがある状態」に慣れる（**現在ここ**）
2. テストの恩恵を実感してから、新機能の開発時に TDD を試す

## 各手法の比較

| | ユニットテスト (Vitest) | 手動テスト項目書 | Playwright MCP | E2E テスト (Playwright) |
|:--|:--|:--|:--|:--|
| 書くもの | テストコード (.test.ts) | チェックリスト (.md / .csv) | 自然言語の依頼 | テストコード (.spec.ts) |
| 実行 | CI で自動実行 | リリース前に人手 | Claude Code との会話中 | CI で自動実行（未導入） |
| 再現性 | 高い | 中（実施者・環境に依存） | 低い | 高い |
| 用途 | ロジックのリグレッション防止 | 画面・権限・実機確認 | 開発中の動作確認・探索的テスト | UI フローのリグレッション防止 |
| 維持コスト | 低い | 中（リリースごとに更新） | なし | 高い |
