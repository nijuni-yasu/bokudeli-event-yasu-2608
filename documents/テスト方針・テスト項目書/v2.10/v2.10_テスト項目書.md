## 2. 重点確認ポイント

v2.10 は画面改修と Functions / CI / リリース基盤の変更が同時に含まれるため、次の観点を重点的に確認する。

- 一般ユーザーのマイページ、プロフィール、たべとも、注文履歴の表示・権限制御が期待どおりであること
- 飲食店向けアプリが `partner` として正しくデプロイ・動作すること
- legacy / Slack / LINE bot 由来の Functions が `functions/default` 側で正しく稼働すること
- 友人データ・プロフィールカウントのバックフィルを安全に実行できること
- production リリース手順が B 版（release ブランチ + PR、タグはマージ後に付与）どおりに実行できること

## 10. production リリース時の注意

### 10.1 バージョン・タグ

- ルート `package.json` / `package-lock.json` を `2.10.0` に上げる。
- `development` は直 push しない。`release/2.10.0` から PR を作成し、`PR verify / verify` 通過後にマージする。
- `v2.10.0` タグは release PR マージ後の `development` HEAD に付ける。
- release ブランチ上で `npm version` によるタグ作成をしない。実行する場合は `npm version minor --no-git-tag-version` を使う。

### 10.2 production デプロイ

- `production` push で本番デプロイが自動実行される。
- 今回は `user` / `partner` / `functions` / `firestore` / `storage` のデプロイが走る想定。
- Actions の並行実行により、Functions が partner Hosting より先に切り替わる可能性がある。
- `ClientError` の `app` 値は `admin` から `partner` に変わるため、partner Hosting 完了前の旧 JS からのエラー報告は短時間 Cloud Logging に残らない可能性がある。

### 10.3 手動設定漏れ

- GitHub Actions Variables の `ADMIN_ENV` は使わず、`PARTNER_ENV` が production に設定されていること。
- Functions の `ADMIN_HOST` は使わず、`PARTNER_HOST` が production に設定されていること。
- Firebase Hosting target `partner` が production プロジェクトで設定済みであること。
- Slack / LINE / Adobe PDF / SendGrid / Stripe / backup 用 Secret が production に登録済みであること。
- Cloud Scheduler の Slack / LINE / backup ジョブが存在し、対象関数名が v2.10 の名前に一致していること。

### 10.4 バックフィル

- `backfillUserFriends` と `backfillUserProfileCounts` は support 権限でのみ実行する。
- 本番では必ず `dry_run=true` で件数・コスト・対象範囲を確認してから本実行する。
- 最初は小範囲で本実行し、画面表示・カウント・Functions ログを確認してから全体実行する。
- バックフィル済みデータはロールバックしても自動では戻らない。問題時は再バックフィルまたは部分補正で復旧する。

### 10.5 ロールバック

- 直前の正常タグは `v2.9.0`。
- コードのロールバックは `main` / `production` を `v2.9.0` に戻して production を再デプロイする。
- Firestore の新規 friends サブコレクションや users のカウントフィールドは残るため、DB を巻き戻すのか、残置して read 側で無視するのかを事前に判断する。
- Slack / LINE / Functions codebase の切り戻し後、旧関数の有無や Scheduler の向き先を必ず確認する。
