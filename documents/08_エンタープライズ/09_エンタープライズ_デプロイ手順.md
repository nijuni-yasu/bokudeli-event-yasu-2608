## 1. 命名規則

### 1.1 Firebase Hosting サイト ID

**`<GCP プロジェクト ID>-enterprise`** とする。

| 環境 | GCP プロジェクト ID 例 | Hosting サイト ID |
| :-- | :-- | :-- |
| sandbox | `bokudeli-event-yasu-2510` | `bokudeli-event-yasu-2510-enterprise` |
| development | `bokudeli-event-dev` | `bokudeli-event-dev-enterprise` |
| production | `bokudeli-event` | `bokudeli-event-enterprise` |

> 既存 Hosting サイトとの対応（参考）  
> - user: プロジェクト ID と同名（例: `bokudeli-event-dev`）  
> - partner: `<PROJECT_ID>-admin`（例: `bokudeli-event-dev-admin`）  
> - enterprise: **`<PROJECT_ID>-enterprise`**

### 1.2 Firebase Hosting target 名

リポジトリ内の target 名は **`enterprise`** 固定（`firebase.json` / CI の `--only hosting:enterprise` と一致）。

### 1.3 GitHub Actions Variable 名

| 変数名 | 説明 |
| :-- | :-- |
| `ENTERPRISE_ENV` | `enterprise/.env` の内容（ビルド時に CI が生成） |
| `FIREBASERC` | `.firebaserc` の JSON 全文（`hosting.enterprise` の target マッピングを含む） |

`PROJECT_ID` / `GCLOUD_SERVICE_KEY` は user / partner と共通。Environment ごと（`development` / `production`）に設定する。

## 2. マージ前チェックリスト（必須）

`development` へマージして CI を走らせる**前**に、対象 Firebase プロジェクトごとに以下を完了すること。  
未設定のままマージすると **CI 失敗・空 `.env` ビルド・Hosting target 未検出** が起き得る。

### 2.1 Firebase / GCP

- [ ] **Hosting サイト作成** — サイト ID = `<PROJECT_ID>-enterprise`（[§3.1](#31-hosting-サイトを作成する)。Terraform 管理プロジェクトは `terraform apply`）
- [ ] **`firebase target:apply`** — `hosting enterprise` → 上記サイト ID（Terraform では作成のみ。target 紐づけは CLI）
- [ ] **`FIREBASERC` 更新** — GitHub Environment の Variable に `hosting.enterprise` を反映
- [ ] **Firestore / Storage ルール** — Phase 1 の `/enterprises` ルールがデプロイ済み（[§5](#5-関連-workflow-初回のみ)）
- [ ] **Functions** — `createEnterprise` / `getEnterpriseByDomain` がデプロイ済み（ドメイン解決・オンボーディング用）

### 2.2 GitHub Actions（Environment 単位）

- [ ] **`ENTERPRISE_ENV`** — Variable を新規登録（[§4](#4-enterprise_env-項目リスト)）
- [ ] **`FIREBASERC`** — `enterprise` target を追記済み（[§3.3](#33-firebaserc-を-github-variable-に反映)）
- [ ] **`PROJECT_ID`** — 既存設定と一致していること
- [ ] **`GCLOUD_SERVICE_KEY`** — Secret が有効であること

### 2.3 ドメイン（本番相当環境）

- [ ] **Firebase Hosting にカスタムドメイン追加** — サブドメイン方式（`*.shokujii.com` 等）
- [ ] **DNS 設定** — Firebase Console の指示どおり
- [ ] **Firestore `/enterprises`** — `subdomain` / `custom_domain` が接続ドメインと一致（テナント解決用）

### 2.4 初回デプロイ確認

- [ ] **`Deploy enterprise` workflow_dispatch** — 手動実行で成功
- [ ] **Hosting URL / カスタムドメイン** — アプリが表示される
- [ ] **テスト企業作成** — [§11](#11-テスト企業の作成-createenterprise) で `createEnterprise` を実行済み
- [ ] **`getEnterpriseByDomain`** — テスト enterprise のドメインで Callable が成功（Functions デプロイ後）

### 2.5 App Check / reCAPTCHA（Phase 2。ログイン濫用対策）

ログイン画面の動作確認のみなら **必須ではない**（`VITE_RECAPTCHA_SITE_KEY` 未設定時は App Check 初期化をスキップ、`ENTERPRISE_APP_CHECK_ENFORCE` 既定は `false`）。本番相当で OTP / ドメイン解決 Callable の濫用対策を有効化する場合は以下を実施する。

- [ ] **Terraform apply** — API 有効化、reCAPTCHA Enterprise キー、App Check プロバイダ登録（[§10.1](#101-terraform-apply) / [§10.2](#102-app-check-プロバイダ登録)）
- [ ] **`ENTERPRISE_ENV`** — `VITE_RECAPTCHA_SITE_KEY` を追加し enterprise Hosting を再デプロイ（[§10.3](#103-enterprise_env-と-hosting-再デプロイ)）
- [ ] **App Check メトリクス** — Firebase Console → App Check → Metrics でトークン記録を確認（第1段階）
- [ ] **（第2段階）Functions** — メトリクス確認後、`ENTERPRISE_APP_CHECK_ENFORCE=true` で Functions を再デプロイ（[§10.5](#105-2段階ロールアウト-enforce)）

> Console で App Check を先行登録している場合は [terraform/README.md](../../terraform/README.md) の import 例で Terraform に取り込む。Terraform 未使用時のみ §10.2 の Console 手順をフォールバックとして利用する。

## 3. Firebase Hosting セットアップ

### 3.1 Hosting サイトを作成する

**方法A: Terraform（推奨）**

[terraform/firebase.tf](../../terraform/firebase.tf) で `google_firebase_hosting_site.enterprise` を定義済み。  
`site_id = "${var.project}-enterprise"`（partner の `-admin` と同型）。

```bash
cd terraform
gcloud config set project <PROJECT_ID>
terraform plan   # Add: google_firebase_hosting_site.enterprise / google_recaptcha_enterprise_key.enterprise_app_check を確認
terraform apply
```

**`terraform.tfvars` の `enterprise_base_domain`**

| 環境 | 設定 |
| :-- | :-- |
| development / production | ベースドメイン（例: `shokujii.com` / `shokujii.jp`）。reCAPTCHA の `allowed_domains` に使用 |
| sandbox | **未設定可**（空文字のまま）。`<PROJECT_ID>-enterprise.web.app` のみキーに登録される |

dev / production では [terraform/main.tf](../../terraform/main.tf) の `enterprise_base_domain` を手動で追記してから `apply` する。詳細な import 手順は [terraform/README.md](../../terraform/README.md) を参照。

| 状況 | 手順 |
| :-- | :-- |
| 新規プロジェクト（`init.sh` 後） | 上記 `apply` でサイト作成 |
| Terraform 管理済み・site 未作成 | plan で Add 1 件 → `apply` |
| Console 等で **既に** `<PROJECT_ID>-enterprise` がある | [terraform/README.md](../../terraform/README.md) の import を実行してから `apply` |

```bash
terraform import google_firebase_hosting_site.enterprise "projects/<PROJECT_ID>/sites/<PROJECT_ID>-enterprise"
```

reCAPTCHA Enterprise キーを Console 等で **既に** 作成している場合:

```bash
terraform import google_recaptcha_enterprise_key.enterprise_app_check "projects/<PROJECT_ID>/keys/<KEY_ID>"
```

**方法B: Firebase Console（Terraform 未使用時）**

1. [Firebase Console](https://console.firebase.google.com/) → 対象プロジェクト
2. **Hosting** → **サイトを追加**
3. サイト ID に **`<PROJECT_ID>-enterprise`** を入力して作成

後から Terraform 管理に載せる場合は、上記 **import** を実行する。

### 3.2 target を紐づける

ローカル（Firebase CLI が使える環境）で、**プロジェクトごとに 1 回**実行する。

```bash
firebase login
firebase use <PROJECT_ID>

firebase target:apply hosting enterprise <PROJECT_ID>-enterprise
```

**sandbox の例**

```bash
firebase use bokudeli-event-yasu-2510
firebase target:apply hosting enterprise bokudeli-event-yasu-2510-enterprise
```

実行後、ローカルの `.firebaserc` に次のような対応が追加される。

```json
{
  "projects": {
    "default": "bokudeli-event-yasu-2510"
  },
  "targets": {
    "bokudeli-event-yasu-2510": {
      "hosting": {
        "user": ["bokudeli-event-yasu-2510"],
        "partner": ["bokudeli-event-yasu-2510-admin"],
        "enterprise": ["bokudeli-event-yasu-2510-enterprise"]
      }
    }
  }
}
```

> 上記の `user` / `partner` の配列は環境により異なる。**実際の `.firebaserc` 全文**を GitHub Variable に登録すること。

### 3.3 FIREBASERC を GitHub Variable に反映

`.firebaserc` はリポジトリにコミットしない。CI が **`vars.FIREBASERC`** から生成する。

1. GitHub リポジトリ → **Settings** → **Secrets and variables** → **Actions**
2. **Environments** タブ → `development` または `production`（sandbox リポジトリも同様に Environment を使う）
3. Variable **`FIREBASERC`** を編集
4. `target:apply` 後の `.firebaserc` **JSON 全文**を貼り付け
5. **`targets.<PROJECT_ID>.hosting.enterprise`** に `<PROJECT_ID>-enterprise` が含まれることを確認

## 4. ENTERPRISE_ENV 項目リスト

GitHub Environment Variable **`ENTERPRISE_ENV`** に、`enterprise/.env` と同じ **KEY=VALUE 形式（複数行）** で登録する。  
CI は [deploy_enterprise.yml](../../.github/workflows/deploy_enterprise.yml) の Build 前に `enterprise/.env` へ書き出す。

### 4.1 作成手順

1. 同 Environment の **`USER_ENV`** をコピーしてベースにする（Firebase 接続系は同一プロジェクトなら共通）
2. エンプラ固有の値を差し替える（特に `VITE_ORIGIN_HOST`）
3. ローカルで `enterprise/.env.development` として保存し、`npm -w enterprise run build -- -m development` でビルド確認
4. 確認後、**改行付き全文**を `ENTERPRISE_ENV` に登録

### 4.2 必須項目

| 変数名 | 説明 | 設定の目安 |
| :-- | :-- | :-- |
| `VITE_API_KEY` | Firebase Web API Key | `USER_ENV` と同値 |
| `VITE_AUTH_DOMAIN` | Firebase Auth ドメイン | `USER_ENV` と同値 |
| `VITE_PROJECT_ID` | GCP プロジェクト ID | `PROJECT_ID` と同値 |
| `VITE_STORAGE_BUCKET` | Firebase Storage バケット | `USER_ENV` と同値 |
| `VITE_MESSAGE_SENDER_ID` | FCM Sender ID | `USER_ENV` と同値 |
| `VITE_APP_ID` | Firebase App ID | `USER_ENV` と同値 |
| `VITE_MEASUREMENT_ID` | Google Analytics（使用時） | `USER_ENV` と同値 |
| `VITE_ORIGIN_HOST` | エンプラアプリの公開ホスト名 | **エンプラ用ドメイン**（下表参照） |
| `VITE_ENTERPRISE_BASE_DOMAIN` | テナント用サブドメインのベースドメイン | 本番: `shokujii.jp` 等、dev: `shokujii.com` 等。**sandbox（カスタムドメイン前提）は未設定可**。Functions 側の `ENTERPRISE_BASE_DOMAIN` と同値にする |

### 4.3 機能利用時に必要な項目

| 変数名 | 説明 | 設定の目安 |
| :-- | :-- | :-- |
| `VITE_RECAPTCHA_SITE_KEY` | App Check（reCAPTCHA Enterprise）サイトキー | Phase 2 以降必須。[§10](#10-app-check-phase-2) 参照 |
| `VITE_CHANNEL_IO_PLUGIN_KEY` | Channel.io | 利用する場合 `USER_ENV` と同値 |
| `VITE_TINYMCE_API_KEY` | TinyMCE エディタ | イベント編集を使う場合 |
| `VITE_POSTCODE_API_KEY` | 郵便番号 API | 住所入力を使う場合 |
| `VITE_SLACK_BOT_FUNCTION_URL` | Slack Bot Cloud Run URL | Slack 連携を使う場合 |

### 4.4 ローカル開発・エミュレータ用（CI では通常不要）

| 変数名 | 説明 |
| :-- | :-- |
| `VITE_ENTERPRISE_SUBDOMAIN` | ローカル開発専用。テスト企業の `subdomain`（例: `company-a`）。設定時は `getEnterpriseByDomain` に `${VITE_ENTERPRISE_SUBDOMAIN}.${VITE_ENTERPRISE_BASE_DOMAIN}` を渡す。[§4.7](#47-ローカル開発での-enterprise-解決) 参照。**`ENTERPRISE_ENV` には登録しない** |
| `VITE_FIREBASE_FUNCTIONS_EMULATOR_HOST` | Functions エミュレータ |
| `VITE_FIRESTORE_EMULATOR_HOST` | Firestore エミュレータ |
| `VITE_FIREBASE_STORAGE_EMULATOR_HOST` | Storage エミュレータ |
| `VITE_FIREBASE_AUTH_EMULATOR_HOST` | Auth エミュレータ |

### 4.5 不要な項目

| 変数名 | 理由 |
| :-- | :-- |
| `VITE_STRIPE_PUBLISHABLE_KEY` | 現行コード未使用（[Stripe 環境構築手順](../07_リファクタリング/03_stripe決済の環境構築手順.md) §4） |

### 4.6 VITE_ORIGIN_HOST の例

エンプラは **1 ビルド・複数テナント（サブドメイン）** 方式。  
`VITE_ORIGIN_HOST` は URL 生成（共有リンク等）の基準ホストとして使う。

| 環境 | 例 |
| :-- | :-- |
| sandbox | Firebase Hosting のデフォルト URL ホスト、または検証用サブドメイン |
| development | `enterprise.shokujii.com` 等（dev 用ドメイン） |
| production | `enterprise.shokujii.jp` 等（本番ドメイン） |

テナントごとの `company-a.shokujii.com` は **`getEnterpriseByDomain`** で解決する。  
Hosting に接続したドメインと Firestore `/enterprises` の `subdomain` / `custom_domain` を一致させる（[02_全体構成 §2](./02_エンタープライズ_全体構成・アーキテクチャ.md)）。

### 4.7 ローカル開発・sandbox での enterprise 解決

`getEnterpriseByDomain` は `*.{ENTERPRISE_BASE_DOMAIN}` のサブドメイン抽出と `custom_domain` 完全一致のみで判定する（ベースドメインは環境変数。[02_全体構成 §2.4](./02_エンタープライズ_全体構成・アーキテクチャ.md) 参照）。`localhost` や Firebase Hosting デフォルト URL（`<PROJECT_ID>-enterprise.web.app`）ではそのままでは not-found になる。

| 環境 | 推奨手順 |
| :-- | :-- |
| **sandbox / CI デプロイ後** | [§11](#11-テスト企業の作成-createenterprise) の `createEnterprise` リクエストに `custom_domain: "<PROJECT_ID>-enterprise.web.app"` を含める（推奨）。Hosting デフォルト URL で `getEnterpriseByDomain` がヒットする。事後更新する場合は Firestore Console で `/enterprises/{id}` の `custom_domain` を更新。`ENTERPRISE_BASE_DOMAIN` は未設定でよい |
| **ローカル開発** | `enterprise/.env.development` に `VITE_ENTERPRISE_SUBDOMAIN=company-a`（テスト企業の `subdomain`）を設定。フロントは `window.location.hostname` の代わりに `${VITE_ENTERPRISE_SUBDOMAIN}.${VITE_ENTERPRISE_BASE_DOMAIN}` を Callable に渡す |
| **未ヒット時** | 全画面エラーページ。「企業が見つかりません。ご利用の URL をご確認のうえ、貴社の管理者にお問い合わせください」。デフォルトドメイン（例: `enterprise.shokujii.com`）も MVP では同じ案内（企業選択 UI は作らない） |
| **Hosting プレビューチャネル** | ホスト名が動的なため MVP では使用しない方針 |

**Functions 側の環境変数**: `ENTERPRISE_BASE_DOMAIN`（`defineString`）を `deploy_functions.yml` の環境変数（または `.env.<project>` ファイル）に追加する。フロントの `VITE_ENTERPRISE_BASE_DOMAIN` と同値にすること。

## 5. 関連 workflow（初回のみ）

Phase 1 では Hosting 以外も変更している。初回環境では以下もデプロイが必要な場合がある。

| 内容 | workflow / コマンド |
| :-- | :-- |
| Firestore ルール（`/enterprises`） | [`deploy_firestore.yml`](../../.github/workflows/deploy_firestore.yml) または `firebase deploy --only firestore` |
| Storage ルール（`/enterprises`） | [`deploy_storage.yml`](../../.github/workflows/deploy_storage.yml) または `firebase deploy --only storage` |
| Functions（`createEnterprise` 等） | [`deploy_functions.yml`](../../.github/workflows/deploy_functions.yml) |

**推奨順序（初回）**

1. Firestore / Storage ルール
2. Functions（`createEnterprise` / `getEnterpriseByDomain` 等）
3. Terraform（enterprise Hosting サイト + reCAPTCHA Enterprise キー。[§3.1](#31-hosting-サイトを作成する) / [§10.1](#101-terraform-apply)）
4. `firebase target:apply` と `FIREBASERC` 更新（[§3.2](#32-target-を紐づける)〜[§3.3](#33-firebaserc-を-github-variable-に反映)）
5. （Phase 2）App Check Console 登録 + `ENTERPRISE_ENV` に `VITE_RECAPTCHA_SITE_KEY` 追加（[§10](#10-app-check-phase-2)）
6. enterprise Hosting デプロイ（[§6](#6-デプロイの実行)）
7. テスト企業作成（[§11](#11-テスト企業の作成-createenterprise)）
8. （任意・Phase 2 第2段階）App Check enforce 有効化（[§10.5](#105-2段階ロールアウト-enforce)）

## 6. デプロイの実行

### 6.1 自動トリガー

[`deploy_enterprise.yml`](../../.github/workflows/deploy_enterprise.yml) は次で起動する。

- **`development` / `production` ブランチへの push** かつ `enterprise/**` または `base/**` の変更
- **`workflow_dispatch`**（手動）

### 6.2 初回は手動実行を推奨

1. GitHub → **Actions** → **Deploy enterprise**
2. **Run workflow**
3. Environment: `development`（または sandbox リポジトリの Environment 名）
4. 成功ログで `hosting:enterprise` のデプロイ完了を確認

### 6.3 ローカルでのデプロイ（任意）

```bash
# .firebaserc と enterprise/.env を手元で用意したうえで
npm -w enterprise run build -- -m development
firebase --project <PROJECT_ID> deploy --only hosting:enterprise
```

## 8. トラブルシュート

| 症状 | 想定原因 | 対処 |
| :-- | :-- | :-- |
| `Hosting site or target enterprise not detected` | `FIREBASERC` に `enterprise` target がない | §3.2〜3.3 を再実施 |
| `Error 409` で enterprise site 作成失敗 | Console 等で site 済み・Terraform state 未 import | §3.1 の import 後に `apply` |
| ビルド成功・Firebase 接続エラー | `ENTERPRISE_ENV` 未設定 or 誤り | §4 を確認。空 `.env` になっていないか Actions ログを見る |
| デプロイ成功だが画面が真っ白 | `VITE_*` 欠落 | §4.2 の必須項目を確認 |
| ドメインは開くが企業情報が取れない | Hosting ドメインと Firestore の不一致、Functions 未デプロイ、テスト企業未作成 | §2.1 / §2.3 / §5 / [§11](#11-テスト企業の作成-createenterprise) |
| CI は `development` のみ反応する | workflow の branch 設定 | sandbox では `workflow_dispatch` を使うか、対象ブランチへ merge |
| Callable `app-check` / `failed-precondition` | App Check Console 未登録、または enforce のみ先行 | [§10](#10-app-check-phase-2)。第1段階では `ENTERPRISE_APP_CHECK_ENFORCE=false` を維持 |
| reCAPTCHA ドメインエラー | `allowed_domains` に Hosting ホストが未登録 | `terraform.tfvars` の `enterprise_base_domain` または Console でドメイン追加 |
| App Check が初期化されない | `VITE_RECAPTCHA_SITE_KEY` 未設定 | [§4.3](#43-機能利用時に必要な項目) / [§10.3](#103-enterprise_env-と-hosting-再デプロイ) |
| `createEnterprise` が `permission-denied` | 実行者 UID が `support_user_ids` に含まれない | Firestore `config/global` を確認。[§11.1](#111-前提) |

## 10. App Check（Phase 2）

未認証 Callable（`getEnterpriseByDomain` / `requestEnterpriseEmailLogin` / `confirmEnterpriseEmailLogin`）の濫用対策。`04_認証` §8-2 / `08_実装計画` Phase 2-5 が正本。

**Terraform でできること / できないこと**

| 項目 | Terraform | 手動 / 別作業 |
| :-- | :-- | :-- |
| API 有効化（`recaptchaenterprise` / `firebaseappcheck`） | [terraform/api.tf](../../terraform/api.tf) | — |
| reCAPTCHA Enterprise キー | [terraform/recaptcha_enterprise.tf](../../terraform/recaptcha_enterprise.tf) | — |
| App Check への Web アプリ登録 | [terraform/firebase_app_check.tf](../../terraform/firebase_app_check.tf) | Console 先行登録時は import |
| クライアント反映 | — | `ENTERPRISE_ENV` + Hosting 再デプロイ |
| Callable enforce | — | `ENTERPRISE_APP_CHECK_ENFORCE` + Functions 再デプロイ |

### 10.1 Terraform apply

1. `terraform.tfvars` に `enterprise_base_domain` を設定（dev / production。sandbox は省略可。[§3.1](#31-hosting-サイトを作成する)）
2. `cd terraform && terraform plan`
   - Add または既存管理: `google_recaptcha_enterprise_key.enterprise_app_check`
   - Add または既存管理: `google_firebase_app_check_recaptcha_enterprise_config.enterprise_web`
   - API 2件（`recaptchaenterprise.googleapis.com` / `firebaseappcheck.googleapis.com`）が有効化されること
   - **Destroy 0** であること
3. `terraform apply`
4. 公開サイトキーを取得:

```bash
terraform output enterprise_recaptcha_site_key
```

> output は **公開サイトキー**（`6Lf...` 形式）を返す。[Google Cloud Console → reCAPTCHA Enterprise](https://console.cloud.google.com/security/recaptcha) の表示と一致することを確認する。

### 10.2 App Check プロバイダ登録

**Terraform（推奨）**: `terraform apply` で [terraform/firebase_app_check.tf](../../terraform/firebase_app_check.tf) が Web アプリ（`google_firebase_web_app.default`）と reCAPTCHA Enterprise キーを紐付ける。

Console で App Check を **先行登録済み** の場合は 409 を避けるため [terraform/README.md](../../terraform/README.md) の import 例で state に取り込んでから apply する。

**Console（フォールバック）**: Terraform を使わない場合のみ以下を手動実施する。

1. [Firebase Console](https://console.firebase.google.com/) → 対象プロジェクト → **App Check**
2. **Apps** → Web アプリ（[terraform/firebase.tf](../../terraform/firebase.tf) の `google_firebase_web_app.default` と同一）を選択
3. **Register**（未登録の場合）→ プロバイダ **reCAPTCHA Enterprise** を選択
4. §10.1 のサイトキーを紐付け
5. **Metrics** タブでリクエストが記録されることを確認（§10.3 の Hosting 再デプロイ後）

### 10.3 ENTERPRISE_ENV と Hosting 再デプロイ

1. GitHub Environment Variable **`ENTERPRISE_ENV`** に `VITE_RECAPTCHA_SITE_KEY=<サイトキー>` を追加（[§4.3](#43-機能利用時に必要な項目)）
2. **Deploy enterprise** を再実行（または [§6.3](#63-ローカルでのデプロイ任意)）
3. ブラウザ DevTools → Network で App Check トークン取得エラーがないことを確認

`VITE_RECAPTCHA_SITE_KEY` が空の場合、クライアントは App Check を初期化しない（`enterprise/src/firebaseAppCheck.ts`）。

### 10.4 ローカル開発（debug token）

1. `enterprise/.env.development` で dev モードのみ App Check debug token が有効（コード側で `import.meta.env.DEV` 時に設定）
2. ブラウザコンソールに表示される debug token を Firebase Console → App Check → Apps → Web アプリ → **Manage debug tokens** に登録
3. エミュレータ利用時も同手順

### 10.5 2段階ロールアウト（enforce）

| 段階 | 設定 | 確認 |
| :-- | :-- | :-- |
| **第1段階** | クライアント App Check 初期化のみ。`ENTERPRISE_APP_CHECK_ENFORCE` は **`false`（既定）** | Console メトリクスで正規トークン率を数日確認 |
| **第2段階** | Functions 環境変数 `ENTERPRISE_APP_CHECK_ENFORCE=true` を設定し Functions を再デプロイ | 3 Callable（ドメイン解決 / OTP 送信 / OTP 確認）が App Check 付きで成功 |

enforce 対象は上記3 Callable のみ。**PF Callable には付けない**（`userProfile.ts` 等の既存方針と整合）。`createEnterprise` 等の認証済み Callable は enforce 対象外（`04_認証` §8-3）。

Functions 側の判定: `functions/default/src/utils/enterpriseAppCheck.ts`（`defineString('ENTERPRISE_APP_CHECK_ENFORCE', { default: 'false' })`）。

### 10.6 sandbox での custom_domain（enterprise 解決と併用）

§4.7 / [§11](#11-テスト企業の作成-createenterprise) と合わせ、`createEnterprise` の `custom_domain` に `<PROJECT_ID>-enterprise.web.app` を指定すると、デプロイ後の Hosting URL で `getEnterpriseByDomain` が成功する。

## 11. テスト企業の作成（createEnterprise）

Hosting デプロイ後、ログイン検証のために **テスト用 enterprise ドキュメントと初代 admin** を作成する。API 仕様の正本は [04_オンボーディング](./04_エンタープライズ_詳細仕様_オンボーディング.md) §3。

### 11.1 前提

| 項目 | 内容 |
| :-- | :-- |
| Functions | `createEnterprise` がデプロイ済み（[§5](#5-関連-workflow-初回のみ)） |
| 実行者 | Firebase Auth でログイン済み。**UID が Firestore `config/global.support_user_ids` に含まれる**サポートアカウントのみ実行可 |
| 認証方式 | Callable は `request.auth` 必須。`functions:shell` では auth コンテキストを付けにくいため、**Client SDK + support ログイン**を推奨 |

> **将来**: 運営用 CLI（`scripts/create-enterprise.mjs` 等）のリポジトリ整備は後続タスク。現状は一時スクリプトまたは DevTools からの Callable 呼び出しで運用する。

### 11.2 リクエスト JSON 例（sandbox）

`<PROJECT_ID>` / メールアドレス / ドメインは環境に合わせて置換する。型の正本は [common/src/apis/enterprise.ts](../../common/src/apis/enterprise.ts) の `CreateEnterpriseRequest`。

```json
{
  "enterprise_id": "company-a",
  "company_name": "テスト株式会社A",
  "subdomain": "company-a",
  "custom_domain": "bokudeli-event-yasu-2510-enterprise.web.app",
  "allowed_email_domains": ["example.com"],
  "theme_color": "#1976D2",
  "initial_subsidy_settings": {
    "type": "fixed",
    "value": 500,
    "monthly_limit_per_user": 10000
  },
  "initial_admin": {
    "email": "admin@example.com",
    "display_name": "管理者太郎",
    "department": "総務部"
  }
}
```

| フィールド | sandbox での注意 |
| :-- | :-- |
| `custom_domain` | `<PROJECT_ID>-enterprise.web.app` を指定すると §4.7 の事後 Firestore 更新が不要 |
| `subdomain` | DNS ラベル規則・予約語に注意（`common/src/schemas/Enterprise.ts` の `RESERVED_ENTERPRISE_SUBDOMAINS`） |
| `initial_admin.email` | `allowed_email_domains` のいずれかと一致すること |
| `initial_subsidy_settings.type` | `fixed` または `percentage`（percentage 時は 0〜100） |

### 11.3 実行方法（Client SDK）

**手順概要**

1. サポートアカウントで Firebase Auth にログイン（user アプリ等、同一 Firebase プロジェクトに接続されたクライアント）
2. `httpsCallable(functions, 'createEnterprise')` に §11.2 の payload を渡して実行
3. レスポンスの `enterprise_id` / `initial_admin_user_id` を控える

**一時スクリプトの骨子（Node / TypeScript）**

```typescript
import { initializeApp } from 'firebase/app'
import { getAuth, signInWithEmailAndPassword } from 'firebase/auth'
import { getFunctions, httpsCallable } from 'firebase/functions'

// 1. 同一プロジェクトの Firebase 設定で initializeApp
// 2. signInWithEmailAndPassword(auth, supportEmail, supportPassword)
// 3. httpsCallable(getFunctions(app, 'asia-northeast1'), 'createEnterprise')(payload)
```

リージョンは Functions デプロイ先（`asia-northeast1`）に合わせる。

### 11.4 成功確認

| # | 確認 | 期待結果 |
| :-- | :-- | :-- |
| 1 | Callable レスポンス | `enterprise_id` / `initial_admin_user_id` が返る |
| 2 | Firestore | `/enterprises/{enterprise_id}` が作成されている |
| 3 | Auth / member | `/enterprises/{id}/members/{uid}`、custom claims に `enterprise_id` / `enterprise_role: admin` |
| 4 | Hosting URL | `<PROJECT_ID>-enterprise.web.app`（または `custom_domain`）で企業名・テーマが表示 |
| 5 | OTP ログイン | `initial_admin.email` で pass-code ログイン成功（SendGrid テンプレート設定済みであること。[Phase2 検証](../テスト/08_エンタープライズ_Phase2_検証シナリオ.md)） |

### 11.5 よくあるエラー

| エラー | 原因 | 対処 |
| :-- | :-- | :-- |
| `permission-denied` / `support only` | 実行者が support ではない | `config/global.support_user_ids` に UID を追加 |
| `already-exists` | `enterprise_id` / `subdomain` / `custom_domain` 重複 | 別 ID を使用 |
| `invalid-argument` | subdomain 形式、メールドメイン不一致、割引設定不正 | [04_オンボーディング](./04_エンタープライズ_詳細仕様_オンボーディング.md) §3.3 を確認 |
