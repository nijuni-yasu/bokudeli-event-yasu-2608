## 1. 命名規則

### 1.1 Firebase Hosting サイト ID

**`<GCP プロジェクト ID>-enterprise`** とする。

| 環境 | GCP プロジェクト ID 例 | Hosting サイト ID |
| :-- | :-- | :-- |
| sandbox | `bokudeli-event-yasu-2510` | `bokudeli-event-yasu-2510-enterprise` |
| development | `bokudeli-event-dev` | `bokudeli-event-dev-enterprise` |
| production | `bokudeli-event` | `bokudeli-event-enterprise` |

> 既存 Hosting サイトとの対応（参考）  
> - user: プロジェクト ID と同名（例: `bokudeli-event-dev`）  
> - partner: `<PROJECT_ID>-admin`（例: `bokudeli-event-dev-admin`）  
> - enterprise: **`<PROJECT_ID>-enterprise`**

### 1.2 Firebase Hosting target 名

リポジトリ内の target 名は **`enterprise`** 固定（`firebase.json` / CI の `--only hosting:enterprise` と一致）。

### 1.3 GitHub Actions Variable 名

| 変数名 | 説明 |
| :-- | :-- |
| `ENTERPRISE_ENV` | `enterprise/.env` の内容（ビルド時に CI が生成） |
| `FIREBASERC` | `.firebaserc` の JSON 全文（`hosting.enterprise` の target マッピングを含む） |

`PROJECT_ID` / `GCLOUD_SERVICE_KEY` は user / partner と共通。Environment ごと（`development` / `production`）に設定する。

## 2. マージ前チェックリスト（必須）

`development` へマージして CI を走らせる**前**に、対象 Firebase プロジェクトごとに以下を完了すること。  
未設定のままマージすると **CI 失敗・空 `.env` ビルド・Hosting target 未検出** が起き得る。

### 2.1 Firebase / GCP

- [ ] **Hosting サイト作成** — サイト ID = `<PROJECT_ID>-enterprise`（[§3.1](#31-hosting-サイトを作成する)。Terraform 管理プロジェクトは `terraform apply`）
- [ ] **`firebase target:apply`** — `hosting enterprise` → 上記サイト ID（Terraform では作成のみ。target 紐づけは CLI）
- [ ] **`FIREBASERC` 更新** — GitHub Environment の Variable に `hosting.enterprise` を反映
- [ ] **Firestore / Storage ルール** — Phase 1 の `/enterprises` ルールがデプロイ済み（[§5](#5-関連-workflow-初回のみ)）
- [ ] **Functions** — `createEnterprise` / `getEnterpriseByDomain` がデプロイ済み（ドメイン解決・オンボーディング用）

### 2.2 GitHub Actions（Environment 単位）

- [ ] **`ENTERPRISE_ENV`** — Variable を新規登録（[§4](#4-enterprise_env-項目リスト)）
- [ ] **`FIREBASERC`** — `enterprise` target を追記済み（[§3.3](#33-firebaserc-を-github-variable-に反映)）
- [ ] **`PROJECT_ID`** — 既存設定と一致していること
- [ ] **`GCLOUD_SERVICE_KEY`** — Secret が有効であること

### 2.3 ドメイン（本番相当環境）

- [ ] **Firebase Hosting にカスタムドメイン追加** — サブドメイン方式（`*.shokujii.com` 等）
- [ ] **DNS 設定** — Firebase Console の指示どおり
- [ ] **Firestore `/enterprises`** — `subdomain` / `custom_domain` が接続ドメインと一致（テナント解決用）

### 2.4 初回デプロイ確認

- [ ] **`Deploy enterprise` workflow_dispatch** — 手動実行で成功
- [ ] **Hosting URL / カスタムドメイン** — アプリが表示される
- [ ] **`getEnterpriseByDomain`** — テスト用 enterprise ドキュメントでドメイン解決ができる（Functions デプロイ後）

## 3. Firebase Hosting セットアップ

### 3.1 Hosting サイトを作成する

**方法A: Terraform（推奨）**

[terraform/firebase.tf](../../terraform/firebase.tf) で `google_firebase_hosting_site.enterprise` を定義済み。  
`site_id = "${var.project}-enterprise"`（partner の `-admin` と同型）。

```bash
cd terraform
gcloud config set project <PROJECT_ID>
terraform plan   # Add: google_firebase_hosting_site.enterprise を確認
terraform apply
```

| 状況 | 手順 |
| :-- | :-- |
| 新規プロジェクト（`init.sh` 後） | 上記 `apply` でサイト作成 |
| Terraform 管理済み・site 未作成 | plan で Add 1 件 → `apply` |
| Console 等で **既に** `<PROJECT_ID>-enterprise` がある | [terraform/README.md](../../terraform/README.md) の import を実行してから `apply` |

```bash
terraform import google_firebase_hosting_site.enterprise "projects/<PROJECT_ID>/sites/<PROJECT_ID>-enterprise"
```

**方法B: Firebase Console（Terraform 未使用時）**

1. [Firebase Console](https://console.firebase.google.com/) → 対象プロジェクト
2. **Hosting** → **サイトを追加**
3. サイト ID に **`<PROJECT_ID>-enterprise`** を入力して作成

後から Terraform 管理に載せる場合は、上記 **import** を実行する。

### 3.2 target を紐づける

ローカル（Firebase CLI が使える環境）で、**プロジェクトごとに 1 回**実行する。

```bash
firebase login
firebase use <PROJECT_ID>

firebase target:apply hosting enterprise <PROJECT_ID>-enterprise
```

**sandbox の例**

```bash
firebase use bokudeli-event-yasu-2510
firebase target:apply hosting enterprise bokudeli-event-yasu-2510-enterprise
```

実行後、ローカルの `.firebaserc` に次のような対応が追加される。

```json
{
  "projects": {
    "default": "bokudeli-event-yasu-2510"
  },
  "targets": {
    "bokudeli-event-yasu-2510": {
      "hosting": {
        "user": ["bokudeli-event-yasu-2510"],
        "partner": ["bokudeli-event-yasu-2510-admin"],
        "enterprise": ["bokudeli-event-yasu-2510-enterprise"]
      }
    }
  }
}
```

> 上記の `user` / `partner` の配列は環境により異なる。**実際の `.firebaserc` 全文**を GitHub Variable に登録すること。

### 3.3 FIREBASERC を GitHub Variable に反映

`.firebaserc` はリポジトリにコミットしない。CI が **`vars.FIREBASERC`** から生成する。

1. GitHub リポジトリ → **Settings** → **Secrets and variables** → **Actions**
2. **Environments** タブ → `development` または `production`（sandbox リポジトリも同様に Environment を使う）
3. Variable **`FIREBASERC`** を編集
4. `target:apply` 後の `.firebaserc` **JSON 全文**を貼り付け
5. **`targets.<PROJECT_ID>.hosting.enterprise`** に `<PROJECT_ID>-enterprise` が含まれることを確認

## 4. ENTERPRISE_ENV 項目リスト

GitHub Environment Variable **`ENTERPRISE_ENV`** に、`enterprise/.env` と同じ **KEY=VALUE 形式（複数行）** で登録する。  
CI は [deploy_enterprise.yml](../../.github/workflows/deploy_enterprise.yml) の Build 前に `enterprise/.env` へ書き出す。

### 4.1 作成手順

1. 同 Environment の **`USER_ENV`** をコピーしてベースにする（Firebase 接続系は同一プロジェクトなら共通）
2. エンプラ固有の値を差し替える（特に `VITE_ORIGIN_HOST`）
3. ローカルで `enterprise/.env.development` として保存し、`npm -w enterprise run build -- -m development` でビルド確認
4. 確認後、**改行付き全文**を `ENTERPRISE_ENV` に登録

### 4.2 必須項目

| 変数名 | 説明 | 設定の目安 |
| :-- | :-- | :-- |
| `VITE_API_KEY` | Firebase Web API Key | `USER_ENV` と同値 |
| `VITE_AUTH_DOMAIN` | Firebase Auth ドメイン | `USER_ENV` と同値 |
| `VITE_PROJECT_ID` | GCP プロジェクト ID | `PROJECT_ID` と同値 |
| `VITE_STORAGE_BUCKET` | Firebase Storage バケット | `USER_ENV` と同値 |
| `VITE_MESSAGE_SENDER_ID` | FCM Sender ID | `USER_ENV` と同値 |
| `VITE_APP_ID` | Firebase App ID | `USER_ENV` と同値 |
| `VITE_MEASUREMENT_ID` | Google Analytics（使用時） | `USER_ENV` と同値 |
| `VITE_ORIGIN_HOST` | エンプラアプリの公開ホスト名 | **エンプラ用ドメイン**（下表参照） |
| `VITE_ENTERPRISE_BASE_DOMAIN` | テナント用サブドメインのベースドメイン | 本番: `shokujii.jp` 等、dev: `shokujii.com` 等。**sandbox（カスタムドメイン前提）は未設定可**。Functions 側の `ENTERPRISE_BASE_DOMAIN` と同値にする |

### 4.3 機能利用時に必要な項目

| 変数名 | 説明 | 設定の目安 |
| :-- | :-- | :-- |
| `VITE_RECAPTCHA_SITE_KEY` | App Check（reCAPTCHA Enterprise）サイトキー | Phase 2 以降必須。[§10](#10-app-check-phase-2) 参照 |
| `VITE_CHANNEL_IO_PLUGIN_KEY` | Channel.io | 利用する場合 `USER_ENV` と同値 |
| `VITE_TINYMCE_API_KEY` | TinyMCE エディタ | イベント編集を使う場合 |
| `VITE_POSTCODE_API_KEY` | 郵便番号 API | 住所入力を使う場合 |
| `VITE_SLACK_BOT_FUNCTION_URL` | Slack Bot Cloud Run URL | Slack 連携を使う場合 |

### 4.4 ローカル開発・エミュレータ用（CI では通常不要）

| 変数名 | 説明 |
| :-- | :-- |
| `VITE_ENTERPRISE_SUBDOMAIN` | ローカル開発専用。テスト企業の `subdomain`（例: `company-a`）。設定時は `getEnterpriseByDomain` に `${VITE_ENTERPRISE_SUBDOMAIN}.${VITE_ENTERPRISE_BASE_DOMAIN}` を渡す。[§4.7](#47-ローカル開発での-enterprise-解決) 参照。**`ENTERPRISE_ENV` には登録しない** |
| `VITE_FIREBASE_FUNCTIONS_EMULATOR_HOST` | Functions エミュレータ |
| `VITE_FIRESTORE_EMULATOR_HOST` | Firestore エミュレータ |
| `VITE_FIREBASE_STORAGE_EMULATOR_HOST` | Storage エミュレータ |
| `VITE_FIREBASE_AUTH_EMULATOR_HOST` | Auth エミュレータ |

### 4.5 不要な項目

| 変数名 | 理由 |
| :-- | :-- |
| `VITE_STRIPE_PUBLISHABLE_KEY` | 現行コード未使用（[Stripe 環境構築手順](../07_リファクタリング/03_stripe決済の環境構築手順.md) §4） |

### 4.6 VITE_ORIGIN_HOST の例

エンプラは **1 ビルド・複数テナント（サブドメイン）** 方式。  
`VITE_ORIGIN_HOST` は URL 生成（共有リンク等）の基準ホストとして使う。

| 環境 | 例 |
| :-- | :-- |
| sandbox | Firebase Hosting のデフォルト URL ホスト、または検証用サブドメイン |
| development | `enterprise.shokujii.com` 等（dev 用ドメイン） |
| production | `enterprise.shokujii.jp` 等（本番ドメイン） |

テナントごとの `company-a.shokujii.com` は **`getEnterpriseByDomain`** で解決する。  
Hosting に接続したドメインと Firestore `/enterprises` の `subdomain` / `custom_domain` を一致させる（[02_全体構成 §2](./02_エンタープライズ_全体構成・アーキテクチャ.md)）。

### 4.7 ローカル開発・sandbox での enterprise 解決

`getEnterpriseByDomain` は `*.{ENTERPRISE_BASE_DOMAIN}` のサブドメイン抽出と `custom_domain` 完全一致のみで判定する（ベースドメインは環境変数。[02_全体構成 §2.4](./02_エンタープライズ_全体構成・アーキテクチャ.md) 参照）。`localhost` や Firebase Hosting デフォルト URL（`<PROJECT_ID>-enterprise.web.app`）ではそのままでは not-found になる。

| 環境 | 推奨手順 |
| :-- | :-- |
| **sandbox / CI デプロイ後** | テスト企業の Firestore `/enterprises/{id}` に `custom_domain: "<PROJECT_ID>-enterprise.web.app"` を登録（`createEnterprise` 後に Admin SDK または Firestore Console で更新）。Hosting デフォルト URL で `getEnterpriseByDomain` がヒットする。`ENTERPRISE_BASE_DOMAIN` は未設定でよい |
| **ローカル開発** | `enterprise/.env.development` に `VITE_ENTERPRISE_SUBDOMAIN=company-a`（テスト企業の `subdomain`）を設定。フロントは `window.location.hostname` の代わりに `${VITE_ENTERPRISE_SUBDOMAIN}.${VITE_ENTERPRISE_BASE_DOMAIN}` を Callable に渡す |
| **未ヒット時** | 全画面エラーページ。「企業が見つかりません。ご利用の URL をご確認のうえ、貴社の管理者にお問い合わせください」。デフォルトドメイン（例: `enterprise.shokujii.com`）も MVP では同じ案内（企業選択 UI は作らない） |
| **Hosting プレビューチャネル** | ホスト名が動的なため MVP では使用しない方針 |

**Functions 側の環境変数**: `ENTERPRISE_BASE_DOMAIN`（`defineString`）を `deploy_functions.yml` の環境変数（または `.env.<project>` ファイル）に追加する。フロントの `VITE_ENTERPRISE_BASE_DOMAIN` と同値にすること。

## 6. デプロイの実行

```bash

firebase --project <PROJECT_ID> deploy --only hosting:enterprise
```

## 8. トラブルシュート

| 症状 | 想定原因 | 対処 |
| :-- | :-- | :-- |
| `Hosting site or target enterprise not detected` | `FIREBASERC` に `enterprise` target がない | §3.2〜3.3 を再実施 |
| `Error 409` で enterprise site 作成失敗 | Console 等で site 済み・Terraform state 未 import | §3.1 の import 後に `apply` |
| ビルド成功・Firebase 接続エラー | `ENTERPRISE_ENV` 未設定 or 誤り | §4 を確認。空 `.env` になっていないか Actions ログを見る |
| デプロイ成功だが画面が真っ白 | `VITE_*` 欠落 | §4.2 の必須項目を確認 |
| ドメインは開くが企業情報が取れない | Hosting ドメインと Firestore の不一致、Functions 未デプロイ | §2.1 / §2.3 / §5 |
| CI は `development` のみ反応する | workflow の branch 設定 | sandbox では `workflow_dispatch` を使うか、対象ブランチへ merge |

## 10. App Check（Phase 2）

未認証 Callable（`getEnterpriseByDomain` / `requestEnterpriseEmailLogin` / `confirmEnterpriseEmailLogin`）の濫用対策。`04_認証` §8-2 / `08_実装計画` Phase 2-5 が正本。

### 10.1 プロバイダとキー

| 項目 | 推奨 |
| :-- | :-- |
| プロバイダ | **reCAPTCHA Enterprise**（Google 推奨。無料枠 1万 assessment/月） |
| サイトキー | `VITE_RECAPTCHA_SITE_KEY` を `ENTERPRISE_ENV` に追加（§4.3） |
| 初期化 | enterprise パッケージの Firebase 初期化直後に App Check を有効化 |
| enforce 対象 | 上記3 Callable に `enforceAppCheck: true`。**PF Callable には付けない**（`userProfile.ts` 等の既存方針と整合） |

**Terraform 管理**: API 有効化とサイトキー作成は `terraform/api.tf` で管理する。

| リソース | 内容 |
| :-- | :-- |
| API 有効化 | `recaptchaenterprise.googleapis.com` / `firebaseappcheck.googleapis.com` を有効化サービスに追加 |
| サイトキー | `google_recaptcha_enterprise_key`（WEB タイプ。`allowed_domains` = ベースドメイン + `<PROJECT_ID>-enterprise.web.app`） |
| キーの受け渡し | `terraform output` の値を `ENTERPRISE_ENV` の `VITE_RECAPTCHA_SITE_KEY` に登録 |
| 注意 | App Check 側の「Web アプリとサイトキーの紐付け」は Terraform プロバイダの対応が薄いため **Firebase Console で手動**設定する |

### 10.2 ローカル開発（debug token）

1. `enterprise/.env.development` で dev モードのみ `self.FIREBASE_APPCHECK_DEBUG_TOKEN = true` を有効化
2. ブラウザコンソールに表示される debug token を Firebase Console → App Check → Apps → enterprise Web アプリ → Manage debug tokens に登録
3. エミュレータ利用時も同手順

### 10.3 2段階ロールアウト

1. **第1段階**: クライアントで App Check 初期化のみデプロイ。Functions は `enforceAppCheck` **なし**。Firebase Console の App Check メトリクスで正規トークン率を数日確認
2. **第2段階**: 3 Callable に `enforceAppCheck: true` を有効化して Functions をデプロイ
3. Firebase Console → App Check → reCAPTCHA Enterprise のドメイン登録に、本番・sandbox の Hosting ドメイン（`*.web.app` 含む）を追加

### 10.4 sandbox での custom_domain 登録（enterprise 解決と併用）

§4.7 と合わせて、テスト企業の `custom_domain` に `<PROJECT_ID>-enterprise.web.app` を登録し、デプロイ後の URL で `getEnterpriseByDomain` が成功することを §7 の確認項目とする。
