# 割引・決済 詳細仕様

本ドキュメントは `01_仕様概要`、`02_全体構成・アーキテクチャ` の決定事項に基づき、割引計算・月額上限管理・Stripe決済連携の機能仕様を詳細に定義する。


# 1. 概要

エンタープライズ版では、イベントの支払い方式として新たに `enterprise_subsidy`（福利厚生割引）を追加する。この方式が選択されたイベントでのみ、企業の割引ルールに基づき注文金額を自動割引する。既存の支払い方式（参加者事前決済、主催者請求書払い）もオプションとして利用可能。

## 1.1 支払い方式の全体像

### PF版（既存）

| 値 | ラベル | 挙動 |
|:--|:--|:--|
| `user_advance` | 参加者事前決済 | 参加者が全額クレカ事前決済 |
| `user_on_day` | 当日払い | **deprecated（利用実績なし。エンプラ版では選択不可）** |
| `community_bill` | 主催者請求書払い | コミュニティに請求書発行。参加者は0円 |

### エンタープライズ版で追加

| 値 | ラベル | 挙動 |
|:--|:--|:--|
| `enterprise_subsidy` | 福利厚生割引 | 企業が設定した割引を適用。残額は参加者がクレカ決済 |

### エンプラ版での利用可否

| 支払い方式 | エンプラ版 | デフォルト | 割引計算 |
|:--|:--|:--|:--|
| `enterprise_subsidy` | 利用可 | **デフォルト** | **あり** |
| `user_advance` | 利用可（オプション） | | なし（PF版と同じ処理） |
| `community_bill` | 利用可（オプション） | | なし（PF版と同じ処理） |
| `user_on_day` | **利用不可** | | — |

**割引計算ロジックが走るのは `enterprise_subsidy` の場合のみ。** 他の支払い方式では PF版と同じ処理がそのまま使われる。

**ゲスト参加時の注文フロー**は本ドキュメントのスコープ外とする。`enterprise_subsidy` のイベントにゲスト（PF版ユーザー）が参加した場合の決済フロー・割引適用有無は `04_ゲスト参加` で定義する。

### common スキーマへの影響

```typescript
// 現行
export const EVENT_PAYMENT_VALUES = ['user_advance', 'user_on_day', 'community_bill'] as const

// 変更後
export const EVENT_PAYMENT_VALUES = ['user_advance', 'user_on_day', 'community_bill', 'enterprise_subsidy'] as const
```

`user_on_day` は後方互換性のために値として残すが、エンプラ版のイベント作成UIでは選択肢に表示しない。

## 1.2 PF版との主な差分（enterprise_subsidy 選択時）

| 項目 | PF版（user_advance） | エンプラ版（enterprise_subsidy） |
|:--|:--|:--|
| 割引 | なし（全額ユーザー負担） | 企業の割引ルールを適用 |
| 月額上限 | なし | 1人あたり月額上限あり |
| 決済金額 | 注文合計額 = Stripe 請求額 | ユーザー自己負担額 = Stripe 請求額 |
| 自己負担0円 | なし | Stripe スキップで直接注文確定 |
| 注文確定の Functions | PF版の既存 Functions を使用 | 新規 Functions を作成 |
| キャンセル時 | Stripe Refund のみ | Stripe Refund + 割引利用実績の戻し |

## 1.3 決定事項サマリ

| # | 論点 | 決定 |
|:--|:--|:--|
| D-1 | 割引対象は税込/税抜か | 税込 |
| D-2 | 割合割引の端数処理 | 切り捨て（Math.floor） |
| D-3 | 月額上限は税込/税抜で管理するか | 税込 |
| D-4 | usage 加算タイミング | 決済完了時。ただし月はイベント開催月に紐づく |
| D-5 | 上限ギリギリで同時注文した場合 | 早い者勝ち。後者は割引なし |
| D-6 | Stripe への金額の渡し方 | 割引適用後の合計を1つの line_item |
| D-7 | 自己負担0円の場合 | Stripe スキップで直接確定 |

| D-9 | キャンセル可能期限 | PF版と同じ |
| D-10 | Functions は新規作成 vs PF版拡張 | 新規作成 |
| D-11 | エンプラ版のデフォルト支払い方式 | enterprise_subsidy |

| D-16 | キャンセル時の Stripe Refund 失敗 | retry（最大3回）。全失敗時は管理者に通知 |


# 2. 割引計算ロジック

**本章の割引計算は `event_payment == 'enterprise_subsidy'` の場合にのみ適用される。** `user_advance` や `community_bill` のイベントでは割引計算は行わず、PF版と同じ処理となる。

## 2.1 計算式

すべて**税込**ベースで計算する。PF版のメニュー価格が税込（`tax_behavior: 'inclusive'`）のため、統一する。

```
① 注文合計額（税込）
   total_amount = Σ(menu.price × menu.count)

② 割引候補額
   - 固定金額の場合: candidate = enterprise.discount_value
     例: discount_value = 500 → candidate = 500円
   - 割合の場合: candidate = Math.floor(total_amount × enterprise.discount_value / 100)
     例: discount_value = 50, total_amount = 1,200 → candidate = Math.floor(600) = 600円

③ イベント開催月の残枠
   remaining = Math.max(0, enterprise.monthly_limit_per_user - イベント開催月の current usage)
   ※ Math.max(0, ...) でガード。キャンセル戻しのタイミング等で usage > limit になるエッジケースに備える

④ 実際の割引額
   discount_amount = Math.min(candidate, remaining, total_amount)
   ※ candidate: 割引ルールに基づく割引候補額
   ※ remaining: 月額上限の残枠（0なら割引額 = 0）
   ※ total_amount: 注文合計額を超えないようにキャップ

⑤ ユーザー自己負担額
   user_paid_amount = total_amount - discount_amount
```

## 2.2 計算例

### 企業設定

```
discount_type: "percentage"
discount_value: 50（50%割引）
monthly_limit_per_user: 7500
```

### ケース別

| ケース | 注文合計 | 割引候補 | 残枠 | 割引額 | 自己負担 |
|:--|:--|:--|:--|:--|:--|
| 通常 | 1,200円 | 600円 | 7,500円 | 600円 | 600円 |
| 端数あり | 1,150円 | 575円 | 7,500円 | 575円 | 575円 |
| 残枠不足 | 1,200円 | 600円 | 300円 | 300円 | 900円 |
| 残枠0 | 1,200円 | 600円 | 0円 | 0円 | 1,200円 |
| 割引 > 注文額（固定500円、注文300円） | 300円 | 500円 | 7,500円 | 300円 | 0円 |

## 2.3 割引計算の責務

| 場所 | 役割 |
|:--|:--|
| フロントエンド | **表示用**の割引額計算。注文確認画面に割引後の金額を表示する。正式な金額ではない |
| Functions | **正式な**割引額計算。Stripe に渡す金額を確定する。フロントエンドの計算結果は信頼しない |

フロントエンドで計算して表示するのは UX 目的のみ。実際の割引適用額は Functions 側で検証・確定する（02_全体構成 3.4 で決定済み）。


# 3. 月額利用実績管理

## 3.1 イベント開催月に紐づける

月額利用実績は**決済日ではなくイベント開催月**に紐づく。

```
例1: 6月25日に、7月3日開催イベントの注文を決済
  → 7月分の usage に加算

例2: 6月28日に、6月30日開催イベントの注文を決済
  → 6月分の usage に加算
```

これにより、6月末に「6月のイベント」と「7月のイベント」の注文を同時に行う場合、それぞれの月の枠が独立してチェックされる。

## 3.2 EnterpriseMember スキーマ（辞書フィールド方式）

02_全体構成の `EnterpriseMember` スキーマを以下に変更する。

```typescript
interface EnterpriseMember {
  user_id: string
  role: "admin" | "member"
  is_active: boolean
  display_name?: string
  department?: string

  // === 割引利用実績（月別辞書） ===
  monthly_usage: Record<string, number>         // { "2026-06": 5000, "2026-07": 1200 }
  monthly_order_count: Record<string, number>   // { "2026-06": 8, "2026-07": 2 }

  created_at: Timestamp
  updated_at: Timestamp
}
```

**旧スキーマからの変更点:**

| 旧 | 新 |
|:--|:--|
| `current_month: string` | 削除 |
| `current_month_usage: number` | `monthly_usage: Record<string, number>` |
| `current_month_order_count: number` | `monthly_order_count: Record<string, number>` |

**辞書方式を選択した理由:**
- 1ドキュメントで全月分の使用量を取得できる（追加クエリ不要）
- Transaction 内で扱いやすい（1ドキュメントの読み取り+書き込みで排他制御が完結）
- 異なる月のイベントを同時に注文する場合にも対応可能

**アカウント作成時の初期値:**

```typescript
{
  monthly_usage: {},
  monthly_order_count: {},
}
```

**古い月のクリーンアップ:**
- MVP: クリーンアップしない。辞書に月が蓄積されるが、1ユーザーあたり年12エントリ程度なのでサイズ問題はない
- Phase 2: Scheduled Function で3ヶ月以上前のエントリを削除する

## 3.3 usage の読み取り

```typescript
const getUsageForMonth = (member: EnterpriseMember, yearMonth: string): number => {
  return member.monthly_usage[yearMonth] ?? 0
}

const getOrderCountForMonth = (member: EnterpriseMember, yearMonth: string): number => {
  return member.monthly_order_count[yearMonth] ?? 0
}
```

辞書にキーが存在しない月は `0` として扱う。旧スキーマの「`current_month` が現在月と不一致なら0扱い」に相当する。

## 3.4 usage の更新（Transaction 内）

```typescript
// イベント開催月のキーを生成
const eventMonth = formatYearMonth(event.event_start_datetime)  // "2026-07"

// Transaction 内で member ドキュメントを読み取り+更新
transaction.update(memberRef, {
  [`monthly_usage.${eventMonth}`]: FieldValue.increment(discountAmount),
  [`monthly_order_count.${eventMonth}`]: FieldValue.increment(1),
  updated_at: FieldValue.serverTimestamp(),
})
```

## 3.5 同時注文の排他制御

月額上限を厳密に制御するため、割引適用時は必ず Transaction を使用する。

```
注文A（Webhook到着）           注文B（Webhook到着）
  Transaction 開始               Transaction 開始
  member Doc 読み取り（ロック）   → ロック待ち
  残枠 2,000円 → 割引 500円      │
  usage += 500                    │
  Transaction 完了                ロック解除 → 再読み取り
                                  残枠 1,500円 → 割引 500円
                                  usage += 500
                                  Transaction 完了
```

同じ member ドキュメントに対する Transaction で排他制御が保証される。

## 3.6 Phase 2: 月次バッチ再集計

フィールド保持方式は加算/減算の漏れによる不整合リスクがあるため、Phase 2 で安全網として月次再集計バッチを導入する。

- Scheduled Function で月初に前月分の orders から `discount_amount` を再集計
- `monthly_usage` の値と一致するか検証
- 不一致があれば管理者に通知 + 自動補正


# 4. 注文〜決済フロー

## 4.1 event_payment による分岐

注文〜決済のフローはイベントの `event_payment` の値によって分岐する。

| event_payment | 注文フロー | 割引 |
|:--|:--|:--|
| `enterprise_subsidy` | **本章のフロー**（createEnterpriseCheckout → 割引計算 → Stripe or 直接確定） | あり |
| `user_advance` | PF版と同じ（createStripeCheckoutSession → Stripe 決済） | なし |
| `community_bill` | PF版と同じ（請求書払い。参加者の決済なし） | なし |

`user_advance` / `community_bill` のイベントでは、PF版の既存 Functions をそのまま使用する。以降のフロー・Functions は `enterprise_subsidy` のイベントに限定した仕様である。

### user_advance / community_bill のエンプラ版での扱い

PF版と完全に同じ処理を行う。エンプラ版固有の変更は `enterprise_id` のセットのみ。

| 項目 | 挙動 |
|:--|:--|
| 注文Doc | `enterprise_id` をセット。`discount_amount`, `user_paid_amount` はセットしない |
| 割引 | なし |
| Functions | PF版の既存 Functions を使用 |
| `community_bill` の請求先 | コミュニティに対して請求書発行（PF版と同じ）。01_仕様概要の「請求先はMVPでは全社管理者に一本化」はゲスト参加時の費用負担先を指す |

## 4.3 カート追加（既存 addOrder の流用）

メニュー選択・カート追加は PF版の `addOrder` をそのまま使用する。この時点では割引計算は行わない。注文Docは `status: in_cart` で作成される。

## 4.4 注文確認画面（フロントエンド）

`enterprise_subsidy` のイベントでは、注文確認画面で割引後の金額を表示用に仮計算する。

### 月額利用状況の常時表示

ヘッダーまたはサイドメニューに、当月の利用状況を表示する。


**注意:** 「今月」は**現在月**のイベント分の利用額を表示する。来月のイベントを先に注文した場合の来月分は、この表示には含まれない（混乱を避けるため）。

## 4.5 注文確認画面で表示する月の判定

注文確認画面では、**注文対象イベントの開催月**の残枠を表示する。

```typescript
const eventMonth = formatYearMonth(event.event_start_datetime)
const usage = getUsageForMonth(member, eventMonth)
const remaining = enterprise.monthly_limit_per_user - usage
```

7月のイベントを6月に注文する場合、「7月分の残枠」が表示される。


# 5. Functions 設計

## 5.1 createEnterpriseCheckout

割引を計算し、Stripe Checkout Session を作成する（または自己負担0円の場合は直接注文確定する）。

### リクエスト

```typescript
interface CreateEnterpriseCheckoutRequest {
  community_id: string
  event_id: string
  order_id: string
}
```

### 処理フロー

```
--- Transaction 外 ---

1. 認証チェック
   → 未認証 → HttpsError('unauthenticated')
   → custom claims から enterprise_id, user_id を取得

2. 注文Docを取得
   → /communities/{communityId}/events/{eventId}/orders/{orderId}
   → 存在しない or status != 'in_cart' → HttpsError('not-found')
   → user_id が一致しない → HttpsError('permission-denied')

3. イベントDocを取得
   → 注文期限チェック
   → enterprise_id の一致チェック
   → event_payment が 'enterprise_subsidy' であることを確認
     ※ それ以外の場合は PF版の既存 Functions を使用するため、ここでは HttpsError('failed-precondition') を返す

4. 企業設定を取得
   → /enterprises/{enterpriseId} から割引設定（discount_type, discount_value, monthly_limit_per_user）
   → payment_method が 'credit_card' であることを確認（MVP では固定値。Phase 2 で 'payroll_deduction' 追加時の分岐ポイント）

5. メンバー情報を取得
   → /enterprises/{enterpriseId}/members/{userId} から monthly_usage

6. 割引計算
   a. イベント開催月を特定: eventMonth = formatYearMonth(event.event_start_datetime)
   b. 注文合計額を計算: total_amount = Σ(menu.price × menu.count)
   c. 割引候補額を計算（2.1 の計算式）
   d. 残枠を計算: remaining = Math.max(0, monthly_limit_per_user - (monthly_usage[eventMonth] ?? 0))
   e. 割引額を確定: discount_amount = Math.min(candidate, remaining, total_amount)
   f. 自己負担額: user_paid_amount = total_amount - discount_amount

7. 注文Docを更新
   → enterprise_id, discount_amount, user_paid_amount をセット

8. 分岐
   [A] user_paid_amount > 0 の場合:
       → Stripe Checkout Session を作成（5.2 参照）
       → session URL を返す
       ※ この時点では monthly_usage を加算しない（Webhook 到着時に加算する）

   [B] user_paid_amount == 0 の場合:
       → Transaction 内で直接注文確定（5.3 参照）
       → Transaction 内で monthly_usage を加算
       → 完了画面の URL を返す
```

### monthly_usage の加算タイミング

`monthly_usage` の加算は **決済完了時** に行う。

| ケース | 加算タイミング | 加算場所 |
|:--|:--|:--|
| `user_paid_amount > 0` | Stripe Webhook 到着時 | `handleEnterpriseStripeWebhook`（Transaction 内） |
| `user_paid_amount == 0` | `createEnterpriseCheckout` 内で直接確定時 | `createEnterpriseCheckout`（Transaction 内） |

**Checkout Session 作成時点では加算しない。** Stripe Checkout Session 作成から決済完了（Webhook 到着）までの間に、同一ユーザーの別注文が割引を消費する可能性があるが、以下の理由により許容する:

- `monthly_usage` はユーザー単位のため、同一ユーザーが同時に2つの Checkout を進めるシナリオでのみ発生する
- 超過しても最大で1注文分の割引額（数百円〜数千円）程度であり、福利厚生費として致命的ではない
- Phase 2 の月次バッチ再集計（3.6）が不整合を検知・補正する

### レスポンス

```typescript
interface CreateEnterpriseCheckoutResponse {
  type: 'stripe' | 'direct'
  url: string                    // Stripe Checkout URL or 完了画面 URL
  discount_amount: number
  user_paid_amount: number
```

## 5.3 直接注文確定（user_paid_amount == 0 の場合）

自己負担0円の場合は Stripe 決済が不要。Functions 内で直接注文を確定する。

```
Transaction 内で:
1. 注文Doc の status を 'ordered' に更新、ordered_at をセット
2. member の monthly_usage[eventMonth] を加算
3. member の monthly_order_count[eventMonth] を加算
4. 監査ログを記録（action: 'order_create'）
```

## 5.4 handleEnterpriseStripeWebhook

Stripe Webhook `checkout.session.completed` を受け取り、注文を確定する。

### 処理フロー

```
1. Webhook イベントを検証（Stripe signature）
2. metadata から enterpriseId, eventId, communityId, orderId, userId を取得
3. 注文Docを取得
   → discount_amount を取得
4. イベントDocを取得
   → eventMonth = formatYearMonth(event.event_start_datetime)
5. Transaction 内で:
   a. 注文Doc の status が 'in_cart' であることを確認
   b. 注文Doc の status を 'ordered' に更新、ordered_at, payment_intent をセット
   c. /enterprises/{enterpriseId}/members/{userId} を取得
   d. monthly_usage[eventMonth] += discount_amount
   e. monthly_order_count[eventMonth] += 1
   f. 監査ログを記録（action: 'order_create'）
```

### Webhook エンドポイントの分離方針

PF版とエンプラ版で **別々の Webhook URL** を使用する。

| | URL | Stripe Webhook 設定 |
|:--|:--|:--|
| PF版 | `/stripe-webhook` （既存） | 既存の Webhook endpoint をそのまま使用 |
| エンプラ版 | `/enterprise-stripe-webhook`（新規） | Stripe Dashboard で新しい endpoint を追加 |

同一URLで `metadata` 分岐する方式も可能だが、Webhook signing secret が共通になり、将来的にエンプラ版専用の Stripe アカウント分離に対応しづらくなるため、MVPから別URLにしておく。

### PF版の Webhook との関係

PF版は `onOrderChanged`（Firestore トリガー）で注文ステータス変更を検知してメール送信を行っている。エンプラ版でも注文Doc の status が `ordered` に変わるため、この Firestore トリガーが発火する。ただし、エンプラ版では送信するメールの内容が異なる可能性があるため、`enterprise_id` の有無でメール送信を分岐する設計を検討する（詳細はメール配信仕様書にて定義）。

## 5.5 cancelEnterpriseOrder

注文をキャンセルし、割引利用実績を戻す。

### リクエスト

```typescript
interface CancelEnterpriseOrderRequest {
  community_id: string
  event_id: string
  order_id: string
}
```

### 処理フロー

```
1. 認証チェック
2. 注文Docを取得
   → status != 'ordered' → HttpsError('failed-precondition')
   → user_id が一致しない → HttpsError('permission-denied')
3. イベントDocを取得
   → イベント開催月を算出: eventMonth = formatYearMonth(event.event_start_datetime)
4. キャンセル可能期限チェック（PF版と同じ基準）

--- Stripe Refund（Transaction 外）---

5. user_paid_amount > 0 の場合: Stripe Refund を実行（最大3回 retry）
   → 全 retry 失敗 → 管理者に通知 + HttpsError('internal') を返す
   → Refund 成功 → refund_id を取得

--- Firestore 更新（Transaction 内）---

6. Transaction 内で:
   a. 注文Doc の status を 'canceled' に更新、canceled_at, refund_id をセット
   b. discount_amount > 0 の場合:
      /enterprises/{enterpriseId}/members/{userId} の monthly_usage[eventMonth] -= discount_amount
      monthly_order_count[eventMonth] -= 1
   c. 監査ログを記録（action: 'order_cancel'）
```

**Stripe Refund と Firestore Transaction を分離する理由:**
Firestore Transaction 内では外部API（Stripe）を呼び出すべきではない。Transaction が競合でリトライされると Refund が重複実行される恐れがあるため、Refund を先に実行し、成功後に Firestore を更新する。

**Stripe Refund 成功 → Firestore Transaction 失敗の場合:**
Firestore Transaction を retry する（最大3回）。全 retry 失敗時は管理者に通知する。Stripe 側は既に Refund 済みのため、Firestore の不整合は Phase 2 の月次再集計で検知・補正される。

### キャンセル時の割引戻しについて

- キャンセルすると `monthly_usage` から `discount_amount` を減算し、枠を復元する
- 復元された枠は次回以降の注文で使用可能
- `monthly_usage` が負にならないよう `Math.max(0, usage - discount_amount)` でガードする

# 補足資料: Phase 2 仕様概要

MVPでは実装しないが、Phase 2 以降で対応する項目の仕様概要を記載する。


## A. 給与天引き対応（CSV出力）

### 背景

クレジットカード決済ではなく、給与天引きで従業員の自己負担分を回収する方式。大企業の経理部門から要望が出る可能性が高い。

### 仕様概要

- 企業設定に `payment_method: "payroll_deduction"` を追加
- 注文時は Stripe 決済をスキップし、直接注文確定
- 月末に「従業員別自己負担額一覧CSV」を管理者画面からダウンロード可能
- CSV項目: 従業員名、部署、メールアドレス、注文数、自己負担合計、割引合計


## B. 月次バッチ再集計

### 背景

フィールド保持方式の不整合リスクに対する安全網。

### 仕様概要

- Scheduled Function で月初に前月分の全 orders を集計
- 各メンバーの `monthly_usage` と照合し、差異があれば管理者に通知
- 差異が小さい場合は自動補正、大きい場合は管理者承認後に補正


## C. 割引ルールの拡張

### 背景

企業ごとに異なる複雑な割引ルールに対応する。

### 仕様概要

- 部署別の割引ルール（部署Aは50%割引、部署Bは30%割引）
- 時間帯別の割引（ランチタイムは割引率アップ）
- 注文回数に応じた段階的割引
- 複数の割引ルールの組み合わせ（最大割引 or 合算）
