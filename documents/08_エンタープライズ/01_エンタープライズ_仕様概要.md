# shokujiiエンタープライズ版 仕様概要書

## 概要
- 中規模企業（100名~300名）・大企業（300名〜）に対して、shokujiiの社内専用サイトを構築・提供する
- 社内におけるコミュニケーション活性ツールとして導入。お昼の福利厚生としつつ、社内の偶発的なコミュニケーションを誘発する
- 導入費用(数十万円〜)、月額費用（5万円〜）、従量課金をいただくビジネスモデル

## 前提

## プロジェクト
- これまで開発してきたものを「shokujiiプラットフォーム版」と呼び、企業向けを「shokujiiエンタープライズ版」と呼ぶ
- 「コミュニティ作成」「コミュニティ管理」「イベント作成」「イベント参加注文」などの基本機能はshokujiiのプラットフォーム版を踏襲
- baseパッケージのコンポーネントを使用する。userパッケージをコピーして構築する想定

## MVP(Minimum Valuable Product)
- まずは必要最小限の工数でリリースまで漕ぎ着けたい
- ただし、MVPをベースにしつつ、改善アップデートできるように、仕様変更に耐えうる全体設計を行いたい

## ユースケースの想定
- 人事部・総務部・経営部などの特定権限の方が「全社管理者」となる
- 「全社管理者」が「全社設定」や「月額割引額」などを設定する
- 「全社管理者」が「アカウント一括作成」「コミュニティ一括作成」を行う
- 部署ごとなどに「コミュニティ」でイベント作成・管理・予約申請を行う
- 「公開設定」のものは全社誰でも参加できる。「URL限定公開」はURLを知るものだけが参加できる
- 人事部・総務部の「全社管理者」は毎日開催して、誰でも注文できる状態を作る
- 各部署は、限定公開で毎週定例ランチミーティングを行う。各部署は月1で外部部署からも参加できるオープンな食事会も開催する
- 一般従業員が部活や社内サークル目的などに「コミュニティ」を作ることもできる。コミュニティ作成後、「全社管理者」が承認・非承認する
- 従業員は会社負担で利用できる。福利厚生費とする場合、半額自己負担・半額会社負担で、1人月額7,500円(税別)までであれば非課税となる
- 就活生や外部パートナーとの会食にも利用可能（ゲスト参加機能）


## ユーザーロール定義

| ロール | 対象 | 主な権限 |
|:--|:--|:--|
| **全社管理者** | 人事部・総務部・経営部など | 全社設定、アカウント管理、コミュニティ承認、割引設定、ダッシュボード閲覧 |
| **コミュニティ管理者** | 部署リーダー、サークル代表など | コミュニティ内のイベント作成・管理、予約申請 |
| **一般従業員** | 社内ユーザー全般 | イベント参加・注文、コミュニティ参加・作成（要承認） |
| **ゲスト** | 就活生、外部パートナーなど | ゲストOKイベントへの参加・注文（プラットフォーム版ユーザーとして参加） |


## 技術方針

## Firebase構成: 単一Project + テナント論理分離

プラットフォーム版と同一のFirebaseプロジェクトを使用し、`enterprise_id` でテナントを論理分離する。

### 方針の根拠
- MVP工数を最小化できる（企業追加 = Firestoreに1ドキュメント追加のみ）
- 飲食店データ（partners / shops / menus）をそのまま共有できる
- プラットフォーム版の `common` パッケージのスキーマ・ユーティリティを最大限流用できる
- デプロイが1回で済む

### テナント分離の方法
- すべてのエンタープライズ関連ドキュメントに `enterprise_id` を付与する
- Firestore Security Rules で `request.auth.token.enterprise_id == resource.data.enterprise_id` を強制し、他社データへのアクセスを防止する
- ユーザーDocに `user_type`（`"platform"` / `"enterprise"`）フラグを持たせ、プラットフォーム版ユーザーとエンタープライズ版ユーザーを区別する

### コレクション構成（プラットフォーム版との共存）
```
/enterprises/{enterpriseId}         ← 【新規】企業設定・割引ルール

/communities/{communityId}          ← 既存構造を踏襲
  /events/{eventId}
    /orders/{orderId}
    /menus/{menuId}
  /members/{userId}
  /invites/{inviteId}
  /letters/{letterId}

/partners/{partnerId}               ← 既存構造を踏襲（飲食店データ共有）
  /shops/{shopId}
  /menus/{menuId}

/users/{userId}                     ← 既存構造に enterprise_id, user_type を追加
/users_personal_information/{userId}
```

### 物理分離（企業ごとProject）について

**単一Projectを選択した理由:**

1. **SaaS業界の標準的なアプローチ**
   - Slack、Notion、Google Workspace 等の主要なエンタープライズSaaSも、単一環境でのテナント論理分離が基本
   - 企業ごとにインフラを分離する方式は、ごく一部の高セキュリティ要件（金融・医療・政府機関向け等）に限られる
   - shokujiiのサービス特性（食事注文・社内コミュニケーション）上、扱うデータの機密度は比較的低く、論理分離で十分なセキュリティを担保できる

2. **飲食店データ共有の問題**
   - 企業ごとにProjectを分離した場合、飲食店データ（partners / shops / menus）を各Projectに同期する基盤が必要になる
   - 飲食店向けの専用Projectを新たに構築し、全企業Projectとのデータ同期を実装する工数が非常に大きい
   - 単一Projectであれば飲食店データをそのまま共有でき、同期基盤の開発が不要

3. **運用・デプロイコスト**
   - 企業ごとにProjectを分けると、Functions / Hosting / Security Rules のデプロイが企業数分必要になる
   - バグ修正1つでもN社分のデプロイが必要となり、運用負荷が企業数に比例して増加する
   - 単一Projectなら1回のデプロイで全企業に反映される

4. **将来の移行パス**
   - すべてのドキュメントに `enterprise_id` を持たせる設計のため、将来的に特定企業のデータのみ別Projectへ移行することは技術的に可能
   - 全企業を一斉に分離する必要はなく、要件が出た企業のみ個別対応できる

**物理分離が必要になった場合の対応方針:**
- 金融・医療系など、コンプライアンス上データの物理分離が必須となる大企業に対しては、別途専用環境として提供することを検討する
- その場合も `enterprise_id` ベースの設計により、該当企業のデータのみを別Projectへ移行可能
- ただしMVPフェーズでは想定しない

## 認証方式

| フェーズ | 認証方式 | 実装 |
|:--|:--|:--|
| **MVP** | 企業メールドメイン + 6桁OTP | Firebase Auth + custom claims（`enterprise_id`） |
| **Phase 2** | 企業ごとにSSO対応 | Identity Platform にアップグレード + テナント作成 |

- 特定ドメインのメールアドレスのみログイン可能
- SNSログインはエンタープライズ版では提供しない
- Identity Platform のマルチテナント機能を使えば、将来的に企業ごとに異なる認証方式（SAML/OIDC）を設定可能

## 将来の技術移行に備えた設計指針
- データアクセス層を抽象化し、Firestore への直接依存を最小限にする
- 集計ロジック（ダッシュボードなど）は Cloud Functions に寄せ、フロントエンドからの直接集計を避ける
- `enterprise_id` を一貫して全ドキュメントに持たせ、将来のDB移行時にテナント分離がスムーズになるようにする


## 画面・機能

## 一般従業員画面・機能
- 専用ドメイン
- メールアドレスログイン機能
    - 特定ドメインのメールアドレスのみログインできる機能
    - メールアドレスでログインし、6桁のワンタイムパスワードでログインする
- イベント支払い方式
    - **福利厚生割引（enterprise_subsidy）**: デフォルト。管理者が指定した金額または割合を割引し、残りはクレジットカードで決済。月額上限に達した場合は割引なし（全額自己負担）で注文可能
    - **参加者事前決済（user_advance）**: PF版と同じ。全額クレジットカード決済。割引なし
    - **主催者請求書払い（community_bill）**: PF版と同じ。コミュニティに請求書発行。参加者は0円
    - ※ 当日払い（user_on_day）は deprecated のためエンプラ版では選択不可
- イベント連続作成機能
    - イベント複製機能を「最大10個」同時に作成できる
- イベント自動中止機能
    - 「注文期限の3日前」に「注文個数がXX個」以下の場合、自動で予約がキャンセルされる
    - デフォルト設定は、お店が設定する「最小注文個数」の前提

## 全社管理者画面・機能【人事部・総務部など】
- 全社設定機能
    - 会社名
    - 企業ロゴ
    - テーマカラー etc.
- アカウント発行機能
    - アカウント一括発行機能
        - CSV登録で一括登録することができる
    - アカウント停止・管理機能
- コミュニティ管理機能
    - 従業員が作成したコミュニティについて承認・非承認・管理する
    - コミュニティ一括作成機能（事業部ごとのコミュニティなどをCSVで一括作成）
- 割引指定機能・月額上限設定
    - 割引タイプ: 「固定金額」または「割合」を選択
    - 固定金額の場合: 1注文あたりの割引金額（ex. 500円引き）
    - 割合の場合: 1注文あたりの割引率（ex. 50%引き）
    - 1人あたりの1ヶ月の上限金額（ex. 7,500円）
- 支払い方式のデフォルト設定
    - デフォルト: 福利厚生割引（enterprise_subsidy）
    - オプション: 参加者事前決済、主催者請求書払いも選択可能
- ダッシュボード
    - 月別
        - 利用回数
        - 利用人数
        - 利用金額
        - CSVダウンロード
    - メンバー一覧
        - 利用回数
        - 利用人数
        - 利用金額
        - CSVダウンロード
- 監査ログ閲覧機能
    - ログイン履歴、管理者操作、注文履歴の閲覧
    - 直近のログを一覧表示

## ゲスト参加機能
- エンタープライズ版のイベントで「ゲストOK」と設定した場合、プラットフォーム版ユーザーも参加可能
- ゲストの決済方式（イベント作成時にコミュニティ管理者が選択）:
    - **無料参加**: ゲストは無料。費用は企業負担
    - **自己負担**: ゲストは全額クレジットカード決済
- ゲスト参加時の請求先: MVP では全社管理者に一本化

## メール配信機能の修正
- プラットフォーム版のメール配信について、エンタープライズ版のイベント・ユーザーには不要なメールを送信しないよう制御する
- **送信しないメール（PF only）:** イベント/コミュニティの `enterprise_id` が存在する場合は送信スキップ。詳細は `04_エンタープライズ_詳細仕様_メール配信` を参照
    - 注文締切リマインダー（未注文メンバー向け）
    - イベント終了アンケート
    - カート未完了リマインダー
    - 新着イベント通知
    - 注文完了通知（主催者向け）
    - 注文締切リマインダー（主催者向け）
    - イベント情報メール（全ユーザー向け。`user_type: "enterprise"` のユーザーには送信しない）
- 実装は `enterprise_id`（イベント/コミュニティ）および `user_type`（全ユーザー向けメール）で送信対象を区別する


## フェーズ分け

## MVP（Phase 1）
- 企業メールドメイン + OTP ログイン
- 全社管理者画面（全社設定、アカウント管理、コミュニティ承認、割引設定、ダッシュボード）
- 一般従業員画面（イベント参加・注文、割引参加、コミュニティ作成）
- 支払い方式: 福利厚生割引（デフォルト）、参加者事前決済、主催者請求書払い
- 割引機能（福利厚生割引時のみ。固定金額 + 割合。月額上限あり。上限超過後は全額自己負担で注文可能）
- 決済: クレジットカード決済のみ
- ゲスト参加（無料参加 / 自己負担の2択）
- イベント連続作成（複製のみ）
- イベント自動中止
- ダッシュボード（月別基本集計 + CSV）
- メール通知（最低限のみ: 注文確認、イベントリマインダー等）
- セッションタイムアウト（60分無操作で自動ログアウト）
- 監査ログ（基本: ログイン、管理者操作、注文の記録）

## Phase 2
- SSOログイン（Identity Platform + SAML/OIDC）
- 給与天引き対応（CSV出力）
- ゲストへの割引適用
- ゲスト請求先の選択（全社管理者 / コミュニティ管理者）
- 割引ルールの拡張
- イベント連続作成の一括編集連動（1つ編集すると他にも反映）
- IPアドレス制限
- 監査ログ拡張（ログ保持期間設定、エクスポート機能、タイムアウト時間の企業カスタマイズ）


## 決定事項（検討事項からの卒業）

## ログインについて → 決定済み
- MVP: 企業メールドメイン + 6桁OTPのみ。SNSログインはエンタープライズ版では提供しない
- Phase 2: Identity Platform にアップグレードし、企業ごとにSSO（SAML/OIDC）対応

## セキュリティ対策 → 方針決定済み
- **データ暗号化**: MVP では Firebase デフォルトの保存時暗号化で十分。追加の暗号化は Phase 2 以降で必要に応じて検討
- **IPアドレス制限**: MVP では不要。企業メールドメイン制限で十分。Phase 2 以降で必要に応じて対応
- **Firebase構成**: 単一Project + `enterprise_id` による論理分離。物理分離は行わない
- **セッション管理**: MVP から対応。60分無操作で自動ログアウト（フロントエンド実装）。アカウント停止時は `revokeRefreshTokens()` で即時セッション無効化
- **監査ログ**: MVP から基本的なログ基盤を構築。ログイン、管理者操作、注文の記録を最低限実装する。後付けするとログの欠損期間が発生し大企業への説明で致命的になるため、初期から導入する
- **メール通知**: MVP では最低限（注文確認、イベントリマインダー等）のみ。プラットフォーム版から必要なものを選定
- **メール配信制御**: エンタープライズ版のイベント・ユーザー向けに不要なメール（注文締切リマインダー、イベント終了アンケート、新着イベント通知、イベント情報メール等）は送信しない。`enterprise_id` および `user_type` で制御。詳細は `04_エンタープライズ_詳細仕様_メール配信` を参照

## ゲスト参加機能 → 決定済み
- MVP から対応する
- プラットフォーム版ユーザーがエンタープライズ版の「ゲストOK」イベントに参加できる
- ゲストの決済は「無料参加」「自己負担（全額クレカ）」の2択（MVP）
- ゲストへの割引適用は Phase 2
- 請求先は MVP では全社管理者に一本化。Phase 2 でコミュニティ管理者の選択に対応

## 支払い方式・決済 → 決定済み
- エンプラ版のイベントでは3つの支払い方式から選択可能
    - **福利厚生割引（enterprise_subsidy）**: デフォルト。企業の割引ルール適用後、残額をクレカ決済
    - **参加者事前決済（user_advance）**: PF版と同じ処理。割引なし
    - **主催者請求書払い（community_bill）**: PF版と同じ処理。割引なし
- **当日払い（user_on_day）は deprecated**。PF版でも利用実績なし。エンプラ版では選択不可
- 割引計算ロジックは `enterprise_subsidy` の場合のみ走る
- Phase 2: 給与天引き対応（CSV出力）

## 割引ルール → 決定済み
- MVP: 固定金額割引 + 割合割引の両方に対応。福利厚生費（食事補助）の半額負担ルールに対応するため
- 月額上限あり（ex. 1人あたり月7,500円）。月はイベント開催月に紐づく
- 上限超過後は割引なし（全額自己負担）で注文可能
