# イベント管理 詳細仕様

本ドキュメントは `01_エンタープライズ_仕様概要`、`02_エンタープライズ_全体構成・アーキテクチャ`、`04_エンタープライズ_詳細仕様_全社管理者画面` の決定事項に基づき、エンタープライズ版のイベント関連機能（連続作成・自動中止・PF版との差分・コミュニティ作成）の仕様を詳細に定義する。

## 前提とする仕様書

本ドキュメントは EventMemberOrder 設計（`05_EventOrder→EventMemberOrder.md`）を前提とする。注文集計の参照先は `members/{userId}/member_orders/{orderId}` に変更される（旧 `orders` コレクションは廃止）。


# 1. 概要

## 1.1 対象機能

| 機能 | 概要 |
|:--|:--|
| イベント連続作成 | 複製UIの拡張。最大10個の一括複製、日付の自動設定（毎日/毎週/毎月等） |
| イベント自動中止 | 注文期限3日前に注文個数が最小催行数を下回った場合、自動で予約キャンセル |
| プラットフォーム版との差分 | エンプラ版で追加/変更/非表示にする機能の明確化 |
| コミュニティ作成 | エンプラ版での作成フロー（作成→承認待ち→承認後に公開）の詳細 |

## 1.2 決定事項サマリ

| # | 論点 | 決定 |
|:--|:--|:--|
| E-1 | イベント連続作成の最大数 | 1回の操作で最大10個 |
| E-2 | 日付自動設定パターン | 毎日 / 毎週（曜日指定）/ 毎月（日付指定）/ 隔週 |
| E-3 | 自動中止の判断タイミング | 注文期限の3日前（注文期限日の00:00から3日を引いた日） |
| E-4 | 自動中止の閾値 | デフォルトは店舗の「最小注文個数」（shop_range_min_orders） |
| E-5 | SNS投稿・ハッシュタグ | イベントページ・注文完了時の投稿はなし。ハッシュタグ入力欄も非表示 |
| E-6 | コミュニティ作成 | 従業員作成時は承認待ち。管理者直接作成時は自動承認 |


# 2. イベント連続作成

## 2.1 プラットフォーム版の現状

- **イベントコピー**（`documents/02_主催者獲得と継続/04_イベントコピー.md`）
  - 1回の操作で **1イベントのみ** 複製
  - コピー元選択 → 日付選択 → 作成
  - 開催日時: 同じ時刻・同じ曜日、かつ「現在から2週間以上後」
  - タイトル末尾に「のコピー」を付与
  - 下書き保存

- **CopyEventDialog.vue**: 単発コピーのみ。`eventCopy` Callable Function を呼び出し

## 2.2 エンプラ版の仕様

### 2.2.1 複製UI

| 項目 | 内容 |
|:--|:--|
| 配置 | イベント一覧画面。PF版の「イベントをコピーする」に加え、「連続作成」ボタンを追加 |
| 最大個数 | 1回の操作で **最大10個** まで作成 |
| 作成フロー | ①コピー元イベント選択 → ②開始日選択 → ③繰り返しパターン選択 → ④プレビュー表示 → ⑤確認ダイアログ → ⑥一括作成 |

### 2.2.2 日付の自動設定パターン

| パターン | 説明 | 例 |
|:--|:--|:--|
| 毎日 | 開始日から連続で毎日（最大10日分） | 3/10〜3/19 |
| 毎週 | 同じ曜日で最大10週分 | 毎週月曜 × 10回 |
| 毎月 | 同じ日付で最大10ヶ月分 | 毎月15日 × 10回 |
| 隔週 | 2週間おきで最大10回 | 3/10, 3/24, 4/7... |

- 営業日チェック: PF版と同様、`isInShopTime` で店舗の営業日のみ候補とする
- タイムゾーン: Asia/Tokyo で統一
- 開始日: 現在から2週間以上後（PF版と同様）

### 2.2.3 複製時の設定

| 項目 | 内容 |
|:--|:--|
| タイトル | 1個目は「のコピー」付与。2個目以降は日付を付与（例: 「〇〇のコピー 3/11」） |
| メニュー | コピー元の `is_selected` 状態を引き継ぎ、`partnerId/menus` から複製 |
| ステータス | すべて「下書き」（in_draft）で保存 |
| enterprise_id | コピー元の `enterprise_id` を引き継ぐ |

### 2.2.4 Functions 設計

| 関数名 | トリガー | 概要 |
|:--|:--|:--|
| eventBulkCopy | onCall | 連続作成。`{ srcEventId, startDate, pattern, count }` を受け取り、最大10個まで複製 |

**引数:**

```typescript
interface EventBulkCopyParams {
  srcEventId: string
  startDate: number       // 開始日の epoch ms（その日の開始時刻 + 元イベントの時刻オフセット）
  pattern: 'daily' | 'weekly' | 'monthly' | 'biweekly'
  count: number           // 1〜10。バリデーション必須
}
```

**戻り値:**

```typescript
{ newEventIds: string[] }
```

**認証:** イベントのコミュニティ管理者（manager ロール）かつ `enterprise_id` が一致すること

## 2.3 実装優先度

| Phase | 内容 |
|:--|:--|
| MVP | 連続作成（最大10個、日付自動設定） |
| Phase 2 | 一括編集連動（1つ編集すると他にも反映） |


# 3. イベント自動中止

## 3.1 仕様概要

「注文期限の3日前」に「注文個数が最小催行数以下」の場合、自動で予約をキャンセルする。デフォルトの閾値は店舗が設定する「最小注文個数」。

## 3.2 「注文期限3日前」の計算

| 項目 | 内容 |
|:--|:--|
| 計算方法 | `event_deadline_datetime` を Asia/Tokyo で解釈し、その日の 00:00 から 3日（72時間）を引いた日 |
| 判定ウィンドウ | 判断日の 00:00:00 〜 23:59:59 の間に Scheduled Function が実行された場合に判定 |

**計算例:**

```
注文期限: 3/15 12:00
→ 判断日: 3/12
→ 3/12 00:00 〜 3/12 23:59 の間に実行された polling で判定
```

```typescript
// 計算例（Luxon 使用）
const deadline = DateTime.fromMillis(event_deadline_datetime, { zone: 'Asia/Tokyo' })
const judgmentDate = deadline.startOf('day').minus({ days: 3 })
// 判定: 現在時刻が judgmentDate の日付範囲内か
```

## 3.3 注文個数の算出

| 項目 | 内容 |
|:--|:--|
| 集計対象 | **`member_orders` コレクション** で `status === 'ordered'` のドキュメント数（1 メニュー = 1 ドキュメントのため、ドキュメント数 = メニュー個数の合計） |
| クエリ | `collection('communities/{cid}/events/{eid}/members')` 配下の各 `member_orders` を集計、または `collectionGroup('member_orders').where('event_id', '==', eid)` |
| 参照 | PF版の集計ロジックも EventMemberOrder 化により `member_orders` ベースに変更される（`05_EventOrder→EventMemberOrder.md` 参照） |
| 閾値 | 店舗の `shop_range_min_orders` から `min_orders_on_spot` を算出（配送距離に応じた最小注文数。EventEdit.vue と同様のロジック） |

> 旧設計では `orders/{oid}.menus[].count` の合計でメニュー個数を算出していたが、新設計では 1 ドキュメント = 1 メニューのため `member_orders` ドキュメント数で直接カウントできる。

## 3.4 Scheduled Function の仕様

| 項目 | 内容 |
|:--|:--|
| スケジュール | 毎分実行（`*/1 * * * *`）。既存 `pollingTask` に統合するか、別 Function として実装するか要検討 |
| 対象 | `enterprise_id` が設定されたイベントのみ |
| 条件 | `event_status.value === 'accepting_order'` かつ 判断日時を過ぎている |
| 処理 | 注文個数 ≤ 最小注文個数 の場合、イベントを `event_canceled` に更新し、返金・通知を実行 |

### 3.4.1 処理フロー

1. 毎分実行の Scheduled Function が起動
2. `enterprise_id` が存在し、`event_status.value === 'accepting_order'` のイベントを取得
3. 各イベントの `event_deadline_datetime` から判断日を計算
4. 現在日時が判断日に該当するイベントについて、注文個数を集計
5. 注文個数 ≤ 最小注文個数の場合:
   - `event_status` を `event_canceled` に更新
   - **全 `member_orders` の status を `event_canceled` に更新**（1 注文 = 複数ドキュメントになるため、`collectionGroup` または各 members 配下のループで一括更新）
   - 返金処理（PF版の `08_イベント中止と返金.md` に準拠。新設計では `stripes` ドキュメント単位で Stripe Refund を実行）
   - 注文者・主催者・飲食店へメール通知（同一注文者への通知は重複防止）

## 3.5 注文者への通知内容

| 項目 | 内容 |
|:--|:--|
| 件名 | イベントが中止となりました |
| 本文 | イベント名、開催予定日、中止理由（参加人数が最小催行数に達しなかったため）、返金の案内 |
| 送信タイミング | 自動中止処理の直後 |
| 送信対象 | `status === 'ordered'` の注文者全員 |

## 3.6 主催者・飲食店への通知

| 対象 | 内容 |
|:--|:--|
| 主催者 | 自動中止の旨、理由（注文個数不足）、返金実施の案内 |
| 飲食店 | 予約キャンセルの通知（PF版のイベント中止時と同様） |

## 3.7 Firestore スキーマ

PF版の `08_イベント中止と返金.md`、`09_イベントの最小催行人数設定.md` を参照。`event_canceled` ステータス、`cancel_reason`、`refund_status` 等を利用する。

自動中止の場合は `canceled_by` にシステム識別子（例: `"system_auto_cancel"`）を設定し、`cancel_reason` に「参加人数が最小催行数に達しなかったため」等の定型文を設定する。

## 3.8 監査ログ

| アクション | 内容 |
|:--|:--|
| event_auto_cancel | 自動中止時に記録。`target_type: 'event'`, `target_id: eventId`, `details: { order_count, min_required }` |


# 4. プラットフォーム版との差分

## 4.1 エンプラ版で追加する機能

| 機能 | 概要 |
|:--|:--|
| イベント連続作成 | 最大10個の一括複製、毎日/毎週/毎月等の日付自動設定 |
| イベント自動中止 | 注文期限3日前の注文個数チェックと自動キャンセル |
| ゲスト参加 | `allow_guest`, `guest_payment`（04_ゲスト参加 参照） |
| 福利厚生割引 | `event_payment: 'enterprise_subsidy'`（04_割引・決済 参照） |

## 4.2 エンプラ版で変更する機能

| 機能 | PF版 | エンプラ版 |
|:--|:--|:--|
| 支払い方式 | user_advance, user_on_day, community_bill | enterprise_subsidy（デフォルト）, user_advance, community_bill。**user_on_day は選択不可** |
| イベントコピー | 1個ずつ | 最大10個の連続作成に対応 |
| コミュニティ作成 | 即時公開 | 作成 → 承認待ち → 承認後に公開 |

## 4.3 エンプラ版で非表示にする機能

| 機能 | 非表示箇所 | 理由 |
|:--|:--|:--|
| SNS投稿ボタン | イベントページ（`EventDetailsCard.vue` の shareSnsButton） | 社内利用のため不要 |
| 注文完了時のSNSシェア | `UserSuccessJoinEventDialog.vue` の「参加することをSNSで友だちにも知らせよう」 | 同上 |
| ハッシュタグ入力 | イベント編集の `event_sns_hash_tag`、コミュニティ編集の `community_sns_hash_tag` | SNS投稿機能を使わないため |
| 当日払い | `user_on_day` 選択肢 | deprecated。PF版でも利用実績なし |

### 4.3.1 非表示の実装方針

- `enterprise` パッケージでは、base の `EventDetailsCard`、`UserSuccessJoinEventDialog`、`EventDetailCard`、`CommunitySetupForm` 等をラップし、SNS・ハッシュタグ関連の UI を出さない
- または base に `hideSnsFeatures?: boolean` のような props を追加し、エンプラ版から `true` で渡す
- 既存データの `event_sns_hash_tag` は DB 上は残すが、エンプラ版 UI では表示・編集しない


# 5. コミュニティ作成（エンプラ版フロー）

## 5.1 一般従業員が作成する場合

```
1. コミュニティ作成フォーム入力・送信
2. Firestore に保存（approval_status: "pending", enterprise_id: 設定）
3. 全社管理者全員にメール通知「新しいコミュニティが申請されました」
4. 作成者のコミュニティ管理画面に「承認待ち」として表示（他ユーザーには非表示）
5. 全社管理者が承認 or 却下
6. 承認時: approval_status: "approved" → 作成者にメール → コミュニティ一覧に表示
7. 却下時: approval_status: "rejected" + rejection_reason → 作成者にメール → 再申請可能
```

詳細は `04_エンタープライズ_詳細仕様_全社管理者画面.md` の「5. コミュニティ承認・管理画面」を参照。

## 5.2 全社管理者が直接作成する場合

- 承認フローをスキップし、`approval_status: "approved"` で保存
- コミュニティ一括作成（CSV）でも同様に自動承認

## 5.3 表示ルール

| 条件 | 表示 |
|:--|:--|
| approved | コミュニティ一覧に表示。全従業員が参加可能 |
| pending | 作成者本人のコミュニティ管理画面にのみ表示。「承認待ち」ラベル付き |
| rejected | 作成者本人のコミュニティ管理画面にのみ表示。「却下」ラベル + 却下理由表示 + 「再申請」ボタン |


# 6. その他検討事項

## 6.1 イベント関連

| 検討事項 | 内容 |
|:--|:--|
| 予約申請フロー | エンプラ版でも飲食店の予約承認フロー（applying_reservation → applying_to_admin → accepting_order）を維持する |
| 店舗選択 | エンプラ版でも PF版の partners/shops を共有。企業専用店舗は要検討 |
| イベント公開設定 | `is_public` / URL限定公開の扱い（01_仕様概要の「公開設定」「URL限定公開」） |
| 自動中止の閾値カスタマイズ | MVPでは店舗の最小注文個数のみ。Phase 2 でイベント単位の上書き可否を検討 |

## 6.2 コミュニティ関連

| 検討事項 | 内容 |
|:--|:--|
| 承認待ち中の編集 | pending 中に編集可能。編集後も再申請は不要（既に pending のまま） |
| 却下後の再申請 | 編集必須か、そのまま再申請可能か → 04_全社管理者画面 で「できる」と決定済み |

## 6.3 メール・通知関連

| 検討事項 | 内容 |
|:--|:--|
| イベント情報メール | `eventInformation` はエンプラユーザーには送信しない（04_エンタープライズ_詳細仕様_メール配信 に記載済み） |
| 自動中止通知 | 新規メールテンプレートの作成が必要 |
| 注文期限リマインド | PF版の `sendOrderDeadlineReminderToCommunityMembers`（2日前）をエンプラ版でも利用する |

## 6.4 パフォーマンス・運用

| 検討事項 | 内容 |
|:--|:--|
| 連続作成のタイムアウト | 10個一括作成時の Functions タイムアウト（540秒想定で足りるか） |
| 自動中止の実行順 | 既存 `pollingTask` に統合する場合、処理時間増加の影響を確認 |
| 返金処理 | 自動中止時の返金は、手動中止と同様に Stripe 返金 API を使用。**新設計では `stripes` ドキュメント単位** で Refund を実行（`04_割引・決済` 5.5 / `02_全体構成` 3.5 参照） |
| `monthly_usage` の戻し | 自動中止で `enterprise_subsidy` 注文を `event_canceled` に変更する際、当該 `member_orders` の `pay_enterprise_subsidy_amount` 合計を `EnterpriseMember.monthly_usage` から減算する（`04_割引・決済` 3.4 / 5.5 と同じロジック） |
