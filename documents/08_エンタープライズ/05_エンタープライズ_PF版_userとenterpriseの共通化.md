
# user（PF版）と enterprise の共通化について

## 1. 現状の設計

`02_全体構成・アーキテクチャ` では **「user をコピーして enterprise を独立パッケージにする」** 方針です。

一方で、1.4 には次の方針があります。

> **共通ロジックは可能な限り `base` / `common` に寄せる**
> - コピー後に enterprise 固有でない変更を user に入れた場合、base に引き上げることを検討する

つまり、「コピー」を前提にしつつ、**共通部分は base/common に寄せる** という共通化はすでに想定されています。

---

## 2. 共通化のパターン

「PF版で新機能を作ったら enterprise にも反映される」ようにするには、次のような選択肢があります。

### パターンA: base を厚くする

**考え方**: user と enterprise を薄い「シェル」にして、共通画面・ロジックを base に寄せる。

```
base/                          ← 共通部分を拡張
├── components/
│   ├── pages/                 ← コミュニティ一覧、イベント詳細、カート、マイページ等
│   └── ...
├── composables/
├── stores/
└── ...

user/                          ← PF版シェル（薄い）
├── pages/
│   ├── index.vue              ← PF版トップ（公開イベント一覧）
│   ├── login.vue              ← SNS + メールOTP
│   └── ...
└── router/

enterprise/                    ← エンプラシェル（薄い）
├── pages/
│   ├── index.vue              ← エンプラトップ（企業ブランディング）
│   ├── login.vue              ← メールOTP のみ
│   ├── admin/                 ← 全社管理者画面（エンプラ固有）
│   └── ...
└── router/
```

**メリット**:
- 新機能を base に置けば、user と enterprise の両方に反映される
- 差分はログイン・トップ・ナビ・全社管理者画面などに限定できる
- 既存の base/common の流れに沿っている

**デメリット**:
- base の責務が増える
- base が router/utils などに依存している問題を解消する必要がある（05_PF版_リファクタリング の内容）

---

### パターンB: 1パッケージ + ビルド時切り替え

**考え方**: user 1本のソースを、ビルドフラグで PF版 / enterprise のどちらかとしてビルドする。

```typescript
// Vite の define で
define: {
  VITE_APP_MODE: JSON.stringify(process.env.VITE_APP_MODE) // 'platform' | 'enterprise'
}
```

分岐は **エントリーポイント付近** に限定する想定です。

- `main.ts`: 認証・ルーターの初期化をモードで分岐
- `router/`: PF版と enterprise でルート定義を出し分け
- `layouts/`: ナビゲーションをモードで出し分け
- `pages/login.vue`: モードで SNS ボタンの表示を切り替え

**メリット**:
- 1箇所の修正が両方に反映される
- 共通部分に `if` をほとんど書かなくてよい

**デメリット**:
- 分岐が増えると複雑になりやすい（当初コピー方式を選んだ理由）
- ビルド・デプロイの設定がやや複雑になる

---

### パターンC: コピー + 継続的マージ

**考え方**: 現状どおりコピーしつつ、user の変更を enterprise に定期的にマージする。

- スクリプトで `user/` の差分を `enterprise/` に適用
- マージコンフリクトは enterprise 固有部分だけ手動で解決
- 共通タスク（05_プラットフォーム版共通タスク）は PF版で先に実装し、その結果を enterprise にマージ

**メリット**:
- 既存の「コピー」方針を大きく変えずに済む
- パッケージは独立したまま

**デメリット**:
- マージ作業が継続的に発生する
- 反映漏れのリスクがある

---

## 3. 採用方針: コピー + 継続的マージ

**結論**: **パターンC（コピー + 継続的マージ）** を採用する。

現状どおり user をコピーして enterprise を作成し、user の変更を enterprise に定期的にマージする方針とする。

### 3.1 採用理由

| 観点 | パターンA（base を厚くする） | パターンC（コピー + マージ） |
|------|------------------------------|------------------------------|
| 事前準備 | base の大規模リファクタが必要 | 不要。すぐ着手できる |
| 工数・リスク | 05_PF版_リファクタリングの実施が必要。user/admin への影響リスク | 既存コードへの影響が少ない |
| 開発開始 | enterprise 開発開始が遅れる | 早期に enterprise 開発を開始できる |
| 現実性 | base の責務拡大や境界の判断が難しい | 既存の「コピー」方針を維持できる |

「ほとんどが共通」という前提であっても、base を厚くするには事前のリファクタリング工数が大きく、現時点では **コピー + マージの方が現実的** と判断する。

### 3.2 考慮点

- **マージ作業**: 継続的に発生する。定期的な運用として組み込む
- **反映漏れ**: リスクはあるが、マージ頻度やチェックリストで軽減する
- **将来の見直し**: マージの負荷が大きくなった段階で、base への共通化を再検討する

---

## 4. マージを円滑にする工夫

| 工夫 | 内容 |
|------|------|
| **マージの頻度** | 週1回やスプリント単位など、定期的にマージする |
| **マージの単位** | 機能単位でマージし、コンフリクトを小さくする |
| **差分の集約** | enterprise 固有の変更を `enterprise/` 配下に集約し、マージ時のコンフリクトを減らす |
| **マージスクリプト** | `git merge` や `git diff` を使った半自動マージの検討 |
| **共通タスクの優先** | `05_プラットフォーム版共通タスク` は PF版で先に実装し、その結果を enterprise にマージする |

---

## 5. 設計ドキュメントとの整合

`02_全体構成・アーキテクチャ` の 1.4「長期メンテのコスト軽減策」は以下の通り維持する。

- **共通ロジックは可能な限り `base` / `common` に寄せる**
  - コピー後に enterprise 固有でない変更を user に入れた場合、base に引き上げることを検討する
- **エンタープライズ固有の差分だけを `enterprise` パッケージに残す意識を持つ**

共通化は「マージ時に base に寄せられる部分があれば検討する」程度とし、事前の大規模リファクタは行わない。
