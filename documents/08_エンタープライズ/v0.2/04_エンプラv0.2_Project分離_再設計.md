## 1. 目的とスコープ

- v0.1 は **単一 Firebase Project** に PF（user/partner）とエンプラ（enterprise）を同居させ、`enterprise_id` で論理分離していた。
- パターン B では **PF Project と Enterprise Project を物理分離**する。企業間は引き続き `enterprise_id` の論理分離。
- 本書は「v0.1 から **何が変わるか**」の差分設計に絞る。変わらない部分（割引計算・monthly_usage・課金スナップショット等のドメインロジック）は v0.1 を踏襲する。

### 1.1 パターン B で解決する課題（再掲）

| v0.1 の課題 | パターン B での解決 |
|:--|:--|
| PF/エンプラの Firebase Auth 混在 | Auth が Project 単位で物理分離 |
| エンプラユーザーが PF 版にログイン | Project が別 = ログイン不能 |
| PF 版にエンプライベントが表示（フィルタ漏れ） | PF Project にエンプラデータが存在しない |
| PF マイページにエンプラ情報が表示 | `users` が別 DB |

## 2. 全体構成

```
┌─────────────────────────── PF Firebase Project ───────────────────────────┐

│ Auth: PF ユーザー（SNS / メール）                                          │

                 ▲ 飲食店マスター参照 / 予約承認 / 注文参照（Bridge: §4.5）
                 │
┌──────────────────────── Enterprise Firebase Project ───────────────────────┐
│ Hosting: enterprise（全社・サブドメインで企業切替）                        │

└────────────────────────────────────────────────────────────────────────────┘

共有（ソースコード・npm workspaces）: common / base / functions_base
```

## 4. 領域別の再設計

### 4.1 Firebase Project / 環境

- **新規に Enterprise Project を各環境分作成**（sandbox / development / production）。
- `PROJECT_ID` / `GCLOUD_SERVICE_KEY` / Secret Manager が **PF とは別系統**になる。
- env ファイル接尾辞（`-m development` 等）の運用は維持しつつ、`enterprise/.env.*` の `VITE_PROJECT_ID` 等が Enterprise Project を指す。
- terraform は Enterprise Project 用の構成を分離（§4.12）。

**論点**: 環境数 × 2 Project になるため、IAM・課金・モニタリングの初期セットアップが増える（ただし企業数には依存しない＝ N 倍にならない、がパターン B の肝）。

### 4.2 認証・Auth（分離）

| 項目 | v0.1 | パターン B |
|:--|:--|:--|
| Auth インスタンス | PF と共有 | Enterprise Project 専用 |
| `user_type` の役割 | PF/エンプラの判別フラグ（必須） | **判別目的では不要**（Project が境界）。データ属性としては残してよい |
| エンプラユーザーの PF ログイン | Rules / UI で抑止 | **物理的に不可** |
| custom claims | `enterprise_id` / `enterprise_role` / `user_type` | `enterprise_id` / `enterprise_role` を継続。`user_type` は任意 |
| OTP 認証 | PF と同一プロジェクトの Functions | Enterprise Project の Functions |

- メール配信の `user_type` フィルタ（v0.1 §6.3）は、**そもそも PF と DB が別**なので「エンプラ宛に PF メールを送らない」制御が不要になるケースがある（PF メール送信ロジックが Enterprise Project に存在しない）。残すのは Enterprise 側で送る/送らないの制御のみ。
- セッション管理（60分無操作・`revokeRefreshTokens`）は v0.1 を踏襲。

### 4.3 Firestore データモデル（PF 共存の解消）

v0.1 は「PF データ（`enterprise_id` 欠如）と企業データを同一 DB に共存」させ、`data.get('enterprise_id', null)` で判別していた。パターン B では **Enterprise Project に PF データが存在しない**ため、次が変わる。

- `enterprise_id` は Enterprise Project 内で **常に必須**（optional ではなく required にできる）。
- 「`enterprise_id == null` = PF データ」という分岐が **不要**。
- ただし `enterprise_id` は **企業間分離**のために引き続き全 doc に必須（D / B′ への移行余地・企業別削除のため。再検討.md §9.4.1）。
- コレクション構成自体（`enterprises` / `communities` / `events` / `members` / `member_orders` / `stripes` / `audit_logs`）は v0.1 を踏襲。
- **PF の partners/shops/menus は Enterprise Project に存在しない** → §4.6 で参照方法を再設計。

### 4.4 Security Rules（単純化）

v0.1 §5.2 の `docEnterpriseId(data) == null || isSameEnterprise(data)` は、PF データ共存のための分岐だった。パターン B では:

```javascript
// Enterprise Project の Rules（PF 共存分岐が消える）
function isSameEnterprise(data) {
  return request.auth != null
    && data.enterprise_id == request.auth.token.enterprise_id;
}

match /communities/{communityId} {
  allow read: if isSameEnterprise(resource.data);   // null 分岐が不要
  // ...
}
```

- PF 回帰テスト（PF データが壊れないか）が **不要**になり、Rules CI は「他社 read 拒否 / 自社 read 許可」に集中できる。
- `docEnterpriseId(data) == null` で表現していた「エンプラユーザーの PF イベント参加」(§5.1) は **別 DB なので Rules では表現できない** → §4.7 ゲスト/社外イベント参加の再設計が必要。
- Rules ユニットテスト基盤（`tests/firestore-rules`）は Enterprise Project の rules を対象にする。

### 4.5 partner 連携（最重要論点・Bridge 設計）

v0.1 では partner と enterprise が同一 DB だったため、予約承認・注文参照が単一クエリで完結していた。パターン B では partner（PF Project）と企業データ（Enterprise Project）が **別 Project** になる。`01_再設計.md` §partner の論点が全てここに集約される。

| 処理 | v0.1 | パターン B の選択肢 |
|:--|:--|:--|
| 予約申請の承認/却下（`event_status: applying_reservation`） | 同一 DB の events を更新 | (a) partner が Enterprise Project にも接続 (b) Functions 経由で更新 |
| memberOrders / 注文の参照 | collectionGroup 1 回 | (a) partner が両 Project を読む (b) 集約 API |
| PartnerMenus → EventMenus コピー | 同一 DB 内コピー | PF Project → Enterprise Project へクロスコピー（§4.6） |

**推奨 Bridge 設計（T-4）**:
- partner アプリ自体は **PF Project を hub** とし、Enterprise Project のデータは **Functions（Admin SDK）経由の集約 API** で取得・更新する。
- 理由: partner クライアントが多数の Project に直接接続するのは認証・SDK 初期化が複雑化するため。Functions に寄せると Project 境界を 1 箇所に閉じ込められる。
- 代替: partner が Enterprise Project にも Firebase 接続（読み取り専用 + Rules で partner ロール許可）。実装は軽いが、企業 Project が増えた場合（D/B′）に接続先が増える弱点。

→ **本書では論点提示に留め、Bridge 詳細は別紙化**（再検討.md §13 のアクション）。MVP は「企業数 1 Enterprise Project」なので、まず (a) partner が PF + Enterprise の 2 Project read で開始し、API 集約は後続で検討する案も可。

### 4.6 飲食店マスター / メニューコピー

- `partners / shops / menus` は **PF Project に残す**（飲食店の正本。partner アプリが管理）。
- Enterprise アプリがメニューを使う経路:
  1. **イベント作成時に EventMenus へコピー**（v0.1 同様）。コピー元は PF Project の partner メニュー → Enterprise Project の `events/{eid}/menus` へ。クロス Project コピーは **Functions（Admin SDK で両 Project にアクセス）** で実装。
  2. 注文フロー自体は Enterprise Project 内の EventMenus で完結（v0.1 と同じ）。
- Enterprise アプリが「店舗・メニュー一覧を選ぶ」UI でマスターを読む場合は、PF Project の読み取り用 API（Functions）を経由。

**設計判断**: コピー方式により、注文・決済の主要フローは Enterprise Project 内で閉じる。クロス Project が必要なのは「メニュー選択・コピー」「予約承認」「partner の注文参照」に限定される。

### 4.7 ゲスト参加（専用アカウント）

v0.1 は「PF ユーザーがエンプラの allow_guest イベントに参加」（同一 Auth/DB 前提）だった。パターン B では Auth/DB が別になるため、`01_再設計.md` §ゲストの方針に沿って再設計する。

| 項目 | v0.1 | パターン B |
|:--|:--|:--|
| ゲストの正体 | PF ユーザー | **Enterprise Project 内の専用ゲストアカウント** |
| 認証 | PF ログイン流用 | メール + パスコードでゲストアカウント作成 |
| 企業をまたぐ場合 | 同一 PF アカウント | **企業ごとに作り直し**（別 Project / 別 Enterprise） |
| 社外イベント（PF コミュニティ）への参加 | `enterprise_id==null` read で許可 | 別 DB のため **この導線は廃止 or 別設計** |

→ ゲスト関連は v0.1 の [04_ゲスト参加](../v0.1/04_エンタープライズ_詳細仕様_ゲスト参加.md) を **パターン B 前提で改訂**する必要がある（要別タスク）。

### 4.8 common / base / functions 分割

- **common / base**: ソースは両 Project のビルドで共有（npm workspaces）。デプロイ先 Project が変わるだけで、コード共有方針は不変。
- **functions の分割**（`01_再設計.md` §2 / T-5）:

```
functions/
  functions_base/      … utils, store(partner/event/community), 共通ロジック
  functions_user/      … PF 業務 + 飲食店マスター提供 API（PF Project へデプロイ）
  functions_enterprise/… OTP, オンボーディング, 集計, 決済, 監査ログ（Enterprise Project へデプロイ）
```

- **懸念（`01_再設計.md` §懸念）**: Firebase Functions は 1 ディレクトリしかデプロイできない。`functions_base` の取り込みは:
  - 案A: シンボリックリンク（現状 common が `libs/` に貼っているのと同型）
  - 案B: GitHub Actions のフックで `functions_base` をコピーしてからデプロイ
  - 案C: TypeScript ビルド後に `functions_base` の実体をコピー
- v0.1 の `functions/default` の各処理（`memberOrders` / `stripe` / `stripeWebhook` / `cancelOrders` / `createEnterprise` 等）を `_user` / `_enterprise` / `_base` に振り分ける。

### 4.9 Hosting / ドメイン

- enterprise Hosting と `getEnterpriseByDomain` / `createEnterprise` は **Enterprise Project へ移設**。
- v0.1 デプロイ手順（[09_デプロイ手順](../v0.1/09_エンタープライズ_デプロイ手順.md)）の「同一 Project に enterprise target を追加」は、「**Enterprise Project の Hosting**」に置き換わる。
- サブドメインで企業を切替える「1 ビルド・複数テナント」方式（v0.1 §2）は維持。ドメイン解決 Functions も Enterprise Project に置く。
- `FIREBASERC` / `ENTERPRISE_ENV` は Enterprise Project を指す値に。

### 4.10 Stripe / 決済

- Stripe アカウント自体は Firebase Project と独立のため、**同一 Stripe アカウントを継続利用可能**。
- 変更点: `createStripeCheckoutSession` / `stripeWebhook` が **Enterprise Project の Functions** になり、**Webhook エンドポイント URL が変わる**（Stripe ダッシュボードのエンドポイント追加が必要）。
- `EventStripe` / `pay_enterprise_subsidy_amount` の計算ロジックは v0.1 を踏襲。
- **論点**: PF と Enterprise で Stripe の Connect アカウント / 売上計上を分けるか（決済・会計の要件次第。別途確認）。

### 4.11 Storage

- enterprise の Storage（`/enterprises/{eid}/` 配下、v0.1 §3.7）は **Enterprise Project のバケット**へ。
- PF と共有していたアセット（もしあれば）は、コピー or PF Project の公開 URL 参照で対応。
- Storage Rules も Enterprise Project 側に配置（`enterprise_id` パス一致）。

### 4.12 デプロイ / CI / terraform

| 項目 | v0.1 | パターン B |
|:--|:--|:--|
| `deploy_enterprise.yml` | PF と同一 Project の hosting:enterprise | **Enterprise Project** へデプロイ |
| `deploy_functions.yml` | functions/default を 1 Project へ | `_user` → PF Project、`_enterprise` → Enterprise Project |
| `deploy_firestore.yml` / `deploy_storage.yml` | 1 Project の rules | Project ごとに rules / indexes を分離 |
| Secret Manager | 1 Project | Project ごと（同期スクリプトは将来の D/C で必要、B では 2 系統） |
| terraform | 1 Project | Enterprise Project の構成を追加（Hosting / reCAPTCHA / API 有効化等） |

- **重要**: パターン B はデプロイが **2 系統で固定**（企業数に依存しない）。これがパターン C（100 系統）との決定的な差。

### 4.13 監査ログ・ドメインロジック（影響小）

- 監査ログ（`/enterprises/{eid}/audit_logs`）、割引計算、`monthly_usage` トランザクション、課金スナップショットは **v0.1 を踏襲**。Enterprise Project 内で完結するため、むしろ Rules・集計がシンプルになる。
