## 1. 目的とスコープ

- **目的**: `06` のタスク（PA-xx）を、実行順序・並行トラック・マイルストーン・ゲートに整理し、着手の迷いをなくす。
- **スコープ内**: v0.2 パターンA 実装（Phase 0〜1）と Phase 2 の入口。
- **スコープ外**:
  - PF版データ露出フィルタ（`enterprise_id == null` 必須化）→ **v0.3 §3-1 が正本**。
  - Project 分離（パターンB）そのもの → `03` の将来トリガー次第。
  - B′（エンプラ専用 Firestore Database）→ **v0.2 ではやらない**。blast radius を構造的に潰す必要が出た時のみ（`03` §4 トリガー）。`02` §13 の「B′ PoC」は将来アクションへ格下げ済み。

> **⚠️ 期待値合わせ（重要）**: 本計画（v0.2 単体）では、ユーザーの体感課題のうち **「PF版にエンプラのイベント/コミュニティ/ともだちが見える」は解消しない**。これはデータ露出（クエリ/Rules フィルタ）の問題で、**IdP マルチテナンシーでは消えない**（`06` §1・`03` §5.1）。解消するには PF版クエリへの `enterprise_id == null` 必須化が必要で、**正本は v0.3 §3-1**。v0.2 で解消するのは **Auth 境界（越境ログイン）** までである点をステークホルダーと合意しておくこと。

## 2. 前提・原則（3つだけ覚える）

1. **移行コストの非対称性**: sandbox がデータ削除可能な今のうちに、**本番に企業ユーザーが積まれる前に「認証モデルだけ」前倒し**する（`07` 確定方針 §3）。ゲスト/SSO/UI は移行に鈍感なので後続でよい。
2. **最小出荷ライン = Phase 0**。Phase 0 だけで「越境ログイン抑止・subsidy テスト分離・`if==enterprise` 撲滅・デプロイ独立・Rules 安全網」という v0.2 主目的を達成できる。
3. **ゲートで止める**: スキーマ（PA-10a PoC ＋ v0.3 §1〜§3 確定）と IdP（MAU 課金試算・移行論点）は**ゲート通過まで本実装に進まない**。

## 4. Phase 0（M0）— 4トラック並行

Phase 0 のタスクは相互依存が薄く、**4つの独立トラックに分けて並行実行**できる。

| トラック | タスク | 着手順 | 並行可否 |
|:--|:--|:--|:--|
| **T-A: Functions 純粋関数化（山場）** | PA-20a（最小境界定義）→ PA-21a → PA-21b → PA-21c/d → PA-21e → PA-21f | 最初に着手・最長 | 単独で進む |
| **T-B: DI 化（3 ファイル）** | PA-30a → PA-30b / PA-31a / PA-31b | T-A と並行 | 可 |
| **T-C: Auth 暫定ガード** | PA-03d | 即着手・即完了 | 可 |
| **T-D: CI / デプロイ独立** | PA-22a → PA-22b、PA-23、PA-24a → PA-24b | 即着手 | 可 |

- **着手順の考え方**: T-C・T-D の小タスク（PA-03d / PA-24a-b / PA-22a）は**クイックウィン**。最初のスプリントで即クローズし、可視課題（越境ログイン）とリリース独立を早期確保する。並行して**最長・最難の PA-21a（memberOrders 分岐抽出）に早く取りかかる**のがクリティカルパス短縮の鍵。
- **入口条件**: なし（すぐ着手可）。
- **出口条件（M0 達成）**: subsidy ロジックがユニットテスト可能 ／ `base` から `if==enterprise` 消滅 ／ エンプラ・PF 関数が独立デプロイ ／ Rules テストが CI 必須。

## 5. Phase 1（M1 → M2）— 認証モデルは直列・スキーマはゲート

### 5.1 M1: IdP 認証モデル（直列）

`07` §2 の通りクライアントの `tenantId` 固定が絡むため、バックエンド → クライアントの順で固める。

```
PA-01a/b（IdP 有効化・tenantId ログイン疎通）
  → PA-01d（enterprise_id ↔ tenantId 設計）／ PA-01c（Rules tenant 検証）／ PA-01e（移行方針）
    → PA-02a（authForTenant util）
      → PA-02b/c（auth.ts テナント化）・PA-02d（onboarding テナント化＝本丸）・PA-02e/f（メアド検索テナント化）
        → PA-03a（base tenantId 設定）→ PA-03b（ログイン UI）→ PA-03c（guard 拡張）
```

- **着手前ゲート（必須）**: `06` §1「認証モデル着手時に詰める論点」を先に確定する。
  - ロールバック境界（PA-02d の連鎖失敗時の補償）
  - 方式併存ウィンドウ（`enterprise_id` claim 方式 ↔ tenant 方式）
  - MAU 課金試算（Identity Platform）
  - partner 横断への影響確認
  - ゲスト身元＝**デフォルトプール固定**（`07` §3）を前提として固定
- **本丸 PA-02d**: 企業作成＝テナント作成＋初期管理者＋claims＋`users` doc の連鎖。トランザクション境界とロールバックを設計してから着手。

### 5.2 M2: スキーマ型分岐（別トラック・ゲート付き）

M1 と並行で PoC まで進められるが、本実装はゲート通過を待つ。

```
PA-10a（PoC・3 方式比較）→ [ゲート G1: PoC OK] → [ゲート G2: v0.3 §1〜§3 確定]
  → PA-11a 〜 PA-11d → PA-11e（partner 互換テスト）
```

## 7. クリティカルパス（実行視点）

```
[Phase 0] PA-21a ──→ PA-21b-f ┐
                               ├─→ M0
       PA-30a → PA-31a/b ──────┘
[Phase 1] (M0 と独立に着手可) 論点確定 → PA-01 → PA-02d → PA-03 ─→ M1
[ゲート] v0.3 §1-3 確定 → PA-11 ─→ M2
```

- 最長経路は **PA-21a（Phase 0 の本丸）** と **PA-02d（Phase 1 の本丸）** の 2 つ。
- この 2 つは**独立**なので、人員が 2 系統あればフェーズをまたいで同時進行できる（Phase 0 の T-A を進めつつ、別系統で M1 の論点確定〜PA-01 に着手）。

## 8. ゲート・意思決定ポイント

| ゲート | 判定内容 | 通らない場合 |
|:--|:--|:--|
| **G1: スキーマ PoC**（PA-10a） | discriminatedUnion × プロジェクト規約（`updateXXX` 全書き戻し・`withConverter`・`optionalDeleteField`）× partner 互換が成立するか | 方式を変える／Phase 2 へ延期 |
| **G2: v0.3 スキーマ確定** | `event.publish_scope` / `community.join_type` 等が固まったか | PA-11 着手を待つ |
| **G3: IdP 着手前論点** | ロールバック・方式併存・MAU 課金・partner 影響を確定したか | **M1 を延期**し、テナントなし `enterprise_id` claim 方式のまま本番投入。IdP は **後追い移行（プロジェクトレベル uid → テナント uid の重い移行＋テストを許容）** と決め直す（前倒しの非対称性メリットを放棄する判断・§2 原則1 の例外）。特に **MAU 課金が想定超過の場合の既定フォールバック** |

## 9. リスクとロールバック（要点）

| リスク | 対策 |
|:--|:--|
| PA-02d の連鎖失敗（テナント作成成功・管理者作成失敗等） | 補償トランザクション／ロールバック境界を設計してから着手（G3） |
| 方式併存ウィンドウの取りこぼし | `enterprise_id` claim 方式と tenant 方式の 2 方式併存期間の Rules / トークン判定を明文化 |
| MAU 課金の想定超過 | Phase 1 着手判断の入力として有効アカウント数で事前試算（G3）。**超過時は G3 フォールバック**（M1 延期・claim 方式で本番投入・IdP 後追い移行）を既定とする |
| 共有モジュール変更による両方テスト | PA-21（純粋関数化）で真の共有範囲を最小化（ゼロにはできない・`06` §3） |
