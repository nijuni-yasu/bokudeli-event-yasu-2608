## 0. 最重要：B起点のDとA起点のDの違い

既存の D 関連ドキュメント（`02` §9.2、`04_再設計`、`04_実装タスク`）は、**パターンB（PF Project + 共有 Enterprise Project）の上に Silo を載せる**前提で書かれている。

| | B起点のD（既存ドキュメント） | **A起点のD（本書）** |
|:--|:--|:--|
| 標準プラン | PF Project + 共有 Enterprise Project | **単一 Project（PF + 全エンプラ同居）** |
| Silo | Enterprise 側に専用 Project を1つ追加 | **単一 Project から1社を抜いて専用 Project へ** |
| partner Bridge | B 構築時にすでに存在（PF ↔ 共有 Enterprise） | **初回 Silo でゼロから構築** |
| 初回 Silo の重さ | 増分のみ（Bridge 拡張） | **B 相当の基盤を後払い** |

**A起点のDでは、最初の1社を切り出す瞬間に、A がわざと回避してきた multi-App 化・cross-project・partner Bridge・メニュークロスコピーを初めて全部作る。**「A は安い」前提のまま「最初の Silo は安い」とはならない。本書はその会計を明示する。

## 1. 構成イメージ（A + Silo 1社）

```
┌──────── 共有 Project（パターンA のまま）────────┐
│ PF: user / partner / partners・shops・menus（マスター）
│ エンプラ: enterprises / communities / events / member_orders …
│           （enterprise_id 論理分離。Silo 化した1社を除く全社が同居）
│ Auth: PF + 残りエンプラが混在（A の弱点は残る）
└───────────────────────────────────────────────┘
        ▲ 飲食店マスター参照 / 予約承認 / 注文参照 / メニューコピー
        │ （cross-project = 初回 Silo で新規構築）
        │
┌──────── 専用 Project（Silo: 企業X）────────┐
│ Auth: 企業X 専用
│ Firestore / Storage: 企業X のデータのみ
│ Functions: 企業X 用（または共有 Functions から cross-project）
└────────────────────────────────────────────┘
```

**ポイント**

- 共有側は A のまま。Auth 混在・blast radius・PF 露出リスクは**残存**する（消えるのは Silo 化した1社ぶんのみ）。
- partner は **「共有 Project（単一DB・collectionGroup 1回）」＋「Silo Project」** を読む Bridge クライアントになる。
- 2社目以降の Silo は、1社目で作った Bridge / multi-App / cross-project 基盤を**再利用**し増分で足す。

## 2. Silo オプションの2段（D vs B′）

「特定企業だけ物理分離」には、Project を増やす **D** と、Project は1つのまま Firestore Database だけ分ける **B′** の2段がある（`02` §6.5 / §4.1）。

| 手段 | 満たせること | 向かないこと |
|:--|:--|:--|
| **D（専用 Project）** | 契約書に「専用 Firebase Project / 専用環境」と明記できる。Project 単位 IAM・監査スコープ切り出し | Secret / terraform / デプロイが Silo ごとに増える |
| **B′（専用 Firestore DB）** | 他社到達不能・DB 単位 IAM・CMEK。運用は共有 Project 1 系統のまま | 契約上「専用 Project」文言が必須なら不足 |

**判断基準**（`02` §4.1）: 顧客要求の大半は Project 分割なしで満たせる。Project 分割が本質的に必要なのは **「契約上、専用環境を明記する」** ケース。本書の PD-xx は主に **D** を対象とするが、§8 で B′ を代替として併記する。

## 7. IdP マルチテナンシーが初回 Silo を救う構造

`05` §1 / `03` §5.1 と同内容を、Silo 文脈で強調する。

- A のまま **IdP マルチテナンシー（企業=テナント 1:1）**（PD-00b / PA-01〜04）を先にやると、各エンプラ企業の Auth は**テナントで uid 名前空間が分離**済みになる。
- Silo 移行は「**1テナントを丸ごと別 Project へ昇格**」に近づき、PD-13 がテナント単位 export/import で済む。
- IdP 化していない A だと、単一 Auth プールから `enterprise_id` でユーザーを選別する泥臭い作業が毎回発生する。

→ **A で進めるなら、PD-00b（IdP テナント化）は「将来の Silo 保険」としての価値が高い。** Silo を安く出せるオプションを成立させる前提投資として位置づける（`05` の PA-01〜04 と同一作業）。

## 8. B′（専用 Firestore DB）を Silo 代替とする場合

契約上「専用 Project」が不要なら、**Project を増やさず**企業X だけ named database を分ける B′（`02` §6.5）が運用負荷の面で有利な場合がある。

| 観点 | D（専用 Project） | B′（専用 DB、同一 Project） |
|:--|:--|:--|
| 他社データ到達 | 完全分離 | DB 単位で到達不能 |
| 運用者閲覧制御 | Project 単位 IAM | DB 単位 IAM 条件 |
| Secret / terraform / デプロイ | Silo ごとに増える | **1 系統のまま** |
| partner 横断 | 共有 DB + Silo Project | 共有 DB + Silo named DB（DB を N 回読む） |
| 契約「専用環境」 | Project 明記可 | 「専用 DB」で足りるか要法務確認 |

B′ 採用時のタスクは PD-10〜16 の Project 新設の代わりに「named DB 作成 + DB ごと Rules/index デプロイ」に置き換わる。Bridge（PD-20〜27）の本質（partner が複数データ境界を読む）は残る。

## 9. コストプロファイル（A→D vs A→B→D）

| 観点 | A→D（直接 Silo） | A→B→D（B を挟む） |
|:--|:--|:--|
| 初回 Silo のコスト | **高**（Bridge / multi-App / cross-project をゼロから構築） | B で先払い済み。Silo 追加は増分のみ |
| 共有側の Auth 混在 | **残る**（PF + 残エンプラ） | B で解消済み |
| 2社目以降の Silo | 1社目の基盤を再利用 → 増分 | 同左 |
| 向いているケース | Silo 要求が **1〜2社で打ち止め** の見込み | Silo **複数 / 常態化**、または共有側の Auth 混在も解消したい |

**示唆**: 初回 Silo 契約のタイミングで **A→B 移行を兼ねる**選択肢を常に比較する。2社目が見えている・エンプラ主力化（`03` §9）なら、トータルで B→D が安く、共有側の A 負債も解消できる可能性が高い。
