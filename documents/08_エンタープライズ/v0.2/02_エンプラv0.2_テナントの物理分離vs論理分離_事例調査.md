# エンタープライズ v0.2 テナントの物理分離 vs 論理分離 事例調査

`02_エンプラv0.2_テナントの物理分離vs論理分離_再検討.md` を補強するための **国内外のスタートアップ・SaaS の実例集**。各事例に出典 URL を付す。

> **要約**
> - 国内スタートアップは **ほぼ全社が論理分離（共有インフラ + テナントID）でスタート**。機微情報を扱う SmartHR ですら論理分離。
> - **物理分離（顧客ごと環境）からスタートした企業は、軒並み「論理分離への統合」に半年〜1.5年を費やしている**（counterworks / hacomono / ecforce）。
> - 海外でも DB-per-tenant は「スケールで破綻するアンチパターン」とされ、Atlassian は 750+ クラスタを 16 に集約した。
> - shokujii v0.2 の「100 社 = 100 Firebase Project」は、これら失敗事例と同じ構造。

## 1. 国内: 論理分離（共有インフラ + テナントID）スタートの事例

| 企業 | 事業 / 機微度 | 採用方式 | 出典 |
|:--|:--|:--|:--|
| **SmartHR** | 労務管理（マイナンバー・給与） | スキーマ単位の論理分離（Rails `apartment` → Citus `activerecord-multi-tenant`）。**物理 DB 分離はしない** | [SmartHR Tech Blog](https://tech.smarthr.jp/entry/2018/04/06/100000) |
| **ZOZOMETRY**（ZOZO） | BtoB 計測 | Pool 型。「ローンチ直後で専用リソースは管理コスト増」と判断し、アプリ層で tenant_id 保持 | [ZOZO TECH BLOG](https://techblog.zozo.com/entry/building-multi-tenant-system-with-zozometry) |
| **PHARMAX** | 医療（薬局） | GCP Identity Platform マルチテナンシー + Firestore Rules。**1 プロジェクト内の論理テナント** | [Zenn / pharmax](https://zenn.dev/pharmax/articles/95a2f0f76fd016) |
| **AProf** | 食品製造業 B2B（ワンオペ） | Firestore + tenant_id + Security Rules の多層防御。**shokujii に最も近い小規模 Firebase 構成** | [note / aprof](https://note.com/aprof/n/n136387f5300e) |
| **counterworks（SCE）** | 商業施設向け | Rails + PostgreSQL RLS の二重防御（ホスト名で企業分離） | [Zenn / counterworks 二重防御編](https://zenn.dev/counterworks/articles/1887cb36a1b701) |
| **freee** | 会計・人事労務 | 論理分離 + モジュラーモノリス。物理分割（マイクロサービス）は「失敗談が多い」と慎重 | [日経xTECH](https://xtech.nikkei.com/atcl/nxt/column/18/02744/020900003/) |

### 1.1 注目ポイント: 機微情報でも論理分離

SmartHR はマイナンバー・給与という最高クラスの機微情報を扱うが、物理 DB 分離ではなくスキーマ単位の論理分離を選択している。

> マイナンバーや給与情報などのセンシティブな個人情報を扱う...導入企業間でのデータの分離を保証しなければならない...初期選定として apartment というライブラリを選択した
> （出典: [SmartHR Tech Blog](https://tech.smarthr.jp/entry/2018/04/06/100000)）

→ shokujii が扱う「食事注文・社内コミュニケーション」は機微度がより低く、**論理分離で十分という主張は国内事例と整合する**。

### 1.2 注目ポイント: Firebase なら Identity Platform マルチテナンシー

PHARMAX は **プロジェクトを分けずに** Identity Platform の論理テナント機能で本番運用している。

> 既存のシステムが Firebase を使用していたため、Firebase とシームレスに統合できる Identity Platform が最も適していると判断した
> （出典: [Zenn / pharmax](https://zenn.dev/pharmax/articles/95a2f0f76fd016)）

→ shokujii が認証境界を強化したいなら、**「100 プロジェクト」の前に Identity Platform マルチテナンシー**が中間解になりうる。

## 2. 国内: 物理分離スタート → 論理分離へ統合した「後悔・苦労」事例

**最重要セクション。** shokujii v0.2 の「顧客ごとに環境を分ける」案と同じ構造で始め、その後に統合した事例。

### 2.1 counterworks「ショップカウンター エンタープライズ」

導入企業ごとに **独立した AWS アカウント** を立て、Rails アプリ・RDS・S3 を配置。1 社契約ごとに Terraform で環境一式が増える運用だった。これを **10 ヶ月かけて 1 環境に統合**。

挙げられた具体的な苦痛（v0.2 の `01_再設計.md` §CI とほぼ同一）:

- **インフラコストの線形増加**: 1 社追加 = AWS アカウント 1 個 = RDS + ECS + S3 一式追加
- **新規導入のリードタイム**: 受注のたびに Terraform で環境構築 + 外部サービス個別設定で数日〜1週間
- **デプロイパイプラインの増殖**: 企業数だけ CI/CD・Secrets が並列。1 修正で環境数だけデプロイ
- **リリース作業の負担**: 深夜メンテを企業数だけ繰り返す
- **監視・運用の分散**: ダッシュボードが企業数だけ並び、障害調査が困難
- **横断分析が困難**: 「全企業合計の予約数・請求サマリ」を一発で出せない

> 出典: [Zenn / counterworks 俯瞰編](https://zenn.dev/counterworks/articles/3e0df3b62f55f9)

**shokujii との対応**: 「デプロイ増殖」「Secret 管理」「partner の横断 read（= 横断分析）」は、`01_再設計.md` が懸念している点とそのまま一致する。

### 2.2 hacomono「シングルテナントの受難」

顧客ごとにインフラを分けた結果、AWS のサービスクォータと運用に苦しみ、ティアベースのマルチテナント化へ。

- EC2 の SLA、メモリ管理、**毎週の AWS 上限緩和チェック**（VPC / Elastic IP / S3 / EC2 / RDS が数千必要）
- リソースのムダ使い → Fargate + RDS 1 インスタンスで複数顧客対応へ
- 移行時の課題: **大量顧客のテナント移行・DB 移行が非常に大変。数千環境分。顧客によっては契約書レベルの修正対応**

> 出典: [Speaker Deck / hacomono](https://speakerdeck.com/hacomono/singurutenantonoshou-nan)

### 2.3 ecforce（SUPER STUDIO）

契約ごとに顧客専用リポジトリ + 専用インスタンスを作る方式で、**300 リポジトリ + 300 インスタンス**に到達。マルチテナント化に **約 1.5 年**。

> 顧客がサービスを契約するたびに、その顧客専用のリポジトリを新規作成...顧客ごとに専用のサーバーインスタンスを立て...300 個のリポジトリと 300 個のインスタンスが存在する状況

CTO の総括:

> シングルテナントという選択肢は取らないと思うのですが、**最初からマルチテナンシーを作り込まないというセンスは優れた判断**だった

> 出典: [Findy Tools / アーキテクチャConference 2025](https://findy-tools.io/articles/architecture-con2025-delta/259)

### 2.4 ripla（受託視点）の警鐘

> 当初 1 社専用で動かしていたシステムを複数社に提供したくなった段階で、**3,000 本超の SQL 文の書き換えと半年以上の開発期間**が発生。追加コストは数百万円規模

ただしこれは「論理分離設計を後回しにした」場合の話で、**テナント分離設計自体は初期に決めるべき**という教訓。

> 出典: [note / ripla](https://note.com/ripla_business/n/n9e1549d15ee3)

## 3. 海外: DB / 環境-per-tenant のスケール破綻事例

| 事例 | 内容 | 出典 |
|:--|:--|:--|
| **Atlassian Forge** | テナントごとスキーマ（DB=schema）で **750+ の PostgreSQL クラスタ**に膨張。bin-packing・接続プール・ホットスポット管理が運用負荷化 → **16 TiDB クラスタへ集約**。コスト・運用を大幅削減 | [PingCAP / Atlassian](https://www.pingcap.com/blog/how-atlassian-scaled-three-million-tables-multi-tenancy-tidb/) |
| **DB-per-tenant の罠** | 500〜1,000 テナントで破綻。接続プール枯渇、`ALTER TABLE` が 1,000 回の分散問題化、99% 空の DB が大量発生。解決は Cell ベース（複数テナントを 1 DB に束ねる）+ RLS | [DEV / The Multi-Tenant Trap](https://dev.to/ameer-pk/the-multi-tenant-trap-why-database-per-tenant-fails-at-scale-and-the-hybrid-fix-1c) |
| **PlanetScale** | DB-per-tenant の最大問題は接続上限。`CREATE DATABASE` ごとに system catalog が複製され、数百テナントでスケールしなくなる | [PlanetScale](https://planetscale.com/blog/approaches-to-tenancy-in-postgres) |
| **コスト試算** | DB-per-tenant は ~5,000 テナントで経済的に破綻。コスト曲線が垂直化。<1k テナントでの採用は「安全に感じる」だけの過剰設計 | [Appycodes](https://appycodes.dev/blog/multi-tenant-architecture-cost-study-2026/) |

共通する破綻パターン:

1. **マイグレーション地獄**: スキーマ変更が「テナント数 × 1 回」になり、部分失敗・バージョン不整合が発生
2. **接続プール枯渇**: テナントごとの接続が積み上がり DB の上限に達する
3. **オンボーディング律速**: 新規テナント = 環境構築。手動運用が人的ボトルネック化
4. **横断クエリ不能**: 課金集計・管理ダッシュボードが別 ETL を要する

## 5. shokujii v0.2 への示唆

| 論点 | 事例からの学び | shokujii への当てはめ |
|:--|:--|:--|
| 100 社 = 100 Project | counterworks / hacomono / ecforce が同構造で破綻し統合に半年〜1.5年 | 同じ轍。デプロイ・Secret・監視・横断分析の負荷は実証済み |
| 機微情報だから物理分離 | SmartHR（マイナンバー）すら論理分離 | 食事データは論理分離で説明可能 |
| 認証境界の強化 | PHARMAX は Identity Platform マルチテナンシーで対応 | 100 Project の前に検討すべき中間解 |
| partner の横断 read | 物理分離は「横断分析が困難」が共通の痛み | partner 全テナント read は物理分離で最も悪化する |
| 再構築リスク | 分離設計の後付けが最大の地雷 | v0.1 で `enterprise_id` 付与済み = 先回りできている |

**暫定結論**: 国内外の事例は「**最初から全社物理分離は過剰設計で、後で統合コストを払う**」という方向でほぼ一致する。shokujii は v0.1 の論理分離設計を維持しつつ、`再検討.md` の **パターン B（プロダクト分離）+ パターン D（要件企業のみ Silo）** が事例とも整合する。
