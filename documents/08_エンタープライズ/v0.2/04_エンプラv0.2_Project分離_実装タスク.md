### 2.1 補足（現状の構成メモ）

- **Functions**: 単一コードベース `functions/default`（v2 / `asia-northeast1`）に **66 本**。`common` は `libs/common` symlink + `file:` 依存 + tsconfig paths の併用で取り込み。
- **enterprise 関連**: Callable 15 本（`enterprise/*`）+ index 未エクスポートの `communityManager` 2 本（`getInvitationUrlForEnterpriseCommunityManager` / `acceptInvitationForEnterpriseCommunityManager`）。
- **月次集計**: 専用バッチは無く、`stores/enterprise.ts` の `adjustEnterpriseMemberMonthlyUsage` によるリアルタイム更新モデル。
- **enterprise テナント切替**: Firebase App 切替ではなく、`getEnterpriseByDomain` Callable → Pinia（`useEnterpriseStore`）→ クエリ/ルートガードでの論理分離。物理分離後も流れ自体は維持可能。
- **CI**: 6 workflow とも GitHub Environment の `vars.PROJECT_ID` / `secrets.GCLOUD_SERVICE_KEY` を共有し**同一 Project** へデプロイ。`firebase.json` は rules / functions codebase / hosting を 1 セットで保持。
- **terraform**: 1 Project = 1 state。Enterprise 用 Hosting site / reCAPTCHA / Secret 12 件もこの中に同居。

## 4. クリティカルパスと PoC 優先度

再設計書 §8「段階計画（案）」を、実態を踏まえ精緻化したもの。

1. **最優先 PoC（並行可）**
   - `T-20` functions_base 取り込み方式（PB-2）
   - `T-10` / `T-31` `base/firebase.ts` の多 App 化（F-1）← **partner Bridge とメニューコピーの両方の前提**
2. **基盤**: T-01〜07（Project / terraform / CI）
3. **データ層**: T-13〜16（Rules 単純化・`enterprise_id` required）
4. **Functions 分割**: T-20 → T-21 → T-22 / T-23（ハイブリッド 6 関数の振り分け T-22 が山場）
5. **partner Bridge**: T-30 → T-31 → T-32 / T-33（F-2・F-3 が機能要件の最難所）
6. **メニューコピー**: T-40（F-4 クロス Project Admin SDK）
7. **ゲスト**: T-50 → T-51

特に **T-10 / T-31（多 App 化）**、**T-22（ハイブリッド関数振り分け）**、**T-33（partner の enterprise read Rules）** は、再設計書に明記されていない / 軽く触れられているだけで、実態上は最大級のリスク。
