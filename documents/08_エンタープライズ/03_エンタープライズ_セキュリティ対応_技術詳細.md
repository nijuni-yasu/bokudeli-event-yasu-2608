# セキュリティ対応 技術詳細

MVPでは最小限のセキュリティ対策（企業メールドメイン制限 + Firestore Security Rules）で運用する。
本ドキュメントでは、Phase 2 以降で必要に応じて導入するセキュリティ施策の実装可能性と具体的な方法を記載する。

**すべての施策は Firebase / GCP の機能で実現可能である。**

※ ビジネス優先度順（企業から要求される頻度・導入阻害度が高い順）に記載。

| 優先度 | 項目 | 難易度 | 推奨フェーズ | 優先度の根拠 |
|:--|:--|:--|:--|:--|
| 1 | SSO（SAML/OIDC） | 低〜中 | Phase 2 | 大企業が最も求める機能。導入の必須条件になりうる |
| 2 | IPアドレス制限（API層） | 中 | Phase 2 | セキュリティチェックシートで頻出。API層のみで実質的に十分 |
| 3 | データ暗号化（CMEK） | 低（コード変更不要） | Phase 2 | コード変更不要で導入容易だが要求頻度は SSO/IP より低い |
| 4 | フィールドレベル暗号化 | 中（クエリ制約あり） | 必要時のみ | 適用範囲が限定的。医療・金融等の特殊要件 |
| 5 | IPアドレス制限（完全） | 高（構成複雑・コスト大） | 大企業要件時のみ | API層制限で十分なケースが大半 |
| 6 | 物理分離（企業ごとProject） | 高（運用コスト大） | 大企業要件時のみ | 最も工数が大きい。コンプライアンス必須時のみ |


# 1. SSO（SAML/OIDC）

## 1.1 概要

Firebase Auth を Identity Platform にアップグレードし、企業ごとにテナントを作成して異なる認証プロバイダー（Azure AD、Okta 等）を設定する。**最も実装が確実な施策。**

大企業が最も求める機能であり、「自社の Azure AD / Okta でログインしたい」は導入の必須条件になることが多い。Phase 2 で最優先に対応すべき。

## 1.2 実装手順

### サーバー側: テナント作成 + SAMLプロバイダー設定

```typescript
// 1. テナント作成（Admin SDK）
const tenant = await getAuth().tenantManager().createTenant({
  displayName: 'Company A',
  emailSignInConfig: { enabled: true, passwordRequired: false },
})

// 2. SAML プロバイダー追加（Admin SDK）
await getAuth().tenantManager().authForTenant(tenant.tenantId)
  .createProviderConfig({
    providerId: 'saml.company-a-azure-ad',
    displayName: 'Company A Azure AD',
    enabled: true,
    idpEntityId: 'https://sts.windows.net/{tenant-id}/',
    ssoURL: 'https://login.microsoftonline.com/{tenant-id}/saml2',
    x509Certificates: ['-----BEGIN CERTIFICATE-----\n...'],
    rpEntityId: 'https://company-a.shokujii.com',
    callbackURL: 'https://PROJECT_ID.firebaseapp.com/__/auth/handler',
  })
```

### フロントエンド: 企業設定に応じてログインフローを切り替え

```typescript
// enterprise パッケージ内のログイン処理
if (enterprise.sso_provider) {
  // SSO ログイン
  auth.tenantId = enterprise.tenant_id
  const provider = new SAMLAuthProvider(enterprise.sso_provider)
  await signInWithPopup(auth, provider)
} else {
  // OTP ログイン（MVP と同じ）
  await sendOtp(email)
}
```

### Firestore スキーマ追加（/enterprises/{enterpriseId}）

```typescript
{
  // Phase 2 で追加
  tenant_id?: string       // Identity Platform テナントID
  sso_provider?: string    // SAMLプロバイダーID（例: "saml.company-a-azure-ad"）
}
```

## 1.3 料金

| 認証方式 | 無料枠 | 超過後 |
|:--|:--|:--|
| メール+OTP（Tier 1） | 月49,999 MAUまで無料 | $0.0055/MAU〜 |
| SAML/OIDC（Tier 2） | 月49ユーザーまで無料 | $0.015/MAU |

SSO を使う企業は通常それなりの規模のため、料金は導入企業への月額費用に転嫁できる。

## 1.4 導入の流れ

1. GCPコンソールで Identity Platform にアップグレード（ワンクリック。既存ユーザーはそのまま引き継がれる）
2. SSO が必要な企業ごとにテナントを作成し、SAML/OIDC プロバイダーを設定
3. SSO が不要な企業はそのまま OTP ベースのログインを継続（テナント作成不要）
4. enterprise パッケージのログイン画面で、企業設定に応じてフローを分岐


# 2. IPアドレス制限

## 2.1 Firebase の制約

Firebase Hosting 単体にはIPアドレス制限機能がない。これが最大の制約。
Firestore Security Rules にもIPアドレス情報は渡らないため、Rules でのIP制限は不可。

## 2.2 方式A: Cloud Functions でIPチェック（推奨）

フロントエンド（HTML/JS）のアクセスは制限しないが、**データアクセス（API呼び出し）をIP制限**する方式。追加インフラコスト不要で、企業ごとの個別設定も容易。

### 実装イメージ

```typescript
// functions/default/src 内の共通ミドルウェア
export const enterpriseCallable = onCall(async (request) => {
  const uid = request.auth?.uid
  if (!uid) throw new HttpsError('unauthenticated', '認証が必要です')

  const enterpriseId = request.auth.token.enterprise_id
  const enterprise = await getEnterprise(enterpriseId)

  // IP制限が設定されている企業の場合のみチェック
  if (enterprise.allowed_ips && enterprise.allowed_ips.length > 0) {
    const clientIp = request.rawRequest.headers['x-forwarded-for']
    if (!enterprise.allowed_ips.includes(clientIp)) {
      throw new HttpsError('permission-denied', '許可されていないIPアドレスです')
    }
  }

  // 本来の処理...
})
```

### Firestore スキーマ追加（/enterprises/{enterpriseId}）

```typescript
{
  // Phase 2 で追加
  allowed_ips?: string[]  // 許可IPアドレスリスト（未設定 = 制限なし）
}
```

### メリット
- ロードバランサー不要。追加インフラコストなし
- 企業ごとに `/enterprises/{enterpriseId}` の `allowed_ips` を設定するだけ
- IP制限が不要な企業はフィールドを空にするだけでスキップ

### 制限
- フロントエンド（HTML/JS）自体は読み込める（ログイン画面は表示される）
- ログイン・データ取得はIP制限されるため、実質的に利用は不可能

## 2.3 方式B: Cloud Load Balancer + Cloud Armor（完全なIP制限）

フロントエンドへのアクセス自体をIPで制限する方式。Firebase Hosting の前段にロードバランサーを配置する。

### 構成

```
ユーザー → Cloud Load Balancer → Cloud Armor（IP制限） → Firebase Hosting
                                    ↓ 拒否
                              403 Forbidden
```

### 実装手順

```bash
# 1. Cloud Armor ポリシー作成
gcloud compute security-policies create shokujii-enterprise-policy

# 2. 特定IPレンジのみ許可
gcloud compute security-policies rules create 1000 \
  --security-policy=shokujii-enterprise-policy \
  --src-ip-ranges="203.0.113.0/24" \
  --action=allow \
  --description="Company A office IP"

# 3. デフォルト: 拒否
gcloud compute security-policies rules update 2147483647 \
  --security-policy=shokujii-enterprise-policy \
  --action=deny-403
```

### 注意点
- Firebase Hosting のデフォルトドメイン（`*.web.app`）には Cloud Armor を適用できない。**カスタムドメイン必須**
- ロードバランサーの月額費用が発生（最低でも月$20程度〜）
- 企業ごとに異なるIP制限を設定するには、Cloud Armor のルールをドメインごとに管理する必要があり運用が複雑
- 方式Aで実質的に十分なケースが多いため、方式Bは金融・医療系等の厳格な要件がある場合のみ検討する


# 3. データ暗号化

## 3.1 デフォルト暗号化（MVP）

Firestore はすべてのデータを保存時に自動で暗号化（AES-256、Google管理の鍵）している。追加の設定は不要で、復号もシステムが自動で行う。MVPではこれで十分。

## 3.2 CMEK（顧客管理暗号鍵）

Google管理の鍵ではなく、自社で管理する暗号鍵で Firestore のデータを暗号化する方式。**コード変更不要**で導入できる。

### メリット
- 鍵の無効化・破棄でデータへのアクセスを即時遮断できる（企業の契約終了時に有用）
- 鍵のローテーション、監査ログを自社で管理可能
- Firestore の SLA・パフォーマンスに影響なし

### 実装手順

```bash
# 1. Cloud KMS で鍵を作成
gcloud kms keyrings create shokujii-keyring --location=asia-northeast1
gcloud kms keys create shokujii-key \
  --keyring=shokujii-keyring \
  --location=asia-northeast1 \
  --purpose=encryption

# 2. Firestoreデータベースに鍵を紐付け（DB作成時に指定）
gcloud firestore databases create \
  --location=asia-northeast1 \
  --kms-key-name=projects/PROJECT_ID/locations/asia-northeast1/keyRings/shokujii-keyring/cryptoKeys/shokujii-key
```

### コスト
Cloud KMS の料金（鍵の管理 + 暗号化/復号オペレーション）。Firestore は5分ごとに暗号化/復号を実行するため、一般的に低額。

### 注意点
- CMEK は **Firestore データベース作成時** に設定する必要がある。既存DBへの後付けは不可
- 将来的に CMEK を導入する場合は、新規DBを作成してデータを移行する必要がある

## 3.3 フィールドレベル暗号化

特定の機密フィールド（例: 従業員の個人情報）のみ、アプリ側で暗号化してから Firestore に書き込む方式。

### 実装イメージ

```typescript
// Google の暗号化ライブラリ Tink + Cloud KMS を使用
import { AeadKeyTemplates, KeysetHandle, Aead } from '@aspect/tink'

// 暗号化して書き込み
const aead = await keysetHandle.getPrimitive(Aead)
const encrypted = await aead.encrypt(
  Buffer.from(personalData),
  Buffer.from(enterpriseId)  // AAD（追加認証データ）にテナントIDを使用
)
await setDoc(doc(db, 'users_personal_information', userId), {
  encrypted_data: encrypted,
})

// 復号して読み取り
const decrypted = await aead.decrypt(encrypted, Buffer.from(enterpriseId))
```

### 注意点
- **暗号化したフィールドでは Firestore のクエリ（where, orderBy）が使えなくなる**
- 検索が必要なフィールドは暗号化できないため、適用対象は個人情報等の限定的なフィールドに限る
- 暗号化/復号の処理コストがフロントエンドまたは Functions に発生する


# 4. 物理分離（企業ごとProject）

## 4.1 概要

`01_エンタープライズ_仕様概要.md` および `02_エンタープライズ_全体構成・アーキテクチャ.md` で決定した通り、MVPでは物理分離は行わない。ここでは将来的に特定企業のみ物理分離が必要になった場合の移行手順を記載する。

## 4.2 移行手順（特定企業のみ分離する場合）

```
1. 新規 Firebase Project を作成
2. enterprise_id でフィルタして該当企業のデータをエクスポート
   → gcloud firestore export でコレクション単位でエクスポート
   → enterprise_id でフィルタして新Projectにインポート
3. Firebase Auth ユーザーを新Projectに移行
   → Admin SDK でユーザーデータをエクスポート → 新Projectにインポート
   → custom claims を再設定
4. Functions / Hosting / Security Rules を新Projectにデプロイ
5. DNS を新Projectの Hosting に切り替え
6. 旧Projectから該当企業のデータを削除
```

## 4.3 最大の課題: 飲食店データの扱い

分離先のProjectでも飲食店データ（partners / shops / menus）が必要になる。対応方式は以下のいずれか。

| 方式 | 内容 | 工数 |
|:--|:--|:--|
| **データコピー** | 飲食店データを分離先Projectにコピーし、定期同期する | 高（同期基盤の開発が必要） |
| **API経由で取得** | 分離先ProjectのアプリがメインProjectの Functions 経由で飲食店データを取得する | 中（APIの開発が必要） |

いずれも大きな開発工数が発生するため、物理分離は「コンプライアンス上必須」となった企業に限定し、追加費用を請求する前提で対応する。

## 4.4 enterprise_id 設計による移行容易性

`02_エンタープライズ_全体構成・アーキテクチャ.md` で定義した通り、すべてのドキュメントに `enterprise_id` を持たせているため、特定企業のデータのみを抽出・移行することは技術的に可能。全企業を一斉に分離する必要はなく、要件が出た企業のみ個別対応できる。
