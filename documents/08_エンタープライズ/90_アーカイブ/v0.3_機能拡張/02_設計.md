## 1. コミュニティ参加・イベント公開モデル（3軸モデル）★中核

`01` の §3「部署限定イベント」「コミュニティ参加の概念」「コミュニティ名称/概念」を統合し、**3つの独立した軸**として設計する。Facebook グループの仕様（グループ参加の承認制 / イベント公開区分）を参考にする。

### 1-1. 前提：コミュニティ概念は維持する

- エンプラ版でも PF版の `communities` 構造を維持する（廃止しない。PF版依存が大きくコスト過大なため）。
- 全社管理者が **`community_type`**（部署 / 課 / サークル / 部活 など）を作成・設定できる。
- ただし **`community_type` は表示ラベルのみ**とし、参加方式（軸1）や自動加入（軸3）のデフォルト値は持たせない。各コミュニティで独立に設定する。

### 1-2. 軸1：コミュニティへの参加方式 — `community.join_type`

| 値 | 意味 | 参加ボタンの挙動 | 想定 |
|:--|:--|:--|:--|
| `approval` | 承認制 | 「参加申請」→ `pending` → コミュニティ管理者 / 全社管理者が承認 | 部署・課 |
| `open` | 自由参加 | 「参加」→ 即 `CommunityMember` 作成 | サークル・部活 |

- 参加ボタンの不整合（`01` L57-61）は、`open` のみ即参加ボタン、`approval` は申請ボタンに分岐して解消。
- **退出 / 除名**：`CommunityMember` の delete をコミュニティ管理者・全社管理者に許可（Security Rules 追加）。

### 1-3. 軸2：イベント公開区分 — `event.publish_scope`（PF / エンプラ共通）

`01` L71 の4区分を、**PF版・エンプラ版で共通の `publish_scope`（列挙）** に一本化する。`is_public`（boolean）は**パスワード保護を含む4状態を表現できない**ため、`publish_scope` を正として段階的に廃止する。

**enum 定義・一覧/注文マトリクス・expand/migrate/contract の詳細は [ADR-003_publish_scope移行.md](../../20_設計判断_ADR/ADR-003_publish_scope移行.md) を正本とする。** 以下は 3 軸モデル文脈での要約のみ。

#### 共通スキーマ案（要約）

```ts
publish_scope: 'public' | 'community' | 'url'
allow_guest?: boolean     // 外部ゲスト可否（エンプラ）。既存どおり直交
access_password?: string  // Phase 2（ADR-003 §4 参照）
```

| `publish_scope` | 一覧表示 | 注文 | 旧 `is_public` |
|:--|:--|:--|:--|
| `public` | 表示 | 全員可 | `true` |
| `community` | 表示（非メンバー閲覧のみ） | `CommunityMember` のみ | （新規） |
| `url` | 非表示 | URL を知る人のみ | `false` |

- **`community` の非メンバー向け表示**：一覧 + 詳細閲覧可。**注文ボタンのみ無効**（`01` L52-55）。
- 「存在自体を隠す」= `url`。「部署主催の全社オープン食事会」= 同コミュニティ配下で `publish_scope: 'public'`。
- **`community` は PF版でも有効**。PF版への展開タイミングは実装フェーズで判断。

#### `is_public` の段階的廃止

[ADR-003 §3](../../20_設計判断_ADR/ADR-003_publish_scope移行.md) に expand → migrate → contract の手順・消費者一覧・インデックス注意を記載。本書では重複記載しない。

#### 1-3a. パスワード保護（`access_password`）— Phase 2

**MVP スコープ外。** アクセス付与基盤（Callable + access_grants）が必要なため Phase 2 に委譲。理由と想定実装は [ADR-003 §4](../../20_設計判断_ADR/ADR-003_publish_scope移行.md) を参照。

### 1-4. 軸3：イベント参加とメンバーシップの関係 — `community.auto_join_on_event_order`

PF版では「注文＝`EventMember`（イベント単位）作成」。`CommunityMember`（コミュニティ単位）は別レイヤーなので、**「イベント参加はするがコミュニティには自動加入しない」**を矛盾なく実現できる。

| 値 | 注文時の挙動 |
|:--|:--|
| `false` | `EventMember` のみ作成。`CommunityMember` には追加しない（部署に勝手に入らない） |
| `true` | `EventMember` + `CommunityMember` 作成（コミュニティ通知を受け取れる） |

- コミュニティごとに独立設定（`community_type` のデフォルトには紐づけない）。
- `01` L65/L67 の「メンバーにならず参加」= `false`。

### 1-5. 整合性チェック（主要ユースケース）

| ユースケース | join_type | publish_scope | auto_join | allow_guest / password |
|:--|:--|:--|:--|:--|
| 部署定例ランチ（部署限定） | `approval` | `community` | `false` | - |
| 部署主催の全社オープン食事会 | `approval` | `public` | `false` | - |
| サークル活動 | `open` | `community` | `true` | - |
| 人事の毎日ランチ（全社・誰でも） | - | `public` | - | - |
| 就活生・外部との会食 | - | `community` 等 | - | `allow_guest` |
| 秘匿イベント（URL + 合言葉） | - | `url` | - | `access_password` |

### 1-6. members のデータ / スキーマ（`01` §3 membersのデータ）

- `department` の立ち位置・`displayName` の設計は、本章の3軸確定後に `common/src/schemas`（`shokujii-common-schemas` 範囲）で別途定義する。
- `community_type` マスターをどこに持つか（`enterprises/{}` 配下 or コミュニティのフィールド）も併せて設計する。

## 2. 管理者・全社管理画面

### 2-1. 管理者名称（決定）

- 「**コミュニティ管理者**」「**全社管理者**」で確定（`01` §3 管理者の名称、v0.1 `01` ロール定義と一致）。
- 内部表現：`community manager` / `enterprise_admin`。

### 2-2. 全社管理者の全イベント編集権限【MVP前倒し】

- 全社管理者は同一 `enterprise_id` 内の**全イベントを編集可**とする。
- Security Rules：`(コミュニティ manager) OR (role == 'enterprise_admin' && enterprise_id 一致)`。

### 2-3. コミュニティ一括作成時のデフォルト画像

- 画像未指定時は、**複数プリセット画像からランダム付与**する（現状の「1色画像」だけでなく多様化）。
- §3 のカバー画像自動設定と実装を統合する。

### 2-4. 既存 doc へ委譲

- メンバー別利用状況 + CSV（`01` §3）→ v0.1 `04_全社管理者画面`。
- 全社請求・請求書ダウンロード（`01` §3）→ v0.1 `04_請求`。

### 2-5. 機能 ON/OFF 設定（保留：Phase 2 寄り）

- `enterprises/{}` に `feature_flags`（`slack` / `flyer` / `group_chat` 等の boolean）を持たせ、各機能で参照する想定。
- v0.3 MVP 前倒し対象には含めない（必要に応じて前倒し判断）。

### 2-6. トップバナー画像設定（保留：Phase 2 寄り）

- `enterprises/{}` に `top_banner`（`image_url` + `link_url`）を持たせ、エンプラ版トップに表示する想定。
- v0.3 MVP 前倒し対象には含めない。

## 3. PF版露出・ログイン / マイページ・セッション

### 3-1. PF版へのエンプラ露出（`01` §1）

- PF版の**全一覧・検索・`collectionGroup` クエリに `enterprise_id == null` を必須条件**にする。
- 設計上はすでに分離前提（v0.1 `04_イベント管理` §4.1）。実装の行き渡り確認タスク。

### 3-2. 未ログイン時の表示（`01` §1）

- エンプラ版のイベント / コミュニティページは、**未ログイン時はコンテンツを描画せずログイン画面へリダイレクト**。
- ただし **`allow_guest == true` のイベントは例外**（既存 Rules で未認証 read 可）。ゲスト参加導線を壊さない。
- ログイン画面 UI のリッチ化はデザインタスク（実装フェーズ）。

### 3-3. セッションタイムアウト【MVP前倒し・方針変更】

- **無操作 1 週間でログアウト**に変更する。
- v0.1 `01` の「60分無操作で自動ログアウト」決定を**上書き**する点に注意（v0.1 `01` 側の追記が必要）。
- Firebase の ID トークンは1時間で自動更新されるため、調整対象は「無操作タイムアウト」値のみ。

### 3-4. マイページ：福利厚生割の利用状況【MVP前倒し】

- マイページに「**今月の利用額 / 今月の残り予算 / 過去月の利用履歴**」を表示する。
- データ源：`enterprises/{}/members/{userId}` の `monthly_usage` / `monthly_order_count`、企業設定の `monthly_limit_per_user`（集計済みフィールドを流用、追加集計不要）。
- v0.1 `01` では Phase 2 だったものを MVP 前倒しする。

### 3-5. プロジェクト分離へ委譲

- PF版マイページでのエンプラ情報表示・ともだち数非表示、エンプラユーザーの PF版ログイン可否、Authentication 分離 → v0.2 `03`〜`05`。
