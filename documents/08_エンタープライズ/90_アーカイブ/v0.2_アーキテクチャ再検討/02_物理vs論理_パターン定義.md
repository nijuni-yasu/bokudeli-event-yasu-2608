## 1. この文書の目的

v0.1 では「単一 Firebase Project + `enterprise_id` 論理分離」を採用した。v0.2 再設計では「PF 版とエンプラ版を Firebase Project で分ける」「企業ごとに Project を作る（100 社 = 100 Project）」が検討されている。

本検討のゴールは次の 3 点。

1. **物理分離派が挙げるリスクが、実際に何を防げるか**を明確にする
2. **論理分離で足りない点・足りる点**を実装観点で整理する
3. v0.2 で採るべき **段階的な分離レベル**を合意できる形で提案する

「論理分離で十分」と一方的に言うのではなく、**分離の粒度を段階で選べる設計**を前提に議論する。

## 2. 用語定義（議論のすり合わせ）

| 用語 | 定義 | shokujii での例 |
|:--|:--|:--|
| **テナント** | 契約・データ境界の単位。本サービスでは原則 **1 企業 = 1 テナント** | `enterprise_id` で識別する企業 |
| **論理分離** | 共有インフラ上で tenant ID + 認可でデータを分離 | 同一 Firestore + Rules + claims |
| **物理分離** | テナントごとにインフラ境界（Project / DB 等）を分ける | 企業ごとに Firebase Project |
| **プロダクト分離** | PF 版とエンプラ版で Firebase Project を分ける | PF Project と Enterprise Project（1 つまたは N 個） |

**注意**: 「テナント分離しない」ではない。v0.1 も v0.2 案も **テナント分離はする**。争点は **分離を論理でやるか物理でやるか、どの境界まで物理にするか** である。

## 3. v0.1 実装・MVP 検証で露呈した「本当の課題」

`01_経緯_再設計_partner_CI_functions.md` から、物理分離を検討する動機を整理する。

### 3.1 認証・プロダクト境界の混在（最重要）

| 課題 | 内容 | 論理分離だけで防げるか | 物理分離で改善するか |
|:--|:--|:--|:--|
| PF/エンプラ Auth 混在 | 同一 Firebase Auth に PF ユーザーとエンプラユーザーが共存 | Rules / アプリで制御可能だが漏れやすい | **PF Project 分離で根本解消** |
| エンプラユーザーが PF 版にログイン | `user_type` 未検証・UI 露出で PF 画面に入れる | アプリ + Rules + Hosting 分離で対応可 | **Project 分離が最も確実** |
| PF 版にエンプライベントが表示 | `enterprise_id` フィルタ漏れ（collectionGroup 等） | クエリ修正 + Rules で対応可 | Project 分離なら PF 側にエンプラデータ自体が存在しない |
| エンプラ情報が PF マイページに表示 | 同一 `users` コレクション共有 | Callable 認可 + 表示フィルタで対応可 | Project 分離でデータ自体が分かれる |

**考察**: 物理分離派が感じる「不安の多くは、PF 版とエンプラ版の境界問題」に起因している。これは **企業ごと 100 Project** まで行かなくても、**PF Project ≠ Enterprise Project** の **プロダクト分離**で大きく改善できる。

### 3.2 企業間（テナント間）の混在

| 課題 | 内容 | 論理分離 | 物理分離（企業ごと Project） |
|:--|:--|:--|:--|
| 他社データ閲覧 | `where('enterprise_id')` 漏れ、Rules バグ | Rules + テストで防止（実装品質依存） | Firestore 自体が別なのでクエリ漏れでも他社 DB に到達しない |
| collectionGroup 横断 | 全テナントを横断するクエリが混在しうる | Rules + 必須フィルタ + テスト | 企業 Project 内のみ。ただし partner は N Project を読む必要 |
| Rules 変更の blast radius | 1 箇所のバグが全企業に影響 | 全テナント影響 | 1 企業 Project のみ影響 |
| 運用者の GCP コンソールアクセス | 1 Project 内の全企業データが見える | IAM 最小権限 + 運用規程 | 企業 Project 単位で IAM を分けられる |

**考察**: 企業間分離については、物理分離のメリットは**明確**である。一方でコスト・partner 横断・飲食店マスター同期の代償も大きい（§6 参照）。

### 3.3 セキュリティチェックシート・導入審査

`03_セキュリティチェックシート` 4-4 / 4-5 より:

- 現状回答: 論理分離 + 「必要なら特定企業のみ別 Project へ移行可能（追加費用）」
- 導入企業の質問は「論理でどう担保するか」と「物理分離オプションはあるか」の **両方** が来る

**考察**: 全社を最初から物理分離する必要はなくとも、**物理分離オプションのストーリー**は営業・導入審査上重要。

### 3.4 具体的インシデント・シナリオ（脅威モデル）

物理分離派の不安を抽象論で流さず、論理分離で「実際に起きうる事故」を具体化する。各シナリオに対し、どの防御層（§7）が機能するか、物理分離でどう変わるかを併記する。

| ID | シナリオ | 起点 | 影響範囲（論理のみ） | 第一防御 | 最終防御 | 物理分離での差 |
|:--|:--|:--|:--|:--|:--|:--|
| S-1 | `firestore.rules` のデプロイに typo（`\|\|` と `&&` の取り違え等） | リリース作業 | 全テナント一時露出 | Rules ユニットテスト + CI（§7.2） | PITR / ロールバック | C: 1 社のみ。B: 全エンプラ。B′: 1 DB のみ |
| S-2 | collectionGroup クエリで `enterprise_id` フィルタ漏れ | アプリ実装 | 他社データが UI に出る | lint / レビュー / テスト | Rules（L3） | C/B′: そもそも他社 DB に到達不能 |
| S-3 | Callable Function で `enterprise_id` を request から検証せず使用 | Functions 実装 | 他社データ操作 | コードレビュー | 監査ログで事後検知 | C: Admin SDK が別 Project |
| S-4 | 運用者が本番コンソールで他社データを閲覧 | insider | 全社 | IAM 最小権限 | 監査・規程 | C: Project 単位 IAM。B′: **DB 単位 IAM 条件**で限定可 |
| S-5 | バックアップ / エクスポートに他社データが混在 | 運用 | エクスポート流出 | 企業別エクスポート（§7.2） | アクセス制御 | C/B′: DB / Project 単位で完全分離 |

**結論**: S-1〜S-3 は **実装・CI 品質**の問題であり、物理分離は「保険」にはなるが本質解決ではない。一方 S-4 / S-5 は **運用・IAM 設計**の問題で、物理分離が明確に効く。→ B を選ぶなら S-1〜S-3 は CI / テストで、S-4 / S-5 は IAM + 運用規程で塞ぐことが**前提条件**（§7.1, §7.2）。なお S-2 / S-4 / S-5 は **B′（企業ごと Firestore Database, §6.5）** でも Project 分割なしに物理的に塞げる。

## 4. 業界の実態（参考）

主要エンタープライズ SaaS の多くは **共有インフラ + 論理分離** を基本とする。

| サービス | 基本モデル | 大企業向けオプション |
|:--|:--|:--|
| Slack | 共有クラウド、workspace / org でシャード | データレジデンシー、EKM。自前ホスト・企業専用 Project は不可 |
| Notion | 共有 PostgreSQL、`workspace_id` でシャード | リージョン選択。企業ごと DB インスタンスは標準提供なし |
| Salesforce | 共有 DB、OrgID + パーティション | 専用インスタンスは契約・規制対応の例外 |
| Google Workspace | 共有インフラ、論理分離 | データリージョン選択。物理 sole-tenant は限定的 |
| Microsoft 365 | マルチテナント共有、Entra tenant container | 論理分離で物理分離と同等の保護と公式記載 |

AWS Well-Architected SaaS Lens では **Pool（共有）/ Silo（専用）/ Bridge（ハイブリッド）** の 3 パターンが定義され、成熟 SaaS は **標準は Pool、エンタープライズ契約は Silo オプション** に収束する、という整理が一般的。

**shokujii への示唆**:

- 「業界標準 = 全社論理分離」は **おおむね正しい**
- ただし「大企業・規制業種には物理分離オプションを用意する」のも業界標準
- v0.2 で「100 社すべて Silo」は業界のデフォルトではなく、**最もコストの高い例外戦略** に相当

### 4.1 エンタープライズ顧客が「実際に」要求する統制 → 対応マップ

導入審査・セキュリティチェックシートで来る要求は、多くが「Firebase Project を分けること」ではなく、**個別の統制**である。要求ごとに、Project 分割が必要か / 別手段で満たせるかを整理する。

| 顧客要求 | Project 分割が必要か | shokujii での充足手段 | 充足パターン |
|:--|:--|:--|:--|
| データの暗号化（保存時） | 不要 | Firebase デフォルト暗号化 | A/B/B′/C |
| 顧客管理鍵（CMEK） | 不要 | Firestore は CMEK 対応（Cloud KMS 鍵）。DB / Project 単位で鍵を割当 | B′/C（要 PoC） |
| データレジデンシー（国内保管） | 不要 | Firestore リージョン固定（`asia-northeast1` 等） | A/B/B′/C |
| ネットワーク境界（VPC-SC） | perimeter 設計が必要 | VPC Service Controls の perimeter | B/C |
| アクセスログ・監査ログ | 不要 | 監査ログ基盤（v0.1 §7）+ Cloud Logging | A/B/B′/C |
| SSO（SAML/OIDC） | 不要 | Identity Platform マルチテナント | B（Phase 2） |
| IP 制限 | 不要 | Functions / Hosting レベル制御 | B（Phase 2） |
| 第三者ペネトレーションテスト報告 | 不要 | 年次 pentest + 報告書 | A/B/B′/C |
| 契約終了時のデータ完全削除 | あれば容易だが必須ではない | 企業別削除バッチ（§9.6）。B′/C は DB / Project 削除で自明 | B/B′/C |
| 運用者が他社データを見られない | あれば容易 | B′ は DB 単位 IAM 条件、C は Project 単位 IAM | B′/C |
| 「専用環境であること」を契約に明記 | **必要** | Silo オプション（パターン D・§9.2） | D |

**示唆**: 顧客要求の **大半は Project 分割なしで満たせる**。Project 分割が本質的に必要なのは「契約上、専用環境を明記する」ケースのみ。CMEK・データレジデンシー・運用者分離といった「物理分離らしい要求」の多くは、**B′（企業ごと Firestore Database, §6.5）** や CMEK 構成で満たせる。→ パターン B / B′ + オプション Silo（パターン D）が合理的である根拠。

> **要確認**: CMEK / VPC-SC の対応可否・コストは Firestore のエディション・リージョン依存のため、営業資料に載せる前に GCP 側で要確認（PoC 推奨）。

## 5. 分離パターンの比較（shokujii 向け）

### 5.1 パターン一覧

| パターン | 構成 | 分離レベル | 主なメリット | 主なデメリット |
|:--|:--|:--|:--|:--|
| **A. v0.1 現状** | 1 Project × 1 DB（PF + 全エンプラ） | 企業間: 論理のみ | 工数最小、partner そのまま、デプロイ 1 回 | Auth/データ混在リスク最大。実装漏れが直撃 |
| **B. プロダクト分離** | PF Project + 1 Enterprise Project（企業間は `enterprise_id`） | PF/エンプラ: 物理。企業間: 論理 | Auth 混在解消。飲食店マスター共有維持。デプロイは 2 系統 | 企業間は Rules 品質依存。エンプラ Project 内 blast radius あり |
| **B″. プロダクト DB 分離（MVP 不採用・§6.6）** | 1 Project × 2 DB（`(default)` + `enterprise`） | PF/エンプラ: 物理（DB 単位）。企業間: 論理 | B のデータ層メリットを Project 二重化なしで取得。Auth/Secret/terraform は 1 系統 | partner の PF↔エンプラ越境 read が 2 DB クエリ化。cross-DB トランザクション不可 |
| **B′. 企業ごと DB 分離（MVP 不採用・§6.5）** | 1 Project × N DB（企業ごと named database） | 企業間: 物理（DB 単位）。PF/エンプラ: 同一 Project 内 | 他社到達不能・Rules blast radius を企業単位に・DB 単位 IAM/CMEK。Secret/terraform は 1 系統 | partner は DB を N 回読む。新規企業 = DB 作成 + Rules/index デプロイ |
| **C. エンプラ全社 Silo** | PF Project + 企業ごと Enterprise Project（N Project） | PF/エンプラ: 物理。企業間: 物理 | 企業間の最強分離。導入審査で有利。Rules blast radius 最小 | 運用・デプロイ・Secret・terraform が N 倍。partner 横断 read が複雑 |
| **D. Bridge（推奨候補）** | 標準は A ＋ 要件企業のみ専用 Project（Silo） | 標準: 論理 / 例外: 物理 | コストとセキュリティのバランス。営業ストーリーと一致 | 2 系統の実装・運用パスを維持する必要 |

### 5.2 アーキテクチャ図

#### パターン B: プロダクト分離

```
[PF Firebase Project]
  ├── user (Hosting)
  ├── partner (Hosting)
  ├── partners / shops / menus（マスター）
  └── functions_user

[Enterprise Firebase Project]  ← 全エンプラ企業
  ├── enterprise (Hosting) × 企業サブドメイン or ルーティング
  ├── enterprises / communities / events / ...（enterprise_id で論理分離）
  ├── Firebase Auth（エンプラ専用）
  └── functions_enterprise
```

#### パターン C: 企業ごと Silo（v0.2 再設計案）

```
[PF Firebase Project]
  └── partners / shops / menus + partner + user

[Enterprise Project: 企業A]
[Enterprise Project: 企業B]
  ...
[Enterprise Project: 企業N]
  └── 各社の Auth / Firestore / Functions / Hosting

[Partner または PF Functions]
  └── N Project 横断 read / 予約承認 / メニューコピー 等
```

### 5.3 物理分離が「確実に」解決するもの / 解決しないもの

| 懸念 | 企業ごと Project で解決 | 解決しない / 別途必要 |
|:--|:--|:--|
| PF とエンプラの Auth 混在 | △（PF Project 分離も必要） | — |
| 他社 Firestore データへの到達 | ✅ | — |
| Rules バグの影響範囲 | ✅（1 企業に限定） | — |
| partner の全テナント横断 read | — | ❌ N Project 読みに **より複雑化** |
| 飲食店マスター（menus）共有 | — | ❌ **同期 API or コピー基盤が必須** |
| 予約承認・EventMenus コピー | — | ❌ **クロス Project Functions** が必須 |
| デプロイ・Secret・terraform | — | ❌ **N 倍運用**（`01_経緯_再設計_partner_CI_functions` §CI 記載の通り） |
| ゲスト（PF ユーザー）参加 | — | ❌ 別設計（エンプラ専用ゲストアカウント化） |
| 運用者の insider リスク | △（IAM を企業単位にできる） | 当社運用者の権限設計は別問題 |

**物理分離派への整理**: 懸念はもっともだが、**企業ごと Project は銀の弾丸ではない**。特に shokujii は **partner が全テナント横断**、**飲食店マスターは PF 側** という構造上、完全 Silo は **新たな分散システム** を生む。

## 6. v0.2 再設計案（企業ごと Project）の影響整理

`01_経緯_再設計_partner_CI_functions.md` に記載の論点を、工数・リスク観点で再掲する。

### 6.1 partner への影響（最大の技術論点）

| 処理 | v0.1（単一 Project） | v0.2 Silo（N Project） |
|:--|:--|:--|
| 予約申請の承認/却下 | 単一 Firestore | N Project を横断 |
| memberOrders 参照 | collectionGroup 1 回 | N Project クエリ or 集約 API |
| PartnerMenus → EventMenus コピー | 同一 DB 内コピー | クロス Project コピー |
| 新規企業追加 | `enterprises` に 1 doc | terraform + Project 作成 + デプロイ + Secret 設定 |

partner は **飲食店向け 1 アプリ** のまま、バックエンドだけが **マルチ Project クライアント** になる。これは v0.1 より **複雑度が上がる**。

### 6.2 CI / 運用（`01_経緯_再設計_partner_CI_functions` §CI）

| 項目 | 100 社 Silo 時の影響 |
|:--|:--|
| `deploy_enterprise.yml` | 企業数分（または Project 数分）並列デプロイ |
| `deploy_functions.yml` | 同上。バグ修正の反映が N 回 |
| Secret Manager | 新規 secret 追加時に N Project へ同期スクリプト必須 |
| terraform | 新規企業 = Project 新規作成。管理画面からのボタン化は別途 |
| 監視・アラート | Project ごとに設定 or 集約基盤 |

### 6.3 ゲストユーザー（`01_経緯_再設計_partner_CI_functions` §ゲスト）

Silo + 「PF ユーザーはエンプラにログイン不可」とすると:

- ゲストは **エンプラ Project 内で別アカウント作成**（メール + パスコード）
- 企業をまたぐゲストは **アカウント作り直し**
- PF 版ゲスト参加（v0.1 で想定していた PF ユーザー参加）との整合を別途決める必要あり

### 6.4 パターン C（全社 Silo）の定量コスト

「N 倍」を体感ではなく数値・制約で示す。

| 項目 | 単価 / 制約 | 100 社時の影響 |
|:--|:--|:--|
| GCP プロジェクト数 | 組織あたり既定上限あり（要 quota 増申請） | 100+ Project で quota 申請が前提 |
| 新規企業オンボーディング | terraform + Project 作成 + API 有効化 + 初期デプロイ + Secret 設定 | 1 社ごとに発生。自動化しないと数十分〜の手作業 |
| Functions デプロイ | 1 Project あたり数分 | バグ修正 1 件 = 100 Project へ反映。部分失敗の管理が必要 |
| Secret 追加 / ローテーション | 1 Project ごとに設定 | スクリプト必須。失敗時の「ある社だけ古い」リスク |
| 監視・課金 | Project ごとに設定 / 請求 | 集約ダッシュボード・請求集約が別途必要 |
| Rules / インデックス | Project ごとにデプロイ | インデックス追加も N Project へ |

→ コストは企業数 N に**線形**に増える。MVP の段階で 100 Project 前提の自動化基盤（terraform + 並列デプロイ + Secret 同期 + 集約監視）を作り切る必要があり、リリース速度と直接トレードオフになる。

### 6.5 中間案 B′：単一 Enterprise Project + 企業ごと Firestore Database

Firestore の**マルチデータベース**（1 Project に最大 100 個の named database を持てる）を使い、企業ごとに DB を分ける案。B と C の中間で、**物理分離派の中核懸念（他社到達・Rules blast radius・運用者の閲覧）に Project 分割なしで応えられる**のが特徴。

| 観点 | B（単一 DB・論理） | **B′（企業ごと DB）** | C（企業ごと Project） |
|:--|:--|:--|:--|
| Rules の blast radius | 全エンプラ | **DB 単位（1 社）** | 1 社 |
| 他社データ到達 | 論理のみ | **DB が物理的に別** | 完全分離 |
| 運用者の閲覧制御 | Project IAM のみ | **DB 単位の IAM 条件**で限定可 | Project 単位 IAM |
| CMEK | DB 単位で可 | **DB 単位で別鍵**を割当可 | Project / DB 単位 |
| デプロイ | 1 Project | 1 Project（Rules / index は DB ごと） | N Project |
| Secret / terraform | 1 系統 | 1 系統 | N 倍 |
| 飲食店マスター共有 | そのまま | そのまま（同一 Project 内・別 DB から Admin SDK で参照） | 同期必要 |
| partner 横断 read | collectionGroup 1 回 | **DB を N 回**（collectionGroup は DB 内のみ） | N Project クエリ |
| 新規企業追加 | doc 1 件 | **DB 1 個作成 + Rules / index デプロイ** | Project 作成 + 全デプロイ |

**技術根拠（確認済み）**:
- 1 Project につき最大 100 DB。**Security Rules は DB ごとに個別管理・デプロイ**（`firebase.json` の `firestore` 配列で DB ごとに `rules` / `indexes` を割当）
- **IAM Conditions で DB 単位のアクセス権限**を設定できる（運用者の他社 DB 閲覧を制限可能）
- CMEK・PITR とも DB 単位で構成可能

**評価**: B′ は「他社到達」「Rules blast radius」「運用者の閲覧」という物理分離派の3大懸念を、**Project を増やさずに**潰せる。MVP の運用負荷（Secret / terraform / デプロイ）は B と同じ 1 系統に保てる。一方、**partner は DB を N 回読む必要**があり collectionGroup 横断ができない点は C と同じ弱点で、企業数増加時の partner 集約は別途設計が要る（§6.1, T-4）。また DB 数上限（100、要申請で拡張）と、新規企業追加時に DB + Rules / index デプロイが必要になる点は B より重い。

> **位置づけ**: B′ は「B の強化版」。物理分離派の懸念に最大限応えつつ運用 1 系統を維持したい場合の有力候補。partner 横断の重さを許容できるか（T-4）が採否の分かれ目。

### 6.6 中間案 B″：単一 Project + PF/エンプラの Firestore Database 分離（**MVP では採用しない**）

B′（企業ごと DB）が「企業 ↔ 企業」を割るのに対し、B″ は **B と同じ「PF ↔ エンプラ」境界を、Project ではなく Firestore Database（named database）で割る**案。単一 Project のまま `(default)` DB（PF）と `enterprise` DB（全エンプラ）の 2 つに分ける。思想的には **「B のデータ層メリットを Project 二重化なしで取りに行く案」** であり、割る境界は B と同一・実現手段だけが DB という違い。

> **MVP での扱い（不採用）**: v0.2 / MVP では **採用しない**。現行決定は **パターン A（単一 Project・単一 DB）＋ IdP マルチテナンシー**（[ADR-001](../../20_設計判断_ADR/ADR-001_Project分離なし.md)）。B″ は ADR-001 §4 の将来トリガー（データレジデンシー・blast radius の構造的ゼロ化・Firestore ハード上限・エンプラ主力化など）が発火し、かつ **必要な隔離が「PF↔エンプラ」止まりで「企業↔企業」まで要らない**場合の、**B′ より軽い移行先候補**として記録する。`enterprise_id` 付与済みの安全網（ADR-001 §2.6）は B″ にもそのまま効くため、「今は A で出し、必要時に B″ へ移す」出口は確保されている。

| 観点 | A（単一 DB・論理） | **B″（PF/エンプラ DB 分離）** | B′（企業ごと DB） | B（Project 分離） |
|:--|:--|:--|:--|:--|
| DB 数 | 1 | **2（固定）** | N（企業数） | 2 Project |
| 割る境界 | なし | **PF ↔ エンプラ** | 企業 ↔ 企業 | PF ↔ エンプラ |
| Auth | 単一（IdP） | **単一（IdP のまま）** | 単一 | 二重管理 |
| Secret / terraform / IAM Project | 1 系統 | **1 系統** | 1 系統 | ×2 |
| 2nd Firebase App / 再認証 | 不要 | **不要（同一 Auth）** | 不要 | 必要 |
| blast radius PF↔エンプラ | 残る | **遮断** | 遮断 | 遮断 |
| blast radius エンプラ↔エンプラ | 残る | **残る（全エンプラ同一 DB）** | 遮断（DB 単位） | 残る |
| partner 越境 read | collectionGroup 1 回 | **PF↔エンプラで 2 DB クエリ + マージ** | DB を N 回 | 2 Project クエリ |
| メニューコピー（PartnerMenus→EventMenus） | 同一 DB 内 | **cross-DB write（原子性なし・Function 経由）** | cross-DB write | cross-project write |
| エンプラ内部 tx（monthly_usage 等） | 単一 DB | **エンプラ DB 内で完結（原子性維持）** | DB 内で完結 | Project 内で完結 |
| CMEK / リージョン / DB 単位 IAM | Project 単位 | **DB 単位で可** | DB 単位で可 | Project 単位 |
| 新規企業追加 | doc 1 件 | **doc 1 件（DB 固定）** | DB 作成 + Rules/index デプロイ | doc 1 件 |
| 契約「専用環境」明記 | 不可 | 不可（DB 文言で足りるか要法務） | 不可（同上） | 可 |

**技術根拠**:

- Firestore は 1 Project に複数の named database を持てる。**Security Rules / indexes は DB ごとに個別管理・デプロイ**（`firebase.json` の `firestore` を配列化し DB ごとに `rules` / `indexes` を割当）。
- クライアント / Admin SDK とも `getFirestore(app, 'enterprise')` で **同一 App・同一 Auth トークンのまま** 2 つ目の DB ハンドルを取得できる（B の 2nd Firebase App + custom token 再認証が不要）。
- **トランザクション・バッチ・collectionGroup は単一 DB 内に閉じる**（DB をまたぐ原子性・横断 read は不可）。

**評価**: B″ は ADR-001 §10.1 で「IdP 込み A に対し B が固有に残すメリット = Project/DB 単位でしか割れないもの」とされた項目のうち、**DB 単位で割れる部分（blast radius・スケール予算・DB 単位 IAM・CMEK/リージョン）だけ**を、B の運用二重化（Auth/Secret/terraform/2nd App）を払わずに取得する。一方で **B の最大コストである partner 越境（ADR-001 §10.6 ①③④⑥）は「Project 境界ではなくデータ境界」由来のためほぼそのまま残る**。採否の分かれ目は (1) 欲しい隔離が PF↔エンプラ止まりか企業間まで要るか、(2) partner が PF とエンプラのイベントを横断する度合い、(3) DB 単位でしか取れないメリット（リージョン固定・CMEK・blast radius ゼロ）を前倒しする価値があるか。なお emulator のマルチ DB + `singleProjectMode` 両立、CMEK の DB 単位適用可否は要 PoC。

## 7. 論理分離の防御深度（物理分離派への回答）

「論理分離 = 安全でない」ではない。**防御の層**を明示すれば、導入審査でも説明可能。

| 層 | 仕組み | 備考 |
|:--|:--|:--|
| L1: 認証 | Firebase Auth + custom claims（`enterprise_id`, `enterprise_role`, `user_type`） | プロダクト分離で Auth 自体を分けられる |
| L2: アプリ | 全クエリに `enterprise_id` フィルタ。エンプラ画面は未ログイン非表示 | 実装漏れは pr-2071 等で既に指摘済み。lint / レビュー / テストで担保 |
| L3: Security Rules | `docEnterpriseId` / `isSameEnterprise` パターン（`02_全体構成` §5.2） | **最後の砦**。Rules ユニットテスト必須 |
| L4: Functions | 集計・横断処理は Callable 経由。Admin SDK で `enterprise_id` 検証 | クライアント直接集計を避ける |
| L5: 監査 | 監査ログ、Cloud Logging、管理者操作の記録 | insider / 異常検知は運用設計 |
| L6: 運用 | GCP IAM 最小権限、本番データ直接操作禁止 | 物理分離と**両方必要** |

Microsoft 365 / Google Workspace も同様に、**共有インフラ + 多層論理分離** で「物理分離と同等の保護」を公式に説明している。

**論理分離の弱点（正直に認める）**:

- Rules / クエリの **実装ミス** が全テナント影響になりうる → **テストと CI で締める**
- 運用者が 1 Project 内の全データを見える → **IAM + 規程 + 監査**
- 導入企業が「共有インフラ NG」と契約で言った場合 → **Silo オプション**（パターン D）

### 7.1 パターン B に残るリスクの正直な会計（物理分離派への誠実な回答）

パターン B（PF / Enterprise のプロダクト分離）でも、**全エンプラ企業が単一 Enterprise Project（単一 Firestore）を共有**する。物理分離派が最も懸念する点を、逃げずに会計する。

**B で消えない残存リスク**

| 残存リスク | 重大度 | なぜ残るか | B′ なら |
|:--|:--|:--|:--|
| Rules バグの blast radius が「全エンプラ」 | 高 | 1 Project の Firestore / Rules を全社共有 | DB 単位に縮小 |
| collectionGroup の横断クエリが全エンプラに届きうる | 中 | 同一 Firestore のため物理的に到達可能 | DB が別なので到達不能 |
| 運用者が Enterprise Project 内の全社データを見られる | 中 | Project 単位の IAM のみ | DB 単位 IAM 条件で限定 |
| 単一 Project / DB の障害が全エンプラ同時影響 | 中 | 可用性の単一障害点 | DB 分散で一部緩和 |

**B を許容できると判断する根拠**

1. S-1〜S-3（§3.4）は **CI・テストで検知可能**。Rules ユニットテストを全 PR 必須にすれば、blast radius が広くても事故確率自体を下げられる。
2. 業界標準（§4）も Microsoft 365 / Google Workspace が「共有インフラ + 論理分離」で **物理分離と同等の保護**と公式説明しており、共有 Project は逸脱ではない。
3. 「全社 Silo でないと防げない事故」は S-4 / S-5 に限られ、これは **IAM + 運用規程**、あるいは **B′（§6.5）** で代替できる。

**パターン B 採用の「前提条件」（これを満たして初めて B は許容される）**

物理分離派の合意を得るための**拘束条件**として、以下を MVP の完了条件に含める。これらは「B の代わりにやる妥協」ではなく、**C / B′ を選んでも結局必要な統制**である（物理分離は実装ミスの保険にはなるが、CI / テスト / IAM を不要にはしない）。

- [ ] Rules ユニットテスト（`@firebase/rules-unit-testing`）を CI 必須化（「他社 claims で read 拒否」「PF データ未認証 read」を最低ケース）
- [ ] 全 collectionGroup クエリに `enterprise_id` フィルタを強制（lint ルール or レビュー観点）
- [ ] Callable は `request.auth.token.enterprise_id` を**サーバー側で必ず検証**（クライアント値を信用しない）
- [ ] Enterprise Project の本番データへの人手アクセスを原則禁止（IAM 最小権限 + 承認フロー + 監査）
- [ ] Firestore PITR 有効化 + 企業別エクスポート手順を整備（§7.2）

### 7.2 ブラスト半径を運用で縮小する統制（パターン B の補強）

「1 つの Rules バグで全社終わる」懸念に対し、blast radius を**運用と CI で**縮小する。

| 統制 | 内容 |
|:--|:--|
| **Rules CI** | PR で Rules ユニットテストを必須化。`firebase emulators` で「他社 read 拒否」を自動検証。`firestore.rules` 変更は必ずテスト更新とセット |
| **段階ロールアウト** | Rules / Functions のデプロイを検証用 `enterprise_id`（カナリア）→ 全社の順で適用 |
| **PITR** | Firestore Point-in-Time Recovery を有効化（事故時に過去断面へ巻き戻し / クローン復元） |
| **企業別バックアップ / エクスポート** | `enterprise_id` 単位でエクスポートし、他社混在を防ぐ（B′ なら DB 単位で自明） |
| **権限分離** | 本番 Enterprise Project への人手アクセスを IAM 最小権限 + 承認フロー化。B′ では DB 単位 IAM 条件で運用者の他社閲覧を制限 |

→ これらにより、B でも「事故確率の低減」と「事故時の復旧速度」を担保でき、blast radius の広さという弱点を実害ベースで小さくできる。

## 9. 推奨案（段階的分離）

物理分離を求めるエンジニアの懸念を **否定せず**、**どこまで物理にするかを段階で選ぶ** 提案。

### 9.1 v0.2 MVP: パターン B（プロダクト分離）を採用

**採用するもの**

```
PF Firebase Project     … user, partner, partners/shops/menus, functions_user
Enterprise Firebase Project … enterprise（全社）, functions_enterprise
                            … 企業間は enterprise_id + Rules で論理分離
```

**理由**

1. `01_経緯_再設計_partner_CI_functions.md`・`03_意思決定` の **PF 露出・Auth 混在** を根本から解消できる（物理分離派の最重要懸念に応える）
2. partner / 飲食店マスターの構造を **大きく壊さない**
3. デプロイは 2 系統（PF / Enterprise）に留まり、100 系統にならない
4. v0.1 の `enterprise_id` 設計・Rules パターンを **そのまま Enterprise Project 内で継続** できる

**v0.2 で捨てるもの（v0.1 からの変更）**

- PF とエンプラの **同一 Firebase Auth / 同一 Firestore**
- エンプラユーザーの PF 版ログイン（仕様として禁止）

### 9.2 v0.2 以降: パターン D（Bridge）を製品方針として明示

- **標準プラン**: 共有 Enterprise Project + 論理分離（パターン B のまま）
- **エンタープライズ専用プラン（追加費用）**: 該当企業のみ専用 Firebase Project（Silo）
  - `01_仕様概要` §物理分離が必要になった場合の対応方針 と整合
  - `03_セキュリティチェックシート` 4-5 の回答と整合

### 9.3 v0.2 では採用しない案: 全企業 Silo（パターン C）

**採用しない理由（暫定）**

1. partner 横断処理・飲食店同期の工数が MVP の数倍になる
2. 100 社時の CI / Secret / terraform が運用上限を超えやすい
3. 導入企業の大半は論理分離で足りる（業界標準と一致）
4. 全社 Silo は **営業要件が来てから** でも、1 社単位で移行可能（`enterprise_id` 設計の意図）

**再検討トリガー**（以下のいずれかが確定したらパターン C を再評価）:

- [ ] 最初の有償導入企業が契約上「専用環境必須」と明示
- [ ] 金融・医療・政府系を主ターゲットに変更
- [ ] partner 横断 read を廃止し、企業ごとに飲食店データをコピーする設計に変える意思決定
- [ ] terraform による Project 自動作成 + 全デプロイ自動化の工数が確保された

### 9.4 Silo オプションを「本物」にするための具体設計

パターン D の Silo オプションが「口先の逃げ」でないことを示すため、**移行手順・リードタイム・価格・前提コーディング規約**を先に定義しておく。これがセキュリティチェックシート 4-5 への最強の回答になる。

**9.4.1 Silo-ready コーディング規約（標準プランから守る）**

将来 1 社を専用 Project / DB に切り出せるよう、共有 Enterprise Project の段階から以下を守る。

- 企業間を跨ぐ参照を書かない（あるエンプラのコードが他社 doc を読まない）
- すべての doc に `enterprise_id` を保持（v0.1 設計を継続）
- Storage パスに `enterprise_id` を含める（v0.1 §3.7 を継続）
- 集計は Callable 経由（クライアント直接 collectionGroup を避ける）

**9.4.2 Silo 移行手順（1 社を専用 Project へ）**

1. 新規 Project を terraform で作成（Auth / Firestore / Functions / Hosting）
2. 該当 `enterprise_id` の Firestore データをエクスポート → 新 Project へインポート（B′ なら DB クローン / エクスポートが流用可能）
3. Storage の `/enterprises/{eid}/` 配下を新 Project バケットへコピー
4. Auth ユーザーを移行（Admin SDK の import / export）
5. ドメイン / サブドメインを新 Project の Hosting へ切替
6. partner の参照先に新 Project を追加（Bridge 設計・T-4）
7. 旧 Project / DB から該当企業データを削除（§9.6）

**9.4.3 リードタイム・価格（暫定）**

| 項目 | 暫定値 |
|:--|:--|
| 移行リードタイム | 数営業日（データ量・partner 連携調整に依存） |
| 初期費用 | 専用環境構築費（別途見積） |
| 月額 | 標準プラン + 専用環境運用費 |

### 9.5 再評価トリガーの厳格化（測定可能・期限・オーナー付き）

§9.3 のトリガーを「誰が・いつ・何を見て」判断するか明確化する（「いつまでも判断しない」を防ぐ）。

| トリガー | 測定指標 | オーナー | レビュー周期 |
|:--|:--|:--|:--|
| 専用環境必須の有償契約 | 契約書に明記された時点 | 営業 + CTO | 商談ごと |
| 規制業種ターゲット化 | 事業方針の変更 | 経営 | 四半期 |
| partner 横断廃止の意思決定 | アーキ決定 | テックリード | 設計レビュー |
| Project 自動化工数の確保 | 工数アサイン確定 | EM | 四半期 |
| B′ への移行 | 物理データ分離の要求頻度が増加 | テックリード | 四半期 |

### 9.6 契約終了・データ削除・可搬性（reversibility）

物理分離派が重視する「抜けやすさ（出口）」を、論理分離（B）でも担保する設計。

| 要件 | パターン B での対応 | B′ / C での対応 |
|:--|:--|:--|
| 契約終了時の全データ削除 | `enterprise_id` 単位の削除バッチ（Firestore / Storage / Auth） | DB / Project 削除で自明 |
| 削除の証跡 | 削除ログ + 完了レポート | DB / Project 削除ログ |
| データ可搬性（エクスポート提供） | `enterprise_id` 単位エクスポート | DB / Project 単位エクスポート |

→ B でも「企業別削除バッチ + 証跡」を MVP で用意すれば、契約終了・データ持ち出し要件は満たせる。B′ / C ではこれが DB / Project 操作で自明になる。

## 10. 物理分離派の懸念 → パターン B/D での対応表

| 懸念（よくある主張） | パターン B/D での対応 |
|:--|:--|
| 「1 つの Rules バグで全社終わる」 | Enterprise Project 内の全社には当てはまる。**Rules ユニットテスト + CI 必須**。Silo オプションで 1 社限定の blast radius 縮小も可能 |
| 「Firebase Auth が混ざるのが危険」 | **PF / Enterprise で Auth を分離**（パターン B で解消） |
| 「エンプラデータが PF に出る」 | Enterprise Project にエンプラデータのみ。PF Project には載せない |
| 「運用者が全社データを見れる」 | IAM 最小権限 + 運用規程。Silo 企業は Project 単位で IAM 分離 |
| 「セキュリティチェックシートで論理だけは弱い」 | 多層防御（§7）+ Silo オプション（追加費用）を明記 |
| 「Slack も分離してるだろ」 | Slack は workspace 単位の**論理シャード**が基本。企業ごと Firebase Project 相当の完全 Silo ではない |
| 「最初から Silo で作れば後で楽」 | shokujii は partner 横断・飲食店共有があり、**最初から Silo は後で楽にならない**（分散同期が増える） |
| 「他社 DB に物理的に到達できるのが嫌」 | **B′（企業ごと Firestore DB, §6.5）**で Project を増やさず DB を物理分離。他社到達不能 + DB 単位 IAM 条件で運用者閲覧も制限 |
| 「CMEK / 顧客管理鍵が必須と言われる」 | Firestore は CMEK 対応。B′ なら **DB 単位で別鍵**を割当可（§4.1・要 PoC） |
| 「論理分離だと事故ったら全社巻き込む」 | Rules CI + 段階ロールアウト + PITR + 企業別バックアップ（§7.2）で確率と復旧速度を担保。さらに B′ で blast radius を DB 単位に縮小可能 |

## 12. 結論（暫定）

1. **「テナント分離をしない」わけではない**。v0.1 の論理分離方針は、**分離の境界が不十分だった**（PF とエンプラが同一 Project）という問題が v0.2 で顕在化した。
2. **物理分離派の懸念は妥当**。特に Auth 混在・PF 露出は、論理分離の実装品質ではなく **プロダクト境界の設計問題**。
3. **ただし「100 社 = 100 Firebase Project」はデフォルトにすべきではない**。partner 構造・飲食店マスター・運用コストとトレードオフが大きすぎる。
4. **v0.2 推奨**: **パターン B（PF / Enterprise のプロダクト分離）** を MVP とし、**パターン D（標準は共有 Enterprise Project、要件企業のみ Silo）** を製品・営業方針として明示する。
5. 全社 Silo（パターン C）は **§9.3 の再検討トリガー** が満たされた場合に限り再評価する。
6. **B は無条件採用ではなく、§7.1 の「前提条件」（Rules CI・collectionGroup フィルタ強制・Callable 検証・IAM・PITR）を満たすことを条件とする**。これは C / B′ を選んでも必要な統制であり、物理分離派の懸念に CI・運用で具体的に応える拘束条件である。
7. 物理データ分離の要求が強い場合は、**Project を増やさず DB を物理分離する B′（企業ごと Firestore Database, §6.5）** を有力な中間解として PoC する。他社到達・Rules blast radius・運用者閲覧の3大懸念を運用 1 系統のまま潰せる。採否は partner 横断（T-4）の許容度で判断する。
