# エンタープライズ実装計画

本ドキュメントは、`08_エンタープライズ` 配下の各仕様書（仕様概要・アーキテクチャ・課金設計・各詳細仕様・PF版移行/共通化・EventMemberOrder 論点・マイページ友人）の決定事項を踏まえ、フェーズ分けした実装計画を整理する。

## 全体方針（各仕様書からの確定事項）

- **パッケージ**: `user` をコピーして `enterprise` パッケージを新規作成する（パターンC: コピー＋継続マージ）。共通部分は可能な範囲で `base` / `common` に寄せる。
- **テナント分離**: 単一 Firebase Project + `enterprise_id` による論理分離。custom claims（`enterprise_id` / `enterprise_role` / `user_type`）で制御する。
- **データ基盤の前提**: EventMemberOrder 設計（`members/{uid}/member_orders` + `stripes`）が本番反映済みであること。
- **着手順の鉄則**（`06_EventMemberOrder対応論点` §7.1）: ① EventMemberOrder リファクタ → ② `pay_community_bill_off_amount` 対応 → ③ エンプラ版。①② が本番反映された後に ③ へ着手する。**①② は実装済み**のため、③ に着手可能な状態。
- **割引フィールド**: `/enterprises` はフラット `discount_*`、Event はネスト `enterprise_subsidy_settings`（`02` §3.5。`community_bill_settings` と同様の責務分離）

### Phase 2 検証シナリオ（sandbox）

`createEnterprise` で作成した初代 admin を使い、以下を通す:

1. `getEnterpriseByDomain` で企業情報（`allowed_email_domains` 含む）取得
2. ログイン → OTP 受信・入力 → custom claims 確認
3. 60分タイムアウト（または last_activity_at を手動変更して短縮検証）
4. アカウント停止（`disableEnterpriseMember` — Phase 3 実装後、または Admin SDK で先行検証）→ 即時セッション失効
5. 復活 → 再ログイン

一般 member のテストは CSV 作成（Phase 3）前のため、必要なら `createEnterprise` を別企業で実行するか Admin SDK で補う。
