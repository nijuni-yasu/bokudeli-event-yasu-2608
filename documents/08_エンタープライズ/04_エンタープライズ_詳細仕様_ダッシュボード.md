# ダッシュボード 詳細仕様

本ドキュメントは `01_仕様概要`、`02_全体構成・アーキテクチャ`、`04_割引・決済`、`04_全社管理者画面` の決定事項に基づき、全社管理者向けダッシュボードの機能仕様を詳細に定義する。

## 前提とする仕様書

本ドキュメントは EventMemberOrder 設計（`05_EventOrder→EventMemberOrder.md`）を前提とする。集計対象のコレクションは `members` / `member_orders` / `stripes` の 3 種となる。


# 1. 概要

## 1.1 位置づけ

- 全社管理者画面のトップページ（`/admin`）として実装
- 対象ロール: `enterprise_role == "admin"` のユーザーのみ
- 月別集計とメンバー別集計の2セクションで構成

## 1.2 決定事項サマリ

# 2. 集計ロジック

## 2.1 データソース

MVP では **ハイブリッド方式** を採用する。D-2（user_advance / community_bill を含める）を満たすため、利用回数・利用人数も `member_orders` から集計する。

| 集計項目 | データソース | 理由 |
|:--|:--|:--|
| 利用人数 | `member_orders` から集計（`user_id` のユニーク数） | 全支払い方式を含む |
| 利用回数（注文セッション数） | `stripes` ドキュメント数 + `confirmOrder` 経由の `member_orders` の確定セッション数 | 「カート確定操作の回数」を表現する。1 メニュー = 1 ドキュメントの新設計のため、`member_orders` 数では「品数」になり意味が変わる |
| 注文合計額（税込） | `member_orders` から集計（`Σ menu_price`） | 全支払い方式を含む |
| 自己負担額 | `member_orders` から集計（`Σ (menu_price - pay_enterprise_subsidy_amount)`） | 同上 |
| 企業負担額（補助） | EnterpriseMember の `monthly_usage` の合計（`enterprise_subsidy` のみ） | 決済完了時にリアルタイム更新済み |

> 「利用回数」を `member_orders` ドキュメント数で取ると 1 メニュー = 1 ドキュメントのため「品数」になってしまう。「ユーザーが体感する注文回数」と一致させるため、`stripes` ドキュメント数（Stripe 経由）+ `confirmOrder` 経由のセッション数（無料 / 全額補助）を使う。

### データソースの選択肢（参考）

| 方式 | データソース | メリット | デメリット |
|:--|:--|:--|:--|
| EnterpriseMember のみ | `monthly_usage`, `monthly_order_count` | 軽量・高速 | enterprise_subsidy のみ。user_advance / community_bill が含まれない |
| member_orders + stripes（採用） | 後述の Collection Group クエリ | 全項目を正確に集計可能 | 企業内全 `member_orders` のスキャンが必要 |
| monthly_usage コレクション | `/enterprises/{id}/monthly_usage/{yearMonth}` | 月別集計が高速 | **Phase 2**。MVP では未実装 |

### member_orders / stripes のクエリ方法

`member_orders` は `communities/{cid}/events/{eid}/members/{uid}/member_orders/{oid}` のサブコレクション、`stripes` は `communities/{cid}/events/{eid}/stripes/{sid}` のサブコレクションのため、**Firestore Collection Group クエリ** を使用する。

```typescript
// 注文金額・補助額・自己負担額の集計
collectionGroup('member_orders')
  .where('enterprise_id', '==', enterpriseId)
  .where('status', '==', 'ordered')

// 注文セッション数（Stripe 経由）の集計
collectionGroup('stripes')
  .where('enterprise_id', '==', enterpriseId)
```

- `enterprise_id` を含む複合インデックスを `firestore.indexes.json` に追加する（02 全体構成 6.5 参照）
- イベント開催月で絞る場合: `member_orders` 取得後、各 order の `event_id` から events を参照し、`event_start_datetime` の年月でフィルタする（`04_割引・決済` と同様に、`member_orders` に `event_month` は持たせない方針）

### `confirmOrder` 経由の注文セッション数

`stripes` ドキュメントは Stripe 経由の決済時にしか作成されない（`04_割引・決済` 6.3 参照）。無料 / 全額補助で `confirmOrder` 経由で確定したセッションは `stripes` を持たないため、別途カウントが必要。

| 方式 | 内容 |
|:--|:--|
| A. 監査ログから | `audit_logs` の `action == 'order_create' && target_type == 'order_session' && target_id == null` をカウント（`confirmOrder` 経由で `stripes` を持たないセッション。Stripe 経由は `target_id` に `stripes` ドキュメント ID が入る。`04_監査ログ` 4.2 の使用例と整合） |
| B. members.monthly_order_count から | 「カート確定回数」ではなく「ordered な member_orders 件数」になるため不適 |
| C. 専用フィールドを追加 | `EnterpriseMember.monthly_session_count` を新設（Phase 2） |

**MVP の採用案: A（監査ログから）**。`audit_logs` の集計は `enterprise_id` で絞り込めるため、Functions で軽量に取得できる。

**監査ログ依存の注意**: 監査ログは `04_監査ログ` のとおりベストエフォートで欠損しうる（例: 書き込み直前の異常終了）。MVP の「利用回数」で A を採用する場合、数値が実態より少なく見える可能性を許容し、Phase 2 の月次再集計（`04_割引・決済` 3.6）や専用カウンタ（上表 C）で補正する想定とする。

## 2.2 集計タイミング

| 項目 | タイミング |
|:--|:--|
| EnterpriseMember の更新 | `confirmOrder` / `stripeWebhook` 時にリアルタイム更新（`04_割引・決済` で定義済み） |
| ダッシュボード表示 | 画面表示時に Functions を呼び出し、集計結果を取得 |
| monthly_usage コレクション | Phase 2 で Scheduled Function による月初バッチ更新を検討 |

## 2.3 集計対象の注文

| 条件 | 含める |
|:--|:--|
| 支払い方式 | `enterprise_subsidy`, `user_advance`, `community_bill` すべて |
| ステータス | `ordered` のみ（`in_cart`, `canceled` は除外） |
| ゲスト注文 | 含めない（`members.is_guest == false` の注文のみ） |

ゲスト注文は `monthly_usage` に加算されないため、企業負担額には自動的に含まれない。注文合計額・自己負担額・利用人数・利用回数の集計時も `members.is_guest == true` のメンバー配下の `member_orders` は除外する。

> ゲスト判定は `member_orders.is_guest_order` ではなく **親 members ドキュメントの `is_guest`** を参照する（02 論点 1.4 で決定。`members.is_guest` に配置）。

### user_advance / community_bill の注文フィールド

`04_割引・決済` では、user_advance / community_bill の `member_orders` には `pay_enterprise_subsidy_amount` をセットしないと定義されている。集計時の扱い:

| 支払い方式 | pay_enterprise_subsidy_amount | pay_community_bill_off_amount | 注文合計額 | 自己負担額 |
|:--|:--|:--|:--|:--|
| enterprise_subsidy | 設定あり（残枠次第で undefined） | 未設定 | `Σ menu_price` | `Σ (menu_price - pay_enterprise_subsidy_amount)` |
| user_advance | 未設定 | 未設定 | `Σ menu_price` | `Σ menu_price`（全額自己負担） |
| community_bill | 未設定 | 設定あり（free / discount で値が入る） | `Σ menu_price` | `Σ (menu_price - pay_community_bill_off_amount)`（多くは 0） |

> ダッシュボードでは「企業負担額」= `pay_enterprise_subsidy_amount` の合計のみを集計する（D-2 が指す「自社の福利厚生としての負担額」のため）。`pay_community_bill_off_amount` はコミュニティ主催者の負担であり、企業負担とは別軸。Phase 2 で「コミュニティ主催者負担額」も別軸として表示する案を検討。


# 3. 表示項目

## 3.1 月別集計

| 項目 | 定義 | データソース |
|:--|:--|:--|
| 利用回数 | 注文セッション数 | `stripes` ドキュメント数 + `audit_logs` の `order_create`（`target_type == 'order_session' && target_id == null`。2.1 参照） |
| 利用人数 | ユニークユーザー数 | `member_orders` から集計（`user_id` のユニーク数） |
| 注文合計額（税込） | 補助前の税込合計 | `member_orders` から集計（`Σ menu_price`） |
| 企業負担額（補助） | 企業補助額の合計 | EnterpriseMember の `monthly_usage` 合計 |
| 自己負担額 | ユーザー支払額の合計 | `member_orders` から集計（`Σ (menu_price - pay_enterprise_subsidy_amount)`） |
| 企業請求見込額 | shokujii から企業へ後請求する見込み合計 | ゲスト無料分 + `enterprise_subsidy` 補助分（`04_請求` §2 参照） |

### 月の定義

イベント開催月（`event.event_start_datetime` の年月）に紐づける。`04_割引・決済` の月額利用実績と同一のルール。

## 3.2 メンバー別集計

| 項目 | 定義 | データソース |
|:--|:--|:--|
| 利用回数 | 注文セッション数 | `stripes` + `audit_logs` の `order_create`（`target_id == null`。対象期間・当該 user_id に限定） |
| 注文合計額（税込） | 補助前の税込合計 | `member_orders` から集計 |
| 企業負担額（補助） | 企業補助額の合計 | `monthly_usage`（対象期間の合計） |
| 自己負担額 | ユーザー支払額の合計 | `member_orders` から集計 |

メンバー一覧は**対象期間に注文が1件以上あるメンバーのみ**表示する。画面表示と CSV 出力で同一の条件とする。

## 3.3 グラフの種類

| 用途 | グラフ | 備考 |
|:--|:--|:--|
| 月別トレンド | 棒グラフ | 月ごとの利用回数・金額の推移 |
| 月別内訳 | 積み上げ棒グラフ | 企業負担 vs 自己負担の比率（Phase 2 で検討） |
| メンバー別 | テーブル | 一覧表示。上位 N 名のランキング表示は Phase 2 で検討 |

MVP では棒グラフ（月別）+ テーブル（月別・メンバー別）を実装する。棒グラフは**利用回数**と**注文合計額**の2系列を表示する（タブまたは切り替えで選択可能）。

# 5. パフォーマンス・実装方針

## 5.1 集計の実行場所

`01_仕様概要` の技術方針に従い、**集計は Cloud Functions で行う**。フロントエンドからの直接集計は行わない。

### 理由

| 観点 | Functions | フロント |
|:--|:--|:--|
| データ量 | 企業内全 `member_orders` をスキャン可能 | クライアントに大量データを送るのは非現実的 |
| セキュリティ | enterprise_id でテナント分離を厳密に制御 | クライアントに生データを渡すリスク |
| 読み取りコスト | サーバー側で制御可能 | クライアント数 × 読み取り回数で増加 |
| キャッシュ | 集計結果のキャッシュが可能（Phase 2） | 難しい |

## 5.2 API 設計

### 認証・検証

- 呼び出し元は認証済みユーザーであること（Firebase Auth）
- `request.auth.token.enterprise_id` とパラメータの `enterpriseId` を照合し、**一致しない場合はエラー**とする
- または、`enterpriseId` をパラメータで受け取らず、`request.auth.token.enterprise_id` のみを使用する方式も可（クライアント改ざんのリスクを排除）

### getDashboardMonthlyData

| 項目 | 内容 |
|:--|:--|
| 種別 | onCall |
| パラメータ | `enterpriseId`, `startYearMonth`, `endYearMonth` |
| 戻り値 | 月別集計の配列 |

### getDashboardMemberData

| 項目 | 内容 |
|:--|:--|
| 種別 | onCall |
| パラメータ | `enterpriseId`, `startYearMonth`, `endYearMonth` |
| 戻り値 | メンバー別集計の配列 |

### getDashboardCsvMonthly / getDashboardCsvMembers

CSV 用の集計データを返す。フロントエンドで `downloadCsv` を呼び出してダウンロードする。または、Functions で CSV 文字列を生成して返す方式も検討可能。

## 5.3 負荷対策

| 規模 | 対策 |
|:--|:--|
| EnterpriseMember | 100〜300人規模。全件取得は問題なし |
| `member_orders` | `enterprise_id` インデックス + 期間絞りでクエリ最適化（02 全体構成 6.5 のインデックス参照） |
| `stripes` | 同様に `enterprise_id` インデックスで絞り込み |
| Phase 2 | `monthly_usage` コレクションを導入し、月別集計を事前計算に移行 |

## 6.2 他ドキュメントとの整合

- **02_全体構成:** `monthly_usage` コレクションは Phase 2 のまま。MVP では使用しない。`enterprise_id` を含む `collectionGroup('member_orders')` / `collectionGroup('stripes')` のインデックスは 6.5 で定義
- **04_割引・決済:** EnterpriseMember の `monthly_usage` / `monthly_order_count` の更新タイミングは `confirmOrder` / `stripeWebhook` 完了時。`monthly_order_count` は「ordered な member_orders ドキュメント数」を意味するため、ダッシュボードの「利用回数」（注文セッション数）とは別概念
- **04_ゲスト参加:** ゲスト注文（`members.is_guest == true`）は集計対象外。D-3 で決定
- **04_全社管理者画面:** ダッシュボードは本ドキュメントで詳細化
- **04_請求:** 企業請求見込額の集計定義（MVP）。ダッシュボード §3.1 の「企業請求見込額」列と連動
- **04_監査ログ:** 「利用回数」の `confirmOrder` 経由セッション数は `audit_logs` の `action == 'order_create' && target_type == 'order_session' && target_id == null` で導出（2.1 および `04_監査ログ` 4.2 参照）
