## 0. 分離パターン早見表（簡略版）

> 詳細・評価軸の正本: [02_物理vs論理_パターン定義.md](../90_アーカイブ/v0.2_アーキテクチャ再検討/02_物理vs論理_パターン定義.md) §5.1 / §6.5 / §6.6
>
> **記号**: B′ = 企業ごと DB 分離。B″ = PF↔エンプラ の DB 分離（named database）。B″ / B′ は **Project を増やさない** DB 分離の段階手段。

**争点の整理**: いずれも **テナント（企業）分離はする**。違いは **どの境界を物理で割るか**（Project / Firestore DB / 論理のみ）。

| パターン | 構成（Project × DB） | 物理で割る境界 | 企業間 | MVP |
|:--|:--|:--|:--|:--|
| **A** | 1 × **1**（PF + 全エンプラ同居） | なし（`enterprise_id` 論理分離） | 論理 | **採用**（＋ IdP） |
| **B** | **2** × 各 1（PF / エンプラ） | PF ↔ エンプラ | 論理 | 不採用 |
| **B″** | 1 × **2**（`(default)` + `enterprise`） | PF ↔ エンプラ | 論理 | 不採用 |
| **B′** | 1 × **N**（企業ごと named database） | 企業 ↔ 企業 | 物理（DB 単位） | 不採用 |
| **C** | **N** × 各 1（企業ごと Project） | PF↔エンプラ + 企業間 | 物理 | 不採用 |
| **D** | **標準は A** ＋ 要件企業のみ **専用 Project**（Silo） | 例外企業だけ PF↔エンプラ（＋企業単位） | 標準: 論理 / 例外: 物理 | 不採用（将来オプション） |

### エスカレーション（データ層分離が必要になったとき）

```
A（現行・MVP）
 └─ データ層だけ分けたい（Project は 1 系統のまま）
     ├─ B″ … PF↔エンプラ だけ（2 DB 固定・B′ より軽い）
     └─ B′ … 企業間も（N DB）
 └─ Project も分けたい
     └─ B … PF / エンプラ の 2 Project
 └─ 全社 Silo（非デフォルト）
     └─ C … 企業ごと Project（運用 ×N）
 └─ 特定企業だけ Silo（営業オプション）
     └─ D … 標準 A ＋ 例外 1 社ずつ専用 Project
```

### 選び方（要点）

| 欲しいもの | 向くパターン |
|:--|:--|
| 今すぐ出す・partner 横断を最優先 | **A** |
| Auth 混在の解消（Project は増やしたくない） | **A ＋ IdP**（B は不要） |
| PF の PII とエンプラデータの blast radius 遮断 | **B″** → 足りなければ **B′** |
| 企業間の物理隔離・DB 単位 IAM・CMEK | **B′** |
| PF/エンプラの Auth・Hosting・原価も完全分離 | **B** |
| 契約書に「専用 Firebase Project」と明記 | **D**（Silo） |

**partner 連携**: A 以外（B″ / B′ / B / C / D）は events / member_orders の横断 read が **2 回以上**（DB または Project を跨ぐ）＋メニューコピーは Function 経由（§10.6）。

## 1. 結論

**Project 分離なし（パターン A = 単一 Firebase Project を継続）。** そのうえで **Identity Platform マルチテナンシーを導入**し、PF / エンプラの認証境界だけを論理テナントで強化する。

- 単一プロジェクトの強み（partner 横断 read の単純さ・ゲスト参加の自然さ・運用 1 系統・リリース速度）を維持する。
- B の最大の動機だった「**Auth 混在の解消**」は、IdP マルチテナンシーで**プロジェクトを増やさずに**得られる（§5.1）。
- B のもう一つの売りだった「**Functions デプロイ独立**」も、選択的デプロイ／マルチ codebase で A のまま実現できる（§8.2・§3.3 注）。
- 残る B 固有のメリット（可用性/障害分離 SLA・監査スコープ・原価分離など、Project/DB 単位でしか割れないもの）は「今すぐ必要なハード制約」ではなく**将来の保険**。`enterprise_id` 付与済みで後から分離する出口も確保済み（§2.6）。
- データ/インフラの物理分離が本当に必要になったら、**B″（PF↔エンプラ の DB 分離）**・**B′（企業ごと DB 分離）**・**特定企業のみ Silo（パターン D）** で段階対応する（§4・§5.3・§10.3・`06_将来_パターンD_特定企業だけ分離.md`）。**MVP ではいずれも採用しない**（[02_物理vs論理_パターン定義.md](../90_アーカイブ/v0.2_アーキテクチャ再検討/02_物理vs論理_パターン定義.md) §6.6）。

## 2. 結論に至った経緯

### 2-1. 何を比較したか
単一 Project に PF と全エンプラを同居させる **A** と、PF / Enterprise の境界だけを物理分離する **B** の二択（§0）。B は「企業ごとに環境を分ける（C）」ではなく **PF とエンプラを 2 つに割るだけ**で、コストは企業数に対して線形に増えない（固定費 ×2、§1）。事例調査が示す「物理分離の地獄」は C の話であって B への反証ではない。

### 2-2. B が解決する一番の問題は「Auth 境界」だった
A の弱点は「PF とエンプラの Auth 混在・越境ログイン・PF へのデータ露出」という**設計問題**で、テスト・レビューで抑え込む経常コストが残る（§4）。B はこれを構造的に消せる点が最大の売りだった。

### 2-3. しかし IdP マルチテナンシーで Auth 境界は A のまま解決できる
Identity Platform のマルチテナンシーは 1 プロジェクト内でテナントごとに認証空間を分ける機能で、Firebase Auth からは無停止アップグレード。これにより越境ログイン遮断・同一メアド衝突の解消・企業別 SSO への道が、**プロジェクトを増やさずに**手に入る（§5.1）。
→ **B を選ぶ最大の動機（Auth 混在解消）が消えた。**

### 2-4. 残る B のメリットは「将来の保険」に縮小
IdP 導入後に B だけが固有に解くのは、Project/DB 単位でしか割れないもの（可用性/障害分離 SLA・監査スコープ・原価分離・Firestore スケール予算など、§10.1）。いずれも**今のフェーズで必須のハード制約ではない**。
- 「Functions デプロイ独立」は B 固有ではなく、A の選択的デプロイ／マルチ codebase で獲得できる（§8.2・§3.3 注）。
- データ層の「混在が気持ち悪い」も、DB 分離ではなく専用コレクション＋discriminated union で解消できる（DB 境界の問題ではない、§10.2）。

### 2-5. 一方 A の優位は shokujii の中核構造と直結
partner が全テナントの events / member_orders を横断 read し、メニューコピー・予約承認もテナントを跨ぐ。A ならこれが単一 DB の collectionGroup 1 発で済む（§2.1）。B にすると partner が cross-project 化し、横断 read の 2 クエリ化・横断 write の関数経由化・2nd Firebase App 認証など重い作り替えが発生する（§10.6）。ゲスト参加（PF ユーザーのエンプライベント参加）も A だから自然に成立する（§8.7）。partner 連携が中核に残る前提では、この優位は手放せない。

### 2-6. 出口も確保済みなので「今は分けない」が安全
全 doc・Storage パスに `enterprise_id` を付与済みで、「分離設計の後付け地雷」を回避済み（§2.6）。今は A で出し、リージョン要求・大口の物理分離要件・別プロダクト化などが現実になった時点で **B″ / B′ / 特定企業 Silo** へ進める（§4・§10.3）。

## 3. 判断の前提（崩れたら見直す）

この結論は次の前提に依存する。前提が変わったら §4 のトリガーで再評価する。

- **partner（飲食店連携）がエンプラの中核に残る**（横断 read が生き続ける）。
- **PF とエンプラの乖離は可能性レベル**（社内 SNS・サーベイ中心化などの別プロダクト化は確定ロードマップではない、§10.4・§10.5）。

**共有 / 分岐の境界規則**（「共通化前提」に引っ張られすぎないための線引き。基準は「partner が触るか」）:

| 面 | 方針 |
|:--|:--|
| partner が横断 read する面（`events` 本体・`menus`・`member_orders`） | 共有・安定を維持（分岐させると partner が 2 形を扱い A 最大優位を失う） |
| エンプラ専用面（communities 相当・管理画面・将来の SNS/サーベイ） | 分岐を明示的に許可（専用コレクション＋discriminated union） |

## 0. パターン定義（再掲）

> **全パターン（A / B / B″ / B′ / C / D）の簡略版は冒頭 §0**。本節は IdP 確定前の **A vs B 二択**比較の経緯記録。


|            | パターン A（v0.1 現状）                    | パターン B（プロダクト分離）                         |
| ---------- | ---------------------------------- | --------------------------------------- |
| 構成         | 1 Firebase Project に PF + 全エンプラを同居 | PF Project + Enterprise Project（1 つ）に分離 |
| Auth       | PF / エンプラ共通の Firebase Auth         | PF と Enterprise で Auth を分離              |
| Firestore  | PF データ・全エンプラデータが同一 DB              | エンプラデータは Enterprise Project に独立         |
| 企業間（テナント間） | `enterprise_id` による論理分離            | **B でも企業間は `enterprise_id` 論理分離のまま**    |
| デプロイ系統     | 1 系統                               | 2 系統（PF / Enterprise）                   |


**重要**: B は「企業ごとに Project を分ける」案ではない。PF とエンプラの境界**だけ**を物理分離し、エンプラ企業同士は引き続き論理分離である（企業ごと物理分離は C、企業ごと DB は B′、**PF↔エンプラ の DB 分離は B″**）。

## 1. 前提の整理：B のコストは「×2」であって「×N」ではない

意思決定で最も誤解されやすい点をここで固定する。

- 事例調査（counterworks 10 ヶ月、hacomono、ecforce 1.5 年）が示す「物理分離の地獄」は、**すべてパターン C（顧客ごとに環境を分ける = 100 社 100 環境）の話**である。
- **パターン B は「PF と エンプラ」の 2 つに割るだけ**。企業が何社増えても Enterprise Project は 1 つのままで、コストは企業数に対して**線形に増えない**。

→ 「B にすると開発コストが上がる」は正しいが、その増分は **環境あたり 1 → 2 プロジェクト（固定）** であり、事例の破綻パターン（C）とは別物。**事例調査を根拠に A を擁護するのは筋が悪い**（あれは C への反証であって、B への反証ではない）。

### 1.1 現状実装はすべて「1 プロジェクト前提」

- `firebase.json`: `functions/default` 単一（`codebase: "default"`）、`firestore.rules` 単一、`storage.rules` 単一、emulator は `singleProjectMode: true`
- `.github/workflows/deploy_enterprise.yml`: 単一 `PROJECT_ID` / 単一 `FIREBASERC` を生成してデプロイ

B はこの「1 プロジェクト前提」を崩す。これが B の開発コストの実体である（§3）。

## 2. パターン A のメリット（深掘り）

### 2.1 「横断 read」が単一 DB で完結する（A 最大の構造的優位）

shokujii は構造的に **partner が全テナントの events / memberOrders を横断 read** し、**予約承認・`PartnerMenus → EventMenus` コピー**もテナントを跨ぐ（`01_再設計` §partner、事例調査 §5「物理分離で最も悪化するのが横断 read」）。

A ではこれが **collectionGroup 1 回 / 同一 DB 内コピー**で済む。これは単に安いだけでなく、**分散システム化を完全に回避できる**点に本質的価値がある。B では partner のバックエンドが PF / エンプラ境界をまたぐ **cross-project Admin SDK クライアント**になる。

### 2.2 ローカル開発・emulator が単一で完結

`singleProjectMode: true` により 1 つの emulator に Auth / Firestore / Functions / Hosting / Storage が同居。横断機能（partner → エンプラ）も**ローカルで 1 発で再現・テスト**できる。

### 2.3 CI・Secret・Rules・インデックスが全部 1 系統

- デプロイ: PF とエンプラが同じ `PROJECT_ID`
- `firestore.rules` / `firestore.indexes.json`: 1 セット
- Secret Manager / IAM / サービスアカウント / 課金: 1 プロジェクト

### 2.4 横断分析・課金集計が 1 クエリ

「全エンプラ + PF 合計の予約数・請求サマリ」を単一クエリで出せる（事例調査 §2.1 で物理分離の痛点とされた部分）。

### 2.5 リリース速度（MVP 最優先なら最強）

v0.1 のまま追加実装ゼロ。`再検討.md` §8 でも工数・リリース速度は A が最も高い評価。

### 2.6 「後から分離できる」余地は既に確保済み

v0.1 で全 doc に `enterprise_id`、Storage パスにも `enterprise_id` を付与済み（`再検討.md` §9.4.1）。事例調査が繰り返す「**分離設計の後付けが最大の地雷**（ripla: 3,000 本の SQL 書き換え）」を、shokujii は**すでに回避できている**。「今 A で進めて、必要になってから B / B″ / B′ / C へ移行」という出口が技術的に確保されている。

## 3. パターン B のデメリット（開発コスト中心に深掘り）

### 3.1 環境が「3 → 6 プロジェクト」相当になる

現状は sandbox / development / production の 3 環境 = 3 プロジェクト。B では各環境に PF と Enterprise の 2 つが必要で、**実質 6 プロジェクト管理**になる。それぞれに以下が二重化する。

- Firebase プロジェクト作成・課金設定
- サービスアカウント・`GCLOUD_SERVICE_KEY`
- IAM・Secret Manager
- ドメイン / Hosting ターゲット

→ 「**sandbox が 2 つ必要になる**」という懸念はこれであり、**正しい指摘**。ただし固定費（×2）であって企業数線形（×N）ではない。

### 3.2 Auth 基盤の二重管理（base への波及）

`base` は user / partner / enterprise で共有される共通 UI 層。B では Firebase Auth が PF と Enterprise で別インスタンスになるため、**共通の認証初期化・claims 設計を 2 系統**に分ける必要がある。これは「B の本来の狙い（Auth 混在解消）」の裏返しで、**得たいメリットそのものが開発コスト**になる。

### 3.3 functions の分割が必須でセットになる

`01_再設計` §2 の通り、B を本気でやると `functions_user` / `functions_enterprise` / `functions_base`（共通）の分割が要る。ところが「firebase functions は 1 ディレクトリしかデプロイできない」「`functions_base` をどう取り込むか（シンボリックリンク or ビルド後コピー）」という**未解決の仕組み作り**が前提になる。今の `functions/default` 単一構成を作り替える、地味だが重いインフラ作業。

> **注（2026-06-18 追記・`06` §3 と整合）**: 「1 ディレクトリしかデプロイできない」は正確ではない。Firebase は ①選択的デプロイ（`firebase deploy --only functions:<names>`）、②同一 Project 内のマルチ codebase（`firebase.json` の `functions` 配列を複数エントリ化）でデプロイ単位を割れる。したがって**「デプロイを独立させる」目的だけなら B（Project 分離）は不要**で、A のまま実現できる（`06` PA-24）。B で `functions_base` 取り込みの仕組みが要るのは「ソースを物理分割する」場合に限られ、デプロイ独立性そのものとは別問題。この訂正は §8.2・§8.12 #19・§10.1 の評価に波及する。

### 3.4 partner が cross-project になる（技術的に一番厄介）

partner は Enterprise Project の events / memberOrders を読み、予約承認やメニューコピーを跨いで行う。A なら同一 DB、B では**別プロジェクトへの Admin SDK アクセス + 権限設計**。`singleProjectMode` 前提のローカル開発も崩れる。

### 3.5 Firestore Rules / index / seed の二重管理

`firestore.rules` を PF 用とエンプラ用に分割。インデックス追加・seed データ投入・E2E も 2 プロジェクトに対して行う。

### 3.6 データ移行コスト（v0.1 → B）

`再検討.md` §9.1 の「捨てるもの」の通り、**同一 Auth / 同一 Firestore からの移行**が発生する。sandbox はデータ削除前提（`01_再設計` 冒頭）なので軽いが、ゼロではない。

## 4. ただし、A で「構造的に消せない」核心問題（A を選ぶ場合の残存リスク）

> **注（IdP 確定後）**: 以下は IdP 導入**前**の議論として記録したもの。Auth 混在・越境ログイン（表の上 2 行）は IdP マルチテナンシーで大部分が解消される（§5.1・冒頭 §1）。PF へのデータ露出（表 3 行目）は単一 DB のまま残る。

A のメリットは**ほぼ全てが「コスト・速度・運用の単純さ」**に属する。一方で B が解決する問題は性質が違う。メリットだけでなく、A を選んでも残る弱点を隠さず並べる。


| A で残る問題              | 性質                 | A での対処                                                |
| -------------------- | ------------------ | ----------------------------------------------------- |
| PF / エンプラ Auth 混在    | **設計問題**（実装品質ではない） | テスト・レビューで「抑え込む」だけ。構造的には残る                             |
| エンプラユーザーが PF にログイン可能 | 同上                 | UI / Rules / claims で都度ガード                            |
| PF 画面にエンプラデータ露出      | 同上                 | `enterprise_id` フィルタ・collectionGroup の漏れ防止を**永続的に**負担 |


`再検討.md` §12-2 が明言する通り、これは「論理分離の実装品質」ではなく **プロダクト境界の設計問題**。A を選ぶ = 「この境界バグのリスクを、テストと規律で永久に払い続ける」選択になる。1 つのフィルタ漏れが PF 全体に露出する blast radius も残る。

**コストの性質の違い（意思決定の本質）**:

- **B のコスト（×2 の二重管理）は一度払えば終わる**（固定費・初期投資）。
- **A のコスト（境界ガードの永続的負担 + 事故リスク）は毎回の実装で発生し続ける**（経常費・技術的負債）。

### 4.1 スキーマ分岐の自由度（A のもう一つのデメリット / B のメリット）

「PF とエンプラで Firestore のスキーマ・データ構造を大きく変えられる」点は、開発コストと並ぶ **B の実質的なメリット**であり、裏返すと **A のデメリット**である。

**A で既に起きている「optional 汚染」（現状コードで確認できる）**

PF とエンプラが同一 Firestore の同一コレクション（`events` / `communities` / `users`）を共有するため、**エンプラ専用フィールドはすべて `optional` でぶら下がっている**。

```120:124:common/src/schemas/Event.ts
  community_bill_settings: optionalDeleteField(CommunityBillSettingsDbSchema),
  enterprise_id: NonEmptyStringSchema.optional(),
  enterprise_subsidy_settings: optionalDeleteField(EnterpriseSubsidySettingsDbSchema),
  canceled_at: TimestampSchema.optional(),
  canceled_by: z.string().nonempty().optional(),
```

```33:34:common/src/schemas/User.ts
  user_type: z.enum(USER_TYPE_VALUES).optional(),
  enterprise_id: NonEmptyStringSchema.optional(),
```

A で顕在化する問題は 2 種類:

1. **共有コレクションの optional 肥大**: 追加仕様が多いエンプラ固有フィールド（割引設定・部署・承認ワークフロー等）が共有スキーマに `optional` で増え続ける。型システムは「このフィールドはエンプラ時のみ存在」を保証できず、PF 側コードも防御的に扱う必要がある。
2. **エンプラ専用コレクションの混在**: `/enterprises`・`/enterprises/{id}/members`・`/audit_logs`・`passCodes` など PF では不要なコレクションが同一 Firestore に同居する。

**B のメリット**: Enterprise を別 Firestore に持てば、エンプラ専用の `events` スキーマを独立定義でき、**エンプラ固有フィールドを必須化**でき、**PF 側に専用コレクションや optional を持ち込まない**。

**ただし「効く条件」と留保**

1. **根本原因は DB 境界ではなくコード共有戦略**。v0.1 は「user をコピーして構築・base コンポーネント使用・common スキーマ流用」（`01_仕様概要` L16-18, L56）が方針。B でプロジェクトを分けても、`common` の `Event` スキーマ・`base` コンポーネントを共有し続ける限り**型レベルでは共有**される。スキーマを実際に分岐させるには `common` 側で `EnterpriseEvent` を別定義（フォーク）する必要があり、これは**プロジェクト分割とは別のコード設計判断**。B は分岐を「やりやすくする」だけで、自動的に optional 汚染を消すわけではない。
2. **分岐は諸刃の剣**。エンプラを PF の上に作る理由は再実装を避けるため。スキーマを大きく分岐させるほど再利用メリットを失い、**2 コードベース維持コスト**に転化する。「分岐できる」は「分岐したい範囲」に比例してのみ価値を持つ。
3. **partner 横断との干渉**: partner は PF・エンプラ両方の `events` / `memberOrders` を横断 read する。エンプラのスキーマを分岐させると **partner は 2 つの形を扱う**ことになり、A の「optional 付き単一スキーマ（partner は 1 形）」より複雑化する。

**A 内でも緩和できる手段**

- **エンプラ専用コレクションは A でも分離可能（既に実施済み）**。`/enterprises`・`/audit_logs` は別コレクションで、optional 汚染しているのは「コード再利用したい」`events` / `communities` / `users` のみ。
- **discriminated union で型安全性を回復**。判別子を入れれば「エンプラ時のみ割引設定が必須」を**型で強制**できる（既に `CommunityBillSettings` で `discriminatedUnion` を使用する前例あり）。DB を分けずに optional 汚染の「型安全性」面を解消できる。
- **拡張スキーマのファイル分離**: collection は共有でも `EventEnterpriseExtension` 等を別ファイルに切り出し、PF コードから見えにくくする。

**評価**: この軸は **B の正当なメリット**だが、重みは「**エンプラ版が PF からどれだけ乖離する見込みか**」に依存する。乖離が大きい見込みなら B（やがて B′/C）の価値が上がり、乖離が小さい（PF 機能の踏襲が中心）なら **A + discriminatedUnion** で型安全性面はかなり代替できる。「物理的に別 DB でないと困るほどスキーマが乖離するか」がこの軸での分かれ目。

## 5. コストを抑えて A の利点を残す「中間解」

「sandbox 2 つは重い」という懸念に直接効く案がある。

### 5.1 Identity Platform マルチテナンシー（A のまま実装可能・PHARMAX 事例）

事例調査 §1.2 / §5:

> PHARMAX は**プロジェクトを分けずに** Identity Platform の論理テナント機能で本番運用

→ **単一プロジェクトのまま Auth の境界だけを論理テナントで強化**する案。B の「Auth 混在解消」という最重要メリットの大部分を、**プロジェクトを増やさずに（sandbox を 2 つにせず）**得られる。A 継続を検討するなら、まずこれで A の弱点をどこまで埋められるかを評価する価値が高い。

**A のまま実装できる根拠**

- Identity Platform のマルチテナンシーは **1 プロジェクト内**でテナントごとにログイン方式・ユーザー空間を分ける機能（[Google Cloud Japan 解説](https://zenn.dev/google_cloud_jp/articles/idp-multi-tenancy)）。プロジェクト分割（B）とは別レイヤーで、**プロジェクトは 1 つのまま**。
- Firebase Auth → Identity Platform は **同一 SDK・ユーザー移行不要のアップグレード**（API 有効化のみ）（[PharmaX 記事](https://zenn.dev/pharmax/articles/95a2f0f76fd016)）。
- これは v0.1 仕様の認証方式テーブル（MVP=Firebase Auth+claims / Phase 2=Identity Platform+テナント作成）と一致する **既定路線の前倒し**（`01_仕様概要` §認証方式）。

**何が解決し、何が残るか**

- **解決（A の弱点の "Auth 部分"）**: エンプラユーザーをテナント所属にすると uid 名前空間が分離され、`firebase.auth().tenantId` 指定でしか認証できない。Rules で `request.auth.token.firebase.tenant` を参照でき、PF/エンプラ越境ログインをトークンレベルで遮断。企業別 SSO（SAML/OIDC）への道も開く。
- **残る（解決しない）**: Firestore は単一 DB のままなので、blast radius・collectionGroup 越境・運用者の全社閲覧・単一障害点は A のまま。**「IdP マルチテナンシー = データの物理分離」ではない**（PharmaX も DB は分けず Rules + 多層防御）。データ分離まで要るなら B″ / B′ / C（§5.3・§10.3）。

**このコードベースでの実装インパクト**（現状テナント概念は未使用）


| 箇所                                                                                                  | 現状                        | 必要な変更                                                          |
| --------------------------------------------------------------------------------------------------- | ------------------------- | -------------------------------------------------------------- |
| `functions/default/src/enterprise/auth.ts`（`createCustomToken` / `setCustomUserClaims` / `getUser`） | プロジェクトレベル                 | テナント対応（`getAuth().tenantManager().authForTenant(tenantId)...`） |
| `functions/default/src/enterprise/onboarding.ts`（`createUser`）                                      | プロジェクトレベル                 | テナント内ユーザー作成 + 企業ごとテナント作成                                       |
| `functions/default/src/stores/user.ts`（`getUserIdFromEmail`）                                        | プロジェクト全体検索                | テナントスコープ検索                                                     |
| `base/src/firebase.ts`（`getAuth(app)`）                                                              | テナント未指定                   | エンプラアプリでログイン前に `auth.tenantId` を設定                             |
| `firestore.rules`                                                                                   | `enterprise_id` claim で判定 | 必要なら `firebase.tenant` 判定を追加（任意）                               |


**設計判断・留意点**

- **テナント粒度**: 「企業ごと 1 テナント」推奨（企業別 SSO・サブドメインと整合、`enterprise_id` ↔ `tenantId` を 1:1）。「エンプラ全体で 1 テナント」は PF/エンプラ分離のみでシンプルだが企業別 SSO 不可。
- **ゲスト整合**: テナント所属ユーザーは uid 名前空間が分かれ、PF ユーザーはエンプラテナントにログインできない。これは v0.2 の「PF ユーザーはエンプラにログイン不可・専用ゲストアカウント」（`01_再設計` §ゲスト）と方向性が一致。
- **課金**: Identity Platform は MAU 課金（無料枠あり）。有効アカウント数で試算が必要。
- **PharmaX の学び**: テナント追加ごとの Rules ハードコードは shokujii では `enterprise_id` claim で汎用化済みのため回避可能。コンソール検索フィルタの弱さに注意。SDK 対応言語は Node 対応済みで問題なし。
- **移行**: 既存エンプラ Auth ユーザーはプロジェクトレベル作成済みのためテナント所属へ作り直し（or import）が必要。v0.2 は sandbox データ削除前提（`01_再設計` 冒頭）なので**今が移行の好機**。

### 5.2 B′（企業ごと Firestore Database）

[02_物理vs論理_パターン定義.md](../90_アーカイブ/v0.2_アーキテクチャ再検討/02_物理vs論理_パターン定義.md) §6.5。プロジェクトは 1 つのまま **企業ごと**に named database を分ける案。**企業間**の物理隔離が必要なときの移行先。partner は DB を N 回読む必要があり、A より重い。MVP では採用しない。

### 5.3 B″（PF/エンプラ の Firestore Database 分離・**MVP 不採用**）

[02_物理vs論理_パターン定義.md](../90_アーカイブ/v0.2_アーキテクチャ再検討/02_物理vs論理_パターン定義.md) §6.6。B′ が「企業 ↔ 企業」を割るのに対し、B″ は **B と同じ「PF ↔ エンプラ」境界を Project ではなく named database で割る**案（単一 Project のまま `(default)` + `enterprise` の 2 DB）。

| 観点 | B″ | B′ |
|:--|:--|:--|
| 割る境界 | PF ↔ エンプラ | 企業 ↔ 企業 |
| Auth / Secret / terraform | 1 系統（IdP のまま） | 1 系統 |
| 2nd Firebase App | 不要 | 不要 |
| blast radius PF↔エンプラ | 遮断 | 遮断 |
| blast radius エンプラ↔エンプラ | 残る | 遮断 |
| partner 越境 | 2 DB クエリ + マージ | N DB クエリ |
| 新規企業追加 | doc 1 件 | DB 作成 + Rules/index |

**B″ vs B′ の選び方**（§4 トリガー発火時）: 必要な隔離が **PF↔エンプラ 止まり**なら **B″**（B′ より軽い・partner は 2 DB で済む）。**企業間**まで物理隔離が要るなら **B′**。契約上「専用 Project」が必須なら **D（Silo）**。

partner 越境（§10.6）は B と同様に残るが、B 固有の Auth 二重化・2nd App は不要。emulator マルチ DB・CMEK の DB 単位適用は要 PoC。

## 6. 意思決定のための問い

「A のままで良いか / B にすべきか」は最終的に次に集約される。

1. **PF と エンプラの Auth 混在・データ露出を "設計で消す" ことにどれだけ価値を置くか?**
  - 「テスト・レビューで抑え込めば実害は出ない」と判断できる → A で十分
  - 「境界バグのリスクを構造的にゼロにしたい・導入審査で説明したい」 → B
2. **Auth 境界だけが目的なら、プロジェクトを増やさず Identity Platform マルチテナンシーで足りないか?**（A 継続の現実的補強・§5.1）
3. **B の "一度きりの ×2 コスト" を払えば、その後の境界ガードの経常負担と事故リスクが消える ── このトレードを今のフェーズで取るべきか?**
4. **エンプラ版が PF からどれだけスキーマ・データ構造で乖離する見込みか?**（§4.1）
  - 乖離が大きい（エンプラ独自仕様が増え PF と共有したくない） → B の価値が上がる
  - 乖離が小さい（PF 機能の踏襲が中心） → A + discriminatedUnion で型安全性面はかなり代替可能

## 7. 当時の結論（IdP 確定前・参考）

1. **事例調査（C の失敗）を根拠に A を擁護するのは誤り**。A vs B の本当の争点は「Auth / データ境界を**設計で消すか、規律で抑え続けるか**」の一点。
2. **A の強みは「横断 read の単純さ・運用 1 系統・リリース速度」**で、これは shokujii の partner 横断構造と相性が良く、軽視できない。
3. **A の弱みは「Auth 混在・PF 露出という設計問題が構造的に残る」こと**。テスト・レビューで抑え込む経常コストと事故リスクを永続的に負う。
4. **B の弱みは「環境 ×2（sandbox 2 つ）・Auth 二重管理・functions 分割・partner の cross-project 化」という一時的な開発コスト**。固定費であり企業数線形ではない。
5. リリース速度最優先で境界リスクを運用許容できる短期なら A、プロダクトとして長く育てるなら B が合理的。
6. 「sandbox 2 つ問題」が A 傾倒の主因なら、**まず Identity Platform マルチテナンシー（A のまま実装可能・§5.1）で A の認証境界をどこまで補強できるか**を確認するのが、コストと安全性のバランスとして筋が良い。これは v0.1 仕様の Phase 2（Identity Platform 化）の前倒しでもある。
7. **スキーマ分岐（§4.1）は B の正当なメリット**だが、根本原因は DB 境界よりコード共有戦略であり、A 内でも discriminatedUnion・専用コレクション分離で型安全性面は緩和できる。採否は「物理的に別 DB でないと困るほど乖離するか」次第。

## 8. その他の論点（ブレスト）

§1〜§7 でカバーした軸（横断 read・開発コスト・Auth 混在・スキーマ分岐・IdP 中間解）以外に、**事業・運用・コンプライアンス視点**で効く論点を洗い出す。新論点の多くは「コンシューマ PF と有償エンプラを同じ箱に入れることの事業リスク」という一貫テーマに収束し、**B 寄りに働くものが多い**。

### 8.1 可用性・障害分離（SLA）

- **A**: 1 プロジェクトの障害（Firestore 障害、Functions 暴走、コンシューマ PF のトラフィック急増）が **PF とエンプラを同時に巻き込む**。有償エンプラに SLA を約束しづらい。
- **B**: エンプラ Project の障害が PF に波及しない（逆も同様）。**有償エンプラの可用性をコンシューマ PF のスパイクから守れる**。
- → `再検討.md` §7.1 の「単一障害点」を、SLA 営業観点の独立論点に格上げ。**重要度: 高**。

### 8.2 Functions のデプロイ結合（見落とされがち）

- 現状 `functions/default` は**単一コードベース**。`deploy_functions.yml` は `--only functions`・単一 `PROJECT_ID` で **PF とエンプラの関数を一括デプロイ**する。
- **A の隠れたリスク**: エンプラ関数の修正デプロイが **PF の全関数を再デプロイ**する（コールドスタート・障害の巻き込み・リリース独立性なし）。
- **B**: `functions_enterprise` を独立デプロイでき、**リリースサイクルを分離**できる（大口顧客の繁忙期はエンプラを凍結しつつ PF を回す等）。
- **A での軽減（重要）**: 上記は**現状の `--only functions` 一括デプロイの実装問題**であって A の構造的限界ではない。選択的デプロイ／マルチ codebase（§3.3 注）で、エンプラ関数群と PF 関数群を別 workflow にすれば「片方リリースで他方を再デプロイ」は A のまま解消できる（`06` PA-24）。
- → よって本論点の **B 有利は実質ほぼ中立化**する（IdP が #11・#12 を中立化したのと同じ構図）。残る差は「Project 単位の**障害**分離（§8.1）」であって「デプロイ独立」ではない。**重要度: 高 → 中（A で軽減可）**。

### 8.3 Firestore のスケール制約・インデックス予算

- Firestore は**複合インデックス上限（DB あたり 200）**や書き込みレート上限を **DB 単位**で持つ。
- **A**: PF（コンシューマ大量トラフィック）とエンプラがインデックス予算・スループット・ホットスポットを**共有**。
- **B / B″ / B′**: 予算が分かれる。
- → 企業数・機能増で顕在化。**重要度: 中**。

### 8.4 コンプライアンス監査スコープ（SOC2 / ISO27001 / Pマーク）

- **A**: 監査・ペネトレーションテストの**スコープにコンシューマ PF が必ず含まれる**（境界がない）。
- **B**: エンプラ Project を**監査スコープとして切り出せる**。審査対象が小さく、コンシューマ変更が監査に影響しにくい。
- → 導入審査の「説明しやすさ」に直結。**重要度: 中〜高**。

### 8.5 コスト按分・ユニットエコノミクス

- **A**: GCP 請求が混在し、**エンプラ 1 社あたりのインフラ原価**が見えない。500円/アカウント（`01_仕様概要`）の採算検証がしづらい。
- **B**: Project 単位課金で**エンプラ事業のインフラ原価**を分離計測できる。**重要度: 中**。

### 8.6 チーム・IAM・権限分離

- **A**: 全員が単一 Project の本番にアクセスしうる（IAM 条件で絞るしかない）。
- **B**: エンプラ Project だけに権限を付与でき、**最小権限が自然**。**重要度: 中**。

### 8.7 ゲスト参加 ＝ 分離に逆らう機能（A 有利の独立論点）

- ゲスト = **PF ユーザーがエンプライベントに参加**する、境界をまたぐ唯一の正規フロー。
- **A**: 同一 Auth・同一 DB で自然に実装できる。
- **B / B′ / C**: 「PF ユーザーはエンプラにログイン不可・専用ゲストアカウント作り直し」（`01_再設計` §ゲスト、`再検討.md` §6.3）という **UX 劣化を伴う再設計**が必須。
- → §2 の A メリットとして独立計上に値する。**重要度: 高**。

### 8.8 ログ・調査の分離

- **A**: Cloud Logging に PF とエンプラのログが混在。エンプラ顧客のインシデント調査でノイズが多い。
- **B**: ログが Project 単位で分離 → 調査が速く、顧客開示も切り出しやすい。**重要度: 中**。

### 8.9 BigQuery / 分析基盤（A 有利）

- **A**: Firestore→BigQuery エクスポートが**混在データセット**。全社横断分析は楽。
- **B**: データセットが分かれ、エンプラ単体分析は素直だが PF×エンプラ横断は要結合。
- → §2.4（横断分析）の裏返しで **A 有利方向**。**重要度: 中**。

### 8.10 base / common の依存逆転クリーンアップ（両面）

- AGENTS.md が認める「`base` が `user` 等に依存逆転」している箇所。
- **B**: プロジェクト分割が**依存整理（`functions_base` 抽出・層分離）を強制**する。短期はコスト、長期は設計健全化のドライバ。**重要度: 中（両面）**。

### 8.11 Stripe / 決済設定の分離

- エンプラは「企業請求一本化」、PF は「個人クレカ決済」（`01_仕様概要`）。
- **B**: Stripe アカウント・Webhook・鍵を Project 単位で分離でき、決済設定の混線を防げる（`stripeWebhook.ts` の責務分離にも寄与）。**重要度: 中**。

## 10. IdP マルチテナンシー前提での再評価（2026-06-18 追記）

§1〜§9 は「IdP を入れるか」も含めた A vs B の比較だった。本節は **IdP マルチテナンシーを導入前提に固定**したうえで、改めて Project 分離の要否を再評価する。[ADR-002_IdP採用とゲスト方針.md](./ADR-002_IdP採用とゲスト方針.md) で IdP を end-state として採用する方針を確定したことを受けた追補である。

### 10.1 前提の変化：IdP は「Auth 層だけ」を解決する

IdP マルチテナンシーが解決するのは **Auth 層に限定**される（§5.1・§198）。比較軸は「A vs B」から **「IdP込みA」vs「IdP込みB」** に変わり、両者の差分は **Auth 層を除いた残り全部**になる。重要なのは、IdP を入れた時点で **B 本来の最大の売りだった Auth 混在解消（#11・#12）が A でも手に入る**点。したがって B を選ぶ動機はデータ層・インフラ層・事業層へ移る。

| 層 | IdP マルチテナンシーで解決するか |
|:--|:--|
| Auth 層（混在解消・越境ログイン遮断・同一メアド衝突） | ✅ ほぼ解決（§198） |
| データ層（blast radius・スキーマ分岐・スケール予算） | ❌ 単一 DB のまま残る |
| インフラ/運用層（可用性/障害分離・監査・原価・IAM・ログ） | ❌ 単一 Project のまま残る |
| デプロイ独立（functions レベル） | ✅ A で軽減可（選択的デプロイ/マルチ codebase・§8.2・§3.3 注） |

→ **IdP 込みで残る B のメリット = §8.12 ②③④のうち、可用性/障害分離 SLA（§8.1）・監査スコープ（§8.4）・原価可視化（§8.5）・IAM（§8.6）・ログ分離（§8.8）・Stripe 分離（§8.11）・スキーマ分岐（§4.1）**。Auth 系（#11・#12）は IdP に、**Functions デプロイ独立（#19）は A の選択的デプロイ（§8.2）に吸収される**。つまり「IdP＋選択的デプロイ込みの A」に対し B が固有に上乗せするのは、**Project/DB 単位でしか割れないもの（可用性・監査・原価・IAM・ログ・データ物理隔離）に絞られる**。

### 10.2 データ層分離の正体：「スキーマ衛生」と「物理隔離」は別物

「PF とエンプラの仕様が乖離し別物データが混在する」懸念に対して、**DB 分離は的外れ**である。データ層分離は2つの異なる関心事が混ざっている。

| 関心事 | 正体 | 分離が正しい手段か |
|:--|:--|:--|
| スキーマ乖離・別物データの混在 | コード/型の衛生問題 | ❌ DB 分離は的外れ |
| 物理的隔離（blast radius・リージョン・スケール予算・原価） | インフラの問題 | ✅ DB 分離が唯一の手段 |

§163 のとおり Project/DB を分けてもスキーマは自動で分かれない。逆に **単一 DB でもスキーマは分岐できる**（専用コレクション＋discriminated union、§169-170）。エンプラ専用データ（`/enterprises`・`/audit_logs`）は既に別コレクションで、optional 汚染は `events`/`users` の共有コレクションでのみ発生する。**「混在が気持ち悪い」だけが理由ならデータ層分離の優先度は高くない**。

### 10.3 DB 分離が本当に効く「後悔シナリオ」と B″ / B′ という段階的手段

DB 分離が「やっぱりやっておけば」になるのは、スキーマではなく **後から変えられない/移行が激高なインフラ制約**に当たったとき。可逆性で並べると、Auth（IdP・無停止）＜コード/functions 構造（いつでもリファクタ可）＜ **データ（Firestore）＝後悔の本丸**。

| # | 後悔シナリオ | 効き | 向く手段（§4 トリガー） |
|:--|:--|:--|:--|
| 1 | データレジデンシー / 海外展開 | ★最も不可逆 | B″ / B′ / B（DB または Project 新規＋移行） |
| 2 | 大口顧客が物理分離をハード要件化 | 高 | D（Silo）。B″ / B′ では契約「専用 Project」が通らない場合あり |
| 3 | インシデント時の blast radius | 中〜高 | **B″**（PF↔エンプラ の同時露出を遮断）。企業間も要るなら **B′** |
| 4 | Firestore のハード上限（複合インデックス 200/DB 等） | 中 | **B″**（PF とエンプラで予算を 2 分割）。企業ごとに要るなら **B′** |
| 5 | カーブアウト / 事業売却 / 分社 | 中〜高 | B / C（Project 単位の切り出し） |
| 6 | エンプラ ARR が PF を超え主力化 | 高 | B / B″ / B′（可用性・原価・監査独立の段階） |

**安全網**: shokujii は全 doc・Storage パスに `enterprise_id` 付与済み（§2.6・§9.4.1）で「後付け地雷」を回避済み。「今は分けず、必要時に分ける」出口が開いている。

**B″ / B′ の位置づけ（いずれも MVP 不採用）**:

- **B″**: Auth/IAM/課金を単一 Project に保ったまま **PF↔エンプラ だけ**を named database で物理分離。シナリオ 3・4 で **企業間隔離まで要らない**場合の **B′ より軽い**移行先。`sandbox ×2` 不要・2nd Firebase App 不要（§5.3）。
- **B′**: 同上の運用 1 系統を保ちつつ **企業間**まで DB 単位で隔離。運用者 IAM・Rules blast radius を企業単位に縮小（§5.2）。
- いずれも **partner 横断の複雑化（§10.6）は B と同様に残る**（データ境界由来。B″ は 2 DB、B′ は N DB）。Project 分離（B）まで行かない限り、2nd App コストは B″ / B′ では不要。

「データ層分離」だけが目的なら B 全面より **B″ → B′ → D** の順で段階的にエスカレートするのが筋。

### 10.4 大幅乖離（別プロダクト化）シナリオの扱い

「コミュニティ廃止・events のみ」「社内 SNS・エンゲージメントサーベイなど PF に無い概念」のような**大幅乖離**でも、**新規エンプラ専用コレクションの追加自体は DB 分離のトリガーにならない**。PF が一切触らない専用コレクション（`/enterprise_posts`・`/surveys`）は単一 DB で最もクリーンに収まる（§157・§169）。optional 汚染は共有コレクションでのみ起きるため、新概念は PF を汚さない。

効くのは新概念そのものではなく、**それが「エンプラ＝別プロダクト化」のシグナル**である点（§9 マルチプロダクト化）。§164 のとおり、共有面が消えるほど「1 Project で同居させる根拠（コード再利用・単一横断 read）」が蒸発し、同居コスト（境界ガード・blast radius・デプロイ結合）だけが残る。

**決定変数は新コレクションの数ではなく次の2点**：

1. PF と本当に共有し続けるのか（共有面が縮小し続けるか）
2. partner はエンプラの events を横断 read し続けるのか（A 最大優位 #1・#8 が生きるか）

この2点が No に傾くほど分離（少なくともコード/functions、状況により B）の正当性が上がる。逆に partner 横断が中核に残るなら、A 最大優位が生き続け、分離は partner を cross-project 化する逆風になる（§10.6）。

### 10.5 前提条件と確定結論（2026-06-18）

意思決定の入力として、次を確定した。

- **大幅乖離（SNS・サーベイ中心化、コミュニティ廃止）は可能性レベル**（確定ロードマップではない）
- **partner（飲食店連携）はエンプラの中核に残る**

→ §10.4 の決定変数が両方とも A 寄り（partner 横断が生きる・乖離は仮説）。したがって **A（単一 Project）＋ IdP ＋ 徹底モジュール分離**が筋。「共有に賭ける」は合理的だが、賭けるのは **partner 接触面の共有**であって、エンプラ専用機能まで共有することではない。

**共有 / 分岐の境界規則（引っ張られすぎを防ぐ）**: スキーマ検討時に「共通化前提」へ過剰に引っ張られるリスクは、線引きの言語化で防げる。基準は「**partner が触るか**」。

| 面 | 方針 | 理由 |
|:--|:--|:--|
| partner が横断 read する面（`events` 本体・`menus`・`member_orders`） | 共有・安定を維持 | 分岐させると partner が 2 形を扱い A 最大優位（§2.1）を失う |
| エンプラ専用面（communities 相当・管理画面・将来の SNS/サーベイ） | 分岐を明示的に許可（専用コレクション＋discriminated union） | PF が触らないので分岐しても波及しない（§169） |

### 10.6 後で分離する場合のコスト：データ移行より partner cross-project 化が本体

将来 A → B を選んだ場合、**「行のコピー」は軽いが、それは移行コストの主役ではない**。

- **軽い部分**: `enterprise_id` 付与済みのため抽出は機械的（`enterprise_id` で引いて新 Project へ書く）。sandbox はデータ削除前提（`01_再設計` 冒頭）。純粋なコピー＋検証で **1〜3 週間規模**。
- **重い部分（本体）**: 分離が **partner を cross-project 化**する設計変更。エンプラ event は `partner_id` / `community_account` で PF 側店舗を指すため、分離後この参照がプロジェクト跨ぎになる。本番にライブ顧客がいる状態ではデュアルライト/カットオーバー/整合検証が必要で **月単位**（§3.6 の実体）。

**partner cross-project 化で具体的に壊れる点**（現状はすべて単一 DB の `collectionGroup` 1 クエリで成立している）：

現状のイベント一覧は `collectionGroup('events')` を `partner_id` / `community_account` で絞るだけで PF・エンプラを1クエリ混在取得する。

```54:68:base/src/stores/eventList.ts
          const count = (await getCountFromServer(q)).data().count
```

分離後はこれらが次のように壊れる。

| # | 壊れる点 | 内容 |
|:--|:--|:--|
| ① | collectionGroup が片方の Project しか見ない | PF・エンプラ両方担当の partner は **2 Project に別クエリ＋手元マージ**。`IncrementalLoader` の `totalCount` / `startAfter` ページネーション（`eventList.ts`）も和集合では成立せず作り替え |
| ② | 2 つ目の Firebase App＋認証配線 | クライアント SDK は 1 App = 1 Project。partner フロントで **2 つ目の App 初期化＋エンプラ Project 認証**（custom token）が必要 |
| ③ | member_orders 購読が Project 跨ぎ | `onSnapshot(collectionGroup('member_orders'))` は 1 Project 内限定。`useEventStore` を **Project 認識（db ハンドル DI）** に変更 |
| ④ | メニューコピー（PartnerMenus → EventMenus）が cross-project write | 店舗メニューは PF、エンプラ event の `menus` は エンプラ Project。**クライアント batch/transaction 不可** → 両 Project アクセス可の Function 経由（§3.4）で**原子性喪失** |
| ⑤ | 予約承認・ステータス更新も function 経由へ | partner のエンプラ event/注文更新が cross-project write になり関数化＋権限設計 |
| ⑥ | Rules が跨いで検証できない | エンプラ Project の Rules は PF Project の doc を `get()` できない。整合検証を function へ移設 or 非正規化 |
| ⑦ | ローカル開発・テストが単一 emulator で再現不可 | `singleProjectMode`（§2.2）が崩れ 2 emulator 連携が必要。E2E も 2 Project に |

severity は **「1 partner が PF とエンプラ両方の event を担当する度合い」** に比例する。partner が PF 専用/エンプラ専用にきれいに分かれていれば ①③⑤ は稀になるが、**④ のメニューコピー（店舗とメニューは PF 側、event はエンプラ側）は構造的に必ず跨ぐ**。

→ 緩和策: 将来の分離に備え、せめて **`base` の event/注文系ストアを Project 非依存（db ハンドル DI）に寄せておく**と分離コストが下がる（`06` の DI 方針と整合）。

> **※ v0.2 / MVP での扱い（2026-06-18 決定）**: 本緩和策（`base` ストアの Project 非依存・db ハンドル DI 化）は **A 継続のため MVP ではタスク化しない**。将来 **B″ / B′ / B 移行トリガー（冒頭 §4）** が発火した時点で実施する。`06`/`08` のタスク一覧には含めない（過剰投資を避けるため）。なお `06` で進める `if==enterprise` の DI 化（PA-30/31）は「B 移行の地ならし」として別途実施するが、それは `base` の **分岐除去**であって、ここで言う **Project（db ハンドル）非依存化**とは別物。
