## 確定方針（2026-06-18）

本書の検討を経て、以下を確定した。詳細根拠は各節を参照。

1. **製品の核は「クローズド（社内専用の安心感）」**。企業横断の「オープン交流」は将来の別機能として温存（§6）。
2. **IdP（Identity Platform マルチテナンシー）を end-state として採用**。理由: ①Auth 混在を構造的に解消、②同一メアド衝突が消える（§4）、③**企業別 SSO（テナント単位の SAML/OIDC）への唯一の正道**（§1.5）。
3. **移行コストの非対称性**から、IdP の**認証モデル（テナント onboarding・メアド検索のテナント化）だけ v0.2 に前倒し**。ゲストフロー・SSO・UI は後続（§7。`06` の「IdP 丸ごと Phase 2」は本方針に反映済み）。
4. **ゲスト身元は「デフォルトプール固定」**（PF版 uid を使い、テナントに入れない）。`allow_guest` イベントだけを Security Rules の例外で開ける**「意図的な扉」**とする（§3・§5・§6）。これによりクローズド既定とオープン交流（将来）の両立を、追加実装だけで安価に保てる。

## 0. 結論（早見）

| 論点 | IdP **なし**（現状・単一 Auth） | IdP **あり**（テナント分離） |
|:--|:--|:--|
| ゲスト参加 | **PF版アカウント（同一 uid）のまま**ゲスト注文できる（現行 `04_ゲスト参加` がこの設計） | **ゲストはデフォルトプール（PF版 uid）で参加**（従業員はテナント）。確定方針 §3 |
| 同一メアドで PF版併用（従業員） | **不可**（1 メアド = 1 uid）。PF版に先在すると CSV 作成エラー → PF版メアド変更等で対応 | **可**（テナントごとに uid 名前空間分離。衝突が構造的に解消） |
| PF版にエンプライベント表示 | MVP では非表示（`enterprise_id == null` 除外）。将来 G-1: `allow_guest && publish_scope === 'public'` で PF 発見面に掲載、詳細・注文は Enterprise URL | 同上 |
| 企業別 SSO（企業Aだけ Microsoft 等） | 不可（テナント単位の IdP 設定ができない・§1.5） | **可**（テナントごとに独立した SAML/OIDC を設定。§1.5） |

**要点**: ゲスト参加（PF版ユーザーが境界を越えて参加するフロー）と IdP テナンシー（境界を構造的に分離する仕組み）は思想が逆方向だが、**ゲスト身元をテナントではなくデフォルトプールに置けば両立できる**（従業員＝クローズド、ゲスト＝`allow_guest` の扉だけ開く。§3）。「IdP ＝ゲスト不可」ではなく「**ゲストをテナントに入れようとすると詰まる**」が正確（§2）。

## 1. 前提（現行のゲスト参加・認証モデル）

- **ゲストの定義**（`04_ゲスト参加` 1.1）: 就活生・外部パートナー等、`user_type` が `platform`（または未設定）で **`enterprise_id` claim を持たない** PF版ユーザー。イベント単位でのみ参加し、コミュニティメンバーにはしない（`EventMember.is_guest = true`）。
- **ゲスト認証**（`04_ゲスト参加` 2.4）: Enterprise アプリのログイン画面に「ゲストの方はこちら」を設け、**PF版相当の認証（メール+OTP / SNS）**を提供。**PF版の `requestEmailLogin` / `confirmEmailLogin` を流用**し、custom claims は付けない。→ つまり **PF版と同じ Firebase Auth uid をそのまま使う**前提。
- **メアド一意性**（`04_認証` 4-2 / 5.4）: MVP は 1 メアド = 1 アカウント。CSV 作成時に PF版と同一メアドが存在すると**エラー**。`getUserIdFromEmail` がプロジェクト全体検索のため衝突する。
- **PF版露出**（`04_ゲスト参加` G-1 / [02_アーキテクチャ](../10_仕様/02_アーキテクチャ.md)）: MVP マージでは PF クエリに `enterprise_id == null` を必須化しエンプラ doc を除外する。将来 G-1 では `allow_guest == true` かつ `publish_scope === 'public'` のイベントのみ PF 一覧に掲載する（クエリ B）。PF は**発見面のみ**、詳細・注文・認証は **Enterprise URL** 上で完結する。

## 1.5 企業別 SSO とマルチテナンシーの関係（IdP 採用の決め手の一つ）

「企業A だけ Microsoft（Azure AD / Entra ID）でログイン」のような**企業別 SSO** は、認証基盤の段階で実現可否が決まる。

| 前提 | できること |
|:--|:--|
| **素の Firebase Auth**（現状・無料） | Google / Apple 等のソーシャル + メール+OTP のみ。**SAML/OIDC（企業 IdP 連携）は不可** |
| **Identity Platform（テナントなし＝プロジェクトレベル）** | SAML/OIDC の設定は**可能だが全社共有（グローバル）**。「企業A だけ」を**構造的に分離できない**（アプリのロジックで無理やり出し分けるしかなく、社数が増えると破綻） |
| **Identity Platform（マルチテナンシー）** | **テナントごとに独立した SAML/OIDC プロバイダ**を持てる。企業A=Azure AD、企業B=Okta、企業C=OTP のみ、を**綺麗に分離**して実現 |

- 結論: **企業別 SSO をまともにやるにはマルチテナンシーが事実上必須**。
- 含意: SSO は **Identity Platform へのアップグレードが前提**（素の Firebase Auth では不可）。IdP を入れる＝SSO への道が自動的に開く。これが「中長期で困らない」観点で IdP を end-state に選ぶ強い理由（確定方針 §1.5）。

## 2. 技術的な核心 — なぜ「ゲストをテナントに入れる」と詰まるか

ポイントは **「エンプラアプリの Firebase Auth インスタンスは `auth.tenantId` を 1 つしか持てない」** こと。

- IdP で従業員をログインさせるには、エンプラアプリ起動時に `auth.tenantId = <企業テナント>` を設定する（`06` PA-03a）。
- すると、その Auth インスタンスは**そのテナント内ユーザーしか認証できない**。PF版 uid（＝プロジェクトレベル / デフォルトプール）は、このテナントコンテキストでは**ログインできない**。
- 一方、現行ゲスト設計は「**同じエンプラアプリ上で PF版 uid をそのまま使う**」前提。
- → 結果として「**同一アプリ・同一 Auth インスタンス上で、テナント従業員（テナント uid）とゲスト（テナント外 uid）を同時に扱う**」ことになり、IdP テナンシーと正面衝突する。これが `03` §8.7「ゲスト参加＝分離に逆らう機能」の実体。

**補足（誤解しやすい点）**: バックエンド（Functions）は障害にならない。Admin SDK はテナント / デフォルトプールを横断操作できるため、注文確定処理自体はどちらでも動く。**詰まるのはクライアントのログインコンテキストと Security Rules**。

## 3. ゲストの実装方式 — 「デフォルトプール固定」を採用（確定）

IdP を入れる場合、ゲスト身元の置き方は 2 択になる。**本プロジェクトは選択肢B（デフォルトプール固定）を採用**する。理由は「クローズド既定とオープン交流（将来）を両立でき、将来の手戻りが最小」だから（§6）。

### ✅ 採用：選択肢B（ゲストはデフォルトプール固定・PF版 uid）

| 観点 | 内容 |
|:--|:--|
| 認証 | ゲストは**プロジェクトレベル（テナントなし）のデフォルトプール**で認証し、**PF版 uid をそのまま使う**。テナントには入れない |
| 従業員との関係 | 従業員＝テナント（クローズド）、ゲスト＝デフォルトプール、と**身元の置き場で役割を分離**（`request.auth.token.firebase.tenant` が null か否かで判別可能） |
| Security Rules | テナントを持たない認証ユーザーは、**`allow_guest == true` のエンプライベントと自分の member/order ドキュメントのみ** read/write 可、という例外を明示的に切る（現行 Rules は `enterprise_id` claim ＋ `allow_guest`。`04_ゲスト参加` §8 を拡張） |
| ゲスト導線 | **PF版 = 発見面のみ**（将来 G-1 で一覧掲載）。詳細・注文・認証は **Enterprise アプリ（Enterprise URL）** 上で完結する。ゲスト uid はデフォルトプール（§3）。IdP 下では Enterprise 側で secondary Firebase app 等によりデフォルトプール Auth を扱う |
| メリット | ①PF版 uid 再利用で UX 劣化なし ②**オープン交流（将来）が「Rules 例外＋PF 一覧クエリ B 追加」だけで安価に開ける** ③従業員のクローズド境界は不変 |
| コスト | エンプラアプリ内でゲスト（デフォルトプール）を扱う場合は tenant あり/なしの二重 Auth コンテキストが要る（secondary Firebase app 等） |

### ❌ 不採用：選択肢A（ゲストも企業テナントに所属＝テナント内ゲスト）

| 観点 | 内容 |
|:--|:--|
| 概要 | テナント内に動的にゲストアカウントを作る（PF版に同メアドがあっても別 uid で作り直し＝別人格） |
| 不採用の理由 | **オープン交流（将来）の芽を摘む**。ゲストがテナント縛りになると、PF版表示・企業横断参加に作り変える際に**ゲスト身元の再設計**が必要になり高コスト |
| 補足 | 「純クローズドに振り切り、オープン交流を完全に捨てる」なら A も成立する（就活生がメアド+OTP で即作成でき軽い）。ただし本プロジェクトはオープン交流を**温存**するため B を採る |

## 4. 同一メアド併用（IdP で"向き"が逆転する）

| | IdP **なし**（現状・単一 Auth） | IdP **あり**（テナント分離） |
|:--|:--|:--|
| メアドと uid | **1 メアド = 1 uid**（プロジェクト全体で一意） | **テナントごとに uid 名前空間が分離**。同一メアドでも別アカウント |
| PF版に同メアドが先在する場合 | CSV 作成が**エラー**（`04_認証` 4-2 / 5.4）。対応は PF版メアド変更 or Phase 2「昇格フロー」（`04_認証` 補足 §F） | **自然に共存可**（PF版アカウントとエンプラアカウントが別物として並立） |
| 関連コード | `getUserIdFromEmail` がプロジェクト全体検索（衝突の温床） | テナントスコープ検索に変更（`06` PA-02e） |

→ ユーザー懸念「IdP を入れない場合、同じメアドで PF版を使えない（過去に PF版で作成済みなら PF版メアド変更等で対応）」は**正しい**。そして **それを構造的に解消するのが IdP 導入のメリット**（`06` §1・`03` §5.1）。

## 5. 「PF版にエンプライベントを表示」の整理（露出ポリシーの話）

- これは **IdP の有無で決まる話ではなく、データ露出ポリシーの独立判断**。
- 現行方針（MVP）: エンプライベントは **PF版トップ／一覧には表示しない**。PF版クエリ A に `enterprise_id == null` を必須化（[02_developmentマージ](../00_計画/02_developmentマージ.md) §2.2）。
- 将来（G-1）: `allow_guest == true` かつ `publish_scope === 'public'` のイベントを PF 一覧に掲載する（クエリ B）。別フラグ（`site_targets` / `enterprises/{}`）は**不採用**。
- IdP を入れなくても「出さない」ことは可能。逆に「出す」ことも事業判断としては可能。
- **IdP あり でも、ゲストをデフォルトプール（§3 採用）に置けば PF 発見面への掲載＋ PF版 uid のまま Enterprise URL 上でゲスト注文完結が可能**。テナント境界は従業員データだけを守り、ゲストはデフォルトプール文脈なので影響を受けない。

→ かつて「IdP ありだと PF版 uid のままゲスト注文は不可」としていたのは、**テナント固定のエンプラアプリ内でやろうとした場合**の話。Enterprise 側でデフォルトプール Auth（secondary app 等）を扱えば、IdP の有無に関わらず実現できる。

### 5.1 オープン交流（将来機能）の実装イメージ

IdP（従業員＝テナント）の上で、`allow_guest` イベントだけを外部に開ける「意図的な扉」。**構造的トンネルではなく、企業が明示的に開けたオプトインの扉**にするのがポイント。

| 要素 | 実装 |
|:--|:--|
| ① ゲスト身元 | **デフォルトプールの PF版 uid を使う**（テナントに入れない）。§3 採用方針 |
| ② PF版に表示 | クエリ A（`enterprise_id == null`）に加え、クエリ B（`allow_guest == true` かつ `publish_scope === 'public'`）を PF トップで取得しクライアントマージする。カードリンクは Enterprise URL（新タブ）。[04_詳細_ゲスト参加](../10_仕様/04_詳細_ゲスト参加.md) §2.1 |
| ③ PF版アカウントで参加 | Security Rules に明示例外: テナントを持たない認証ユーザーは `allow_guest == true` のエンプライベントと**自分の** member/order のみ read/write 可 |
| ④ 注文・決済 | 既存 `04_ゲスト参加` のゲスト分岐（`is_guest`・`monthly_usage` 非加算・請求書回収）をそのまま流用 |
| ⑤ 従業員データ | テナント側で完全クローズドのまま。開く扉は **`allow_guest` イベントだけ**（オプトイン） |

- 純クローズドを望む企業は `allow_guest` を使わない／`publish_scope: 'public'` にしないだけでよい。
- これは**追加実装（②③）だけで開けられる**ため、v0.2 で無理に作らず将来機能として温存できる（§3 採用＝デフォルトプール固定にしておく前提）。

## 6. 設計判断（確定済み / 残課題）

**確定済み**

1. ✅ 製品の核は**クローズド**。オープン交流は将来の別機能として温存（§5.1）。
2. ✅ IdP（Identity Platform マルチテナンシー）を **end-state として採用**（§1.5 SSO・§4 メアド衝突解消が決め手）。
3. ✅ ゲスト身元は**デフォルトプール固定**（§3 選択肢B）。テナント内ゲスト（選択肢A）は不採用。
4. ✅ オープン交流は **`allow_guest` イベントだけを開けるオプトインの扉**として将来追加（§5.1）。
5. ✅ PF 掲載条件: **`allow_guest == true` かつ `publish_scope === 'public'`**（イベント単位。別フラグ不採用）。
6. ✅ ゲスト導線: **PF = 発見面のみ**、詳細・注文・認証 = **Enterprise URL**（[04_詳細_ゲスト参加](../10_仕様/04_詳細_ゲスト参加.md) §2.2）。

**残課題（着手時に詰める）**

1. `allow_guest` に対する **Security Rules のテナント例外**の具体設計（no-tenant ユーザーの read/write 範囲を `allow_guest` イベント＋本人ドキュメントに限定）。
2. IdP 下での **Enterprise アプリ内デフォルトプール Auth**（secondary Firebase app 等）の具体実装。
3. 既存課題: **PF版の「アカウント作成 / ログイン入口の分離」**（未登録メールに即 OTP を送り `confirmEmailLogin` で `createUser` してしまう。`functions/default/src/user.ts`）。IdP 採否と独立に要対応で、エンプラ誤ログイン・誤作成の温床。別タスクで起票する。

## 7. v0.2 段階適用との対応（`06` §5.1 に反映済み）

確定方針 §3 により「IdP 丸ごと Phase 2」ではなく、**移行に敏感な認証モデルだけ前倒し**する。理由は移行コストの非対称性（sandbox がデータ削除可能な今が最安。本番に企業ユーザーが積まれると移行＋テストが重い）。

| フェーズ | 本書に関係する内容 |
|:--|:--|
| Phase 0〜1（v0.2 で前倒し・移行に敏感） | IdP の**認証モデル**: テナント onboarding（`06` PA-01d / PA-02a/d）・`getUserIdFromEmail` のテナントスコープ化（PA-02e）・`enterprise_id ↔ tenantId` 1:1 設計。PF版露出は [02_developmentマージ](../00_計画/02_developmentマージ.md) §2（`enterprise_id: null` materialize）、越境ログイン抑止は `06` (b) ルートガード（PA-03d） |
| Phase 2 以降（移行に鈍感） | ゲスト参加フロー（§3・デフォルトプール）・企業別 SSO（§1.5）・オープン交流の扉（§5.1）・UI リッチ化 |

> **`06` へ反映済み**: `06` の §1 / §5.1 / §6 を本書の確定方針に合わせ、「認証モデルは Phase 0〜1 前倒し、ゲスト/SSO/UI は Phase 2」へ更新済み。
