# shokujiiエンタープライズ版 仕様概要書

> **原典**: `90_アーカイブ/v0.1原典/01_仕様概要.md` を v0.3 差分・ADR で現行化。

## 概要
- 中規模企業（100名~300名）・大企業（300名〜）に対して、shokujiiの社内専用サイトを構築・提供する
- 社内におけるコミュニケーション活性ツールとして導入。お昼の福利厚生としつつ、社内の偶発的なコミュニケーションを誘発する
- 福利厚生として導入する前提のビジネスモデル（詳細は `02_課金設計`）
    - 初期費用: 無料
    - お試し: 3ヶ月間プラットフォーム利用料無料
    - 月額（企業）: 有効アカウント 500円/件（停止中は0円）
    - 従量（企業）: 食事補助・ゲスト無料分など実費の取次（マージンなし、`04_請求`）
    - 送客手数料（飲食店）: エンプラ経由注文に対し別途実施予定

## 前提

## プロジェクト
- これまで開発してきたものを「shokujiiプラットフォーム版」と呼び、企業向けを「shokujiiエンタープライズ版」と呼ぶ
- 「コミュニティ作成」「コミュニティ管理」「イベント作成」「イベント参加注文」などの基本機能はshokujiiのプラットフォーム版を踏襲
- baseパッケージのコンポーネントを使用する。userパッケージをコピーして構築する想定

## MVP(Minimum Valuable Product)
- まずは必要最小限の工数でリリースまで漕ぎ着けたい
- ただし、MVPをベースにしつつ、改善アップデートできるように、仕様変更に耐えうる全体設計を行いたい

## ユースケースの想定
- 人事部・総務部・経営部などの特定権限の方が「全社管理者」となる
- 「全社管理者」が「全社設定」や「月額割引額」などを設定する
- 「全社管理者」が「アカウント一括作成」「コミュニティ一括作成」を行う
- 部署ごとなどに「コミュニティ」でイベント作成・管理・予約申請を行う
- **MVP**: 「公開設定」（`is_public: true`）のものは一覧に表示され全社誰でも参加できる。「URL限定」（`is_public: false`）は URL を知るものだけが参加できる
- **Phase 2**: 「公開設定」（`publish_scope: public`）のものは全社誰でも参加できる。「URL限定」（`publish_scope: url`）は URL を知るものだけ。コミュニティ限定（`community`）は一覧表示可・メンバーのみ注文（[04_詳細_イベント管理](./04_詳細_イベント管理.md) §4.1）
- 人事部・総務部の「全社管理者」は毎日開催して、誰でも注文できる状態を作る（**注文0件の公開イベントも参加者トップに表示** — [04_詳細_参加者画面](./04_詳細_参加者画面.md) §2）
- 各部署は、限定公開で毎週定例ランチミーティングを行う。各部署は月1で外部部署からも参加できるオープンな食事会も開催する — **Phase 2**（`publish_scope: community` / `public` の組合せ）で実現
- 一般従業員が部活や社内サークル目的などに「コミュニティ」を作ることもできる（MVP: **作成は全従業員可**、**更新はコミュニティ manager 限定** — PF の update ルールに準拠。**参加は即時** — PF 共有 UI。Phase 2 で `join_type`（承認制）を PF 版と合わせて導入可）
- 従業員は会社負担で利用できる。福利厚生費とする場合、半額自己負担・半額会社負担で、1人月額7,500円(税別)までであれば非課税となる
- 就活生や外部パートナーとの会食にも利用可能（ゲスト参加機能）


## ユーザーロール定義

| ロール | 対象 | 主な権限 |
|:--|:--|:--|
| **全社管理者** | 人事部・総務部・経営部など | 全社設定、アカウント管理、コミュニティ承認、割引設定、ダッシュボード閲覧 |
| **コミュニティ管理者** | 部署リーダー、サークル代表など | コミュニティ内のイベント作成・管理、予約申請 |
| **一般従業員** | 社内ユーザー全般 | イベント参加・注文、コミュニティ参加・作成（要承認） |
| **ゲスト** | 就活生、外部パートナーなど | ゲストOKイベントへの参加・注文（プラットフォーム版ユーザーとして参加） |


## 技術方針

## Firebase構成: 単一Project + テナント論理分離

プラットフォーム版と同一のFirebaseプロジェクトを使用し、`enterprise_id` でテナントを論理分離する。

### 方針の根拠
- MVP工数を最小化できる（企業追加 = Firestoreに1ドキュメント追加のみ）
- 飲食店データ（partners / shops / menus）をそのまま共有できる
- プラットフォーム版の `common` パッケージのスキーマ・ユーティリティを最大限流用できる
- デプロイが1回で済む

### テナント分離の方法
- すべてのエンタープライズ関連ドキュメントに `enterprise_id` を付与する
- Firestore Security Rules で `request.auth.token.enterprise_id == resource.data.enterprise_id` を強制し、他社データへのアクセスを防止する
- ユーザーDocに `user_type`（`"platform"` / `"enterprise"`）フラグを持たせ、プラットフォーム版ユーザーとエンタープライズ版ユーザーを区別する

### コレクション構成（プラットフォーム版との共存）

EventMemberOrder 設計（`07_リファクタリング/05_EventOrder→EventMemberOrder.md`）を前提とする。注文は `members/{userId}/member_orders/{orderId}` に **1 メニュー = 1 ドキュメント** で格納し、Stripe 決済情報は `stripes/{stripeId}` に分離する。

```
/enterprises/{enterpriseId}                     ← 【新規】企業設定・割引マスター（discount_type / discount_value / monthly_limit_per_user）
  /members/{userId}                             ← 【新規】EnterpriseMember（monthly_usage / monthly_order_count）
  /audit_logs/{logId}                           ← 【新規】監査ログ

/communities/{communityId}                      ← 既存構造を踏襲（enterprise_id を追加）
  /events/{eventId}                             ← enterprise_id, enterprise_subsidy_settings を追加（allow_guest, guest_payment は将来実装）
    /menus/{menuId}
    /members/{userId}                           ← EventMember。enterprise_id を追加（is_guest は将来実装）
      /member_orders/{orderId}                  ← EventMemberOrder。1 メニュー = 1 ドキュメント。pay_enterprise_subsidy_amount, enterprise_id を追加
    /stripes/{stripeId}                         ← EventStripe。Stripe 決済セッション単位。enterprise_id, pay_enterprise_subsidy_amount を追加
  /members/{userId}                             ← CommunityMember（既存）
  /invites/{inviteId}
  /letters/{letterId}

/partners/{partnerId}                           ← 既存構造を踏襲（飲食店データ共有）
  /shops/{shopId}
  /menus/{menuId}

/users/{userId}                                 ← 既存構造に enterprise_id, user_type を追加
/users_personal_information/{userId}
```

> **凡例**:
> - 旧 `/communities/{cid}/events/{eid}/orders/{oid}` は廃止。`members/{uid}/member_orders/{oid}` に置き換え
> - 1 注文セッション（カート確定操作）= 複数の `member_orders` ドキュメント + 任意の 1 `stripes` ドキュメント
> - ゲスト判定は `members.is_guest` に配置（`member_orders` 側には持たせない）— **将来実装**（`04_ゲスト参加` 正本）

詳細は [02_アーキテクチャ.md](./02_アーキテクチャ.md) 3章を参照。

### 物理分離（企業ごとProject）について

**単一Projectを選択した理由:**

1. **SaaS業界の標準的なアプローチ**
   - Slack、Notion、Google Workspace 等の主要なエンタープライズSaaSも、単一環境でのテナント論理分離が基本
   - 企業ごとにインフラを分離する方式は、ごく一部の高セキュリティ要件（金融・医療・政府機関向け等）に限られる
   - shokujiiのサービス特性（食事注文・社内コミュニケーション）上、扱うデータの機密度は比較的低く、論理分離で十分なセキュリティを担保できる

2. **飲食店データ共有の問題**
   - 企業ごとにProjectを分離した場合、飲食店データ（partners / shops / menus）を各Projectに同期する基盤が必要になる
   - 飲食店向けの専用Projectを新たに構築し、全企業Projectとのデータ同期を実装する工数が非常に大きい
   - 単一Projectであれば飲食店データをそのまま共有でき、同期基盤の開発が不要

3. **運用・デプロイコスト**
   - 企業ごとにProjectを分けると、Functions / Hosting / Security Rules のデプロイが企業数分必要になる
   - バグ修正1つでもN社分のデプロイが必要となり、運用負荷が企業数に比例して増加する
   - 単一Projectなら1回のデプロイで全企業に反映される

4. **将来の移行パス**
   - すべてのドキュメントに `enterprise_id` を持たせる設計のため、将来的に特定企業のデータのみ別Projectへ移行することは技術的に可能
   - 全企業を一斉に分離する必要はなく、要件が出た企業のみ個別対応できる

**物理分離が必要になった場合の対応方針:**
- 金融・医療系など、コンプライアンス上データの物理分離が必須となる大企業に対しては、別途専用環境として提供することを検討する
- その場合も `enterprise_id` ベースの設計により、該当企業のデータのみを別Projectへ移行可能
- ただしMVPフェーズでは想定しない

## 認証方式

| フェーズ | 認証方式 | 実装 |
|:--|:--|:--|
| **MVP** | Identity Platform マルチテナンシー + 企業メールドメイン + 6桁OTP | テナント onboarding + custom claims（[05_認証・テナント](./05_認証・テナント.md)、[ADR-002](../20_設計判断_ADR/ADR-002_IdP採用とゲスト方針.md)） |
| **Phase 2** | 企業ごとに SSO（SAML/OIDC） | テナント単位 IdP 設定 |

- 特定ドメインのメールアドレスのみログイン可能（従業員）
- SNSログインはエンタープライズ版従業員向けには提供しない
- ゲストはデフォルトプール（PF版 uid）で参加（[04_詳細_ゲスト参加](./04_詳細_ゲスト参加.md)）

## 将来の技術移行に備えた設計指針
- データアクセス層を抽象化し、Firestore への直接依存を最小限にする
- 集計ロジック（ダッシュボードなど）は Cloud Functions に寄せ、フロントエンドからの直接集計を避ける
- `enterprise_id` を一貫して全ドキュメントに持たせ、将来のDB移行時にテナント分離がスムーズになるようにする

    - 注文締切リマインダー（未注文メンバー向け）

    - カート未完了リマインダー
    - 新着イベント通知

    - 注文締切リマインダー（主催者向け・日数ベース）

## 決定事項（検討事項からの卒業）

## ログインについて → 決定済み
- MVP: Identity Platform マルチテナンシー + 企業メールドメイン + 6桁OTP。従業員向け SNS ログインなし
- Phase 2: 企業ごと SSO（SAML/OIDC）

## セキュリティ対策 → 方針決定済み
- **データ暗号化**: MVP では Firebase デフォルトの保存時暗号化で十分。追加の暗号化は Phase 2 以降で必要に応じて検討
- **IPアドレス制限**: MVP では不要。企業メールドメイン制限で十分。Phase 2 以降で必要に応じて対応
- **Firebase構成**: 単一Project + `enterprise_id` による論理分離。物理分離は行わない
- **セッション管理**: **無操作 1 週間**で自動ログアウト（フロントエンド実装）。アカウント停止時は `revokeRefreshTokens()` で即時セッション無効化
- **監査ログ**: MVP から基本的なログ基盤を構築。ログイン、管理者操作、注文の記録を最低限実装する。後付けするとログの欠損期間が発生し大企業への説明で致命的になるため、初期から導入する
- **メール通知**: MVP では最低限（注文確認、イベントリマインダー等）のみ。プラットフォーム版から必要なものを選定
- **メール配信制御**: MVP（D-1）はコード固定デフォルトで PF 不要メールを抑制。全社 ON/OFF 設定 UI は Phase 2。詳細は `04_詳細_メール配信` を参照

## ゲスト参加機能 → 決定済み（MVP 外 / WS-G）
- **MVP（Phase 1）には含めない**。Phase 2 以降（[01_MVP全体計画](../00_計画/01_MVP全体計画.md) WS-G G-1）で実装
- プラットフォーム版ユーザーがエンタープライズ版の「ゲストOK」イベントに参加できる（将来）
- ゲストの決済は「無料参加」「自己負担（全額クレカ）」の2択（実装時）
- ゲストへの割引適用は Phase 2
- 請求先は MVP では全社管理者に一本化（実装時も初期方針）。Phase 2 でコミュニティ管理者の選択に対応

## 支払い方式・決済 → 決定済み
- エンプラ版のイベントでは **2 つの支払い方式**から選択可能
    - **福利厚生割引（enterprise_subsidy）**: デフォルト。企業の割引ルール適用後、残額をクレカ決済
    - **参加者事前決済（user_advance）**: PF版と同じ処理。割引なし
- **主催者請求書払い（community_bill）はエンプラ版では選択不可**。企業請求の一本化（全社管理者への請求）と、PF版固有の10%請求書手数料との混同を避ける（`04_割引・決済` D-13、`02_課金設計` P-13）。コミュニティ manage「請求書」タブ・イベント請求書 PDF 等も非表示（`04_イベント管理` §4.3）
- **当日払い（user_on_day）は deprecated**。PF版でも利用実績なし。エンプラ版では選択不可
- 割引計算ロジックは `enterprise_subsidy` の場合のみ走る
- Phase 2: 給与天引き対応（CSV出力）

## 割引ルール → 決定済み
- MVP: 固定金額割引 + 割合割引の両方に対応。福利厚生費（食事補助）の半額負担ルールに対応するため
- 月額上限あり（ex. 1人あたり月7,500円）。月はイベント開催月に紐づく
- 上限超過後は割引なし（全額自己負担）で注文可能
