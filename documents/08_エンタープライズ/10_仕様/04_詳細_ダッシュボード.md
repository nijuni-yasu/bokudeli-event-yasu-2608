> **原典**: `90_アーカイブ/v0.1原典/` の 04_ダッシュボード を現行化。

本ドキュメントは `01_仕様概要`、`02_アーキテクチャ`、`02_課金設計`、`04_割引・決済`、`04_全社管理者画面` の決定事項に基づき、全社管理者向けダッシュボードの機能仕様を詳細に定義する。

## 2.1 データソース

MVP では **ハイブリッド方式** を採用する（D-2: user_advance を含む全支払い方式に対応）。

| 集計項目 | データソース | 理由 |
|:--|:--|:--|
| 利用人数 | `member_orders` から集計（`user_id` のユニーク数） | 全支払い方式を含む |
| 利用回数（注文セッション数） | `stripes` ドキュメント数 + `audit_logs` の `order_create`（`target_id == null`） | 「カート確定操作の回数」。`member_orders` 件数は 1 メニュー = 1 ドキュメントのため「品数」になり不適（D-9） |
| 注文合計額（税込） | `member_orders` から集計（`Σ menu_price`） | 全支払い方式を含む |
| 自己負担額 | `member_orders` から集計（`Σ (menu_price - (pay_enterprise_subsidy_amount ?? 0))`） | 同上 |
| 企業負担額（補助） | `member_orders` から集計（`Σ (pay_enterprise_subsidy_amount ?? 0)`） | イベント開催月フィルタと一体。D-13 |
| 企業請求見込額（食事） | `member_orders` から集計（`04_請求` §2） | 補助分 + ゲスト無料分（G-1 前は補助分のみ） |

> 「利用回数」を `member_orders` ドキュメント数で取ると 1 メニュー = 1 ドキュメントのため「品数」になってしまう。「ユーザーが体感する注文回数」と一致させるため、`stripes` ドキュメント数（Stripe 経由）+ `confirmOrder` 経由のセッション数（無料 / 全額補助）を使う。

### データソースの選択肢（参考）

| 方式 | データソース | メリット | デメリット |
|:--|:--|:--|:--|
| EnterpriseMember のみ | `monthly_usage`, `monthly_order_count` | 軽量・高速 | enterprise_subsidy のみ。user_advance が含まれない |
| member_orders + stripes（採用） | 後述の Collection Group クエリ | 全項目を正確に集計可能 | 企業内全 `member_orders` のスキャンが必要 |
| monthly_usage コレクション | `/enterprises/{id}/monthly_usage/{yearMonth}` | 月別集計が高速 | **Phase 2**。MVP では未実装 |

### member_orders / stripes のクエリ方法

`member_orders` は `communities/{cid}/events/{eid}/members/{uid}/member_orders/{oid}` のサブコレクション、`stripes` は `communities/{cid}/events/{eid}/stripes/{sid}` のサブコレクションのため、**Firestore Collection Group クエリ** を使用する。

```typescript
// 注文金額・補助額・自己負担額の集計
collectionGroup('member_orders')
  .where('enterprise_id', '==', enterpriseId)
  .where('status', '==', 'ordered')

// 注文セッション数（Stripe 経由）の集計
collectionGroup('stripes')
  .where('enterprise_id', '==', enterpriseId)
```

- `enterprise_id` を含む複合インデックスを `firestore.indexes.json` に追加する（02 全体構成 6.5 参照）
- イベント開催月で絞る場合: `member_orders` 取得後、各 order の `event_id` から events を参照し、`event_start_datetime` の年月でフィルタする（`04_割引・決済` と同様に、`member_orders` に `event_month` は持たせない方針）

### `confirmOrder` 経由の注文セッション数

`stripes` ドキュメントは Stripe 経由の決済時にしか作成されない（`04_割引・決済` 6.3 参照）。無料 / 全額補助で `confirmOrder` 経由で確定したセッションは `stripes` を持たないため、別途カウントが必要。

| 方式 | 内容 |
|:--|:--|
| A. 監査ログから | `audit_logs` の `action == 'order_create' && target_type == 'order_session' && target_id == null` をカウント（`confirmOrder` 経由で `stripes` を持たないセッション。Stripe 経由は `target_id` に `stripes` ドキュメント ID が入る。`04_監査ログ` 4.2 の使用例と整合） |
| B. members.monthly_order_count から | 「カート確定回数」ではなく「ordered な member_orders 件数」になるため不適 |
| C. 専用フィールドを追加 | `EnterpriseMember.monthly_session_count` を新設（Phase 2） |

**MVP の採用案: A（監査ログから）**。`audit_logs` の集計は `enterprise_id` で絞り込めるため、Functions で軽量に取得できる。

**監査ログ依存の注意**: 監査ログは `04_監査ログ` のとおりベストエフォートで欠損しうる（例: 書き込み直前の異常終了）。MVP の「利用回数」で A を採用する場合、数値が実態より少なく見える可能性を許容し、Phase 2 の月次再集計（`04_割引・決済` 3.6）や専用カウンタ（上表 C）で補正する想定とする。

### イベント開催月への帰属（stripes / audit_logs）

期間選択（開始月・終了月）は **イベント開催月**（`event.event_start_datetime` の YYYY-MM）基準とする。決済日（`audit_logs.timestamp`）ではない。

| ソース | 帰属の求め方 |
|:--|:--|
| `member_orders` | 各 order の `event_id` → events をバッチ取得 → `formatYearMonth(event_start_datetime)` |
| `stripes` | 各 stripe の `event_id` → 同上 |
| `audit_logs`（`target_id == null`） | `details.order_ids` の先頭 order 等から `event_id` を解決 → 同上。ログに `event_id` は持たない |

Functions 実装では N+1 を避けるため、orders / stripes / audit から必要な `event_id` をユニーク化し、events をバッチ get する。

| 項目 | タイミング |

| EnterpriseMember の更新 | `confirmOrder` / `stripeWebhook` 時にリアルタイム更新（`04_割引・決済` で定義済み） |

## 2.3 集計対象の注文

| 条件 | 含める |
|:--|:--|
| 支払い方式 | `enterprise_subsidy`, `user_advance` |
| ステータス | `ordered` のみ（`in_cart`, `canceled` は除外） |
| ゲスト注文 | **利用統計（D-3）では含めない**（`members.is_guest == false` の注文のみ）。**MVP**: `is_guest` 未導入のため **スキップ可**。G-1 後にフィルタを有効化。**企業請求見込額**は G-1 後にゲスト無料分を含む（`04_請求` §2） |

ゲスト参加（G-1）導入後は、**利用回数・利用人数・注文合計額・自己負担額**の集計時に `members.is_guest == true` のメンバー配下の `member_orders` を除外する（D-3）。**`enterprise_billing_amount` 列はゲスト無料分を含む**（`04_請求` §2）。

> ゲスト判定は `member_orders.is_guest_order` ではなく **親 members ドキュメントの `is_guest`** を参照する（02 論点 1.4）。G-1 後に有効化。

### user_advance の注文フィールド

`04_割引・決済` では、user_advance の `member_orders` には `pay_enterprise_subsidy_amount` をセットしないと定義されている。集計時の扱い:

| 支払い方式 | pay_enterprise_subsidy_amount | 注文合計額 | 自己負担額 |
|:--|:--|:--|:--|
| enterprise_subsidy | 設定あり（残枠次第で undefined） | `Σ menu_price` | `Σ (menu_price - pay_enterprise_subsidy_amount)` |
| user_advance | 未設定 | `Σ menu_price` | `Σ menu_price`（全額自己負担） |

> ダッシュボードでは「企業負担額」= `pay_enterprise_subsidy_amount` の合計のみを集計する（D-2 / D-13）。E-4 マイページの当月サマリは `EnterpriseMember.monthly_usage` 直読みだが、イベント開催月キーは同一（`04_割引・決済` §3.1）。

### キャンセルとセッション数（MVP の許容）

| 項目 | 扱い |
|:--|:--|
| 金額・人数 | `status == ordered` の `member_orders` のみ。キャンセル済みは除外 |
| 利用回数（session） | `stripes` ドキュメント + `order_create` 監査ログは **キャンセル後も残りうる** |
| MVP | 上記ズレを許容。Phase 2 の月次再集計で補正 |


# 3. 表示項目

## 3.1 月別集計

| 項目 | 定義 | データソース |
|:--|:--|:--|
| 利用回数 | 注文セッション数 | `stripes` ドキュメント数 + `audit_logs` の `order_create`（`target_type == 'order_session' && target_id == null`。2.1 参照） |
| 利用人数 | ユニークユーザー数 | `member_orders` から集計（`user_id` のユニーク数） |
| 注文合計額（税込） | 補助前の税込合計 | `member_orders` から集計（`Σ menu_price`） |
| 企業負担額（補助） | 企業補助額の合計 | `member_orders` から集計（`Σ (pay_enterprise_subsidy_amount ?? 0)`）。D-13 |
| 自己負担額 | ユーザー支払額の合計 | `member_orders` から集計（`Σ (menu_price - (pay_enterprise_subsidy_amount ?? 0))`） |
| 企業請求見込額（食事） | shokujii から企業へ後請求する食事従量の見込み | ゲスト無料分 + `enterprise_subsidy` 補助分（`04_請求` §2 参照）。**D-3 のゲスト除外は適用しない** |

| プラットフォーム利用料 | 有効アカウント月額 | **確定月**: スナップショット。**当月**: ライブ集計。お試し期間内は 0 |
| 合計請求見込額 | 当月の請求見込み総額 | `platform_fee_amount + enterprise_billing_amount` |
| 確定状態 | 請求確定 / 見込み | `billing_status`: `final` / `provisional`（当月のみ provisional） |

### 月の定義

| 集計項目 | 帰属ルール |
|:--|:--|
| 利用回数・人数・注文合計額・自己負担・企業負担（補助） | **イベント開催月**（`event.event_start_datetime` の年月）。`04_割引・決済` の月額利用実績と同一。ゲスト注文は D-3 で除外 |
| 企業請求見込額（食事） | **イベント開催月**（同上）。ゲスト無料分を含む（`04_請求` §2） |
| 有効アカウント数・プラットフォーム利用料 | **暦月**（`YYYY-MM`）。`02_課金設計` P-7 |

月別テーブルの各行は `year_month` でキーが揃うが、上記2種の帰属ルールが異なる。画面に注記を表示する（文案は `02_課金設計` §5.2）。当月行には **「見込み」** ラベルを付与する。

## 3.2 メンバー別集計

| 項目 | 定義 | データソース |
|:--|:--|:--|
| 利用回数 | 注文セッション数 | `stripes` + `audit_logs` の `order_create`（`target_id == null`。対象期間・当該 user_id に限定） |

## 3.3 グラフの種類

| 用途 | グラフ | 備考 |
|:--|:--|:--|
| 月別トレンド | 棒グラフ | 月ごとの利用回数・金額の推移 |
| 月別内訳 | 積み上げ棒グラフ | 企業負担 vs 自己負担の比率（Phase 2 で検討） |

# 5. パフォーマンス・実装方針

## 5.1 集計の実行場所

`01_仕様概要` の技術方針に従い、**集計は Cloud Functions で行う**。フロントエンドからの直接集計は行わない。

### 理由

| 観点 | Functions | フロント |
|:--|:--|:--|

## 6.2 他ドキュメントとの整合

- **02_全体構成:** `monthly_usage` コレクションは Phase 2 のまま。MVP では使用しない。`enterprise_id` を含む `collectionGroup('member_orders')` / `collectionGroup('stripes')` のインデックスは 6.5 で定義
- **04_割引・決済:** EnterpriseMember の `monthly_usage` / `monthly_order_count` の更新タイミングは `confirmOrder` / `stripeWebhook` 完了時。`monthly_order_count` は「ordered な member_orders ドキュメント数」を意味するため、ダッシュボードの「利用回数」（注文セッション数）とは別概念
- **04_ゲスト参加:** ゲスト注文（`members.is_guest == true`）は**利用統計（D-3）**では集計対象外。**`enterprise_billing_amount`（請求見込み）は `04_請求` §2 に従いゲスト無料分を含む** — **将来実装**
- **04_全社管理者画面:** ダッシュボードは本ドキュメントで詳細化
- **02_課金設計:** プラットフォーム利用料・お試し期間・合計請求見込額。ダッシュボード §3.1 の `platform_fee_amount` 等と連動
- **04_請求:** 企業請求見込額（食事従量）の集計定義（MVP）。ダッシュボード §3.1 の `enterprise_billing_amount` 列と連動
- **04_マイページ・友人:** E-4 利用状況タブ（本人・Firestore 直読み）と役割分担（§1.3）。全社集計は D-2 のみ
- **04_監査ログ:** 「利用回数」の `confirmOrder` 経由セッション数は `audit_logs` の `action == 'order_create' && target_type == 'order_session' && target_id == null` で導出（§2.1 および `04_監査ログ` 4.2 参照）。イベント開催月帰属は §2.1「イベント開催月への帰属」
