# メール配信 詳細仕様

> **原典**: `90_アーカイブ/v0.1原典/` の 04_メール配信 を現行化。

本ドキュメントは `01_仕様概要` および `02_アーキテクチャ` の決定事項に基づき、エンタープライズ版におけるメール配信制御の仕様を詳細に定義する。

## 前提とする仕様書

本ドキュメントは EventMemberOrder 設計（`05_EventOrder→EventMemberOrder.md`）を前提とする。注文関連のメールトリガーは旧 `onOrderChanged`（`orders` コレクションの Firestore トリガー）から、新設計では **`onMemberOrderChanged`**（`member_orders` の Firestore トリガー）に変わる。1 注文セッション = 複数の `member_orders` ドキュメントになるため、注文完了系メールはセッション単位で **1 回だけ送信** する重複防止が必要（02 論点 8.3）。


# 1. 概要

エンタープライズ版では、プラットフォーム版（PF版）と同一の Firebase プロジェクト・SendGrid を利用する。イベント/コミュニティの `enterprise_id` および `/users` の `enterprise_id`（従業員 uid）に応じて、一部のメールを PF版のみに送信し、エンタープライズ版ユーザーには送信しない。

## 1.1 目的

- エンタープライズ版ユーザーに不要なマーケティング・プロモーション系メールを送信しない
- イベント・注文・認証に関連する必須メールは PF版・エンタープライズ版の両方に送信する
- 実装の工数を最小限に抑える

## 1.2 決定事項サマリ

# 3. PF only / PF + Enterprise の判定

## 3.1 判定基準

| 種別 | 説明 | 判定方法 |
|:--|:--|:--|
| **PF only** | プラットフォーム版ユーザーのみに送信。エンタープライズ版では送信しない | イベント/コミュニティの `enterprise_id` が存在する場合は送信スキップ。全ユーザー向け（#20 / #23）は §3.1.1 も参照 |
| **PF + Enterprise** | 両方に送信。イベント・注文・認証に関連する必須メール | `enterprise_id` の有無に関係なく送信 |

### 3.1.1 全ユーザー向けメール（#20 / #23）の判定

イベント文脈がないため、**宛先**と**本文のイベント一覧**で二重に制御する。

**メールアドレスの保存場所（`05_認証・テナント` §0.2）**

| 用途 | 保存先 |
|:--|:--|
| エンプラ認証 lookup の正本 | `/enterprises/{id}/members/{uid}.user_email` |
| 一斉配信（#20 / #23）の宛先取得 | 現行 `getAllUsers(true)` → `/users` + `/users_personal_information`（members 正本は**参照しない**） |

従業員作成時に UPI にも `user_email` を複製するため、**lookup 分離だけでは #20 / #23 から自動除外されない**。D-1 では `getAllUsers` ループ内で `/users.enterprise_id` によりスキップする。

| 制御 | 判定 | 対象 |
|:--|:--|:--|
| 宛先 | `isEnterpriseUser(user)`（`users.enterprise_id != null`）のユーザーをスキップ | #20 / #23 |
| 宛先（後方互換） | `enterprise_id` が **未設定**（`null` / `undefined` / フィールド欠落）のユーザーは **PF 扱い**とし、送信対象に含める | #20 / #23 |
| 本文（#20 のみ） | `createTemplateDataForEventInformation` で `isEnterpriseEvent(event)` のイベントを**一覧から除外** | PF ユーザー向け週刊メールにエンプライベントを載せない |

# 4. 実装方式

## 4.1 方針：共通ヘルパー + 早期リターン（方式 A・採用）

工数を最小限に抑えるため、**方式 A** を D-1 で採用する。

1. **共通ヘルパー**（`isEnterpriseEvent` / `isEnterpriseUser`）を作成
2. **PF only メール**の各送信処理の冒頭、または `getAllUsers` ループ内で、ヘルパーによる早期リターン / `continue` を追加（1 行）

### 4.1.1 検討した代替方式（送る/送らない）

| 方式 | 概要 | メリット | デメリット | D-1 |
|:--|:--|:--|:--|:--|
| **A. 早期リターン** | 各 `sendXxx` / ループ内で 1 行スキップ | 工数最小・差分が局所 | 新メール追加時に漏れやすい | **採用** |
| B. 中央ポリシー | `shouldSendMail(kind, ctx)` を 1 箇所に集約 | Phase 2 全社 ON/OFF と相性◎ | 全経路で `kind` + context が必要 | Phase 2 で B へ拡張可 |
| C. Send ラッパー | `sendDynamicTemplateSafe` 内で判定 | 送信 API 経由なら漏れにくい | 文脈がバラバラ（`getAllUsers` 等） | 不採用 |
| D. トリガー側フィルタ | `pollingTask` 等でエンプラ除外後に呼ぶ | 関数本体が汚れない | 呼び出し元が複数だと二重管理 | 不採用 |
| E. Functions 分離 | `_user` / `_enterprise` codebase（WS-G G-3） | 境界が明確 | 工数大・店舗共有メールの扱いが重い | MVP 外 |

Phase 2 で全社 ON/OFF（§5.3）を入れる際は、方式 A の 1 行を **方式 B** の `shouldSendEnterpriseMail(settings, kind)` 呼び出しに置き換える想定。

### 4.1.2 D-1 スコープ（配信制御のみ）

| 項目 | D-1 | Phase 2 以降 |
|:--|:--|:--|
| 送る / 送らない | §3 のコード固定デフォルト | 全社 ON/OFF（§5.3） |
| 文言・SendGrid テンプレ | **変更しない**（PF テンプレのまま） | 別テンプレ / ブランディング変数（§5.2） |
| 認証 OTP | 既存どおり PF / エンプラ別テンプレ（`user.ts` / `enterprise/auth.ts`） | — |

配信制御（早期 return）と文言変更（テンプレ resolver）は **関心を分離**する。PF only メールは送信自体をスキップするため、テンプレ分岐は D-1 では不要。

## 4.2 共通ヘルパー

```typescript
// functions/default/src/utils/enterpriseMail.ts（新規）または utils/mail.ts に追加

/** エンプライベントか（Event / Community の enterprise_id） */
export function isEnterpriseEvent(event: { enterprise_id?: string | null }): boolean {
  return event.enterprise_id != null
}

/** エンプラ従業員 uid か（/users.enterprise_id。認証 lookup 正本の members とは別） */
export function isEnterpriseUser(user: { enterprise_id?: string | null }): boolean {
  return user.enterprise_id != null
}
```

### 前提条件

- `enterprise_id` はイベント（Event）または親コミュニティ（Community）に持たせる（エンプラ導入時のスキーマ設計に従う）
- `enterprise_id` が `null` / `undefined` の場合は PF版として扱い、送信する（後方互換）

### enterprise_id の配置（方式A 確定）

**方式A（Event へ denormalize）を採用する。** イベント作成時に `community.enterprise_id` を Event にコピーし、`isEnterpriseEvent(event)` を同期関数のまま使用する。

| 方式 | 内容 | ヘルパー | 採用 |
|:--|:--|:--|:--|
| **A. Event に denormalize** | イベント作成時に `community.enterprise_id` を Event にコピー | 同期 `isEnterpriseEvent(event)` | **確定** |
| B. Community から取得 | Event に `enterprise_id` を持たず都度取得 | 非同期 `isEnterpriseEventAsync(event)` | 不採用 |

### 不変条件

Community が `enterprise_id` を持つ場合、配下の **Event / members / member_orders / stripes** にも必ず同一の `enterprise_id` を denormalize する。詳細は `02_アーキテクチャ 3.4` を参照。

| 経路 | 処理 |
|:--|:--|
| イベント作成 / 複製 | `community.enterprise_id` を Event にコピー |
| `addToCart` | Event の `enterprise_id` を members / member_orders にコピー |
| `stripeWebhook` | Event の `enterprise_id` を stripes にコピー |

## 5.3 全社メール通知設定（Phase 2・MVP 外）

**MVP（D-1）では実装しない。** D-1 は §3 の**コード固定デフォルト**のみを `isEnterpriseEvent` / `isEnterpriseUser` で適用する（§4.1.2）。

Phase 2（WS-G）で、全社管理者が `/admin/settings` から**一部メール種別の ON/OFF** を変更できるようにする。詳細 UI・schema は Phase 2 設計時に `04_詳細_全社管理者画面` と合わせて定義する。

### 三層モデル（Phase 2 設計方針）

| 層 | 内容 | 全社設定 |
|:--|:--|:--|
| **Layer 1: プラットフォーム固定** | PF マーケ（#20 / #23 / #6 等）、認証 OTP（#18）、店舗（#14〜17） | **変更不可**（D-1 で常に抑制または PF 共通） |
| **Layer 2: 業務必須デフォルト ON** | 参加者 #1 #2、主催者 #8 #11、コミュニティ #12 #13、店舗 #14〜17 | MVP はコード固定。**Phase 2 でも OFF 禁止**を推奨 |
| **Layer 3: 全社設定で変更可** | 例: 主催者 #7、アンケート #4、レター #21 | **Phase 2** で ON/OFF 可能。デフォルトは §3.2 の D-1 固定値 |

Phase 2 実装時は `enterprises.mail_notification_settings`（仮）と `shouldSendEnterpriseMail(settings, kind)` ヘルパーを導入し、Layer 3 のみ上書き可能とする。
