# 1. 概要

## 1.1 機能の目的

エンタープライズ版でも、従業員が **参加実績・同席関係・注文履歴** をプロフィールから振り返れるようにする。社内コミュニケーション活性化の一環として、部署横断の「食事でつながった人」を可視化する。

ただし PF版 Phase 1 が採用している **未ログイン・完全公開** の友人一覧は、社内専用 SaaS および導入審査（P マーク・セキュリティチェックシート）の観点から **そのまま適用しない**。

## 1.2 PF版との主な差分（サマリ）

| 項目 | PF版 Phase 1 | エンタープライズ版（本仕様） |
|:--|:--|:--|
| プロフィール閲覧 | 未ログイン可 | **ログイン必須**（MVP） |
| 友人一覧閲覧 | 未ログイン可・完全公開 | **同一 `enterprise_id` の従業員のみ**（MVP） |
| テナント分離 | なし | Callable で `enterprise_id` を検証 |
| プロフィール項目 | SNS リンク等 | **SNS 非表示**（イベント管理 §4.3 と整合） |
| 追加表示 | — | **部署名**（`EnterpriseMember.department`、任意）、**利用状況タブ**（本人のみ — §4.2.9） |
| アカウント無効化 | `users.is_deleted` → `not-found` | **`disableEnterpriseMember`（`is_active: false`）も `not-found` 扱い** |
| ゲスト | — | 同席で友人成立しうる。**表示・リンクは別ルール**（§4.4） |
| 友人招待 | 提供 | **MVP では非表示**（SNS 連携方針と整合） |
| プロフィール設定（`/profile`） | PF 同等（メール変更・自己削除あり） | **メール変更・自己削除 UI 非表示**（`04_認証` §6.3） |

# 2. ねらい

## 2.1 ビジネス目標

- 社内の偶発的コミュニケーション（食事同席）を可視化し、**再参加・部署横断交流** を促進する
- 福利厚生ツールとして、**個人の参加実績** を本人が確認できるようにする
- **テナント分離・最小公開** を守り、大企業導入のセキュリティ要件を満たす

## 2.2 ユーザー価値

- 同じ会社の同僚について「いつ・どの社内食事会で同席したか」を振り返れる
- プロフィールから **参加イベント・所属コミュニティ・注文履歴（本人）** に辿れる
- **福利厚生割の月次利用額・残予算** を本人が **利用状況タブ** から確認できる（D-10）

## 2.3 成功指標（KPI）

- エンプラ版 `/u/:userId` の PV（本人 / 他者従業員の内訳）
- 「ともだち」タブ遷移率
- セキュリティレビュー指摘（他社データ閲覧・未認証アクセス）の **ゼロ件**


# 3. 前提条件

## 3.1 技術的前提条件

- **クライアント**: `enterprise` パッケージ（`user` コピー＋差分）。ユーザーページ `/u/:userId` は PF版と同 URL 形状を維持する想定
- **共有 UI**: `base` の `UserProfilePage`（`user` ラッパー）、`FriendCard.vue`、`FriendMeetLogDialog.vue` を流用
- **バックエンド**: PF版 Callable（`getUserProfilePreview` / `getUserFriends` / `getUserFriendMeetLog` / `getUserFoods`）に **エンタープライズ認可レイヤ** を追加する。専用 Callable への完全分岐は Phase 2 で必要に応じて検討
- **認証**: 従業員は `enterprise_id` / `enterprise_role` / `user_type: "enterprise"` を custom claims で保持（`04_認証` 参照）
- **データ**: `users/{uid}` に `enterprise_id` / `user_type`、`/enterprises/{eid}/members/{uid}` に `department` 等（`02_アーキテクチャ` §3.2）

## 3.2 ビジネス的前提条件

- 友人（たべとも）の成立条件は PF版と同一（同一イベントで `status === 'ordered'` の参加確定）
- エンプライベントは原則 `communities` / `events` に `enterprise_id` が付与される
- ゲスト参加（`allow_guest`）により、PF版ユーザーと従業員の **友人ドキュメントが双方向に作成されうる**（`04_ゲスト参加`）

## 3.3 依存関係

- PF版マイページ・友人一覧の Phase 1 実装（Callable・副作用・スキーマ）
- `05_認証・テナント`（アカウント停止・CSV 作成・セッションタイムアウト）
- `04_ゲスト参加`（ゲスト判定 `members.is_guest`）
- `04_イベント管理`（SNS 非表示。コミュニティ承認は Phase 2）
- `04_割引・決済`（`monthly_usage` / `monthly_order_count` の更新タイミング・イベント開催月キー — D-10）
- `profileItemVisibility.ts`（限定公開の **リンク可否** — PF版 §4.2.0 と共有）


# 4. 画面仕様

PF版 §4（タブ構成・プレビュー・空状態）は **原則踏襲** する。以下はエンタープライズ版での **上書き・追加** のみ記載する。

## 4.1 画面遷移・アクセス

- パス: `/u/:userId`（PF版同様）。タブクエリ `?tab=friends|events|communities|foods|usage|orders`（`usage` はエンプラ本人のみ — §4.2.9）
- **未ログイン**で `/u/:userId` を開いた場合 → **ログイン画面へリダイレクト**（return URL 保持）
- **ゲスト**（claims に `enterprise_id` なし）が `/u/:userId` を開いた場合 → **エラー表示**（トップまたは参加中イベント一覧へ誘導。404 相当の文言）
- **他社従業員**（`auth.token.enterprise_id !== target.users.enterprise_id`）→ Callable が `permission-denied` → UI は「閲覧権限がありません」
- **停止・退会済み** `target_user_id` → Callable `not-found` → PF版同様「存在しないユーザーです」
- **`?tab=usage` のガード**（注文履歴 `?tab=orders` と同型）:
  - 本人以外が URL 直叩き → **プロフィールタブ**（`?tab` なし）にフォールバック
  - 本人だが `monthly_limit_per_user` 未設定 → **利用状況タブを表示しない**ためプロフィールタブにフォールバック
- **`/mypage`** → ログイン中 uid の `/u/:auth.uid`（デフォルトはプロフィールタブ。利用状況タブへの自動遷移は MVP では行わない）

## 4.2 UI 要素（エンタープライズ差分）

### 4.2.1 プロフィールタブ

| 要素 | PF版 | エンタープライズ版 |
|:--|:--|:--|
| 表示名・画像・自己紹介 | 表示 | 表示（CSV / `users` ベース） |
| **部署** | なし | `EnterpriseMember.department` があれば表示（`04_認証` の CSV 項目） |
| **SNS リンク** | 表示 | **非表示**（EP-9） |
| カウント | PF版 §5.1.2 | **エンプライベント・コミュニティのみ**集計（EP-11） |
| 友人プレビュー | PF版 §5.5 | 認可後のみ。ゲスト友人は **アバター・名前のみ（リンクなし）** |

### 4.2.9 利用状況タブ（D-10 / E-4）

エンタープライズ版 **独自タブ**。PF版には存在しない。

**タブ定義**:

| 項目 | 値 |
|:--|:--|
| 内部キー | `usage`（定数 `TAB_USAGE`） |
| URL | `/u/:userId?tab=usage` |
| ラベル（i18n） | `user_profile.tab_usage` → 「利用状況」（`enterprise/src/locales/messages/ja.ts`） |
| アイコン | `mdiSale` 等（福利厚生・割引のイメージ。実装時に Vuetify MDI から選定） |
| 並び順 | プロフィールタブの直後（EP-25） |

**表示条件**（すべて満たすとき **タブ自体** を表示）:

1. 閲覧者がログイン済み従業員（EP-1 / EP-2）
2. **本人プロフィール**（`auth.uid === :userId` — EP-18）
3. 企業に `monthly_limit_per_user` が設定されている（EP-20）

> 条件 3 を満たさない場合、タブは **DOM にも出さない**（注文履歴タブの `v-if="isOwner"` と同型 + 上限設定の追加条件）。

**タブ内容**（`EnterpriseSubsidyUsagePanel.vue`）:

| 領域 | 項目 | データ | 備考 |
|:--|:--|:--|:--|
| サマリ（当月） | 今月の利用額 | `monthly_usage[YYYY-MM]` | `YYYY-MM` = **イベント開催月**の当月（EP-21）。`04_割引・決済` §3.1 |
| サマリ（当月） | 月額上限 | `Enterprise.monthly_limit_per_user` | 円。整数表示 |
| サマリ（当月） | 残り予算 | `max(0, limit - used)` | 円 |
| サマリ（当月） | 注文メニュー数（当月） | `monthly_order_count[YYYY-MM]` | MVP で表示（EP-23） |
| 履歴テーブル | 年月 | `monthly_usage` のキー | 降順。直近 12 ヶ月（EP-22） |
| 履歴テーブル | 利用額 | `monthly_usage[key]` | 企業補助額の合計（税込） |
| 履歴テーブル | 注文メニュー数 | `monthly_order_count[key]` | EP-23 |

> **「今月」の注意書き（推奨文案）**: 「利用額は **イベント開催月** ごとに集計されます。来月開催のイベントを今月注文した場合、来月分に計上されます。」（`04_割引・決済` §10 / カート `cart.enterprise_subsidy_month` と整合）

**空状態**:

| 条件 | 表示 |
|:--|:--|
| 当月・過去とも利用 0 | サマリは `0円 / 上限` を表示。履歴は当月行のみ、または「利用履歴はありません」 |
| `monthly_limit_per_user` 未設定 | **タブごと非表示**（EP-20） |

**他者プロフィール**: 利用状況タブは **DOM にも出さない**（同社管理者が他従業員の `/u/:userId` を見ても利用額は表示しない — EP-18）。全社管理者向けの従業員別集計は **ダッシュボード D-2** が担う。

**URL・状態管理**（`UserProfilePage.vue` 実装指針）:

- `resolveTabFromQuery`: `case 'usage':` → 本人かつ上限設定ありなら `TAB_USAGE`、それ以外は `TAB_PROFILE`
- `watch(isOwner)`: 本人でなくなった、または `usage` タブ表示不可になったら `TAB_PROFILE` へ
- `syncTabToUrl`: `usage` はクエリ `?tab=usage` を付与（`profile` はクエリ省略の既存ルール踏襲）
- データ取得: タブが `usage` に切り替わったタイミングで one-shot 読込（EP-26）

**カートとの整合**: 当月サマリの数値は `enterpriseCartMonthlyUsageLoader`（`enterprise/src/composable/enterpriseCartMonthlyUsage.ts`）と **同一ロジック・同一キー** で取得する。実装時は loader と composable を共通化すること。

**i18n**: タブラベル・パネル文言は **`enterprise/src/locales/messages/ja.ts`** の `user_profile` 配下に追加（日本語のみ）。金額ラベルは `cart.monthly_usage_label` と用語を揃える。

**Phase 2（任意）**: カート画面から `?tab=usage` への導線リンク。

### 4.2.5 注文履歴タブ（本人のみ）

# 5. 技術仕様・データ構造設計

## 5.1 スキーマ（追加・変更）

PF版スキーマ（`users` カウントフィールド、`users/{uid}/friends`）は **変更しない**。エンタープライズ差分は以下。

### 5.1.1 表示用（レスポンス拡張）

`getUserProfilePreview` / `getUserFriends` のレスポンスに、エンタープライズ版クライアント向けに次を **追加してよい**（DB 物理名と無関係な API フィールド）。

| フィールド | 型 | 説明 |
|:--|:--|:--|
| `department` | `string \| null` | `/enterprises/{eid}/members/{uid}.department`。プロフィールタブのみ |
| `is_guest_friend` | `boolean` | 友人一覧の相手が PF版ゲストのとき `true`。リンク制御用 |
| `is_linkable` | `boolean` | プロフィールへ `<router-link>` してよいとき `true` |

### 5.1.2 Phase 2: 公開範囲設定（未実装）

PF版 Phase 2 想定（`02_友人一覧機能` §7.2）と整合するフィールドを **`users/{uid}` または `/enterprises/{eid}` 企業デフォルト** に追加する案。MVP では **設けない**。

| フィールド（案） | 説明 |
|:--|:--|
| `friends_visibility` | `enterprise_only` / `friends_only` / `private` 等 |
| `profile_visibility` | 同上 |

## 5.2 Callable 認可（エンタープライズ拡張）

PF版 Callable の **入口** に共通関数 `assertEnterpriseProfileAccess(viewer, targetUserId)` を置く（実装場所: `functions/default/src/utils/enterpriseProfileAccess.ts` 等）。

### 5.2.1 処理順（エンタープライズ版）

1. **認証必須**: `auth == null` → `unauthenticated`
2. **閲覧者がゲスト**（`enterprise_id` claim なし）→ `permission-denied`（友人・プロフィール系）
3. **対象ユーザー取得**: `users/{target_user_id}`。未取得 / `is_deleted` → `not-found`
4. **対象が停止中**: `/enterprises/{eid}/members/{target}` の `is_active == false` → `not-found`（EP-5）
5. **テナント一致**: `viewer.enterprise_id !== target.enterprise_id` → `permission-denied`（EP-4）
6. **対象が enterprise ユーザーでない**（ゲスト uid を target に指定）→ `not-found` または `permission-denied`（EP-7）
7. 以降、PF版と同一のデータ取得（ただし **enterprise_id フィルタ** 付き）

**クライアント（RC-44）**: `enterprise` の `/u/:userId` では `getUserProfilePreview` 成功まで本体を表示しない。イベント/フードタブ store は `autoLoad: false` とし、preview 成功後にのみ `reload` する（Firestore 直読・Callable の先行 fetch を防ぐ）。

### 5.2.2 対象 Callable

| Callable | エンタープライズ差分 |
|:--|:--|
| `getUserProfilePreview` | §5.2.1 + プレビュー各種に enterprise フィルタ + `department` 付与 |
| `getUserFriends` | §5.2.1 + 友人解決後に **他社・無効ユーザ除外** + `is_guest_friend` |
| `getUserFriendMeetLog` | §5.2.1 + meet_log を **当該 enterprise の event のみ** |
| `getUserFoods` | §5.2.1 + `member_orders` / イベントの enterprise フィルタ |
| `backfillUserProfileCounts` / `backfillUserFriends` | **管理者（support）** は PF版同様。エンプラテナント単位の `enterprise_id` 絞り込み引数を **Phase 2** で追加検討 |

### 5.2.3 アプリ種別の判定

| 条件 | 扱い |
|:--|:--|
| Request の `Authorization` + claims に `enterprise_id` | エンタープライズ従業員 → 本仕様の認可 |
| claims に `enterprise_id` なし | PF版ユーザー → PF版 Callable 認可（完全公開）のまま |
| 同一 Firebase Project | **Callable 内で claims により分岐**。クライアントアプリ（`user` vs `enterprise`）の混呼びは claims を正とする |

> **実装方針（MVP）**: PF版 Callable 本体に `if (isEnterpriseViewer(auth)) { ... }` 分岐を入れる。エンプラ専用の duplicate 実装は避ける。

## 5.3 データ取得フィルタ（enterprise_id スコープ）

### 5.3.1 `recountUserProfileCounts(uid)`（エンタープライズ従業員）

| カウント | PF版定義 | エンタープライズ上書き |
|:--|:--|:--|
| `participated_event_count` | ordered イベントユニーク数 | 上記 + **`event.enterprise_id == users.enterprise_id`** |
| `ordered_food_count` | ordered 注文数 | 上記 + **`member_orders.enterprise_id` 一致**（またはイベント経由で判定） |
| `joined_community_count` | members に含まれるコミュニティ | + **`community.enterprise_id` 一致** + **本人カウントは approved + 本人 pending を含む**（他者表示は approved のみ — EP-14） |
| `managed_community_count` | managers に含まれる | + **`community.enterprise_id` 一致** |
| `friend_count` | getUserFriends 除外規則と一致 | + **表示可能な友人のみ**（退会除外 + **同 enterprise 従業員 + 同席ゲスト**）。ゲスト uid は friend_count に含めてよい（EP-6 推奨） |

**副作用フック**（注文・コミュニティ・友人更新）は PF版 §5.1.4 踏襲。エンプライベントでも同一関数が走る。

### 5.3.2 友人一覧のゲストフィルタ（推奨）

`resolveUserFriendsList` の後処理:

1. 各 `friend_user_id` の `users` を解決
2. `friend.enterprise_id` が **target と異なる enterprise** → 除外
3. `friend` に `enterprise_id` なし（PF版ゲスト）→ レスポンスに含めるが `is_guest_friend: true`, `is_linkable: false`
4. `friend.is_deleted` または `/enterprises/.../members` で `is_active == false` → 除外（PF版 S-1 踏襲）

## 5.4 Firestore Security Rules

# 7. 注意事項

## 7.1 既存システムへの影響

- **PF版挙動は claims 分岐により維持** する。`user` アプリ利用者（platform）には EP-1〜11 を適用しない
- `base` コンポーネントに **props 追加**（`hideSns`, `friendLinkDisabled` 等）が必要になる可能性。PF版への影響はデフォルト OFF で無害化
- 友人・カウントの **データモデルは共通** のため、PF版ユーザーがエンプライベント（ゲスト）に参加すると **グローバルな `friends` に記録が残る**。表示は本仕様で制限する

## 7.2 セキュリティ考慮事項

- **他社プロフィールの存在確認**: EP-4 で `permission-denied` を返すため、uid 総当たりで在籍確認されるリスクは **uid 推測困難性 + レート制限（Phase 2）** で緩和
- **ソーシャルグラフ**: 同社従業員に開示する範囲を EP-3 で限定。導入企業向けプライバシーポリシーに **友人一覧の取り扱い** を記載（`03_セキュリティポリシー` Part 3 整備時）
- **meet log**: enterprise フィルタ後に PF版 §4.2.0（他者にもメタ表示・リンクはプロフィール所有者本人のみ）

## 7.3 パフォーマンス考慮事項

- enterprise フィルタは **Firestore クエリ段階** で `enterprise_id` を含めることを優先（取得後フィルタのみにしない）
- 必要に応じて `events` / `communities` / `member_orders` の **enterprise_id 複合インデックス** を追加（実装 PR と同タイミングで `firestore.indexes.json` 更新）

## 7.4 PF版マージ運用

- `05_PF版_userとenterpriseの共通化`: PF版マイページ改修は **base へ引き上げ** を優先し、`enterprise` へのマージコンフリクトを減らす
- エンタープライズ固有差分は **`enterprise/src` のラッパー** と **Functions 認可分岐** に集約する
