# 割引・決済 詳細仕様

> **原典**: `90_アーカイブ/v0.1原典/` の 04_割引・決済 を現行化。

本ドキュメントは `01_仕様概要`、`02_アーキテクチャ` の決定事項に基づき、割引計算・月額上限管理・Stripe決済連携の機能仕様を詳細に定義する。

## 前提とする仕様書

本ドキュメントは EventMemberOrder 設計（`05_EventOrder→EventMemberOrder.md` および `03_無料参加・割引参加_EventMemberOrder対応.md`）を前提とする。注文関連のデータは以下のパスに格納される。

```
/communities/{communityId}/events/{eventId}/members/{userId}/member_orders/{orderId}   # 1メニュー = 1ドキュメント
/communities/{communityId}/events/{eventId}/stripes/{stripeId}                          # Stripe決済情報
```

論点の決定経緯は `06_エンタープライズ_EventMemberOrder対応論点.md` を参照。


# 1. 概要

エンタープライズ版では、イベントの支払い方式として新たに `enterprise_subsidy`（福利厚生割引）を追加する。この方式が選択されたイベントでのみ、企業の割引ルールに基づき注文金額を自動割引する。`user_advance`（参加者事前決済）はオプションとして利用可能。**`community_bill`（主催者請求書払い）はエンプラ版では選択不可**（D-13）。

## 1.1 支払い方式の全体像

### PF版（既存）

| 値 | ラベル | 挙動 |
|:--|:--|:--|
| `user_advance` | 参加者事前決済 | 参加者が全額クレカ事前決済 |
| `user_on_day` | 当日払い | **deprecated（利用実績なし。エンプラ版では選択不可）** |
| `community_bill` | 主催者請求書払い | コミュニティに請求書発行。参加者は0円（または `community_bill_settings.type='discount'` で差額をクレカ決済） |

### エンタープライズ版で追加

| 値 | ラベル | 挙動 |
|:--|:--|:--|
| `enterprise_subsidy` | 福利厚生割引 | 企業が設定した割引を適用。残額は参加者がクレカ決済 |

### エンプラ版での利用可否

| 支払い方式 | エンプラ版 | デフォルト | 割引計算 |
|:--|:--|:--|:--|
| `enterprise_subsidy` | 利用可 | **デフォルト** | **あり** |
| `user_advance` | 利用可（オプション） | | なし（PF版と同じ処理） |
| `community_bill` | **利用不可** | | — |
| `user_on_day` | **利用不可** | | — |

**割引計算ロジックが走るのは `enterprise_subsidy` の場合のみ。** `user_advance` では PF版と同じ処理がそのまま使われる。

**ゲスト参加時の注文フロー**は本ドキュメントのスコープ外とする。`enterprise_subsidy` のイベントにゲスト（PF版ユーザー）が参加した場合の決済フロー・割引適用有無は `04_ゲスト参加` で定義する。

### common スキーマへの影響

```typescript
// 現行
export const EVENT_PAYMENT_VALUES = ['user_advance', 'user_on_day', 'community_bill'] as const

// 変更後
export const EVENT_PAYMENT_VALUES = ['user_advance', 'user_on_day', 'community_bill', 'enterprise_subsidy'] as const
```

`user_on_day` および `community_bill` は後方互換性のために common スキーマの値として残すが、**エンプラ版のイベント作成 UI では選択肢に表示しない**。Functions 側でも `enterprise_id` 付きイベントに `community_bill` が指定された場合は `invalid-argument` で拒否する。

## 1.2 PF版との主な差分（enterprise_subsidy 選択時）

| 項目 | PF版（user_advance） | エンプラ版（enterprise_subsidy） |
|:--|:--|:--|
| 割引 | なし（全額ユーザー負担） | 企業の割引ルールを適用 |
| 月額上限 | なし | 1人あたり月額上限あり |
| 決済金額 | 注文合計額 = Stripe 請求額 | ユーザー自己負担額 = Stripe 請求額 |
| 自己負担0円 | なし | Stripe スキップで `confirmOrder` で直接確定 |
| 注文確定の Functions | PF版の `addToCart` / `confirmOrder` / `createStripeCheckoutSession` / `stripeWebhook` / `cancelOrders` | **同じ Functions に `event_payment === 'enterprise_subsidy'` 分岐を追加** |
| キャンセル時 | Stripe Refund のみ | Stripe Refund + `monthly_usage` の戻し |

# 2. 割引計算ロジック

**本章の割引計算は `event_payment == 'enterprise_subsidy'` の場合にのみ適用される。** `user_advance` のイベントでは割引計算は行わず、PF版と同じ処理となる。

## 2.1 計算式

EventMemberOrder 化により、**1 メニュー = 1 ドキュメント** となるため、割引計算もメニュー単位に行う。

すべて**税込**ベースで計算する。PF版のメニュー価格が税込（`tax_behavior: 'inclusive'`）のため、統一する。

```
■ メニュー1品（1 member_orders ドキュメント）あたりの計算

① 割引候補額（type で分岐）
   - 固定金額の場合: candidate = min(settings.value, menu_price)
     例: settings.value = 500, menu_price = 800 → candidate = 500
     例: settings.value = 500, menu_price = 300 → candidate = 300（menu_price でキャップ）
   - 割合の場合: candidate = min(Math.floor(menu_price × settings.value / 100), menu_price)
     例: settings.value = 50, menu_price = 1,200 → candidate = 600

② 月額残枠（イベント開催月）
   remaining = Math.max(0, settings.monthly_limit_per_user - 当該月の monthly_usage - addToCart 内累計補助額)
   ※ Math.max(0, ...) でガード。キャンセル戻しのタイミング等で usage > limit になるエッジケースに備える
   ※ addToCart で N 個追加するときはループ内で残枠を減算しながら計算

③ 1品分の補助額
   pay_enterprise_subsidy_amount = Math.min(candidate, remaining)
   ※ remaining が 0 の場合は補助額もゼロ → フィールドを保存しない（undefined。0 は保存しない）

④ 1品分のユーザー自己負担額（導出）
   per_item_payment = menu_price - (pay_enterprise_subsidy_amount ?? 0)
```

```
■ カート全体（order_ids 分）の合計

total_amount  = Σ menu_price                                  // 全メニューの合計
total_subsidy = Σ (pay_enterprise_subsidy_amount ?? 0)        // 補助合計
total_payment = total_amount - total_subsidy                   // 参加者支払合計（Stripe 請求額）
```

> `pay_community_bill_off_amount`（`03_無料参加・割引参加_EventMemberOrder対応.md`）と並列の構造。`× count` の乗算は不要（同一メニューを 3 個注文した場合は同じ `pay_enterprise_subsidy_amount` を持つ 3 つのドキュメントが作られる）。

## 2.2 計算例

### 企業設定

```
discount_type: "percentage"
discount_value: 50（50%割引）
monthly_limit_per_user: 7500
```

### ケース別（カート全体・残枠 7,500 円のスタート想定）

| ケース | カート内訳 | 補助合計 | 自己負担合計 |
|:--|:--|:--|:--|
| 通常 | 600円 × 2 | 600（300×2） | 600 |
| 端数あり | 575円 × 2 | 574（287×2、Math.floor） | 576 |
| 残枠不足 | 600円 × 4 | 残枠 300 まで（4品目以降は補助なし） | 2,100 |
| 残枠0 | 600円 × 2（既に上限到達） | 0（フィールドなし） | 1,200 |
| 割引 > 単価 | 300円 × 1（固定 500） | 300（menu_price でキャップ） | 0 |

> 「残枠不足」のケース：1 品目で 300、2 品目で 300、3 品目で 300、4 品目以降は残枠ゼロのため `pay_enterprise_subsidy_amount` フィールドなし、という扱いになる。

## 2.3 割引計算の責務（02 全体構成 3.4 と整合）

| タイミング | 処理 |
|:--|:--|
| `addToCart` | 各 `member_orders` ドキュメント作成時に、Cloud Functions が `pay_enterprise_subsidy_amount` を算出して書き込む（`computePaymentEnterpriseSubsidyAmount` ヘルパ）。月額上限は `members.monthly_usage` を参照しつつ、ループ内累計を考慮して切り下げる |
| `confirmOrder` / `createStripeCheckoutSession` | サーバー側で各 order について再計算し、ストアード値と一致するか検証（`isPaymentEnterpriseSubsidyAmountConsistent` ヘルパ）。一致しない場合 `failed-precondition` + `enterprise_subsidy_recalculated` 監査ログ |
| `confirmOrder` / `stripeWebhook` | Transaction 内で `EnterpriseMember.monthly_usage` をイベント開催月キーで加算 |
| `cancelOrders` | Transaction 内で `EnterpriseMember.monthly_usage` から減算（イベント開催月キー） |

フロントエンドで計算して表示するのは UX 目的のみ。実際の割引適用額は Functions 側で検証・確定する。

## 2.4 共通ヘルパ（common/src/utils/）

`paymentCommunityBillOffAmount.ts` と並列に、`paymentEnterpriseSubsidyAmount.ts` を新設する（02 全体構成 3.5 と同一）。

```typescript
// 1 つの member_orders ドキュメントに適用する企業補助額を算出する
// remainingMonthlyLimit: 当該月の残枠（monthly_limit_per_user - runningUsage）
// 0 以下の場合は undefined（フィールド省略 = 自己負担）
export function computePaymentEnterpriseSubsidyAmount(
  eventPayment: EventPaymentType,
  settings: EnterpriseSubsidySettings | undefined,
  menu_price: number,
  remainingMonthlyLimit: number,
): number | undefined {
  if (eventPayment !== 'enterprise_subsidy') return undefined
  if (settings == null) throw new Error('enterprise_subsidy requires enterprise_subsidy_settings')
  if (remainingMonthlyLimit <= 0) return undefined

  let baseAmount: number
  if (settings.type === 'fixed') {
    baseAmount = Math.min(settings.value, menu_price)
  } else {
    baseAmount = Math.min(Math.floor((menu_price * settings.value) / 100), menu_price)
  }
  return Math.min(baseAmount, remainingMonthlyLimit)
}

// サーバー側再計算とストアード値の整合チェック（confirmOrder / createStripeCheckoutSession 用）
// remainingMonthlyLimit は addToCart と同じ順序でループ再現した当該 order の残枠
export function isPaymentEnterpriseSubsidyAmountConsistent(
  eventPayment: EventPaymentType,
  settings: EnterpriseSubsidySettings | undefined,
  order: EventMemberOrder,
  remainingMonthlyLimit: number,
): boolean {
  const expected = computePaymentEnterpriseSubsidyAmount(
    eventPayment,
    settings,
    order.menu_price,
    remainingMonthlyLimit,
  )
  return expected === order.pay_enterprise_subsidy_amount // 両方 undefined も一致とみなす
}

// 1 注文ごとの参加者支払額（line net = menu_price - 企業補助相当）
export function computeEnterpriseOrderLineNet(
  order: EventMemberOrder,
  eventPayment?: EventPaymentType,
  settings?: EnterpriseSubsidySettings,
  remainingMonthlyLimit = Number.MAX_SAFE_INTEGER,
): number { /* ... */ }

// カート全体（order_ids 分）の参加者支払合計
export function computeTotalPayment(orders: EventMemberOrder[]): number {
  return orders.reduce(
    (sum, o) => sum + o.menu_price - (o.pay_enterprise_subsidy_amount ?? 0),
    0,
  )
}
```


# 3. 月額利用実績管理

## 3.1 イベント開催月に紐づける

月額利用実績は**決済日ではなくイベント開催月**に紐づく。

```
例1: 6月25日に、7月3日開催イベントの注文を決済
  → 7月分の usage に加算

例2: 6月28日に、6月30日開催イベントの注文を決済
  → 6月分の usage に加算
```

これにより、6月末に「6月のイベント」と「7月のイベント」の注文を同時に行う場合、それぞれの月の枠が独立してチェックされる。

## 3.2 EnterpriseMember スキーマ（辞書フィールド方式）

02_全体構成の `EnterpriseMember` スキーマを以下に変更する。

```typescript
interface EnterpriseMember {
  user_id: string
  role: "admin" | "member"
  is_active: boolean
  display_name?: string
  department?: string

  // === 割引利用実績（月別辞書） ===
  monthly_usage: Record<string, number>         // { "2026-06": 5000, "2026-07": 1200 }
  monthly_order_count: Record<string, number>   // { "2026-06": 8, "2026-07": 2 }

  created_at: Timestamp
  updated_at: Timestamp
}
```

**旧スキーマからの変更点:**

| 旧 | 新 |
|:--|:--|
| `current_month: string` | 削除 |
| `current_month_usage: number` | `monthly_usage: Record<string, number>` |
| `current_month_order_count: number` | `monthly_order_count: Record<string, number>` |

**辞書方式を選択した理由:**
- 1ドキュメントで全月分の使用量を取得できる（追加クエリ不要）
- Transaction 内で扱いやすい（1ドキュメントの読み取り+書き込みで排他制御が完結）
- 異なる月のイベントを同時に注文する場合にも対応可能

**アカウント作成時の初期値:**

```typescript
{
  monthly_usage: {},
  monthly_order_count: {},
}
```

**古い月のクリーンアップ:**
- MVP: クリーンアップしない。辞書に月が蓄積されるが、1ユーザーあたり年12エントリ程度なのでサイズ問題はない
- Phase 2: Scheduled Function で3ヶ月以上前のエントリを削除する

## 3.3 usage の読み取り

```typescript
const getUsageForMonth = (member: EnterpriseMember, yearMonth: string): number => {
  return member.monthly_usage[yearMonth] ?? 0
}

const getOrderCountForMonth = (member: EnterpriseMember, yearMonth: string): number => {
  return member.monthly_order_count[yearMonth] ?? 0
}
```

辞書にキーが存在しない月は `0` として扱う。旧スキーマの「`current_month` が現在月と不一致なら0扱い」に相当する。

## 3.4 usage の更新（Transaction 内）

注文確定時（`confirmOrder` / `stripeWebhook`）に、当該セッションの `order_ids` の `pay_enterprise_subsidy_amount` を集計し、イベント開催月キーで加算する。

```typescript
// 注文セッション全体の集計
const eventMonth = formatYearMonth(event.event_start_datetime)  // "2026-07"
const subsidyTotal = orders.reduce(
  (sum, o) => sum + (o.pay_enterprise_subsidy_amount ?? 0),
  0,
)
const orderCount = orders.length  // 確定対象の member_orders 件数（status 更新前の in_cart / processing を含む）

// Transaction 内で member ドキュメントを読み取り+更新
transaction.update(memberRef, {
  [`monthly_usage.${eventMonth}`]: FieldValue.increment(subsidyTotal),
  [`monthly_order_count.${eventMonth}`]: FieldValue.increment(orderCount),
  updated_at: FieldValue.serverTimestamp(),
})
```

> 1 ドキュメント = 1 メニューになったため、`monthly_order_count` は「ordered になった member_orders ドキュメントの件数」を意味する。「注文セッション数」ではないため、ダッシュボード表示時は注意（詳細は `04_詳細仕様_ダッシュボード` 参照）。

## 3.5 同時注文の排他制御

月額上限を厳密に制御するため、`confirmOrder` / `stripeWebhook` での加算は必ず Transaction を使用する。

```
注文A（Webhook到着）           注文B（Webhook到着）
  Transaction 開始               Transaction 開始
  member Doc 読み取り（ロック）   → ロック待ち
  整合チェック OK                 │
  usage += subsidyTotal          │
  Transaction 完了                ロック解除 → 再読み取り
                                  整合チェック → 残枠不足で失敗
                                  → enterprise_subsidy_recalculated 監査ログ
                                  → クライアントに再カート操作を促す
```

`addToCart` 時点では加算しないため、複数の `addToCart` が同時実行されても上限超過は防げない。`confirmOrder` / `stripeWebhook` で必ず最新の `monthly_usage` を読み取って整合チェックする。

## 3.6 Phase 2: 月次バッチ再集計

フィールド保持方式は加算/減算の漏れによる不整合リスクがあるため、Phase 2 で安全網として月次再集計バッチを導入する。

- Scheduled Function で月初に前月分の `member_orders` を `collectionGroup` で集計（`enterprise_id` + `event_id` の Where 条件）
- `pay_enterprise_subsidy_amount` の合計を `monthly_usage` の値と照合
- 不一致があれば管理者に通知 + 自動補正


# 4. 注文〜決済フロー

## 4.1 event_payment による分岐

注文〜決済のフローは PF版の Callable Functions（`addToCart` / `confirmOrder` / `createStripeCheckoutSession` / `stripeWebhook` / `cancelOrders`）に **`event_payment` 分岐** を追加して実装する。エンプラ専用 Function は新設しない（02 論点 6.1 で決定）。

| event_payment | カート | 確定 | 割引 |
|:--|:--|:--|:--|
| `enterprise_subsidy` | `addToCart` で `pay_enterprise_subsidy_amount` を算出 | `total_payment === 0` なら `confirmOrder`、`> 0` なら `createStripeCheckoutSession` → `stripeWebhook` | あり |
| `user_advance` | PF版と同じ | `createStripeCheckoutSession` → `stripeWebhook` | なし |

`user_advance` のイベントでは、PF版の既存 Functions ロジックがそのまま動作する。エンプラ版固有の変更は `enterprise_id` を各ドキュメントにセットするのみ。

### user_advance のエンプラ版での扱い

PF版と完全に同じ処理を行う。エンプラ版固有の変更は `enterprise_id` のセットのみ。

| 項目 | 挙動 |
|:--|:--|
| `member_orders` Doc | `enterprise_id` をセット。`pay_enterprise_subsidy_amount` はセットしない |
| 割引 | なし |

## 4.3 カート追加（addToCart）

```
1. 認証チェック

2. イベントDocを取得
   → Enterprise.subsidy_settings_history を eventMonth で resolve → settings
```

## 5.2 confirmOrder / createStripeCheckoutSession の確定前再同期（D-20 / #2252）

`confirmOrder` および `createStripeCheckoutSession` の Transaction **冒頭**で、最新 `monthly_usage` と Enterprise 履歴から `replayEnterpriseSubsidyAmountsForOrders` を実行し、結果を `member_orders.pay_enterprise_subsidy_amount` に**書き戻してから**確定処理に進む。

```
1. enterprise = getEnterprise(enterprise_id)
2. eventMonth = formatYearMonth(event.event_start_datetime)
3. settings = resolveEnterpriseSubsidySettingsForMonth(enterprise.subsidy_settings_history, eventMonth)
4. member = getEnterpriseMember(...)
5. replay = replayEnterpriseSubsidyAmountsForOrders(..., settings, orders, member.monthly_usage[eventMonth] ?? 0)
6. 各 order の pay_enterprise_subsidy_amount を replay.expectedAmounts[i] で update（不一致時のみ）
7. used + replay.subsidyTotal > settings.monthly_limit_per_user なら failed-precondition
8. 以降、confirmOrder / Stripe Session 作成
```

- 書き戻し後は stored と replay が一致するため、厳密一致検証のみの二重チェックは不要
- 金額が変わった場合はレスポンスで `subsidy_recalculated: true` を返し、クライアントはカート再表示を促す（サイレント Checkout 禁止）
- Webhook 確定時は Checkout 作成時点の stored 値をスナップショットとして扱う（現行どおり replay 再検証しない）

## 5.5 cancelOrders の `enterprise_subsidy` 分岐

PF版の `functions/default/src/cancelOrders.ts` に分岐を追加する。

### 処理フロー

```
1. 認証チェック
2. キャンセル対象 member_orders を取得
   → status != 'ordered' → HttpsError('failed-precondition')
3. イベントDocを取得
   → eventMonth = formatYearMonth(event.event_start_datetime)
4. キャンセル可能期限チェック（PF版と同じ基準）

--- Firestore 更新（Transaction 内・PF 版 cancelOrders と同型）---

5. Transaction 内で:
   a. 全 order の status を 'canceled' に更新、canceled_at をセット
   b. event_payment === 'enterprise_subsidy' の場合:
      subsidyTotal = Σ(pay_enterprise_subsidy_amount ?? 0)  // キャンセル分のみ
      memberRef を読み取り、
      monthly_usage[eventMonth] = max(0, used - subsidyTotal)
      monthly_order_count[eventMonth] = max(0, count - orders.length)
   → Transaction 失敗時は Stripe Refund 前に全体失敗（PF 版と同型）

--- Stripe Refund（Transaction 外・PF 版 cancelOrders と同型）---

6. stripe_id でグルーピングし、stripe_id ごとに:
   - 当該グループの返金額 = Σ(menu_price - pay_enterprise_subsidy_amount)
   - Stripe Refund を実行（最大3回 retry、idempotencyKey 付き）
   - 成功時: 別 Transaction で stripes ドキュメントの refunds 配列に追記
   → 全 retry 失敗 → refund_errors に記録し、レスポンスに user_message を付与（注文は canceled のまま。運営が手動返金）

7. 監査ログ order_cancel を記録（details.order_ids、refund_amount、returned_subsidy_amount）
```

> **順序の根拠（PF 版 `cancelOrders.ts` 準拠）**: Firestore でキャンセル確定 → その後 Stripe Refund。Refund 失敗時は `refund_errors` を返し、注文ステータスは canceled を維持する（返金のみ未完了）。Refund 成功後の stripes 更新 Transaction 失敗は idempotencyKey により再実行可能。

**Stripe Refund と Firestore Transaction を分離する理由:**
Firestore Transaction 内では外部API（Stripe）を呼び出すべきではない。Transaction が競合でリトライされると Refund が重複実行される恐れがあるため、Refund を先に実行し、成功後に Firestore を更新する。

**Stripe Refund 成功 → Firestore Transaction 失敗の場合:**
Firestore Transaction を retry する（最大3回）。全 retry 失敗時は管理者に通知する。Stripe 側は既に Refund 済みのため、Firestore の不整合は Phase 2 の月次再集計で検知・補正される。

### キャンセル時の割引戻しについて

- キャンセルすると `monthly_usage` から当該 order の `pay_enterprise_subsidy_amount` 合計を減算し、枠を復元する
- 復元された枠は次回以降の注文で使用可能
- `monthly_usage` が負にならないよう `Math.max(0, usage - subsidyTotal)` でガードする

# 9. Security Rules

割引・決済に関連する Security Rules は **02 全体構成 5.2** で定義済み。本章では補足のみ。

```javascript
// member_orders（注文）: PF版公開 + エンプラ自社 + 本人（ゲスト含む）
match /communities/{cid}/events/{eid}/members/{uid}/member_orders/{oid} {
  allow read: if resource.data.enterprise_id == null
              || (request.auth != null && (
                   resource.data.enterprise_id == request.auth.token.enterprise_id
                   || request.auth.uid == resource.data.user_id
                 ));
  allow write: if false;   // Functions のみ
}

// stripes（Stripe決済情報）: 本人のみ read（MVP）。ゲストも user_id 一致で可
match /communities/{cid}/events/{eid}/stripes/{sid} {
  allow read: if request.auth != null && request.auth.uid == resource.data.user_id;
  allow write: if false;
}

// 企業設定の割引情報: 同一企業のメンバーは読み取り可能
match /enterprises/{enterpriseId} {
  allow read: if request.auth.token.enterprise_id == enterpriseId;
  allow write: if request.auth.token.enterprise_id == enterpriseId
                && request.auth.token.enterprise_role == "admin";
}

// EnterpriseMember: 同一企業内 read、クライアント write 禁止（02 全体構成 5.2 と同一）
// ※ メンバー情報の更新も monthly_usage もすべて Admin SDK / Callable 経由
match /enterprises/{enterpriseId}/members/{userId} {
  allow read: if request.auth.token.enterprise_id == enterpriseId;
  allow write: if false;   // Functions のみ
}
```

- 初期表示: Firestore `/enterprises/{id}` の `subsidy_settings_history` を admin read
- **当月適用中**の settings: `resolveEnterpriseSubsidySettingsForMonth(history, 当月)` をフォーム初期値に使用
- 保存: Callable `updateEnterpriseSubsidySettings`（§5.0）

### 保存時の注記（画面に常時表示）

> 補助設定は**翌月以降**（適用開始月）から有効になります。当月分は変更できません。
>
> 適用開始月以降に開催されるイベントでは、**設定変更後に新規にカートへ追加する注文**から新設定が適用されます。
>
> **すでに確定済み（注文完了）の注文**には反映されません。補助額の差額が自動で返金・再請求されることはありません。自己負担額の見直しが必要な場合は、注文期限内であれば**キャンセル後に再注文**してください（キャンセル時の Stripe 返金は自己負担分のみ）。

「補助設定を保存しました」トースト表示。

| 設定項目 | 内容 |
|:--|:--|
| 適用開始月 | `effective_from_month`: `YYYY-MM`（履歴エントリのキー） |
| 割引タイプ | `type`: `fixed`（固定金額）/ `percentage`（割合） |
| 割引値 | `value`: 固定=円 / 割合=パーセント（0〜100） |

# 補足資料: Phase 2 仕様概要

MVPでは実装しないが、Phase 2 以降で対応する項目の仕様概要を記載する。


## A. 給与天引き対応（CSV出力）

### 背景

クレジットカード決済ではなく、給与天引きで従業員の自己負担分を回収する方式。大企業の経理部門から要望が出る可能性が高い。

### 仕様概要

- 企業設定に `payment_method: "payroll_deduction"` を追加
- 注文時は Stripe 決済をスキップし、`confirmOrder` で直接注文確定
- 月末に「従業員別自己負担額一覧CSV」を管理者画面からダウンロード可能
- CSV項目: 従業員名、部署、メールアドレス、注文数（`monthly_order_count`）、自己負担合計、補助合計


## B. 月次バッチ再集計

### 背景

フィールド保持方式の不整合リスクに対する安全網。

### 仕様概要

- Scheduled Function で月初に前月分の `member_orders` を `collectionGroup` で集計
  - クエリ: `collectionGroup('member_orders')` + `where('enterprise_id', '==', ...)` + `where('status', '==', 'ordered')` + イベント開催月で絞り込み
- 各メンバーの `monthly_usage` と `Σ pay_enterprise_subsidy_amount` を照合
- 差異があれば管理者に通知
- 差異が小さい場合は自動補正、大きい場合は管理者承認後に補正


## C. 割引ルールの拡張

### 背景

企業ごとに異なる複雑な割引ルールに対応する。

### 仕様概要

- 部署別の割引ルール（部署Aは50%割引、部署Bは30%割引）
- 時間帯別の割引（ランチタイムは割引率アップ）
- 注文回数に応じた段階的割引
- 複数の割引ルールの組み合わせ（最大割引 or 合算）


## D. 確定済み注文への差額返金（Phase 2・任意）

### 背景

`subsidy_settings_history` の適用開始月変更後、**すでに確定済み**（`status === 'ordered'`）の注文は `pay_enterprise_subsidy_amount` が不変のまま残る。新設定下ではユーザーに有利な差額（自己負担過払い）が発生しうる。

### MVP の方針

- **自動返金・追徴は行わない**
- 管理者 UI 脚注 + 手動キャンセル→再注文で対応（§10.4）
- 実装 Issue は Phase 2 検討用に起票可

### Phase 2 で検討する範囲（実装する場合）

| 方向 | 方針 |
|:--|:--|
| 自己負担の**返金**（新設定で補助増 → ユーザー有利） | `stripe.refunds.create` で部分返金。`pay_enterprise_subsidy_amount` / `monthly_usage` 更新。管理者手動実行または Callable |
| 自己負担の**追徴**（新設定で補助減） | **対象外**（Checkout 後の自動追徴不可） |
| トリガー | 設定保存時の一括処理は非推奨。対象注文をクエリし、管理者確認後に実行 |

### 関連

- `cancelOrders` の Stripe 返金（自己負担全額）は MVP 実装済み
- #2252（in_cart 確定前再同期）は MVP 必須（§5.2 / D-20）
