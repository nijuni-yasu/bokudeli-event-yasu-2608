## IdP 採用方針（仕様要約）

| 項目 | 仕様 |
|:--|:--|
| 認証基盤 | Identity Platform **マルチテナンシー**（end-state）。MVP でテナント onboarding・claims まで前倒し |
| 従業員 | 企業テナント内 uid。`auth.tenantId` をエンプラアプリ起動時に設定 |
| ゲスト | **デフォルトプール固定**（PF版 uid）。テナントに入れない。`allow_guest` イベントのみ Rules 例外 |
| 同一メアド | テナントごとに uid 名前空間分離。PF版とエンプラで**共存可** |
| SSO | Phase 2。テナント単位 SAML/OIDC（[ADR-002 §1.5](../20_設計判断_ADR/ADR-002_IdP採用とゲスト方針.md)） |
| PF 露出 | エンプライベントは PF 一覧非表示。PF クエリは `enterprise_id == null` 必須（02_アーキテクチャ） |

経緯・選択肢の比較は ADR-002 を参照。本書は実装者向けの**仕様**に徹する。

## 前提とする仕様書

本ドキュメントは EventMemberOrder 設計（`05_EventOrder→EventMemberOrder.md`）を前提とする。次の概念区別が重要:

| コレクション | 説明 | エンプラ追加フィールド |
|:--|:--|:--|
| `/enterprises/{eid}/members/{uid}` (`EnterpriseMember`) | 企業の従業員レコード。本ドキュメントの主な対象 | `monthly_usage`, `monthly_order_count`, `role`, `is_active` 等 |
| `/communities/{cid}/events/{eid}/members/{uid}` (`EventMember`) | イベント参加者レコード。`addToCart` 時に作成 | `is_guest`, `enterprise_id` |

`EnterpriseMember` には `is_guest` を持たせない（定義上ゲストではない）。`is_guest` は **イベント参加時の `EventMember` 作成時** にセットする（`04_ゲスト参加` 5.1 参照）。


# 1. 概要

認証・アカウント管理はエンタープライズ版のすべての機能の前提となる。
プラットフォーム版の OTP 認証の仕組みをベースに、企業メールドメイン制限・custom claims・アカウント一括管理などのエンタープライズ固有要件を追加する。

**企業・初代 admin の作成**は運営専用 `createEnterprise`（`04_オンボーディング` §3 参照）で行う。CSV 一括作成（`createEnterpriseMembers`）は既存 admin が前提。

## 1.1 PF版との主な差分

| 項目 | PF版 | エンタープライズ版 |
|:--|:--|:--|
| ログイン方法（従業員） | メール + OTP / SNS | メール + OTP のみ（SNSログインなし） |
| ログイン方法（ゲスト） | — | PF版と同等（メール+OTP、SNS）。04_ゲスト参加 参照 |
| アカウント作成 | ユーザー自身がログイン画面から作成 | 全社管理者が事前にCSV一括作成 |
| メールドメイン制限 | なし | 企業の allowed_email_domains に限定 |
| custom claims | なし | enterprise_id, enterprise_role, user_type |
| セッション管理 | なし（無期限） | **1週間**無操作で自動ログアウト |
| Functions | requestEmailLogin / confirmEmailLogin | 新規 Functions を作成（既存を拡張しない） |
| 自己アカウント削除 | プロフィールから `deleteUserAccount` 可能 | **不可**（全社管理者の停止フローのみ。§6.3 参照） |
| メールアドレス変更 | プロフィールから `requestEmailChange` 可能 | **MVP では不可**（§6.3 参照） |

## 1.2 決定事項サマリ

| # | 論点 | 決定 |
|:--|:--|:--|
| 1-1 | Functions の新規作成 vs 既存拡張 | 新規作成 |
| 1-2 | 未登録メールのログイン | エラー。全社管理者が事前にアカウント作成する前提 |
| 1-3 | OTP有効期限の短縮 | MVPでは実装しない。PF版と同じ24時間 |
| 1-4 | OTP最大試行回数の制限 | MVPでは実装しない |
| 1-5 | OTP再送間隔の制限 | MVPでは実装しない |
| 4-1 | CSV一括作成のエラー処理 | エラー行をスキップして残りを処理 |
| 4-2 | PF版との重複メールアドレス | IdP 採用により**共存可**（テナントスコープで別 uid）。移行期は PA-02e 参照 |
| 4-4 | アカウント作成完了メール | MVPでは実装しない |
| 6-1 | 最後のadmin降格制限 | 不可。最低1人のadminを維持 |
| 7-1 | 初回ログインのプロフィール設定 | 不要。CSV設定済みのため |
| 7-2 | 従業員による自己アカウント削除 | **不可**。PF版 `deleteUserAccount` は `EnterpriseMember` を処理しないため UI も Callable も提供しない（§6.3） |
| 7-3 | 従業員によるメールアドレス変更 | **MVP では不可**。ログイン識別子は CSV 登録時の `user_email` と `allowed_email_domains` に依存（§6.3） |
| 8-1 | メンバー一覧のメール取得 | Functions 集約方式（`getEnterpriseMembers`）。Rules は本人 read のみ据え置き |
| 8-2 | 未認証 Callable の濫用対策 | MVP で App Check を有効化（`getEnterpriseByDomain` / `requestEnterpriseEmailLogin` / `confirmEnterpriseEmailLogin`）。レート制限等は将来 |
| 8-3 | 企業・初代 admin 作成 | 運営専用 `createEnterprise`（`04_オンボーディング` 参照） |
| 8-4 | Phase 3 admin Callable の App Check | **enforce しない**（認証必須のため。§8-3 参照） |
| 8-5 | 最後の admin 停止防止 | `disableEnterpriseMember` で有効 admin が1人のみの場合は停止不可（§6.1） |

### Phase 2 で対応する項目

- OTP有効期限の短縮（10〜15分）
- OTP最大試行回数の制限（5回でロック）
- OTP再送間隔の制限（60秒クールダウン）
- アカウント作成完了メールの送信
- 本人によるセルフ登録（allowed_email_domains に該当するメールアドレスで本人が直接アカウント作成）
- PF版アカウントとの統合（「昇格」フロー）
- エンプラ専用メール変更フロー（`confirmEmailChange` 用 pass-code 分岐、または管理者操作）
- エンプラ退会フロー（`EnterpriseMember` 停止と Auth 無効化の一括。自己削除 UI は本フロー実装後のみ検討）


# 2. ログインフロー

## 2.1 全体フロー

```
① ユーザーがエンタープライズ版のURL（例: company-a.shokujii.com）にアクセス
② アプリがドメインから enterprise_id を特定（[02_アーキテクチャ](./02_アーキテクチャ.md) 2.4 参照）
③ ログイン画面を表示（企業ロゴ + テーマカラー適用、SNSログインボタンなし）
④ ユーザーがメールアドレスを入力
⑤ フロントエンドでメールドメインバリデーション（即時フィードバック）
⑥ requestEnterpriseEmailLogin（Functions）を呼び出し
   → メールドメインの二重チェック
   → 登録済みメンバーか確認
   → OTP生成・SendGrid で送信
⑦ OTP入力画面に遷移
⑧ ユーザーが6桁OTPを入力
⑨ confirmEnterpriseEmailLogin（Functions）を呼び出し
   → OTP検証
   → カスタムトークン発行
⑩ フロントエンドで signInWithCustomToken → ログイン完了
⑪ トップページへ遷移（初回ログインでもプロフィール設定画面には遷移しない）
```

## 2.2 ログイン画面の仕様

### 画面構成

| 要素 | 内容 |
|:--|:--|
| 企業ロゴ | `/enterprises/{enterpriseId}` の `company_logo_url` を表示 |
| テーマカラー | `/enterprises/{enterpriseId}` の `theme_color` を適用 |
| メールアドレス入力欄 | 必須。メール形式バリデーション |
| ログインボタン | 「ログイン」ラベル |
| SNSログインボタン | **従業員向けには表示しない** |

### PF版ログイン画面との差分

PF版 `user/src/pages/login.vue` では Google / Facebook / X のSNSログインボタンを表示しているが、エンタープライズ版の**従業員向け**ではメールアドレス + OTP のみとする。ログイン画面は `enterprise/src/pages/login.vue` として新規作成する。

### ゲスト向け認証（04_ゲスト参加 との整合）

ゲスト（allow_guest イベントに参加するプラットフォーム版ユーザー）が注文するには認証が必要。ログイン画面に「ゲストの方はこちら」セクションを追加し、**PF版と同等の認証方式**を提供する。

| 項目 | 内容 |
|:--|:--|
| メールアドレス+OTP | PF版の `requestEmailLogin` / `confirmEmailLogin` を流用。メールドメイン制限なし |
| SNSログイン | Google / Apple 等。PF版と同様 |
| custom claims | 設定しない（ゲストは `enterprise_id` を持たない） |
| アクセス範囲 | `allow_guest == true` のイベントのみ |

詳細は `04_ゲスト参加` 2.4 を参照。

**Phase 2（認証）での実装範囲**: ログイン画面のゲストセクションは **Phase 5（ゲスト参加）で追加**する。Phase 2 では従業員向けメール+OTPのみ実装し、ログイン画面は「従業員ログイン」をコンポーネント分離した構造にしておく（Phase 5 でゲストセクションを挿入可能にする）。


# 3. メールドメインバリデーション

## 3.0 メールアドレス正規化（共通ルール）

エンタープライズ版のすべてのメールアドレス入口で、`trim().toLowerCase()` による正規化を行う。

| 対象 | 正規化タイミング |
|:--|:--|
| `requestEnterpriseEmailLogin` / `confirmEnterpriseEmailLogin` | リクエスト受信直後 |
| `createEnterpriseMembers` / `createEnterprise`（初代 admin） | バリデーション前 |
| `/users_personal_information` への保存 | アカウント作成時（`saveUser` 経由） |

**理由**: `getUserIdFromEmail` は `user_email` の完全一致検索のため、大文字混じり入力で逆引きに失敗する。エンプラアカウントは新規作成時に正規化して保存する（PF版との重複は MVP でエラーとするため、PF側の既存データとの衝突は起きない）。**PF版の既存メール保存・検索ロジックは変更しない。**

## 3.1 フロントエンド（即時フィードバック）

```
1. ユーザーがメールアドレスを入力
2. @以降のドメインを抽出
3. アプリ起動時に取得済みの enterprise.allowed_email_domains と照合
4. 一致しない場合 →「このメールアドレスではログインできません」を即時表示
5. 一致する場合 → ログインボタンを有効化
```

### 実装イメージ

```typescript
const validateEmailDomain = (email: string, allowedDomains: string[]): boolean => {
  const domain = email.split('@')[1]
  return allowedDomains.includes(domain)
}
```

## 3.2 Functions 側（セキュリティ担保）

フロントエンドのバリデーションはバイパス可能なため、Functions 側でも同じチェックを行う。

```
1. requestEnterpriseEmailLogin で enterprise_id + email を受け取る
2. /enterprises/{enterpriseId} の allowed_email_domains を取得
3. メールドメインが含まれるかチェック
4. 含まれない → HttpsError('permission-denied', 'このメールアドレスではログインできません')
5. 含まれる → 次のステップへ
```


# 4. Functions 設計

PF版の `requestEmailLogin` / `confirmEmailLogin` を拡張せず、エンタープライズ専用の Functions を新規作成する。エンタープライズ固有のロジック（ドメインチェック、メンバー存在確認、custom claims）が多く、既存を壊すリスクを避けるため。

## 4.0 getEnterpriseByDomain

ドメイン（hostname）から企業情報を取得する。ログイン画面の表示に使用する。未認証ユーザーから呼び出されるため、認証不要。

### リクエスト

```typescript
interface GetEnterpriseByDomainRequest {
  hostname: string  // 例: "company-a.shokujii.com" or "lunch.company-a.com"
}
```

### 処理フロー

```
1. hostname を受け取る
2. サブドメイン方式の判定: hostname が "*.{ENTERPRISE_BASE_DOMAIN}" パターンか確認
   → ENTERPRISE_BASE_DOMAIN（Functions の環境変数。defineString）からパターンを組み立てる
   → サブドメイン部分を抽出し、/enterprises で subdomain == 抽出値 のドキュメントを検索
   → ENTERPRISE_BASE_DOMAIN 未設定の場合はこのステップをスキップ（custom_domain のみで判定）
3. カスタムドメイン方式の判定: 2 でヒットしない場合
   → /enterprises で custom_domain == hostname のドキュメントを検索
4. いずれもヒットしない → HttpsError('not-found', '企業が見つかりません')
5. is_active == false → HttpsError('not-found', '企業が見つかりません')
6. 公開情報のみをレスポンスとして返す
```

**ベースドメインの環境変数化**: サブドメイン判定のベースドメイン（例: 本番 `shokujii.jp`、dev `shokujii.com`）はコードにハードコードせず、Functions は `ENTERPRISE_BASE_DOMAIN`、フロントは `VITE_ENTERPRISE_BASE_DOMAIN` で指定する。sandbox はカスタムドメイン前提（`custom_domain` に Hosting デフォルト URL を登録）のため未設定でも動作する。詳細は `09_デプロイ手順` §4 参照。

### レスポンス

```typescript
interface GetEnterpriseByDomainResponse {
  enterprise_id: string
  company_name: string
  company_logo_url: string
  theme_color: string
  subdomain: string                  // 実装済み。維持
  allowed_email_domains: string[]    // フロント即時バリデーション用（§3.1）
}
```

`common/src/apis/enterprise.ts` の `GetEnterpriseByDomainResponse` 型と一致させること。

### セキュリティ上の注意

- 認証不要のため、返却する情報は公開情報に限定する
- 割引設定、請求設定、メンバー情報などは返却しない
- `allowed_email_domains` はログイン試行で推測可能な情報であり秘匿価値は低い。即時バリデーション（§3.1）に必須のためレスポンスに含める
- **MVP で App Check を有効化**する（ボットによるドメイン列挙攻撃の防止。対象は §4.0 / §4.1 / §4.2 参照）
- IP ベースのレート制限は将来検討

## 4.1 requestEnterpriseEmailLogin

OTP を生成し、SendGrid で送信する。**MVP で App Check を有効化**する（未認証 Callable の濫用対策。レート制限等の詳細制御は将来）。

### リクエスト

```typescript
interface RequestEnterpriseEmailLoginRequest {
  enterprise_id: string
  email: string
}
```

### 処理フロー

```
1. enterprise_id + email を受け取る（email は §3.0 で正規化）
2. /enterprises/{enterpriseId} を取得
   → 存在しない or is_active == false → HttpsError('not-found')
3. メールドメインバリデーション
   → allowed_email_domains に含まれない → HttpsError('permission-denied')
4. メールアドレスからメンバーを特定（2段階検索）
   a. /users_personal_information で user_email == email のドキュメントを検索し userId を取得
   b. /enterprises/{enterpriseId}/members/{userId} が存在するか確認
   → a で該当なし or b で該当なし → HttpsError('not-found', '登録されていません。管理者にお問い合わせください')
   → b で is_active == false → HttpsError('permission-denied', 'アカウントが停止されています')
5. OTP を生成（PF版と同じ PassCode クラスを使用）
6. /pass_code にOTPを保存（PF版と同じコレクションを共有）
7. SendGrid でOTPメールを送信
8. レスポンスを返す
```

**補足: メンバー検索が2段階になる理由**
`/enterprises/{id}/members` のスキーマにはメールアドレスフィールドがないため、まず `/users_personal_information` で email → userId を逆引きし、次にその userId で members コレクションの所属を確認する。

### レスポンス

```typescript
interface RequestEnterpriseEmailLoginResponse {
  success: true
}
```

### PF版との違い

- PF版は新規ユーザーかどうかを `isNew` で返すが、エンタープライズ版では新規作成が発生しないため不要
- メールドメインバリデーションとメンバー存在確認を追加

### pass_code コレクションの共有について

MVPでは PF版と同じ `/pass_code` コレクションを共有する。`getValidPassCodeFromEmail` も PF版と共通で使用する。将来 OTP有効期限をエンプラ版のみ短縮する場合（補足資料A参照）、コレクション分離またはクエリ条件の分岐が必要になる。

### OTP メール（SendGrid テンプレート）

テンプレートの内容（件名・本文骨子・差し込み変数）の正本は [`documents/sendgridテンプレ/01_enterprise_pass_code.md`](../../sendgridテンプレ/01_enterprise_pass_code.md)。

| 項目 | 仕様 |
|:--|:--|
| テンプレート | **エンプラ専用**を新規作成。PF版の `USER_PASS_CODE_TEMPLATE_ID` は流用しない（PF前提文言が含まれる可能性があるため）。SendGrid アカウント・テンプレートは sandbox / 本番で共有 |
| 定数名 | `ENTERPRISE_PASS_CODE_TEMPLATE_ID`（`functions/default/src/enterprise/auth.ts` にハードコード。PF版 `USER_PASS_CODE_TEMPLATE_ID` と同方式） |
| 差し込み変数 | `user_pass_code`（6桁。PF版テンプレとキー名を統一）、`company_name`（`/enterprises/{id}` の `company_name`） |
| 企業ブランディング | MVP は社名テキスト差し込みのみ。ロゴ画像の動的差し込みは将来対応 |
| 差出人 | PF版と同じ `DEFAULT_FROM` |
| 有効期限の記載 | 「24時間」（PF版と同じ `PASS_CODE_DURATION`。将来短縮時にテンプレートも更新） |

## 4.2 confirmEnterpriseEmailLogin

**MVP で App Check を有効化**する（OTP ブルートフォース対策。§8-2 参照）。

OTP を検証し、カスタムトークンを発行する。

### リクエスト

```typescript
interface ConfirmEnterpriseEmailLoginRequest {
  enterprise_id: string
  email: string
  pass_code: string
}
```

### 処理フロー

```
1. enterprise_id + email + pass_code を受け取る（email は §3.0 で正規化）
2. /pass_code から有効なOTPを取得（PF版と同じ getValidPassCodeFromEmail を使用）
   → 存在しない or 不一致 → HttpsError('invalid-argument', 'パスコードが正しくありません')
3. /users_personal_information で user_email == email のドキュメントを検索し userId を特定
4. /enterprises/{enterpriseId}/members/{userId} が存在するか確認
   → 存在しない → HttpsError('not-found', '該当する企業のメンバーではありません')
   → is_active == false → HttpsError('permission-denied', 'アカウントが停止されています')
   （enterprise_id とメンバーの所属を検証し、別企業のOTPを流用した不正ログインを防止する）
5. OTPドキュメントを削除（所属確認成功後。設定ミス等で所属確認が失敗した場合に再送を強いない）
6. custom claims の再同期: getAuth().getUser(uid) で現 claims を取得し、
   { enterprise_id, enterprise_role: member.role, user_type: 'enterprise' } と不一致なら
   setCustomUserClaims で再設定（手動修復・移行後のドリフトをログイン時に自己修復）
7. カスタムトークンを発行: getAuth().createCustomToken(uid)
8. 監査ログを記録（action: 'login'）
9. レスポンスを返す
```

### レスポンス

```typescript
interface ConfirmEnterpriseEmailLoginResponse {
  token: string
}
```

### PF版との違い

- PF版は `isNew: true` の場合に Firebase Auth ユーザーの新規作成と `/users` ドキュメントの作成を行うが、エンタープライズ版ではアカウント作成済みが前提のためこの処理は不要
- enterprise_id の所属検証を追加（別企業からの不正ログイン防止）
- 監査ログの記録を追加


# 5. アカウント一括作成（CSV）

全社管理者が CSV をアップロードし、従業員アカウントを一括作成する。

## 5.1 CSV フォーマット

```csv
email,display_name,department,role
tanaka@company-a.com,田中太郎,開発部,member
suzuki@company-a.com,鈴木花子,人事部,admin
yamada@company-a.com,山田一郎,営業部,member
```

| 列 | 必須 | 説明 | バリデーション |
|:--|:--|:--|:--|
| email | 必須 | メールアドレス | メール形式 + allowed_email_domains に含まれること |
| display_name | 必須 | 表示名 | 空文字不可 |
| department | 任意 | 部署名 | |
| role | 任意 | ロール | "admin" or "member"。省略時は "member" |

## 5.2 処理上限・パフォーマンス

- 1回のCSVアップロードで最大 **500件**
- Firebase Auth の `createUser` のレート制限を考慮
- Functions のタイムアウトを **300秒**に設定（デフォルト60秒では500件処理に間に合わない可能性がある）
- 1件あたり最大5つの非同期処理（Auth createUser + setCustomUserClaims + Firestore 3ドキュメント作成）が発生するため、並列度を制御して処理する（例: 10件ずつの並列バッチ）

## 5.3 Functions: createEnterpriseMembers

### リクエスト

```typescript
interface CreateEnterpriseMembersRequest {
  enterprise_id: string
  members: {
    email: string
    display_name: string
    department?: string
    role?: 'admin' | 'member'
  }[]
}
```

### 処理フロー（行ごと）

```
1. バリデーション
   a. メール形式チェック
   b. メールドメインが allowed_email_domains に含まれるか
   c. display_name が空でないか
   d. role が "admin" or "member" であるか（省略時は "member"）
   e. 同一CSV内での重複メールチェック
   f. 既存アカウントとの重複チェック（2段階検索）
      i.  /users_personal_information で user_email == email のドキュメントを検索
      ii. 該当あり → そのuserIdが /enterprises/{id}/members に存在するか確認
          - members に存在する → エラー: 「このメールアドレスは既に登録済みです」（エンプラ版重複）
          - members に存在しない → エラー: 「このメールアドレスは既に別のアカウントで使用されています」（PF版重複）
      iii. 該当なし → 新規ユーザーとして続行

2. Firebase Auth ユーザーを作成（**tenant-aware**）
   a. `/enterprises/{enterpriseId}` から `tenant_id` を取得
   b. `getAuth().tenantManager().authForTenant(tenantId).createUser({ email, emailVerified: true })`

3. custom claims を設定（同一 tenant Auth インスタンス）
   authForTenant(tenantId).setCustomUserClaims(uid, {
     enterprise_id,
     enterprise_role: role,
     user_type: 'enterprise'
   })

4. Firestore ドキュメントを作成
   a. /enterprises/{enterpriseId}/members/{userId}
      初期値: {
        user_id, role, display_name, department,
        is_active: true,
        last_activated_at: serverTimestamp(),
        last_deactivated_at: null,
        monthly_usage: {},                 // 月別の補助利用合計（円）
        monthly_order_count: {},           // 月別の ordered な member_orders ドキュメント数
        created_at: serverTimestamp(),
        updated_at: serverTimestamp()
      }
      ※ monthly_usage / monthly_order_count の更新責務は本 Function ではなく
        confirmOrder / stripeWebhook / cancelOrders にある（04_割引・決済 3.4 参照）
   b. /users/{userId}（user_type: 'enterprise', enterprise_id を設定）
   c. /users_personal_information/{userId}（user_email を設定）

5. 監査ログを記録（action: 'account_create'）
```

> **実装追随（別 Issue）**: 現行 `functions/default/src/enterprise/members.ts` / `onboarding.ts` は project-level `getAuth().createUser` のまま。本仕様（tenant-aware）への追随は IdP Phase 1 実装タスクとして別途行う。`createEnterprise`（初代 admin）も同様に `authForTenant(tenantId)` 経由とする。

### エラーハンドリング

- **エラー行スキップ方式**: バリデーションエラーの行はスキップし、残りの行を処理する
- 全行の処理完了後、行ごとの成功/失敗を結果として返す

### レスポンス

```typescript
interface CreateEnterpriseMembersResponse {
  total: number
  success_count: number
  error_count: number
  results: {
    row: number          // CSV の行番号（1始まり、ヘッダー除く）
    email: string
    status: 'success' | 'error'
    error_message?: string
  }[]
}
```

### エラーメッセージ例

| エラー | メッセージ |
|:--|:--|
| メール形式不正 | メールアドレスの形式が正しくありません |
| ドメイン不一致 | 許可されていないメールドメインです |
| PF版との重複 | このメールアドレスは既に別のアカウントで使用されています |
| エンプラ版での重複 | このメールアドレスは既に登録済みです |
| display_name 空 | 表示名は必須です |

## 5.4 PF版メールアドレスとの重複について

MVPでは PF版に同じメールアドレスが存在する場合はエラーとする。

**理由:**
- 1メールアドレス = 1アカウントの原則を維持し、Security Rules をシンプルに保つ
- エンタープライズ版は企業メールドメインが前提であり、PF版に企業メールで登録しているユーザーは少ない
- 万が一重複した場合は、PF版のメールアドレスを変更すれば解決できる

**Phase 2 での対応:**
- PF版アカウントをエンタープライズ版に「昇格」するフローを追加
- 既存アカウントに enterprise_id と custom claims を付与する方式


# 6. アカウント停止・復活

全社管理者がメンバーのアカウントを停止・復活する。

## 6.1 アカウント停止: disableEnterpriseMember

### 処理フロー

```
1. 全社管理者が管理画面からアカウント停止を実行
2. Functions: disableEnterpriseMember を呼び出し
3. 最後の有効 admin を停止しようとしていないかチェック
   → role == 'admin' かつ is_active == true のメンバーが1人のみで、対象がその1人の場合
   → HttpsError('failed-precondition', '最低1人の有効な管理者が必要です')
   （updateEnterpriseRole の「最後の admin 降格不可」と対になる）
4. Firebase Auth のユーザーを無効化
   getAuth().updateUser(uid, { disabled: true })
5. リフレッシュトークンを無効化（即時セッション無効化）
   getAuth().revokeRefreshTokens(uid)
6. /enterprises/{enterpriseId}/members/{userId} の is_active を false に更新
   last_deactivated_at を serverTimestamp() で更新（last_activated_at は変更しない）
7. 監査ログを記録（action: 'account_disable'）
```

**custom claims について**: 停止時は **custom claims を変更しない**。Auth の `disabled: true` と Firestore の `is_active: false` で制御する。`requestEnterpriseEmailLogin` は `is_active` を検証し、`revokeRefreshTokens` で既存セッションを無効化する。

### 停止されたユーザーの挙動

- ログイン中の場合: IDトークンの有効期限（最大1時間）が切れたタイミングでログアウトされる
- ログイン試行時: requestEnterpriseEmailLogin で `is_active == false` を検出し、エラーを返す

## 6.2 アカウント復活: enableEnterpriseMember

### 処理フロー

```
1. 全社管理者が管理画面からアカウント復活を実行
2. Functions: enableEnterpriseMember を呼び出し
3. Firebase Auth のユーザーを有効化
   getAuth().updateUser(uid, { disabled: false })
4. /enterprises/{enterpriseId}/members/{userId} の is_active を true に更新
   last_activated_at を serverTimestamp() で更新（**last_deactivated_at は null に戻さない**。`02_課金設計` §2.3）
5. 監査ログを記録（action: 'account_enable'）
```

**custom claims について**: 復活時も **custom claims を変更しない**。Auth の `disabled: false` と Firestore の `is_active: true` で制御する。claims はアカウント作成時またはログイン時の再同期（§4.2 手順6）で維持される。

## 6.3 従業員による自己削除・メール変更（MVP では不可）

### 自己アカウント削除

- エンタープライズ版では **従業員がプロフィール設定画面（`/profile`）からアカウントを削除する機能を提供しない**。
- PF版 `deleteUserAccount` は `/users` と Auth のみ匿名化し、`/enterprises/{eid}/members/{uid}` の `EnterpriseMember` を停止・削除しない。
  - active な `EnterpriseMember` が残り **課金対象・管理対象に見え続ける**（`02_課金設計` §2.3）。
  - `/users_personal_information` の `user_email` が消えるため **同一メールでの再ログイン・再作成が破綻**しうる。
- 退職・アカウント無効化は **全社管理者の `disableEnterpriseMember`（§6.1）** に一本化する（`03_セキュリティチェックシート` 1-9 と整合）。

### メールアドレス変更

- エンタープライズ版では **従業員によるセルフサービスのメール変更 UI を提供しない**。
- PF版 `requestEmailChange` で送られる OTP は、エンプラの `/pass-code`（`confirmEnterpriseEmailLogin`）では完了できない。
  - 新メールはまだ `EnterpriseMember` / `users_personal_information` に紐づかず `member not found` となる。
- MVP ではメール変更が必要な場合は **全社管理者への依頼**とする。管理者向けメール変更 Callable や CSV 再登録は **Phase 2 で検討**（§1.2 Phase 2 参照）。

### Phase 2 で検討する項目

- エンプラ専用メール変更フロー（`confirmEmailChange` 用 pass-code 分岐、または管理者操作）
- エンプラ退会フロー（`EnterpriseMember` 停止 + Auth 無効化を一括で行う Callable）— 自己削除 UI の復活は本フロー実装後のみ


# 7. ロール変更

全社管理者がメンバーのロールを変更する。

## 7.1 updateEnterpriseRole

### 処理フロー

```
1. 全社管理者が管理画面からロール変更を実行
2. Functions: updateEnterpriseRole を呼び出し
3. 最後の admin を member に降格しようとしていないかチェック
   → 最後の admin の場合 → HttpsError('failed-precondition', '最低1人の管理者が必要です')
4. custom claims を更新
   getAuth().setCustomUserClaims(uid, { ...既存claims, enterprise_role: newRole })
5. /enterprises/{enterpriseId}/members/{userId} の role を更新
6. 監査ログを記録（action: 'role_change', details: { old_role, new_role }）
```

### custom claims の即時反映について

`setCustomUserClaims` を呼んでも、既存のIDトークンは最大1時間有効なまま残る。対象ユーザーがブラウザを開いている場合、ロール変更は IDトークンの自動更新タイミング（約1時間後）まで反映されない。

**MVP での対応:**
- ロール変更は即座に Firestore の `/enterprises/{id}/members/{userId}` に反映されるため、アプリ側でメンバー情報を Firestore から取得する画面（管理者画面等）では即時反映される
- Security Rules レベルでのロール反映は最大1時間の遅延がある（IDトークンの有効期限）

**Phase 2 での改善案:**
- フロントエンドでロール変更を検知し、`getIdToken(true)` で強制的にトークンを更新するリアルタイムリスナーを追加


# 8. セッション管理

`02_アーキテクチャ` の 4.3 節で設計済み。ここでは画面仕様に関する補足のみ記載する。

## 8.1 無操作タイムアウト

- **1週間**間無操作で自動ログアウト
- 監視するイベント: click, keydown, scroll, mousemove
- **実装方式**: `localStorage` の `enterprise:last_activity_at`（epoch millis）で最終操作時刻を記録し、各タブが 60 秒間隔の `setInterval` と `visibilitychange`（復帰時）で `now - last_activity_at > 1週間` を判定する（[02_アーキテクチャ](./02_アーキテクチャ.md) §4.3 参照）
- localStorage への書き込みは 10 秒間隔で throttle する
- **適用範囲**: enterprise アプリ上の**全ログインセッション**（ゲスト含む。Phase 5 でゲスト参加を実装した場合も同一タイムアウトを適用）
- ログアウト時はログイン画面にリダイレクト

## 8.2 タイムアウト時のUX

```
1. 1週間無操作（localStorage の last_activity_at で判定）
2. logEnterpriseLogout（action: session_timeout）を await（失敗時は握りつぶす）
3. auth.signOut() を実行
4. ログイン画面にリダイレクト
5. 「セッションがタイムアウトしました。再度ログインしてください」をトースト表示
```

手動ログアウト時も同順序: `logEnterpriseLogout`（action: logout）を **await してから** `signOut()`。

## 8-3 Phase 3 admin Callable の App Check

Phase 2 で App Check を有効化する対象は**未認証 Callable 3つ**（`getEnterpriseByDomain` / `requestEnterpriseEmailLogin` / `confirmEnterpriseEmailLogin`）に限定する。

Phase 3 で追加する admin 認証済み Callable（`getEnterpriseMembers` / `createEnterpriseMembers` / `disableEnterpriseMember` 等）には **`enforceAppCheck: true` を付けない**。Firebase Auth 必須のため、App Check なしでもボット濫用リスクは Phase 2 の未認証入口より低い。

## 8.3 ログアウト時の監査ログ

| トリガー | action |
|:--|:--|
| ユーザーが手動でログアウト | logout |
| セッションタイムアウト | session_timeout |

ログアウト時は `logEnterpriseLogout`（Functions）を呼び出して監査ログを記録する。**`signOut()` の前に呼び出す**（signOut 後は unauthenticated になるため）。Functions 呼び出し失敗時は握りつぶし、signOut は必ず実行する。

**注意: ベストエフォートでの記録**
ログアウト・タイムアウトの監査ログはフロントエンドから Functions を呼び出す方式のため、以下のケースでは記録されない可能性がある:
- ブラウザを直接閉じた場合
- ネットワーク切断中にタイムアウトした場合
- ブラウザがクラッシュした場合

これらのケースでの完全な記録が必要な場合は、Phase 2 でサーバーサイドのセッション管理を検討する。

### assertEnterpriseAdmin（共通ヘルパ）

Phase 3 の admin 限定 Callable 冒頭で使用する。`functions/default/src/utils/enterpriseAuthHelpers.ts` に定義。

```typescript
function assertEnterpriseAdmin(
  auth: CallableRequest['auth'],
  enterpriseId: string,
): asserts auth is NonNullable<typeof auth> {
  if (auth?.uid == null) throw new HttpsError('unauthenticated', 'not logged in')
  if (auth.token.enterprise_id !== enterpriseId || auth.token.enterprise_role !== 'admin') {
    throw new HttpsError('permission-denied', 'enterprise admin only')
  }
}
```

## 9.1 getEnterpriseMembers

admin 向けメンバー一覧取得。`EnterpriseMember` と `/users_personal_information` の `user_email` を Functions 内で join して返す。

### リクエスト

```typescript
interface GetEnterpriseMembersRequest {
  enterprise_id: string
  search?: string           // display_name 前方一致 + email 部分一致
  role?: 'admin' | 'member' | 'all'
  is_active?: boolean       // undefined = 全件
  sort_by?: 'display_name' | 'department' | 'role' | 'is_active' | 'created_at' | 'monthly_usage'  // monthly_usage: 当月 YYYY-MM キー（JST）
  sort_order?: 'asc' | 'desc'
  page?: number             // 1 始まり。既定 1
  page_size?: number        // 既定 50
}
```

### 処理フロー

```
1. assertEnterpriseAdmin（enterprise_id 一致 + enterprise_role == 'admin'）
2. /enterprises/{enterpriseId}/members を Firestore から全件取得
3. 各 userId で /users_personal_information/{userId} から user_email を取得（Admin SDK）して join
4. Functions 内で search / role / is_active による filter
   - search: display_name 前方一致 + email 部分一致
5. Functions 内で sort_by / sort_order による sort
   - sort_by == 'monthly_usage' のとき、リクエスト実行時点の暦月キー（`YYYY-MM`、JST）の辞書値で比較（`04_全社管理者画面` §4.1「当月利用額」列と整合）
6. total_count を算出後、page / page_size でスライス（ページ番号方式）
7. レスポンス返却
```

> **ページネーション方針**: search / sort が全件メモリ処理のため、カーソル（`startAfter`）は採用しない。企業内メンバー数は小〜中規模を前提とし、全件取得 → スライスとする。将来数千件超で性能問題が出た場合にカーソル化を再検討する。

### レスポンス

```typescript
interface GetEnterpriseMembersResponse {
  members: {
    user_id: string
    display_name: string
    department?: string
    role: 'admin' | 'member'
    is_active: boolean
    email: string
    monthly_usage: Record<string, number>
    created_at: number
  }[]
  total_count: number
}
```

**`/users_personal_information` の Rules は本人 read のみ据え置き**とする。admin がメールを見る経路は本 Function のみ。

| ソート | `sort_by` / `sort_order`（テーブル列ヘッダと連動） |
| アクション | 停止 / 復活 / ロール変更 |
| CSV一括作成ボタン | /admin/members/import に遷移 |

**メールアドレスの取得について**

`EnterpriseMember` スキーマにはメールアドレスフィールドがない。**MVP では Functions 集約方式**を採用する。

- Callable `getEnterpriseMembers`（admin 限定）が `EnterpriseMember` 一覧に `/users_personal_information` の `user_email` を join して返す
- `/users_personal_information` の Security Rules は**本人 read のみ据え置き**（admin 向け Rules 緩和は行わない）
- フロントエンドは Firestore 直接 read ではなく `getEnterpriseMembers` を呼び出す

| 操作 | コレクション | 読み/書き | 実行者 |
|:--|:--|:--|:--|

### 注意: ドメインから企業情報取得について

ログイン画面表示時（未認証状態）に `/enterprises` コレクションの企業情報（ロゴ、テーマカラー、allowed_email_domains）を取得する必要がある。Security Rules で未認証でも特定フィールドのみ読み取り可能にするか、Cloud Functions 経由で取得するかの設計判断が必要。

**MVP での方針:**
- Cloud Functions 経由で取得する（`getEnterpriseByDomain`）
- 未認証ユーザーに Firestore への直接アクセスを許可しない
- 取得する情報は公開情報（企業名、ロゴ、テーマカラー、allowed_email_domains）に限定


# 12. Security Rules（認証・アカウント管理に関連する部分）

`02_アーキテクチャ` **5.2** が EnterpriseMember の Security Rules の**正本**である。以下は同一内容の抜粋（認証・アカウント管理の文脈で参照しやすくするため）。

```javascript
// EnterpriseMember 情報: 同一企業のメンバーは全員閲覧可能、書き込みは Functions のみ
// （monthly_usage の更新が confirmOrder / stripeWebhook / cancelOrders からの Functions 書き込みのため、
//  クライアント直接書き込みは禁止）
match /enterprises/{enterpriseId}/members/{userId} {
  allow read: if request.auth.token.enterprise_id == enterpriseId;
  allow write: if false;   // すべて Functions 経由
}

// パスコード: クライアントからの直接アクセスは禁止（Functions のみ）
match /pass_code/{passCodeId} {
  allow read, write: if false;
}
```

**補足:**
- メンバーの作成・停止・復活・ロール変更はすべて Functions（Admin SDK）経由で行うため、Security Rules では `write: if false` で十分
- **`/users_personal_information` は本人 read のみ**（admin 向け Rules 緩和は行わない）。admin のメール表示は `getEnterpriseMembers`（§9.1）経由
- `monthly_usage` / `monthly_order_count` も Functions（`confirmOrder` / `stripeWebhook` / `cancelOrders`）からのみ更新される（04_割引・決済 3.4 / 5 参照）
- `/pass_code` はPF版で既にクライアントからのアクセスを禁止しているはずだが、念のため確認が必要
- `EventMember` (`/communities/{cid}/events/{eid}/members/{uid}`) の Rules は 02_アーキテクチャ 5.2 を参照。`is_guest` フラグはここに保存される

# 補足資料: Phase 2 仕様概要

MVPでは実装しないが、Phase 2 以降で対応する項目の仕様概要を記載する。
実装時に詳細仕様を別途策定する前提のドラフトである。


## A. OTP有効期限の短縮

### 背景

MVPでは PF版と同じ24時間。セキュリティチェックシートで「OTPの有効期限は？」と聞かれた際に「15分」と回答できるようにするため短縮する。

### 仕様概要

- 変更後の有効期限: 10〜15分
- 変更箇所: `/pass_code` のクエリ条件（`created_at` の差分チェック）
- PF版への影響判断が必要:
  - 案A: common の `PASS_CODE_DURATION` を短縮（PF版にも影響）
  - 案B: エンプラ用に `ENTERPRISE_PASS_CODE_DURATION` を別定数として追加


## B. OTP最大試行回数の制限

### 背景

ブルートフォース攻撃対策。6桁OTPは100万通りしかないため、試行回数制限がないとセキュリティリスクとなる。

### 仕様概要

- 5回連続でOTPを間違えた場合、15分間アカウントを一時ロック
- 実装方式: `/pass_code` ドキュメントに `attempt_count` フィールドを追加
  - `confirmEnterpriseEmailLogin` 呼び出し時にカウントアップ
  - 5回到達 → `locked_until = now + 15分` を設定
  - `requestEnterpriseEmailLogin` 時に `locked_until` をチェック
- ロック解除: 15分経過で自動解除。管理者による手動解除は不要
- フロントエンド: ロック中は「しばらく時間をおいてから再度お試しください」を表示


## C. OTP再送間隔の制限

### 背景

OTPメールのスパム送信を防ぐUX改善。

### 仕様概要

- 60秒のクールダウン期間中はOTPの再送を制限
- 実装箇所: フロントエンドのみ（Functions 側の制限は不要）
  - 「再送信」ボタンを60秒間無効化し、カウントダウンを表示
  - 60秒経過後にボタンを有効化


## D. アカウント作成完了メール

### 背景

CSVでアカウントを一括作成した後、対象者にログイン方法を通知する。

### 仕様概要

- `createEnterpriseMembers` でアカウント作成成功後、対象者に通知メールを送信
- メール内容:
  - 件名: shokujii のアカウントが作成されました
  - 本文: ログインURL、メールアドレス、初回ログイン手順の案内
- SendGrid テンプレートを新規作成（PF版とは別テンプレート）
- 送信タイミング: 一括作成の成功行ごとに送信
- 500件一括作成時の送信負荷: SendGrid のレート制限を考慮しバッチ送信を検討


## E. 本人によるセルフ登録

### 背景

管理者の事前登録なしに、正しい企業メールドメインを持つ本人が自分でアカウントを作成できる機能。中小企業や、入社直後の従業員が即座に利用開始できるメリットがある。

### 仕様概要

- フロー:
  1. ログイン画面でメールアドレスを入力
  2. `allowed_email_domains` に該当 → OTP送信
  3. OTP検証成功
  4. `/enterprises/{id}/members` に存在しない → 新規作成フローに分岐
  5. 表示名・部署を入力する画面を表示
  6. アカウント作成（Firebase Auth + Firestore + custom claims）
  7. 管理者への通知（新しいメンバーが自己登録しました）
- 企業設定に `allow_self_registration: boolean` フラグを追加し、企業ごとにON/OFF可能にする
- セキュリティ上の考慮: ドメインを持つ人なら誰でも登録できるため、管理者承認フローの追加も検討


## F. PF版アカウントとの統合（昇格フロー）

### 背景

PF版に同じメールアドレスで登録済みのユーザーを、エンタープライズ版に移行する機能。MVPでは重複をエラーとしているが、将来的にはスムーズな移行を提供する。

### 仕様概要

- フロー:
  1. CSV一括作成時に PF版との重複を検出
  2. エラーではなく「昇格候補」として結果に表示
  3. 管理者が昇格を承認
  4. Functions で既存アカウントに `enterprise_id` と custom claims を付与
  5. `/users/{userId}` に `user_type: 'enterprise'`, `enterprise_id` を設定
  6. `/enterprises/{id}/members/{userId}` ドキュメントを作成
- 考慮事項:
  - PF版での注文履歴・コミュニティ参加状況はそのまま維持
  - PF版のSNSログイン連携は解除するか維持するかの判断が必要
  - 昇格後にエンタープライズ契約終了した場合のPF版への戻し（降格）を想定するか
