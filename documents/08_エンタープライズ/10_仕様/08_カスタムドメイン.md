# エンタープライズ カスタムドメイン

エンプラ版の **テナント URL**（サブドメイン方式・企業別カスタムドメイン）の仕組みと、Firebase Hosting / DNS / Auth への接続手順の正本。

- アーキテクチャ概要: [02_アーキテクチャ.md](./02_アーキテクチャ.md) §2
- テナント解決（Auth）: [05_認証・テナント.md](./05_認証・テナント.md)
- Hosting 初回セットアップ・ENTERPRISE_ENV: [07_デプロイ・運用.md](./07_デプロイ・運用.md)
- development 環境への初回投入順: [03_デプロイ手順.md](../00_計画/03_デプロイ手順.md)

---

## 1. 基本方針

- **1 環境 = enterprise Hosting サイト 1 つ**（例: `bokudeli-event-test-enterprise`）。全企業が同じビルドを共有する。
- 企業ごとに Hosting サイトや DNS レコードを増やさない（**ワイルドカード方式**が理想）。
- アクセス中の **ホスト名** から Firestore `/enterprises` を引き、ブランディング・テナント境界を決める。
- PF 版（`user`）とエンプラ（`enterprise`）は **Hosting サイトが別**。同じ apex 配下でもサブドメインで分ける。

> **Firebase Console の制約**: 標準 Firebase Hosting は **wildcard カスタムドメイン（`*.example.com`）を Console で追加できない**ことが多い（sandbox2510 実績）。その場合は [§6.1b](#61b-console-個別-fqdn-フォールバックsandbox-実績) のとおり **テナント FQDN を個別追加**する。

## 2. 2 つの URL 方式

| 方式 | URL 例 | Firestore フィールド | 用途 |
|:--|:--|:--|:--|
| **サブドメイン（デフォルト・推奨）** | `company-a.test.tabete.co` | `subdomain: "company-a"` | 複数企業を 1 サイト + ワイルドカード DNS で運用 |
| **カスタムドメイン（オプション）** | `lunch.company-c.com` | `custom_domain: "lunch.company-c.com"` | 企業が自社 DNS で CNAME 設定。Hosting にドメイン追加が必要 |

### 2.1 サブドメイン方式の解決フロー

1. ブラウザが `company-a.{BASE_DOMAIN}` で enterprise SPA を開く（例: BASE = `test.tabete.co`）。
2. フロント `useEnterpriseStore` が `window.location.hostname`（またはローカル用 `VITE_ENTERPRISE_SUBDOMAIN`）を `getEnterpriseByDomain` に渡す。
3. Functions `resolveEnterpriseByHostname`（`functions/default/src/utils/enterpriseBaseDomain.ts`）が正規表現 `^([a-z0-9-]+)\.{BASE_DOMAIN}$` で `subdomain` を抽出し Firestore を検索。
4. ヒットした enterprise のロゴ・テーマ・`enterprise_id` で UI を描画。

`ENTERPRISE_BASE_DOMAIN` / `VITE_ENTERPRISE_BASE_DOMAIN` が**未設定**の場合、サブドメイン判定はスキップされ **`custom_domain` 完全一致のみ**（sandbox の [§6.2](#62-webapp-のみdns-なし最小構成) 向け）。`tabete.co` カスタムドメイン利用時は BASE を設定する（[§3.2](#32-sandbox-向け命名tabeteco推奨)）。

### 2.2 カスタムドメイン方式

- 企業ごとに Firebase Hosting へ **その FQDN を追加**し、DNS を Firebase 指示どおり設定する。
- App Check（reCAPTCHA）有効時は、Terraform `enterprise_base_domain` 以外のホストは `allowed_domains` に**個別追加**が必要（[07 §10](./07_デプロイ・運用.md)、RC-117 系）。

## 3. 環境別のベースドメイン

| 環境 | GitHub Environment | Firebase プロジェクト | PF 版 URL | エンプラ BASE_DOMAIN | エンプラ URL 例 |
|:--|:--|:--|:--|:--|:--|
| テスト | `development` | `bokudeli-event-test` | `test.tabete.co` | **`test.tabete.co`** | `company-a.test.tabete.co` |
| 本番 | `production` | `bokudeli-event-dev` | `shokujii.jp` | **`shokujii.jp`** | `company-a.shokujii.jp` |
| sandbox | （個人 repo / `sandbox2510` 等） | `bokudeli-event-yasu-2510` 等 | **`sandbox2510.tabete.co`**（推奨） | **`sandbox2510.tabete.co`** | `yasu-test.sandbox2510.tabete.co` 等 |

> **注意**: Git ブランチ `development` ≠ Firebase `bokudeli-event-dev`（本番 ID）。詳細は [08_カスタムドメイン.md §3](./08_カスタムドメイン.md) / [03_デプロイ手順.md §3](../00_計画/03_デプロイ手順.md)。

### 3.1 PF 版とエンプラのドメイン分担（development / テスト環境）

| ホスト名 | 向け先 Hosting サイト | 備考 |
|:--|:--|:--|
| `test.tabete.co` | `bokudeli-event-test`（**user**） | PF 版。既存 |
| `*.test.tabete.co` | `bokudeli-event-test-enterprise`（**enterprise**） | エンプラ全テナント共用（DNS ワイルドカード。Console は [§6.1b](#61b-console-個別-fqdn-フォールバックsandbox-実績) 参照） |
| `test.tabete.co` 自体 | `*.test.tabete.co` には**マッチしない** | ワイルドカードは 1 ラベル下のみ |

### 3.2 sandbox 向け命名（`tabete.co`・推奨）

個人 sandbox（`bokudeli-event-yasu-2510` 等）も development と**同型**のドメイン分担にできる。Git リモート名 `sandbox2510` と対応させる命名を推奨する。

#### 命名規則

| 要素 | パターン | 例（sandbox2510） |
|:--|:--|:--|
| sandbox 識別子 | `sandbox` + 数字（リモート名と揃える） | `sandbox2510` |
| PF 版（user） | `{識別子}.tabete.co` | `sandbox2510.tabete.co` |
| エンプラ BASE_DOMAIN | `{識別子}.tabete.co`（PF と同値） | `sandbox2510.tabete.co` |
| エンプラ Hosting ワイルドカード（理想） | `*.{識別子}.tabete.co` | `*.sandbox2510.tabete.co` |
| テナント URL | `{subdomain}.{識別子}.tabete.co` | `yasu-test.sandbox2510.tabete.co` |

他 sandbox も同型: `sandbox2603.tabete.co` / `*.sandbox2603.tabete.co` 等。

#### Hosting サイトへの接続（例: `bokudeli-event-yasu-2510`）

| ホスト名 | 向け先 Hosting サイト | 備考 |
|:--|:--|:--|
| `sandbox2510.tabete.co` | `bokudeli-event-yasu-2510`（**user**） | PF 版 |
| `*.{識別子}.tabete.co` またはテナント FQDN | `bokudeli-event-yasu-2510-enterprise`（**enterprise**） | Console wildcard 不可時は [§6.1b](#61b-console-個別-fqdn-フォールバックsandbox-実績) |
| `sandbox2510.tabete.co` 自体 | `*.sandbox2510.tabete.co` には**マッチしない** | §3.1 と同じワイルドカードの性質 |

#### 環境変数（例）

| 変数 | 値 |
|:--|:--|
| `VITE_ENTERPRISE_BASE_DOMAIN` | `sandbox2510.tabete.co` |
| `ENTERPRISE_BASE_DOMAIN` | `sandbox2510.tabete.co` |
| `enterprise_base_domain`（`terraform.tfvars`） | `sandbox2510.tabete.co` |

Firebase Auth: **user** 用に `sandbox2510.tabete.co`、**enterprise OTP** 用にテナント FQDN（例: `yasu-test.sandbox2510.tabete.co`）を `auth_authorized_domains_extra` 等で追加。

#### テナント `subdomain` について

- Firestore の `subdomain` は **`yasu-test` / `company-a` 等のテナント ID** を指定する（`sandbox2510` は環境名であり、テナント subdomain に使わない）。
- URL の第 1 ラベル（`yasu-test.sandbox2510.tabete.co` → `yasu-test`）と Firestore `subdomain` を一致させる。
- `RESERVED_ENTERPRISE_SUBDOMAINS`（`www` / `admin` 等）に抵触しないラベルを選ぶ（[04_詳細_オンボーディング.md](./04_詳細_オンボーディング.md) §3.3）。

## 4. 複数企業を載せるときに増えるもの

| 項目 | 企業追加ごとに必要？ | 内容 |
|:--|:--|:--|
| enterprise Hosting サイト | ❌ | 1 つのまま |
| ワイルドカード DNS / Hosting カスタムドメイン | ❌（理想） / ⚠️（Console 個別 FQDN 時） | 理想: `*.test.tabete.co` 等を **1 回**。Console が wildcard 非対応の場合は **テナント FQDN ごと**に Console + DNS + Auth（[§6.1b](#61b-console-個別-fqdn-フォールバックsandbox-実績)） |
| Firestore `/enterprises` | ✅ | `createEnterprise` で `subdomain`（または `custom_domain`） |
| `ENTERPRISE_BASE_DOMAIN` | ❌ | 環境共通（`tabete.co` 利用時は [§5.4](#54-環境変数functions--フロント) 必須） |
| Firebase Auth authorized domains | ⚠️ | **ワイルドカード非対応**。OTP ログイン検証時はテナント FQDN を追加する運用になり得る |
| **Storage CORS**（チャット画像 `getBlob` / `uploadBytes`） | ⚠️ | GCS は **ワイルドカード不可**。テナント FQDN ごとに `auth_authorized_domains_extra` → **`terraform apply`**（[terraform/README.md](../../../terraform/README.md) Storage CORS、[§5.5](#55-firebase-auth-ログイン時と-storage-corsチャット画像)）。`<PROJECT>-enterprise.web.app` は Terraform 既定 origin に含む（[#2241](https://github.com/nijuniinc/bokudeli-event-new/issues/2241)） |
| reCAPTCHA `allowed_domains` | ⚠️ | ベースドメインは Terraform。`custom_domain` 利用時は個別追加 |

**新規テナント追加の運用（wildcard 利用時）**: `createEnterprise`（subdomain 指定）のみ。Hosting / DNS は触らない（インフラ側 wildcard 済みの場合）。**Storage CORS は GCS 都合で wildcard 不可**のため、テナント URL（`{subdomain}.{BASE}`）を初めて使うときは [§5.5](#55-firebase-auth-ログイン時と-storage-corsチャット画像) のとおり **FQDN 列挙 + `terraform apply` が別途必要**になり得る。

**新規テナント追加の運用（§6.1b フォールバック時）**: 上記に加え、テナント FQDN を Console + DNS（TXT + CNAME）+ **`auth_authorized_domains_extra` + `terraform apply`**（Auth と Storage CORS）。FQDN 行の生成は [terraform/scripts/print-enterprise-tenant-fqdns.sh](../../../terraform/scripts/print-enterprise-tenant-fqdns.sh) を参照。

## 5. 設定手順（サブドメイン方式）

Terraform は **Hosting サイト作成**まで。カスタムドメイン接続は **Firebase Console + DNS**（[07 §3](./07_デプロイ・運用.md)）。

### 5.1 前提

- Hosting サイト `<PROJECT_ID>-enterprise` が存在する（例: `bokudeli-event-test-enterprise`）。
- `firebase target:apply hosting enterprise <SITE_ID>` 済み、`FIREBASERC` 反映済み。

### 5.2 Firebase Console（Hosting）

1. [Firebase Console](https://console.firebase.google.com/) → 対象プロジェクト（例: `bokudeli-event-test`）。
2. **Hosting** → サイト **`bokudeli-event-test-enterprise`** を選択（マルチサイトではサイト選択を誤らない）。
3. **カスタムドメインを追加** → 理想形は `*.test.tabete.co`（本番は `*.shokujii.jp` 等）。**Console が wildcard を拒否する場合**は [§6.1b](#61b-console-個別-fqdn-フォールバックsandbox-実績) へ。
4. 表示される **TXT（所有確認）** と **A/AAAA または CNAME** をメモ。

> Firebase Hosting は wildcard カスタムドメインを **公式にサポートしない**（各 FQDN を Console に明示追加）。インフラ側 DNS の wildcard と Console 手順は別問題。

### 5.3 DNS（`tabete.co` 管理画面）

#### 5.3.1 `hosting-site` TXT + CNAME（CNAME 方式・実績）

CNAME を `*.web.app` に向ける場合、**所有権 TXT も必須**。CNAME だけでは Firebase の **Site Not Found** になる（`<PROJECT_ID>.web.app` は表示されるのにカスタムドメインだけ失敗、という切り分け）。

| DNS サブドメイン（`tabete.co` 配下） | 種別 | 内容 | 向け先 Hosting サイト |
|:--|:--|:--|:--|
| `test` | TXT | `hosting-site=bokudeli-event-test` | **user** |
| `test` | CNAME | `bokudeli-event-test.web.app` | **user** |
| `sandbox2510` | TXT | `hosting-site=bokudeli-event-yasu-2510` | **user** |
| `sandbox2510` | CNAME | `bokudeli-event-yasu-2510.web.app` | **user** |
| `{subdomain}.{識別子}`（例: `yasu-test.sandbox2510`） | TXT | `hosting-site=<PROJECT_ID>-enterprise` | **enterprise** |
| 同上 | CNAME | `<PROJECT_ID>-enterprise.web.app` | **enterprise** |

- **user** と **enterprise** で `hosting-site` の SITE_ID が異なる（enterprise は `-enterprise` 付き）。
- TXT は SSL 更新のため **削除しない**（Firebase 公式: 所有権 TXT を継続保持）。
- Console が A/AAAA を指示した場合は CNAME の代わりにそちらを優先。

確認例:

```bash
dig sandbox2510.tabete.co TXT +short
# "hosting-site=bokudeli-event-yasu-2510"

dig yasu-test.sandbox2510.tabete.co TXT +short
# "hosting-site=bokudeli-event-yasu-2510-enterprise"
```

#### 5.3.2 ワイルドカード DNS（インフラ側・理想形）

Firebase Console の指示に従い、インフラが wildcard を許容する場合（例）:

```
# 所有確認（Console 表示値）
_acme-challenge.test.tabete.co    TXT    ...

# ワイルドカード → Firebase Hosting
*.test.tabete.co                  A      ...
*.test.tabete.co                  AAAA   ...
```

DNS の管理主体は社内インフラ担当。リポジトリ外の作業。

### 5.4 環境変数（Functions / フロント）

GitHub Environment ごとに **同じベースドメイン**を設定する。`tabete.co` サブドメイン方式では **Functions 側 `ENTERPRISE_BASE_DOMAIN` が未設定だと `getEnterpriseByDomain` が 404** になる（[§7.1](#71-企業が見つかりませんの切り分け)）。

| 変数 | 設定先 | テスト例 |
|:--|:--|:--|
| `VITE_ENTERPRISE_BASE_DOMAIN` | `ENTERPRISE_ENV` | `test.tabete.co` |
| `ENTERPRISE_BASE_DOMAIN` | `FUNCTIONS_ENV` | `test.tabete.co` |
| `enterprise_base_domain` | `terraform.tfvars`（reCAPTCHA 用） | `test.tabete.co` |

### 5.5 Firebase Auth（ログイン時）と Storage CORS（チャット画像）

Terraform `auth_authorized_domains_extra`（[firebase.tf](../../../terraform/firebase.tf)）に、利用するホストを追加。

- 最低: ベース `test.tabete.co` だけでは **`company-a.test.tabete.co` が足りない**ことが多い。
- テナント追加時に authorized domain を追加し、**同じリストが Storage CORS origin にも `https://` 付きで反映**される（[locals_storage_cors.tf](../../../terraform/locals_storage_cors.tf)）。
- **`createEnterprise` は Firestore / IdP のみ**。テナント URL を初めて使う場合は [04_詳細_オンボーディング.md](./04_詳細_オンボーディング.md) §3.5 のチェックリストまで完了すること。
- `<PROJECT>-enterprise.web.app` は Auth / CORS の **Terraform 既定**に含む（[#2241](https://github.com/nijuniinc/bokudeli-event-new/issues/2241)）。`{subdomain}.{BASE}` 型 URL は **FQDN ごとに extra へ列挙**が必要。

**Identity Platform マルチテナント**: エンプラ IdP は **`allow_tenants = true`** 前提（[05_認証・テナント.md](./05_認証・テナント.md)）。[firebase.tf](../../../terraform/firebase.tf) に `multi_tenant` を定義済み。**plan に `multi_tenant` 削除（`- allow_tenants = true`）が出る Auth apply は禁止**（テナント作成・ログインに影響）。詳細は [terraform/README.md](../../../terraform/README.md) の **Storage CORS（チャット画像添付等）** 節内 **Identity Platform マルチテナント（`multi_tenant`）** を参照。

**手順（テナント FQDN 追加時）**

1. FQDN を決める（Functions と同型: `getEnterpriseSubdomainHost` / `getAllowedEnterpriseHosts`）
2. `terraform.tfvars` の **`auth_authorized_domains_extra`** にホスト名を追加（`https://` なし）。sandbox 例は README の tfvars サンプル参照
3. **`terraform plan`** — Auth: **`multi_tenant` 削除なし**、authorized domains に追加 FQDN が消えないこと。Storage: `google_storage_bucket.default` の CORS **Update in-place**（Destroy なし）
4. **`terraform apply`** — plan が上記を満たすならフル apply 可。**Auth に別差分が残る**場合は `-target=google_storage_bucket.default` のみ apply し、OTP 用 domains は Console 追加も可（CORS は Terraform 必須）
5. 受け入れ: OTP ログイン、**チャット画像の送受信**（DevTools に CORS エラーなし）

**CORS 初回反映後**: デフォルト Storage バケットを Terraform import 済みなら、**既存テナント origin の「CORS 未設定」問題は再発しにくい**。新テナント FQDN 追加時の extra 更新 + apply（または targeted bucket）は引き続き必要。フル plan の **Destroy / 他リソース差分**は CORS とは無関係なので、毎回 plan を確認する。

**半自動（FQDN 行の出力）**:

```bash
cd terraform
./scripts/print-enterprise-tenant-fqdns.sh --subdomain company-a --base-domain sandbox2510.tabete.co
# 出力行を auth_authorized_domains_extra に追記して apply
```

### 5.6 テスト企業

```json
{
  "enterprise_id": "company-a",
  "subdomain": "company-a",
  "company_name": "テスト株式会社A"
}
```

→ `https://company-a.test.tabete.co` で `getEnterpriseByDomain` が成功すること。必須フィールドの正本は [04_詳細_オンボーディング.md](./04_詳細_オンボーディング.md) §3。

## 6. sandbox 向け構成

### 6.1a `tabete.co`・理想形（インフラ wildcard 対応時）

[§3.2](#32-sandbox-向け命名tabeteco推奨) のとおり、development と同型。インフラが `*.sandbox2510.tabete.co` の DNS wildcard を張れる場合の目標像。

**Firebase Console（Hosting）** — プロジェクト `bokudeli-event-yasu-2510` の例:

1. サイト **`bokudeli-event-yasu-2510`**（user）→ `sandbox2510.tabete.co`
2. サイト **`bokudeli-event-yasu-2510-enterprise`**（enterprise）→ `*.sandbox2510.tabete.co`（**Console 入力では通らないことが多い** → §6.1b）

**DNS** — §5.3.2 参照。

### 6.1b Console 個別 FQDN フォールバック（sandbox 実績）

Firebase Console が `*.sandbox2510.tabete.co` を拒否する場合の **正**（sandbox2510 で検証済み）。

#### 作業順（推奨）

1. **user**: `sandbox2510.tabete.co` — Console + DNS（§5.3.1 の user 行）
2. **Deploy user** — `bokudeli-event-yasu-2510.web.app` で PF 版表示を確認
3. **`ENTERPRISE_BASE_DOMAIN` / `VITE_ENTERPRISE_BASE_DOMAIN`** = `sandbox2510.tabete.co` を設定 → Functions / enterprise 再デプロイ
4. **enterprise**: テナント FQDN を Console + DNS（下表）
5. **`createEnterprise`** — `subdomain` = URL 第 1 ラベル（例: `yasu-test`）
6. **Terraform** — テナント FQDN を `auth_authorized_domains_extra` に追加 → **`terraform plan`**（`multi_tenant` 削除なし）→ **`terraform apply`** または Storage のみ `-target=google_storage_bucket.default`（[§5.5](#55-firebase-auth-ログイン時と-storage-corsチャット画像)）。`./scripts/print-enterprise-tenant-fqdns.sh --subdomain <label> --base-domain sandbox2510.tabete.co`
7. **`https://{subdomain}.sandbox2510.tabete.co/login`** — シークレットウィンドウ + **https 明示**で確認
8. **チャット画像** — 同一 URL の `/chat/{roomId}` で添付画像が表示されること（Storage CORS。未設定時は「画像の読み込みに失敗しました」）

#### 例: `yasu-test.sandbox2510.tabete.co`

| 項目 | 値 |
|:--|:--|
| Console（**enterprise** サイト） | `yasu-test.sandbox2510.tabete.co`（`*.` プレフィックス不可） |
| DNS サブドメイン | `yasu-test.sandbox2510` |
| TXT | `hosting-site=bokudeli-event-yasu-2510-enterprise` |
| CNAME | `bokudeli-event-yasu-2510-enterprise.web.app` |
| Firestore `subdomain` | `yasu-test` |
| `createEnterprise` | `"subdomain": "yasu-test"`（`custom_domain` に web.app を指定した §6.2 構成とは併用しない） |

**partner** は未指定でよい（`<PROJECT>-admin.web.app` のまま）。揃える場合は `{識別子}-admin.tabete.co`（例: `sandbox2510-admin.tabete.co`）も可。

### 6.2 `web.app` のみ（DNS なし・最小構成）

ワイルドカード DNS を張らない個人 sandbox 向けの簡易構成:

1. `ENTERPRISE_BASE_DOMAIN` は**未設定**でよい。
2. `createEnterprise` の `custom_domain` に `<PROJECT_ID>-enterprise.web.app` を指定。
3. ローカルは `VITE_ENTERPRISE_SUBDOMAIN=company-a` + `VITE_ENTERPRISE_BASE_DOMAIN`（[07 §4.7](./07_デプロイ・運用.md)）。

実機確認・共有 URL には **§6.1a / §6.1b を推奨**（development / 本番と URL 体系が揃う）。

## 7. トラブルシュート

| 症状 | 原因 | 対処 |
|:--|:--|:--|
| `<PROJECT_ID>.web.app` は OK、カスタムドメインのみ Firebase **Site Not Found** | `hosting-site` TXT 未設定 / SITE_ID 誤り | [§5.3.1](#531-hosting-site-txt--cnamecname-方式実績) |
| Console **接続済み** だが Site Not Found | ブラウザキャッシュ（TXT 追加前の 404） | **https 明示** + シークレット / スーパーリロード（`Cmd+Shift+R`） |
| **保護されていない通信** / ServiceWorker SSL error | 証明書発行中（「証明書を作成しています」） | Console で Connected まで待つ（最大 24h） |
| エンプラ SPA は出るが **企業が見つかりません** | `getEnterpriseByDomain` 404 | [§7.1](#71-企業が見つかりませんの切り分け) |
| SPA は表示されるが「企業が見つかりません」（その他） | BASE_DOMAIN 不一致 / `subdomain` 未登録 | env と Firestore を照合 |
| `company-a.test.tabete.co` が PF 版になる | 誤った Hosting サイトにドメイン接続 | enterprise サイトに接続 |
| `yasu-test.sandbox2510.tabete.co` が PF 版になる | user サイトに enterprise FQDN を接続した | enterprise サイトに接続（§6.1b） |
| OTP ログインで Auth エラー | authorized domains 未追加 | テナント FQDN を Auth に追加 |
| App Check 失敗（enforce 時） | reCAPTCHA `allowed_domains` 不足 | Terraform または Console でドメイン追加 |

### 7.1 「企業が見つかりません」の切り分け

エンプラ SPA（ログイン画面のエラーモーダル）が出る場合、DevTools → Network で **`getEnterpriseByDomain` が 404** か確認する。

| # | 確認 | 期待 |
|:--|:--|:--|
| 1 | Firestore `/enterprises` | `subdomain` が URL 第 1 ラベルと一致（例: `yasu-test`） |
| 2 | `FUNCTIONS_ENV` | `ENTERPRISE_BASE_DOMAIN=sandbox2510.tabete.co` 等、環境の BASE と一致 |
| 3 | Functions 再デプロイ | env 変更後に **Deploy functions**（enterprise グループ）済み |
| 4 | `createEnterprise` | 未実施なら [07 §11](./07_デプロイ・運用.md) で作成 |
| 5 | §6.2 との混同 | `custom_domain: web.app` のみの enterprise は `*.tabete.co` URL ではヒットしない |
