# 1. パッケージ構成

## 1.1 方針: user をコピーして enterprise パッケージとして独立

プラットフォーム版の `user` パッケージをコピーし、エンタープライズ専用の `enterprise` パッケージを新規作成する。
`base`（共有UIコンポーネント）と `common`（共有スキーマ・ユーティリティ）は両者で共有する。

### モノレポ構成

```
/                              ← モノレポルート
├── common/                    ← 共有スキーマ・ユーティリティ（既存）
├── base/                      ← 共有UIコンポーネント（既存）
├── user/                      ← プラットフォーム版ユーザー向け（既存）
├── enterprise/                ← 【新規】エンタープライズ版ユーザー向け（user からコピー）
├── partner/                   ← 飲食店管理画面（既存）
├── functions/default/         ← バックエンド（既存）
└── firebase.json
```

### package.json（ルート）への追加

```json
{
  "workspaces": [
    "common",
    "base",
    "user",
    "enterprise",
    "partner",
    "functions/default"
  ]
}
```

### enterprise/package.json

`user/package.json` と同様に `@shokujii/base` と `@shokujii/common` を依存として参照する。

```json
{
  "name": "enterprise",
  "dependencies": {
    "@shokujii/base": "file:../base",
    "@shokujii/common": "file:../common"
  }
}
```

## 1.2 コピー方式を選択した理由

| 比較軸 | コピー（独立パッケージ） | 設定切り替え（1パッケージ） |
|:--|:--|:--|
| コードの独立性 | 完全に独立。互いに影響しない | 1つのコードベースに `if (isEnterprise)` 分岐が増加 |
| UIカスタマイズ自由度 | 完全に自由 | 条件分岐の範囲内 |
| base/common の流用 | そのまま使える | そのまま使える |
| 長期メンテ | PF版のバグ修正を手動で取り込む必要がある | 1箇所修正で両方に反映 |

エンタープライズ版はログイン画面、トップページ、ナビゲーション構造がプラットフォーム版と大きく異なる（SNSログインなし、企業ブランディング、全社管理者画面への導線など）ため、設定切り替え方式では `if` 分岐が爆発的に増え可読性・テストの複雑さが急速に悪化する。

## 1.3 全社管理者画面のパッケージ構成

全社管理者画面は `enterprise` パッケージ内に `/admin/*` ルートとして実装する。別パッケージ（`enterprise-admin`）は作成しない。

```
enterprise/src/pages/
  ├── index.vue                    ← 一般従業員向けトップページ
  ├── login.vue                    ← ログイン画面
  ├── c/[communityId]/             ← コミュニティ・イベント関連
  ├── manage/                      ← コミュニティ管理者向け（PF版と同等）
  └── admin/                       ← 【エンプラ固有】全社管理者画面
        ├── index.vue              ← ダッシュボード
        ├── settings.vue           ← 全社設定（会社名、ロゴ、テーマカラー）
        ├── members.vue            ← アカウント管理（一覧、一括作成、停止）
        ├── communities.vue        ← コミュニティ承認・管理
        └── discount.vue           ← 割引設定・月額上限
```

- 1つのパッケージに従業員画面と管理者画面の両方を含めることで、MVP工数を削減する
- ルーティングのナビゲーションガードで `enterprise_role == "admin"` を検証し、管理者以外のアクセスを制御する

## 1.4 長期メンテのコスト軽減策

- **共通ロジックは可能な限り `base` / `common` に寄せる**
  - コピー後に enterprise 固有でない変更を user に入れた場合、base に引き上げることを検討する
- エンタープライズ固有の差分だけを `enterprise` パッケージに残す意識を持つ

### i18n 方針（日本語のみ）

- **共通 UI 文言**: `base/src/locales/messages/ja.ts` に集約（PF版と共有）
- **enterprise 固有文言**（管理画面・福利厚生割引・ゲスト等）: `enterprise/src/locales/messages/ja.ts` に追加
- **base コンポーネントのエンプラ差分**（SNS 非表示等）: 新規 locale を作らず props で出し分け（`hideSnsFeatures?: boolean` 等）
- `en.ts` 等の英語 locale ファイルは作らない（`AGENTS.md` 日本語のみ方針に準拠）


# 2. Hosting とドメイン設定

## 2.1 方針

- Firebase Hosting に `enterprise` の target を1つ追加する
- 全企業で同じビルド成果物をデプロイする（単一のエンタープライズアプリ）
- **サブドメイン方式をデフォルト**とし、カスタムドメインはオプションとする
- アプリはアクセス元のドメインから `enterprise_id` を動的に解決し、企業ごとのブランディング（ロゴ、テーマカラー）を動的に適用する

## 2.2 ドメイン構成

```
enterprise target（1つの Hosting target）
  ├── enterprise.shokujii.com          ← デフォルト
  ├── company-a.shokujii.com           ← A社サブドメイン
  ├── company-b.shokujii.com           ← B社サブドメイン
  └── lunch.company-c.com              ← C社カスタムドメイン（オプション）
```

| 方式 | URL例 | 企業側の作業 | shokujii側の作業 |
|:--|:--|:--|:--|
| **サブドメイン（デフォルト）** | `company-a.shokujii.com` | なし | DNS + Firebase Hosting にドメイン追加 |
| **カスタムドメイン（オプション）** | `lunch.company-c.com` | DNS設定（CNAME） | Firebase Hosting にドメイン追加 |

## 2.3 firebase.json への追加

```json
{
  "hosting": [
    { "public": "partner/dist", "target": "partner", "..." : "..." },
    { "public": "user/dist", "target": "user", "..." : "..." },
    {
      "public": "enterprise/dist",
      "target": "enterprise",
      "ignore": ["**/.*", "**/node_modules/**"],
      "rewrites": [
        { "source": "**", "destination": "/index.html" }
      ]
    }
  ]
}
```

## 2.4 ドメインから enterprise_id を解決する仕組み

アプリ起動時にアクセス元のホスト名から Firestore の企業設定を取得する。

### ベースドメインの環境変数化

サブドメイン判定のベースドメイン（テナント用ワイルドカード DNS を張るドメイン）はコードにハードコードせず、環境変数で指定する。

| 場所 | 変数 | 例 |
|:--|:--|:--|
| Functions | `ENTERPRISE_BASE_DOMAIN`（`firebase-functions/params` の `defineString`） | 本番: `shokujii.jp`、dev: `shokujii.com`、sandbox: 未設定可 |
| フロント | `VITE_ENTERPRISE_BASE_DOMAIN`（`ENTERPRISE_ENV` に追加） | 同上 |

`getEnterpriseByDomain` は `ENTERPRISE_BASE_DOMAIN` からサブドメイン判定の正規表現を組み立てる。未設定の場合は `custom_domain` 完全一致のみで判定する（sandbox はカスタムドメイン前提のため未設定でも動作する）。

### フロントのブートストラップ（useEnterpriseStore）

企業情報は Pinia store（`enterprise/src/stores/enterprise.ts` の `useEnterpriseStore`）に保持する。

```typescript
// state（イメージ）
{
  enterprise: GetEnterpriseByDomainResponse | null
  status: 'loading' | 'ready' | 'not_found' | 'error'
}
// actions
// resolveEnterprise():
//   hostname 決定（VITE_ENTERPRISE_SUBDOMAIN 設定時は
//   `${VITE_ENTERPRISE_SUBDOMAIN}.${VITE_ENTERPRISE_BASE_DOMAIN}` を優先）
//   → getEnterpriseByDomain 呼び出し → state 更新
```

- **呼び出しタイミング**: `main.ts` で mount 前に `resolveEnterprise()` を開始し、`App.vue` が `status` で表示分岐（`loading` = `public/loader.css` 流用、`not_found` / `error` = 全画面エラーページ）
- **キャッシュ**: MVP はキャッシュなし（リロード毎に取得）。ちらつきが問題になれば sessionStorage キャッシュを後付け
- `enterprise_id` / `allowed_email_domains` / `theme_color` はすべてこの store から参照する（login → pass-code 間の `enterprise_id` 持ち回りも store で解決。query で渡すのは `email` のみ）

### theme_color の動的適用

`enterprise/src/themes/light.ts` / `dark.ts` の `'primary': '#1AC662'` を**デフォルト値として残し**、store が `ready` になった時点で Vuetify テーマを動的上書きする。

```typescript
// resolveEnterprise 成功後（イメージ）
const theme = useTheme()
for (const name of ['light', 'dark']) {
  theme.themes.value[name].colors.primary = enterprise.theme_color
  theme.themes.value[name].colors['primary-darken-1'] = darken(enterprise.theme_color, 0.2)
}
```

- `primary-darken-1` は計算ユーティリティ（`darken()`）で導出。`on-primary: #fff` は固定
- base の SCSS にハードコードされた primary 色（例: `TinyMCEViewer.vue` の `#1ac662`）には動的テーマが効かない。Phase 2 では許容し（ログイン画面・管理画面では未使用）、`rgb(var(--v-theme-primary))` への置換は base 側の改善として将来対応

Firestore の `/enterprises` コレクションに `subdomain` と `custom_domain` フィールドを持たせ、ドメインからの逆引きに使用する。

**ローカル開発・sandbox**: `localhost` や `<PROJECT_ID>-enterprise.web.app` ではそのまま not-found になるため、[09_デプロイ手順 §4.7](./09_エンタープライズ_デプロイ手順.md) の運用（`custom_domain` 登録 / `VITE_ENTERPRISE_SUBDOMAIN`）に従う。未ヒット時は企業選択 UI ではなくエラーページを表示する（文言は `enterprise/src/locales/messages/ja.ts` に追加）。

## 3.2 新規コレクション

### `/enterprises/{enterpriseId}` — 企業設定

```typescript
interface Enterprise {
  // === 基本情報 ===
  enterprise_id: string           // ドキュメントID
  company_name: string            // 会社名
  company_logo_url: string        // 企業ロゴURL
  theme_color: string             // テーマカラー（hex）

  // === ドメイン設定 ===
  subdomain: string               // サブドメイン（例: "company-a" → company-a.shokujii.com）
  custom_domain?: string          // カスタムドメイン（オプション。例: "lunch.company-a.com"）
  allowed_email_domains: string[] // ログイン許可メールドメイン（例: ["company-a.com", "company-a.co.jp"]）

  // === 割引設定 ===
  discount_type: "fixed" | "percentage"  // 固定金額 or 割合
  discount_value: number                  // 固定: 金額（例: 500）、割合: パーセンテージ（例: 50）
  monthly_limit_per_user: number          // 1人あたり月額上限（例: 7500）

  // === 請求設定 ===
  payment_method: "credit_card"   // MVP: クレカのみ。Phase 2 で "payroll_deduction" 追加
  billing_settings: {            // プラットフォーム利用料（02_課金設計）
    unit_price: number           // デフォルト 500（円/有効アカウント/月）
    trial_months: number         // デフォルト 3
    billing_trial_ends_at: Timestamp
  }

  // === 管理 ===
  is_active: boolean              // 企業アカウント有効/無効
  created_at: Timestamp
  updated_at: Timestamp
}
```

### `/enterprises/{enterpriseId}/members/{userId}` — 企業メンバー

```typescript
interface EnterpriseMember {
  user_id: string                        // ユーザーID（= /users/{userId} と同じ）
  role: "admin" | "member"               // 全社管理者 or 一般従業員
  is_active: boolean                     // アカウント有効/無効（現在のログイン可否）
  last_activated_at: Timestamp | null    // 直近の有効化（作成・enable 時。§02_課金設計 §2.3）
  last_deactivated_at: Timestamp | null  // 直近の停止（disable 時。enable では消さない）
  display_name?: string                  // 社内表示名（任意）
  department?: string                    // 部署（任意、CSV一括登録時に設定）

  // === 割引利用実績（月別辞書） ===
  monthly_usage: Record<string, number>         // { "2026-06": 5000, "2026-07": 1200 }
  monthly_order_count: Record<string, number>   // { "2026-06": 8, "2026-07": 2 }

  created_at: Timestamp
  updated_at: Timestamp
}
```

**月別辞書方式の設計:**
- キーはイベント開催月（"YYYY-MM" 形式）、値は割引利用合計額 / 注文回数
- 月額利用実績は**決済日ではなくイベント開催月**に紐づく（6月に7月イベントを決済した場合、7月分に加算）
- 辞書にキーが存在しない月は `0` として扱う（明示的なリセット処理は不要）
- 1ドキュメントで全月分を管理できるため、Transaction 内での排他制御がシンプル
- 詳細は `04_割引・決済` を参照

### `/enterprises/{enterpriseId}/billing_snapshots/{yearMonth}` — 課金スナップショット（MVP-B）

```typescript
interface EnterpriseBillingSnapshot {
  year_month: string              // "2026-07"（暦月）
  active_account_count: number    // billable_in(YM) 件数（02_課金設計 §2.3）
  unit_price: number
  platform_fee_amount: number     // お試し期間内は 0
  is_trial: boolean
  meal_billing_amount: number     // 食事従量（イベント開催月ベースの enterprise_billing_amount）
  total_billing_amount: number
  snapshot_at: Timestamp
  billing_status: 'final' | 'provisional' // 当月のみ provisional（通常は final）
}
```

**毎月 1 日 00:05 JST** バッチ（`captureEnterpriseBillingSnapshots`）で**直前暦月**を確定。手動請求の根拠。詳細は `02_課金設計` §5.3〜5.4。

> **フィールド名対応（確定済み）**:
> - Firestore `billing_snapshots.meal_billing_amount` — 食事従量の永続化
> - API / CSV `enterprise_billing_amount` — 表示層（同一値）
> - `getDashboardMonthlyData` は過去月でスナップショットの `meal_billing_amount` を `enterprise_billing_amount` にマッピング

**event_payment の値について:**

Event スキーマの既存フィールド `event_payment` に新しい値 `enterprise_subsidy` が追加される。common スキーマの `EVENT_PAYMENT_VALUES` を拡張する。

```typescript
// 変更前
export const EVENT_PAYMENT_VALUES = ['user_advance', 'user_on_day', 'community_bill'] as const

// 変更後
export const EVENT_PAYMENT_VALUES = ['user_advance', 'user_on_day', 'community_bill', 'enterprise_subsidy'] as const
```

| 値 | 概要 | エンプラ版 |
|:--|:--|:--|
| `enterprise_subsidy` | 福利厚生割引。企業の割引ルール適用後、残額をクレカ決済 | **デフォルト** |
| `user_advance` | 参加者事前決済（PF版と同じ） | オプション |
| `community_bill` | 主催者請求書払い（PF版と同じ） | **選択不可**（D-13） |
| `user_on_day` | 当日払い（deprecated。PF版でも利用実績なし） | **選択不可** |

エンプラ版のイベント作成時のデフォルト値は `enterprise_subsidy`。`event_payment === 'enterprise_subsidy'` の場合、`enterprise_subsidy_settings` フィールド（3.5 参照）を必須とする。イベントドキュメントへスナップショット保存し、`addToCart` / `confirmOrder` / `createStripeCheckoutSession` で参照する。

### `/communities/{communityId}/events/{eventId}/members/{userId}` — フィールド追加

新設計の `EventMember` スキーマ（`05_EventOrder→EventMemberOrder.md` 参照）に以下を追加する。

```typescript
// 既存の EventMember スキーマに追加
{
  enterprise_id?: string        // 所属企業ID（イベントが enterprise_id を持つ場合に必ず設定）
  is_guest?: boolean            // ゲスト参加者フラグ — **将来実装**（04_ゲスト参加 参照）
}
```

`is_guest` は「同一ユーザーが同じイベント内の異なるメニューでゲスト/メンバーを変える」ユースケースは想定されないため、`members` ドキュメント側に持たせる。`member_orders` 側には持たせない。— **将来実装**

### `/communities/{communityId}/events/{eventId}/members/{userId}/member_orders/{orderId}` — フィールド追加

新設計の `EventMemberOrder` スキーマ（`05_EventOrder→EventMemberOrder.md` 参照）に以下を追加する。

```typescript
// 既存の EventMemberOrder スキーマに追加
{
  enterprise_id?: string                    // 所属企業ID（イベントが enterprise_id を持つ場合に必ず設定）
  pay_enterprise_subsidy_amount?: number    // この 1 品に適用された企業補助額（addToCart 時にサーバー算出）
}
```

**`pay_enterprise_subsidy_amount` の値の決まり方（1 ドキュメント単位）:**

`pay_community_bill_off_amount` と同じ思想で、1 ドキュメント = 1 品のため `× count` の乗算は不要。同一メニューを 3 個注文した場合は同じ `pay_enterprise_subsidy_amount` を持つ 3 つのドキュメントが作られる。

| `enterprise_subsidy_settings.type` | 値 |
|:--|:--|
| `fixed`（固定金額） | `min(value, menu_price)` |
| `percentage`（割合） | `min(floor(menu_price × value / 100), menu_price)` |
| 月額上限超過分 | **フィールドなし**（`undefined`。3.6 参照） |
| 割引なし（非エンプライベント） | フィールドなし |

`user_paid_amount`（自己負担額）は **保持しない**（`menu_price - pay_enterprise_subsidy_amount` で導出する）。`pay_community_bill_off_amount` の設計と整合させる。

### `/communities/{communityId}/events/{eventId}/stripes/{stripeId}` — フィールド追加

新設計の `EventStripe` スキーマ（`05_EventOrder→EventMemberOrder.md` 参照）に以下を追加する。

```typescript
// 既存の EventStripe スキーマに追加
{
  enterprise_id?: string                    // 所属企業ID
  pay_enterprise_subsidy_amount?: number    // 当該セッションの企業補助合計
                                            // = Σ (member_order.pay_enterprise_subsidy_amount ?? 0)
}
```

`stripes.pay_amount + stripes.pay_enterprise_subsidy_amount = Σ menu_price` が成り立つ（`pay_community_bill_off_amount` と同じ設計思想）。

**無料 / 補助後 ¥0 確定**（`confirmOrder` 経由、Stripe 未使用）では `stripes` ドキュメントを作成しない（`stripe_id` は `member_orders` に設定されない）。

## 3.4 設計上の注意点

### enterprise_id の冗長化

`communities`, `events`, `members`, `member_orders`, `stripes` のそれぞれに `enterprise_id` を持たせている。正規化の観点では冗長だが、以下の理由で全コレクションに保持する。

- **`collectionGroup` クエリ**: 企業横断集計（例: 全社の月次注文一覧、特定ユーザーの注文履歴）には `collectionGroup('member_orders')` + `where('enterprise_id', '==', ...)` のクエリが必要。フィールドとして持っていないとクエリできない
- **Security Rules**: `resource.data.enterprise_id == request.auth.token.enterprise_id` のような単純なルールで「自社のみ可視」を表現できる
- **JOIN 不在の補完**: Firestore は JOIN ができないため、親ドキュメントの `enterprise_id` を取りに行くと N+1 クエリになる
- **メール配信制御**: `isEnterpriseEvent(event)` が Event ドキュメント単体で同期判定できる（`04_メール配信` 方式A 確定）

`05_EventOrder→EventMemberOrder.md` で `community_id` を冗長化した判断と同じ理由。書き込みは store 経由で一元化し、`enterprise_id` の取り違えが起きないようにする。

### enterprise_id の不変条件（方式A 確定）

Community が `enterprise_id` を持つ場合、配下の **Event / EventMember / EventMemberOrder / EventStripe** にも必ず同一の `enterprise_id` を denormalize してセットする。Event 作成・複製・`addToCart` 等、すべての書き込み経路で store がこの不変条件を保証する。

| 経路 | 処理 |
|:--|:--|
| コミュニティ作成 | `community.enterprise_id` をセット |
| イベント作成 / 複製 | `community.enterprise_id` を Event にコピー |
| `addToCart` | Event の `enterprise_id` を members / member_orders にコピー |
| `stripeWebhook` | Event の `enterprise_id` を stripes にコピー |

- Community の `enterprise_id` は作成後に変更しない（変更運用は想定しない）
- PF版既存データは `enterprise_id` 未設定（= null）のまま従来挙動

### 既存データとの後方互換性

追加フィールドはすべて optional（`?`）にしている。プラットフォーム版の既存データには `enterprise_id` も `user_type` もないので、`undefined` = プラットフォーム版として扱う。既存コードへの影響を最小化できる。

### 割引計算の責務

`pay_community_bill_off_amount` と同じ責務分離を採用する。

| タイミング | 処理 |
|:--|:--|
| `addToCart` | 各 `member_orders` ドキュメント作成時に、Cloud Functions が `pay_enterprise_subsidy_amount` を算出して書き込む（`computePaymentEnterpriseSubsidyAmount` ヘルパを `common/src/utils/` に追加） |
| `confirmOrder` / `createStripeCheckoutSession` | サーバー側で各 order ドキュメントについて再計算し、ストアード値と一致するか検証（`isPaymentEnterpriseSubsidyAmountConsistent` ヘルパ）。一致しない場合 `failed-precondition` |
| `cancelOrders` | キャンセル対象 order の `pay_enterprise_subsidy_amount` 分を、イベント開催月の `monthly_usage` から減算 |

フロントエンドで計算して表示するのは表示用のみで、実際の割引適用額は Functions 側で検証・確定する。これにより割引ルールの改ざんを防止する。

### エンタープライズ必須フィールドの optional 問題

プラットフォーム版と Firestore コレクションを共有するため、エンタープライズ版では必須のフィールド（`enterprise_id`, `approval_status` 等）が DB スキーマ上は optional にならざるを得ない。ゲスト関連（`allow_guest` 等）は **将来実装** のため MVP スキーマには含めない。

**MVP の方針: optional のまま使う**

エンタープライズ版のコードでは、データ作成時に必ずセットする運用とする。読み取り時に `undefined` が返ることは基本的にないため、実害は小さい。

```typescript
// enterprise パッケージ内ではデータ作成時に必ずセットする
const community = new Community(id, {
  ...data,
  enterprise_id: currentEnterpriseId,  // 必ずセット
  approval_status: 'pending',          // 必ずセット
})
```

enterprise パッケージ内で型安全性が必要な場合は、型ガード関数で対処する。

```typescript
// enterprise パッケージ内に配置するユーティリティ
function assertEnterpriseCommunity(c: Community): asserts c is Community & {
  enterprise_id: string
  approval_status: "pending" | "approved" | "rejected"
} {
  if (!c.enterprise_id) throw new Error('enterprise_id is required')
  if (!c.approval_status) throw new Error('approval_status is required')
}

// 使用例
const community = new Community(id, data)
assertEnterpriseCommunity(community)
// ここ以降、community.enterprise_id は string 型（必須）として扱える
```

**将来的に extend() を導入する場合の実装イメージ**

スキーマが複雑化し、エンタープライズ固有のバリデーションが多数必要になった場合は、Zod の `.extend()` でエンタープライズ専用スキーマを作成する。

```typescript
// common/src/schemas/EnterpriseCommunity.ts

import { z } from 'zod'

export const EnterpriseCommunityDbSchema = CommunityDbSchema.extend({
  enterprise_id: z.string().nonempty(),                              // optional → 必須に上書き

export const EnterpriseEventDbSchema = EventDbSchema.extend({

  allow_guest: z.boolean(),                              // 将来実装時に追加
  guest_payment: z.enum(["free", "self_pay"]).optional(), // 将来実装時に追加

})

export const EnterpriseEventMemberDbSchema = EventMemberDbSchema.extend({
```

ただし、extend() を導入すると `Community`, `Event`, `EventMember`, `EventMemberOrder`, `EventStripe` それぞれにエンタープライズ版スキーマが追加され、フィールド変更時に両方をメンテする必要が生じる。MVPでは型ガード関数で十分であり、extend() はスキーマ複雑化時に検討する。

## 3.5 企業補助設定（enterprise_subsidy_settings）

### マスターとスナップショットの責務分離

`community_bill_settings` と同様、**注文計算は Event 上のスナップショットのみを参照**する。エンプラ版では企業全体のルール（マスター）が `/enterprises/{eid}` にあるため、2 段構成となる。

| レイヤ | フィールド | 役割 |
|:--|:--|:--|
| `/enterprises/{eid}`（マスター） | `discount_type`, `discount_value`, `monthly_limit_per_user`（フラット） | 全社管理者が変更する現在のルール |
| `Event`（スナップショット） | `enterprise_subsidy_settings: { type, value, monthly_limit_per_user }`（ネスト） | 作成時・draft 保存時にマスターからコピー。公開後は固定 |

変換は `enterpriseSubsidySettingsFromEnterprise()`（`common/src/utils/`）で行う。`createEnterprise` のリクエスト DTO はネスト形式を受け付けてもよいが、**Firestore 保存はフラット3フィールド**とする（`04_オンボーディング` §3.2 参照）。

### スキーマ（Event スナップショット）

`event.enterprise_subsidy_settings` の構造は以下とする。`community_bill_settings` と同じく、イベント作成時に企業設定（マスター）をスナップショットしてイベントドキュメントに保存する。

```typescript
interface EnterpriseSubsidySettings {
  type: 'fixed' | 'percentage'
  value: number                    // fixed: 円、percentage: %
  monthly_limit_per_user: number   // この時点での月額上限
}
```

### イベントへの反映タイミング

| ステータス | 挙動 |
|:--|:--|
| イベント新規作成時 | 企業設定（`/enterprises/{eid}` の `discount_type` / `discount_value` / `monthly_limit_per_user`）をスナップショットして保存 |
| **下書き保存時（`draft`）** | **企業設定を再取得してスナップショットを上書き**する |
| 公開後（`published` 以降） | スナップショット固定（変更しない）。企業側で割引設定を変更しても影響なし |

下書き保存タイミングで再取得することで、「企業が割引額を変更 → 主催者が下書きイベントを保存 → 最新設定が反映される」という運用フローが成り立つ。すでに公開済みのイベントは過去注文の整合性を守るため変更しない。

### 計算ヘルパ（common/src/utils/）

`pay_community_bill_off_amount` の `paymentCommunityBillOffAmount.ts` と並列に、エンプラ用ヘルパを `common/src/utils/paymentEnterpriseSubsidyAmount.ts` に追加する。

```typescript
// 1 つの member_orders ドキュメントに適用する企業補助額を算出する
// 月額上限は別途考慮（3.6 参照）
export function computePaymentEnterpriseSubsidyAmount(
  eventPayment: EventPaymentType,
  settings: EnterpriseSubsidySettings | undefined,
  menu_price: number,
): number | undefined {
  if (eventPayment !== 'enterprise_subsidy') return undefined
  if (settings == null) return undefined
  if (settings.type === 'fixed') return Math.min(settings.value, menu_price)
  if (settings.type === 'percentage') {
    return Math.min(Math.floor((menu_price * settings.value) / 100), menu_price)
  }
  return undefined
}

// サーバー側再計算とストアード値の整合チェック（confirmOrder / createStripeCheckoutSession 用）
export function isPaymentEnterpriseSubsidyAmountConsistent(
  eventPayment: EventPaymentType,
  settings: EnterpriseSubsidySettings | undefined,
  order: EventMemberOrder,
): boolean {
  const expected = computePaymentEnterpriseSubsidyAmount(eventPayment, settings, order.menu_price)
  const stored = order.pay_enterprise_subsidy_amount
  return expected === stored   // 両方 undefined も一致とみなす
}
```

> 命名は `pay_community_bill_off_amount` 系（`computePaymentCommunityBillOffAmount` / `isPaymentCommunityBillOffAmountConsistent`）と統一している。

## 3.6 月額上限（monthly_usage）のトランザクション設計

### 基本方針

- **消費タイミング**: `confirmOrder` / `stripeWebhook` の Transaction 内で `monthly_usage` を加算する。`addToCart` 段階では `monthly_usage` を消費しない（カート放置の影響を排除）
- **減算タイミング**: `cancelOrders` の Transaction 内で `monthly_usage` を減算する。`removeFromCart` では操作しない（消費していないため）
- **キー**: `"YYYY-MM"` 形式の **イベント開催月**（`event.event_start_datetime` の年月）
- **配置**: `/enterprises/{enterpriseId}/members/{userId}` の `monthly_usage: Record<string, number>` フィールド（3.2 参照）

### 上限超過分の挙動

`addToCart` 時点では `monthly_usage` を消費しないが、上限到達状況を見て `pay_enterprise_subsidy_amount` を切り下げる必要がある。

| 状態 | `pay_enterprise_subsidy_amount` |
|:--|:--|
| 残枠が `computePaymentEnterpriseSubsidyAmount` の結果以上 | 算出値そのまま |
| 残枠が一部のみ（例: 残枠 ¥300、補助額 ¥500） | 残枠分のみ（¥300） |
| 残枠ゼロ | **フィールドなし**（`undefined`。全額自己負担） |

これにより「収まる分だけ補助、超過分は自己負担」を実現する。`addToCart` で N 個追加する際は、ループ内で残枠を減算しながら各ドキュメントの補助額を決定する。

### Transaction 設計（confirmOrder 例）

```typescript
// confirmOrder の Transaction 内
await runTransaction(db, async (tx) => {
  // 1. 対象 order_ids を読み取り、企業補助額を集計
  const orders = await getOrdersByIds(...)
  const subsidyByYearMonth: Record<string, number> = {}
  for (const order of orders) {
    const ym = formatYearMonth(event.event_start_datetime)
    subsidyByYearMonth[ym] = (subsidyByYearMonth[ym] ?? 0) + (order.pay_enterprise_subsidy_amount ?? 0)
  }

  // 2. EnterpriseMember を読み取り、月額上限の整合チェック
  const member = await getEnterpriseMember(enterprise_id, user_id, tx)
  for (const [ym, amount] of Object.entries(subsidyByYearMonth)) {
    const used = member.monthly_usage[ym] ?? 0
    const limit = event.enterprise_subsidy_settings.monthly_limit_per_user
    if (used + amount > limit) {
      throw new HttpsError('failed-precondition', '月額上限を超過しています')
    }
  }

  // 3. order の status を ordered に更新
  for (const order of orders) {
    await saveOrder(...)
  }

  // 4. EnterpriseMember.monthly_usage を更新
  await saveEnterpriseMember(enterprise_id, user_id, {
    ...member,
    monthly_usage: mergeMonthlyUsage(member.monthly_usage, subsidyByYearMonth),
  }, tx)
})
```

### キャンセル時の減算

```typescript
// cancelOrders の Transaction 内
const subsidyToReturn: Record<string, number> = {}
for (const order of canceledOrders) {
  const ym = formatYearMonth(event.event_start_datetime)
  subsidyToReturn[ym] = (subsidyToReturn[ym] ?? 0) + (order.pay_enterprise_subsidy_amount ?? 0)
}
const member = await getEnterpriseMember(enterprise_id, user_id, tx)
const updated = {} as Record<string, number>
for (const [ym, used] of Object.entries(member.monthly_usage)) {
  updated[ym] = Math.max(0, used - (subsidyToReturn[ym] ?? 0))
}
await saveEnterpriseMember(enterprise_id, user_id, { ...member, monthly_usage: updated }, tx)
```

### `addToCart` の擬似フロー

```
1. event.enterprise_subsidy_settings を取得
2. EnterpriseMember.monthly_usage を取得
3. count 個分のループ:
   a. computePaymentEnterpriseSubsidyAmount で算出値を計算
   b. 残枠 (= monthly_limit_per_user - 当該月の monthly_usage - ループ内累計補助額) と比較
   c. 残枠以下なら算出値、残枠が一部のみなら残枠分、残枠ゼロなら undefined
   d. 各 member_orders ドキュメントを作成
4. ※ EnterpriseMember.monthly_usage 自体は更新しない（confirmOrder で消費するため）
```

> **注意**: 同時カート操作のレースコンディションは `addToCart` では防げないため、`confirmOrder` / `stripeWebhook` で必ず最新の `monthly_usage` を読み取って整合チェックする。チェックで失敗した場合は `enterprise_subsidy_recalculated` 監査ログ（7.2 参照）を残し、ユーザーに再カート操作を促す。

## 3.7 Storage パス設計

Firebase Storage にアップロードするファイル（企業ロゴ、ユーザーアバター等）は、パスに `enterprise_id` を含める。契約終了時のデータ一括削除・将来の物理分離に対応するため、MVP 段階から必須。

### パス構成

```
/enterprises/{enterpriseId}/
  ├── logo/company-logo.png              ← 企業ロゴ
  ├── members/{userId}/avatar.png        ← メンバーアバター
  └── communities/{communityId}/         ← コミュニティ関連画像
        ├── cover.png
        └── events/{eventId}/photos/
```

### Security Rules（Storage）

`/enterprises/` 配下は原則 **Functions 経由の write のみ**（`allow write: if false`）。**企業ロゴ**のみ Phase 3 で例外とし、全社管理者（`enterprise_role == "admin"`）によるクライアント直アップロードを許可する（`04_全社管理者画面` §3.2 参照）。

```javascript
// デフォルト: 同一 enterprise のメンバー read のみ。write は禁止
match /enterprises/{enterpriseId}/{allPaths=**} {
  allow read: if request.auth != null
              && request.auth.token.enterprise_id == enterpriseId;
  allow write: if false;
}

// 企業ロゴのみ admin write を許可（より具体的な match が優先）
match /enterprises/{enterpriseId}/logo/{fileName} {
  allow read: if request.auth != null
              && request.auth.token.enterprise_id == enterpriseId;
  allow write: if request.auth != null
               && request.auth.token.enterprise_id == enterpriseId
               && request.auth.token.enterprise_role == 'admin'
               && request.resource.size < 2 * 1024 * 1024
               && request.resource.contentType.matches('image/(png|jpeg|svg\\+xml)');
}
```

パス定数は `common/src/utils/storagePaths.ts` に `getEnterpriseLogoStoragePath(enterpriseId)` を追加する（例: `/enterprises/{enterpriseId}/logo/company-logo.png`）。

`updateEnterpriseSettings` では `company_logo_url` が自社 Storage バケットの `/enterprises/{enterpriseId}/logo/` 配下であることを検証し、任意 URL の注入を防ぐ。

### 設計上の注意

- プラットフォーム版の既存 Storage パスはそのまま維持（変更不要）
- エンタープライズ版は `/enterprises/` 以下に格納することで完全に分離
- `enterprise_id` がパスに含まれていないと、契約終了時に該当企業のファイルだけを削除することが困難になる
- この設計は後から変更すると既存ファイルの移行が必要になるため、MVP 段階で確定する


# 4. 認証フローの技術設計

## 4.1 OTP 認証（MVP）

プラットフォーム版と同等の OTP 認証（メールアドレス + 6桁ワンタイムパスワード）を使用する。

### 認証フロー

```
① ユーザーがメールアドレスを入力
② フロントエンドでメールドメインバリデーション（allowed_email_domains に含まれるか）
③ Cloud Functions でメールドメインの二重チェック + OTP を生成・SendGrid で送信
④ ユーザーが OTP を入力
⑤ Cloud Functions で OTP を検証 → Firebase Auth のカスタムトークンを発行
⑥ フロントエンドでカスタムトークンでログイン → JWT に custom claims が含まれる
```

### メールドメインバリデーション

フロントエンド（入力時の即時フィードバック用）と Cloud Functions（セキュリティ担保用）の **二重チェック** で実装する。

## 4.2 Custom Claims 設計

Custom claims は Firebase Auth のユーザーに対して、サーバー側（Admin SDK）から追加のカスタム属性を JWT トークンに埋め込む機能。Firestore Security Rules から `request.auth.token.*` で直接参照できる。

### 設定するフィールド

```typescript
// Firebase Auth の custom claims に設定する値
{
  enterprise_id: string            // 所属企業ID（例: "company-a"）
```

## 4.3 セッション管理

### Firebase Auth のデフォルト動作

- ID トークン: 1時間で失効（SDK が自動更新）
- リフレッシュトークン: **無期限**（明示的に取り消さない限り有効）

デフォルトのままでは一度ログインすれば永久にセッションが維持されるため、エンタープライズ向けには以下の対策を MVP から実装する。

### MVP で実装する対策

| 項目 | 実装方法 |
|:--|:--|
| **無操作タイムアウト** | `localStorage` の `enterprise:last_activity_at` で最終操作時刻を記録。各タブが 60 秒間隔の `setInterval` と `visibilitychange`（復帰時）で超過判定し、`logEnterpriseLogout` → `signOut()` を実行 |
| **アカウント停止時の即時無効化** | 全社管理者がアカウント停止 → Functions で `revokeRefreshTokens()` を呼ぶ |

### 無操作タイムアウト（フロントエンド実装イメージ）

複数タブ間の同期とバックグラウンドタブの `setTimeout` スロットリングを避けるため、**時刻比較方式 + localStorage 同期**を採用する。

```typescript
// enterprise/src 内のセッション管理（イメージ）
const TIMEOUT_MS = 60 * 60 * 1000 // 60分
const STORAGE_KEY = 'enterprise:last_activity_at'
const THROTTLE_MS = 10 * 1000 // localStorage 書き込みは 10 秒間隔で throttle
const CHECK_INTERVAL_MS = 60 * 1000 // 60 秒間隔で超過判定

let lastWriteAt = 0

const touchActivity = () => {
  const now = Date.now()
  if (now - lastWriteAt < THROTTLE_MS) return
  lastWriteAt = now
  localStorage.setItem(STORAGE_KEY, String(now))
}

const checkTimeout = async () => {
  const last = Number(localStorage.getItem(STORAGE_KEY) ?? 0)
  if (Date.now() - last <= TIMEOUT_MS) return
  try {
    await logEnterpriseLogout({ action: 'session_timeout' }) // 失敗時は握りつぶす
  } finally {
    await auth.signOut()
  }
}

['click', 'keydown', 'scroll', 'mousemove'].forEach((event) =>
  document.addEventListener(event, touchActivity)
)
setInterval(checkTimeout, CHECK_INTERVAL_MS)
document.addEventListener('visibilitychange', () => {
  if (document.visibilityState === 'visible') checkTimeout()
})
```

**適用範囲**: enterprise アプリ上の全ログインセッション（ゲスト含む）。

# 5. Security Rules 設計方針（概要）

詳細は別途仕様書で定義する。ここでは基本方針のみ記載。

## 5.1 基本原則

- エンタープライズユーザーは、自社の `enterprise_id` に紐づくデータのみアクセス可能
- `request.auth.token.enterprise_id`（custom claims）を使って制御する
- プラットフォーム版の既存ルールはそのまま維持し、エンタープライズ向けのルールを追加する
- **エンプラユーザーは PF版コミュニティ（`enterprise_id` 未設定 = PF データ）にもアクセス可能**（ゲスト参加機能と組み合わせ、社外イベントへの参加を許可）。Rules 上は `docEnterpriseId(data) == null` で表現（§5.2）

## 5.2 主要なルールパターン

PF版既存データには `enterprise_id` フィールドが存在しない。`resource.data.enterprise_id == null` はフィールド欠如時に評価エラーになるため、**`data.get('enterprise_id', null)` パターン**を用いる（`null` = PF版データとして扱う）。

```javascript
// 共通ヘルパー（firestore.rules）
function docEnterpriseId(data) {
  return data.get('enterprise_id', null);   // フィールド欠如時も安全に null
}
function isSameEnterprise(data) {
  return request.auth != null
    && docEnterpriseId(data) != null
    && docEnterpriseId(data) == request.auth.token.enterprise_id;
}
// 使用例: allow read: if docEnterpriseId(resource.data) == null || isSameEnterprise(resource.data);

// ヘルパー（エンプラ communities 用。PF 版 isManager() と同等の manager 判定 + テナント分離）
function isEnterpriseCommunityManager(communityId) {
  return request.auth != null
    && exists(/databases/$(database)/documents/communities/$(communityId)/members/$(request.auth.uid))
    && "manager" in get(/databases/$(database)/documents/communities/$(communityId)/members/$(request.auth.uid)).data.roles
    && docEnterpriseId(get(/databases/$(database)/documents/communities/$(communityId)).data) == request.auth.token.enterprise_id;
}

// エンタープライズ企業設定: 同一企業メンバーは read、write は Functions のみ
// - 会社名・ロゴ・割引ルールの更新は updateEnterpriseSettings / updateEnterpriseSubsidySettings 経由（監査ログ必須）
// - theme_color / allowed_email_domains は MVP では運営（isSupport）が createEnterprise または Admin SDK で設定
match /enterprises/{enterpriseId} {
  allow read: if request.auth.token.enterprise_id == enterpriseId;
  allow write: if false;
}

// エンタープライズメンバー（EnterpriseMember）: 同一企業メンバーは read、クライアントからの write は禁止
// - アカウント作成・表示名/部署更新・停止・復活・ロール変更は Cloud Functions（Admin SDK）経由（例: createEnterpriseMembers, updateEnterpriseMember）
// - monthly_usage / monthly_order_count は confirmOrder / stripeWebhook / cancelOrders のみが更新するため、クライアント write を許すと改ざんリスクがある
match /enterprises/{enterpriseId}/members/{userId} {
  allow read: if request.auth.token.enterprise_id == enterpriseId;
  allow write: if false;   // Functions のみ
}

// コミュニティ: PF 版 create 維持 + エンプラは同一 enterprise の全従業員可。update は PF 同等（community manager 限定）
match /communities/{communityId} {
  allow read: if docEnterpriseId(resource.data) == null
              || isSameEnterprise(resource.data);
  allow create: if (request.auth != null && request.resource.data.get('enterprise_id', null) == null)
              || (request.auth.token.enterprise_id != null
                  && request.resource.data.enterprise_id == request.auth.token.enterprise_id);
  allow update: if isSupport() || isEnterpriseCommunityManager(communityId);
}

// EventMember (members コレクション): PF版公開 + エンプラ自社 + 本人（ゲスト含む）
//   collectionGroup クエリ用ルールも同一条件（/{path=**}/member_orders/{oid}）
match /communities/{cid}/events/{eid}/members/{uid} {
  allow read: if docEnterpriseId(resource.data) == null
              || (request.auth != null && (
                   isSameEnterprise(resource.data)
                   || request.auth.uid == uid
                   || request.auth.uid == resource.data.user_id
                 ));
  allow write: if false;   // Functions のみ

  // EventMemberOrder (member_orders サブコレクション)
  match /member_orders/{oid} {
    allow read: if docEnterpriseId(resource.data) == null
                || (request.auth != null && (
                     isSameEnterprise(resource.data)
                     || request.auth.uid == resource.data.user_id
                   ));
    allow write: if false;
  }
}

// Event: PF版公開 + 同社従業員（allow_guest 未認証閲覧は将来実装）
//   collectionGroup クエリ用ルールも同一条件（/{path=**}/events/{event}）
match /communities/{cid}/events/{eid} {
  allow read: if docEnterpriseId(resource.data) == null
              || isSameEnterprise(resource.data);
  // write は既存ルールに従う
}

// EventStripe (stripes コレクション): 本人のみ read（MVP）
//   ゲストも request.auth.uid == resource.data.user_id で本人 read 可能
//   全社管理者の閲覧可否は将来再検討
match /communities/{cid}/events/{eid}/stripes/{sid} {
  allow read: if request.auth != null && request.auth.uid == resource.data.user_id;
  allow write: if false;
}

// collectionGroup 用（ダッシュボード集計は Functions 経由が正。クライアント direct クエリ用）
// ネスト match と同一 read 条件。/{path=**}/... が collectionGroup('member_orders') 等にマッチする
match /{path=**}/member_orders/{oid} {
  allow read: if docEnterpriseId(resource.data) == null
              || (request.auth != null && (
                   isSameEnterprise(resource.data)
                   || request.auth.uid == resource.data.user_id
                 ));
  allow write: if false;
}

match /{path=**}/stripes/{sid} {
  allow read: if request.auth != null && request.auth.uid == resource.data.user_id;
  allow write: if false;
}

match /{path=**}/events/{eventId} {
  allow read: if docEnterpriseId(resource.data) == null
              || isSameEnterprise(resource.data);
  allow write: if false;
}
```

# 7. 監査ログ設計

## 7.1 方針

MVP から最低限の監査ログ基盤を構築する。後付けするとログの欠損期間が発生し、大企業への説明で致命的になるため、初期から導入する。

## 7.2 ログ種別（MVP）

| 種別 | トリガー | 取得方法 |
|:--|:--|:--|
| `login` | 認証成功時 | Cloud Functions（OTP 検証成功時に記録） |
| `logout` | ユーザーによる手動ログアウト | フロントエンドから Functions を呼び出し |
| `session_timeout` | セッションタイムアウト（60分無操作） | フロントエンドから Functions を呼び出し |
| `account_create` | 管理者によるアカウント作成 | Cloud Functions 内で記録 |
| `account_disable` | 管理者によるアカウント停止 | Cloud Functions 内で記録 |
| `account_enable` | 管理者によるアカウント復活 | Cloud Functions 内で記録 |
| `role_change` | 管理者によるロール変更 | Cloud Functions 内で記録 |
| `community_approve` | 管理者によるコミュニティ承認 | Cloud Functions 内で記録 |
| `community_reject` | 管理者によるコミュニティ却下 | Cloud Functions 内で記録 |
| `discount_update` | 管理者による割引設定変更 | Cloud Functions 内で記録 |
| `order_create` | 注文確定時（`confirmOrder` / `stripeWebhook` の 1 回 = 1 ログ） | Cloud Functions 内で記録 |
| `order_cancel` | 注文キャンセル時（`cancelOrders` の 1 回 = 1 ログ） | Cloud Functions 内で記録 |
| `monthly_usage_exceeded` | `addToCart` 時に月額上限超過分が自己負担に切り替わった | Cloud Functions 内で記録 |
| `enterprise_subsidy_recalculated` | `confirmOrder` / `createStripeCheckoutSession` のサーバー側再計算で `failed-precondition` 発生 | Cloud Functions 内で記録 |

### ログ粒度の方針

EventMemberOrder 化により 1 メニュー = 1 ドキュメントとなったため、**注文系ログは「ユーザーが体感する 1 操作」単位** で記録する。メニュー単位で書くとログが膨大になるため、以下のとおり粒度を整理する。

| 種別 | 書き込み元 | 1 ログの単位 | `details` の必須項目 |
|:--|:--|:--|:--|
| `order_create` | `confirmOrder` 完了時 **または** `stripeWebhook` 完了時のいずれか 1 度のみ | 1 セッション（同時確定された order 群） | `order_ids: string[]`, `stripe_id?: string`, `total_payment: number`, `pay_enterprise_subsidy_amount?: number` |
| `order_cancel` | `cancelOrders` 完了時 | 1 キャンセル操作（複数 order をまとめて指定） | `order_ids: string[]`, `stripe_id?: string`, `refund_amount: number`, `returned_subsidy_amount?: number` |
| `monthly_usage_exceeded` | `addToCart` 内 | 1 カート操作 | `event_id: string`, `year_month: string`, `requested_amount: number`, `granted_amount: number`, `unfilled_count: number`（各キーの意味は `04_エンタープライズ_詳細仕様_監査ログ.md` 3.4 および 4.2 と同一） |
| `enterprise_subsidy_recalculated` | `confirmOrder` / `createStripeCheckoutSession` | 1 リクエスト | `event_id: string`, `order_ids: string[]`, `expected: number[]`, `stored: (number\|null)[]` |

> `cart_add` / `cart_remove` のようなカート操作ログは MVP では **追加しない**（`addToCart` / `removeFromCart` の頻度が高くノイズになるため）。Phase 2 で必要性を再検討する。

## 7.3 Firestore コレクション

企業ごとのサブコレクションとして格納する。全企業共通の `/audit_logs` にすると Security Rules が複雑になるため。

```
/enterprises/{enterpriseId}/audit_logs/{logId}
```

```typescript
interface AuditLog {
  enterprise_id: string
  user_id: string                 // 操作を行ったユーザーのID
  action: string                  // ログ種別（上記テーブル参照）
  target_id?: string              // 操作対象のドキュメントID（注文系では stripe_id 等の代表 ID）
  target_type?: string            // 'community' | 'event' | 'order_session' | 'member' | 'settings' | 'enterprise' | 'enterprise_subsidy_settings'
  timestamp: Timestamp
  ip_address?: string             // リクエスト元IPアドレス
  details?: Record<string, unknown>  // 追加情報（変更前後の値、order_ids 配列など）
}
```

> 注文系ログでは複数の `order_id` を `details.order_ids: string[]` に含めることでセッション全体を 1 ログで表現する（7.2 ログ粒度の方針参照）。

## 7.4 実装方式

| 出力先 | 用途 | 実装 |
|:--|:--|:--|
| **Firestore**（`/enterprises/{enterpriseId}/audit_logs`） | 全社管理者画面での閲覧 | Cloud Functions 内で操作実行時に書き込み |
| **Cloud Logging** | GCP コンソールでの横断検索・長期保存 | Cloud Functions の `logger.info()` で同時出力 |

### 実装イメージ（共通ユーティリティ）

```typescript
// functions/default/src/utils/auditLog.ts
import { logger } from 'firebase-functions/v2'
import { getFirestore, Timestamp } from 'firebase-admin/firestore'

interface WriteAuditLogParams {
  enterpriseId: string
  userId: string
  action: string
  targetId?: string
  targetType?: string
  ipAddress?: string
  details?: Record<string, unknown>
}

export async function writeAuditLog(params: WriteAuditLogParams): Promise<void> {
  const log = {
    enterprise_id: params.enterpriseId,
    user_id: params.userId,
    action: params.action,
    target_id: params.targetId ?? null,
    target_type: params.targetType ?? null,
    timestamp: Timestamp.now(),
    ip_address: params.ipAddress ?? null,
    details: params.details ?? null,
  }

  // Firestore に書き込み（管理者画面表示用）
  await getFirestore()
    .collection(`enterprises/${params.enterpriseId}/audit_logs`)
    .add(log)

  // Cloud Logging にも出力（横断検索・長期保存用）
  logger.info('audit_log', log)
}
```

## 7.5 Security Rules

```javascript
match /enterprises/{enterpriseId}/audit_logs/{logId} {
  // 読み取り: 全社管理者のみ
  allow read: if request.auth.token.enterprise_id == enterpriseId
              && request.auth.token.enterprise_role == "admin";
  // 書き込み: Cloud Functions（Admin SDK）からのみ。クライアントからの直接書き込みは禁止
  allow write: if false;
```

## 7.7 ログ保持期間

- MVP: 無期限（Firestore に蓄積）
- Phase 2: TTL（Time to Live）設定の導入を検討。Firestore の TTL ポリシーで自動削除が可能
- Cloud Logging 側はデフォルト30日保持。長期保存が必要な場合は Cloud Storage へのエクスポートを設定
