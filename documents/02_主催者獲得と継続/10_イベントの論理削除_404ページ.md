# イベントの論理削除_404ページ

## 1. 概要
### 1.1 機能の目的
論理削除されたイベントへのアクセスを適切に制限し、削除済みイベントを「存在しないイベント」として扱うことで、プライバシー保護とセキュリティを強化する。

### 1.2 主要な機能
- 削除済みイベント（`is_deleted: true`）へのアクセス時に404ページを表示
- ルーターガードによる一元的なアクセス制御
- 予約申請、注文などの全操作を自動的にブロック
- プライバシー保護（削除されたことを明示しない）

### 1.3 対象ユーザー
- **主催者**: 削除したイベントへの誤アクセスを防止
- **参加者**: 削除済みイベントへの注文やカート追加を防止
- **飲食店**: 削除済みイベントの予約承認を防止

### 1.4 現状の課題
- イベントの論理削除（`is_deleted: true/false`）は実装済み
- ユーザーは下書き中のイベントを削除できる
- しかし、論理削除のため、URLリンクを知っているとページが表示される
- 主催者による「予約申請」ができてしまう
- 飲食店による「予約承認」ができてしまう
- 参加者による「カート追加」「注文」ができてしまう

## 2. ねらい
### 2.1 ビジネス目標
- 削除済みイベントへの不正アクセス防止
- プライバシー保護の強化

### 2.2 ユーザー価値
- **主催者**: 削除したイベントが完全に非表示になることで安心感を提供
- **参加者**: 削除済みイベントへの誤った注文を防止
- **飲食店**: 削除済みイベントの処理を削減

### 2.3 成功指標（KPI）

- 削除済みイベントへの予約申請・注文が0件になる

#### 5.2.2 ルーター設定
**対象ファイル**:
- `user/src/router/index.ts`
- `admin/src/router/index.ts`

**実装内容**:
```typescript
// 1. 404ページルートを追加
const routes = [
  // ... 既存のルート
  { 
    path: '/404', 
    name: '404', 
    component: () => import('@/pages/404.vue') 
  },
  { 
    path: '/:pathMatch(.*)*', 
    redirect: '/404' 
  }, // 存在しないパスも404へ
]

// 2. ルーターガードで is_deleted チェックを追加
router.beforeEach(async (to) => {
  // イベント詳細ページへのアクセスの場合
  const eventIdMatch = to.path.match(/\/c\/[^/]+\/e\/([^/]+)/)
  if (eventIdMatch) {
    const eventId = eventIdMatch[1]
    const eventStore = useEventStore(eventId) as EventStore
    
    // イベント取得を待つ
    const event = await new Promise<BokudeliEvent | null>((resolve) => {
      watch(
        () => eventStore.event,
        (event) => {
          if (event != null) {
            resolve(event)
          }
        },
        { immediate: true }
      )
      
      // タイムアウト処理（5秒後に null を返す）
      setTimeout(() => resolve(null), 5000)
    })
    
    // 削除済みまたは存在しない場合は404へ
    if (!event || event.is_deleted) {
      return { name: '404' }
    }
  }
})
```

**実装箇所**:
- 既存の`router.beforeEach`（262行目あたり）に統合するか、新規で追加
- イベント情報取得のロジックは既存コードを再利用

### 5.4 Firestoreセキュリティルール（将来対応）
削除済みイベントへのアクセスをFirestoreレベルでも制限することを推奨します。

```javascript
// firestore.rules に追加
rules_version = '2';
service cloud.firestore {
  match /databases/{database}/documents {
    match /communities/{communityId}/events/{eventId} {
      // 削除済みイベントは読み取り不可（管理者を除く）
      allow read: if resource.data.is_deleted == false
                  || isManager(communityId)
                  || isSupport();
      
      // 削除済みイベントは書き込み不可（削除操作以外）
      allow update: if !resource.data.is_deleted 
                    || request.resource.data.is_deleted == true;
    }
  }
}
```

### 5.5 処理フロー
#### 5.5.1 削除済みイベントへのアクセスフロー
```markdown
1. ユーザーが削除済みイベントのURLにアクセス
2. ルーターガード（router.beforeEach）が起動
3. URLから eventId を抽出
4. useEventStore(eventId) でイベント情報を取得
5. event.is_deleted をチェック
   - is_deleted === true の場合: 404ページにリダイレクト
   - is_deleted === false の場合: ページを表示
6. 404ページが表示される
7. ユーザーは「トップページに戻る」ボタンでTOPページに遷移
```

#### 5.5.2 エラーハンドリング
```markdown
- イベント取得失敗時: タイムアウト（5秒）後に404ページへリダイレクト
- ネットワークエラー時: ローディング表示後、404ページへリダイレクト
- 存在しないイベントID: 404ページへリダイレクト
```

## 8. 検討した実装案
### 8.1 対応案1: 個別操作の制限
- 主催者による「予約申請」をブロック
- 飲食店による「予約承認」をブロック
- 参加者による「カート追加」「注文」をブロック

**不採用理由**: 実装箇所が多く、漏れが発生しやすい。メンテナンスコストが高い。

### 8.2 対応案2: モーダル表示 → TOP遷移
- 削除されたイベントページに遷移した時にモーダル画面で「イベントページは削除されています」と表示
- 数秒後自動的にTOPページに遷移

**不採用理由**: 数秒待たせるのはUX的に不適切。削除されたことを明示してしまう。

### 8.3 対応案3: 即座にTOP遷移
- 削除されたイベントページに遷移した時、有無を言わさず、TOPページに遷移
- ルーターで処理

**不採用理由**: ユーザーへのフィードバックが不十分。TOPページ以外に遷移したい場合に対応できない。

### 8.4 対応案4: 404ページ表示（採用）
- 削除済みイベントを「存在しないイベント」として扱い、404ページを表示
- ルーターで`is_deleted`を判定して、404ページに遷移

**採用理由**:
- プライバシー保護: 削除されたことを明示的に隠せる
- 実装がシンプル: ルーターガードで一元管理
- セキュリティ: 全操作を自動的にブロック
- 拡張性: 将来的に存在しないイベントIDやCommunityAccountにも対応可能
- UX: 標準的な404ページとして扱えるため、ユーザーの理解が容易
