# イベントページの「保存して進む」ボタン

## 1. 概要

### 1.1 課題
イベント作成や編集において入力途中の状態で保存されないことによって、ユーザーが離脱してしまう。別の画面に遷移したり、リロードすると入力内容がクリアされてしまう。画面ごとに保存ボタンを設けることで解決したい。

### 1.2 機能の目的
イベントページ作成時の5ステップのうち、複数のステップで下書き保存機能を提供し、ユーザーの入力ストレスを軽減し、離脱率を削減する。

### 1.3 主要な機能
- イベント作成・編集時の複数ステップでの下書き保存機能
- 「1.基本情報入力画面」「3.メニュー確認画面」「4.イベント詳細入力画面」の「次へボタン」を「保存して進む」ボタンに変更
- 下書き保存時の緩いバリデーション（途中経過でも保存可能）
- 予約申請時の厳格なバリデーション（全必須項目のチェック）

### 1.4 対象ユーザー
- イベント主催者
- コミュニティ管理者

## 2. ねらい

### 2.1 ビジネス目標
- イベント作成の離脱率を削減
- 主催者獲得率の向上
- 入力途中での離脱によるデータ損失の防止

### 2.2 ユーザー価値
- イベント作成プロセスのストレス軽減
- 途中保存による安心感の提供
- 画面遷移やリロード時の入力内容消失の防止

### 2.3 成功指標（KPI）
- イベント作成完了率の向上
- 下書き保存から本保存への変換率
- ユーザー満足度スコア
- 入力途中での離脱率の削減

## 5. 技術仕様・データ構造設計

### 5.1 バリデーション設計

#### 5.1.1 下書き保存時のバリデーション（緩い）
- **目的**: 途中経過でも保存できるようにする
- **適用タイミング**: 「保存して進む」ボタン押下時
- **バリデーションルール**:
  - 必須項目のチェックを緩くする
  - 入力されている項目のみを保存
  - 未入力項目は空文字やデフォルト値で保存可能
  - `EventDraftDbSchema`を使用（後述）

#### 5.1.2 予約申請時のバリデーション（厳格）
- **目的**: 全ての必須情報が揃っていることを保証
- **適用タイミング**: 「予約申請」ボタン押下時
- **バリデーションルール**:
  - `EventDbSchema`で全ての必須項目をチェック
  - 必須項目が不足している場合はエラー
  - エラーダイアログで「XXXが入力されていません」と表示
  - バリデーション成功時のみ予約申請を実行

### 5.2 Firestoreスキーマ設計

#### 5.2.1 EventDraftDbSchema（下書き保存用）
- **用途**: 下書き保存時に使用するスキーマ
- **特徴**:
  - バリデーションが緩い（必須項目が少ない）
  - 途中経過でも保存可能
  - `EventDbSchema`とは別に定義することを検討
- **必須項目の例**:
  - `event_id`, `community_id`, `community_name`, `community_account`
  - `event_status.value`: `'in_draft'`
  - その他の項目はオプションまたはデフォルト値で保存可能

#### 5.2.2 EventDbSchema（予約申請用）
- **用途**: 予約申請時に使用するスキーマ
- **特徴**:
  - 全必須項目が揃っている必要がある（厳格なバリデーション）
  - `applying_reservation`への遷移時に使用
- **必須項目の例**:
  - `event_id`, `community_id`, `community_name`, `community_account`
  - `event_postalcode`: 7桁の数字
  - `event_address`: 空でない文字列
  - `shop_id`, `shop_name`: 空でない文字列
  - `event_name`, `event_cover_url`: 空でない文字列（URL形式）
  - `organizer_fullname`, `organizer_company`, `organizer_email`, `organizer_phone_personal`, `organizer_memo`: 空でない文字列
  - その他、日時やステータス関連の必須項目

#### 5.2.3 データ構造（参考）
```typescript
// イベントドキュメント（in_draft時）
interface EventDraft {
  // ステータス
  event_status: {
    value: 'in_draft'
    shop_comment?: string
  }

  // 基本情報（下書き保存時に入力された項目）
  event_start_datetime?: Timestamp;
  event_end_datetime?: Timestamp;
  event_postalcode?: string;
  event_address?: string;
  
  // デフォルト値または後から入力
  event_name?: string;
  event_cover_url?: string;
  event_desc?: string;
  event_payment?: 'user_advance';
  event_max_people?: number;
  is_public?: boolean;
  
  // 後から入力される項目（オプション）
  shop_id?: string;
  shop_name?: string;
  event_deadline_datetime?: Timestamp;
  
  // 主催者情報（予約申請時に必須）
  organizer_fullname?: string;
  organizer_company?: string;
  organizer_email?: string;
  organizer_phone_personal?: string;
  organizer_memo?: string;
}
```

### 5.3 Firestoreフロントエンド処理
- **データ更新処理**: 複数ステップで下書き保存実行（`EventDraftDbSchema`を使用）
- **バリデーション処理**: 予約申請時に`EventDbSchema`による全必須データチェック
- **リアルタイム監視**: イベントステータスの変更を監視
- **エラーハンドリング**: 保存失敗時のリトライ機能

### 5.4 Functions設計
なし

### 5.5 処理フロー

#### 5.5.1 下書き保存処理フロー（「保存して進む」ボタン押下時）
1. ユーザーが各ステップで情報を入力
2. フォームバリデーション実行（緩いバリデーション）
3. 下書き保存用データを構築
   - `EventDraftDbSchema`を使用
   - 入力されている項目のみを保存
   - 未入力項目は空文字やデフォルト値で保存可能
4. Firestoreにイベントドキュメント作成または更新
   - 新規作成時: イベントIDを生成して作成
   - 既存更新時: 既存のイベントを更新
5. 成功通知を表示
6. 次のステップに遷移

#### 5.5.2 予約申請処理フロー（「予約申請」ボタン押下時）
1. ユーザーが「予約申請」ボタンを押下
2. `EventDbSchema`による全必須データのバリデーション実行
   - 必須項目が不足している場合はバリデーション失敗
3. バリデーション成功時:
   - `event_status.value`を`'applying_reservation'`に更新
   - `EventDbSchema`にパースしてFirestoreに保存
   - 成功通知を表示
4. バリデーション失敗時:
   - エラーダイアログを表示
   - 不足している必須項目を「XXXが入力されていません」と表示
   - ステータス遷移を阻止（`in_draft`のまま）
   - 該当する入力画面に遷移を促す
