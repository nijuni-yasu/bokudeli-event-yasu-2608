# アルバム機能

## 1. 概要

### 1.1 機能の目的

コミュニティ単位で複数枚の写真を登録・並べ替え・説明付きで管理し、コミュニティページおよびイベントページでメインカバー画像の**下**にサムネイル行としてスライド表示できるようにする。ainii の「体験に複数写真」のように、一度登録したアルバムを複数イベントで使い回せる前提とする。

### 1.2 主要な機能

- コミュニティ管理画面でアルバム画像の追加・削除・説明文・並び替え（admin の並び替え UI パターンに準拠）
- コミュニティページ／イベントページで、メインカバー**直下**にサムネイルを **最大 4 枚まで** 横一列で表示し、ainii に近い「全ての写真を表示する」導線とライトボックス（暗転・説明文・左右ナビ）で閲覧する
- イベント編集画面で、アルバム画像のうち「このイベントで表示する／しない」を選択（デフォルトは全件表示）
- イベント編集画面からのアップロードはコミュニティアルバムへの追加とする

### 1.3 対象ユーザー

- コミュニティ管理者（画像管理・イベントごとの表示制御）
- コミュニティ・イベント閲覧ユーザー（閲覧・ライトボックス操作）

## 2. ねらい

### 2.1 ビジネス目標

- 主催者がコミュニティの魅力を視覚的に伝えやすくし、イベント参加・リピートに寄与する（数値目標はプロダクト側で設定）

### 2.2 ユーザー価値

- 一枚のカバーに頼らず雰囲気を伝えられる
- イベントごとに写真の出し分けができ、準備の手間を抑えつつ見せ方を調整できる

### 2.3 成功指標（KPI）（例）

- アルバム掲載コミュニティ数、アルバム画像枚数の分布
- イベントページにおけるライトボックス操作率（取得可能なら）

## 3. 前提条件

### 3.1 技術的前提条件

- 画像アップロードは既存ユーティリティをベースにする。**リサイズ（クライアント・サーバーサムネイル生成）は別イシューとして扱い、Phase 1 ではリサイズなしで実装する**（最大サイズ・拡張子・枚数上限などビジネスルールは別途定義）
- **メール・OGP・既存のカバー参照箇所**は、従来どおり **カバー画像 1 枚**（`community_cover_image_url` / `event_cover_url` 等）を維持する。アルバムはこれらの代替にはしない
- Firestore / Storage の操作はプロジェクトルールどおり **store 経由・withConverter・Zod スキーマ**で定義する（実装フェーズで `common` / `base` に反映）

### 3.2 ビジネス的前提条件

- コミュニティアルバムの登録 **最大枚数** は**要検討**（上限なしはストレージ・読み込みコストの観点で非推奨）
- **公開ページのギャラリー**では、カバー画像の**直下のサムネイル行**にアルバムを **最大 4 枚** まで並べる（5 枚目以降はサムネイル行には出さず、ライトボックス内で閲覧する）。イベント編集の `event_album_item_ids` による絞り込みがある場合は、**絞り込み後のリストの先頭から最大 4 枚**をサムネイル行に表示する

### 3.3 依存関係

- コミュニティ・イベントの既存権限（管理者・編集者）
- 既存のコミュニティページ・イベント編集・イベント詳細の UI 構成

## 4. 画面仕様

### 4.1 画面遷移

- **コミュニティ管理** → `album` タブ（既存タブ `slackSetting` の次に新設。`user/src/pages/manage/community/[communityAccount]/[tab].vue` の `tabs` に `'album'` を追加し、`user/src/components/manage/community/album.vue` を作成する）
- **イベント編集** → アルバム表示設定（一覧＋表示 ON/OFF）＋ アップロード（コミュニティアルバムへ追加）
- **コミュニティページ／イベントページ** → カバー全幅＋**その下**のサムネイル行 **最大 4 枚** → 画像タップまたは「全ての写真を表示する」でライトボックス（先頭スライドはカバー）

### 4.2 UI 要素

#### 4.2.1 コミュニティ管理（画像管理／アルバム）

- 複数画像をアップロードできる。画像ごとに説明文言を追加できる
- 並び順を編集できる（admin の並び順変更 UI を利用）
- コミュニティアルバムとして登録可能な最大枚数（**要検討**）
- 削除（確認ダイアログ）
- **アルバム 0 件時**：「まだアルバム画像がありません」等の空状態メッセージとアップロード誘導 UI を表示する

#### 4.2.2 イベント編集

- 表示する画像を選択できる。デフォルトで全て表示。クリックで非表示
- 画像をアップロードするとコミュニティのアルバム画像として登録される（当該イベントではデフォルト表示とする想定）
- イベント編集画面で表示可能な最大枚数（**要検討**）

#### 4.2.3 コミュニティページ（公開）

コミュニティページとイベントページで **ギャラリーとライトボックスの挙動は原則共通** とする。相違点はカバー画像の参照元のみ（本節はコミュニティ用）。

- **レイアウト**：**上段**に **コミュニティカバー**（`community_cover_image_url`）を**全幅**で表示する。**下段**に **アルバム画像を親コミュニティの `community_album_item_ids` の順で最大 4 枚**を**横一列**で並べる。サムネイル行は常に **4 スロット**とし、表示対象が 4 枚未満のスロットはプレースホルダーで埋める。5 枚目以降のアルバムはサムネイル行には表示しない
- **サムネイルの幅**：カバーと同じコンテナ幅を基準に、各サムネイルの幅はおおよそ **カバー幅の 1/4.1** 程度とし、スロット間のギャップを考慮して調整する（実装では `calc` 等で行う）
- **サムネイル比率**：**1200:630（約 1.9:1）** とし、`object-fit: cover` でトリミング表示する
- **角丸**：カバーとサムネイルに同一の角丸スタイルを適用する（例：Vuetify の `rounded`）
- **「全ての写真を表示する」ボタン**：ギャラリー領域（カバーとサムネイル行をまとめたブロック）の **右下** に重ねて表示する。文言は **全ての写真を表示する** とする（i18n キーは実装で定義）
  - アルバムが **1 件以上** あるときに表示する。**アルバム 0 件時はボタンを出さない**
  - クリックでライトボックスを開く。開いたときの **初期スライドインデックスは 0**（カバー画像）
- **クリックでライトボックス**：カバー画像、サムネイル行の各サムネイルの **表示領域をクリックしたとき** にライトボックスを開く。クリックした画像が **ライトボックス上で何枚目に相当するか** を初期インデックスとする（カバーは 0 番目、サムネイル行 1 枚目のアルバムは 1 番目、…、4 枚目は 4 番目）
- **ボタンとクリックの競合**：ボタン上のクリックは「全ての写真を表示する」動作のみとし、背面のカバー／サムネイルのクリックハンドラと二重に発火しないよう制御する
- **アルバム 0 件時**：従来どおり **カバー画像のみ全幅**（サムネイル行・右下ボタンは非表示）
- **レスポンシブ**：現状はカバー下の横一列を**ブレークポイントによらず共通**とする。折り返し・横スクロール等の最適化は**要検討**

#### 4.2.4 イベントページ（公開）

- **レイアウト・ボタン・クリック挙動**：4.2.3 と同様。上段のカバーは **`event_cover_url`** を用いる
- **表示するアルバムの集合**：Phase 2 で `event_album_item_ids` を実装した場合は **その配列に含まれる ID のみを、配列の順序どおり** を対象とし、未実装または空配列の後方互換時は **`community_album_item_ids` の順でコミュニティアルバム全件** を対象とする。対象リストの **先頭から最大 4 枚** をサムネイル行に表示する
- **実装箇所**：イベント詳細は `base/src/components/EventDetailsCard.vue` を拡張する。親ページからアルバム用の URL 一覧等を props で渡す。`admin` ではこのコンポーネントを使用しないため、`base` 変更の影響範囲は公開 user アプリのイベント詳細に限定される

#### 4.2.5 ライトボックス内のスライド順（公開ページ共通）

- **1 番目（インデックス 0）**：必ず **当該ページのカバー画像**（コミュニティページなら `community_cover_image_url`、イベントページなら `event_cover_url`）。説明タイトルは空またはイベント名・コミュニティ名など実装で決める
- **2 番目以降**：対象となる **全アルバム画像** を、当該ページの **有効な並び**（コミュニティページなら `community_album_item_ids` の順、イベントページなら §4.2.4 と同じく `event_album_item_ids` が非空ならその順・空なら `community_album_item_ids` の全件順）で並べる。サムネイル行に出していない枚数もここに含め、枚数制限はライトボックス内では行わない
- **「全ての写真を表示する」**：常にインデックス 0 から開く

#### 4.2.6 ライトボックスの実装方針（ライブラリ）

- **専用ライブラリを使用する**。自前実装はせず、Vue 3 対応のライトボックスライブラリ（例：`vue-easy-lightbox`、`v-viewer` 等）を選定する
- 選定基準：Vue 3 対応、TypeScript 型定義あり、スワイプ対応、メンテナンスが継続されている、バンドルサイズが小さい
- ライブラリの最終選定は実装時に行う

#### 4.2.7 アクセシビリティ（推奨）

- ライトボックス：閉じる操作、フォーカストラップ、キーボード操作を可能な範囲で検討する

## 5. 技術仕様・データ構造設計

### 5.1 方針

- **`event_cover_url` のようなカバー用 URL フィールドをアルバム分には増やさない**方針を維持する。アルバムは別ドキュメント群で管理する
- **Storage** は決め打ちパスにアップロードする。**並び順はコミュニティ親ドキュメントの `community_album_item_ids`（`albumItemId` の配列）**で管理し、**説明文等のメタデータは `album_items` サブコレクション**に持つ。ファイル名に並び順を埋め込まない
- **アルバム画像の download URL（トークン付き HTTPS URL）は Firestore に保存しない**。Firebase プロジェクト移行時に保存 URL が無効化されるのを避けるため。表示時は `communityId` と `albumItemId` から **コード上で組み立てた Storage パス**に対し、`getDownloadURL()` 等で都度取得する（既存のカバーは `event_cover_url` 等に **URL を保存**する実装だが、アルバムは **URL もパス文字列も DB に持たない**）
- **Storage 上のオブジェクトキー（パス）は Firestore に保存しない**。`communityId` と `albumItemId`（ドキュメント ID）から `common/src/utils/storagePaths.ts` の規約どおりに常に一意に生成できるため冗長としない
- **メール・OGP** は従来のカバー 1 枚を継続利用し、アルバム用フィールドは追加しない
- **公開ページのライトボックス用スライド配列**は Firestore に保存せず、フロントで **先頭に既存のカバー URL フィールド**、続けて **対象アルバムを当該ページの有効な並び（4.2.5）** で結合して組み立てる

### 5.2 Firestore スキーマ設計（案）

#### 5.2.0 並び順の持ち方（方針）

- **`album_items` ドキュメントには並び用フィールド（旧案の `album_sort_number` 等）を持たせない**。並び替えのたびに多数のサブドキュメントを更新するのを避けるため。
- **コミュニティ親ドキュメント**に **`community_album_item_ids: string[]`** を新設し、**配列の順序＝コミュニティ全体での表示順**とする（先頭が先に表示）。各要素は `album_items` のドキュメント ID（`albumItemId`）と一致させる。
- 一覧表示時は **`community_album_item_ids` の順に ID を解決**し、必要に応じて `album_items/{albumItemId}` を読む（実装では `album_items` を一括取得したうえでクライアント側で配列順に並べ替えてもよい）。

#### 5.2.1 コミュニティ親ドキュメントへのフィールド追加（案）

**パス**

```
/communities/{communityId}
```

| フィールド | 型 | 必須 | DbSchema | AppSchema | 説明 |
|-----------|-----|------|----------|-----------|------|
| `community_album_item_ids` | `string[]` | 任意 | `z.array(z.string()).optional()` | `z.array(z.string()).default([])` | **アルバム表示順**。各要素は `album_items` のドキュメント ID。未定義・空配列はアルバム 0 件相当。実データとの整合（配列にあってサブコレクションにない ID、逆にサブコレクションのみ存在）は実装でフィルタする |

※ 既存コミュニティにはフィールドがないため optional／default で後方互換とする。

#### 5.2.2 新規サブコレクション（案）

**コレクション配置図**（既存構造に対する追加位置）

```
/communities/{communityId}
  /events/{eventId}
    /orders/{orderId}
    /menus/{menuId}
  /members/{userId}
  /invites/{inviteId}
  /letters/{letterId}
  /bots/{botId}
  /album_items/{albumItemId}  ← 新規追加
```

**パス**

```
/communities/{communityId}/album_items/{albumItemId}
```

| フィールド | 型 | 必須 | DbSchema | AppSchema | 説明 |
|-----------|-----|------|----------|-----------|------|
| `album_caption` | string | 任意 | `NonEmptyStringSchema.optional()` | `z.string().default('')` | 説明文（空文字はフィールド削除に変換される） |
| `created_at` | Timestamp | 必須 | `TimestampSchema` | `EpochMillisSchema` | 作成日時 |
| `updated_at` | Timestamp | 必須 | `TimestampSchema` | `EpochMillisSchema` | 更新日時 |

※ 画像の場所は **`albumItemId`（ドキュメント ID）** と親の `communityId` から決める（下記 §5.3）。`storage_path` や download URL は持たない。
※ **表示順は本ドキュメントではなく `community_album_item_ids` の配列順で決まる**。

#### 5.2.3 イベントごとの表示制御（Phase 2）

**※ Event スキーマ（`common/src/schemas/Event.ts`）へのフィールド追加は Phase 2 で実施する。Phase 1 では Event に手を入れない。**

`/communities/{communityId}/events/{eventId}` に以下のフィールドを追加する：

- **`event_album_item_ids: string[]`** … **このイベントで表示する `albumItemId` のリスト**（表示リスト方式）。**配列の順序がイベントページでの表示順**とする

**表示リスト方式の挙動**：
- **イベント作成時**：当時の **`community_album_item_ids` をコピー**して `event_album_item_ids` とする（デフォルト全表示・順序もコミュニティに合わせる）
- **イベント編集時**：コミュニティアルバム一覧を表示し、チェック ON/OFF や並び替えで `event_album_item_ids` を更新する。コミュニティに新しく追加された画像は「未選択」状態で表示される
- **コミュニティで画像削除**：イベントからも消える（実体がないため）。`event_album_item_ids` に残った ID は表示時に無視する
- **コミュニティで画像差し替え**：イベントにも反映される（同じ ID のため）
- **コミュニティで画像追加**：イベントには**自動追加されない**（`event_album_item_ids` に入っていないため）。これにより、**イベント作成時点の画像構成がほぼ維持される**

既存イベントにはこのフィールドが存在しないため、**DbSchema では `z.array(z.string()).optional()`、AppSchema では `z.array(z.string()).default([])` とする**。`event_album_item_ids` が空配列のイベントでは、**`community_album_item_ids` の順でコミュニティアルバム全件**を表示する（後方互換）。

#### 5.2.4 インデックス

- 並びは親ドキュメントの配列で完結するため、**`album_sort_number` 用の単一フィールドインデックスは不要**。
- `album_items` を親配下で **条件なし一覧取得**する程度であれば複合インデックスは不要なことが多い（実装時にクエリを確定し、必要なら `firestore.indexes.json` を更新）

### 5.3 Storage

- **パス上のセグメント名**は Firestore のサブコレクション **`album_items`** と**同一**とする（`…/album/…` など別名は用いない）。開発段階のため既存オブジェクトの移行は不要
- **オブジェクトキー（パス）の規約**（例）：`communities/{communityId}/album_items/{albumItemId}`  
  - **`albumItemId` をファイル名相当の末尾とする**（＝ドキュメント ID と 1 対 1）。**拡張子は付けない**（`.jpg` / `.png` / `.webp` 等どれでもよい前提で、拡張子に依存しない）
  - アップロード時は Storage メタデータで **`contentType`** を必ず設定する（拡張子推測に頼らない）。画像差し替え時は同一キーに上書きし、必要に応じて `contentType` も更新する
- **パス文字列は Firestore に保存しない**。`getCommunityAlbumItemStoragePath(communityId, albumItemId)` のような関数で生成し、`ref` → 表示時に `getDownloadURL()` 等で取得する
- **詳細**は `common/src/utils/storagePaths.ts` に関数を追加して定義する
- プロジェクト移行時は、**同一のオブジェクトキー規約**で Storage をコピーすれば、Firestore の `albumItemId` のみで参照を再構築できる
- **アップロードユーティリティ**：既存の `base/src/utils/storage.ts` の `uploadImage` は download URL を返す関数のため、アルバムでは URL を返さない専用関数（例：`uploadAlbumImage`）を追加する。`contentType` は `File` オブジェクトの `type` プロパティから **推論**する（`uploadBytes` の第3引数に `{ contentType: file.type }` を渡す）。`File.type` が空文字の場合は `application/octet-stream` をフォールバックとする
- **画像リサイズ**：アルバム画像のリサイズ方針（クライアント側でのリサイズ・サーバー側でのサムネイル生成など）は**別イシューとして実装する**。Phase 1 ではリサイズなしで原寸アップロードとし、後続イシューでリサイズ・サムネイル生成の要否と手段を決定する
- **アップロード上限**：**1 枚あたり最大 10MB**。Storage ルールで `request.resource.size < 10 * 1024 * 1024` をチェックし、クライアント側でもファイル選択時にバリデーションする
- **`getDownloadURL` のキャッシュ戦略**（Phase 2）：Store の subscribe 時に全 `albumItemId` に対して `getDownloadURL()` をまとめて呼び出し、**メモリ上にキャッシュ**する（Firestore には保存しない）。ページ離脱（Store の unsubscribe）でキャッシュを破棄する。これにより一覧表示時のネットワークコールを初回のみに抑える。**Phase 1 では専用 store は作成せず、コンポーネント内で直接 `getDownloadURL()` を呼ぶ簡易実装とする**。store の subscribe / unsubscribe ライフサイクル設計は Phase 2 で行う
- **複数枚一括アップロード**：`<input type="file" multiple accept="image/*">` で複数ファイルを選択可能にする。選択後は**逐次（シーケンシャル）アップロード**とし、全体の進捗を表示する（「3/5 枚アップロード中...」等）。1 枚が失敗した場合は**成功分は保存し、失敗分のみエラー表示**する（全体ロールバックはしない）。各成功分ごとに **`album_items` 作成と `community_album_item_ids` への ID 追加**を行い、**選択順がそのまま配列末尾に追記される**ようにする（一括の末尾にまとめて追加してもよいが、**ユーザーが選んだ順序を保つ**こと）

### 5.4 Firestore セキュリティルール・Storage ルール

#### Firestore（`album_items`・コミュニティ親の `community_album_item_ids`）

既存の `isManager()` 関数（`members` サブコレクション + `roles` フィールドで判定）を再利用する。

- **`album_items`**：読み取り・更新は既存のコミュニティ公開範囲・管理者権限の方針に合わせる（下記は案。公開ページからの読み取りが必要なら `read` を緩和する等、実装時に確定）
- **`/communities/{communityId}` の `community_album_item_ids`**：並び替え・追加・削除のたびにコミュニティ親ドキュメントを更新する。**既存の `communities` 更新ルール**にこのフィールドの変更が含まれるよう整理する（マネージャーのみが更新可能、など）

```javascript
match /communities/{community} {
  // 既存の isManager() をそのまま利用
  // function isManager() {
  //   return request.auth != null &&
  //     exists(/databases/$(database)/documents/communities/$(community)/members/$(request.auth.uid)) &&
  //     "manager" in get(/databases/$(database)/documents/communities/$(community)/members/$(request.auth.uid)).data.roles
  // }

  match /album_items/{albumItemId} {
    allow read, write: if isManager()
  }
}
```

#### Storage（`communities/{communityId}/album_items/{albumItemId}`）

```javascript
match /communities/{communityId}/album_items/{albumItemId} {
  allow read: if true;  // 公開画像として扱う（Firestore 側で公開制御）
  allow write: if request.auth != null
    && request.auth.uid in firestore.get(/databases/(default)/documents/communities/$(communityId)).data.managers
    && request.resource.contentType.matches('image/.*')
    && request.resource.size < 10 * 1024 * 1024;  // 10MB 上限
}
```

※ 上記はルール案。現行の `storage.rules` は期限付きの緩いルールのため、本番水準への移行は別タスクとして扱う場合あり。

### 5.5 Functions 設計

- **原則不要**：フロントから Firestore + Storage で完結できるなら Callable は作らない（プロジェクトの Functions 方針に合わせる）
- 複数ドキュメントの一貫更新が必要な場合のみ Transaction や Callable を検討

### 5.5.1 並び替え保存の方針

- 並び替えは **`/communities/{communityId}` の `community_album_item_ids` だけを更新**する（**1 ドキュメント・1 回の書き込み**で済む）。配列を UI 上の並びどおりに並べ替えて `update` する
- `album_items` サブドキュメントの並び用フィールドは持たないため、**`writeBatch` で多数の `album_items` を更新する処理は不要**
- 競合時は最終書き込み優先になりうるため、必要に応じて **Transaction** や **楽観的ロック**を検討する（枚数・更新頻度が低ければ単純 `update` で開始してよい）

### 5.6 処理フロー（例：アルバム画像追加）

1. 管理者が画像を選択
2. `doc()` で `albumItemId` を**事前に生成**する（ドキュメントはまだ作成しない）
3. `communities/{communityId}/album_items/{albumItemId}`（拡張子なし）へ Storage にアップロードし、`contentType` を設定する
4. アップロード成功後に **`album_items/{albumItemId}` ドキュメントを作成**し、**同一トランザクションまたは続けて** コミュニティ親の **`community_album_item_ids` の末尾に `albumItemId` を追加**する（配列の順が表示順）
5. コミュニティページの購読／再取得で反映

**一時状態への対処**：ドキュメント作成は Storage アップロード成功後に行う（ID は `doc()` で先に生成するが、Firestore への書き込みは後）。これにより「ドキュメントはあるが画像がない」状態を防ぐ。**`album_items` の作成と `community_album_item_ids` の更新は原則まとめて成功させる**（Transaction 推奨）。片方だけ成功すると「配列にないサブドキュメント」や「配列だけ残ってメタデータがない ID」が一時的に生じうるため、実装では整合チェック・再試行を検討する。万一 Storage アップロードが成功して Firestore 書き込みが失敗した場合は、Storage に孤立オブジェクトが残るが、ドキュメント／配列に載らないため画面には表示されない（孤立オブジェクトの掃除は運用考慮事項として扱う）。

### 5.7 処理フロー（例：アルバム画像削除）

1. 管理者が削除対象の画像を選択し、確認ダイアログで承認
2. **Firestore**：`album_items/{albumItemId}` を削除し、**コミュニティ親の `community_album_item_ids` から当該 ID を除去**する（Transaction 推奨）→ 画面から即座に消える（subscribe で検知）
3. **Storage オブジェクト削除**：`communities/{communityId}/album_items/{albumItemId}` を削除する → 孤立ファイル防止
4. Firestore 削除が成功しても Storage 削除が失敗した場合は、孤立オブジェクトが残るがユーザーには表示されない（ドキュメントがないため）。エラーログを記録し、運用で定期清掃する想定
5. イベント側の `event_album_item_ids` に削除済み ID が残っている場合は、表示時に存在チェックして無視する（明示的な除去は不要。イベント編集時に保存すればリストが自然に更新される）

### 5.8 処理フロー（例：アルバム画像差し替え）

1. 管理者が既存のアルバム画像をクリックし、差し替え用のファイルを選択する
2. 同一 `albumItemId` の Storage パス（`communities/{communityId}/album_items/{albumItemId}`）に新しい画像を**上書きアップロード**する（`contentType` も `file.type` から更新）
3. アップロード成功後、Firestore ドキュメント（`album_items/{albumItemId}`）の `updated_at` を更新する
4. **`getDownloadURL` のキャッシュ無効化**：Storage オブジェクトが上書きされるとトークンが変わるため、該当 `albumItemId` のキャッシュを破棄し、`getDownloadURL()` を再取得する
5. 画面上で新しい画像に差し替わる

### 5.9 処理フロー（例：イベントのアルバム表示制御）

1. イベント作成時：当時の **`community_album_item_ids` をそのまま（順序を保って）`event_album_item_ids` にコピー**する
2. イベント編集時：コミュニティアルバム一覧を表示し、チェック ON/OFF や並び替えで `event_album_item_ids` を更新する
3. イベントページでは **`event_album_item_ids` が非空ならその配列順で** ID を解決して表示し、**空配列の場合は `community_album_item_ids` の順で全件表示**＝後方互換

### 5.10 Zod スキーマ定義案

`common/src/schemas/AlbumItem.ts` に定義する。既存の `User.ts`、`EventMenu.ts` 等のパターンに合わせる。利用側では `import { AlbumItem } from '@shokujii/common/schemas/AlbumItem.js'` のように**直接パス指定**でインポートする（既存スキーマと同じパターン。`index.ts` からの re-export は不要）。

```typescript
import { z } from 'zod'
import { EpochMillisSchema, NonEmptyStringSchema, TimestampSchema } from './firebase/index.js'

const AlbumItemDbSchema = z.object({
  // Mandatory
  created_at: TimestampSchema,
  updated_at: TimestampSchema,
  // Optional
  album_caption: NonEmptyStringSchema.optional(),
})

const AlbumItemAppSchema = z.object({
  // Default
  album_caption: z.string().default(''),
  created_at: EpochMillisSchema,
  updated_at: EpochMillisSchema,
})

const convertToDb = (item: AlbumItem) => {
  return {
    ...item,
    updated_at: Date.now(),
  }
}

export class AlbumItem {
  readonly id: string
  album_caption!: string
  created_at!: number
  updated_at!: number

  constructor(id: string, src: Partial<AlbumItem>) {
    Object.assign(this, AlbumItemAppSchema.parse(src))
    this.id = id
  }

  isValidForDatabase(): boolean {
    return AlbumItemDbSchema.safeParse(convertToDb(this)).success
  }

  toFirestore(): z.infer<typeof AlbumItemDbSchema> {
    return AlbumItemDbSchema.parse(convertToDb(this))
  }
}
```

※ 表示順は **`community_album_item_ids` / `event_album_item_ids`** 側で持つため、本スキーマには含めない。Community / Event のスキーマに上記配列フィールドを追加する（実装時に `common` で定義）。

## 8. 注意事項

### 8.1 既存システムへの影響

#### 8.1.1 データベース構造への影響

- **新規サブコレクション**：`album_items`（案）
- **コミュニティ親ドキュメント**：`community_album_item_ids` 追加
- **既存イベントドキュメント**：表示制御フィールド追加（`event_album_item_ids`）
- **インデックス**：並びは配列で完結するため `album_sort_number` 用インデックスは不要。`album_items` の取得クエリ確定後に必要なら `firestore.indexes.json` を更新

#### 8.1.2 アプリケーションへの影響

- **OGP・メール**：カバー 1 枚維持のため、`event_cover_url` / `community_cover_image_url` 参照に論理変更なし（アルバムは追加表示のみ）
- **カバー vs アルバムの保存の違い**：カバーは URL をフィールドに保存する。アルバムは **URL もパス文字列も保存せず**、`communityId` + `albumItemId` から Storage 参照を組み立てる
- **フロント**：コミュニティトップ・イベント詳細のレイアウト変更、ライトボックスコンポーネント新規、公開ギャラリーの **カバー下サムネイル行最大 4 枚**・**全ての写真を表示する** ボタン・**カバーを先頭としたスライド配列** など ainii 準拠 UI の追加・変更。**表示順は `community_album_item_ids` / `event_album_item_ids` の配列順**で組み立てる

#### 8.1.3 運用への影響

- **ストレージ**：枚数上限の設計がないと使用量が増加しうる
- **整合性**：画像削除時に Storage オブジェクト削除と Firestore の整合（孤立ファイル防止）
- **パフォーマンス**：大量画像時は一覧取得のページングまたは件数上限を検討

### 8.2 セキュリティ考慮事項

- アルバムの read は公開コミュニティ／公開イベントの範囲に合わせる
- write はコミュニティ管理者のみ

### 8.3 運用考慮事項

- ログ・監視：必要に応じてアップロード失敗・ルール拒否を記録
- 拡張性：将来、コミュニティ間共有などが必要になった場合の ID 設計を意識する
