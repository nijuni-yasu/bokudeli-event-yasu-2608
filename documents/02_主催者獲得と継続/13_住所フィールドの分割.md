# 住所フィールドの分割

## 課題

- イベントの詳細住所の入力欄を入れ忘れることがある
- 現状郵便番号を入れたら次に進める
- 予約申請後は主催者も変更することができない状態

## 対応

- これまでの住所データを「基本住所」「詳細住所」に分割する
- 郵便番号APIから取得できる値が「基本住所」それ以外が「詳細住所」
- イベント編集画面においては「詳細住所」も入力しないと、次に進めないようにする
- **既存の値はバッチ処理で一括分割する（バッチ処理を前提に進める）**
- **Event のみ** `event_address` を過去データ用に **EventAppSchema のみ**で保持（`default('')`）。**EventDbSchema には含めない**（`toFirestore` で新規保存時はフィールドを出力しない）。既存ドキュメントの `event_address` は上書きしない
- **Shop / Community** の単一住所フィールド（`shop_address` / `community_address`）は**スキーマから廃止**。バッチでレガシー列を**削除してもよいが、残置してもよい**。アプリの新規作成ではレガシー列を**書かない**。既存ドキュメントを更新保存してもレガシー列を**削除・空文字化しない**（放置）
- **Event** の `event_address` は二重表示フォールバック用のため**バッチでは削除しない**。新規作成では書かない。既存の更新保存でも**削除・空文字化しない**
- イベントページ等の表示は `fullAddress`（下記「Event の fullAddress」参照）

### Event の fullAddress（二重表示の検知）

分割バッチで分割不能だった場合、`event_address_base` に API 結果・`event_address_detail` に**元住所全体**が入り、`base` + `detail` 結合で**基本住所が二重**になり得る。

**方針**

- 基本は **base と detail を結合**した文字列を表示する
- 二重と判定でき、かつレガシー **`event_address` が残っている**場合は **`event_address` を表示**する（過去の単一文字列のほうが正しいため）

**二重判定（`common/src/utils/splitAddress.ts` と同一ロジック）**

1. **正規化:** 同ファイルの `normalizeAddressForComparison`。バッチ 0035・チェック 0035 の `lib/normalizeAddressForComparison.js` と同一。処理順は先頭末尾 trim → ハイフン類を半角ハイフンに統一（長音 U+30FC は対象外）→ 全角英数字 U+FF01〜U+FF5E を半角へ → Unicode 空白をすべて除去 → ゼロ幅文字 (U+200B〜U+200D, U+FEFF) を除去。`computeEventFullAddress` 内の二重判定はこの関数を使用する
2. **条件A:** 正規化後の `event_address_base` が、正規化後の `event_address_detail` の**先頭に含まれる**（`detail` が `base` で始まる）→ 二重とみなす
3. **条件B:** 日本の**都道府県名**の一覧を用意し、正規化後の `base` の先頭と `detail` の先頭が**同一の都道府県名**で始まる → 二重とみなす

**条件A または B を満たし、`event_address_detail` が空でない**とき、二重候補とする。レガシー `event_address` が非空ならそれを返し、無ければ結合結果を返す。

**Community / Shop:** 上記のような過去データの表示経路は想定しない。二重になるデータは**手作業で修正**する。

## 共通UI仕様（Event / Community / Shop 共通）

- 郵便番号入力 → PostcodeJP API で基本住所を取得 → `*_address_base` に自動入力（readonly）
- `*_address_detail` をユーザーが手入力
- **Event / Shop の各設定画面:** `*_address_detail` は必須。空の場合は次に進めない
- **Community:** 住所は必須ではない（任意）

## 用語定義

| 用語 | 説明 | 例 |
| :--- | :--- | :--- |
| 基本住所 | 郵便番号APIから取得できる住所（都道府県〜町域） | 東京都渋谷区神宮前 |
| 詳細住所 | ユーザーが手入力する番地・建物名等 | 1-2-3 ○○ビル 301号室 |

## スキーマ変更

フィールド名は `*_address_base` / `*_address_detail` とする。Firestore コンソールでアルファベット順に並べた際、`event_address_base`、`event_address_detail` が隣接し、住所関連の確認がしやすい。

| 対象 | フィールド | 制約 |
| :--- | :--- | :--- |
| **Event のみ** | `event_address` | 過去データ用（**DbSchema には含めない**）。アプリは `EventAppSchema` で `default('')` |
| **Shop / Community** | （単一住所フィールド） | **スキーマに持たない**（バッチ完了後は Firestore からも削除） |

## バッチ処理

### 対象コレクション

1. **partner_shops** — `shop_address` → `shop_address_base` + `shop_address_detail`
2. **communities** — `community_address` → `community_address_base` + `community_address_detail`
3. **events** — `event_address` → `event_address_base` + `event_address_detail`

### 実行順序

住所コピー元（Shop、Community）を先に分割するため、**partner_shops → communities → events** の順で実行する。

### 処理フロー

1. 対象コレクションの全ドキュメントを取得
2. 各ドキュメントの郵便番号で PostcodeJP API（`https://apis.postcode-jp.com/api/v6/postcodes/{postalCode}`）を呼び出し
3. 郵便番号が無い or APIがエラーの場合: そのドキュメントはスキップ（更新しない）。**Shop/Community** はレガシー単一フィールドのみのまま（手当ては別途）
4. それ以外の場合:
   - **`*_address_base`**: 郵便番号APIから取得した値（`allAddress`）に対し、アプリ（`base/src/composable/fetchLocation.ts`）と同一の `allAddress` 末尾除去を適用してから設定（事業所個別郵便番号の階数注記などを除去）
   - **`*_address_detail`**: API 結果と元の単一住所文字列で逆算して分割できた場合は基本住所以降を設定、分割できなかった場合は元住所をそのまま detail に入れる
5. 書き戻し後:
   - **partner_shops / communities:** レガシーフィールド **`shop_address` / `community_address` は削除してもよいが、残置してもよい**（後からバッチで削除可能。アプリは新規に書かず、既存更新でも触らない）
   - **events:** **`event_address` は削除しない**（二重表示フォールバック用。`fullAddress` のレガシー表示に利用）。`event_address_base` / `event_address_detail` を設定

### 分割の判定

- **比較用正規化:** 登録側の単一住所と PostcodeJP の `allAddress`（必要なら strip 後）の**両方**に、`splitAddress.ts` の `normalizeAddressForComparison` と同一の処理をかけ、正規化後の文字列で **登録側が API 基本住所で始まるか**を判定する
- **detail の切り出し:** 正規化後に一致する最短の接頭辞の直後から元文字列を `detail` とする（途中の空白の有無で文字数がずれても正規化に整合する）。フォールバックとして API 文字列の文字数で切る
- 元の単一住所が API の基本住所で始まる場合 → 分割可能。base に API 結果、detail に残り（空になる場合あり）
- 分割できない場合 → base に API 結果、detail に元の住所全体
- 郵便番号が無い or APIがエラーの場合: そのドキュメントは更新しない
- **events の表示:** バッチ前は `event_address` のみのドキュメントもあり得る → **`event_address_base` が無ければ `fullAddress` がレガシー `event_address` を返す**。バッチ後に base+detail と二重になる場合は上記の二重判定でレガシーを優先

### APIレート制限への配慮

- PostcodeJP API の呼び出し間隔を適切に制御する
- 処理結果のログを残す（成功 / 分割不可で detail に元住所全体 / 郵便番号なし or APIエラーでスキップの件数）

### ロールバック

- バッチ実行前に元データのバックアップを取得する
- Shop/Community でレガシーフィールドを削除した後の復元はバックアップから行う

### convertToDb の仕様

- **Event:** `event_address` を `convertToDb` で上書きしない。**EventDbSchema に `event_address` を含めない**ため、`toFirestore` の出力からは除外され、新規ドキュメントではフィールドが作られない。既存ドキュメントのレガシー `event_address` はアプリ保存で消さない（`merge` 未使用の `set` では注意）
- **Shop / Community:** 単一住所フィールドはスキーマにない。読み込みデータに残っていても `CommunityDbSchema` / `PartnerShopDbSchema` の parse で除外される。Firestore 上のレガシー列はバッチで削除してもよいが**残置可**。アプリ保存では削除・空文字化しない
- `*_address_base`、`*_address_detail` はそのまま保存する

## 実装順序

バッチ処理を前提とするため、以下の順序で進める。

### Phase 1: バッチ処理

1. バッチ処理の実装・実行（partner_shops → communities → events の順）
2. partner_shops / communities: 分割後、レガシー列は**削除してもよいが残置してもよい**
3. events: `event_address` は**残す**（二重表示フォールバック用）

### Phase 2: アプリ・スキーマ変更

3. `common`: Event は `EventDbSchema` から `event_address` を外し `convertToDb` で上書きしない・`fullAddress` は base 優先。Shop/Community は単一フィールドをスキーマから削除
4. `base`: EventBasicInfoCard の保存ロジック変更
5. `base`: EventShop は店舗選択時に住所をコピーしない（仕様どおり維持）
6. `base`: 住所表示コンポーネントの更新（Event / Community / Shop）
7. `admin`: 店舗編集・注文表示の更新
8. `admin`: events/create.vue の Shop → Event コピーを base/detail に変更
9. `admin`: community.vue の Shop → Community コピーを base/detail に変更
10. `user`: 住所表示箇所の更新
11. `functions`: メールテンプレート・ICS生成・eventCopy 等の更新
12. `manager`: 住所表示箇所の更新（CommunityList, ShopList, EventList）

**補足:** Event の `fullAddress` は `computeEventFullAddress` により、base 無し・結合・二重時のレガシー優先を切り替える。

## Firestore Security Rules

- `*_address_base`、`*_address_detail` に対する読み書き権限を、従来の住所まわりと同等に設定する
- バッチ処理は Admin SDK 経由のため Security Rules の影響なし
