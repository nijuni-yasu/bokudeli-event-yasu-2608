## 1. 概要・推奨方針

イベント申込時の事前アンケートを Shokujii 内で作成・回答・管理できるようにする。主催者が氏名・会社名・連絡先・参加目的などを収集し、イベント運営に使うことを目的とする。

初期リリースでは、一般ユーザー向けアプリのコミュニティ管理者と、ログイン済みの申込者を対象とする。フォームはコミュニティ単位で再利用でき、1イベントに1フォームを設定する。回答は **1イベント × 1ユーザーに1件** を推奨する。

現行の注文は料理1個ごとに作成されるため、「1注文につき1回答」では、同じ人が料理を複数注文した場合にアンケートが重複する。同行者全員の情報収集が必要な場合は、申込者と参加者を分ける設計が別途必要になる。

## 2. ねらい・成功指標

- 主催者が外部フォームと参加申込を照合する作業をなくす。
- 必須回答の欠落をサーバー側で防ぎ、申込者に紐づいた回答を取得する。
- 利用イベント数、フォーム表示から申込完了までの離脱率、主催者の一覧・CSV利用を測定する。事業上の数値目標は導入前の実績を見て決定し、既存案の「20%向上」「80%以上」は確定値として引き継がない。
- 機能の受入基準として、フォーム付きイベントの新規申込は全件で回答検証を通過することを求める。

## 3. 前提条件と MVP 範囲

| 項目 | 推奨案 |
| --- | --- |
| 作成・管理者 | 対象コミュニティの管理者。`user` のコミュニティ管理画面に設置 |
| 回答者 | ログイン済みの申込者本人 |
| フォーム再利用 | 同じコミュニティ内で作成・編集・複製・アーカイブ |
| イベント設定 | 1イベントに0または1フォーム |
| 回答タイミング | カートで、注文確定・Stripe 決済開始の前 |
| 回答単位 | 1イベント × 1ユーザーに1件。追加注文では有効な既存回答を再利用 |
| 項目 | 1行テキスト、複数行テキスト、メール、電話、日付、複数選択、単一選択、ドロップダウン |
| 項目設定 | ラベル、説明、必須・任意、選択肢、並べ替え、プレビュー |
| 主催者の回答確認 | イベント別一覧・詳細・CSV |
| 本人の回答確認・編集 | 同じイベントの再注文フロー内でのみ、過去の回答を初期表示して編集可能。本人向け一覧・詳細・単独編集画面は設けない |
| 初期対象 | 通常のコミュニティイベント。エンタープライズでの提供は後続候補 |
| 後続候補 | ファイル添付、条件分岐、匿名回答、単独フォーム、事後アンケート、回答グラフ、通知、公開テンプレート集 |

上限のたたき台は、1フォーム20項目、選択肢は1項目30件、短文200文字、長文2,000文字とする。固定上限で開始し、主催者が自由な正規表現を設定する機能は含めない。電話番号は文字列で扱い、日付回答はタイムゾーン変換しない日付文字列とする。具体的な許容書式は実装仕様で定義する。

## 4. 画面・操作仕様

```text
主催者: コミュニティ管理 → フォーム一覧 → 作成・編集・プレビュー
                             ↓
         イベントへフォームを設定（下書き、予約申請中、申請中、参加受付中）

申込者（そのイベントにフォームがある）:
  カートの当該イベント
    「事前アンケートに回答する」
      → そのイベントの回答画面（過去の回答または決済中断時の試行を初期表示）
      → 末尾の「お支払いに進む」または「注文を確定する」
      → 決済／注文確定

申込者（そのイベントにフォームがない）:
  カートの当該イベントの「お支払いに進む」または「注文を確定する」
    → 現行どおり決済／注文確定

主催者: イベント管理 → 回答一覧 → 回答詳細／CSV
```

- ボタンの置換はイベントごと。カートに複数イベントがあるとき、フォームがあるイベントだけ「事前アンケートに回答する」になる。フォームがないイベントは現行の「お支払いに進む」（Stripe）または「注文を確定する」（それ以外）のまま、そのイベントの注文へ進む。
- 現行の「お支払いに進む」は確認ダイアログなしで Checkout を開始する。「注文を確定する」は確認ダイアログのあと `confirmOrder` を呼ぶ。回答画面の末尾ボタンも、この現行の進み方を維持する。
- 末尾ボタンは、表示中の回答をサーバーへ保存し、保存が成功したときだけそのイベントの決済または注文確定へ進む。画面上の未保存の編集では注文へ進まない。
- フォーム未設定のイベントは、現在の注文フローを維持する。
- イベントページで事前アンケートがあることを案内する。回答の入力はカートの当該イベントのボタンから開く回答画面で行う。
- マイページ・注文履歴・申込内容確認に、本人の回答一覧や回答閲覧・編集への導線は追加しない。過去の回答は同じイベントの再注文フロー内でのみ表示する。
- 回答画面には、情報を受け取るコミュニティ名と主催者が設定した利用目的を表示する。
- 氏名・メール等の入力補助を行う場合も本人が確認して送信する。アカウントの非公開情報を主催者へ自動開示しない。
- 必須項目は未入力・空白だけの回答を認めない。選択式は実在する選択肢のみ受け付ける。
- 任意項目は未回答でも進める。全項目が任意でも、末尾の「お支払いに進む」または「注文を確定する」を押して保存に成功したことを、有効な回答として残す。
- エラーは項目単位で表示する。入力済みの値を残し、再送できるようにする。
- 回答の取得と書き込みは、対象イベントに本人の `in_cart` の注文があるときだけ許可する。`processing` 中は取得も編集もしない。過去の確定注文があるだけでは許可しない。
- 初期表示は、未確定の試行が残っていて決済中断から戻ったときはその試行、それ以外は主催者に公開している確定済み回答とする。入力途中の自動保存・別端末同期は MVP に含めない。
- 回答一覧は参加確定済みを初期表示とする。未決済の回答を主催者へ公開しない。全注文取消済みは別フィルターで確認できる案とする。
- CSV は回答者1人につき1行とする。アカウント側の列は `ユーザーID` と `表示名`。続けて参加状態、回答日時、更新日時を出す。設問の列ヘッダは `設問:{確定時の設問ラベル}` とし、セルの値は確定時にコピーした選択肢ラベルまたは自由入力とする。複数選択は選択肢ラベルを「、」で連結して1セルに入れ、既存の引用符・改行処理に乗せる。同じ設問ラベルが衝突するときは設問IDをヘッダに足して列を分ける。

## 5. 変更・取消の扱い

### 5.1 フォーム定義

- コミュニティのフォームをイベントに設定するとき、設問と表示文言のコピーをイベント用に保存する。元フォームの編集・アーカイブは設定済みイベントに自動反映しない。
- イベントにコピーした設問は、中止（`event_canceled`）以外の保存値でコミュニティ管理者が変更できる。対象は下書き（`in_draft`）、予約申請中（`applying_reservation`）、申請中（`applying_to_admin`）、参加受付中（`accepting_order`。算出ステータスが注文締切・満員・終了でも含む）である。他のイベント項目は下書き以外では編集できないが、設問の編集はこの範囲でできる。
- 変更しても、すでに確定した回答の本文・設問ラベル・選択肢ラベルは書き換えない。主催者の一覧と CSV は、その回答を確定した時点の文言で表示する。
- 新しい申込と追加注文は、変更後の最新の設問で検証する。必須設問を足した場合、すでに参加確定している人へ回答画面の外から回答を要求しない。次に同じイベントを注文するとき、回答画面で最新設問の不足分を入力する。
- 設問を変更するときは、確定済み回答を最新の設問文へ読み替えない。次を守る。
  - 設問IDと選択肢IDは不変にする。IDを振り直したり、別の設問へ再利用したりしない。
  - 同じ設問IDの項目タイプは変えない。タイプを変えるときは、古い設問IDを新規回答では出さず、新しい設問IDを足す。
  - 確定時に、その時点の設問ラベル・説明・選択肢ラベル・定義バージョンを回答へコピーする。
  - 選択肢を「新規では選べなく」しても、確定済み回答が参照する選択肢IDとラベルは残す。
  - 設問を「新規では出さなく」しても、確定済み回答のその設問は一覧と CSV に残す。
  - 進行中の Checkout は、開始時に検証した定義バージョンの試行を確定する。受付中の設問変更で、その決済を拒否したり、新しい必須設問で上書きしたりしない。
- 未確定の注文試行が最新の定義バージョンと異なるときは、注文確定と Checkout 開始を拒否し、回答画面で最新設問を出し直す。既に確定した回答は、定義が新しくなっても無効にしない。
- 受付開始後に、フォームが無かったイベントへフォームを追加できる。追加後の新しい注文は回答を必要とする。追加前に参加確定した人へ、注文フローの外から回答を要求しない。
- イベントコピー・繰り返し作成では、コピー時点の設問を新しいイベントへコピーできる。回答、回答時点のラベル、回答日時はコピーしない。

### 5.2 回答・参加状態

- 本人による過去の回答の確認・修正は、同じイベントの再注文フロー内に限定する。注文締切前かつイベントが有効であっても、回答だけを閲覧・編集する機能は設けない。
- 再注文時の初期表示は、未確定の試行が残っていて決済中断から戻ったときはその試行、それ以外は確定済み回答とする。設問IDが最新定義にもある値は初期値にし、最新定義だけで検証する。変更せず進むことも、その場で編集してから進むこともできる。
- 主催者が本人の回答を書き換える機能は含めない。
- 料理の追加注文で、設問定義が確定時と同じバージョンなら、確定済み回答を再利用する。定義が新しいときは、最新設問で不足を埋めてから確定する。全取消後の再申込でも、保存期間内かつ同じイベントであれば、回答画面で内容を確認して再利用する。
- 更新反映時点の推奨案: 再注文で編集した内容は、その再注文の確定時に主催者向けの最新回答へ反映する。再注文の途中離脱・決済失敗では、前回の確定済み回答を維持する。決済前の一時保存は確定済み回答と区別する。
- 回答送信と参加確定は別の状態として扱う。申込失敗・決済待ち・決済失敗で「参加者の回答」に混ぜない。
- 一部注文が取消済みでも、有効な確定注文が1件以上残っていれば参加確定として扱う。
- 全取消後も回答を即時消去せず、取消済みとして区別する案とする。保持期間と退会・削除依頼時の削除方法は、公開前に運用方針を決める。

## 6. 技術設計案

### 6.1 保存先

コレクション名・フィールド名は実装設計時に確定する。責務は次のように分ける。

| 保存先案 | 内容 |
| --- | --- |
| `communities/{communityId}/forms/{formId}` | 再利用するフォーム定義。名前、説明、利用目的、設問、アーカイブ状態、作成・更新者／日時 |
| `communities/{communityId}/events/{eventId}/form_configs/current` | イベント用の設問コピー、元フォームID、定義バージョン、作成・更新日時。独立した権限で更新を制御 |
| `communities/{communityId}/events/{eventId}/form_responses/{userId}` | 確定済みの最新回答、確定時の定義バージョン、確定時の設問ラベルと選択肢ラベル、回答・更新日時、競合検知用リビジョン、参加確定記録。注文試行中の回答は別管理とする案 |

- 設問と選択肢に不変のIDを持たせ、配列の位置やラベルを回答キーにしない。
- 回答値は項目タイプごとの文字列・選択肢ID・選択肢ID配列等で型付けする。`any` / `z.any()` は使用しない。
- 主催者には注文確定済みの最新回答を表示する。本人向けの一覧・詳細画面、および回答の編集履歴を閲覧・CSV出力する機能は含めない。
- 注文試行中の回答を保存する場合は、注文試行・Checkout に紐づけて確定済み回答と区別する。再注文確定時の反映順序はサーバー管理のリビジョンで制御し、遅れて届いた古い試行で新しい確定回答を上書きしない。物理的な保存先は実装設計時に確定する。
- 送信するリビジョンと保存済みリビジョンが異なるときは、別タブの古い回答で上書きせず、再読み込みを案内する。
- フォーム設定が存在しないイベントは「フォームなし」とする。ただし権限エラー・読み込み失敗を「フォームなし」と解釈しない。
- 回答を公開される `Event`・イベント `members`・`member_orders` に埋め込まない。

### 6.2 サーバー側の検証と注文接続

- フォーム管理・イベントへの設定・回答の書き込みは認証付き Callable 経由とし、サーバー側で権限・上限・型を検証する。
- 本人向けの回答取得・書き込みは注文フロー用の Callable に限定し、認証UIDを使用する。対象イベントに本人の `in_cart` の注文があること、注文受付条件、最新の設問バージョンを確認する。`processing` 中、および過去の確定注文があるだけ、では取得・編集を許可しない。汎用の本人向け回答一覧・詳細取得・単独編集APIは設けない。
- `confirmOrder` と `createStripeCheckoutSession` の両方で、最新の設問定義に対する有効な保存済み回答があることを検証する。UI のボタン無効化だけで必須回答を保証しない。
- フォーム定義があるのに回答が欠けている、未確定の試行が最新の定義バージョンと異なる、未知の設問／選択肢、必須漏れ、型不一致、上限超過の場合は、新しい注文確定と Checkout 開始を拒否する。Webhook は、そのセッションに紐づく検証済みバージョンの試行を確定し、その後の設問変更を理由に拒否しない。
- Stripe を使わない注文では、回答検証・確定回答の更新・参加確定記録と注文の `ordered` 更新を同じトランザクションで整合させる。
- Stripe を使う場合は、有効な回答を注文試行用に保存してから Checkout を開始する。セッションと検証済みの設問・回答バージョンをサーバー管理の識別情報で関連づけ、Webhook でその試行の注文確定と回答の反映を行う。回答本文は Stripe metadata に送らない。
- 外部決済APIと Firestore を単一トランザクションで扱わない。決済API呼び出しは再実行され得る Firestore トランザクション関数の外で行う。[Firebase のトランザクション仕様](https://firebase.google.com/docs/firestore/manage-data/transactions)
- 決済開始失敗・離脱では回答が残っていても参加確定扱いにしない。Webhook の重複・遅延・順序逆転によって、確定済みを未確定に戻さない。
- 稼働中に機能を公開する場合、公開前に作成済みの Checkout とフォームなしイベントを継続処理できることを確認する。
- 回答を参加確定済みにする処理は、失敗を握りつぶす通知等の後処理だけに置かない。注文確定と同じ書き込み単位、または確実な再試行・照合を備える。

### 6.3 権限・再利用・個人情報

- フォームの作成・変更は `communities/{communityId}/members/{uid}.roles` の `manager` で認可する。一般コミュニティメンバーには許可しない。
- 回答の取得は対象コミュニティ管理者と、注文フロー中の本人に限定する。本人には Firestore の回答ドキュメントを常時直接読む権限を付与せず、注文フロー用 Callable から対象イベントの回答のみを返す。管理者への公開は参加確定後とする。運営のアクセスは既存のサポート権限と運用範囲を確認して明示的に定義する。
- 他コミュニティの管理者、飲食店、他の参加者、未認証ユーザーは回答を取得できない。エンタープライズの利用は API でも明示的に対象外とし、UI 非表示だけに依存しない。
- クライアントからの回答直接書き込みは禁止する。管理用一覧・CSV取得を Callable にする場合も、毎回コミュニティ管理者権限を検証する。
- 公開用の設問取得と非公開の回答取得を分ける。フォーム定義の下書き一覧も公開しない。
- Rules はドキュメント内の一部フィールドだけを非公開にできないため、回答の分離が必要。[Firebase 公式ドキュメント](https://firebase.google.com/docs/firestore/security/rules-fields)
- スキーマは `common/src/schemas` / `common/src/apis`、DB 操作は既存方針どおり store と `withConverter` を使用する。保存日時は `TimestampSchema`、アプリ内日時は `EpochMillisSchema` とする。
- 新規データ中心とし、既存データの一括書き換えを必須にしない。必要になった場合の backfill は `bokudeli-event-batch` 側で扱う。
- 既存の CSV の引用符・改行処理と UTF-8 BOM 付きダウンロードを再利用する。自由入力と設問ラベルに対して数式として解釈される値を無害化する処理を追加する。
- 回答本文をログ・通知・公開プロフィールへ転記しない。保持期限を過ぎた回答と未決済の回答を削除する運用・実行手段を、公開前に決定する。

## 7. 実装順と受入条件

### 7.1 実装順

1. MVP 範囲、回答単位、再注文時の回答更新の反映時点・保持期間を確定する。中止以外での設問変更と、確定済み回答を回答時点の文言のまま残すことは、2026-10-01 のユーザー指定で確定している。
2. スキーマ、store、権限、イベント用設問コピーと回答検証を整備する。
3. 作成・選択・回答 UI と、注文確定／Stripe 決済開始／Webhook を接続する。
4. 回答一覧・詳細・CSVと、回答データの削除運用を整備する。
5. 権限・注文経路・失敗／再試行を通して検証し、既存仕様書を置き換える。

### 7.2 受入条件

- [ ] コミュニティ管理者が8種類の項目を含むフォームを作成・複製し、下書きイベントへ設定できる。
- [ ] フォーム未設定の既存イベントは、追加操作なしで従来どおり注文できる。
- [ ] 必須未回答や不正回答は、通常の注文確定・Stripe 決済開始の直接API呼び出しでも拒否される。
- [ ] 本人の回答一覧・詳細・単独編集画面とその導線が存在しない。
- [ ] 同じイベントの再注文フローでのみ、本人の過去の回答を表示して編集できる。過去の確定注文だけでは取得・編集APIを利用できない。
- [ ] 対象管理者以外は回答の一覧・CSVを取得できず、注文フロー中の本人以外の参加者は個別の回答本文も取得できない。
- [ ] 同一イベントで複数料理・追加注文をしても、回答は1ユーザー1件となる。
- [ ] フォームがあるイベントでは、カートの当該イベントのボタンが「事前アンケートに回答する」になり、回答画面の末尾からそのイベントだけ決済または注文確定へ進む。フォームがないイベントは現行のボタンのままである。
- [ ] 決済中断からの復帰では未確定の試行を初期表示し、それ以外の再注文では確定済み回答を初期表示する。`processing` 中と、カートが無い状態では回答を取得できない。
- [ ] CSV の設問セルは確定時のラベルであり、複数選択は「、」で1セルに入る。`ユーザーID` と `表示名` はアカウント情報である。
- [ ] 下書き・予約申請中・申請中・参加受付中に設問の追加・ラベル変更・選択肢の新規非表示ができる。中止後は変更できない。確定済み回答の文言は変わらない。変更後の新しい注文は最新設問で検証される。進行中の Checkout は開始時のバージョンで確定する。
- [ ] 元フォームの編集・アーカイブやイベントコピーで、設定済みイベントの確定済み回答が変化しない。
- [ ] 決済中断・失敗・再試行・遅延成功・重複Webhookで、参加状態と回答公開範囲が破綻しない。
- [ ] 再注文の確定時に編集後の回答を反映し、再注文の途中離脱・決済失敗では前回の確定済み回答を維持する（反映時点の推奨案を採用した場合）。
- [ ] 一部取消・全取消・再申込と回答の修正が、定めたルールで処理される。
- [ ] CSVが1回答者1行で出力され、日本語・改行・引用符・複数選択・数式に見える文字列を正しく扱う。
- [ ] 未決済回答・イベント終了後の回答・退会／削除依頼の保持と削除手段が決まっている。
