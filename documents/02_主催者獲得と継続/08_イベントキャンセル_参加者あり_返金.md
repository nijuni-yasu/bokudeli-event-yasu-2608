主催者 UI からの「参加者あり・一括返金キャンセル」は、次が未確定のため **現時点では product スコープ外**とする。

## 1. 概要（Phase A）

### 1.1 機能の目的

**ordered 注文が存在するイベント** を、サーバー側で一括して中止し、必要に応じて Stripe 返金・enterprise 補助戻し・関係者通知を行う **共通処理（コア）** を提供する。最小催行の自動中止など、複数の起動元から同じ終端状態を保証する。

### 1.2 Phase A の主要な機能

- イベントを `event_canceled` に更新（`cancel_reason` / `canceled_at` / `canceled_by`）
- 対象イベントの `status === 'ordered'` な **EventMemberOrder** を一括 `canceled`
- `event_payment` に応じた Stripe 返金（**stripes** ドキュメント経由。`cancelOrders` と共通化）
- `enterprise_subsidy` の **monthly_usage 戻し**
- 注文キャンセル副作用（`recalcEventMembers`・チャット等。`applyOrderCanceledSideEffects`）
- 飲食店向け・参加者向けメール（テンプレートは起動元で分岐可）
- エンプラ: 自動中止時は監査ログ `event_auto_cancel`（`04_詳細_監査ログ.md`）

### 1.3 Phase A で **含めない** もの

- 主催者向け管理画面からの Callable 公開（**`cancelEvent` は Phase 1 の契約のまま**）
- Phase B の UI（§4）

### 1.4 対象ユーザー（Phase A）

- **システム**（Scheduled / 最小催行チェック）
- **参加者**: 返金・通知の受益者
- **飲食店**: 中止通知の受信者

## 5. 技術仕様・データ構造設計

### 5.1 設計方針

- Phase 1 で導入した `event_status` / `canceled_at` / `canceled_by` をそのまま使用
- 返金の正本は **stripes**（`refunds[]`）。`member_orders` は `status: 'canceled'` と `canceled_at`
- 処理は **Admin SDK のみ**（Phase A ではクライアント Callable を export しない）

### 5.2 Firestore スキーマ

#### イベントドキュメント（変更なし）

```typescript
event_status: {
  value: RawEventStatusType   // 'event_canceled'
  shop_comment?: string
  cancel_reason?: string      // 中止理由（自動中止は定型文言）
}
canceled_at?: Timestamp
canceled_by?: string          // 主催者 uid または "system"
```

#### EventMemberOrder / stripes

パス: `/communities/{communityId}/events/{eventId}/members/{uid}/member_orders/{orderId}`  
返金セッション: `/communities/{communityId}/events/{eventId}/stripes/{stripeId}`

```typescript
// member_orders（既存）
status: 'canceled'
canceled_at?: Timestamp
stripe_id?: string            // user_advance 等

// stripes（既存 — cancelOrders と同様）
refunds: Array<{ refund_id: string; amount: number; ... }>
```

### 5.3 Firestore セキュリティルール

Phase A コアは Admin SDK のみ。ルール追加は不要。Phase B で Callable を公開する場合も、本体は Admin SDK 経由とする。

### 5.4 Functions 設計

#### 5.4.1 イベント一括中止コア（Phase A・正本）

**配置（予定）**: `functions/default/src/` 配下の内部モジュール（例: `cancelEventBulkCore.ts`）。**Cloud Functions として export しない**（Scheduled・単体テスト・将来 Phase B から import）。

**入力（例）**:

| フィールド | 説明 |
|:--|:--|
| `community_id`, `event_id` | 対象イベント |
| `cancel_reason` | `event_status.cancel_reason` に保存 |
| `canceled_by` | `"system"` または将来用 uid |
| `initiator` | `'minimum_participants' \| 'organizer_manual' \| 'support'`（ログ・監査用。Firestore 必須フィールドにはしない） |

**事前条件**:

1. イベントが存在し、`is_deleted === false`
2. `calculatedEventStatus` が `applying_reservation` または `accepting_order`（`finished` / `order_closed` 等は拒否）
3. 既に `event_status.value === 'event_canceled'` の場合は **冪等** — 成功相当で return（二重返金・二重メールを防ぐ具体条件は実装時にテストで固定）

**人数・注文の判定（中止するかどうかは呼び出し元の責務）**:

- 最小催行: 呼び出し前に `event_num_members`（または `recalcEventMembers` 後の ordered ユニーク人数）と閾値を比較
- コア自体は「中止せよ」と指示されたら実行する

**処理フロー**:

1. （推奨）`recalcEventMembers` で `event_num_members` を ordered ベースに同期
2. トランザクションで Event を `event_canceled` に更新（`cancel_reason`, `canceled_at`, `canceled_by`）
3. 対象イベントの `status === 'ordered'` な **全 member_orders** を `canceled`（ユーザー単位の `cancelOrders` と同等のバリデーションを **一括用** に展開）
4. `event_payment === 'user_advance'`: **stripe_id 単位**で Stripe 返金（`cancelOrders` と共通化。idempotency key 必須）
5. `enterprise_subsidy`: `revertEnterpriseSubsidyUsageOnCancel` 等（`cancelOrders` と共通化）
6. `applyOrderCanceledSideEffects`（members・チャット）
7. SendGrid: 飲食店向け中止メール（Phase 1 `cancelEvent` テンプレート流用可）
8. ordered があった場合: **参加者向け返金通知メール**（新規 SendGrid テンプレ。**PF・エンタープライズとも送信**。`enterpriseMail` のイベント系 skip 対象に **含めない**）
9. エンプラかつ `initiator === 'minimum_participants'`: `writeAuditLog` — `action: 'event_auto_cancel'`, `user_id: 'system'`, `details: { order_count, min_required }`

**支払方式別（`cancelOrders` と同じ分岐）**:

| `event_payment` | 一括中止時 |
|:--|:--|
| `user_advance` | `ordered` を `canceled`。`stripe_id` あり → Stripe 返金（stripes） |
| `enterprise_subsidy` | `ordered` を `canceled` + `monthly_usage` 戻し + 監査（一括分） |
| `community_bill` / `user_on_day` | **`ordered` を `canceled` のみ**（Stripe 返金なし。`cancelOrders` と同様） |

**`in_cart` の扱い**:

- 一括中止時も **`in_cart` は更新しない**（`ordered` のみ `canceled` + Event `event_canceled`）
- 新規注文・決済は `event_canceled` ガードで不可。既存の期限切れ `in_cart` と同様にドキュメントは残りうる

#### 5.4.2 Callable `cancelEvent`（Phase 1 — 変更しない）

- 引き続き **参加者なし・ordered なしのみ**（`hasOrderedOrders` / members チェック）
- Phase B まで **参加者ありは拒否**。UI はサポート案内のまま

#### 5.4.3 Callable `cancelEvent` 拡張（Phase B — 保留）

Phase B 実装時: 主催者認可 → Phase A コアを `initiator: 'organizer_manual'`, `canceled_by: uid` で呼ぶ。**Phase A リリース時点では実装しない。**

#### 5.4.4 返金処理の失敗時

- `cancelOrders` と同様: 注文の `canceled` 更新後に Stripe 失敗があり得る
- Runbook: `12_cancelOrders_返金失敗時_Runbook.md`
- 自動リトライは Phase C（§6.3）

### 5.5 起動元別処理フロー

#### 5.5.1 最小催行・人数不足（09 連携）

1. Scheduled が §5.5.1 の条件でイベントを検出（`judgment_evaluated_at` 未設定）
2. 人数 &lt; `count` ならコア呼び出し。継続なら中止しない
3. **いずれも** `judgment_evaluated_at` をセット（09 モデル A）
4. `cancel_reason` / `canceled_by: "system"` / `initiator: 'minimum_participants'`

#### 5.5.2 主催者手動（Phase B — 未実装）

§4 の UI → 拡張 `cancelEvent` → コア（`initiator: 'organizer_manual'`）
