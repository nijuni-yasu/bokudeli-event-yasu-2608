# イベントキャンセルと返金

## 1. 概要
### 1.1 機能の目的
主催者がイベントをキャンセルした際に、参加者への返金処理と関係者への通知を自動化し、円滑なイベントキャンセルプロセスを提供する。

### 1.2 主要な機能
- 主催者によるイベントキャンセル申請
- イベントキャンセル理由の入力（50文字以上必須）
- イベントキャンセル確定前の確認ダイアログ
- 参加者への自動返金処理
- 飲食店へのメール・電話通知
- イベントステータスの自動更新

### 1.3 対象ユーザー
- **主催者**: イベントをキャンセルする権限を持つユーザー
- **参加者**: 事前決済で参加申込をしたユーザー
- **飲食店**: イベントに関連する店舗

### 1.4 前提
- Phase 1（参加者なしキャンセル）が実装済みであること
- 参考: `documents/02_主催者獲得と継続/08_イベントキャンセル_参加者なし.md`

## 2. ねらい
### 2.1 ビジネス目標
- イベントキャンセル時の運営負荷を軽減
- 参加者への返金処理を自動化し、信頼性向上
- 飲食店への迅速な通知による関係性維持

### 2.2 ユーザー価値
- 主催者: イベントキャンセルの手続き簡素化
- 参加者: 確実で迅速な返金処理
- 飲食店: 早期の情報共有による対応準備

### 2.3 成功指標（KPI）
- イベントキャンセル処理の完了率: 95%以上
- 返金処理の完了率: 100%
- 飲食店通知の到達率: 100%

## 3. 前提条件
### 3.1 技術的前提条件
- イベント管理システムが稼働していること
- 決済システム（Stripe）との連携が確立されていること
- メール送信機能（SendGrid）が利用可能であること

### 3.2 ビジネス的前提条件
- イベント注文期限の前日までにキャンセル申請を行うこと
- 主催者がイベントキャンセルの権限を持っていること
- 参加者の事前決済が完了していること

### 3.3 依存関係
- イベント管理機能
- 決済処理機能（Stripe）
- メール通知機能（SendGrid）
- ユーザー認証機能

  - テキストエリア形式
  - 最小50文字、最大1000文字

  - キャンセル理由が50文字未満の場合は無効化

  - モーダル形式

  - 「はい」ボタン（赤系）
  - 「いいえ」ボタン（グレー系）

## 5. 技術仕様・データ構造設計

### 5.1 設計方針
- Phase 1（参加者なしキャンセル）で導入した `event_status` のデータ構造をそのまま使用する
- 新規フィールドの追加は最小限に抑える
- 返金の記録は注文（orders）側で管理する（イベント側に集計値を持たない）

### 5.2 Firestore スキーマ

#### イベントドキュメント（変更なし）
Phase 1 で追加済みのデータ構造をそのまま使用する。

```typescript
// event_status 内
event_status: {
  value: RawEventStatusType   // 'event_canceled' を含む
  shop_comment?: string
  cancel_reason?: string      // キャンセル理由 (50-1000文字)
}

// トップレベル（updated_at / updated_by と同列）
canceled_at?: Timestamp       // キャンセル日時
canceled_by?: string          // キャンセル実行者の userId
```

#### 注文ドキュメント（既存フィールドで対応）
`/communities/{communityId}/events/{eventId}/orders/{orderId}`

イベントキャンセルによる注文キャンセル・返金は、既存フィールドで記録する:

```typescript
// 既存フィールド（変更不要）
status: 'canceled'           // 既存の値を使用
canceled_at?: Timestamp      // キャンセル日時（既存）
payment_intent?: string      // Stripe PaymentIntent ID（既存）
refund_id?: string           // Stripe Refund ID（既存）— 存在すれば返金済み
```

### 5.3 Firestore セキュリティルール
キャンセル処理は Callable Function 経由で Admin SDK を使用するため、セキュリティルールの追加変更は不要。

### 5.4 Functions 設計

#### 5.4.1 Callable Function: `cancelEvent`（Phase 1 の拡張）
Phase 1 では参加者なしのみ対応していた `cancelEvent` を拡張し、参加者ありの場合も処理する。

- **引数**: `{ communityId: string, eventId: string, cancelReason: string }`
- **戻り値**: `{ success: boolean, event_id: string }`
- **認証**: イベント主催者のみ

**処理フロー:**
1. 認証チェック（呼び出しユーザーが members に含まれるか）
2. ステータスチェック（`applying_reservation` or `accepting_order` であること）
3. イベントドキュメント更新
   - `event_status.value` → `'event_canceled'`
   - `event_status.cancel_reason` → 入力されたキャンセル理由
   - `canceled_at` → 現在時刻
   - `canceled_by` → 呼び出しユーザーの userId
4. 参加者がいる場合:
   - 全注文の `status` → `'canceled'`、`canceled_at` を記録
   - 各注文の `payment_intent` に対して Stripe で返金処理を実行
   - 返金成功時に `refund_id` を記録
5. SendGrid で飲食店に予約キャンセルメール送信
6. 参加者がいる場合: SendGrid で参加者に返金通知メール送信

#### 5.4.2 返金処理の失敗時
- Callable Function 内で返金が失敗した注文はログに記録
- 運用でリトライ対応（Phase 1 では自動リトライは実装しない）

### 5.5 処理フロー
1. 主催者がイベント管理画面で「イベントをキャンセルする」を押下
2. キャンセル理由を50文字以上で入力
3. 「イベントキャンセルを確定する」を押下
4. 確認ダイアログが表示され、「はい」で確定
5. Callable Function `cancelEvent` を呼び出し
6. イベントドキュメントを更新（`event_status.value = 'event_canceled'`）
7. 参加者の注文ステータスを `canceled` に更新
8. 事前決済参加者への Stripe 返金処理を実行、`refund_id` を記録
9. 飲食店へのメール通知を送信
10. 参加者への返金通知メールを送信

## 7. 注意事項
### 7.1 既存システムへの影響
- **イベント管理**: Phase 1 で追加済みの `event_canceled` ステータスを使用
- **注文管理**: 既存の `canceled` ステータスと `refund_id` フィールドを使用（新規フィールド不要）
- **決済システム**: Stripe Refund API との連携が必要

### 7.2 セキュリティ考慮事項
- **認証**: 主催者のみがイベントキャンセルを実行可能
- **権限チェック**: イベント主催者かどうかの厳密な確認
- **入力値検証**: キャンセル理由の文字数制限とサニタイゼーション
- **決済セキュリティ**: 返金処理は Callable Function（サーバーサイド）で実行

### 7.3 運用考慮事項
- **ログ記録**: イベントキャンセルの全プロセスを詳細にログ記録
- **エラー監視**: 返金処理失敗時の自動アラート
- **データ整合性**: イベントキャンセル後のデータ整合性チェック
