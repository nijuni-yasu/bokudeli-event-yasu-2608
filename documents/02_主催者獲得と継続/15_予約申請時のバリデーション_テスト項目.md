# 予約申請時のバリデーション（テスト項目）

本書は `15_予約申請時のバリデーション.md` に基づく機能の、テスト観点と実施手順をまとめたものである。実装の正本は `common/src/utils/validateReservationRequest.ts`、画面の起点は `base/src/components/EventEdit.vue` の `submitReservation`、メッセージ変換は `base/src/utils/reservationRequestMessages.ts` と `base/src/locales/messages/ja.ts` の `reservation_request_reason.*` である。

---

## 1. スコープとテストの種類

| 種類 | 目的 | 主な実施者 |
|------|------|------------|
| 単体・ユニット | 理由コードと境界値の網羅 | 開発者、CI |
| 手動・探索 | ウィザードと Firestore・店一覧ロードの整合 | QA、開発者 |

本書の「結果」列は、単体テストでは `validateReservationRequest` の戻り値、手動では画面挙動とステータス遷移を指す。

---

## 2. 前提条件（手動テスト共通）

1. コミュニティに **manager** 権限を持つアカウントでログインする。
2. コミュニティが承認済みであること（未承認時は既存のダイアログで遷移が止まる）。
3. イベントが **in_draft** であること。
4. イベント編集ウィザードを **Step 5** まで進め、下書きが Firestore に存在する状態にする（新規は Step 3 の仮保存経由など）。
5. **郵便番号**から緯度経度が取得できること（`location` が null だと予約申請前にブロックされる）。
6. **店舗一覧**が取得完了していること（`partnerShopListStore.totalCount` が null の間は保存・申請でブロックされ得る）。
7. **ユーザープロフィール**と **personalInformation** がストアに載っていること（null の間は予約申請で別メッセージとなり、集約バリデーションまで到達しない）。

## 5. 手動テスト項目（イベント編集ウィザード）

### 5.1 基本手順

1. 管理画面から対象コミュニティのイベント編集を開く。
2. 上記「前提条件」を満たす。
3. Step 5 で「予約申請」を実行する（確認ダイアログがあれば承認する）。
4. 結果を「結果・期待」列で判定する。

### 5.2 チェックリスト

| ID | 観点 | 操作・条件 | 結果・期待 |
|----|------|------------|------------|
| M01 | 正常系 | 仕様どおり入力済み、店一覧ロード済、メニュー1件以上選択可能 | `applying_reservation` へ遷移し、成功通知が出る |
| M02 | 開催過去 | 開始日時を実行時点より過去に設定してから申請 | 予約用ダイアログにリスト表示。ステータスは in_draft のまま。該当文言は event_start_past 相当 |
| M03 | リードタイム | 開始日時を「JST 当日 0:00 から EVENT_RESERVATION_LEAD_TIME_DAYS 日後の 0:00」未満に設定して申請 | event_start_lead_time 相当の文言 |
| M04 | 日付ピッカー | Step 1 で開催日の選択肢 | `minEventStartDate` より前の日付が選べない、または許可されていないこと |
| M05 | 営業時間外 | 選択店の `shop_time` 外の開始時刻で申請 | shop_not_open 相当の文言 |
| M06 | 店舗不明 | Firestore 上に店 ID は残るが一覧に該当店がない状態を再現できる場合 | shop_not_found 相当。再現困難ならスキップ可 |
| M17 | 店未承認 | イベントに結びつく店が `is_approved === false` である状態で申請を試みることができる環境のみ | shop_not_approved 文言相当。単体では店舗系はこのコードのみとなる |
| M18 | 閉店フラグ | 店ドキュメントの `is_open` が false で `is_approved` は true | shop_closed 文言相当 |
| M07 | 配達圏外 | 郵便番号や位置を変え、配達対象外にしつつ一覧上は店が選べるか否かはデータ次第。検証関数上は shop_not_in_delivery_area | 申請時に該当文言、または保存段階で配達不可メッセージで止まることを仕様として記録 |
| M08 | メニュー0件 | 注文可能かつ選択済みが1件もない状態（全外しまたは全売り切れ相当） | no_orderable_menu_selected 相当 |
| M09 | 申請者氏名 | プロフィールのユーザー名を空にできる環境なら空にして申請 | applicant_user_name_missing 相当 |
| M10 | 申請者画像 | 画像 URL が空になる状態で申請 | applicant_user_image_missing 相当 |
| M11 | 申請者メール | personal のメールを空にし、Auth にもメールが無いテストユーザで申請 | applicant_email_missing 相当 |
| M12 | 主催者不足 | Step 5 手前で主催者連絡先のいずれかを空にして申請 | 対応する organizer_*_missing 相当 |
| M13 | 複数理由 | 意図的に過去日付かつメニュー0件など複数違反 | ダイアログに複数行。順序が仕様のソート順と整合するか目視 |
| M14 | データ未準備 | 店一覧ロード中や personalInformation が未ロードのタイミングで申請 | 集約バリデーション前にブロックされ、読み込み系メッセージが出る |
| M15 | 下書き保持 | いずれかの違反で申請失敗後、画面を再読み込みまたは Step を行き来 | 直前の下書き保存内容が保持されている |
| M16 | 成功時メール | 運用で店向けメールが飛ぶ場合 | バリデーション失敗のみではステータスが変わらないため送信されない想定。成功時のみ従来どおり確認 |

## 6. 回帰・その他

- `user/src/locales/messages/ja.ts` に `reservation_request_reason` が `base` と揃っていること（user アプリで同文言が必要な画面がある場合）。
- `ConfirmDialog` で複数文言がリスト表示されること、アクセシビリティ属性が付与されていること。
- 旧キー `manage.event.reserve_validation_failed` の経路が残っていないこと。
