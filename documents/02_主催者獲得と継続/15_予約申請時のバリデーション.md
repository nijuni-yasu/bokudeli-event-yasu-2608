# 予約申請時のバリデーション

## 1. 概要

### 1.1 機能の目的
イベントが下書きのまま時間が経過したり、店メニューや売り切れ状態が変わったりしても、**予約申請時点で開催・店舗・メニュー・申請者として成立している状態**だけを `applying_reservation` へ進められるようにする。不整合を申請後に検知するのではなく、申請操作の直前でブロックし、主催者と運営の手戻りを減らす。

### 1.2 主要な機能
- **開催日時の妥当性**: 開始日時が申請時点で過去でないこと、および**最短リードタイム**（申請から開催開始まで必要な全日数。`common/src/constants/eventReservation.ts` の `EVENT_RESERVATION_LEAD_TIME_DAYS`、初期値 `3` 日）を満たすことの検証
- **イベント編集ウィザードでの日時制約**: 上記と**同一のルール**に基づき、開催開始日時が選べる範囲を制限する（ルール違反の日時を最初から選べないようにする）
- **店舗の営業時間との整合**: 選択店の `shop_time` に対し、開催開始日時が営業時間内であることの検証（申請時に再確認）
- **注文可能メニュー件数**: 予約申請時に、イベントに紐づくメニューが少なくとも 1 件、注文可能な状態であることの検証
- **申請ユーザー情報の充足**: 予約申請を行う Firebase ユーザーについて、表示・連絡に必要なプロフィール項目が揃っていることの検証
- **コミュニティ運営者情報**: 運営者名・団体名・住所・電話・利用目的などの設定充足（Phase 2 で扱う）

### 1.3 対象ユーザー
- イベント主催者およびコミュニティ管理者（管理画面から予約申請を行うユーザー）
- 仕様・実装のレビューアー、サポート・運営

## 2. ねらい

### 2.1 ビジネス目標
- 無効な内容での予約申請を減らし、店舗・運営とのやり取りの手戻りを抑える
- 受付開始後に「メニュー 0 件」「過去日付のまま」などのデータ不整合が残るリスクを下げる

### 2.2 ユーザー価値
- 申請直後に拒否や差し戻しを食らうより、**申請前に明確なメッセージで修正箇所を示す**体験にする
- 下書きを数日置いた後でも、申請前に日付・店・メニューの齟齬に気づける

### 2.3 成功指標（KPI）
- 予約申請後の差し戻し・問い合わせ件数の減少
- `applying_reservation` 到達後に判明するデータ不整合の減少

## 3. 前提条件

### 3.1 技術的前提条件
- 予約申請フローは `base/src/components/EventEdit.vue` の `submitReservation` を起点とする
- **予約申請可否の判定は `common` の純関数 `validateReservationRequest` に集約する**（後述 §5.3.1）。既存の `common/src/schemas/Event.ts` の `Event.isValidForReservation`（`EventDbSchema` および主催者連絡先 `ReservationRequiredSchema`）は **削除し**、検証ロジックは集約関数の内部に取り込む（後方互換は提供しない。呼び出し側は §6.1 のチェックリストに従って置き換える）
- 店舗の営業時間判定には `common/src/utils/datetime.ts` の `isInShopTime` が利用可能
- メニュー状態は Firestore のイベントサブコレクションおよび Partner メニュー定義に依存する
- 日時の比較・リードタイム計算は **luxon** および **`Asia/Tokyo` 固定**で行う（`common/src/utils/datetime.ts` の `DEFAULT_TIME_ZONE` と同一の運用）。集約関数は zone を引数で受け取らず、内部で `Asia/Tokyo` をハードコードする

### 3.2 ビジネス的前提条件
- イベントステータスが下書き `in_draft` から予約申請により `applying_reservation` へ遷移する既存フローがある
- 開催日時・店・メニューはイベント編集ウィザードで編集可能である

### 3.3 依存関係
- 「イベントページの仮保存」仕様および `EventEdit` ウィザード
- `Event` スキーマ・`PartnerShop` スキーマ
- ユーザープロフィールおよびコミュニティドキュメントの既存フィールド

## 4. 画面仕様

### 4.1 画面遷移
- イベント編集 Step 5（店舗連絡事項）でユーザーが「予約申請」を実行する
- **下書きの保存**（`updateEventDraft` 等）が先に完了したうえで、集約バリデーションを行う。**保存は行い、ステータスを `applying_reservation` に更新できなかった場合も下書き内容は保持する**
- バリデーション失敗時は申請処理を中断し、**モーダル**で理由を示す（文言は i18n で管理する）
- 申請のみ失敗した場合、モーダルで **下書きは保存済みであること** を伝え、修正後に再試行できるようにする（§8.1）

### 4.2 開催日時の入力（ウィザード全体）
- 最短リードタイムおよび「過去でないこと」と**同じ基準**で、イベント編集で選べる開催開始日時の下限を制限する
- 日付の境界の切り方（例: `Asia/Tokyo` の日付単位で `EVENT_RESERVATION_LEAD_TIME_DAYS` 日後から選択可）は、実装と本書で一致させる

### 4.3 UI 要素

#### 4.3.1 予約申請ボタン
- 既存の有効・無効条件（フォーム妥当性・`in_draft`・ロード中など）は維持する
- **本仕様による追加条件（過去・リードタイム・営業時間・メニュー件数・申請者プロフィール等）は、ボタンの事前無効化ではなく、押下後のバリデーションで判定する**（ユーザーは申請を試み、不備があればモーダルで理由を確認できる）

#### 4.3.2 エラー表示（モーダル）
- 失敗理由は **ユーザー向け文言**でモーダルに表示する。複数件ある場合は列挙できる形式とする
- 戻り値は **理由コード**（`common` で定義する union 型）とし、UI 側で i18n キーにマッピングする。内部キーや Zod パスをそのまま表示しない
- **理由コードからユーザー向け文言への変換は集約関数（§5.3.1）の責務**とする。集約関数は `{ ok: false; reasonCodes: ReservationRequestReasonCode[]; messages: string[] }` の形で返し、UI 側はそのまま `messages` を列挙表示するだけにする
- 既存の `manage.event.reserve_validation_failed` のようにフィールド名を直結する方式は廃止し、集約バリデーションのコード一覧に合わせてメッセージを整理する
- **モーダル実装**: 既存の `base/src/components/ConfirmDialog.vue` を流用する。複数行（箇条書き）表示に対応するため、`ConfirmDialog` の `default` slot に `<ul>` を含む内容を渡す形とし、新規ダイアログコンポーネントは追加しない
- **列挙順・アクセシビリティ**: §8.6・§8.7 に従う

## 5. 技術仕様・データ構造設計

### 5.1 Firestore スキーマ設計
- 本仕様は**新規コレクションやフィールド追加を必須としない**。既存の `events`、メニューサブコレクション、ユーザー・コミュニティドキュメントを参照して検証する
- 最短リードタイムの日数は、**Firestore ではなくコード上の定数**（将来はリモート設定に差し替え可能）とし、**`common/src/constants/eventReservation.ts` に `EVENT_RESERVATION_LEAD_TIME_DAYS` として定義**する（初期値 `3`）

### 5.2 バリデーション項目と判定内容

#### 5.2.1 開催日時（過去・最短リードタイム）
- **過去でないこと**: `event_start_datetime` が、予約申請実行時点の基準時刻（`Asia/Tokyo` の「いま」）より前でないこと
- **最短リードタイム**: `common/src/constants/eventReservation.ts` の **`EVENT_RESERVATION_LEAD_TIME_DAYS`**（初期値 `3`）を満たすこと。具体的な比較式（例: JST の日付の先頭から N 日後 0 時以降のみ可、など）は実装時に本書とコードで一致させる
- **背景**: 下書き放置による過去日付のままの申請防止に加え、店舗・運用の準備期間を確保する
- **境界・終了日時の扱い**: §8.2 に従う

#### 5.2.2 店舗の営業時間
- **条件**: `shop_id` が設定され、店マスタから `PartnerShop` 相当が取得できる場合、`isInShopTime(event_start_datetime, shop)` が真であること
- **背景**: ウィザード編集中の watch で営業時間外時に店をクリアする対応はあるが、**申請ボタン押下時には再検証しないと**、画面を開かずに申請する経路や、データのずれに対して抜け穴が残る
- **未取得時・マスタ不整合**: §8.3 に従う

#### 5.2.3 開催場所と配達可能店舗の整合
- **条件**: `shop_id` が設定されている場合、**保存または予約申請の直前時点**において、イベントの `event_postalcode` から解決した緯度経度（開催地）と `event_start_datetime` に対し、店マスタ上で **イベント編集ウィザードの店舗一覧 `shops` と同一のルール**（距離レンジ・営業時間・承認・開店）により注文可能と判定される店の集合に、当該 `shop_id` が含まれること
- **実装の正本**: `common/src/utils/partnerShopDeliverable.ts` の `getDeliverablePartnerShopsSorted` および `isPartnerShopIdDeliverableAt`。クライアントの `EventEdit.vue`（下書き保存・新規下書き作成・予約申請）と、将来の `validateReservationRequest` はこのロジックを参照する
- **不合格時の理由コード（案）**: `SHOP_NOT_IN_DELIVERY_AREA`。`SHOP_NOT_FOUND`（マスタに `shop_id` が存在しない）や `SHOP_NOT_OPEN`（営業時間外）との差分: 本項は「マスタに店はあるが、開催地・開始日時の組み合わせでは配達対象外」ときに用いる
- **店マスタ一覧未取得**: §8.3 の `SHOP_MASTER_NOT_READY` と併用する。一覧取得完了前に `shop_id` のみが残っている状態では、誤った合格を避けるため保存・申請を中断してよい（`EventEdit` では店舗一覧ストアの取得完了を条件に含める）

#### 5.2.4 メニュー個数（注文可能な選択が 1 件以上）
- **条件**: 予約申請時点で、イベントに紐づくメニューのうち**注文可能なものが 1 件以上**あること
- **「注文可能」の定義**: `common/src/utils/eventMenuConverter.ts` の `convertPartnerMenusToEventMenus` / `convertFromPartnerMenuToEventMenu` と同一の除外（論理削除・売り切れ・有効期間外）に基づき、かつ主催者の選択状態（`is_selected`）を反映した結果として 1 件以上であること
- **背景**: 全件売り切れ、店側のメニュー削除、イベントコピー後の期限切れのみ等で「選択 ID はあるが実質 0 件」や「保存結果が空」になり得る。`applyDefaultSelectedMenuIds` だけでは補正できない経路があるため、**申請前に明示的に検証**する
- **参考**: `functions/default/src/eventMenusSnapshot.ts` の承認遷移や `updateEventMenus` 周辺で、受付中イベントに注文可能メニューが 0 件となる経路の防止と合わせて設計する
- **検証タイミング（Phase 1 の範囲）**: §8.4 に従う

#### 5.2.5 申請ユーザーの登録内容
- **条件**: 予約申請を行う認証ユーザーについて、少なくとも以下が登録されていること
  - **ユーザー名**: `User.user_name` が非空
  - **プロフィール画像**: `User.user_image_url` が非空（**空文字 NG のみ**チェック。URL 形式の検証は行わない）
  - **メールアドレス**: `UserPersonalInformation.user_email` または Firebase Auth `email` のいずれかが**存在（非空）**すること（**形式チェックは行わない**）
- **充足定義・購読遅延**: §8.5 に従う

#### 5.2.6 コミュニティ運営者情報（Phase 2）
- **条件**: 運営者名・団体名・住所・電話・利用目的など、運営が定める必須項目がコミュニティ設定に存在すること
- **備考**: 別紙のコミュニティ設定仕様と整合させる

#### 5.2.7 既存の予約必須項目（主催者連絡先・DB 整合）
- **条件**: 従来どおり `EventDbSchema` および `ReservationRequiredSchema` を満たすこと
- **実装**: 上記を **集約バリデーションの内部**で実行し、不足時はユーザー向け理由コードに変換して返す
- **既存 `Event.isValidForReservation` の扱い**: **削除する**。後方互換は提供しない。Phase 1 PR で `common/src/schemas/Event.ts` から該当メソッドを削除し、`base/src/components/EventEdit.vue` の `submitReservation` を含む全呼び出し側を `validateReservationRequest` に置き換える

### 5.3 実装の置き場所（方針）

#### 5.3.1 `common`（必須）
- **単一の入口**として、予約申請時に必要なすべての検証をまとめた純関数 **`validateReservationRequest`** を `common/src/utils/validateReservationRequest.ts` に置く
- **入力**: イベントスナップショット、店情報、メニュー判定に必要なデータ（`PartnerMenu[]` または `EventMenu[]` と `selectedMenuIds`）、申請ユーザー情報（`User` / `UserPersonalInformation` / Firebase Auth `email`）、基準時刻（テスト用に注入可能なミリ秒、`nowMillis`）
- **出力**:
  ```typescript
  type ValidateReservationRequestResult =
    | { ok: true }
    | { ok: false; reasonCodes: ReservationRequestReasonCode[]; messages: string[] }
  ```
  - `reasonCodes` は判定順に並んだ理由コード（重複なし）。
  - `messages` は **i18n 適用済みのユーザー向け文言**で、UI はこれをそのまま列挙表示する。
- **理由コード型 `ReservationRequestReasonCode`**: `common/src/utils/validateReservationRequest.ts` 内に `as const` の union（または `z.enum`）として定義し、`SCREAMING_SNAKE` で命名する（例: `'EVENT_START_PAST'`, `'EVENT_START_LEAD_TIME'`, `'SHOP_NOT_OPEN'`, `'SHOP_NOT_FOUND'`, `'SHOP_NOT_IN_DELIVERY_AREA'`, `'SHOP_MASTER_NOT_READY'`, `'NO_ORDERABLE_MENU_SELECTED'`, `'APPLICANT_USER_NAME_MISSING'`, `'APPLICANT_USER_IMAGE_MISSING'`, `'APPLICANT_EMAIL_MISSING'`, `'ORGANIZER_FULLNAME_MISSING'`, `'ORGANIZER_COMPANY_MISSING'`, `'ORGANIZER_EMAIL_MISSING'`, `'ORGANIZER_PHONE_PERSONAL_MISSING'`, `'ORGANIZER_MEMO_MISSING'`, `'EVENT_DB_INVALID'`）。最終一覧は実装時に確定する。
- **i18n キーの置き場**: `base/src/locales/messages/ja.ts` に **`reservation_request_reason.<理由コード（lowerCamel または snake）>`** の体系で配置する。`validateReservationRequest` は `vue-i18n` インスタンスを直接 import せず、`useI18n()` の `t` 関数を**引数で受け取る**形（例: `(input, t) => Result`）として、`common` から Vue / i18n 依存を切り離す
- **タイムゾーン**: 関数内部で **`Asia/Tokyo` をハードコード**する（`zone` を引数で受け取らない）。`common/src/utils/datetime.ts` の `DEFAULT_TIME_ZONE` と一致させる
- **目的**: `EventEdit.vue` と将来の **Cloud Functions** が**同じロジック**を呼べるようにする（Functions 側は `t` の代わりに同等のメッセージマップを渡す）

#### 5.3.2 クライアント（`EventEdit.vue`）
- `submitReservation` 内で **`updateEventDraft` 完了後**に、上記 `common` 関数を **1 回**呼ぶ。個別の `if` チェックを Vue に散在させない
- 失敗時はモーダル表示。成功時のみ `event_status` を `applying_reservation` に更新する

#### 5.3.3 サーバー（Phase 2）
- 改ざん防止と整合性のため、**Callable 等から同一の `common` 関数を呼ぶ**再検証を推奨する（必須化のタイミングは別判断）

### 5.4 処理フロー（予約申請）
1. ユーザーが Step 5 で予約申請を実行（確認ダイアログ等、既存の導線は維持）
2. **下書きを Firestore に反映**（現状の `updateEventDraft` 等）。メニュー更新を含む
3. **`common` の集約バリデーションを 1 回実行**（過去・リードタイム・営業時間・メニュー件数・申請ユーザー・主催者連絡先・DB 整合・Phase 2 のコミュニティ項目を将来含められる形）
4. すべて成功時のみ `event_status` を `applying_reservation` に更新し保存
5. 失敗時は **モーダルで理由を表示**し、**ステータスは変更しない**（下書きは 2. で保存済み）

## 7. 注意事項

### 7.1 既存システムへの影響
- 集約関数導入に伴い、`reserve_validation_failed` 等の表示は **理由コードベース**に整理する
- メニュー件数チェックは `eventMenusSnapshot` や売り切れ除外のタイミングと**矛盾しない**ように実装する

### 7.2 セキュリティ考慮事項
- クライアントのみのバリデーションは突破可能なため、重要なビジネスルールは **Phase 2 のサーバー側再検証**を検討する

### 7.3 運用考慮事項
- タイムゾーンは `isInShopTime`、開催日時、最短リードタイムの解釈で **Asia/Tokyo 等の既定**をドキュメントとコードで一致させる
- 仕様変更時は本書と `02_イベントページの仮保存.md` の予約申請記述の整合を取る

## 8. 実装前の確定事項（推奨）

実装・レビューでブレないよう、以下を既定とする。理由コードの具体名は実装時に `common` の列挙と i18n を合わせてよい。

### 8.1 フローと責務
- **クライアント**: `updateEventDraft` 完了後に `common` の **`validateReservationRequest`** を **1 回**呼ぶ。集約関数内部に DB 整合および `ReservationRequiredSchema` 相当を含める。**Phase 1 で予約申請専用の Callable は必須としない**。
- **下書き保存後に申請のみ失敗**: **許容**。モーダルで「内容は保存済みだが予約申請できなかった」旨と理由を示す。
- **ロジックの置き場**: **`common/src/utils/validateReservationRequest.ts` の純関数**とし、基準時刻は引数（`nowMillis`）で注入。Vue 側に業務条件の `if` を散在させない。
- **i18n の解決**: 集約関数は `vue-i18n` の `t` 関数を**引数で受け取り**、戻り値の `messages` に翻訳済み文字列を詰める。`common` パッケージから `vue-i18n` への依存は持たない。

### 8.2 開催日時（過去・境界・終了日時）
- **「いま」**: **luxon** + **`Asia/Tokyo` ハードコード**で揃える（`common/src/utils/datetime.ts` の `DEFAULT_TIME_ZONE` と同一運用）。比較はエポックミリ秒で行ってよいが、日付境界の意味はすべて luxon 側のルールに寄せる。集約関数は `zone` を引数で受け取らない。
- **境界（開始＝いま）**: **`event_start_datetime >= nowMillis` なら合格**（「ちょうど今から開始」は許可）。厳密に未来のみとする場合は別理由コードで分ける。
- **`event_end`**: **Phase 1 では予約申請チェックの対象外**（開催**開始**のみ）。開始と終了の整合は既存ウィザードおよび `EventDbSchema` で担保する前提とする。未担保なら別タスクとする。

### 8.3 店舗営業時間・マスタ
- **`PartnerShop` が取得できない（一覧未ロード等）**: **合格にしない**。理由コード `SHOP_MASTER_NOT_READY`。メッセージ例:「店舗情報を読み込み中です。しばらくしてから再度お試しください」。**UI で店舗一覧ロード中は予約ボタンを無効化する**ことを推奨し、併用してよい。
- **`shop_id` はあるがマスタに店がない**: **不合格**。理由コード `SHOP_NOT_FOUND`。店の再選択やサポート依頼を促す文言とする。
- **営業時間外**: 理由コード `SHOP_NOT_OPEN`。
- **開催地と配達圏**: 店マスタ一覧が取得済みで `shop_id` がマスタに存在しても、**郵便番号から解決した開催地と `event_start_datetime` の組み合わせでは配達対象外**のときは不合格。理由コード `SHOP_NOT_IN_DELIVERY_AREA`（§5.2.3）。判定は `common/src/utils/partnerShopDeliverable.ts` と **`validateReservationRequest` 内で同一**に保つ。
- **一覧取得済みだが候補 0 件で `shop_id` のみ残存**: ウィザードでは郵便番号変更時に店を外す等で防ぐが、保存・申請直前チェックでは **§5.2.3 の不合格**として扱う。
- **watch と申請時の差**: 申請時は **`isInShopTime` で必ず再検証**する。必要に応じ、店側マスタ更新の可能性に触れる一文をモーダル補足に含めてよい。

### 8.4 注文可能メニュー・検証タイミング
- **定義・件数**: §5.2.4 のとおり **`eventMenuConverter` と同一の除外**かつ **`is_selected` が真の件数が 1 以上**で固定する。
- **Phase 1 の検証タイミング**: **`updateEventDraft`（`updateEventMenus` 含む）成功直後**に、**クライアントスナップショット**（クライアントが保持する Partner メニュー・選択 ID・イベント開始時刻）で判定する。**メニューの再 fetch は Phase 1 では必須としない**（保存とバリデーションの間に店舗側がメニューを変更したケースは Phase 1 では許容し、Phase 2 のサーバー側再検証で根本対応する）。
- **0 件**: 理由コード `NO_ORDERABLE_MENU_SELECTED`。

### 8.5 申請ユーザー情報
- **メール**: **第1は `UserPersonalInformation.user_email`**（**存在＝非空**のみチェック、**形式チェックは行わない**）。**空のときは Firebase Auth の `email` をフォールバック**。**両方とも空なら不合格**（理由コード `APPLICANT_EMAIL_MISSING`）。
- **Auth のメール検証（`emailVerified`）**: **Phase 1 では必須としない**（必須化する場合は理由コードとフラグを別途追加する）。
- **`personalInformation` が未取得（購読遅延）**: **`null` を「未登録」とみなして不合格にしない**。**購読完了まで予約ボタンを無効**にする等、**誤ブロックを避ける**運用とする（集約関数は購読完了済みの値が渡される前提）。
- **表示名**: `User.user_name` が非空（理由コード `APPLICANT_USER_NAME_MISSING`）。
- **画像**: `User.user_image_url` は **空文字 NG のみ**チェック（理由コード `APPLICANT_USER_IMAGE_MISSING`）。**URL 形式の検証は Phase 1 では行わない**。`null` はスキーマ上空文字に正規化されるため、実質「未設定」は不合格となる。

### 8.6 理由コードの列挙と主催者不足のマッピング
- **複数不合格**: **すべて列挙**する。表示順は **固定のソート順**とする（推奨: 開催日時 → 店舗 → メニュー → 申請者プロフィール → 主催者連絡先／DB）。
- **i18n キーの置き場**: **`base/src/locales/messages/ja.ts` の `reservation_request_reason.*`** に配置する。理由コード（`SCREAMING_SNAKE`）と i18n キー（`lowerCamel` または `snake_case`、ja.ts の既存スタイルに合わせる）を 1:1 で対応させる。
- **既存キーの廃止**: `manage.event.reserve_validation_failed` の **Zod パス直結は廃止**する（既存呼び出し箇所も置き換え。§6.1 のチェックリスト参照）。
- **主催者不足のマッピング**: `EventDbSchema` / `ReservationRequiredSchema` の Zod パスを **安定した理由コード**にマップする（例: パス `organizer_email` → 理由コード `ORGANIZER_EMAIL_MISSING` → i18n キー `reservation_request_reason.organizer_email_missing`）。マッピング表は `validateReservationRequest.ts` の内部に持つ。

### 8.7 モーダルのアクセシビリティ
- **コンポーネント**: 既存の **`base/src/components/ConfirmDialog.vue`** を流用する。新規ダイアログコンポーネントは追加しない。
- 複数理由は **箇条書きリスト**（`<ul>`）で示す。`ConfirmDialog` の `default` slot に「導入文 + `<ul><li>` のリスト」を渡す形とし、`messages` 配列をそのまま `v-for` で展開する。
- モーダルには **`role="alertdialog"`**、または **`aria-modal` と見出しの結合**など、スクリーンリーダーで内容が追える属性を付与する方針とする（実装は Vuetify のダイアログ特性に合わせて調整。`ConfirmDialog` 側に必要な属性が無い場合は同コンポーネントに追加する）。

### 8.8 セキュリティ・メール（Phase 1 / 2）
- **Phase 2**: `applying_reservation` へ遷移し得る **サーバー経路**（Callable 等）で **同一 `common` 集約関数**を実行する。
- **メール**: バリデーション失敗時は **`applying_reservation` に遷移しない**ため、**店向け予約メール等は送信されない**想定とする。実際の送信は **ステータス遷移に紐づく Function／トリガー**側で行われる前提を運用確認する。
