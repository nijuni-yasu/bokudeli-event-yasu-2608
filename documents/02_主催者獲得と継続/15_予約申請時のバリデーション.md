# 予約申請時のバリデーション

## 1. 概要

### 1.1 機能の目的
イベントが下書きのまま時間が経過したり、店メニューや売り切れ状態が変わったりしても、**予約申請時点で開催・店舗・メニュー・申請者として成立している状態**だけを `applying_reservation` へ進められるようにする。不整合を申請後に検知するのではなく、申請操作の直前でブロックし、主催者と運営の手戻りを減らす。

### 1.2 主要な機能
- **開催日時の妥当性**: 開始日時が申請時点で過去でないこと、および**最短リードタイム**（申請から開催開始まで必要な全日数。`common/src/constants/eventReservation.ts` の `EVENT_RESERVATION_LEAD_TIME_DAYS`、初期値 `3` 日）を満たすことの検証
- **イベント編集ウィザードでの日時制約**: 上記と**同一のルール**に基づき、開催開始日時が選べる範囲を制限する（ルール違反の日時を最初から選べないようにする）
- **店舗の営業時間との整合**: 選択店の `shop_time` に対し、開催開始日時が営業時間内であることの検証（申請時に再確認）
- **注文可能メニュー件数**: 予約申請時に、イベントに紐づくメニューが少なくとも 1 件、注文可能な状態であることの検証
- **申請ユーザー情報の充足**: 予約申請を行う Firebase ユーザーについて、表示・連絡に必要なプロフィール項目が揃っていることの検証
- **コミュニティ運営者情報**: 運営者名・団体名・住所・電話・利用目的などの設定充足（Phase 2 で扱う）

### 1.3 対象ユーザー
- イベント主催者およびコミュニティ管理者（管理画面から予約申請を行うユーザー）
- 仕様・実装のレビューアー、サポート・運営

## 2. ねらい

### 2.1 ビジネス目標
- 無効な内容での予約申請を減らし、店舗・運営とのやり取りの手戻りを抑える
- 受付開始後に「メニュー 0 件」「過去日付のまま」などのデータ不整合が残るリスクを下げる

### 2.2 ユーザー価値
- 申請直後に拒否や差し戻しを食らうより、**申請前に明確なメッセージで修正箇所を示す**体験にする
- 下書きを数日置いた後でも、申請前に日付・店・メニューの齟齬に気づける

### 2.3 成功指標（KPI）
- 予約申請後の差し戻し・問い合わせ件数の減少
- `applying_reservation` 到達後に判明するデータ不整合の減少

## 3. 前提条件

### 3.1 技術的前提条件
- 予約申請フローは `base/src/components/EventEdit.vue` の `submitReservation` を起点とする
- **予約申請可否の判定は `common` の純関数 `validateReservationRequest` に集約する**（後述 §5.3.1）。既存の `common/src/schemas/Event.ts` の `Event.isValidForReservation`（`EventDbSchema` および主催者連絡先 `ReservationRequiredSchema`）は **削除し**、検証ロジックは集約関数の内部に取り込む（後方互換は提供しない。呼び出し側は §6.1 のチェックリストに従って置き換える）
- 店舗の営業時間判定には `common/src/utils/datetime.ts` の `isInShopTime` が利用可能
- メニュー状態は Firestore のイベントサブコレクションおよび Partner メニュー定義に依存する
- 日時の比較・リードタイム計算は **luxon** および **`Asia/Tokyo` 固定**で行う（`common/src/utils/datetime.ts` の `DEFAULT_TIME_ZONE` と同一の運用）。集約関数は zone を引数で受け取らず、内部で `Asia/Tokyo` をハードコードする

### 3.2 ビジネス的前提条件
- イベントステータスが下書き `in_draft` から予約申請により `applying_reservation` へ遷移する既存フローがある
- 開催日時・店・メニューはイベント編集ウィザードで編集可能である

### 3.3 依存関係
- 「イベントページの仮保存」仕様および `EventEdit` ウィザード
- `Event` スキーマ・`PartnerShop` スキーマ
- ユーザープロフィールおよびコミュニティドキュメントの既存フィールド

## 4. 画面仕様

### 4.1 画面遷移
- イベント編集 Step 5（店舗連絡事項）でユーザーが「予約申請」を実行する
- **下書きの保存**（`updateEventDraft` 等）が先に完了したうえで、集約バリデーションを行う。**保存は行い、ステータスを `applying_reservation` に更新できなかった場合も下書き内容は保持する**
- バリデーション失敗時は申請処理を中断し、**モーダル**で理由を示す（文言は i18n で管理する）
- 申請のみ失敗した場合、モーダルで **下書きは保存済みであること** を伝え、修正後に再試行できるようにする（§8.1）

### 4.2 開催日時の入力（ウィザード全体）
- 最短リードタイムおよび「過去でないこと」と**同じ基準**で、イベント編集で選べる開催開始日時の下限を制限する
- 日付の境界の切り方（例: `Asia/Tokyo` の日付単位で `EVENT_RESERVATION_LEAD_TIME_DAYS` 日後から選択可）は、実装と本書で一致させる

### 4.3 UI 要素

#### 4.3.1 予約申請ボタン
- 既存の有効・無効条件（フォーム妥当性・`in_draft`・ロード中など）は維持する
- **無効化の二段構え**を取る。ブレないよう次のとおり整理する。
  - **事前無効化（ボタン disabled）**: **データが揃っていない場合**に限定する。具体的には次のいずれかが未取得・購読遅延中のとき。
    - 店舗一覧（PartnerShop ストア）の取得完了前
    - 申請ユーザーの `UserPersonalInformation` 購読完了前
    - イベントメニュー（`EventMenu[]`）の取得・保存完了前
  - **押下後のバリデーション**: **業務ルール違反**（過去・リードタイム・営業時間・配達圏外・メニュー件数・申請者プロフィール・主催者連絡先・DB 整合）は事前無効化せず、押下後に集約バリデーションを実行してモーダルで理由を示す（ユーザーは申請を試みて修正点を一覧で把握できる）。

#### 4.3.2 エラー表示（モーダル）
- 失敗理由は **ユーザー向け文言**でモーダルに表示する。複数件ある場合は列挙できる形式とする
- 集約関数の戻り値は **理由コードのみ**（`{ ok: false; reasonCodes: ReservationRequestReasonCode[] }`）とし、`common` から i18n 依存を切り離す。**メッセージ文言への変換責務は `base` 側のヘルパ関数 `reservationRequestMessages.ts` が担う**（§5.3.1）。UI は `messages` 配列を `<ul><li>` で列挙表示する
- 内部キーや Zod パスをそのまま表示しない（理由コードベースで管理）
- 既存の `manage.event.reserve_validation_failed` のようにフィールド名を直結する方式は廃止し、集約バリデーションのコード一覧に合わせてメッセージを整理する
- **モーダル実装**: 既存の `base/src/components/ConfirmDialog.vue` を流用する。`ConfirmDialog` は既に default slot 対応済みのため、呼び出し側で導入文 + `<ul><li>` を slot に渡せばよい。新規ダイアログコンポーネントは追加しない
- **列挙順・アクセシビリティ**: §8.6・§8.7 に従う

## 5. 技術仕様・データ構造設計

### 5.1 Firestore スキーマ設計
- 本仕様は**新規コレクションやフィールド追加を必須としない**。既存の `events`、メニューサブコレクション、ユーザー・コミュニティドキュメントを参照して検証する
- 最短リードタイムの日数は、**Firestore ではなくコード上の定数**（将来はリモート設定に差し替え可能）とし、**`common/src/constants/eventReservation.ts` に `EVENT_RESERVATION_LEAD_TIME_DAYS` として定義**する（初期値 `3`）

### 5.2 バリデーション項目と判定内容

#### 5.2.1 開催日時（過去・最短リードタイム）
- **過去でないこと**: `event_start_datetime` が、予約申請実行時点の基準時刻（`Asia/Tokyo` の「いま」）より前でないこと（`event_start_datetime >= nowMillis` で合格）
- **最短リードタイム**: `common/src/constants/eventReservation.ts` の **`EVENT_RESERVATION_LEAD_TIME_DAYS`**（初期値 `3`）を満たすこと
- **具体式（確定）**: JST の「いま」が属する日（`startOfJstToday`）の 0:00 を起点として、`event_start_datetime >= startOfJstToday + EVENT_RESERVATION_LEAD_TIME_DAYS 日` を満たすときに合格。
  - 例: `EVENT_RESERVATION_LEAD_TIME_DAYS = 3` で 4/29（火）13:00 JST に申請 → **5/2（金）00:00 JST 以降の開始時刻**を許可（4/30 を 1 日目、5/1 を 2 日目、5/2 を 3 日目とカウント）。
  - luxon 実装イメージ: `DateTime.fromMillis(nowMillis, { zone: 'Asia/Tokyo' }).startOf('day').plus({ days: 3 })` の `toMillis()` を下限とする。
- **背景**: 下書き放置による過去日付のままの申請防止に加え、店舗・運用の準備期間を確保する
- **境界・終了日時の扱い**: §8.2 に従う

#### 5.2.2 店舗の営業時間
- **条件**: `shop_id` が設定され、店マスタから `PartnerShop` 相当が取得できる場合、`isInShopTime(event_start_datetime, shop)` が真であること
- **背景**: ウィザード編集中の watch で営業時間外時に店をクリアする対応はあるが、**申請ボタン押下時には再検証しないと**、画面を開かずに申請する経路や、データのずれに対して抜け穴が残る
- **未取得時・マスタ不整合**: §8.3 に従う

#### 5.2.3 開催場所と配達可能店舗の整合
- **条件**: `shop_id` が設定されている場合、**保存または予約申請の直前時点**において、**開催地座標**（`location: EventLocationLatLng`）と `event_start_datetime` に対し、店マスタ上で **イベント編集ウィザードの店舗一覧 `shops` と同一のルール**（距離レンジ・営業時間・承認・開店）により注文可能と判定される店の集合に、当該 `shop_id` が含まれること
- **開催地座標の取得元（確定）**: 集約関数は **新たな Geocoding を行わない**。座標は `EventEdit.vue` 側で `event_postalcode` から PostcodeJP により非同期解決済みの `location.value`（`{ latitude, longitude }`）が UI から `validateReservationRequest` に **必須引数**として渡される前提とする。Event スキーマ自体には `event_lat` / `event_lng` フィールドは存在しない
- **実装の正本**: `common/src/utils/partnerShopDeliverable.ts` の `getDeliverablePartnerShopsSorted` および `isPartnerShopIdDeliverableAt`。`validateReservationRequest` はこの関数を内部で呼ぶ（重複実装を作らない）
- **不合格時の理由コード**: `SHOP_NOT_IN_DELIVERY_AREA`。`SHOP_NOT_FOUND`（マスタに `shop_id` が存在しない）や `SHOP_NOT_OPEN`（営業時間外）との差分: 本項は「マスタに店はあるが、開催地・開始日時の組み合わせでは配達対象外」ときに用いる
- **店マスタ一覧と座標の引数化**: 集約関数は `partnerShops: PartnerShop[]` および `location: EventLocationLatLng` を **必須引数**で受け取る（`null` / `undefined` を許容しない）。一覧未取得・座標未解決は UI 側で予約ボタンを無効化することで防ぐ（§4.3.1）。これにより集約関数内で `SHOP_MASTER_NOT_READY` を返す経路は不要となり、UI が押下を許可した時点で必要なデータは揃っている前提で動作する

#### 5.2.4 メニュー個数（注文可能な選択が 1 件以上）
- **条件**: 予約申請時点で、イベントに紐づくメニューのうち**注文可能なものが 1 件以上**あること
- **入力型（確定）**: 集約関数の入力は **`EventMenu[]`（保存後のスナップショット）に統一**する。`PartnerMenu[]` + `selectedMenuIds` の組み合わせは受け付けない。理由: `updateEventDraft` 完了後にバリデーションを実行するフロー（§5.4）であれば、その時点で `EventMenu[]` は確定している。両対応はテストケースが膨らむのみで利点がない
- **「注文可能」の定義（確定）**: `EventMenu` には `is_deleted` / `start_date` / `end_date` フィールドが存在せず、論理削除・有効期間外は `PartnerMenu → EventMenu` 変換時点（[`common/src/utils/eventMenuConverter.ts`](../../../common/src/utils/eventMenuConverter.ts) の `convertFromPartnerMenuToEventMenu`）で既に除外済み。集約関数では `is_selected === true && !is_sold_out` を満たすメニューが 1 件以上存在することのみを検証する
- **背景**: 全件売り切れ、店側のメニュー削除、イベントコピー後の期限切れのみ等で「選択 ID はあるが実質 0 件」や「保存結果が空」になり得る。`applyDefaultSelectedMenuIds` だけでは補正できない経路があるため、**申請前に明示的に検証**する
- **参考**: `functions/default/src/eventMenusSnapshot.ts` の承認遷移や `updateEventMenus` 周辺で、受付中イベントに注文可能メニューが 0 件となる経路の防止と合わせて設計する
- **検証タイミング（Phase 1 の範囲）**: §8.4 に従う

#### 5.2.5 申請ユーザーの登録内容
- **条件**: 予約申請を行う認証ユーザーについて、少なくとも以下が登録されていること
  - **ユーザー名**: `User.user_name` が非空
  - **プロフィール画像**: `User.user_image_url` が非空（**空文字 NG のみ**チェック。URL 形式の検証は行わない）
  - **メールアドレス**: `UserPersonalInformation.user_email` または Firebase Auth `email` のいずれかが**存在（非空）**すること（**形式チェックは行わない**）
- **入力の前提（確定）**: 集約関数の入力では `personalInformation: UserPersonalInformation` を **必須引数**とし、`null` / `undefined` を許容しない（購読遅延は UI 側で予約ボタン無効化により防ぐ）。これにより集約関数は「未取得」と「未登録」を判別する責務を持たない
- **充足定義・購読遅延**: §8.5 に従う

#### 5.2.6 コミュニティ運営者情報（Phase 2）
- **条件**: 運営者名・団体名・住所・電話・利用目的など、運営が定める必須項目がコミュニティ設定に存在すること
- **備考**: 別紙のコミュニティ設定仕様と整合させる

#### 5.2.7 既存の予約必須項目（主催者連絡先・DB 整合）
- **条件**: 従来どおり `EventDbSchema` および `ReservationRequiredSchema` を満たすこと
- **実装**: 上記を **集約バリデーションの内部**で実行し、不足時はユーザー向け理由コードに変換して返す
- **形式チェック（#2246 で追加）**: 主催者メールアドレス・電話番号（本人／会社）は、非空のときに `common/src/utils/contactFormat.ts` の `isValidEmail` / `isValidPhone` で形式も検証する（未入力時は MISSING 側のみを返し二重表示しない）。理由コードは `ORGANIZER_EMAIL_INVALID` / `ORGANIZER_PHONE_PERSONAL_INVALID` / `ORGANIZER_PHONE_COMPANY_INVALID`。ウィザード Step 5 の v-form ルール（`emailValidator` / `phoneValidator`）と同一の判定を用い、予約申請ボタンの事前無効化ではなくモーダル表示で理由を示す
- **既存 `Event.isValidForReservation` の扱い**: **削除する**。後方互換は提供しない。Phase 1 PR で `common/src/schemas/Event.ts` から該当メソッドを削除し、`base/src/components/EventEdit.vue` の `submitReservation` を含む全呼び出し側を `validateReservationRequest` に置き換える

### 5.3 実装の置き場所（方針）

#### 5.3.1 `common`（必須）
- **単一の入口**として、予約申請時に必要なすべての検証をまとめた純関数 **`validateReservationRequest`** を `common/src/utils/validateReservationRequest.ts` に置く
- **入力（確定）**: 次のとおり全項目を**必須引数**とし、`null` / `undefined` の取り扱いを集約関数の責務から外す。
  ```typescript
  type ValidateReservationRequestInput = {
    event: Event                        // 保存済みイベント
    handleUserId: string                // 申請者の Firebase UID（主催者連絡先の一致確認等）
    user: User                          // 申請者の User
    personalInformation: UserPersonalInformation // 購読完了済みの個人情報（必須）
    authEmail: string | null            // Firebase Auth の email（フォールバック用）
    eventMenus: EventMenu[]             // 保存後のメニュースナップショット
    partnerShops: PartnerShop[]         // 取得済みの店舗一覧
    location: EventLocationLatLng       // event_postalcode から PostcodeJP で解決済みの開催地座標
    nowMillis: number                   // 基準時刻（テスト注入可能）
  }
  ```
- **出力（確定）**: **理由コードのみ**を返し、メッセージ整形を含めない。`common` を Vue / i18n から完全に切り離す。
  ```typescript
  type ValidateReservationRequestResult =
    | { ok: true }
    | { ok: false; reasonCodes: ReservationRequestReasonCode[] }
  ```
  - `reasonCodes` は固定ソート順（§8.6）で並んだ理由コード（重複なし）。
- **メッセージ整形の責務**: `base/src/utils/reservationRequestMessages.ts`（**Phase 1 で新設**）に `reasonCodesToMessages(reasonCodes: ReservationRequestReasonCode[], t: (key: string) => string): string[]` を置く。UI はこのヘルパで `messages` を生成し、`<ul><li>` で列挙表示する。
- **理由コード型 `ReservationRequestReasonCode`**: `common/src/utils/validateReservationRequest.ts` 内に `as const` の union（または `z.enum`）として定義し、`SCREAMING_SNAKE` で命名する（例: `'EVENT_START_PAST'`, `'EVENT_START_LEAD_TIME'`, `'SHOP_NOT_OPEN'`, `'SHOP_NOT_FOUND'`, `'SHOP_NOT_IN_DELIVERY_AREA'`, `'NO_ORDERABLE_MENU_SELECTED'`, `'APPLICANT_USER_NAME_MISSING'`, `'APPLICANT_USER_IMAGE_MISSING'`, `'APPLICANT_EMAIL_MISSING'`, `'ORGANIZER_FULLNAME_MISSING'`, `'ORGANIZER_COMPANY_MISSING'`, `'ORGANIZER_EMAIL_MISSING'`, `'ORGANIZER_PHONE_PERSONAL_MISSING'`, `'ORGANIZER_MEMO_MISSING'`, `'EVENT_DB_INVALID'`）。最終一覧は実装時に確定する。`SHOP_MASTER_NOT_READY` は集約関数が一覧未取得を引数で受けない方針（§5.2.3）に伴い**廃止**する。
- **i18n キーの置き場**: `base/src/locales/messages/ja.ts` に **`reservation_request_reason.<理由コード（snake_case）>`** の体系で配置する（既存 ja.ts の命名スタイルに合わせる）。集約関数は `vue-i18n` への依存を持たない
- **タイムゾーン**: 関数内部で **`Asia/Tokyo` をハードコード**する（`zone` を引数で受け取らない）。`common/src/utils/datetime.ts` の `DEFAULT_TIME_ZONE` と一致させる
- **目的**: `EventEdit.vue` と将来の **Cloud Functions** が**同じロジック**を呼べるようにする（Functions 側は `reasonCodes` をそのまま `HttpsError.details` に積み、クライアントが i18n マップする）

#### 5.3.2 クライアント（`EventEdit.vue`）
- 予約ボタンの `disabled` 条件に **データ未取得ガード**を加える（§4.3.1）。`partnerShops` / `personalInformation` / `eventMenus` のいずれかが未取得なら無効化。
- `submitReservation` 内で **`updateEventDraft` 完了後**に、`common` 関数 `validateReservationRequest` を **1 回**呼ぶ。個別の `if` チェックを Vue に散在させない
- 失敗時は `reasonCodesToMessages` で文言化し、`ConfirmDialog` に `<ul><li>` を slot で渡してモーダル表示。成功時のみ `event_status` を `applying_reservation` に更新する

#### 5.3.3 サーバー（Phase 2）
- 改ざん防止と整合性のため、**Callable 等から同一の `common` 関数を呼ぶ**再検証を推奨する（必須化のタイミングは別判断）
- 失敗時は `HttpsError`（code 例: `failed-precondition`）に `details: { reasonCodes }` を載せる。クライアントは同じ `reasonCodesToMessages` で文言化する

### 5.4 処理フロー（予約申請）
1. ユーザーが Step 5 で予約申請を実行（確認ダイアログ等、既存の導線は維持）
2. **下書きを Firestore に反映**（現状の `updateEventDraft` 等）。メニュー更新を含む
3. **`common` の集約バリデーションを 1 回実行**（過去・リードタイム・営業時間・メニュー件数・申請ユーザー・主催者連絡先・DB 整合・Phase 2 のコミュニティ項目を将来含められる形）
4. すべて成功時のみ `event_status` を `applying_reservation` に更新し保存
5. 失敗時は **モーダルで理由を表示**し、**ステータスは変更しない**（下書きは 2. で保存済み）

## 8. 実装前の確定事項（推奨）

実装・レビューでブレないよう、以下を既定とする。理由コードの具体名は実装時に `common` の列挙と i18n を合わせてよい。

### 8.1 フローと責務
- **クライアント**: `updateEventDraft` 完了後に `common` の **`validateReservationRequest`** を **1 回**呼ぶ。集約関数内部に DB 整合および `ReservationRequiredSchema` 相当を含める。**Phase 1 で予約申請専用の Callable は必須としない**。
- **下書き保存後に申請のみ失敗**: **許容**。モーダルで「内容は保存済みだが予約申請できなかった」旨と理由を示す。
- **ロジックの置き場**: **`common/src/utils/validateReservationRequest.ts` の純関数**とし、基準時刻は引数（`nowMillis`）で注入。Vue 側に業務条件の `if` を散在させない。
- **i18n の解決（確定）**: 集約関数は `reasonCodes` のみを返し、メッセージ整形は **`base/src/utils/reservationRequestMessages.ts` の `reasonCodesToMessages(reasonCodes, t)`** が担う。`common` から `vue-i18n` への依存を持たないだけでなく、`t` 関数の引数化も `common` の責務から外す（テスト容易性と Functions 移植性のため）。

### 8.2 開催日時（過去・境界・終了日時）
- **「いま」**: **luxon** + **`Asia/Tokyo` ハードコード**で揃える（`common/src/utils/datetime.ts` の `DEFAULT_TIME_ZONE` と同一運用）。比較はエポックミリ秒で行ってよいが、日付境界の意味はすべて luxon 側のルールに寄せる。集約関数は `zone` を引数で受け取らない。
- **境界（開始＝いま）**: **`event_start_datetime >= nowMillis` なら合格**（「ちょうど今から開始」は許可）。厳密に未来のみとする場合は別理由コードで分ける。
- **リードタイム下限の具体式（確定）**: `startOfJstToday = DateTime.fromMillis(nowMillis, { zone: 'Asia/Tokyo' }).startOf('day')` とし、`event_start_datetime >= startOfJstToday.plus({ days: EVENT_RESERVATION_LEAD_TIME_DAYS }).toMillis()` を満たすときに合格（不一致なら `EVENT_START_LEAD_TIME`）。`EVENT_START_PAST` は `event_start_datetime < nowMillis` で判定し、両方該当する場合は `EVENT_START_PAST` を優先する。
- **`event_end`**: **Phase 1 では予約申請チェックの対象外**（開催**開始**のみ）。開始と終了の整合は既存ウィザードおよび `EventDbSchema` で担保する前提とする。未担保なら別タスクとする。

### 8.3 店舗営業時間・マスタ
- **`PartnerShop` が取得できない（一覧未ロード等）**: 集約関数は引数で必須受領するため、**ここに到達する前に UI 側で予約ボタンを無効化する**（§4.3.1）。理由コード `SHOP_MASTER_NOT_READY` は**廃止**し、集約関数の責務から外す。
- **`shop_id` はあるがマスタに店がない**: **不合格**。理由コード `SHOP_NOT_FOUND`。店の再選択やサポート依頼を促す文言とする。
- **店マスタで `is_approved` が false**: **不合格**。理由コード **`SHOP_NOT_APPROVED`**。未承認のため予約申請できない旨の文言。
- **店マスタでドキュメント先頭の `is_open` が false**（`shop_time` の曜日フラグとは別）: **不合格**。理由コード **`SHOP_CLOSED`**。閉店のため予約申請できない旨の文言。順序としては `SHOP_NOT_FOUND` の次に判定し、この不合格時は営業時間・配達圏チェックより先にユーザーへ明示する。
- **営業時間外**: 理由コード `SHOP_NOT_OPEN`（`shop_time` と `isInShopTime` により判定）。
- **開催地と配達圏**: 店マスタ一覧の中に `shop_id` が存在しても、**`location` と `event_start_datetime` の組み合わせでは配達対象外**のときは不合格。理由コード `SHOP_NOT_IN_DELIVERY_AREA`（§5.2.3）。判定は `common/src/utils/partnerShopDeliverable.ts` の関数を**そのまま呼び出す**（重複実装を作らない）。
- **座標未解決**: `location` は集約関数の必須引数。UI 側で `location.value == null` のときは予約ボタンを無効化することで防ぐ（§4.3.1）。集約関数内で `null` を扱う経路は持たない。
- **一覧取得済みだが候補 0 件で `shop_id` のみ残存**: ウィザードでは郵便番号変更時に店を外す等で防ぐが、保存・申請直前チェックでは **§5.2.3 の不合格**として扱う。
- **watch と申請時の差**: 申請時は **`isInShopTime` で必ず再検証**する。必要に応じ、店側マスタ更新の可能性に触れる一文をモーダル補足に含めてよい。

### 8.4 注文可能メニュー・検証タイミング
- **定義・件数**: §5.2.4 のとおり **`eventMenuConverter` と同一の除外**かつ **`is_selected` が真の件数が 1 以上**で固定する。
- **入力型（確定）**: 集約関数は `EventMenu[]`（保存後のスナップショット）のみを受け取る。`PartnerMenu[]` + `selectedMenuIds` は受け付けない。
- **Phase 1 の検証タイミング**: **`updateEventDraft`（`updateEventMenus` 含む）成功直後**に、保存結果として返ってきた `EventMenu[]` で判定する。**メニューの再 fetch は Phase 1 では必須としない**（保存とバリデーションの間に店舗側がメニューを変更したケースは Phase 1 では許容し、Phase 2 のサーバー側再検証で根本対応する）。
- **0 件**: 理由コード `NO_ORDERABLE_MENU_SELECTED`。

### 8.5 申請ユーザー情報
- **メール**: **第1は `UserPersonalInformation.user_email`**（**存在＝非空**のみチェック、**形式チェックは行わない**）。**空のときは Firebase Auth の `email` をフォールバック**。**両方とも空なら不合格**（理由コード `APPLICANT_EMAIL_MISSING`）。
- **Auth のメール検証（`emailVerified`）**: **Phase 1 では必須としない**（必須化する場合は理由コードとフラグを別途追加する）。
- **`personalInformation` の扱い（確定）**: 集約関数の入力では **`UserPersonalInformation` を必須引数**とし、`null` / `undefined` を許容しない。購読遅延中は UI 側で予約ボタンを無効化する（§4.3.1）。これにより集約関数は「未取得」と「未登録（空文字）」を判別する責務から解放される。
- **表示名**: `User.user_name` が非空（理由コード `APPLICANT_USER_NAME_MISSING`）。
- **画像**: `User.user_image_url` は **空文字 NG のみ**チェック（理由コード `APPLICANT_USER_IMAGE_MISSING`）。**URL 形式の検証は Phase 1 では行わない**。`null` はスキーマ上空文字に正規化されるため、実質「未設定」は不合格となる。

### 8.6 理由コードの列挙と主催者不足のマッピング
- **複数不合格**: **すべて列挙**する。表示順は **固定のソート順**とし、`validateReservationRequest` 側で並び替えてから返す（推奨順: 開催日時 → 店舗 → メニュー → 申請者プロフィール → 主催者連絡先／DB）。
- **i18n キーの置き場（確定）**: **`base/src/locales/messages/ja.ts` の `reservation_request_reason.*`** に配置する。理由コード（`SCREAMING_SNAKE`）と i18n キー（`snake_case`、ja.ts の既存スタイルに合わせる）を 1:1 で対応させる。例: `EVENT_START_LEAD_TIME` → `reservation_request_reason.event_start_lead_time`。
- **メッセージ整形**: `base/src/utils/reservationRequestMessages.ts` の `reasonCodesToMessages(reasonCodes, t)` が、固定マップ（`Record<ReservationRequestReasonCode, string>`、各値は i18n キー）を介して `t(key)` を呼び、文言配列を返す。
- **既存キーの廃止**: `manage.event.reserve_validation_failed` の **Zod パス直結は廃止**する（既存呼び出し箇所も置き換え。§6.1 のチェックリスト参照）。
- **主催者不足のマッピング**: `EventDbSchema` / `ReservationRequiredSchema` の Zod パスを **安定した理由コード**にマップする（例: パス `organizer_email` → 理由コード `ORGANIZER_EMAIL_MISSING` → i18n キー `reservation_request_reason.organizer_email_missing`）。マッピング表は `validateReservationRequest.ts` の内部に持つ。
