# イベントページの仮保存機能

## 1. 概要

### 1.1 機能の目的
イベントページ作成時の4ステップのうち、最初のステップ（基本情報入力）完了時に、イベントの新規作成・仮保存機能を提供し、ユーザーの入力ストレスを軽減する。

### 1.2 主要な機能
- イベント基本情報入力時のイベント新規作成・仮保存。
- イベント基本情報入力画面で「保存して進む」を押下したときに自動で仮保存する。

### 1.3 対象ユーザー
- イベント主催者
- コミュニティ管理者

## 2. ねらい

### 2.1 ビジネス目標
- イベント作成の離脱率を30%削減
- 主催者獲得率の向上

### 2.2 ユーザー価値
- イベント作成プロセスのストレス軽減
- 途中保存による安心感の提供

### 2.3 成功指標（KPI）
- イベント作成完了率の向上
- 仮保存から本保存への変換率
- ユーザー満足度スコア

## 3. 前提条件

### 3.1 技術的前提条件
- Firestoreデータベース
- Vue.js 3 + TypeScript
- Firebase Authentication
- 既存のイベント作成フロー（4ステップ）

### 3.2 ビジネス的前提条件
- コミュニティが存在すること
- ユーザーが主催者権限を持っていること
- イベント作成の4ステップフローが確立されていること

### 3.3 依存関係
- コミュニティ管理機能
- イベント作成コンポーネント群
- ユーザー認証システム

## 4. 画面仕様

### 4.1 画面遷移
```
イベント作成開始
    ↓
基本情報入力画面（base/src/components/eventcreate/EventBasicInfoCard.vue）
    ↓
[仮保存実行] （※基本情報入力画面で「保存して進む」を押下するタイミング）

    ↓
```

### 4.2 UI要素
- **新規イベント作成時**: 「次へ」ボタンを「保存して進む」ボタンに文言修正
  - 「保存して進む」ボタン押下時に仮保存を実行
- **既存イベント編集時**: 「次へ」ボタンと表示（変更なし）
  - 「次へ」ボタン押下時は保存せず、次のステップに遷移のみ
  - 既存イベントの判定: `route.query.id`が存在する場合
- 仮保存 完了通知トースト
- 仮保存 エラー通知トースト

## 5. 技術仕様・データ構造設計

### 5.1 Firestoreスキーマ

#### 5.1.1 ステータス設計
- **`in_draft`**: 下書き中
  - 必須データが揃っていなくても保存可能
  - 仮保存時はこのステータスで保存
  - 編集可能な状態
- **`applying_reservation`**: 予約申請中
  - `EventDbSchema`で定義された全ての必須データが揃っている必要がある
  - `in_draft`から`applying_reservation`への遷移時にバリデーションを実行

#### 5.1.2 データ構造
```typescript
// イベントドキュメント（in_draft時）
interface EventDraft {
  // ステータス
  event_status: {
    value: 'in_draft'
    shop_comment?: string
  }

  // 基本情報（仮保存時に入力）
  event_start_datetime: Timestamp;
  event_end_datetime: Timestamp;
  event_postalcode: string;
  event_address: string;
  
  // 仮保存時のデフォルト値
  event_name: string; // "[コミュニティ名]のイベント"
  event_cover_url: string; // コミュニティカバー画像（community_cover_image_urlをコピー）
  event_desc: string; // "[コミュニティ名]のイベント"
  event_payment: 'user_advance'; // デフォルト値
  event_max_people: number; // デフォルト値: 25
  is_public: true // デフォルト値：公開イベント
  
  // 後から入力される項目（in_draft時はオプション、applying_reservation時は必須）
  shop_id?: string;
  shop_name?: string;
  event_deadline_datetime?: Timestamp;
  
  // 主催者情報（in_draft時はオプション、applying_reservation時は必須）
  organizer_fullname?: string;
  organizer_company?: string;
  organizer_email?: string;
  organizer_phone_personal?: string;
  organizer_memo?: string;
}
```

#### 5.1.3 Zodスキーマ設計（`common/src/schemas/Event.ts`）

##### 5.1.3.1 EventAppSchema（新規作成・仮保存用）
- **用途**: イベントオブジェクトの新規作成時に適用されるスキーマ
- **特徴**: 
  - 必須項目にデフォルト値が設定されているため、データが不足していても保存可能
  - `Event`クラスのコンストラクタで使用される
  - 仮保存時（`in_draft`ステータス）に使用
- **主要なデフォルト値**:
  - `event_status.value`: `'in_draft'`
  - `event_payment`: `'user_advance'`
  - `is_public`: true
  - `event_max_people`: `25`
  - `event_postalcode`: `''`（空文字）
  - `shop_id`: `''`（空文字）
  - `organizer_fullname`: `''`（空文字）
  - その他、多くの項目が空文字またはデフォルト値で初期化される

##### 5.1.3.2 EventDbSchema（データベース保存用）
- **用途**: Firestoreへの保存時に適用されるスキーマ
- **特徴**:
  - 全必須項目が揃っている必要がある（`.nonempty()`や`.regex()`などの厳格なバリデーション）
  - `applying_reservation`への遷移時に使用
  - `Event.toFirestore()`メソッドで使用される
- **必須項目の例**:
  - `event_id`, `community_id`, `community_name`, `community_account`
  - `event_postalcode`: 7桁の数字（`/^\d{7}$/`）
  - `event_address`: 空でない文字列
  - `shop_id`, `shop_name`: 空でない文字列
  - `event_name`, `event_cover_url`: 空でない文字列（URL形式）
  - `organizer_fullname`, `organizer_company`, `organizer_email`, `organizer_phone_personal`, `organizer_memo`: 空でない文字列
  - その他、日時やステータス関連の必須項目

##### 5.1.3.3 バリデーション処理の使い分け
- **仮保存時（`in_draft`）**: 
  - `EventAppSchema`を使用してイベントオブジェクトを作成
  - デフォルト値で不足している項目を補完
  - Firestoreに保存する際も、`EventAppSchema`でパースされたデータをそのまま保存可能
- **予約申請時（`applying_reservation`への遷移）**: 
  - `Event.isValidForDatabase(updateUserId)`メソッドで`EventDbSchema`によるバリデーションを実行
  - バリデーション成功時のみ`Event.toFirestore(updateUserId)`で`EventDbSchema`にパースして保存
  - バリデーション失敗時はエラーを表示し、ステータス遷移を阻止（`in_draft`のまま）

#### 5.1.4 イベントIDの生成方法
- **新規イベント作成時（仮保存時）**:
  - Firestoreの`doc(collection(db, 'communities', community_id, 'events')).id`を使用してイベントIDを自動生成
  - 既存のイベント作成方法と同じ方式を使用
  - 生成されたIDは`event_id`フィールドに設定
- **既存イベント編集時**:
  - `route.query.id`から既存のイベントIDを取得
  - 新規IDは生成せず、既存のイベントを更新

#### 5.1.5 カバー画像の扱い
- **仮保存時**:
  - コミュニティのカバー画像（`community_cover_image_url`）をそのまま`event_cover_url`にコピー
  - 画像のアップロード処理は不要
  - `EventAppSchema`のデフォルト値（空文字）ではなく、コミュニティ画像を明示的に設定
- **予約申請時**:
  - `EventDbSchema`で`event_cover_url`が必須のURL形式としてバリデーションされる
  - 仮保存時にコミュニティ画像を設定しているため、バリデーションを通過可能

### 5.2 Firestoreフロントエンド処理
- **データ更新処理**: 基本情報入力時に仮保存実行（`in_draft`ステータスで保存）
- **バリデーション処理**: `applying_reservation`への遷移時に`EventDbSchema`による必須データチェック
- **リアルタイム監視**: イベントステータスの変更を監視
- **エラーハンドリング**: 保存失敗時のリトライ機能

### 5.4 処理フロー

#### 5.4.1 仮保存処理フロー（新規イベント作成時）
1. ユーザーが基本情報（日時・場所）を入力
2. フォームバリデーション実行（基本情報のみ）
3. イベントIDを生成
   - `doc(collection(db, 'communities', community_id, 'events')).id`でFirestoreが自動生成するIDを使用
4. 仮保存用データを構築
   - `Event`クラスのコンストラクタで`EventAppSchema`を使用
   - デフォルト値で不足している項目を自動補完
   - `event_status.value`を`'in_draft'`に設定
   - `event_cover_url`にコミュニティのカバー画像（`community_cover_image_url`）をコピー
5. Firestoreにイベントドキュメント作成
   - `EventAppSchema`でパースされたデータをそのまま保存
   - `EventDbSchema`による厳格なバリデーションは実行しない
6. 成功通知を表示
7. 次のステップ（飲食店選択）に遷移

#### 5.4.3 既存イベント編集時の処理フロー
1. `route.query.id`から既存のイベントIDを取得
2. 既存イベントのデータを読み込み
3. ユーザーが基本情報を編集
4. 「次へ」ボタンを押下
   - **保存処理は実行しない**
   - 次のステップ（飲食店選択）に遷移のみ
5. 各ステップでの編集内容は、最終的な「下書き保存」または「予約申請実行」時に保存される

#### 5.4.2 予約申請処理フロー（`applying_reservation`への遷移）
1. ユーザーが「予約申請」ボタンを押下
2. `Event.isValidForDatabase(updateUserId)`で`EventDbSchema`による全必須データのバリデーション実行
   - `EventDbSchema.safeParse()`を使用してバリデーション
   - 必須項目が不足している場合はバリデーション失敗
3. バリデーション成功時:
   - `event_status.value`を`'applying_reservation'`に更新
   - `Event.toFirestore(updateUserId)`で`EventDbSchema`にパースしてFirestoreに保存
   - 成功通知を表示
4. バリデーション失敗時:
   - エラーメッセージを表示
   - ステータス遷移を阻止（`in_draft`のまま）
   - 不足している必須項目をユーザーに提示
