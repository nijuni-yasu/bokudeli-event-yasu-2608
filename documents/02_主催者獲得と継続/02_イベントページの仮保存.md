# イベントページの仮保存機能

## 1. 概要

### 1.1 機能の目的
イベントページ作成・編集時のユーザー入力ストレスを軽減し、離脱によるデータ損失を防ぐために、以下の2つの仮保存体験を提供する。

- **新規作成時**: 店舗とメニューが確定したタイミング（メニュー選択画面）で、デフォルト値を含む仮保存を自動で行う。
- **編集時**: 各ステップで「保存する」ボタンをいつでも押下でき、現在の入力内容を `in_draft` ステータスのまま保存できる。

### 1.2 主要な機能
- **新規作成時の自動仮保存**: メニュー選択画面で「保存して進む」を押下したタイミングで、未入力項目をデフォルト値で補完したイベントを `in_draft` ステータスで Firestore に新規作成する。
- **編集時の任意保存**: `EventEditStepNav` を二段組にし、下段に「保存する」ボタンを常設。Step 1〜4 のいずれでも、ステップごとの保存可否条件を満たしているとき、現在の入力をそのまま `in_draft` のまま Firestore に書き戻す。
- **予約申請時の厳格バリデーション**: 予約申請（`applying_reservation` への遷移）時にのみ、店舗連絡用の主催者情報（`organizer_*`）を必須項目としてバリデーションする。
- **コミュニティカバー画像の自動コピー**: 仮保存時に、Cloud Functions Callable（`copyCommunityCoverToEvent`）経由でコミュニティのカバー画像をイベントのカバー画像パスへサーバーサイドコピーし、`event_cover_url` を生成する。

### 1.3 対象ユーザー
- イベント主催者
- コミュニティ管理者

編集時（`props.eventId != null` の場合）は、Step 1〜4 すべてで `EventEditStepNav` を二段組にし、下段「保存する」ボタンをいつでも押下できる。

### 4.2 UI 要素

#### 4.2.1 `EventEditStepNav` の二段組化

`EventEditStepNav.vue` に新しい slot 構造を追加する。既存の単一 slot は維持しつつ、二段表示用の `secondary` slot を追加し、各ステップで以下のように使い分ける。

```
┌──────────────────────────────────────────────┐
│  [ 戻る ]   [ 次へ / 保存して進む ]            │ ← 上段（既存 default slot）
│           [ 保存する ]                        │ ← 下段（新規 secondary slot、編集時のみ）
└──────────────────────────────────────────────┘
```

- 上段: ステップごとの主要アクション（戻る、進む、保存して進む）
- 下段: 任意保存用「保存する」ボタン（編集モードのみ表示）

CSS は `EventShopNotice.vue` の `event-shop-notice-footer__stack` パターンを `EventEditStepNav` 内に共通化する。

#### 4.2.2 「保存する」ボタンの実装場所

「保存する」ボタンの表示・押下処理は、各子コンポーネント（`EventBasicInfoCard.vue`, `EventShop.vue`, `EventMenu.vue`, `EventDetailCard.vue`）には実装せず、**親（`EventEdit.vue`）に集約**する。

- 各子コンポーネントは「ステップごとの保存可否条件（後述）」を親に通知する責務のみを持つ（`v-model` で `event` を編集、または props で valid 状態を共有）。
- `EventEdit.vue` が `EventEditStepNav` の `secondary` slot に「保存する」ボタンを差し込み、押下時に保存ハンドラを呼ぶ。
- これにより、子コンポーネントにビジネスロジック（Firestore 書き込み、画像コピー等）を持ち込まない。

なお、現状コードでは `EventShop.vue` / `EventMenu.vue` / `EventShopNotice.vue` が自身で `EventEditStepNav` を Teleport している。本仕様の実装にあたり、**`EventEdit.vue` 側で `EventEditStepNav` を一元管理する形にリファクタリング**する。

#### 4.2.3 ステップごとのボタン表示ルール

| Step | 画面 | 上段（左） | 上段（右） | 下段（編集時のみ） |
| :-- | :-- | :-- | :-- | :-- |
| 1 | 基本情報入力 | （なし） | 「次へ」 | 「保存する」※1 |
| 2 | 店舗選択 | 「戻る」 | 「次へ」 | 「保存する」※1 |
| 3 | メニュー選択 | 「戻る」 | 新規:「保存して進む」<br>編集:「次へ」 | 「保存する」※1 |
| 4 | イベント詳細入力 | 「戻る」 | 「次へ」 | 「保存する」※1 |
| 5 | 店舗連絡事項 | 「戻る」 | 「保存」 | 「予約申請」※2（既存） |

- ※1 「保存する」ボタンは **既に Firestore にイベントが存在する状態（編集モード）でのみ表示**する。新規作成時は Step 3 の「保存して進む」が押されるまでは表示しない。
- ※2 Step 5 の下段「予約申請」は既存実装どおり維持する。

#### 4.2.4 「保存する」ボタンの表示・活性条件

- **表示条件**: `event.event_id` が既に存在する（＝Firestore に保存済みのイベントである）こと。
  - 新規作成時に Step 1〜2 では非表示。
  - Step 3 の「保存して進む」を押した直後から、Step 4 で表示される。
  - 既存イベント編集時は Step 1 から表示される。
- **押下可否（disabled 制御）**: 当該ステップの保存可否条件を満たしているとき有効、満たさないとき disabled。条件はステップごとに以下のとおり。

| Step | 押下可否条件 |
| :-- | :-- |
| 1 | `v-form` の `isValid1`（既存）が `true` |
| 2 | `event.shop_id !== ''`（店舗が選択済み） |
| 3 | `selectedCount > 0`（メニューが1つ以上選択されている） |
| 4 | `v-form` の `isValid4`（既存）が `true` |

- **ステータス制限**: ステータスが `in_draft` のときのみ有効。`applying_reservation` 以降では子コンポーネント側で各入力フィールドが readonly になるため、整合性を保つため「保存する」ボタンも非表示または disabled とする。

#### 4.2.5 通知・エラー表示

通知は `base/src/composable/notification.ts` の `useNotification().show(message, color)` を使用してスナックバー（`v-snackbar`、レイアウトに既配置）で表示する。

- 仮保存 完了通知（`color: 'success'`）
- 仮保存 エラー通知（`color: 'error'`）
- カバー画像コピー エラー通知（`color: 'error'`、ステップ遷移を阻止）
- 予約申請時のバリデーションエラー（不足している主催者情報を提示、ダイアログ表示は既存の `confirm-dialog` を流用）

なお、既存の `EventEdit.vue` は `confirm-dialog` ベースの `showAlertDialog` で通知している箇所があるが、本仕様で追加する「仮保存」「保存する」関連の通知は **`useNotification` ベースのスナックバー**に統一する。

## 5. 技術仕様・データ構造設計

### 5.1 Firestore スキーマ

#### 5.1.1 ステータス設計

- **`in_draft`**: 下書き中
  - 必須データが揃っていなくても保存可能
  - 仮保存・編集時の任意保存はこのステータスで保存
  - 編集可能な状態
- **`applying_reservation`**: 予約申請中
  - `EventDbSchema`（後述）に加えて `ReservationRequiredSchema` を満たしている必要がある
  - `in_draft` から `applying_reservation` への遷移時にバリデーションを実行

#### 5.1.2 データ構造（`in_draft` 時）

```typescript
// イベントドキュメント（in_draft時）
interface EventDraft {
  // ステータス
  event_status: {
    value: 'in_draft'
    shop_comment?: string
  }

  // 基本情報
  event_start_datetime: Timestamp
  event_end_datetime: Timestamp
  event_postalcode: string
  event_address_base: string
  event_address_detail: string

  // 店舗情報（Step 3 仮保存時に確定）
  shop_id: string
  partner_id: string
  shop_name: string
  event_deadline_datetime: Timestamp

  // デフォルト値で初期化される項目
  event_name: string         // "[コミュニティ名]のイベント"
  event_cover_url: string    // コミュニティカバー画像を Storage コピーして生成
  event_desc: string         // "[コミュニティ名]のイベント"
  event_payment: 'user_advance'
  event_max_people: number   // デフォルト 25
```

#### 5.1.3 Zod スキーマ設計（`common/src/schemas/Event.ts`）

##### 5.1.3.1 EventAppSchema（イベントオブジェクト構築用）
- **用途**: `Event` クラスのコンストラクタで使用。デフォルト値で不足項目を補完する。
- **特徴**: 既存仕様どおり、ほぼ全項目に `default('')` または具体的なデフォルト値を持つ。仕様変更なし。

##### 5.1.3.2 EventDbSchema（Firestore 保存用、緩いバリデーション）
- **用途**: Firestore への保存時に適用されるスキーマ。
- **方針**: 主催者情報（`organizer_*`）を optional に変更し、`in_draft` 状態でも保存できるようにする。
- **変更点**（既存スキーマからの差分）:

```typescript
export const EventDbSchema = z.object({
  // ... 既存の必須項目はそのまま ...

  // 変更: nonempty() → optional() に緩和
  organizer_fullname: NonEmptyStringSchema.optional(),
  organizer_company: NonEmptyStringSchema.optional(),
  organizer_email: NonEmptyStringSchema.optional(),
  organizer_phone_personal: NonEmptyStringSchema.optional(),
  organizer_memo: NonEmptyStringSchema.optional(),

  // ... その他は既存どおり ...
})
```

- 上記以外の項目（`event_id`, `community_id`, `event_postalcode`, `shop_id`, `event_cover_url` など）は引き続き `nonempty()` / `regex()` などの厳格バリデーションを維持する。
  - 仮保存タイミング（Step 3）には店舗が選択済み・カバー画像がコピー済みなので、これらは満たされる。

##### 5.1.3.3 ReservationRequiredSchema（予約申請用、追加バリデーション）

- **用途**: `applying_reservation` への遷移時に、主催者情報の必須化チェックを行う。
- **方針**: `EventDbSchema` を緩めた分の必須項目を、追加スキーマとして定義する。

```typescript
const ReservationRequiredSchema = z.object({
  organizer_fullname: z.string().nonempty(),
  organizer_company: z.string().nonempty(),
  organizer_email: z.string().nonempty(),
  organizer_phone_personal: z.string().nonempty(),
  organizer_memo: z.string().nonempty(),
})
```

##### 5.1.3.4 `Event` クラスのメソッド

```typescript
// 既存
isValidForDatabase(updateUserId: string): boolean {
  return EventDbSchema.safeParse(convertToDb(this, updateUserId)).success
}

// 新規追加: 予約申請可否のチェック
isValidForReservation(updateUserId: string): { ok: true } | { ok: false; missing: string[] } {
  const dbResult = EventDbSchema.safeParse(convertToDb(this, updateUserId))
  if (!dbResult.success) {
    return { ok: false, missing: dbResult.error.issues.map((i) => i.path.join('.')) }
  }
  // organizer_* のみを明示的に取り出してパースし、Event クラスの他フィールドの影響を排除する
  const reservationResult = ReservationRequiredSchema.safeParse({
    organizer_fullname: this.organizer_fullname,
    organizer_company: this.organizer_company,
    organizer_email: this.organizer_email,
    organizer_phone_personal: this.organizer_phone_personal,
    organizer_memo: this.organizer_memo,
  })
  if (!reservationResult.success) {
    return { ok: false, missing: reservationResult.error.issues.map((i) => i.path.join('.')) }
  }
  return { ok: true }
}
```

##### 5.1.3.5 バリデーション処理の使い分け

| タイミング | スキーマ | 役割 |
| :-- | :-- | :-- |
| Step 3 仮保存（`in_draft`） | `EventDbSchema`（緩和後） | Firestore 書き込み可否 |
| 編集時「保存する」（`in_draft` 維持） | `EventDbSchema`（緩和後） | 同上 |
| 予約申請（`applying_reservation` 遷移） | `EventDbSchema` + `ReservationRequiredSchema` | 主催者情報を含む全必須項目の確認 |

#### 5.1.4 イベント ID の生成方法

- **新規イベント作成時（仮保存時）**:
  - Firestore の `doc(collection(db, 'communities', community_id, 'events')).id` を使用してイベント ID を自動生成
  - 既存の `BokudeliEvent` コンストラクタ内で行われる方式を踏襲
  - 生成された ID は `event_id` フィールドに設定
- **既存イベント編集時**:
  - `props.eventId` から既存のイベント ID を取得
  - 新規 ID は生成せず、既存のイベントを更新

#### 5.1.5 カバー画像の扱い

##### 5.1.5.1 仮保存時（新規作成時、Step 3 のタイミング）

コミュニティのカバー画像（Storage パス: `communities/{community_id}/community/cover`）を、イベントのカバー画像パス（`communities/{community_id}/events/{event_id}/cover`）に **サーバーサイドでコピー**する。コピー成功後、フロントは `event_cover_url` を `convertStoragePathToURL(getEventCoverStoragePath(...))` で組み立てて Firestore に書き込む。

##### 5.1.5.2 コピー方式（Cloud Functions Callable・既存実装）

サーバーサイドコピーは既存の Callable Function `copyCommunityCoverToEvent` を流用する。

- Callable 定義: `functions/default/src/copyCommunityCoverToEvent.ts`
  - Admin SDK の `bucket.file(srcPath).copy(dstPath)` でストレージ間コピー
  - 認可: ログイン必須、かつコミュニティ `manager` ロール または グローバル `support` ユーザー
  - 失敗ケース:
    - コミュニティ未存在 → `not-found`
    - 権限不足 → `permission-denied`
    - 既存イベントが別コミュニティに属している → `failed-precondition`
    - コミュニティのカバー画像が Storage に存在しない → `not-found`
    - コピー処理失敗 → `internal`
- フロント API: `base/src/apis/copyCommunityCoverToEvent.ts`（`httpsCallable` を `firebase/functions` でラップ）
- 共通の引数型: `common/src/apis/copyCommunityCoverToEvent.ts`

```typescript
// common/src/apis/copyCommunityCoverToEvent.ts（既存）
export type CopyCommunityCoverToEventRequest = {
  communityId: string
  eventId: string
}
```

##### 5.1.5.3 仮保存処理での呼び出し（既存実装）

新規作成時の Storage コピーは、既に `createNewEvent`（`base/src/stores/event.ts`）に組み込み済み。

```typescript
// base/src/stores/event.ts（既存実装の抜粋）
if (coverImage == null) {
  // Callable でコミュニティカバーをコピー。
  // Storage にコミュニティカバーが無い場合は Callable が失敗し setDoc には進まない。
  await callCopyCommunityCoverToEvent({ communityId: community.id, eventId: event.id })
} else {
  await uploadImage(coverImage, getEventCoverStoragePath(community.id, event.id))
}
```

> 補足: `event.event_cover_url` の URL は、上記コピー後に `convertStoragePathToURL(getEventCoverStoragePath(...))` で算出した値を `Event` クラスに設定する想定。Storage パスからの URL 生成は既存の `convertStoragePathToURL`（`base/src/utils/storage.ts`）を流用する。

##### 5.1.5.4 失敗時の挙動とロールバック

- Callable Function が失敗した場合、`createNewEvent` は `await` でエラーを伝播するため `setDoc` には進まない。
- フロントは Callable の例外を捕捉し、スナックバーでエラー通知を行ってステップ遷移（Step 3 → Step 4）を阻止する。

ロールバック仕様:

| 失敗ポイント | Storage の状態 | Firestore の状態 | 対応 |
| :-- | :-- | :-- | :-- |
| `copyCommunityCoverToEvent` 失敗 | サーバー側で原子的に判定。`copy` 失敗時は宛先未作成 | 未書き込み | リトライ可能。サーバーログ（`createModuleLogger('copyCommunityCoverToEvent')`）を確認 |
| `setDoc` 失敗 | コピー済み | 未書き込み | 同 `event_id` での再試行で同 `dstPath` を上書きすれば整合する。孤立画像は許容（Phase 2 でクリーンアップ予定） |
| `updateEventMenus` 失敗 | コピー済み | 書き込み済み | Firestore のドキュメントは残す。再度「保存して進む」を押下すれば `setDoc` が再実行され、`updateEventMenus` も再試行される |

孤立画像（Firestore に紐付かない画像）は Cloud Storage 上に残るが、destPath が `events/{event_id}/cover` であるため、**同 event_id の再作成時に必ず上書き**される。完全な無効化は将来の Storage クリーンアップジョブで対応する（Phase 2）。

##### 5.1.5.5 失敗時のリトライ導線

- 「保存して進む」押下が失敗した場合、ユーザーは Step 3 に留まり、入力（Step 1〜3）は保持される。
- 同じ「保存して進む」ボタンで再試行可能。
- Callable から `not-found`（コミュニティ画像未設定）が返った場合は、コミュニティ設定画面への誘導を含むメッセージで通知する（i18n でメッセージを定義し、`code` ごとに分岐）。
- Callable から `permission-denied` が返った場合は、権限不足である旨を通知する。

##### 5.1.5.6 予約申請時の扱い

- 仮保存時に既に Storage コピー済みの URL が `event_cover_url` に設定されているため、`EventDbSchema` のバリデーションを通過する。
- ユーザーが Step 4（イベント詳細）でカバー画像を差し替えた場合は、既存の `eventStore.updateCoverImage(coverImage)` で上書き保存される（既存仕様維持）。

### 5.2 Firestore フロントエンド処理

#### 5.2.1 保存関数の責務分離

既存の `EventEdit.vue:saveDraft()` は新規作成と既存更新の双方を扱っており、本仕様で「画像コピー」「編集時の任意保存」が加わると責務が肥大化する。そこで以下の **3関数に分離**する。

| 関数 | 役割 | 呼び出し箇所 |
| :-- | :-- | :-- |
| `createEventDraft()` | Step 3「保存して進む」での新規作成。Storage 画像コピー → Firestore 新規作成 → メニュー作成。 | `EventEdit.vue` の Step 3 ハンドラ |
| `updateEventDraft()` | 編集時「保存する」または最終ステップ「保存」。`eventStore.updateEvent` + 必要に応じてメニュー更新・カバー画像差し替え。 | `EventEdit.vue` の各ステップ「保存する」ハンドラ、Step 5「保存」 |
| `submitReservation()` | Step 5「予約申請」。`isValidForReservation` バリデーション → ステータス遷移 → 保存。 | `EventEdit.vue` の Step 5「予約申請」ハンドラ |

`createEventDraft` の処理内容は §5.4.1、`updateEventDraft` は §5.4.2、`submitReservation` は §5.4.4 を参照。

#### 5.2.2 ローディング状態の一元化

既存の `isSubmitting`、`isReserveMailing` に加えて「保存する」用の状態を個別に持つと、複数の非同期処理が競合した際に先祖返りを起こすリスクがある。本仕様では、以下のように **単一のステート**で管理する。

```typescript
type ProcessingState = null | 'creating' | 'saving' | 'submitting' | 'reserving'
const processingState = ref<ProcessingState>(null)

const isProcessing = computed(() => processingState.value != null)
```

- `null`: 待機中
- `'creating'`: Step 3 「保存して進む」処理中
- `'saving'`: 「保存する」処理中
- `'submitting'`: Step 5 「保存」（既存）処理中
- `'reserving'`: Step 5 「予約申請」（既存）処理中

各ボタンは `isProcessing` と「自身が押されたかどうか」を組み合わせて活性／ローディングを表示する（既存の `:loading="..."` パターンを踏襲）。

#### 5.2.3 通知

成功・失敗通知は `useNotification().show(message, color)` を使用する。

```typescript
import { useNotification } from '@shokujii/base/composable/notification'

const { show: showNotification } = useNotification()

showNotification('仮保存しました', 'success')
showNotification('保存に失敗しました', 'error')
```

#### 5.2.4 バリデーション処理

- 各ステップ内で保存可否条件（§4.2.4）を `computed` で判定し、「保存する」ボタンの disabled に渡す。
- 予約申請時に `Event.isValidForReservation()` を呼び、不足項目があればダイアログで提示する。

### 5.3 Functions 設計

本仕様で利用する Callable Functions は以下のとおり。いずれも **既存実装を流用**し、本仕様のために新規 Function を追加することはない。

| Callable | 用途 | 入出力 | 認可 |
| :-- | :-- | :-- | :-- |
| `copyCommunityCoverToEvent` | 仮保存時、コミュニティカバー画像をイベントカバー画像パスへ Storage コピー | `{ communityId, eventId } -> void` | ログイン必須、コミュニティ `manager` または `support` ユーザー |
| `updateEventMenus` | 仮保存・編集時、イベントに紐づくメニューサブコレクションを更新 | 既存仕様どおり | 既存仕様どおり |

Callable のエラーは `firebase/functions` の `FirebaseError` として伝播するので、フロントでは `error.code`（`not-found` / `permission-denied` / `failed-precondition` / `internal` 等）で分岐し、メッセージを切り替える。

### 5.4 処理フロー

#### 5.4.1 `createEventDraft()` フロー（Step 3「保存して進む」）

1. Step 3 で「保存して進む」ボタンが押下される（押下可否: `selectedCount > 0`）。
2. `processingState` を `'creating'` に変更。
3. `event` のデフォルト値を補完
   - `Event` クラスのコンストラクタで `EventAppSchema` を通してデフォルト値を補完済み
   - `event_status.value` が `'in_draft'`、`event_name`、`event_desc` がコミュニティ名ベース
4. `event.event_cover_url` を `convertStoragePathToURL(getEventCoverStoragePath(communityId, eventId))` で算出してセット（実体ファイルは次手順でサーバーがコピー）。
5. **コミュニティカバー画像を Cloud Functions でサーバーコピー**
   - `eventStore.createNewEvent(event, null)` を呼び出す（`coverImage == null` の経路）。
   - 内部で `copyCommunityCoverToEvent({ communityId, eventId })` Callable が呼ばれ、コピー失敗時は例外が伝播して以降の `setDoc` は実行されない。
   - 失敗時はスナックバーでエラー通知し、`processingState` を `null` に戻して終了（ステップ遷移しない）。
6. Firestore にイベントドキュメントを新規作成
   - `createNewEvent` 内で `withConverter(eventConverter)` 経由の `setDoc` が実行される（`EventDbSchema` でパースされ全フィールドが書き込まれる）。
   - メニューを `updateEventMenus(eventId, communityId, selectedMenuIds)` で作成。
7. 成功通知をスナックバーで表示。
8. `processingState` を `null` に戻す。
9. 次のステップ（Step 4 イベント詳細）に遷移。

> 備考: 既存の `createNewEvent`（`base/src/stores/event.ts`）を流用する。同関数は既に `coverImage == null` のときに `copyCommunityCoverToEvent` Callable を呼び出す実装になっているため、フロント側で追加のコピーロジックは持たない。

#### 5.4.2 `updateEventDraft()` フロー（編集時の任意保存）

1. ユーザーが Step 1〜4 の任意のステップで「保存する」ボタンを押下する（押下可否: §4.2.4 の表に従う）。
2. `processingState` を `'saving'` に変更。
3. `event.event_status.value` は `in_draft` のまま維持（ステータス遷移しない）。
4. `eventStore.updateEvent(event)` で Firestore を更新
   - 既存の `withConverter(eventConverter)` 経由のため全フィールドが書き戻される。
5. 必要に応じて副次的な更新を実行
   - Step 3 で押された場合: `updateEventMenus(eventId, communityId, selectedMenuIds)` を呼ぶ
   - Step 4 でカバー画像が差し替えられている場合: `eventStore.updateCoverImage(coverImage)` を呼ぶ（既存仕様）
6. 成功通知をスナックバーで表示。
7. `processingState` を `null` に戻す。
8. ステップ遷移はしない（その場に留まる）。
9. 失敗時はスナックバーでエラー通知し、`processingState` を `null` に戻す。

#### 5.4.3 既存イベント編集時の Step 遷移ボタン

1. `props.eventId` から既存のイベント ID を取得し、`useEventStore` で読み込み（既存仕様）。
2. ユーザーが各ステップで編集。
3. 上段の「次へ」「戻る」ボタン
   - **保存処理は実行しない**（既存仕様維持）
   - 次／前のステップに遷移のみ
4. 下段の「保存する」ボタン
   - 押下時に `updateEventDraft()` を呼ぶ
   - その場に留まる
5. 最終的な「予約申請」または Step 5 での「保存」は既存仕様どおり（§5.4.4 / 既存 `submit`）。

#### 5.4.4 `submitReservation()` フロー（`applying_reservation` への遷移）

1. ユーザーが Step 5 で「予約申請」ボタンを押下。
2. `processingState` を `'reserving'` に変更。
3. `Event.isValidForReservation(updateUserId)` を実行
   - `EventDbSchema.safeParse()` で全 DB 必須項目を確認
   - `ReservationRequiredSchema.safeParse({...organizer_*})` で `organizer_*` を確認
4. バリデーション成功時:
   - `event_status.value` を `'applying_reservation'` に更新
   - `eventStore.updateEvent(event)` で Firestore に保存（`withConverter` 経由）
   - 成功通知を表示
5. バリデーション失敗時:
   - `confirm-dialog` で「XXX が入力されていません」と不足項目を提示
   - ステータス遷移を阻止（`in_draft` のまま）
   - ユーザーに該当ステップへの遷移を促す
6. `processingState` を `null` に戻す。

## 7. 実装上の注意事項

### 7.1 規約遵守

- 文字列の falsy チェック禁止: `if (!str)` ではなく `if (str === '')` または `str == null` を使用
- DB 操作は必ず `store` 経由（`withConverter` 付き ref を使用）
- `withConverter` + `set` で更新する際は、`eventStore.event` がリアルタイム購読されていることを確認したうえで利用
- `defineEmits` は最新型構文（例: `defineEmits<{ save: []; }>()`）

### 7.2 並行処理・競合対策

- `processingState` で全保存処理を一元化し、複数ボタン同時押しを防ぐ
- 「保存する」ボタンは `isProcessing === false` のときのみ活性

### 7.3 Callable のエラーハンドリング

- 画像コピーは Cloud Functions 経由のため、フロントから Storage を直接 `fetch` する処理は持たない（CORS 設定の懸念は対象外）。
- Callable のエラーは `error.code` で分岐し、ユーザー向けメッセージを切り替える（`not-found` / `permission-denied` / `failed-precondition` / `internal`）。
- サーバー側ログは Functions の `createModuleLogger('copyCommunityCoverToEvent')` で出力されるため、運用時は Cloud Logging で `module: copyCommunityCoverToEvent` フィルタを利用する。

### 7.4 既存仕様との関係

- 本仕様は `documents/02_主催者獲得と継続/02_イベントページの作成の初期値.md` の「`event_cover_url` をコミュニティ画像で初期化する」方針を、Storage コピーで具体化したもの。同仕様書とは矛盾せず、補強関係にある。
