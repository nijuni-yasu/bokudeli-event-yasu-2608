# イベントの最小催行人数設定・自動中止

> **正本**: PF 版（プラットフォーム版）の機能仕様。エンタープライズ版 MVP には含めず、PF 版で実装後に `enterprise` パッケージへマージする（`08_エンタープライズ_実装計画` Phase 2 参照）。本ドキュメントはエンプラ仕様書 `04_イベント管理` から移管した。

## 1. 概要
### 1.1 機能の目的
イベント主催者が最小催行人数を設定し、参加人数が不足した場合にイベントを自動的に中止する機能を提供する。

### 1.2 主要な機能
- 最小催行人数の設定・解除
- 判断タイミングの設定
- 自動的なイベント中止処理
- 参加者への返金処理

### 1.3 対象ユーザー
- イベント主催者（コミュニティ管理者）
- イベント参加者

## 2. ねらい
### 2.1 ビジネス目標
- 主催者のリスク軽減（参加人数不足による損失回避）
- イベント品質の維持（適切な規模での開催）

### 2.2 ユーザー価値
- **主催者**: 参加人数不足による損失リスクの軽減
- **参加者**: 適切な規模のイベントへの参加

### 2.3 成功指標（KPI）
- 最小催行人数設定イベントの開催率向上
- 主催者と参加者の満足度向上

## 3. 前提条件
### 3.1 技術的前提条件
- イベント作成・編集機能が実装済み
- **EventMemberOrder 設計**（`members/{uid}/member_orders` + `stripes`）が本番反映済みであること（`07_リファクタリング/05`）
- **イベント一括中止コア（Phase A）** が実装済みであること  
  正本: `documents/02_主催者獲得と継続/08_イベントキャンセル_参加者あり_返金.md` §5.4.1  
  （主催者手動中止 UI・`cancelEvent` 拡張 Phase B は **不要**）

### 3.2 ビジネス的前提条件
- イベントに注文期限（`event_deadline_datetime`）が設定されている
- 参加者の決済が完了している（自動中止・返金対象は `status === 'ordered'`）

### 3.3 依存関係
- イベント管理機能
- 一括中止コア（返金・通知）
- 通知機能（メール）

## 4. 画面仕様
### 4.1 画面遷移
イベント作成・編集画面 → 最小催行人数設定セクション

### 4.2 UI要素
- **最小催行人数設定トグル**: 設定する/設定しない
- **最小催行人数入力**: **1〜5 名**の整数（イベントごと）
- **判断タイミング選択**: 注文期限の **X 日前（1〜5 日前）**（イベントごと）
- **設定説明**: 機能の動作説明（判定ルール・デフォルト値・**1 回判定**・判断日以降の人数減少は対象外 — §4.3.2）

### 4.3 設定の編集可能ステータス

| `event_status.value`（raw） | 最小催行設定の編集 |
|:--|:--|
| `in_draft` | 可 |
| `applying_reservation` | 可 |
| `accepting_order` 以降 | **不可**（設定済みなら表示のみ） |

### 4.4 参加者向け表示（イベント詳細ページ）

`minimum_participants.enabled === true` のとき、**user / enterprise** のイベント詳細に次を表示する（`base` コンポーネント共通化推奨）。

- 最小催行人数（`count` 名）
- 自動判定日時（`judgment_datetime` を参加者向け日時表示）
- **Phase 1 判定ルールの説明**（§4.3.2 の文言をそのまま利用。i18n キー化）

表示例（デフォルト相当）:

> このイベントは、**注文期限の 1 日前**の時点で参加者が **3 名未満**の場合、自動的に中止されます。  
> 判定は **その日時 1 回のみ** 行います。判定日以降に参加者が減っても、自動では中止されません。

### 4.5 デフォルト値と判定ルール（product）

#### 4.5.1 トグル ON 時の UI 初期値

主催者が「最小催行人数を設定する」を **初めて ON にしたとき**（当該イベントに未保存の場合）、入力欄には次を表示する。

| 項目 | デフォルト |
|:--|:--|
| `count` | **3**（名） |
| `judgment_days_before` | **1**（注文期限の 1 日前） |

文言例: 「**注文期限の 1 日前**の時点で、参加者が **3 人未満**ならイベントを自動中止します（**2 人以下**のとき中止）。」

既に `minimum_participants` が保存済みのイベントを編集するときは **保存値を表示**（デフォルトで上書きしない）。

#### 4.5.2 判定ルール（Phase 1 — モデル A: 判断日 1 回のみ）

- **評価タイミング**: `judgment_datetime` を含む Scheduler の **1 分ウィンドウで 1 回だけ**（§5.5.1）。**注文期限での再チェックは Phase 2**（§6.2）。
- 比較対象: `event_num_members`（`status === 'ordered'` のユニーク人数。判定直前の `recalcEventMembers` 推奨）
- **`event_num_members` ≥ `count`** → 開催継続（自動中止しない）
- **`event_num_members` < `count`** → 自動中止（一括中止コア）
- **判断日以降**: 一度「継続」と評価したあと、注文期限前に人数が `count` 未満に減っても **Phase 1 では自動中止しない**（参加者・主催者向け文言で明記 — §4.4）

例（デフォルト `count = 3`）: 判断日時点で **0・1・2 人 → 中止**、**3 人以上 → 継続**（その後 2 人になっても Phase 1 では中止しない）。

#### 4.5.3 評価済みフラグ

- フィールド: `minimum_participants.judgment_evaluated_at`（評価完了日時。Db Timestamp / App epoch millis）
- Scheduled は **`judgment_evaluated_at` 未設定** かつ §5.5.1 の条件を満たすイベントのみ評価する
- 評価完了時（**中止・継続のいずれも**）必ず `judgment_evaluated_at` をセットし、**二重評価・二重メールを防ぐ**（コア冪等のみでは「継続」側を防げない）

#### 4.5.4 バリデーション（保存時）

| ルール | 内容 |
|:--|:--|
| `count` | 整数、**1 ≤ count ≤ 5** |
| `judgment_days_before` | 整数、**1 ≤ judgment_days_before ≤ 5** |
| `enabled === true` かつ算出 `judgment_datetime` | **`judgment_datetime < now` なら保存エラー**（即時判定・days の自動 clamp はしない） |
| `enabled === false` | `minimum_participants` を **ドキュメントから削除**（Db: `deleteField()`。`enabled: false` だけ残さない） |
| `count` と定員 | **`count` ≤ `event_max_people`**（満たさない場合は保存エラー） |

#### 4.5.5 `judgment_datetime` の算出（実装定義）

- 基準: `event_deadline_datetime`（注文期限の日時）
- Luxon **`Asia/Tokyo`**: `DateTime.fromMillis(deadline, { zone: 'Asia/Tokyo' }).minus({ days: judgment_days_before })`
- **分 truncate**: `pollingTask` / 注文期限メールと同様、**秒以下を切り捨て**て epoch を `judgment_datetime` に保存
- Scheduler 検索: 実行時刻の **1 分ウィンドウ** `[start, end)` と `judgment_datetime` の範囲一致（`orderDeadlineMail` の `getAcceptingOrderEventsByTime` パターン）
- 注文期限または `judgment_days_before` を変更したら **`judgment_datetime` を再計算**。`judgment_evaluated_at` は **クリアしない**（既評価イベントの再設定は Phase 1 では `accepting_order` 前のみ想定）

#### 4.5.6 予約申請中（`applying_reservation`）の扱い

- **設定の保存**: `in_draft` / `applying_reservation` で可（`judgment_datetime` も保存してよい）
- **Scheduled 評価**: **`event_status.value === 'accepting_order'` のみ**（予約申請中は評価しない）
- **キャッチアップ**: 受付開始後、初めて `accepting_order` となり、かつ `judgment_datetime` が既に過去で `judgment_evaluated_at` 未設定の場合 → **次回 Scheduled で 1 回評価**（受付開始直後の 1 分ウィンドウ）

## 5. 技術仕様・データ構造設計
### 5.1 Firestoreスキーマ
```typescript
// Eventスキーマに追加するフィールド
interface Event {
  // 既存フィールド...
  event_id: string;
  event_name: string;
  event_deadline_datetime: Timestamp;
  event_max_people: number;
  event_num_members: number;
  // ... その他の既存フィールド
  
  // 最小催行人数設定（新規追加）
  minimum_participants?: {
    enabled: boolean;           // 最小催行人数設定の有効/無効
    count: number;              // 最小催行人数（1-5）。開催に必要な人数（未満なら中止）
    judgment_days_before: number; // 判断日（注文期限のX日前、1-5）
    judgment_datetime: Timestamp; // 保存時に期限から算出（§4.5.5）
    judgment_evaluated_at?: Timestamp; // 判断日評価完了（未設定＝未評価）。中止・継続どちらでも 1 回だけセット
  };
}
```

> **`in_cart`**: 自動中止時も **変更しない**（`ordered` のみ一括 `canceled` + Event `event_canceled`。新規注文は既存ガードで不可）。`08_..._参加者あり_返金.md` §5.4.1。

### 5.2 Zodスキーマ定義
```typescript
export const MinimumParticipantsSchema = z.object({
  enabled: z.literal(true), // 保存時は enabled のみ true で書き込む。OFF はフィールドごと削除
  count: z.number().int().min(1).max(5),
  judgment_days_before: z.number().int().min(1).max(5),
  judgment_datetime: TimestampSchema,
  judgment_evaluated_at: TimestampSchema.optional(), // App: EpochMillisSchema.optional()
});

/** UI 初期値（トグル初回 ON 時）。実装: common 定数化を推奨 */
export const MINIMUM_PARTICIPANTS_DEFAULT_COUNT = 3;
export const MINIMUM_PARTICIPANTS_DEFAULT_JUDGMENT_DAYS_BEFORE = 1;

export const EventDbSchema = z.object({
  // 既存フィールド...
  minimum_participants: MinimumParticipantsSchema.optional(),
});
```

### 5.3 Firestoreフロントエンド処理
- **データ取得・更新**: イベント作成・編集（§4.3）で `minimum_participants` を読み書き
- **算出**: 保存時に `common` の judgment 算出関数で `judgment_datetime` を設定
- 自動判定そのものは **Scheduled のみ**（フロントで `event_num_members` を監視して中止しない）

### 5.4 Firestoreセキュリティルール
主催者による `minimum_participants` の書き込みは、既存のイベント更新権限（manager・編集可能ステータス）に合わせる。

#### 5.4.1 インデックス（`firestore.indexes.json`）

`collectionGroup`: **`events`**（既存の `event_deadline_datetime` クエリと同型）

| フィールド | 用途 |
|:--|:--|
| `is_deleted` | `== false` |
| `event_status.value` | `== 'accepting_order'` |
| `minimum_participants.enabled` | `== true` |
| `minimum_participants.judgment_datetime` | 範囲（ウィンドウ `[start, end)`） |

`judgment_evaluated_at` 未設定は Firestore の null クエリが弱いため、Phase 1 では **ウィンドウ取得後にアプリ側で `judgment_evaluated_at == null` を filter** してよい。件数増加時は評価済みで `enabled` を落とす等を検討。

**キャッチアップ用**（任意・同一 PR）: `accepting_order` + `enabled` + `judgment_datetime` `< now` + 未評価 — または Scheduled 内で別クエリ。

### 5.5 Functions設計

#### 5.5.0 キャンセル時のステータス（EventMemberOrder）

自動中止・返金処理では **EventMemberOrder** を操作する。

| 対象 | ステータス | 備考 |
|:--|:--|:--|
| `member_orders`（`ordered`） | `canceled` | 一括中止コアの対象 |
| `member_orders`（`in_cart`） | **変更なし** | 既存の期限切れ in_cart と同様に放置。`event_canceled` 後は新規決済不可 |
| `Event` ドキュメント | `event_canceled` | イベント全体の中止を示す（`member_orders` とは別値） |

> `member_orders.status` に `event_canceled` は**使わない**。イベント中止は Event 側の `event_status.value` で表現する。

#### 5.5.1 最小催行チェック（Scheduled）

- **関数名（例）**: `checkMinimumParticipants`（`pollingTask` から呼ぶ）
- **トリガー**: 毎分（§4.5.5 の 1 分ウィンドウ）

**対象イベント**（いずれかのクエリ + メモリ filter）:

1. **通常**: `judgment_datetime ∈ [start, end)`、`accepting_order`、`enabled`、`!judgment_evaluated_at`
2. **キャッチアップ**（§4.5.6）: `accepting_order`、`enabled`、`judgment_datetime < end`、`!judgment_evaluated_at`（受付開始後、判断日を過ぎたが未評価）

**処理**（各イベント）:

1. `recalcEventMembers`（推奨）
2. `event_num_members` **<** `count` → 一括中止コア（`initiator: 'minimum_participants'`、監査ログは中止時のみ）
3. それ以外 → 継続（中止しない）
4. **必ず** `minimum_participants.judgment_evaluated_at = now` を保存（中止・継続共通）

#### 5.5.2 定期実行処理

- `pollingTask` 内で §5.5.1 を実行（`orderDeadlineMail` と並列）

### 5.6 処理フロー
1. 主催者が `in_draft` / `applying_reservation` で設定を保存（OFF 時はフィールド削除）
2. 注文受付開始（`accepting_order`）後、Scheduled が §5.5.1 で **1 回だけ**評価
3. 不足時のみ一括中止コア（返金・**PF/エンプラとも参加者メール** — `08` §5.4.1）

## 7. 注意事項
### 7.1 既存システムへの影響
- イベント作成・編集画面のUI変更が必要
- イベントスキーマの拡張が必要
- 既存のイベントには影響なし（オプショナル機能）

### 7.2 運用考慮事項
- 判断日時のタイムゾーン考慮が必要（Asia/Tokyo）
- 返金処理の失敗時の再試行機能（Runbook 参照）
- Cloud Schedulerの定期実行管理（毎分実行）
- 通知配信の失敗時の再試行機能
- イベント削除時の処理（`judgment_datetime`の削除は不要）
- 定期実行処理の負荷管理（大量のイベントがある場合の考慮）
- 判断日はイベント設定の **1–5 日前**（`judgment_days_before`）から選び、主催者 UI からの直前キャンセル（Phase B 保留）とは product 上切り分けられる

### 7.3 セキュリティ考慮事項
- 最小催行人数設定の権限チェック
- 返金処理のセキュリティ（コアは Admin SDK のみ）
- 通知配信の認証・認可
