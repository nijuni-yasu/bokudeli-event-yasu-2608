# 主催自動化（ブレスト）

## 課題

- 主催者の作業を極力自動化したい
- 1 度設定を行ったらあとは「自分の注文」と「当日の受取」くらいにしたい
- 次回設定も面倒。何もしなくても勝手に始まる状態が望ましい
- 大きくは 2 つ「開催（イベント作成・予約申請・中止）の自動化」と「集客の自動化」
- 様々な確度のアイデアを集約し、後続の仕様化・優先度付けのたたき台とする
- **露出獲得（検索・PR・シェア）との対応表**: [13_成長・露出/01_露出獲得施策.md](../13_成長・露出/01_露出獲得施策.md)（集客 A-xx 等を開発・プロモーション施策にマッピング）

## 整理フレーム

### アプローチの 3 層

| 層 | 意味 | 例 |
| --- | --- | --- |
| **自動化** | 定型作業を機械が実行 | シリーズ自動生成、自動注文、告知スケジュール |
| **移譲** | 主催者以外（参加者・店舗・運営）へ再分配 | 受取当番制、店舗空き枠、参加者リクエスト |
| **消滅** | 構造を変えて作業自体をなくす | 定期参加サブスク、店舗先承認、公式オープンテーブル |

「何もしなくても勝手に始まる」に最も効くのは **消滅 / 移譲**。短期で効きやすいのは **自動化**（既存機能の延長）。

### 確度の定義

| 確度 | 意味 |
| --- | --- |
| **高** | 既存機能・仕様の延長、技術的・運用上の未知が少ない |
| **中** | 新概念または複数機能の組み合わせ、設計判断が必要 |
| **低** | 外部 API・法務・運用負荷が大きい、または効果検証が難しい |

### 仕様化の検討用メモ

- **自動化のデフォルト**: オプトイン / オプトアウトどちらか
- **失敗時**: 自動中止 vs 主催者確認 vs 延期
- **「勝手に始まる」の範囲**: 下書きまで / 予約申請まで / 公開まで
- **シリーズの粒度**: コミュニティ単位 vs イベントテンプレート単位

## 詳細メモ（初期ブレスト原文）

### 開催 — 初期アイデア

1. **イベント主催者のアカウント設定**（O-01）
   - どのユーザーが主催者か明示。現状は organizer 情報を手動入力
   - 複数人設定可。主催者は電話番号登録必須
   - 受取時に主催者電話へ連絡できれば OK

2. **最小催行人数**（O-02）→ [09](./09_イベントの最小催行人数設定・自動中止.md)

3. **自動予約申請・シリーズ**（O-03）
   - 次回予約の自動化、シリーズ ID、前回終了トリガー
   - 一括予約申請、設定済みなら自動オープン

4. **飲食店承認が遅い**（O-10）→ Twilio 電話通知

### 集客 — 初期アイデア

1. **他プラットフォーム投稿**（A-01）— 参加は shokujii のみ

2. **ともだち招待**（A-03）
   - 注文完了時、食事回数順・最大 10 名、チェックで選択
