# 仕様書追加のルール

## 1. 仕様書の基本ルール

### 1.1 ファイル命名規則
- **形式**: `{連番}_{機能名}.md`
- **例**: `01_請求書手数料.md`, `02_ユーザー決済手数料.md`
- **連番**: 01から始めて、機能の重要度や実装順序に応じて番号を振る

### 1.2 ディレクトリ構成
```
documents/
├── 00_仕様概要/          # プロジェクト全体の仕様
├── 01_マネタイズと決済/   # 収益化・決済関連
├── 02_主催者獲得/        # 主催者向け機能
├── 03_参加者獲得/        # 参加者向け機能
├── 04_飲食店向け/        # 店舗向け機能
├── 05_コミュニケーションと通知/ # 通知・コミュニケーション機能
└── 06_その他・オペレーション系機能/ # 運営・管理機能
```

### 1.3 仕様書の基本構成
各仕様書は以下の構成に従う：

```markdown
# {機能名称}

## 1. 概要
- 機能の目的と概要
- 解決する課題
- 期待される効果
- 対象ユーザー

## 2. ねらい
- ビジネス目標
- ユーザー価値
- KPI・成功指標

## 3. 前提条件
- 実装に必要な前提条件
- 依存する機能やシステム
- 制約事項

## 4. 画面仕様
- UI/UX設計
- 表示内容
- 操作フロー

## 5. 技術仕様・データ構造設計
- Firestoreデータベーススキーマ
- Functions設計
- 処理フロー

## 6. 実装優先度
- Phase 1（必須）
- Phase 2（将来対応）

## 7. 注意事項
- 制約事項
- 既存システムへの影響
- セキュリティ考慮事項
```

## 2. 各セクションの詳細ルール

### 2.1 概要セクション
- **必須項目**:
  - 機能の目的（1-2行）
  - 主要な機能（箇条書き）
  - 対象ユーザー
- **推奨項目**:
  - 類似機能との違い
  - 競合他社との差別化ポイント

### 2.2 ねらいセクション
- **必須項目**:
  - ビジネス目標（数値目標を含む）
  - ユーザー価値
- **推奨項目**:
  - 成功指標（KPI）
  - 測定方法

### 2.3 前提条件セクション
- **必須項目**:
  - 技術的前提条件
  - ビジネス的前提条件
  - 依存関係
- **推奨項目**:
  - 制約事項
  - リスク要因

### 2.4 画面仕様セクション
- **必須項目**:
  - 画面遷移図
  - 主要なUI要素
- **推奨項目**:
  - レスポンシブ対応
  - アクセシビリティ

### 2.5 技術仕様・データ構造設計セクション
- **必須項目**:
  - Firestoreスキーマ定義
  - 主要な処理フロー
- **推奨項目**:
  - Functions設計
  - エラーハンドリング
  - パフォーマンス考慮事項

### 2.6 実装優先度セクション
- **Phase 1（必須）**: MVPに必要な最小機能、ユーザビリティ向上機能
- **Phase 2（将来対応）**: 拡張・最適化機能

### 2.7 注意事項セクション
- **必須項目**:
  - 既存システムへの影響
  - セキュリティ考慮事項
- **推奨項目**:
  - 運用考慮事項
  - 将来の拡張性

## 3. 記述ルール

### 3.1 コード記述の基本ルール
- **TypeScriptスキーマ**: `common/src/schemas/`に配置し、zodを使用してバリデーションを定義
- **Functions**: `functions/default/src/`に配置し、適切な認証・権限チェックを実装
- **処理フロー**: ステップバイステップで明確に記述し、エラーハンドリングを含める

### 3.2 記述形式
- **スキーマ定義**: 必須フィールド、オプションフィールド、タイムスタンプを明確に分ける
- **Functions設計**: Callable/Trigger/Scheduledの種類を明記し、引数・戻り値・認証要件を記載
- **処理フロー**: 1. 2. 3. の形式で順序を明確にする

## 4. レビュー・更新ルール

### 4.1 仕様書レビュー
- 実装前に技術レビューを実施
- ビジネス要件との整合性確認
- セキュリティ・パフォーマンスの検証

### 4.2 仕様書更新
- 実装中に発見された課題は仕様書に反映
- 変更履歴を記録
- 関連する仕様書への影響を確認

### 4.3 バージョン管理
- 仕様書の変更はGitで管理
- 重要な変更はコミットメッセージで明記
- 実装完了後は仕様書を最終版として確定
