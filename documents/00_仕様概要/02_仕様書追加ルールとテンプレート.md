# 仕様書追加のルール

## 1. 仕様書の基本ルール

### 1.1 ファイル命名規則
- **形式**: `{連番}_{機能名}.md`
- **例**: `01_請求書手数料.md`, `02_ユーザー決済手数料.md`
- **連番**: 01から始めて、機能の重要度や実装順序に応じて番号を振る

### 1.2 ディレクトリ構成
```
documents/
├── 00_仕様概要/          # プロジェクト全体の仕様
├── 01_マネタイズと決済/   # 収益化・決済関連
├── 02_主催者獲得/        # 主催者向け機能
├── 03_参加者獲得/        # 参加者向け機能
├── 04_飲食店向け/        # 店舗向け機能
├── 05_コミュニケーションと通知/ # 通知・コミュニケーション機能
└── 06_その他・オペレーション系機能/ # 運営・管理機能
```

### 1.3 仕様書の基本構成
各仕様書は以下の構成に従う：

```markdown
# {機能名称}

## 1. 概要
- 機能の目的と概要
- 解決する課題
- 期待される効果
- 対象ユーザー

## 2. ねらい
- ビジネス目標
- ユーザー価値
- KPI・成功指標

## 3. 前提条件
- 実装に必要な前提条件
- 依存する機能やシステム
- 制約事項

## 4. 画面仕様
- UI/UX設計
- 表示内容
- 操作フロー

## 5. 技術仕様・データ構造設計
- Firestoreデータベーススキーマ
- Functions設計
- 処理フロー

## 6. 実装優先度
- Phase 1（必須）
- Phase 2（将来対応）

## 9. 注意事項
- 制約事項
- 既存システムへの影響
- セキュリティ考慮事項
```

  - 類似機能との違い

### 2.2 ねらいセクション
- **必須項目**:
  - ビジネス目標（数値目標を含む）
  - ユーザー価値
- **推奨項目**:
  - 成功指標（KPI）
  - 測定方法

### 2.3 前提条件セクション
- **必須項目**:
  - 技術的前提条件

- **推奨項目**:
  - 制約事項
  - リスク要因

### 2.4 画面仕様セクション
- **必須項目**:
  - 画面遷移図

  - レスポンシブ対応

## 3. 記述ルール

### 3.1 コード記述の基本ルール
- **TypeScriptスキーマ**: `common/src/schemas/`に配置し、zodを使用してバリデーションを定義
- **Functions**: `functions/default/src/`に配置し、適切な認証・権限チェックを実装
- **処理フロー**: ステップバイステップで明確に記述し、エラーハンドリングを含める

### 3.2 Firestoreスキーマ記述ルール
- **コレクション名**: 複数形で命名（例: `users`, `events`, `communities`, `orders`, `partners`）
- **ドキュメントID**: 用途に応じて適切な命名規則を採用
  - ユーザー関連: `{uid}`（Firebase Auth UID）
  - イベント関連: `{eventId}`（自動生成またはカスタムID）
  - その他: 用途に応じて適切なID戦略を採用
- **フィールド命名**: snake_caseで統一
- **必須フィールド**: `required`として明記
- **オプションフィールド**: `optional`として明記
- **タイムスタンプ**: `created_at`, `updated_at`を標準で含める
- **参照関係**: 他のコレクションへの参照は`{collection_name}_id`形式で命名
- **配列・オブジェクト**: ネストした構造の詳細を明記
- **データ型**: 各フィールドのデータ型を明確に記載（string, number, boolean, timestamp, array, object等）
- **制約条件**: 文字数制限、数値範囲、正規表現等の制約を明記

### 3.3 記述形式
- **スキーマ定義**: 必須フィールド、オプションフィールド、タイムスタンプを明確に分ける
- **Functions設計**: Callable/Trigger/Scheduledの種類を明記し、引数・戻り値・認証要件を記載
- **処理フロー**: 1. 2. 3. の形式で順序を明確にする
- **インデックス設計**: クエリパフォーマンスに必要なインデックスを明記
- **Zodスキーマ**: TypeScriptの型安全性を保つため、zodを使用したバリデーションスキーマを定義

## 4. レビュー・更新ルール

### 4.1 仕様書レビュー
- 実装前に技術レビューを実施
- ビジネス要件との整合性確認
- セキュリティ・パフォーマンスの検証

### 4.2 仕様書更新
- 実装中に発見された課題は仕様書に反映
- 変更履歴を記録
- 関連する仕様書への影響を確認

### 4.3 バージョン管理
- 仕様書の変更はGitで管理
- 重要な変更はコミットメッセージで明記
- 実装完了後は仕様書を最終版として確定

#### 5.1.3 Zodスキーマ定義
```typescript
// common/src/schemas/{schemaName}.ts
import { z } from 'zod';

export const {SchemaName}DbSchema = z.object({
  // データベーススキーマ（Firestoreから取得したデータの型定義）
  id: z.string(),
  field_name: z.string().min(1).max(100),  // 制約条件を含む
  optional_field: z.string().optional(),
  reference_id: z.string(),
  array_field: z.array(z.string()),
  object_field: z.object({
    nested_field: z.string(),
    nested_optional: z.string().optional(),
  }),
  created_at: z.date(),
  updated_at: z.date(),
});

// クラス定義
export class {SchemaName} {
  id: string = '';
  field_name: string = '';
  optional_field?: string;
  reference_id: string = '';
  array_field: string[] = [];
  object_field: { nested_field: string; nested_optional?: string } = { nested_field: '' };
  created_at: Date = new Date();
  updated_at: Date = new Date();
  
  // バリデーション
  validate(): boolean {
    return this.field_name.length > 0 && this.field_name.length <= 100;
  }
  
  // ファクトリメソッド
  static fromDb(data: any): {SchemaName} {
    const item = new {SchemaName}();
    item.id = data.id;
    item.field_name = data.field_name;
    item.optional_field = data.optional_field;
    item.reference_id = data.reference_id;
    item.array_field = data.array_field || [];
    item.object_field = data.object_field || { nested_field: '' };
    item.created_at = data.created_at.toDate();
    item.updated_at = data.updated_at.toDate();
    return item;
  }
}
```

### 5.5 Functions設計

**注意**: Functionsは必要最小限で使用し、フロントエンドから直接Firestoreを操作できる場合は直接操作を推奨します。Functionsは以下の場合にのみ使用してください：
- 複雑なビジネスロジックが必要な場合
- 外部APIとの連携が必要な場合
- セキュリティ上、サーバーサイドでの処理が必須な場合
- 複数のドキュメントを一貫性を保って更新する必要がある場合
- バッチ処理や定期実行が必要な場合

#### 5.5.1 Callable Functions（フロントエンドから呼び出し）
```typescript
// functions/default/src/apis/{functionName}.ts
export const {functionName} = onCall(async (request) => {
  // 認証チェック
  const uid = request.auth?.uid
  if (uid == null) {
    throw new HttpsError('unauthenticated', '認証が必要です')
  }
  
  // 引数の取得とバリデーション
  const { param1, param2 } = request.data
  if (!param1) {
    throw new HttpsError('invalid-argument', 'パラメータ1は必須です')
  }
  
  // ビジネスロジック実行
  const result = await executeBusinessLogic(param1, param2)
  
  // レスポンス返却
  return {
    success: true,
    data: result
  }
})
```

#### 5.5.2 Trigger Functions（自動実行）
```typescript
// functions/default/src/triggers/{functionName}.ts
export const {functionName} = onDocumentCreated(
  '{collectionName}/{documentId}',
  async (event) => {
    const data = event.data?.data()
    if (!data) return
    
    // 自動処理の実装
    await processAutomatically(data)
    
    console.log(`{functionName} executed for: ${data.id}`)
  }
)
```

#### 5.5.3 Scheduled Functions（定期実行）
```typescript
// functions/default/src/scheduled/{functionName}.ts
export const {functionName} = onSchedule(
  '{cronExpression}',  // 例: '0 2 * * *' (毎日午前2時)
  async () => {
    console.log('Starting {functionName}...')
    
    try {
      const result = await executeScheduledTask()
      console.log(`{functionName} completed: ${result}`)
    } catch (error) {
      console.error('{functionName} failed:', error)
    }
  }
)
```

### 5.6 処理フロー
#### 5.6.1 基本的な処理フロー
```markdown
### {機能名}の処理フロー
1. ユーザーが{画面名}で{操作}を実行
2. フロントエンドでバリデーション（{バリデーション内容}）
3. Callable Function `{functionName}`を呼び出し
4. Firebase Functionで認証チェック
5. 引数のバリデーション
6. {ビジネスロジック}実行
7. Trigger Function `{triggerFunctionName}`が自動実行（該当する場合）
8. {通知処理}（該当する場合）
9. レスポンスをフロントエンドに返却
10. フロントエンドで{結果表示}を実行
```

#### 5.6.2 エラーハンドリングを含む処理フロー
```markdown
### {機能名}の処理フロー（エラーハンドリング含む）
1. ユーザーが{画面名}で{操作}を実行
2. フロントエンドでバリデーション（{バリデーション内容}）
   - 失敗時: エラーメッセージを表示して処理を停止
3. Callable Function `{functionName}`を呼び出し
4. Firebase Functionで認証チェック
   - 失敗時: 認証エラーを返却
5. 引数のバリデーション
   - 失敗時: バリデーションエラーを返却
6. {ビジネスロジック}実行
   - 成功: 処理を継続
   - 失敗: ビジネスロジックエラーを返却
7. Trigger Function `{triggerFunctionName}`が自動実行（該当する場合）
   - 失敗時: ログに記録（ユーザー処理には影響しない）
8. {通知処理}（該当する場合）
   - 失敗時: ログに記録（ユーザー処理には影響しない）
9. レスポンスをフロントエンドに返却
10. フロントエンドで結果表示
    - 成功: {成功時の表示}
    - 失敗: {エラー時の表示}
```

## 6. データマイグレーション（必要な場合）
### 6.1 マイグレーション対象
スキーマに変更がある場合は、既存データのマイグレーション処理を実装する必要があります：

- **フィールド追加**: 新規フィールドのデフォルト値設定
- **フィールド削除**: 不要フィールドの削除
- **フィールド型変更**: データ型の変換処理
- **フィールド名変更**: リネーム処理
- **配列・オブジェクト構造変更**: ネスト構造の変更

### 6.2 マイグレーション実装
```typescript
// functions/default/src/migrations/{migrationName}.ts
export const migrate{CollectionName} = onCall(async (request) => {
  const uid = request.auth?.uid
  if (uid == null) {
    throw new HttpsError('unauthenticated', '認証が必要です')
  }
  
  // 管理者権限チェック
  const user = await getAdminUser(uid)
  if (!user.is_admin) {
    throw new HttpsError('permission-denied', '管理者権限が必要です')
  }
  
  try {
    const batch = db.batch()
    const snapshot = await db.collection('{collectionName}').get()
    
    snapshot.docs.forEach((doc) => {
      const data = doc.data()
      
      // マイグレーション処理
      const migratedData = {
        ...data,
        // 新規フィールドの追加
        new_field: data.old_field || 'default_value',
        // フィールド名の変更
        new_field_name: data.old_field_name,
        // データ型の変換
        converted_field: String(data.numeric_field),
        // タイムスタンプの更新
        updated_at: new Date()
      }
      
      // 不要フィールドの削除
      delete migratedData.old_field
      delete migratedData.old_field_name
      delete migratedData.numeric_field
      
      batch.update(doc.ref, migratedData)
    })
    
    await batch.commit()
    
    return {
      success: true,
      migrated_count: snapshot.docs.length
    }
  } catch (error) {
    console.error('Migration failed:', error)
    throw new HttpsError('internal', 'マイグレーション処理に失敗しました')
  }
})
```
