showAlertDialog($t('manage.event.reserve_validation_failed', { fields: reservationCheck.missing.join('、') }))

### 🟡 提案

**[imo] `updateEventDraft` に同一ロジックが2ブランチ重複している**  
`props.eventId != null` ブランチと `hasFirestoreDraft.value` ブランチで、`updateEvent` / `updateCoverImage` / `updateEventMenus` を呼ぶ処理がほぼ完全に重複している。`eventId` を先に決定してから一本化できる。

```typescript
// base/src/components/EventEdit.vue（現状）
if (props.eventId != null) {
  const eventStore = useEventStore(props.eventId) as EventStore
  await eventStore.updateEvent(event.value)
  ...
}
if (hasFirestoreDraft.value) {
  const eventStore = useEventStore(event.value.event_id) as EventStore
  await eventStore.updateEvent(event.value)
  ...
}

// 改善案
const eventId = props.eventId ?? (hasFirestoreDraft.value ? event.value.event_id : null)
if (eventId == null) return null
const eventStore = useEventStore(eventId) as EventStore
await eventStore.updateEvent(event.value)
...
```

**[imo] Step 5 の「保存する」ボタンに `event_edit.save_draft` を使っているが意味が異なる**  
Steps 1〜4 の「保存する」（`handleSecondarySave`）はその場で下書き保存してページ遷移しない。一方、Step 5 の同ラベルのボタン（`submit`）は保存後 `emits('updated')` で画面遷移する。同じラベルで挙動が異なるため UX 的に誤解を招く。Step 5 では別の i18n キー（例: `event_edit.save_event`「イベントを保存する」）を使うことを検討してほしい。

**[imo] Step 5 の保存ボタンと予約ボタンの `:disabled` ロジックが `isProcessing` を使わず個別比較になっている**  
`isProcessing` computed（`processingState != null` で全 state を網羅）は `secondarySaveDisabledForStep` 内でのみ使われており、Step 5 のボタン `:disabled` では `processingState === 'reserving'` / `'submitting'` と個別比較している。将来 `ProcessingState` に値が追加された場合に漏れが起きやすい。`isProcessing` で統一するか、少なくとも両ボタンの disabled に `isProcessing` を使う方が一貫性が高い。

### 🟢 任意

**[nits] `createEventDraft` 内の `newEvent.event_id !== ''` チェック**  
`createNewEvent` が返す `BokudeliEvent` の `event_id` は必ず UUID が入るため、`!== ''` よりも `newEvent.event_id !== ''` で問題はないが、PR 全体で `!= null` チェックと混在している。`event_id` が存在チェックの対象なら `newEvent.event_id != null && newEvent.event_id !== ''` もしくは `event_id` 生成保証が明示されているならチェック自体を削除してもよい。

**[fyi] `NonEmptyStringSchema.optional()` と既存データの空文字の組み合わせ**  
`NonEmptyStringSchema` は空文字 `""` を `FieldValue.delete()` に transform する実装のため、DB への書き込み時に空文字が残ることはない。`isValidForReservation` では `this.organizer_fullname`（AppSchema 側 = `string | undefined`）を参照しており、フィールドなし（`undefined`）を `z.string().min(1)` が正しく捕捉できる設計になっている。意図どおりの組み合わせであることを確認済み。
