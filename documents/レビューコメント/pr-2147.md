**レビュワー**: Copilot

**指摘箇所**: `functions/default/src/user.ts` — `confirmEmailRegistration`

**該当コード（レビュー時点の diff）**:

```ts
const [token] = await Promise.all([
  getAuth().createCustomToken(uid),
  deletePassCode(passCodeDocument.id),
  saveUser(new ShokujiiUser(uid, { user_email: email })),
])
```

**レビュワーのコメント（原文）**:

**[must] `functions/default/src/user.ts` — `confirmEmailRegistration` の部分失敗による不整合**

`createUser` 成功後に `Promise.all([createCustomToken, deletePassCode, saveUser])` を並列実行しているため、`saveUser` が失敗した場合に以下の不整合状態が発生します。

- Auth ユーザー: 作成済み（孤立）
- Firestore ユーザー: 未作成
- pass code: 削除済み（リトライ不可）

`deletePassCode` は `saveUser` が成功してから実行するよう順序を分けることを推奨します。

**コメント要約**: saveUser 失敗時も deletePassCode が並列で走り pass code が失われリトライ不能になる

**判断結果**: ✅ 対応済み

**PRスコープ**: 📌 スコープ内

**ラベル**: 🐛 実害

**変更種別**: 🔧 微修正

**想定工数**: S

**判断理由**: 指摘は妥当。RC-2 で createUser 失敗の already-exists は対応済みだが、createUser 成功後の saveUser 失敗時の pass code 削除順序は未対応。token 生成と saveUser を先に完了し deletePassCode は直列化すべき。

**対応**: saveUser 成功後に deletePassCode を実行するよう順序を変更。saveUser 失敗時は pass code 未削除を Vitest で検証。

`rejectNewUserOnLogin` の `user.delete()` が失敗した場合、catch ブロックで `return`（undefined）して `/login` へのナビゲーションを続行しますが、この時点で Auth セッション（削除失敗のアカウント）が残ったままです。

ログイン済み状態のまま `/login` に進むと、`isLoggedIn` ガードが `/` へリダイレクトし、その後 `updateProfileFromProviders` が Shokujii ユーザー未存在でエラーになる不整合フローになりえます。

delete が失敗してもベストエフォートで `signOut` を呼び、セッションをクリアする方が安全です。

**コメント要約**: RC-15 で helper 内 signOut をやめた結果、delete 失敗時にセッションが残りログイン済みガードと矛盾しうる

**判断結果**: ✅ 対応済み

**PRスコープ**: 📌 スコープ内

**ラベル**: 🐛 実害

**変更種別**: 🔧 微修正

**想定工数**: S

**判断理由**: RC-15 の意図（delete 失敗を成功扱いにしない）は維持しつつ、catch 側で best-effort signOut を追加するのが妥当。孤児 Auth は残るがログイン済み扱いの誤遷移は防げる。login.vue の DEV ポップアップ経路も同様。

**対応**: signOutBestEffort を authEntryGuards に追加。router / login.vue の rejectNewUserOnLogin catch から呼び出し。
