# テスト方針

## 現状の品質担保手法

現在、自動テスト（ユニットテスト・E2E テスト）はほぼ導入されていない。
代わりに以下の手法で品質を担保している。

| 手法 | 詳細 | CI 実行 |
|:--|:--|:--|
| TypeScript 型チェック | `vue-tsc --noEmit` / `tsc -b` | ビルド時に実行 |
| ESLint | `--max-warnings=0` で警告もエラー扱い | デプロイ時に実行 |
| Prettier | `format:check` でフォーマット統一 | デプロイ時に実行 |
| Zod スキーマバリデーション | `withConverter` 経由で Firestore 読み書き時にランタイム検証 | - |
| AI コードレビュー | `/shokujii-code-review` による PR 単位のレビュー | - |

## テスト手法の全体像と優先度

コストが低い（導入しやすい）ものから順に並べる。

```
コストが低い（導入しやすい）
  ↑
  │  ✅ 型チェック (TypeScript)        ← 導入済み
  │  ✅ Lint / Format                  ← 導入済み
  │  ✅ スキーマバリデーション (Zod)     ← 導入済み
  │  ── ここまでが今のライン ──
  │  ⬜ ユニットテスト (Vitest)
  │  ⬜ Playwright MCP（手動テストの代替）
  │  ⬜ インテグレーションテスト
  │  ⬜ E2E テスト (Playwright)
  │  ⬜ VRT（Visual Regression Test）
  ↓
コストが高い（維持が大変）
```

## 困りごと別の手法選定ガイド

| 困りごと | 向いている手法 | 具体例 |
|:--|:--|:--|
| ロジックのバグが怖い | ユニットテスト (Vitest) | 料金計算、日付処理、参加条件の判定 |
| リリース後に画面が壊れる | E2E テスト (Playwright) | ログイン → イベント参加の主要フロー |
| 手動確認が面倒 | Playwright MCP | 開発中の画面確認を Claude に任せる |
| デザイン崩れに気づけない | VRT (reg-suit 等) | スクリーンショット比較で差分検出 |
| Firestore ルールが不安 | エミュレータテスト | ルールの許可/拒否を自動検証 |

## 導入ステップ

段階的に導入する。いきなり全部入れず、効果が高くコストが低いものから始める。

### Step 1: common のユニットテスト（Vitest）

- Zod スキーマのバリデーション、ユーティリティ関数のテスト
- 依存が少なく書きやすい。壊れにくい
- Vitest は `functions/default` に基盤だけ入っているので横展開するだけ

### Step 2: functions/default のユニットテスト（Vitest）

- 料金計算、メール送信のロジック、Stripe 連携など
- ビジネスロジックのバグは影響が大きいので守る価値が高い

### Step 3: Playwright MCP の導入

- テストコードを書く必要がなく、すぐに使える
- 「ちゃんと動くか見て」を Claude に任せられる
- テストコードの資産にはならないが、開発中の確認作業を効率化できる
- 導入コマンド: `claude mcp add --transport stdio playwright -- npx -y @playwright/mcp@latest`

### Step 4: E2E テスト（Playwright テストコード）— 必要になったら

- 主要フロー（ログイン → イベント参加 → 決済）だけに絞って書く
- 維持コストが高いので「壊れたら困るフロー」に限定する
- CI に組み込むには Firebase エミュレータ環境の整備も必要になる

## TDD（テスト駆動開発）について

TDD（先にテストを書く → Red → Green → Refactor）は手法であってゴールではない。
このプロジェクトでは以下の順番で進める。

1. まず既存コードにテストを後付けして「テストがある状態」に慣れる
2. テストの恩恵を実感してから、新機能の開発時に TDD を試す

## 各手法の比較

| | ユニットテスト (Vitest) | Playwright MCP | E2E テスト (Playwright) |
|:--|:--|:--|:--|
| 書くもの | テストコード (.test.ts) | 自然言語の依頼 | テストコード (.spec.ts) |
| 実行 | CI で自動実行 | Claude Code との会話中 | CI で自動実行 |
| 再現性 | 高い（何度でも同じテスト） | 低い（毎回依頼が必要） | 高い |
| 用途 | ロジックのリグレッション防止 | 開発中の動作確認・探索的テスト | UI フローのリグレッション防止 |
| 維持コスト | 低い | なし | 高い |
