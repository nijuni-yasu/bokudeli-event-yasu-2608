# プロフィールタグ機能

## 1. 概要
### 1.1 機能の目的
ユーザーが自身の興味・関心をタグとして設定し、イベント参加者間での共通点を可視化することで、コミュニティ形成とユーザーエンゲージメントを促進する機能

### 1.2 主要な機能
- ユーザープロフィールでのタグ設定・管理（マスタタグ選択 + フリー入力の併用）
- イベント詳細での**参加者タグ集計**表示（`event_members_tags`）とタグ取り込み
- 共通タグのハイライト表示
- 他ユーザーのタグを自分のタグに取り込み機能（イベントページ・参加者一覧画面・プロフィールページ）
- **参加者一覧画面**（`/members`）での参加者個別タグ表示

### 1.3 対象ユーザー
- イベント参加者
- イベント主催者
- コミュニティ管理者

### 1.4 リリース方針（確定）

- **プロフィールタグ**と**イベントタグ**（[05_イベントタグ機能.md](./05_イベントタグ機能.md)）を **同一リリース（Phase 1）で同時公開** する
- 参加者向け（プロフィールタグ・参加者タグ表示・取り込み）と主催者向け（イベントタグ設定・カード表示）をセットで提供し、「設定 → 閲覧 → 取り込み」のループを初回リリース時点で完成させる
- タグ検索・フィルタ（[06_イベント検索（タグ検索・日付検索・場所検索）.md](./06_イベント検索（タグ検索・日付検索・場所検索）.md)）は **Phase 1 同時リリースの対象外**（Phase 2 以降）

### 1.5 スコープ外（確定・Phase 1 では実装しない）

| 項目 | 理由 |
| --- | --- |
| **want / give**（探している人・できることの2軸） | 食事コミュニティのトーンと合わず、入力・マッチングの複雑さが増す。単一の興味タグリストで十分 |
| **質問形式の誘導**（「好きなスポーツは？」等の必須／構造化フォーム） | 出会い系アプリに見えやすく、Shokujii の主目的（食事イベント参加）からズレる。フリー入力の placeholder とマスタタグ選択・タグ取り込みで誘導する |
| **カート画面でのタグ必須設定**（主催者が「最低 N 個設定してね」を指定） | 参加 CVR を下げる。Phase 2 以降、タグ設定率の計測後にソフト誘導から検討 |
| **参加者一覧の「フード／共通／全て」タブ切り替え** | Phase 1 では `/members` で全件表示 + 共通タグ優先ソートで十分 |
| **イベントカードへの参加者タグ・プロフィールタグ表示** | ノイズになる。カードはイベントタグのみ（[05_イベントタグ機能.md](./05_イベントタグ機能.md) 参照） |
| **イベント詳細の「参加者別のタグを見る」専用導線** | 既存の「参加者プロフィール」→ `/members` で十分。集計見出し横の追加リンクは設けない |
| **マスタタグ廃止（フリータグのみ）** | 表記揺れでマッチング・集計が機能しなくなる。**マスタタグ + フリー入力の併用を維持** |

## 4. 画面仕様
### 4.1 画面遷移
1. ユーザープロフィール設定画面 → タグ設定・編集（マスタタグ選択 or フリー入力）
2. イベント詳細画面 → 参加者ブロック下部の**参加者タグ集計**を表示 → タグクリックで自分のタグに追加／解除

#### 4.2.2 イベント詳細画面（参加者セクション）

**参加者プレビュー（`EventMemberList`）**

- 参加者のアバター・名前（コミュニティ設定で許可時）・注文メニュー・**個別プロフィールタグ**を表示する
- 参加者セクション上部の **「参加者プロフィール」** リンク（既存）は `/members` への導線として維持する

**参加者タグ集計（`EventParticipantTags`）**

- 参加者ブロックの**下部**に **「参加者タグ」** 見出しで集計一覧を表示（`event_members_tags` を使用）
  - **表示順**: ハイライト（自分との共通タグ）を先頭ブロックにまとめ、各ブロック内は使用人数の多い順（`sortTagCountRowsByHighlightThenCount`）
  - **表示上限**: なし（全タグを表示）
  - `event_members_tags` が空の場合はセクションごと非表示
- 集計タグをクリックすると自分の `user_tags` に取り込み／解除できる（§4.2.5）

**イベントタグ（主催者設定）**

- 概要付近の上部に**イベントタグ**（`event_setting_tags`）を表示
  - 空の場合は「タグ未設定」と表示
- イベントタグ・参加者タグ集計は表示上**明確に区別**する（詳細は [05_イベントタグ機能.md](./05_イベントタグ機能.md) 参照）
- イベントタグも集計タグと同様、§4.2.5 の取り込み／解除に対応

#### 4.2.3 参加者一覧画面（`/members`）

- ルート: `/c/{communityAccount}/e/{eventId}/members`（`base/src/components/pages/c/[communityAccount]/e/[eventId]/members.vue`）
- コミュニティの `is_show_member === false` の場合は既存どおり **404**（氏名非公開設定）。イベント詳細の参加者タグ**集計**（タグ名＋人数のみ）は別途表示可
- 各参加者カード（`EventMemberCard`）内に**個別のプロフィールタグをすべて表示**する
  - **表示順**: 自分との**共通タグを先頭**（`orderTagsWithHighlightFirst`）
  - タグが0件の参加者はタグ欄を非表示
- 自分と共通のタグをハイライト表示
- タグクリック時の挙動は §4.2.5 に準拠
- イベント詳細の参加者プレビューとは異なり、**誰がどのタグを持っているか**をカード単位で詳しく確認する専用画面とする

#### 4.2.4 他ユーザーのプロフィールページ
- タグ一覧を表示
- 自分と共通のタグをハイライト表示（色分け）
- タグクリック時の挙動は 4.2.5 に準拠

#### 4.2.5 タグクリック時の取り込み（イベントタグ・参加者タグ・プロフィールタグ共通）

表示上のタグ種別にかかわらず、**同じ操作・同じ API** で自分の `user_tags` を更新する。

| 操作 | 挙動 |
| --- | --- |
| クリック（未所持） | 自分の `user_tags` に追加（`addTagToMyProfile` Callable） |
| クリック（所持済み） | 自分の `user_tags` から解除（`updateUserTags` Callable） |
| フロントエンド | `toggleTagOnMyProfile`（`base/src/apis/userTags.ts`）で上記を切り替え |

- 重複チェック・上限チェック（10個）・正規化は Callable 側で実施
- 成功後は Pinia store を直接更新し、ページリロードなしでリアクティブに反映する
- 未ログイン時はエラートーストを表示し、取り込み不可

## 5. 技術仕様・データ構造設計
### 5.1 タグマスタの管理方針
タグマスタは **Firestore ではなくソースコード（定数ファイル）で管理する**。

- タグの追加・変更頻度が低く、デプロイで十分対応できる
- Firestore への fetch・セキュリティルール設定が不要になり実装がシンプル
- TypeScript の `as const` により型安全に使用できる
- Phase 2 以降で管理画面からの動的変更が必要になった場合に Firestore 移行を検討する

```typescript
// common/src/constants/tags.ts
export const TAG_GENRES = [
  {
    genre: "経営／マネジメント",
    tags: ["DX", "経営戦略", "財務", "不動産", "農業", "モビリティ", "物流" /* ... */],
  },
  {
    genre: "テクノロジー／サイエンス",
    tags: ["AI", "生成AI", "エンジニア", "IoT", "ブロックチェーン", "VR", "AR" /* ... */],
  },
  // ... 全24ジャンル
] as const;

// マスタタグの Union 型（型チェックに活用）
export type MasterTag = (typeof TAG_GENRES)[number]["tags"][number];
```

### 5.2 Firestoreスキーマ
```typescript
// ユーザープロフィールスキーマ（既存スキーマに追加）
// `users/{userId}` ドキュメントに追加
interface UserProfile {
  // 既存フィールド...
  user_tags: string[]; // ユーザーが設定したタグ配列（最大10個、マスタ＋フリーの混在可）
  updated_at: Timestamp;
}
// ※ Zod スキーマでは `user_tags: z.array(z.string()).optional().default([])` として定義する
//   （既存ユーザーのドキュメントに user_tags フィールドが存在しない場合を考慮）

// イベントスキーマ（既存スキーマに追加）
// `communities/{communityId}/events/{eventId}` ドキュメントに追加
interface EventDocument {
  // 既存フィールド...
  event_setting_tags: string[];      // 主催者が設定したイベントタグ（マスタのみ・最大5個）
  event_members_tags?: {             // 参加者タグの集計（Trigger Function が自動更新）
    [tag: string]: number;           // タグ名: 使用人数
  };                                 // ※ 参加者が0人の場合は undefined（フィールド自体が存在しない）
  updated_at: Timestamp;
}
// ※ event_setting_tags の詳細仕様は `05_イベントタグ機能.md` を参照

// 参加者タグ詳細スキーマ（新規）
// `communities/{communityId}/events/{eventId}/member_tags/{userId}` ドキュメント
interface EventMemberTag {
  user_id: string;
  user_tags: string[]; // そのユーザーのタグ（参加時点の最新を常に同期）
  created_at: Timestamp;
  updated_at: Timestamp;
}
```

### 5.3 タグの種類
| 種類 | 説明 | 管理場所 |
|---|---|---|
| **マスタタグ** | 運営がソースコードで定義するタグ | `common/src/constants/tags.ts` |
| **フリータグ** | ユーザーが自由に入力したタグ | Firestore の `user_tags` に文字列として保存 |

- `user_tags` フィールドにはマスタタグ・フリータグを区別せず文字列配列で保存する
- フロントエンドで `TAG_GENRES` 定数と突合し、マスタタグかどうかを判定して表示を制御する（例：バッジの色分け等）

### 5.4 Firestoreフロントエンド処理
- **データ取得処理**:
  - タグ設定画面では `TAG_GENRES` 定数を使用してマスタタグ一覧を表示（Firestore fetch 不要）
  - ユーザープロフィール取得時にタグ情報も取得
  - イベント参加者一覧取得時に各参加者のタグ情報を取得
  - `member_tags` コレクションから個別タグ情報を取得
  - イベントドキュメントの `event_members_tags` をリアルタイム監視
- **データ更新処理**:
  - タグ設定時はユーザープロフィールを更新
  - タグ取り込み時は既存タグに追加（重複チェック・上限チェック）
  - イベント参加時に参加者タグ詳細ドキュメントを作成
  - イベント退出時に参加者タグ詳細ドキュメントを削除
- **リアルタイム監視**:
  - イベント参加者タグ集計の変更を監視
  - 参加者一覧のタグ変更を監視
- **エラーハンドリング**:
  - タグ数上限エラー（10個超過）
  - 重複タグエラー
  - ネットワークエラー

### 5.5 Firestoreセキュリティルール
```javascript
// ユーザープロフィールのタグ更新ルール
match /users/{userId} {
  allow update: if request.auth != null
    && request.auth.uid == userId
    && request.resource.data.user_tags.size() <= 10;
}

// 参加者タグ詳細の読み取りルール（書き込みは Functions 経由のみ）
match /communities/{communityId}/events/{eventId}/member_tags/{userId} {
  allow read: if request.auth != null;
  allow write: if false; // Functions (Admin SDK) 経由のみ書き込み可
}

// イベントドキュメントのタグ集計読み取りルール
match /communities/{communityId}/events/{eventId} {
  allow read: if request.auth != null;
}
```

### 5.6 Functions設計
#### 5.6.1 Callable Functions（フロントエンドから呼び出し）
- `updateUserTags`: ユーザータグ更新
  - **引数**: `tags: string[]`
  - **戻り値**: `{ success: boolean, message: string }`
  - **認証**: ログインユーザーのみ（自分のタグのみ更新可）
  - **バリデーション**:
    - タグ数：10個以下（超過時はエラートーストを表示）
    - 各タグ文字数：最大20文字
    - 正規化処理：フリー入力フィールドでは**入力中にリアルタイム**で以下を適用し、保存前にも再適用する
      - 全角英数字 → 半角に変換
      - アルファベット → lowercase に統一
      - 前後の空白をトリム
      - 正規化後に重複チェック（同一タグとみなす）
  - **成功後**: Pinia store を直接更新してリアクティブに反映する

- `addTagToMyProfile`: 他ユーザーのタグ / イベントタグ / 参加者タグから自分のタグに**1件追加**
  - **引数**: `tag: string`
  - **戻り値**: `{ success: boolean, message: string }`
  - **認証**: ログインユーザーのみ
  - **処理**: `updateUserTags` と同じ正規化処理（全角→半角・lowercase・trim）を適用した上で、重複チェック・上限チェックを行い、自分の `user_tags` に追加
  - **成功後**: Callable Function の戻り値を受け取った後、フロントエンドで Pinia store を直接更新してページリロードなしでリアクティブに反映する
  - **上限超過時**: エラートーストを表示する（10個を超える場合）
  - **UI からの呼び出し**: クリック時はフロントエンドの `toggleTagOnMyProfile` が「未所持 → 追加」「所持済み → 解除」を切り替える（イベントタグ・参加者タグ・プロフィールタグで共通）

#### 5.6.2 Trigger Functions（自動実行）
- `syncMemberTagOnOrderChanged`: 注文ステータス変化に応じて参加者タグ詳細を作成・削除
  - **トリガー**: `communities/{communityId}/events/{eventId}/members/{userId}/member_orders/{orderId}` の `onDocumentWritten`（既存 `createEventMembers` と同パターン）
  - **処理内容**:
    - `ordered` ステータスへの遷移を検知した場合：ユーザーの現在の `user_tags` を取得し `member_tags/{userId}` を作成（既存の場合は上書き）
    - `ordered` ステータスからの離脱（キャンセル・削除）を検知した場合：同一ユーザーの残存 `ordered` 注文を確認し、0件なら `member_tags/{userId}` を削除
  - **重複防止**: 複数商品を同時注文しても1ユーザーにつき `member_tags/{userId}` は1件のみ作成・削除される（`createEventMembers` と同様のガード処理）
  - **権限**: システム権限

- `updateEventMemberTags`: 参加者タグ集計更新
  - **トリガー**: `member_tags/{userId}` ドキュメントの作成・更新・削除時
  - **処理内容**: 該当イベントの `event_members_tags` を再計算・更新
  - **権限**: システム権限

- `syncUserTagsToEvent`: ユーザータグ変更時の同期
  - **トリガー**: ユーザープロフィールの `user_tags` 更新時
  - **参加イベントの取得**: `events` コレクショングループに対して `members` フィールドの `array-contains` で該当ユーザーを絞り込む
    - クエリ: `collectionGroup('events').where('members', 'array-contains', userId).where('is_deleted', '==', false).where('event_end_datetime', '>', now)`
    - ※ `event.members` フィールドは `optional().default([])` として扱い、未定義の場合は空配列として処理する
  - **処理内容**: 取得した終了前イベントの `member_tags/{userId}` を更新
  - **終了判定**: `event_end_datetime` が現在日時より未来のイベントのみ対象（過去イベントはスキップ）
  - **必要インデックス**: `firestore.indexes.json` に `members`（CONTAINS）+ `is_deleted`（ASC）+ `event_end_datetime`（ASC）の複合インデックスを追加
  - **権限**: システム権限

### 5.7 処理フロー
1. ユーザーがプロフィール設定画面でタグを設定（マスタ選択 or フリー入力）
   - フリー入力中にリアルタイム正規化（全角→半角・lowercase・trim）を適用
   - 10個超過時はエラートーストを表示
2. `updateUserTags` を呼び出し、正規化処理を経てユーザープロフィールの `user_tags` を更新
   - 成功後、フロントエンドで Pinia store を直接更新してリアクティブに反映
3. Trigger Function `syncUserTagsToEvent` が実行され、`members` array-contains で参加中の**終了前**イベントを取得し、`member_tags/{userId}` を更新
4. Trigger Function `updateEventMemberTags` が実行され、イベントの `event_members_tags` を再計算・更新
5. ユーザーがイベントに参加すると `member_orders` の `ordered` ステータスへの遷移が発生
6. Trigger Function `syncMemberTagOnOrderChanged` が実行され、`member_tags/{userId}` を自動作成（複数商品を同時注文しても1回のみ実行）
7. Trigger Function `updateEventMemberTags` が実行され、`event_members_tags` を更新
8. イベント詳細画面の参加者プレビュー（`EventMemberList`）に個別タグを表示し、参加者ブロック下部に参加者タグ**集計**を表示
   - `event_members_tags` が `undefined`（参加者0人）の場合は集計セクション非表示
9. 閲覧ユーザーと共通のタグをハイライト表示
10. 集計タグ・プレビュー内個別タグ（およびイベントタグ）クリックで `toggleTagOnMyProfile` を呼び出し、未所持なら `addTagToMyProfile`、所持済みなら `updateUserTags` で自分の `user_tags` を更新
    - 成功後、Pinia store を直接更新してリアクティブに反映（ページリロード不要）
    - 10個超過時はエラートーストを表示
11. 参加者一覧画面（`/members`）では個別参加者のタグを全件表示（共通タグ優先）。遷移は既存の「参加者プロフィール」リンクを使用

## データ更新の流れ

### 1. **イベント参加時（注文 ordered 遷移）**
```typescript
// member_orders の ordered ステータムへの遷移を Trigger Function `syncMemberTagOnOrderChanged` が検知
// `communities/{communityId}/events/{eventId}/member_tags/{userId}` を作成（複数注文でも1回のみ）
{
  user_id: "user123",
  user_tags: ["スタートアップ", "コミュニティ"], // その時点のユーザータグ
  created_at: Timestamp,
  updated_at: Timestamp
}
```

### 2. **プロフィール更新時**
```typescript
// Trigger Function `syncUserTagsToEvent` が実行される
// collectionGroup('events').where('members', 'array-contains', userId)
//   .where('is_deleted', '==', false).where('event_end_datetime', '>', now)
for (const event of participatingActiveEvents) {
  await updateMemberTagDetail(event, newTags);
  // 終了済みイベント（event_end_datetime <= now）はクエリの時点でスキップ済み
}
```

### 3. **自動集計更新**
```typescript
// Trigger Function `updateEventMemberTags` が実行される
// イベントドキュメントの `event_members_tags` を再計算
// ※ 参加者が0人の場合はフィールド自体を削除（undefined 状態）
{
  event_members_tags: {
    "スタートアップ": 5,
    "コミュニティ": 12,
    "フットサル": 3
  }
}
```

## この設計の利点

1. **リアルタイム同期**: ユーザーがタグを変更すると、参加中の終了前イベントに即座に反映
2. **パフォーマンス最適化**: 終了済みイベントへの不要な書き込みをスキップし、更新コストを抑制
3. **効率的な表示**: イベント画面では集計データを表示、参加者一覧では個別データを表示
4. **データ整合性**: ユーザーの現在のタグと終了前イベントの参加者タグ詳細が常に同期
5. **タグ設定の促進**: イベントページ・プロフィールページからワンクリックでタグ取り込みが可能
6. **柔軟なタグ管理**: マスタタグ（品質管理）とフリータグ（自由度）の両立

`EventMemberTag` ドキュメントは「そのユーザーがそのイベントに参加している時点での最新のタグ情報」を保持する役割を果たします。終了済みイベントは更新されないため、終了時点のタグスナップショットとして機能します。
