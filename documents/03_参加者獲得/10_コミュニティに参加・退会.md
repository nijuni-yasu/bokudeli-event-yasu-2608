# コミュニティに参加/コミュニティを退会

## 1. 概要
### 1.1 機能の目的
コミュニティ詳細ページから、ユーザーが自身の参加状態をワンタップで切り替えられるようにし、参加/離脱に伴うデータ整合性を自動で担保する。

### 1.2 主要な機能
- 「コミュニティに参加」ボタンで当該コミュニティに参加
- 「コミュニティを退会」ボタンで当該コミュニティから離脱
- 参加状態に応じたボタン表示と無効化条件の制御
- コミュニティメンバーになっている場合「コミュニティに参加」とボタン表示される
- コミュニティメンバーになっていない場合「コミュニティを退会」とボタン表示される
- 管理者(manager)となっている場合、「コミュニティを退会」を押しても「管理者は退会することができません」と表示される
- Firestoreの `communities/{communityId}` およびサブコレクション `members` の整合更新
- ボタンは、イベントページの「主催者に連絡」の右隣に表示する。
- ボタンは、コミュニティページの「お問い合わせ」の下に表示する。


### 1.3 対象ユーザー
- ログイン済みの一般ユーザー
- コミュニティ管理者（自らの離脱時の挙動も含む）

## 2. ねらい
### 2.1 ビジネス目標
- コミュニティ参加率の向上（CVR向上）
- コミュニティの活性化と継続率向上

### 2.2 ユーザー価値
- 参加/離脱操作の分かりやすさ・即時性
- 不整合のない安定した状態管理

### 2.3 成功指標（KPI）
- 参加ボタンのクリックから参加完了までの成功率
- 離脱ボタンのクリックから離脱完了までの成功率
- 参加/離脱操作の平均処理時間

## 3. 前提条件
### 3.1 技術的前提条件
- Firebase Authentication によりユーザーが特定できること（`uid`）
- Firestore を用いたコミュニティデータ管理

### 3.2 ビジネス的前提条件
- コミュニティは自由参加/自由離脱を許容（承認制や有料化は本仕様の対象外）

### 3.3 依存関係
- コミュニティ詳細ページ表示機能
- ユーザープロフィールの基本スキーマ

## 4. 画面仕様
### 4.1 画面遷移
- ユーザーがコミュニティ詳細画面を開く
- 参加状態により表示ボタンが切替（参加前: 「コミュニティに参加」、参加中: 「コミュニティ参加中」表示。ホバー時のみ「コミュニティを退会」にテキスト変更）

### 4.2 UI要素
#### 4.2.1 ボタン・アクション
- 「コミュニティに参加」
  - カラー: プライマリ
  - 状態: 未参加かつ処理中でない場合に有効
  - アクション: クリックで参加処理を実行し、完了後は「コミュニティ参加中」に切替
- 「コミュニティ参加中」
  - カラー: セカンダリ/ニュートラル（状態表示を優先）
  - 状態: 参加中かつ処理中でない場合に表示
  - アクション: 通常時はクリック不可。マウスオーバー時に表示テキストが「コミュニティを退会」に変化し、その状態でクリック可
- 「コミュニティを退会」（マウスオーバー時の表示テキスト）
  - 表示条件: 「コミュニティ参加中」ボタンにマウスオーバーした場合
  - アクション: クリックでダイアログを表示
    - ダイアログ文言: 「コミュニティを退会しますか？」
    - 選択肢: 「OK」で離脱処理を実行、「キャンセル」で処理中止
    - 離脱完了後は「コミュニティに参加」に切替
  - 管理者(manager)の場合の挙動:
    - 押下可にする。 ダイアログで「OK」を選択後、「管理者はコミュニティを退会することができません」を表示して処理中止

#### 4.2.2 表示要素
- コミュニティ参加数表示: `community_num_members`（リアルタイム反映 or 次回ロード時更新、選択）
- 自分の参加状態バッジ（任意）
  - バッジ例: 「メンバー」「管理者」

#### 4.2.3 バリデーション/エラー表示
- 非ログイン時にボタン押下 → ログイン導線
- 失敗時はトーストで原因を簡潔表示（ネットワーク、権限、データ競合）
 - 管理者離脱禁止: 「管理者はコミュニティを退会することができません」

#### 4.2.4 配置場所（UIレイアウト）
- イベントページ:
  - 配置: 「主催者に連絡」ボタンの右隣（同一行、右側）
  - 余白: 左側に8–12pxの間隔
  - レスポンシブ: スマホ幅では縦積みで「主催者に連絡」の下に表示（上側に8–12pxの間隔）
- コミュニティページ:
  - 配置: 「お問い合わせ」セクションの直下
  - 余白: セクションタイトル/本文との間に16pxの上下余白
  - レスポンシブ: 通常はフル幅ボタン、タブレット以上は内容幅に合わせたボタンサイズ

## 5. 技術仕様・データ構造設計
### 5.1 Firestoreスキーマ設計
#### 5.1.1 コレクション構造
```
/communities/{communityId}
  id: string
  name: string
  members: string[]            // 参加ユーザーuidの配列（必要最小限保持）
  managers: string[]           // マネージャーuidの配列
  community_num_members: number  // コミュニティ人数（冪等更新、既存実装と統一）

/communities/{communityId}/members/{userId}
  id: string                   // userIdと同一
  roles: string[]              // ロール配列（既存実装と統一、例: ['member', 'manager']）
  updated_at: Timestamp
```

補足:
- 正規化優先のため、厳密な参照は `members` サブコレクションを主とし、`communities.members` 配列は高速なUI判定用のキャッシュとして扱う。
- 整合性のため、更新は必ずトランザクションまたはバッチで両方に反映。

#### 5.1.2 Zodスキーマ（common/src/schemas/ を想定）
```typescript
// CommunityDbSchema（抜粋）
id: z.string()
members: z.array(z.string()).default([])
managers: z.array(z.string()).default([])
community_num_members: z.number().int().nonnegative().default(0)  // 既存実装と統一
created_at: z.date()
updated_at: z.date()

// CommunityMemberDbSchema（抜粋）
id: z.string()
user_id: z.string()
roles: z.array(z.enum(['member', 'manager'])).default(['member'])  // 既存実装と統一（配列形式）
joined_at: z.date()
created_at: z.date()
updated_at: z.date()
```

### 5.2 フロントエンド処理
- 参加状態の取得:
  - `communities/{communityId}/members/{uid}` の存在確認
  - もしくは `communities/{communityId}.members` に `uid` が含まれるか（高速判定）
- 参加処理（join）:
  - 認証必須。処理中はボタンをローディング状態に
  - **既存実装との整合性**: 既存の `functions/legacy/src/community-members.js` の `on_write_community_members` トリガーを活用
  - 処理フロー:
    1. `communities/{communityId}/members/{uid}` ドキュメントを作成/更新（`merge: true` を使用、既存実装と同様）
       - 新規作成時: `joined_at`（現在時刻）、`roles`（`['member']`）、`updated_at`（現在時刻）を設定
       - 既存ドキュメントの場合: `updated_at` のみ更新（`joined_at` と `roles` は既存値を維持）
    2. 上記の書き込みにより、既存の `onWrite` トリガー（`on_write_community_members`）が自動発火
    3. トリガー内で以下が自動更新される:
       - `communities/{communityId}.members` 配列（全メンバーの参照配列）
       - `communities/{communityId}.managers` 配列（管理者のみの参照配列、`roles` 配列に `'manager'` が含まれるメンバー）
       - `communities/{communityId}.community_num_members`（メンバー数）
- 離脱処理（leave）:
  - 認証必須。処理中はボタンをローディング状態に
  - 前提チェック: ユーザーが管理者でないことを確認
    - 方法1: `communities/{communityId}/members/{uid}` ドキュメントの `roles` 配列に `'manager'` が含まれているか確認
    - 方法2: `communities/{communityId}.managers` 配列に自身の `uid` が含まれているか確認（高速判定）
    - 管理者の場合は処理を中止し「管理者はメンバーをやめることができません」を表示
  - **既存実装との整合性**: 既存の `functions/legacy/src/community-members.js` の `on_write_community_members` トリガーを活用
  - 処理フロー:
    1. `communities/{communityId}/members/{uid}` ドキュメントを削除
    2. 上記の削除により、既存の `onWrite` トリガー（`on_write_community_members`）が自動発火
    3. トリガー内で以下が自動更新される:
       - `communities/{communityId}.members` 配列（該当ユーザーを除外）
       - `communities/{communityId}.managers` 配列（該当ユーザーが管理者の場合は除外）
       - `communities/{communityId}.community_num_members`（メンバー数を減算）
  - 管理者の離脱可否: 管理者は離脱不可（UIとルール双方で明示的にブロック）

### 5.6 既存実装との整合性
#### 5.6.1 既存の自動更新トリガー
既存実装（`functions/legacy/src/community-members.js`）では、`communities/{communityId}/members/{userId}` への書き込み（作成・更新・削除）が発生すると、自動的に以下の処理が実行される:

```typescript
// functions/legacy/src/community-members.js
export const on_write_community_members = functions
  .region('asia-northeast1')
  .firestore.document('communities/{communityId}/members/{userId}')
  .onWrite(update_community_members)
```

`update_community_members` 関数内で:
- `communities/{communityId}/members` サブコレクションの全ドキュメントを取得
- `communities/{communityId}` ドキュメントの以下を更新:
  - `members`: 全メンバーの参照配列（`db.collection('users').doc(member.id)` 形式）
  - `managers`: 管理者のみの参照配列（`roles` 配列に `'manager'` が含まれるメンバーのみ）
  - `community_num_members`: メンバー数（`members.length`）

#### 5.6.2 新機能での活用方針
- **参加処理**: `communities/{communityId}/members/{uid}` ドキュメントを作成/更新するだけで、既存トリガーが自動的にコミュニティドキュメントを更新
- **離脱処理**: `communities/{communityId}/members/{uid}` ドキュメントを削除するだけで、既存トリガーが自動的にコミュニティドキュメントを更新
- **注意点**: フロントエンドから直接 `communities/{communityId}` の `members`、`managers`、`community_num_members` を更新する必要はない（既存トリガーが自動処理）

#### 5.6.3 既存実装の参考
- **注文完了時のメンバー追加**: `functions/legacy/src/stripe-webhook.js` の `checkout.session.completed` イベント時に `addCommunityUser` 関数を呼び出し、`communities/{communityId}/members/{userDoc.user_id}` に `{ updated_at: Timestamp.now() }` を設定（`merge: true`）。これにより既存トリガーが発火し、コミュニティドキュメントが自動更新される。

### 5.3 セキュリティルール（firestore.rules 追加方針）
- `communities/*/members/*`:
  - create: `request.auth.uid == request.resource.id` かつコミュニティが存在
  - delete: `request.auth.uid == resource.id` かつ ユーザーがコミュニティ管理者でないこと（`get(/databases/$(database)/documents/communities/$(communityId)).data.managers` に含まれない）
  - read: 認証済み（公開方針に応じて調整）
- `communities/*`:
  - `members` 配列からの自身 `uid` の削除は、当該 `uid` が管理者でない場合のみ許可
  - `managers` 配列の編集は原則禁止（管理UI/Functions 経由のみ）
  - Phase 1 はクライアント直更新を最小限許可、Phase 2 で Functions 経由に移行

### 5.4 インデックス設計（必要に応じて）
- `communities` の並び替え・検索要件があれば `community_num_members` 等に複合インデックス
- `members` サブコレクショングループで `roles` 配列などに索引（将来拡張、`array-contains` クエリ用）

### 5.5 データ整合性
- **既存トリガーによる自動整合性保証**: `communities/{communityId}/members/{userId}` への書き込み（作成・更新・削除）により、既存の `on_write_community_members` トリガーが自動発火し、`communities/{communityId}` ドキュメントの `members`、`managers`、`community_num_members` が自動更新される。フロントエンドから直接コミュニティドキュメントを更新する必要はない。
- **トランザクション/バッチ**: サブコレクションへの書き込みはトランザクション/バッチで実施（既存実装では単一ドキュメント操作でも整合性が保証される）
- **再計算可能性**: `community_num_members` は `members` サブコレクションのドキュメント数から再計算可能であり、将来の整合性チェックバッチで修復可能

## 6. 実装優先度
### 6.1 Phase 1（必須）
- 参加/離脱ボタンの実装（UI状態管理を含む）
- `communities/{communityId}/members/{uid}` サブコレクションへの作成/削除処理（既存トリガーが自動的にコミュニティドキュメントを更新）
- 管理者チェック機能（離脱時の管理者判定）
- セキュリティルールの最小許可設定（サブコレクションへの書き込み権限）

### 6.2 Phase 2（将来対応）
- 最後の管理者離脱のブロックと委譲フロー
- Functions 経由更新への移行（権限・監査ログ強化）
- 参加/離脱イベントの通知・ログ蓄積
- 業務バッチでの `community_num_members` 整合性検証/修復

## 7. 注意事項
### 7.1 既存システムへの影響
- **既存トリガーの活用**: `functions/legacy/src/community-members.js` の `on_write_community_members` トリガーが既に動作しているため、新機能でも同じトリガーが自動発火する。既存の注文完了時のメンバー追加処理（`stripe-webhook.js`）と同じ仕組みを利用する。
- `communities` ドキュメントに `members`, `managers`, `community_num_members` を参照する既存箇所の挙動確認（既存トリガーによる自動更新が正常に動作することを確認）
- 参加者数表示の更新タイミング（リアルタイム/次回読み込み）による UI 一貫性（既存トリガーによる更新は非同期のため、リアルタイム監視が必要な場合は考慮が必要）

### 7.2 セキュリティ考慮事項
- 権限昇格防止（自身以外の `members` 変更禁止）
- 管理者配列の不正編集の防止（将来的に Functions 経由）
- 大量書き込み防止のための Rate limit（フロント/バック双方）

### 7.3 運用考慮事項
- 異常終了時の整合性崩れに備えた整合性チェックタスク
- 問い合わせ対応のための監査ログ（Phase 2）
