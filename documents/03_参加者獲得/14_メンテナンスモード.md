# メンテナンスモード

## 1. 概要

### 1.1 機能の目的

システムメンテナンスやデータ移行などの際に、一般ユーザーおよび飲食店管理者向けアプリの利用を一時的に停止し、誤操作やデータ不整合を防ぐ。

### 1.2 主要な機能

- Firestore の `configs/global` に `maintenance_mode`（boolean）を置き、メンテナンスの ON/OFF を表現する
- Zod では **`maintenance_mode: z.boolean().default(false)`** とし、既存ドキュメントにフィールドがなくても未設定は `false` として扱う（後方互換）
- **メンテナンスモードの切り替えは Firestore コンソール**で `configs/global` の `maintenance_mode` を編集する（アプリ内管理画面や Callable Function による切り替えは行わない）
- **アプローチ1: 全面ブロック（ルーターレベル）** — メンテナンス中は指定ルート以外へのアクセスをメンテナンスページへリダイレクトする。実装が単純で、注文・店舗設定の双方を一括で止められる
- トレードオフ: メンテナンス中は**閲覧も含め、アプリの利用を原則できない**（イベント一覧の閲覧のみ許可する等は別途ホワイトリスト設計が必要）
- **user アプリと admin アプリの両方**で、ルーターによりメンテナンスページへ誘導する
- メンテナンス中は参加者は**注文できない**、飲食店管理者は**設定変更などの操作ができない**（全面ブロックにより画面に到達しない）
- **Callable Function や API を直接呼び出してメンテナンスをすり抜ける対策（Functions 側での `maintenance_mode` チェック）は行わない**
- メンテナンス中は **ログイン画面も含めブロック**する。サポートユーザーは **メンテナンス開始前にログインしたセッション**でバイパスする（メンテ中の新規ログインは不可）

### 1.3 対象ユーザー

- **一般ユーザー（user アプリ）**: メンテナンス中は原則すべての画面がメンテナンスページに置き換わる
- **飲食店管理者（admin アプリ）**: 同上
- **運用担当者**: Firestore コンソールで `maintenance_mode` を切り替える

## 2. ねらい

### 2.1 ビジネス目標

- メンテナンス時間帯に注文・設定変更が発生しないようにし、障害やクレームを抑える
- 運用で即座に ON/OFF を切り替えられるようにする（コンソール運用）

### 2.2 ユーザー価値

- メンテナンス中に操作して失敗するのではなく、メンテナンスであることが明示される
- メンテナンス終了後は通常利用に戻れる

### 2.3 成功指標（KPI）

- メンテナンス中に新規注文・設定更新が発生しない（モニタリング・ログで確認）
- メンテナンスページ表示により、問い合わせ内容が「できない」ではなく「メンテナンス中」と説明できる

## 3. 前提条件

### 3.1 技術的前提条件

- Firestore に `configs` コレクションおよびドキュメント `global` が存在し、既存フィールド（例: `support_user_ids`, `system_id`）と併せて管理される
- クライアントは `configs/global` を**読み取り可能**であること（現行のセキュリティルールに準拠）
- `configs` へのクライアントからの **write は不可**（現行ルールのまま）。切り替えはコンソールまたは管理者権限でのみ行う
- user / admin とも Vue Router のグローバルガードでメンテナンス判定を行う

### 3.2 ビジネス的前提条件

- メンテナンス時間は事前に関係者へ共有できる
- 緊急でメンテナンスを切る場合も、コンソールから `maintenance_mode` を更新できる

### 3.3 依存関係

- `common` の `Config`（`configs/global`）スキーマおよび `base` の config ストア（`onSnapshot` 等）による `configs/global` の購読
- user / admin それぞれのルーター初期化（`setupRouter`）

## 4. 画面仕様

### 4.1 画面遷移

- ユーザーがメンテナンス中に**許可ルート以外**へ遷移しようとしたとき、**メンテナンスページ**（例: `/maintenance`）へリダイレクトする
- **`maintenance_mode === false` のとき `/maintenance` へのアクセス（URL 直打ち・ブックマーク・リロードを含む）**は、メンテナンスページを表示せず **トップ（例: `/`）へリダイレクト**する（メンテナンス終了後にメンテ画面の URL のまま残らないようにする）
- **許可ルート（メンテナンス中のみ）**（必須）
  - **`maintenance_mode === true` のとき**、**メンテナンスページ**（例: `/maintenance`）のみを許可する — 無限ループ防止および未ログインユーザーへの表示用。ログイン画面は許可しない
- **サポートユーザー**（`configs/global` の `support_user_ids` に含まれる UID）が **メンテナンス開始前にログイン済み**の場合は、メンテナンスを**バイパス**し通常画面へアクセスできるものとする（運用・検証のため）
- **admin** は `/maintenance` を認証不要で表示できるようにし、未ログインでもメンテナンス文言を表示できるようにする

### 4.2 UI要素

#### 4.2.1 表示要素（メンテナンスページ）

- **タイトル**  
  - i18n キー例: `maintenance.title`（日本語例: 「メンテナンス中」）
- **説明文**  
  - i18n キー例: `maintenance.description`（日本語例: しばらくお待ちいただく旨の文言）
- **レイアウト**  
  - 既存のブランクレイアウト（`layout: blank`）等と整合させ、トップへの導線は要件に応じて表示するか決める

#### 4.2.2 ボタン・アクション

- 全面ブロックのため、メンテナンスページ以外の操作はルーター段階で行えない

## 5. 技術仕様・データ構造設計

### 5.1 Firestoreスキーマ設計

#### 5.1.1 コレクション構造変更

- **新規コレクションは追加しない**
- 既存の **`/configs/global`** ドキュメントにフィールドを追加する

参照（既存構成の一例）:

```
/configs/global
```

#### 5.1.2 ドキュメントスキーマ（追加・変更）

| フィールド名         | 型      | 必須 | 説明 |
|----------------------|---------|------|------|
| `maintenance_mode`   | boolean | 既存ドキュメントでは未設定可 | `true` のときメンテナンス中。未設定は Zod の `.default(false)` で `false` 扱い |

既存の `support_user_ids`, `system_id` 等は変更しない。

#### 5.1.3 Zodスキーマ定義

- ファイル: `common/src/schemas/Config.ts`（既存の `ConfigGlobal`）
- `maintenance_mode` は **`z.boolean().default(false)`** とし、Firestore にフィールドが無い場合もアプリ側では `false` として扱う

```typescript
// 例（実装時のイメージ。詳細は Config.ts に合わせる）
const ConfigGlobalDbSchema = z.object({
  support_user_ids: z.array(z.string().nonempty()),
  system_id: z.string().nonempty(),
  maintenance_mode: z.boolean().default(false),
})
```

### 5.2 Firestoreフロントエンド処理

- **データ取得**: `base/src/stores/config.ts` の既存パターン（`doc(db, 'configs', 'global').withConverter(...)` + `onSnapshot`）で `configs/global` を購読する
- **メンテナンス判定**: ルーターの `beforeEach` で `configs/global` が解決したあと次のとおりとする。ログイン画面は許可しない
  - **遷移先が `/maintenance` の場合**: `maintenance_mode === true` のときのみ当該ルートを許可。`false` のときは **`/` へリダイレクト**（メンテナンス外ではメンテ画面 URL に留まらない）
  - **上記以外のパス**: `maintenance_mode === true` かつバイパス条件に該当しない場合に `/maintenance` へ誘導する
- **admin**: メンテナンス用 `beforeEach` を認証ガードより前に登録し、`/maintenance` は **`maintenance_mode === true` のときのみ**認証ガードでスキップして未ログインでも表示できるようにする（`false` のときは `/` へ）
- **リアルタイム**: `onSnapshot` によりコンソールで `false` に変更した場合、再購読で状態が更新される。**同一ページに留まったまま**メンテ解除を検知して自動でトップへ戻す処理（`watch` 等）は任意（Phase 2）。**リロードまたは `/maintenance` への再ナビゲーション**ではガードにより `/` へ戻る

### 5.3 Firestoreインデックス設計

- **追加不要**（単一ドキュメント `configs/global` の読み取りのみ）

### 5.4 Firestoreセキュリティルール

- **本仕様のためにルールを変更する必要はない**（既存どおり `configs` は read 可、クライアント write 不可でよい）
- メンテナンス ON/OFF はコンソールで更新する

### 5.5 Functions設計

- **メンテナンスフラグの切り替え用の Callable Function は設けない**
- **注文・その他の Callable 内で `maintenance_mode` を検証し、クライアント直呼びを防ぐ処理は行わない**（本仕様のスコープ外）

### 5.6 処理フロー

#### 5.6.1 メンテナンスリダイレクト（ルーター）

1. ユーザーが任意の URL にアクセスする
2. ルーターのグローバルガードが `configs/global` の解決済み状態を参照する
3. **遷移先が `/maintenance` の場合**
   - `maintenance_mode === true` のとき: 当該ページを表示する（無限ループ防止・未ログイン表示用）
   - `maintenance_mode === false` のとき: **トップ（例: `/`）へリダイレクト**する
4. **遷移先が `/maintenance` 以外の場合**、`maintenance_mode === true` かつバイパス対象でない場合、メンテナンスページ（例: `/maintenance`）へリダイレクトする
5. メンテナンス中は当該アプリ内で注文・設定画面に到達しない

## 6. データマイグレーション

### 6.1 マイグレーション対象

- **必須ではない**。`maintenance_mode` は Zod で `.default(false)` とするため、既存の `configs/global` にフィールドがなくても読み取り時にデフォルト適用できる
- 運用で明示的に `maintenance_mode: false` を書き込んでもよい

### 6.2 注意事項

- 本番でフィールドを追加する場合は、メンテナンス時間帯とあわせてコンソールで行う

## 8. 注意事項

### 8.1 既存システムへの影響

#### 8.1.1 データベース構造への影響

- **既存コレクション `configs` の `global` ドキュメントにフィールドを1つ追加**（任意。未追加でもデフォルトで動作）
- インデックス追加は不要

#### 8.1.2 アプリケーションへの影響

- **フロントエンド**: user / admin のルーターにガードを追加し、メンテナンスページを新設する
- **バックエンド**: 本仕様では Callable 側のチェックを追加しないため、Functions の変更は必須ではない

#### 8.1.3 運用への影響

- メンテナンス開始・終了は **Firestore コンソール**で `configs/global` を編集する運用とする
- 全面ブロックのため、メンテナンス中は**閲覧も含め利用できない**（許可ルート以外）

### 8.2 セキュリティ考慮事項

- `configs` のクライアントからの書き込みは引き続き禁止とし、不正にフラグを書き換えられないようにする
- メンテナンスをすり抜ける **API 対策は本仕様では行わない**。必要になった場合は別イシューで Functions 側検証を検討する

### 8.3 運用考慮事項

- **切り替え手順**: コンソールで `maintenance_mode` を `true` → 作業 → `false`
- **告知**: メンテナンス予定は別チャネル（メール・SNS等）で告知するとよい
- **サポート・検証**: `support_user_ids` に登録したユーザーは **メンテナンス開始前にログインした状態**であればメンテナンス中も通常利用できる。メンテ中に新規ログインはできないため、検証担当は事前にセッションを確保する
