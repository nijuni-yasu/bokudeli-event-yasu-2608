# アカウント削除機能

## 1. 概要

### 1.1 機能の目的
ユーザーが自身のアカウントを削除できる機能を提供し、個人情報の削除リクエストに対応する。注文データや参加履歴は残しつつ、個人を特定できる情報のみを削除する。

### 1.2 主要な機能
- ユーザー画面から「アカウント削除」操作を実行可能
- 個人情報（名前・プロフィール画像・メールアドレス・SNS等）を削除し、プレースホルダー値（"-"等）で上書き
- ユーザーID（user_id）は残し、注文データ・イベント参加履歴との整合性を維持
- コミュニティメンバー一覧からは外れる
- Firebase Authentication のアカウントを削除し、再ログイン不可とする

### 1.3 対象ユーザー
- ログイン済みの一般ユーザー（本人のみ実行可能）

## 2. ねらい

### 2.1 ビジネス目標
- ユーザーからの個人情報削除リクエストへの対応
- 法的リスク（個人情報保持）の低減

### 2.2 ユーザー価値
- 自身の個人情報を削除できる権利の保障
- サービス離脱時の明確な出口の提供

### 2.3 成功指標（KPI）
- アカウント削除の完了率
- 削除後のデータ整合性（注文データ・表示の不具合なし）

## 3. 課題・背景

- アカウントを削除する機能がない
- ユーザーからメールを配信してほしいとのリクエストがいくつか発生している
- 注文データは、コミュニティから閲覧する過去の参加人数や、飲食店からの注文データなど削除できない
- 名前・プロフィール画像・メールアドレスなどの個人情報は削除しながら、user_idや注文データは残る設計としたい
- データ構造が壊れないようにしながら、適切にアカウント削除したい

## 4. 方針

### 4.1 基本方針
- **個人情報の扱い**: 個人情報は削除し、表示用プレースホルダー（"-"）をDBに保存する
- **プレースホルダー方針**: フィールドを削除するのではなく、"-" 等の値をDBに保存する。スキーマの厳密さを維持し、既存の表示ロジックをそのまま利用できる
- **ユーザーID**: user_id は残す。注文データ・イベント参加者一覧との参照整合性を維持
- **注文データ**: 店舗から見た注文データは残す。名前は "-" と表示される

### 4.2 削除後の表示
- ユーザー名: "-" と表示
- プロフィール画像: デフォルト画像を表示（user_image_url を空文字に上書き）
- メールアドレス: 空（削除済み）

## 5. 画面仕様

### 5.1 画面遷移
- ユーザーが `/profile` ページ（プロフィール設定）から「アカウント削除」にアクセス

  - カラー: エラー系（赤系）またはニュートラル
  - アクション: クリックで確認ダイアログを表示

#### 5.2.2 確認ダイアログ
- **表示内容**
  - タイトル: 「アカウントを削除しますか？」
  - 本文: 以下を表示する

    【残るもの】
    過去の注文履歴（店舗の管理に必要なため。画面上では個人を特定できない形で表示されます）

- **処理中 UI**: 「削除する」ボタンをローディング表示し、二重送信防止（ボタン無効化）を行う

#### 5.2.3 バリデーション/エラー表示

- 処理失敗時: トーストで「処理に失敗しました。しばらくして再度お試しください」を表示
- **コミュニティ唯一の管理者**: 削除を許容しない。`base` に utils 関数を作成し、該当する場合はボタンを無効化またはエラーメッセージを表示する
  - 表示文言: 「管理者があなたのみのコミュニティがあるため、アカウントを削除できません。先に他の管理者を追加するか、該当コミュニティから退会してください。」

## 6. 技術仕様・データ構造設計

### 6.1 削除対象と更新内容

#### 6.1.1 users（UserDoc）
| 項目 | 更新内容 |
|------|----------|
| user_id | 変更なし（残す） |
| created_at, updated_at | 変更なし |
| **is_deleted** | `true` を設定（スキーマに新規追加） |
| **deleted_at** | 削除日時（epoch ミリ秒）を設定（スキーマに新規追加） |
| user_name | `"-"` に上書き |
| user_description | 空文字 `""` に上書き |
| user_image_url | 空文字 `""` に上書き（デフォルト画像表示） |
| user_sns_* | 空文字 `""` に上書き |
| user_account | 空文字 `""` に上書き |

#### 6.1.2 users_personal_information
| 項目 | 更新内容 |
|------|----------|
| user_id（ドキュメントID） | 変更なし（残す） |
| **is_deleted** | `true` を設定（スキーマに新規追加） |
| **deleted_at** | 削除日時（epoch ミリ秒）を設定（スキーマに新規追加） |
| user_email | 空文字 `""` に上書き |

※ users_personal_information に user_name は存在しない。ユーザー名は users コレクションの user_name で管理。

#### 6.1.3 イベントの注文データ（OrderDoc）
- **変更なし**: user_id はそのまま残す
- 表示: 注文者名は users から取得するため、"-" と表示される

#### 6.1.4 コミュニティメンバー
- **削除対象**: `communities/{communityId}/members/{userId}` を全コミュニティ分削除
- トランザクション内での削除でも、既存の `on_write_community_members` トリガー（legacy）が正常に発火し、`communities.members` 配列が自動更新される

#### 6.1.5 イベント参加者一覧（event.members）
- **変更なし**: event.members の DocumentReference はそのまま残す
- 表示: 参加者名は users から取得するため、"-" と表示される

#### 6.1.6 Firebase Authentication
- **削除**: Admin SDK の `auth.deleteUser(uid)` でアカウントを完全削除
- 再ログイン不可となる

#### 6.1.7 pass_code
- **削除**: user_id が一致する PassCode ドキュメントをすべて削除する（メールアドレス等の個人情報が残らないようにする）

#### 6.1.8 カート内注文（in_cart）
- **変更なし**: 削除時点で in_cart の注文が残っている場合もそのまま残す。user_id は維持され、表示は "-" となる

### 6.2 スキーマ変更

#### 6.2.1 User スキーマ（common/src/schemas/User.ts）
- **UserDbSchema**: `is_deleted: z.boolean().optional()`、`deleted_at: EpochMillisSchema.optional()` を追加（既存データとの互換のため optional）
- **UserAppSchema**: `is_deleted: z.boolean().default(false)`、`deleted_at: z.number().int().positive().optional()` を追加
- **補足**: 削除処理では User クラスの toFirestore は使用せず、Firestore へ直接更新する。is_deleted は読み取り時のスキーマ互換のための追加であり、convertToDb で渡す必要はない

#### 6.2.2 UserPersonalInformation スキーマ（common/src/schemas/UserPersonalInformation.ts）
- **UserPersonalInformationDbSchema**: `is_deleted: z.boolean().optional()`、`deleted_at: EpochMillisSchema.optional()` を追加
- **UserPersonalInformationAppSchema**: `is_deleted: z.boolean().default(false)`、`deleted_at: z.number().int().positive().optional()` を追加

### 6.3 処理フロー

削除処理は **Cloud Functions（Callable）** で実行する。`users_personal_information` は Firestore ルール上クライアントから書き込み不可のため、Functions 経由が必須。

**処理順序**: Firestore 更新を先に完了させ、最後に Firebase Auth の deleteUser を実行する（Auth 削除を先に行うと Firestore 更新時の認証が失われるため）。

```
1. ユーザーが「アカウント削除」をクリック
2. 確認ダイアログで「削除する」を選択
3. クライアントから deleteUserAccount Callable Function を呼び出し（request.auth.uid で本人確認）
4. Functions 内で以下を順次実行:
   a. ユーザーが所属する全コミュニティを取得
      - communities を where('members', 'array-contains', db.doc('users/' + userId)) で検索
   b. トランザクションで:
      - users/{userId}: 個人情報をプレースホルダー値で上書き、is_deleted: true を設定
      - users_personal_information/{userId}: user_email を空に、is_deleted: true を設定
      - 各 communities/{communityId}/members/{userId} を削除
   c. Firebase Auth の deleteUser(uid) を実行
   d. **（RC-50・マイページ整合）** 退会者 B の `users/{B}/friends` を読み、ドキュメント ID ごとに相手 uid を列挙。各相手 uid に `recountUserProfileCounts(uid)` を **トランザクション外**で非同期実行（`Promise.allSettled` 推奨）。失敗時はログのみとし、**アカウント削除の成功レスポンスは返す**（[02_マイページ.md](./02_マイページ.md) §5.1.2 RC-50、[02_友人一覧機能.md](./02_友人一覧機能.md) S-7）
5. クライアント: 完了モーダル「ユーザーアカウントは正常に削除されました」を表示
6. ユーザーが OK 押下: signOut で明示的にログアウトし、`/` へリダイレクト
```

**トランザクション制約**: Firestore トランザクションは 500 操作までの制限があるが、現状の想定ユース（ユーザーが所属するコミュニティ数）では問題ない。

**RC-50（退会後の相手側プロフィールカウント）**:

- 友人関係は [02_友人一覧機能.md](./02_友人一覧機能.md) S-7 のとおり、退会時も `friends` サブコレは **残置**する
- 退会直後、`getUserFriends` は退会者を一覧から除外するが、相手の **`users.friend_count` 冗長フィールド**は再集計まで古い値になりうる
- 上記手順 **4.d** で、同席関係のあった **残存ユーザー**の `friend_count` を `getUserFriends` と同じ除外ルールで更新する
- 実装は `functions/default/src/utils/recountUserProfileCounts.ts` の `recountUserProfileCounts` / `recountUserProfileCountsForUsers` を利用する（store 経由・`createModuleLogger`）

### 6.4 Functions 設計

| 項目 | 内容 |
|------|------|
| 種類 | Callable Function |
| 名前 | `deleteUserAccount` |
| 認証 | 必須（request.auth != null） |
| 権限チェック | request.auth.uid と対象 userId が一致することを確認 |
| 引数 | なし（uid は auth から取得） |
| 戻り値 | 成功時: `{ success: true }`、失敗時: エラーを throw |
| エラー時 | リトライなし。クライアントには「処理に失敗しました。しばらくして再度お試しください」を表示 |
| ログ | `createModuleLogger` を使用（必須）。成功時: ユーザーID のみ（個人情報は含めない）。失敗時: エラー内容とユーザーID |
| 副作用（RC-50） | 成功後: `users/{uid}/friends` の doc ID 集合に対し `recountUserProfileCountsForUsers`（または同等）。失敗はログのみ。本体の `{ success: true }` には影響しない |

### 6.5 クライアント API
- `base/src/apis/user.ts` に `deleteUserAccount` を追加
- `httpsCallable(functions, 'deleteUserAccount')` で呼び出す

### 6.6 コミュニティ一覧の取得方法
- `communities` コレクションの `members` フィールドは `DocumentReference` 配列（`db.doc('users/' + userId)` 形式）
- 既存実装（`user/src/pages/u/[userId].vue`）と同様に、`where('members', 'array-contains', db.doc('users/' + userId))` でユーザーが所属する全コミュニティを取得

## 9. 注意事項

### 9.1 既存システムへの影響
- User / UserPersonalInformation スキーマに `is_deleted` を追加するため、既存コードでこれらのスキーマを参照している箇所の確認が必要
- 既存ユーザードキュメントには `is_deleted` が存在しないため、optional および default(false) で互換性を確保
- **マイページ・友人（RC-50）**: `deleteUserAccount` に相手側 `recountUserProfileCounts` を追加する（[02_マイページ.md](./02_マイページ.md) §5.1.2）

### 9.2 セキュリティ
- 削除処理は本人のみ実行可能（Callable 内で uid 検証）
- users_personal_information の書き込みは Functions 経由のみ（既存ルール維持）

## 10. 参考: 実装しない場合の法的リスク

本機能を実装せず、ユーザーからの個人情報削除リクエストに手作業で対応する場合、以下の法的リスクが考えられる。参考情報として記載する。

### 10.1 日本の個人情報保護法

| リスク | 内容 |
|--------|------|
| **削除請求への対応義務** | 本人から削除・利用停止の請求があった場合、正当な理由なく拒否できない。対応しないと法違反の可能性 |
| **努力義務違反** | 利用目的に必要な期間を過ぎた個人情報は「遅滞なく消去する」努力義務（法22条）。アカウント削除後はメール送信等の利用目的がなくなるため、保有の正当性が弱くなる |
| **漏洩リスクの増大** | 不要な個人情報を長期保有すると、漏洩時の説明責任が重くなる。漏洩時は個人情報保護委員会への報告義務（速報: 3〜5日以内、確報: 30日以内）と本人への通知義務が発生 |
| **改正法の影響** | 2022年施行の改正個人情報保護法により、削除請求がしやすくなり、対応義務が強化されている |

### 10.2 GDPR（EU圏ユーザーがいる場合）

| リスク | 内容 |
|--------|------|
| **削除権（Right to Erasure）** | 本人が削除を求めれば、原則として「不当な遅延なく」削除する義務。対応しないと違反 |
| **保管制限の原則** | 収集目的に必要な期間を超えて保有してはならない |
| **制裁金** | 違反時は売上高の最大4%または2,000万ユーロのいずれか高い方 |

### 10.3 メールアドレスの扱い

- メールアドレスは個人情報保護法上・GDPR上ともに**個人情報**に該当する
- アカウント削除後はメール送信の利用目的がなくなるため、削除の正当性が高い
- 注文データ等は会計・法的義務のため一定期間の保管が必要な場合があるが、**メールアドレス**はその例外に当たりにくい

### 10.4 まとめ

本機能を実装することで、本人の削除請求への対応体制を整え、法的リスクを低減できる。実装しない場合は、手作業での対応体制整備と、削除請求対応マニュアルの整備が推奨される。

## 11. 参考: アカウント削除のアプローチ案と採用理由

アカウント削除時、注文履歴等を残しつつ個人を特定できないようにする方法として、以下の3つのアプローチ案がある。

| アプローチ | 内容 | メリット | デメリット |
|------------|------|----------|------------|
| **user_id を null に置換** | 注文などの履歴は残しつつ、OrderDoc 等の user_id を null にする | 個人と紐づく参照を完全に断てる | スキーマ変更（user_id を optional に）が必要。event.members や注文一覧など、user_id 前提のロジックを広く修正する必要がある |
| **匿名化 ID に置換** | user_id を UUID などの匿名 ID に差し替える | 個人を特定できない | 既存の user_id を全ドキュメントで一括置換する必要があり、OrderDoc・Event・Community 等の参照を全て更新する大規模なマイグレーションが必要 |
| **User の匿名化（現仕様）** | user_id は残し、User ドキュメントの個人情報だけを削除・匿名化する | スキーマ変更不要。参照整合性を維持。既存ロジックをそのまま利用可能。業界で一般的なアプローチ | 特になし（本プロジェクトの要件において） |

### 11.1 採用理由（User の匿名化を採用した理由）

1. **スキーマ・既存コードへの影響が最小**: EventOrder の user_id は `z.string().nonempty()` で必須。null や匿名 ID への置換にはスキーマ変更と広範な修正が必要
2. **参照整合性の維持**: event.members（DocumentReference 配列）、OrderDoc、Community の members 等、user_id を前提とした参照が多数存在。User を匿名化するだけで、これらの参照をそのまま維持できる
3. **一般的なアプローチ**: GDPR 等においても、Identity と Activity を分離し、Identity のみ匿名化して user_id を残すパターンは広く採用されている
4. **個人データの削除**: User の個人情報（名前・メール・画像等）を削除すれば、user_id 単体では個人を特定できないため、法的要件を満たせる
