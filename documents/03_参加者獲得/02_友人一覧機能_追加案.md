# 友人一覧機能_追加案

本ドキュメントは [02_友人一覧機能.md](./02_友人一覧機能.md) の Phase 1 を前提に、「たべとも」一覧の**体験価値（ワクワク感・再会・会話の種・再訪）**を高めるための**未確定アイデア**を集約する。実装優先度・プライバシー・Phase 2（公開範囲・表示項目）は別途判断する。

---

## 1. 背景・課題感

現状の Phase 1 は、**表示名・写真・同席回数・初回／最終会合日・ソート**が中心で一覧性は高い一方、次の感情・行動につなげにくい懸念がある。

- 「もっといろんな人に会いたい」という探索欲
- アプリやタブを**また開きたい**という頻度
- 「久しぶりに会いたい」と思える**間隔や文脈**
- 「あのときここ／あの食事会で会いましたね」という**話題の起点**

Firestore 側では `friends.event_history[]` に **`event_id` / `community_id` / `event_at`** があるため、**画面上ではまだ活かしていない情報**があり、そこが体験拡張の余地になる。

---

## 2. 「あのとき会いましたね？」を生む表示・データ

| アイディア | 内容 | データ・備考 |
| ---------- | ---- | ------------- |
| 共通の食事ログ（折りたたみ） | その人とのカード下に、`event_history` を展開可能なリストで表示。各行に **日付・コミュニティ名・（取得可能なら）イベント題名／店舗名** を出し、記憶のトリガーにする。 | 既存 `event_history` + `events` / `communities` の名前解決。Callable でまとめて返す構成が親和性高い。 |
| 「はじめて同席した会」の一文 | `first_met_at` に対応する `event_id` から、**イベント名やコミュニティ名を 1 行**表示（日付のみより文脈が増える）。 | 同上。 |
| 共通コミュニティバッジ | `event_history` から `community_id` をユニーク集約し、「一緒に参加してきた団体」をチップ表示。 | 名前解決が必要。 |
| 共通タグ／自己紹介（将来） | [02](./02_友人一覧機能.md) の方針どおり、`users` 側にタグや一言が増えたらカードに**共通タグ強調**などを載せられる。 | デノーマライズせず **表示時解決**でよい。 |
| エリア／ざっくり場所 | イベント側に公開可能な**エリア表現**があるなら「〇〇周辺で 3 回」等（粒度はプライバシー優先で粗め）。 | スキーマ・公開範囲の検討が前提。 |

---

## 3. 「もっといろんな人に会いたい」を生む案

| アイディア | 内容 | 備考 |
| ---------- | ---- | ---- |
| おすすめの出会い候補 | **同じコミュニティ**や**共通のたべとも（2-hop）**など、冷たくない距離での「また会えるかも」を示す。 | Phase 2 の公開範囲・辞退設定とセット。迷惑にならない導線（任意・控えめ）が前提。 |
| 参加実績のソーシャルプルーフ | 「このイベント系では〇人とたべとも」など、**集計のみ**の短文（詳細リストは別）。 | KPI とも相性があるが、過度な比較は避ける。 |
| ライトなマイルストーン | 「たべとも N 人」「同席イベント合計 M 回」など、**軽い達成表示**（バッジは控えめに）。 | ストリークのように途切れがストレスになる表現は避け、累計寄りが無難。 |

---

## 4. 開きたくなる頻度・「久しぶり」訴求

| アイディア | 内容 | 備考 |
| ---------- | ---- | ---- |
| ソート／セクション | **最終同席が古い順**のビュー、または「久しぶり」ラベル（例: 90 日以上は閾値をチューニング）。 | 既存 `last_met_at` で足せる。 |
| 相対表現 | 「最後に会ってから約 1 年」など、**人間的な間隔**のコピー。 | 日付表示と併用可。 |
| 本人向けダイジェスト（例） | 本人ページのタブ先頭に「今月の新しいたべとも」等の**短いサマリー**（他者ページでは出さない等）。 | ログイン時のみなど権限設計が必要。 |
| 未来志向の一行（難度高） | 双方の**予定参加**が分かる場合のみ「同じ会に行きそう」等。 | 同意・プライバシー・実装コストが大きい。後回し候補。 |

---

## 5. 実装・方針との整合メモ

- **既存データを活かす近道**: `event_history` を UI に載せる、`community_id` の名前解決、ソートに「最終が古い順」を足す、は [02](./02_友人一覧機能.md) のスキーマと矛盾しにくい。
- **Callable 一本化の方針**（[02](./02_友人一覧機能.md) 5.2 / 5.5）: プロフィール・退会・将来のオプトアウトと一緒に、**イベント名・コミュニティ名の解決**もサーバ側で返す形が自然。
- **プライバシー**: Phase 1 の完全公開のまま「おすすめ」「地図」などを強く出すとリスクが上がる。**Phase 2 の公開範囲・表示項目**とワンセットで優先度を決めるのが安全。

## 追加仕様 / フィードバック 26/6/19

### マイページの「プロフィール」タブのローディング （✅実装済）
- ローディング表示が気持ち的に長く感じる
- 回転するインジケーター以外何も表示されない
- v-cardなどのパネルは先に表示だけしておいて、コンテンツ読み込みのローディングだと改善される気がする

###  「イベントカード」「イベントプレビューカード」 （✅実装済）
- 「URL限定公開」の時に、表示されるがクリックしても遷移しない挙動が不具合のように見える。
- 「URL限定公開」とv-chipで小さく表示するようにする。イベントカードは共通のコンポーネントだが、他画面での表示も共通で良い。

### 「食事をご一緒した順」「最近会った順」のトグル （✅実装済）
- UIに違和感がある。カッコ悪い
- 文言に違和感がある。自然なものにしたい。
- そもそもこの順序トグルは必須なのだろうか

### 他者マイページにおけるともだちとの詳細情報 （✅確定：現状維持・全員表示）
- 「食事回数」などを自分との関係値？と勘違いしてしまう恐れ
- そもそも「自分と他者」ではなく「他者と他者」の、食事回数や参加履歴を見たいのか？見せたいのか？見られていいのか？
- 見せない場合、どこまで見せる？ヒストリーだけ見せない？など
- 例えばFacebookだと「共通の友達」の人数を見せる。他人のマイページでその人の友人一覧を見ても、見ている本人との関係性を表示している
- **決定（26/6/19）**: 他者向けの詳細非表示は**今回は実装しない**。Phase 1 は [02_友人一覧機能.md](./02_友人一覧機能.md) §4.2.1 / [02_マイページ.md](./02_マイページ.md) §4.2.6 どおり、本人・他者・未ログインを問わず `meet_count` / 日付 / 同席記録ボタンを表示する（完全公開のまま）。
- **見送り理由**: 上記懸念は Phase 2 の公開範囲・表示項目の検討に回す。`isOwner` による出し分けは導入しない。

### ともだちカードにSNSアイコン （要検討 → 将来対応）
- ともだちカードにそのユーザーのSNSアイコンを表示したい
- 上記、他者マイページでのともだちカードにおいては、SNSアイコンだけがあるのが良い？

### 同席記録の簡単チェック （要検討 → 将来対応）
- **スコープ**: 閲覧者本人と対象ユーザーの同席履歴（上記「他者マイページの友だち詳細の出し分け」議論とは別 UX）
- **想定導線**: イベント参加者一覧 → 相手プロフィール → 自分との同席記録
他ユーザーのプロフィールタブで同席したイベントの記録がサクッとチェックできると嬉しいと思いました！
たとえば以下の様に画面遷移した時に嬉しいかなと！
 　1．自分が参加するイベントのイベントページから参加者リストを見る
　 2. 気になる参加者をタップする
　 3．遷移した先のプロフィールタブの画面でその人とこれまでどんなイベントで同席したかがすぐに見れる
　微々たる差かもしれませんが、自分だったらこのフローで久々にイベントで会う参加者との話題を考えたりできると嬉しいかもです！
