## ブランチの役割

| ブランチ | 役割 | 更新方法 | push 時の動作 |
|:---------|:-----|:---------|:-------------|
| `development` | 開発用のデフォルトブランチ。feature ブランチのマージ先 | **PR のみ**（直 push 禁止） | テスト環境へ自動デプロイ |
| `main` | リリースタグの目印。直近のリリースコミットを指す | 限定者が直 push | デプロイは走らない |
| `production` | 本番デプロイ用 | 限定者が直 push | **本番環境へ自動デプロイ** |

## 通常時のデプロイ

**目的**: `development` にマージ済みの変更を、マイナーバージョンを上げて `main` / `production` に反映し、本番デプロイする。

**前提**

- リリースに含めたい変更はすべて `development` にマージ済みである。
- リポジトリルートで作業する（`npm version` はルートの `package.json` / `package-lock.json` を更新する）。
- **`development` は直 push 禁止**のため、バージョン bump は **release ブランチ + PR** で取り込む（B 版）。

**手順**

※ 手順 1〜2 は、データマイグレーション（バッチ処理）があるリリースの場合のみ実施する。

1. **Firestore のバックアップを取得する**
   - https://console.cloud.google.com/firestore/databases/-default-/data/panel/assets/center_banners?hl=ja&project=bokudeli-event-dev

2. **bokudeli-event-batch を実行する**
   - https://github.com/nijuniinc/bokudeli-event-batch/tree/main/tasks
   - 例: `0028_fix_menu_name_description_match.js` / `0029_fix_eventmenu_is_selected.js`（実行するタスクはリリース内容に合わせる）

3. **`development` を最新にする**
   - 例: `git fetch origin && git switch development && git pull origin development`

4. **release ブランチを切り、マイナーバージョンを上げる（タグは作らない）**
   - 例: `git switch -c release/2.6.0 development`
   - リポジトリルートで `npm version minor --no-git-tag-version` を実行する。
     - `package.json` のバージョンが上がる（例: 2.5.3 → 2.6.0）。`package-lock.json` も更新される。
     - `--no-git-tag-version` によりコミットもタグも作られない（タグは PR マージ後に付け直すため）。
   - バージョンコミットを作る: `git commit -am "v2.6.0"`（`package.json` / `package-lock.json` を含める）。
   - push する: `git push origin release/2.6.0`

5. **release ブランチ → `development` の PR を作成し、`PR verify` 通過後にマージする**
   - これが `development` を更新する唯一の経路（直 push 禁止）。
   - マージ方式は **merge commit 推奨**（タグを付ける確定コミットが明確になる。squash でも可）。

6. **`development` を最新化し、リリースコミットにタグを付ける**
   - 例: `git switch development && git pull origin development`
   - `git tag v2.6.0`（現在の `development` HEAD = PR マージ後の確定コミットに付与する）。

7. **`main` / `production` をリリースコミットに合わせる**
   - 例: `git branch -f main development && git branch -f production development`
   - ブランチ名を明示することで、HEAD の状態に依存せず安全に操作できる。

8. **`main` / `production` / タグを push する**（⚠️ **`production` の push で本番デプロイが自動実行される**）
   - 例: `git push origin main production v2.6.0`（タグ名は手順 4 で上げたバージョンに合わせる）
   - **`development` は push しない**（手順 5 の PR マージで更新済み）。

**補足**

- 手順 1〜2 を省略するリリースでは、手順 3 から始めてよい。
- タグは必ず **手順 5 のマージ後**（手順 6）に付ける。release ブランチ上で `npm version` がタグを作ると、PR マージで `development` 側のコミットハッシュが変わり、タグが消えるコミットを指してしまう。
- 本番デプロイ後に不具合が見つかった場合の手順は [ロールバック](#ロールバック本番を前バージョンに戻す) を参照。

## 緊急デプロイ / 割り込みリリース / hotfix

**目的**: `development` に未リリースの変更が積まれている状態で、特定の修正だけを本番に先に出す。

**前提**

- `main` / `production` は直近のリリースタグ（例: v2.6.0）に相当するコミットを指している。
- リリースに含めない変更は `development` 側にのみある（`main` / `production` には載せない）。

**手順**

1. **作業ブランチを切る**（ベースはリリース済みの `main`。`fetch` してから行う）
   - 例: `git fetch origin && git switch -c hotfix/1910 origin/main`

2. **必要なコミットだけ cherry-pick**（古い順に。複数ある場合は順番に）
   - 例: `git cherry-pick <commit1> <commit2> ...`
   - コンフリクトは都度解消する。

3. **ビルドが通ることを確認し、個人環境で動作確認する**
   - cherry-pick した変更が `main` ベース上で正しく動作するか検証する。`development` にしかない依存変更（スキーマ変更・store 変更など）が不足していると、ビルドエラーやランタイムエラーになる可能性がある。
   - ローカルでビルドを確認する: `npm ci && npm -w common run build && npm -w user run build && npm -w partner run build`
   - 個人環境（例: `bokudeli-event-yasu-2510` など）にデプロイし、実際の画面で動作確認を行う。

4. **バージョンを patch で上げる**（例: 2.6.0 → 2.6.1）
   - hotfix ブランチ上で、リポジトリルートの `npm version patch` を実行する（通常時の `npm version minor` と同様、ルートの `package.json` / `package-lock.json` が更新され、コミットと `v2.6.1` の Git タグが作られる）。

5. **hotfix ブランチを `main` に取り込み**、`main` とタグを push する。
   - ローカルの `main` をリモートと揃えてからマージする。
   - 例: `git switch main && git pull origin main && git merge hotfix/1910` のあと `git push origin main v2.6.1`

6. **production に反映**（⚠️ **この push で本番デプロイが自動実行される**）
   - 例: `git branch -f production main` のあと `git push origin production`

7. **`development` へ反映**（`development` は直 push 禁止のため **同期ブランチ + PR** で取り込む）
   - 例:
     ```
     git fetch origin
     git switch -c sync/main-to-development origin/development
     git merge main          # コンフリクトは解消する
     git push origin sync/main-to-development
     ```
   - その後、`sync/main-to-development → development` の PR を作成し、`PR verify` 通過後にマージする。
   - **`development` に対して `rebase` で履歴を書き換えない**（共有ブランチのコミットハッシュが変わり、他メンバーと衝突するため）。
   - 緊急で入れた修正とバージョンは `main` 経由のマージで `development` にも含まれる。`development` 上の未リリース WIP はそのまま残る。

**補足**

- cherry-pick したコミットは `main` 上では元ブランチとは **別のコミットハッシュ**になるが、`development` へは **同期ブランチで `main` をマージし PR 経由**で取り込めばよい。
- 以降の通常リリース（「通常時」）に戻る際は、`development` と `main` の差分を確認してから進める。
- `development` から切って作業中の feature ブランチには hotfix のバージョンコミットが含まれない。必要に応じて feature ブランチ側で `git merge development` または `git rebase development` して取り込む。



## ロールバック（本番を前バージョンに戻す）

**目的**: 本番デプロイ後に不具合が見つかった場合、`production` を **直前の正常だったリリースタグ** の状態に戻し、本番デプロイを再実行する。

**前提**

- ロールバックの基準は **Git タグ**（例: `v2.5.3`）である。release ブランチ上の bump コミットやマージコミットを手で選ばない。
- B 版リリースでは、タグは **release PR マージ後の `development` HEAD**（merge commit または squash 後の1コミット）に付いている。ロールバック先はそのタグが指すコミットになる。
- 通常リリース・hotfix のどちらでデプロイした後も、手順は同じ。
- **`development` はロールバックしない**（未リリースの WIP が含まれるため）。本番だけをタグで戻す。

**手順**

1. **戻す先のタグを確認する**
   - 例: 現在が `v2.6.0` で問題が出た → 戻す先は `v2.5.3`（直前のリリースタグ）
   - タグ一覧: `git fetch origin --tags && git tag -l 'v*' --sort=-v:refname | head`

2. **タグが指すコミットを確認する**（任意だが推奨）
   - 例: `git show v2.5.3 --no-patch`
   - `package.json` のバージョンが期待どおりか: `git show v2.5.3:package.json | grep '"version"'`

3. **`production` と `main` をタグのコミットに合わせる**
   - 例:
     ```bash
     git fetch origin --tags
     git branch -f production v2.5.3
     git branch -f main v2.5.3
     ```
   - `main` も同じコミットに揃えておく（タグの目印として整合を保つ）。

4. **`production` を push する**（⚠️ **この push で本番デプロイが自動実行される**）
   - 例: `git push origin production --force-with-lease`
   - `main` も揃えた場合: `git push origin main --force-with-lease`（任意だが推奨）

5. **本番が前バージョンに戻ったことを確認する**
   - GitHub Actions のデプロイ workflow が成功していること
   - 本番環境の `package.json` バージョン（またはアプリ上の表示）が `v2.5.3` 相当であること

**補足**

- ロールバックは `production`（必要なら `main`）への **force push** を使う。branch protection で `production` の force push を **限定許可**にしておくこと（[`03_branch_protection.md`](../AIエージェント/03_branch_protection.md) §3 参照）。
- 問題のあったタグ（例: `v2.6.0`）は **削除しない**（履歴・調査用に残す）。本番は `production` ブランチの先端だけ戻す。
- `development` はそのまま。修正は feature ブランチで行い、通常どおり PR → `development` → 次回リリース、または hotfix 手順で対応する。

**ロールバック後の進め方**

| 状況 | 対応 |
|:-----|:-----|
| 修正が小さい・急ぎ | hotfix 手順（「緊急デプロイ」）で `main` から patch リリース |
| 修正が `development` に既にある | `development` と `main` の差分を確認し、通常リリースまたは hotfix を選択 |
| データマイグレーションを伴う | ロールバックだけでは DB が新スキーマのままの可能性がある。バッチ・手動復旧の要否を別途判断する |
