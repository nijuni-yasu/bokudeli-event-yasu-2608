# メール_コミュニティ管理者_イベント_未注文放置

## 1. 概要
### 1.1 機能の目的
主催者がイベントを予約申請し、店舗が予約承認した後に、主催者がなかなか注文したり告知しない場合のリマインド機能を提供する。

### 1.2 主要な機能
- イベント予約承認後の注文促進リマインドメール送信
- **48 時間（2 日）おき**に自動リマインド送信（`accepting_order` ログの `updated_at` 起点）。承認から **最大 30 日**まで
- 注文完了までの継続的なリマインド機能
- コミュニティ管理者全員への一括送信

### 1.3 対象ユーザー
- コミュニティ管理者（主催者）
- イベント予約承認済みの主催者

## 2. ねらい
### 2.1 ビジネス目標
- イベント予約承認後の注文率向上
- 主催者のアクション促進

### 2.2 ユーザー価値
- 注文忘れの防止
- イベント進行の促進
- 参加者への適切な告知タイミングの確保

### 2.3 成功指標（KPI）
- リマインドメール送信後の注文率
- イベント予約から注文までの平均日数短縮
- 注文キャンセル率の低下

## 5. 技術仕様・データ構造設計
### 5.1 Firestoreスキーマ設計
#### 5.1.1 既存コレクション構造の活用
既存のコレクション構造を活用し、新規コレクションは追加しない。

```
/communities/{communityId}
  /events/{eventId} （既存）
    - event_status: { value: "accepting_order", shop_comment?: string }
    - event_name: string
    - event_start_datetime: Timestamp
    - event_deadline_datetime: Timestamp
    - event_place: string（Optional）
    - shop_name: string
    - community_account: string
    - organizer_*: ...
    - created_at: Timestamp
    - updated_at: Timestamp
  /events/{eventId}/logs/{logId} （既存）
    - event_status: { value: "accepting_order" }
    - updated_at: Timestamp
  /members/{userId} （既存）
    - roles: [manager]
    ※メール・氏名は User から取得する（id が userId）
```

#### 5.1.2 リマインド送信タイミングの判定
- **events/logs** を利用し、`accepting_order` に変更した日時を取得する
- `ShokujiiEvent.getLastUpdatedTimeByStatus('accepting_order')` で取得
- 予約申請のお店へのリマインド（`sendApplyingOrderRemindMailToShop`）と同等の仕組み
- **48 時間おき**の送信：起点から 2 日後、4 日後、6 日後… **最大 30 日後**まで、各 **1 分間ウィンドウ**で判定（`UNORDERED_REMIND_INTERVAL_DAYS` / `MAX_UNORDERED_REMIND_SPAN_DAYS`）

#### 5.1.3 クエリ条件
- **DB 操作は必ず store 経由**で行う
- 対象：`event_status.value === 'accepting_order'`、`event_deadline_datetime > now`、`is_deleted === false`
- **is_public**: 全イベント（公開・非公開を問わない）
- 注文の未完了：`status === 'ordered'` の注文が 0 件

```typescript
// store 経由の例
const events = await getAcceptingOrderEventsBeforeDeadline(nowDateTimeMillis)
for (const event of events) {
  const orders = await event.getOrders('ordered')
  if (orders.length > 0) continue

  const updatedAt = await event.getLastUpdatedTimeByStatus('accepting_order')
  if (updatedAt == null) continue

  // 2 日ごとのウィンドウに該当するかチェック（例：2 日後の場合）
  if (updatedAt > start && updatedAt <= end) {
    // リマインド送信
  }
}
```

### 5.2 Firestoreインデックス設計
#### 5.2.1 複合インデックス

### 5.3 Functions設計
#### 5.3.1 pollingTask への組み込み
専用の onSchedule は作成せず、既存の **pollingTask**（1分ごと実行）に組み込む。Scheduled Function では `DateTime.fromISO(context.scheduleTime)` を使用する。

**引数の意味**

- **nowMillis**: 注文期限フィルタ用の「現在時刻」。pollingTask の **`end`**（スケジュール実行時刻）を渡す。
- **windowStart / windowEnd**: `getLastUpdatedTimeByStatus('accepting_order')`（logs の該当エントリの `updated_at`）が区間 `(windowStart, windowEnd]` に入るかの判定用。**2 日ごと**に **`start - dayOffset*ONE_DAY_MILLIS`, `end - dayOffset*ONE_DAY_MILLIS`** を渡す（`dayOffset = 2, 4, …, 30`）。

```typescript
// functions/default/src/pollingTask.ts（実装済み）
import {
  sendUnorderedRemindMailToManagers,
  UNORDERED_REMIND_INTERVAL_DAYS,
  MAX_UNORDERED_REMIND_SPAN_DAYS,
} from './remindUnorderedMail.js'

for (
  let dayOffset = UNORDERED_REMIND_INTERVAL_DAYS;
  dayOffset <= MAX_UNORDERED_REMIND_SPAN_DAYS;
  dayOffset += UNORDERED_REMIND_INTERVAL_DAYS
) {
  promiseFunctions.push(
    sendUnorderedRemindMailToManagers(
      end,
      start - dayOffset * ONE_DAY_MILLIS,
      end - dayOffset * ONE_DAY_MILLIS,
    ),
  )
}
```

実装本体は [functions/default/src/remindUnorderedMail.ts](../../functions/default/src/remindUnorderedMail.ts) を参照。

#### 5.3.2 SendGrid テンプレート
- SendGrid で動的テンプレートを作成し、4.2 の件名・本文に相当するハンドルバー変数を設定する。
- `dynamicTemplateData` のキー: `community_manager_fullname`, `event_name`, `event_start_datetime`, `event_place`, `shop_name`, `event_url`
- 作成したテンプレート ID（`d-` で始まる 32 桁）を **`REMIND_UNORDERED_TEMPLATE_ID`**（`remindUnorderedMail.ts`）に反映する。未設定のプレースホルダ ID のままでは送信に失敗する。

- **管理者のメール・氏名**: `getUser(managerId, true)` で User から取得。`user_email` がなければ `continue` でスキップ
- **event_url**: `getEventUrl(event.community_account, event.id)` を使用
- **event_place**: Optional のため未設定時は `event.event_address` にフォールバック、それもなければ空文字
- **開催日時**: `convertToDuration(event.event_start_datetime, event.event_end_datetime)` を使用

### 5.4 処理フロー
#### 5.4.1 リマインドメール送信フロー
1. pollingTask が 1 分ごとに自動実行
2. `getAcceptingOrderEventsBeforeDeadline` で注文受付中（`accepting_order`）かつ注文期限が未来のイベントを取得（全イベント、is_public を問わない）
3. 各イベントについて以下を確認：
   - `status === 'ordered'` の注文が 0 件であること
   - `getLastUpdatedTimeByStatus('accepting_order')` で取得した日時が、送信ウィンドウ（`windowStart`, `windowEnd`] に該当すること
4. 条件に合致するイベントのコミュニティ管理者を取得（store 経由）
5. 各管理者に `getUser(managerId, true)` で User を取得し、`user_email` がなければスキップ
6. Promise.allSettled で一括送信し、失敗件数を `createModuleLogger` 経由の `warn` で記録

#### 5.4.2 リマインド回数・停止条件
- **リマインドの継続**: 承認（`accepting_order` ログの `updated_at`）から **最大 30 日**まで、**48 時間おき**（2, 4, …, 30 日後のウィンドウ）
- **送信停止条件**: 注文期限（`event_deadline_datetime`）を過ぎたら送信しない（`getAcceptingOrderEventsBeforeDeadline` で除外）

## 7. 注意事項
### 7.1 既存システムへの影響
#### 7.1.1 データベース構造への影響
- **新規コレクション**: なし（既存コレクションを活用）
- **既存コレクションの変更**: なし
- **インデックス**: 既存の `event_status.value` + `event_deadline_datetime` インデックスを利用（firestore.indexes.json に存在する場合は追加不要）

#### 7.1.2 アプリケーションへの影響
- **フロントエンド**: 影響なし（自動実行機能）
- **バックエンド**: pollingTask への関数追加、event store に `getAcceptingOrderEventsBeforeDeadline` 追加
- **既存機能**: 影響なし

#### 7.1.3 運用への影響
- **パフォーマンス**: 毎日の定期実行による軽微な負荷増加
- **ストレージ**: 影響なし
- **セキュリティ**: 既存のセキュリティルールを活用

### 7.2 セキュリティ考慮事項
