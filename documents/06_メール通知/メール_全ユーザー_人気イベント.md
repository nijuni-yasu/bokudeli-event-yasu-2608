# メール_全ユーザー_人気のイベント

## 1. 概要

### 1.1 機能の目的

注文受付中の公開イベントで、参加人数（`event_num_members`）が運用設定の閾値**以上**になり、かつ定員内であるタイミングをきっかけに、**全ユーザー**へ人気イベントとして紹介メールを**1 イベントにつき 1 回だけ**送る。人数の反映は **`eventMembers`（`member_orders` の `onDocumentWritten`）** で `event_num_members` が更新された直後を基準とする。

### 1.2 主要な機能

- `configs/global` の `popular_event_mail_threshold` による閾値判定（未設定・読取失敗時は送信しない。**正の整数以外はスキップしエラーログ**）
- `event_num_members`・`event_max_people`・`is_public`・`accepting_order`・`sent_popular_event_mail_at` による送信可否判定（**閾値ちょうどで送信**。**定員超過時は送信しない**）
- **`functions/default/src/eventMembers.ts` の `createEventMembers`**（**第 1 トランザクション**でメンバー／`event_num_members` 更新成功後）から人気メール処理を呼び出す想定。**`sent_popular_event_mail_at` の有無・送信可否の判定とフラグ更新は第 2 トランザクションで原子的に**行う（下記 §5.5）。`event_num_members` の更新タイミングと揃えられ、べき等性・二重送信防止
- `getAllUsers` ベースの宛先組み立て（イベント情報メールと同様）、SendGrid 動的テンプレート＋**人気メール専用 ASM グループ**＋**BCC にサポート宛**（**一括送信の全バッチで共通の BCC**。`SUPPORT_MAIL` 等、既存パターンに合わせる）
- イベント差分の **`logs` サブコレクションは既存の eventLog 機能に任せる**（専用のログ書き込み仕様は定義しない）

### 1.3 対象ユーザー

- **メール受信者**: 登録ユーザー全員（メールアドレス取得できるユーザーに限定）
- **間接的な価値**: 参加者（盛り上がるイベントに参加したい）、主催者（閾値達成で全体配信されるインセンティブ）

### 1.4 類似機能との違い

- **新着イベントメール**（`メール_コミュニティメンバー_新着イベント.md`）: コミュニティメンバー向け・初回注文トリガー。人気メールは**全ユーザー向け**・**人数閾値**・**生涯 1 通**。
- **週次イベント情報メール**（`eventInformationMail.ts`）: スケジュール実行・複数イベントまとめ。人気メールは **`member_orders` 更新 → `eventMembers` 集計**に連動・**単一イベント紹介**。

## 2. ねらい

### 2.1 ビジネス目標

- 参加者の参加意欲向上（人気が可視化されたイベントへの誘導）
- 主催者の集客意欲向上（一定人数で全ユーザー配信される目標設定）

### 2.2 ユーザー価値

- 参加者: 注目度の高いイベントを見逃しにくくする
- 主催者: 集客の明確なマイルストーンを持てる

### 2.3 成功指標（KPI）

- 人気メール経由のイベントページ遷移・注文転換（実装後に計測方法を定義してよい）
- 誤送信・二重送信件数ゼロ（運用品質）

## 3. 前提条件

### 3.1 技術的前提条件

- Firebase Functions（`functions/default`）、Firestore、SendGrid 連携が利用可能であること
- `eventMembers.ts` の `createEventMembers` から人気メール用の内部処理を呼び出せること
- `event_num_members` が注文状態と整合するよう、`member_orders` 集計（`eventMembers`）が動作していること
- **`event_max_people` はイベント作成・更新フロー上、未定義・0 となることはない**（本仕様では欠損・0 の分岐は設けない）

### 3.2 ビジネス的前提条件

- `configs/global` に `popular_event_mail_threshold` が運用で設定されること（**デフォルト値は設けない**。未設定時は送信しない）。設定する場合は**正の整数**とする（それ以外は送信されずエラーログとなる）

### 3.3 依存関係

- 新着イベントメール（`sendNewEventNotificationToMembers`）と同様の「トランザクションで先に送信済みフラグを立てる」パターン
- イベント情報メールと同様の `getAllUsers` による宛先列挙
- 関連仕様: `メール_コミュニティメンバー_新着イベント.md`、`メール_一括送信_personalizations.md`（バッチ・ログ）

## 5. 技術仕様・データ構造設計

### 5.1 Firestoreスキーマ設計

#### 5.1.1 コレクション構造変更

**新規コレクションは追加しない。** 既存パスにフィールドを追加する。

```
/configs/global                    （既存ドキュメントにフィールド追加）
/communities/{communityId}/events/{eventId}  （既存ドキュメントにフィールド追加）
  /logs/{logId}                  （既存。eventLog 機能の仕様に従う）
```

#### 5.1.2 ドキュメントスキーマ（追加・変更フィールド）

**`configs/global` に追加**

| フィールド名 | 型 | 必須 | 説明 |
|-------------|-----|------|------|
| `popular_event_mail_threshold` | number（**正の整数**を運用で設定） | 運用上必須 | 人気メール送信の下限人数。**コード上のデフォルトは持たない**。フィールド欠如・読取失敗時は**送信しない**。**正の整数以外**（0・負数・非整数など）が設定されている場合は**常に送信せず、エラーログを出す**。 |

**`communities/{communityId}/events/{eventId}` に追加**

| フィールド名 | 型 | 必須 | 説明 |
|-------------|-----|------|------|
| `sent_popular_event_mail_at` | number（epoch ms）または Timestamp（**`sent_new_event_mail_at` と同一方針で統一**） | optional | 人気メール送信済み時刻。**設定済みなら再送しない**（1 イベント 1 通）。 |

#### 5.1.3 Zodスキーマ定義（想定）

- `common/src/schemas/Config.ts` の `ConfigGlobal` に `popular_event_mail_threshold` を追加（**optional**。未設定は「送信しない」判定に使用）。**実行時は正の整数でない値を検知したら送信せずエラーログ**（Zod で縛るか、Functions 側で二次チェックするかは実装で決める）
- `common/src/schemas/Event.ts` の Event スキーマに `sent_popular_event_mail_at` を追加（`sent_new_event_mail_at` と同型・同オプショナル扱い）

（クラス・`toFirestore` の詳細は既存 `Config` / `Event` のパターンに合わせる。）

### 5.2 Firestoreフロントエンド処理

- 本機能の送信判定・送信実行は **Functions 側**で行う想定。
- フロントは既存の Event ストア経由で `sent_popular_event_mail_at` を表示する必要があれば read のみ（表示要件は別途）。

### 5.3 Firestoreインデックス設計

- 本機能の送信トリガーは **`eventMembers` 内のトランザクション＋イベント単体取得**が中心のため、**新規複合インデックスは原則不要**（既存クエリに依存）。

### 5.4 Firestoreセキュリティルール

- `configs/global`・イベントドキュメントは既存ルールに従う。クライアントから `popular_event_mail_threshold` や `sent_popular_event_mail_at` を**直接書き換えない**運用とする（Functions / 既存更新経路のみ）。

### 5.5 Functions設計

#### 5.5.1 種別

- **呼び出し元**: `onDocumentWritten`（`communities/.../member_orders/{orderId}`）を処理する **`createEventMembers`**（`functions/default/src/eventMembers.ts`）。
- **トランザクションの段階**
  - **第 1 トランザクション**（既存）: `members` / `event_num_members` のみ更新。`updateMembersFieldOnly` の方針どおり `updated_by` 等は触らない。
  - **第 2 トランザクション**（人気メール用）: イベントを読み直し、送信可否を判定し、送信する場合のみ **`sent_popular_event_mail_at` を原子的に設定**する。第 1 と同一トランザクションにまとめない（既存のメンバー更新ロジックとの責務分離）。
- **Callable / 別 Trigger の新設は必須ではない**（入口を `eventMembers` に集約する）。

#### 5.5.2 責務（論理モジュール）

1. `getConfigGlobal` で `popular_event_mail_threshold` を取得。無い・読取失敗なら**即 return**（送信しない）。
2. 取得した値が**正の整数でない**場合（0・負数・`Number.isInteger` が false 等）は**送信せず、エラーログを出して return**。
3. **第 2 トランザクション**内でイベントを取得し、以下を**すべて**満たす場合のみ `sent_popular_event_mail_at` を設定してコミット  
   - `is_public === true`  
   - `event_status.value === 'accepting_order'`  
   - **`event_num_members >= popular_event_mail_threshold`（閾値ちょうどを含む「以上」）**  
   - **`event_num_members <= event_max_people`（定員超過 `event_num_members > event_max_people` のときは送信しない。ちょうど定員は送信可）**  
   - **`event_max_people` は前提どおり正の整数が入っている**（未定義・0 は想定外。本仕様では専用分岐を書かない）  
   - `sent_popular_event_mail_at` が未設定  
4. 第 2 トランザクション成功後にのみ SendGrid で送信。  
5. `member_orders` の更新が短時間に複数回あっても**同一イベントで人気メールは 1 回**（第 2 TX のフラグで担保）。

#### 5.5.3 SendGrid

- 動的テンプレート ID は実装時に定数化。
- **ASM**: イベント情報メールとは**別グループ ID** を新設し、本メールにのみ紐づける。
- **BCC**: **サポート宛**を付与する（`utils/mail` の `SUPPORT_MAIL` 等）。**一括送信（複数バッチに分割する場合も含む）では、全バッチで同一の BCC を共通指定する**（宛先ごとに異なる BCC は設けない）。

#### 5.5.4 宛先リスト

- `eventInformationMail.ts` と同様に `getAllUsers(true)` で全ユーザー走査し、`user_email` 等が取れるユーザーのみ宛先化。
- メール未登録・無効扱いのアドレスは**除外**。
- 最適化（クエリ分割・バッチ取得等）は**挙動同等**を条件に許容。

### 5.6 処理フロー

#### 5.6.1 人気イベントメール送信の処理フロー

1. `member_orders` の書き込みにより **`createEventMembers` が走り、第 1 トランザクションでメンバー／`event_num_members` 更新が成功**する（この時点で人数は最新）
2. トリガー経路で分かっている `communityId`・`eventId`・当該注文の `userId` 等を引き回す
3. `configs/global` から `popular_event_mail_threshold` を読む  
   - 無し / 読取失敗 → **終了（送信しない）**  
   - 値が**正の整数でない** → **終了（送信しない）＋エラーログ**
4. **第 2 トランザクション**を開始  
   - イベント取得  
   - `is_public`・`accepting_order`・**`event_num_members >= threshold` かつ定員内**・`sent_popular_event_mail_at` 未設定を検証  
   - 条件を満たす場合のみ **`sent_popular_event_mail_at` を先に設定**（新着メール `sendNewEventNotificationToMembers` と同パターン）
5. 第 2 トランザクション成功時、全ユーザー宛にテンプレート送信（ASM は人気専用グループ、**BCC はサポートを全バッチ共通で付与**）
6. 送信結果を構造化ログに出力（`feature: popularEvent` 等、既存バッチ送信ログ方針に合わせる）
7. **`events/.../logs` は既存の eventLog 機能に任せる**（差分が出れば従来どおり記録される。個別のログ仕様は本書では定義しない）

#### 5.6.2 エラーハンドリング

- トランザクション競合: 第 2 トランザクションの再試行方針は既存 `saveEvent` 等に合わせる（第 1 トランザクション完了後の失敗はメール未送信のまま再トリガーで再評価されうる）
- SendGrid 失敗: **フラグは既に立っているため再送しない**（新着と同じ運用トレードオフ）。警告ログを残す

### 5.7 日時・タイムゾーン

- 表示・日付処理は **日本 `Asia/Tokyo`** 基準。**サマータイムは考慮しない**。
- 実装では **luxon** を使用（プロジェクト内の他機能と揃える）。

### 5.8 命名

- 機能・ログ・定数は **popular** で統一し、**feature**（注目）という名称は使わない。

## 6. データマイグレーション（必要な場合）

## 8. 注意事項

### 8.1 既存システムへの影響

#### 8.1.1 データベース構造への影響

- `configs/global`・各イベントドキュメントにフィールド追加
- 新規インデックスは原則不要

#### 8.1.2 アプリケーションへの影響

- **バックエンド**: `eventMembers.ts` 周辺の処理追加、SendGrid 送信ボリューム増（新着メール `orderCompletionMail.ts` は従来どおり。同一注文で新着と人気が両方送られうる）
- **フロントエンド**: 表示要件があれば Event ストアの型・表示のみ

#### 8.1.3 運用への影響

- **パフォーマンス**: 全ユーザーへの一括送信のため、送信時間・Functions タイムアウト・メモリ（`eventInformationMail` 準拠）に注意
- **コスト**: SendGrid API リクエスト数・Firestore 読み取り（全ユーザー列挙）

### 8.2 セキュリティ考慮事項

- 閾値・送信済みフラグの改ざん防止（クライアント直接更新を許さない）
- ログにメールアドレスを大量に出さない（既存 `sendgrid` / personalizations 方針に従う）

### 8.3 運用考慮事項

- **ログ**: 送信スキップ理由（未設定閾値・**閾値が正の整数でない**・読取失敗・非公開・ステータス・既送信・**閾値未満**・**定員超過**）を区別してログ可能にすると運用しやすい
- **監視**: バッチ失敗率・受付件数（`totalRecipientsAccepted` 等）

### 8.4 新着イベントメールとの関係

- 同一注文タイミングで**新着と人気の両方が送られてもよい**。抑止・優先順位は設けない。
